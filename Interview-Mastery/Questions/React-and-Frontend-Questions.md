## Answers

1. What is React?
   - **Answer:** React is a JavaScript library for building user interfaces, maintained by Meta and a large open-source community. It is component-based: the UI is decomposed into small, reusable pieces called components, each of which encapsulates its own markup, styling, and behavior. React uses a declarative programming model — instead of imperatively manipulating the DOM with commands like `element.appendChild` or `element.style.color = ...`, developers describe what the UI should look like for a given state, and React figures out how to update the DOM to match. The heart of this mechanism is the virtual DOM, an in-memory tree of plain JavaScript objects that mirrors the real DOM. When state changes, React re-renders the virtual tree, computes the difference (a process called reconciliation) against the previous virtual tree, and then applies only the minimal set of real DOM mutations. This batching of updates keeps re-renders efficient even in data-heavy interfaces. React also follows a unidirectional data flow: data moves down from parent to child through props, and events bubble up through callbacks, which makes data flow predictable and debugging straightforward. Because React is a library rather than a framework, it can be embedded gradually into existing pages and combined with other libraries for routing, state management, and styling.

2. What are components?
   - **Answer:** A component is a self-contained, reusable unit of UI that can accept inputs and return what should be rendered. In modern React, components are JavaScript functions (or classes in older code) that return JSX. A component can be as small as a single button or as large as an entire page layout, which encourages the "compose small pieces to build big things" design philosophy. Components receive data from their parent through `props` and manage data that changes over time through `state`. A well-designed component is usually a pure function of its props: given the same props and state, it always renders the same output. This purity makes components easier to reason about, test, and reuse. Components are organized into a hierarchy — a `Dashboard` may render a `Header`, a `Sidebar`, and a `WidgetGrid`, and each of those in turn renders smaller leaf components. Data flows down this tree through props, while events such as clicks or form submissions flow back up through callback functions. Reusability is a core benefit: a `SensorCard` component can be rendered hundreds of times with different sensor data, and any change to its internals propagates everywhere it is used.

3. What is JSX?
   - **Answer:** JSX is a syntax extension for JavaScript that looks similar to HTML but is transpiled into `React.createElement` calls at build time. It lets developers write UI markup directly inside JavaScript code, which keeps the markup and logic for a component in one place. JSX expressions can embed JavaScript values inside curly braces — for example, `{sensor.name}` renders a variable, and `{isOnline ? <StatusDot/> : <OfflineBadge/>}` renders a whole element conditionally. Because JSX compiles to JavaScript function calls, it supports full JavaScript expression syntax between the braces, though statements like `if` or `for` loops are not allowed inline and must be moved outside. Every JSX element must have one root element or use a fragment (`<></>`) when returning multiple siblings. JSX attributes use camelCase rather than HTML conventions — `className` instead of `class`, `htmlFor` instead of `for`, `onClick` instead of `onclick`. Unlike HTML, component names in JSX must start with an uppercase letter so that React distinguishes user-defined components from built-in DOM elements. Babel or TypeScript compilers perform the JSX-to-JavaScript transformation during the build step, so the code in the browser is plain JavaScript. Writing `React.createElement("div", null, "Hello")` by hand would be verbose and error-prone, which is why JSX is the standard authoring format.

4. What is state?
   - **Answer:** State is data that a component owns and can change over time, and whenever state changes, the component re-renders to reflect the new data. It is the component's "memory" — it stores values that are specific to an instance, such as a form input's current text, the visibility of a modal, or the data received from an API. State is declared with hooks like `useState` in function components or the `this.state` object in class components. Unlike props, state is mutable: it is updated through the setter function returned by the hook, and React schedules a re-render in response. State should be kept as local as possible to the component that needs it; when multiple components need to share the same piece of data, state is "lifted" to their closest common ancestor and passed down as props. A component can hold several independent pieces of state, and each update only triggers that component's re-render. The setter functions also accept an updater function form, `setCount(prev => prev + 1)`, which is the safe way to update state that depends on its previous value. State updates are asynchronous and batched: React may coalesce multiple updates within an event handler into a single re-render. Good practice is to derive computed values from existing state rather than storing redundant copies, which keeps state minimal and avoids synchronization bugs.

5. What are props?
   - **Answer:** Props (short for properties) are read-only inputs passed from a parent component to a child component, analogous to function arguments. The parent passes them when rendering the child: `<SensorCard name={sensor.name} temperature={sensor.temp} />`, and the child receives them as a single object in its function signature. Props enable component reuse and composition — a generic component becomes specialized by the data it receives. Props are immutable from the child's perspective: a child must never attempt to reassign its props; instead, it communicates upward by calling callback functions that the parent supplied as props, such as `onSelect` or `onChange`. This pattern maintains React's unidirectional data flow: data moves down through props and changes move up through callbacks, keeping the mental model simple and predictable. Props can be any JavaScript value, including primitives, objects, arrays, functions, and even other React elements. Since a parent re-renders children on every state change, passing new inline objects or functions creates new references each time, which is why `useCallback` and `useMemo` matter for performance. Prop drilling — passing props through many intermediate components that do not use them — is a symptom that often leads developers to adopt Context or a state management library.

6. Difference between state and props.
   - **Answer:** State and props are the two ways React components handle data, and they differ fundamentally in ownership and mutability. Props are data passed from a parent to a child; they are read-only and cannot be modified by the receiving component. State is data owned and managed by a component itself, and it can be updated through the hook's setter function, which triggers a re-render. In terms of the data flow, props flow downward from parent to child, while state can only change within the component that owns it — a child that needs to alter parent state does so by invoking a callback prop, not by writing to state directly. Both props and state changes cause a component to re-render, and React reconciles the virtual DOM to apply the minimum set of DOM updates. A common rule is that a component should render from "props + state" and derive everything else. When a piece of data is needed by several sibling components, the solution is to lift state into the nearest common ancestor and pass it down as props. State is local by default, whereas props make data shareable across the component tree. Finally, props often hold configuration and data that define what a component shows, while state holds transient, interactive data that changes based on user actions or network responses.

7. What are hooks?
   - **Answer:** Hooks are functions introduced in React 16.8 that let function components use state and lifecycle features without writing classes. They solve several problems of the class model: logic could not be reused across classes without complex render-prop or HOC patterns, and related logic was scattered across lifecycle methods like `componentDidMount` and `componentDidUpdate`. Common built-in hooks include `useState` for local state, `useEffect` for side effects, `useContext` for consuming context, `useReducer` for complex state logic, `useMemo` and `useCallback` for performance, and `useRef` for mutable references that do not trigger re-renders. Hooks follow the Rules of Hooks: they must be called at the top level of a function component (never inside loops, conditions, or nested functions), and they can only be called from React functions. These rules work because React tracks hooks by their call order, so conditional calls would corrupt the association between a component instance and its state. Custom hooks are the mechanism for sharing stateful logic: any function whose name starts with `use` and that calls other hooks can be extracted and reused across components. Custom hooks have enabled a "composition" model that replaces many class lifecycle patterns and libraries like render props. Hooks have also paved the way for concurrent rendering features, since function components with hooks are simpler for React to manage than class instances.

8. What is `useState`?
   - **Answer:** `useState` is a hook that adds local state to a function component. It returns an array with two elements: the current state value and a setter function to update it, typically destructured as `const [count, setCount] = useState(0)`. The argument passed to `useState` is the initial state, which can be a plain value or a lazy initializer function that runs only on the first render. The setter triggers a re-render when the new value differs from the current one, and it accepts either a new value or an updater function that receives the previous state: `setCount(prev => prev + 1)`. The updater form is important when multiple updates depend on the prior value, because state updates are asynchronous and batched. State is stored per component instance, so two instances of the same component keep fully independent state. When a component holds complex or related values, a single object can be used, but each update must set a new object reference since state is treated as immutable. `useState` is the foundation of interactive UI — nearly every form, toggle, and data display is built on it. For state logic that is complex or shared across actions, `useReducer` is often a better fit than multiple `useState` calls. The hook keeps the component model simple by making state explicit in the component body rather than hidden inside a class instance.

9. What is `useEffect`?
   - **Answer:** `useEffect` is the hook for performing side effects after React has committed the render to the DOM — things like fetching data, subscribing to a WebSocket, setting up timers, or manually touching the DOM. It takes a function and an optional dependency array; the function runs after every render where any dependency has changed. The most common patterns are an empty dependency array (`[]`) to run once on mount, omitted dependencies to run after every render, and a populated array to run only when specific values change. The effect can return a cleanup function that runs before the next effect execution and on unmount, which is essential for clearing timers and unsubscribing from external sources to prevent memory leaks. Fetching data inside an effect typically looks like: set loading state, perform the request, then update state with the result. The dependency array is critical: missing dependencies causes stale closures (the effect captures outdated values), while including unstable values causes the effect to run too often or infinitely loop. Modern guidance is to think of effects as a way to synchronize a component with an external system rather than as lifecycle callbacks. In React 18 and later, effects can be set up to avoid flicker by skipping double-invocation of setup/cleanup during development and by using `useSyncExternalStore` for external stores. A common mistake is setting state in an effect that could just be computed during rendering, which causes avoidable extra renders.

10. What is `useMemo`?
    - **Answer:** `useMemo` is a performance hook that caches the result of a computation and recalculates it only when the values in its dependency array change. It is used for expensive calculations that should not run on every render — for example, sorting a large list, aggregating statistics, or deriving a filtered subset of data. The signature is `const total = useMemo(() => computeTotal(items), [items])`, where the first argument is a pure function returning the value and the second is the dependency array. If the dependencies are unchanged between renders, React returns the previously computed value; otherwise, it re-runs the function and stores the new result. A key point is that `useMemo` is about avoiding wasted work, not about memory retention — the value itself is still recalculated whenever dependencies change, and the cached value is dropped when the component unmounts. It is a good practice to run expensive computations in the browser only when necessary, but it is also wise not to overuse `useMemo`, since every hook call has its own overhead. `useMemo` also preserves reference equality for objects and arrays, which helps memoized child components (wrapped in `React.memo`) avoid unnecessary re-renders when they receive derived data as props. The dependency array must list every value from the enclosing scope that the computation reads; an incomplete array produces stale results. It is the memoization counterpart to `useCallback`, which does the same thing but for function references rather than values.

11. What is `useCallback`?
    - **Answer:** `useCallback` returns a memoized version of a function so that the function reference stays stable across renders, changing only when the dependencies in its array change. This matters because functions are recreated on every render by default, and if a child component wrapped in `React.memo` receives a new function prop each render, the memoization is defeated and the child re-renders unnecessarily. The signature is `const handleSelect = useCallback((id) => doSelect(id), [doSelect])`. Internally it is equivalent to `useMemo(() => fn, deps)`, since memoizing the function is just memoizing the value of creating that function. It is most useful when combined with memoized child components, when the function is a dependency of another hook such as `useEffect` or `useMemo`, and when the function is passed through context or a provider that many consumers depend on. Using `useCallback` requires careful dependency management: if the callback closes over a changing value and that value is omitted from the dependencies, the callback captures a stale value, producing a stale closure bug. Because of this complexity, it is recommended to use `useCallback` only when there is a measurable benefit, such as a deep or memoized component tree, and not to wrap every function defensively. In code that computes derived data during rendering, `useCallback` can also help keep expensive event handlers stable. Together with `useMemo`, it is one of the two primary tools for fine-grained performance control in function components.

12. What is controlled component?
    - **Answer:** A controlled component is a form element whose value is driven by React state, making React state the single source of truth. The canonical example is an input that reads its value from state and writes to state on change: `<input value={text} onChange={(e) => setText(e.target.value)} />`. Because the value is bound to state, the input cannot diverge from what the application knows; whatever is typed is immediately reflected in `text`, and the UI always re-renders from that state. This pattern enables instant validation, live preview, transformation of input (such as uppercasing), and the ability to programmatically set or clear the field by updating state. Multiple fields can be handled generically by using `name` attributes and a single state object with a computed property key. Controlled components also make testing easier because the displayed value is predictable and can be asserted directly. The trade-off is that every keystroke triggers a state update and re-render, which is negligible for typical forms but worth considering for very high-frequency inputs. Because form state lives in React, submit handlers read directly from state rather than from the DOM. Controlled components are the recommended default in React because they give developers full control over input behavior.

13. What is uncontrolled component?
    - **Answer:** An uncontrolled component lets the DOM maintain its own input value, and React only reads the value when needed, typically through a ref. Instead of binding `value` and `onChange`, the component renders `<input ref={inputRef} />` and reads `inputRef.current.value` on submit. This resembles traditional HTML form behavior, where the browser manages form state natively. Uncontrolled components can be simpler for forms that only need their values read once, such as a search box submitted on Enter or a form that posts directly to a server. They also avoid re-rendering on every keystroke, since typing does not update React state. The downsides are significant: there is no instant validation or live feedback, no way to programmatically reset or alter the field without imperatively touching the DOM, and testing is harder because values are not visible in React state. Features like character counters, masked inputs, and controlled formatting are difficult to build with uncontrolled inputs. An intermediate approach is to use a default value via the `defaultValue` prop, which lets React set the initial value while the DOM manages it afterward. In general, controlled components are preferred for most forms because they keep data flow unidirectional and predictable; uncontrolled components are best reserved for simple, one-shot submissions.

14. What is conditional rendering?
    - **Answer:** Conditional rendering means rendering different UI output depending on a condition, using normal JavaScript control flow inside JSX. The most common techniques are the logical AND operator (`{isLoading && <Spinner/>}`) for show/hide, the ternary operator (`{isAdmin ? <AdminPanel/> : <ReadOnlyView/>}`) for two alternatives, and early returns at the top of the component for mutually exclusive whole-render branches. Because JSX is just an expression, any JavaScript expression that evaluates to an element, an array, or `null` can be used. A subtle pitfall is that `&&` renders the left operand when it is falsy but not a boolean — `{count && <p>...</p>}` renders `0` when `count` is zero — so the guard should be a boolean condition. Conditional rendering should be used sparingly relative to the component model; breaking each branch into its own component keeps the JSX readable and each branch testable. Other patterns include an `if/else` block before the `return`, or a lookup object mapping a state key to the appropriate component. The condition itself can be derived from state, props, or context, so conditional rendering is the mechanism behind loading spinners, empty states, error messages, authenticated versus guest views, and role-based UI. Modern React also supports conditional rendering with `switch`-like element variables. The key idea is that React treats conditionals as plain JavaScript — no special template syntax is required.

15. What is list rendering?
    - **Answer:** List rendering transforms an array of data into an array of elements using the `Array.map()` method inside the JSX. The standard pattern is `{items.map(item => <Row key={item.id} data={item} />)}`, which produces one child element per array entry. Because `map` returns an array of elements, JSX renders them as siblings automatically. Lists are central to UI: tables, dropdowns, grids, notifications, and feeds are all list rendering in practice. Good list rendering usually extracts the row into its own component, keeping the map body concise and making each row independently reusable and testable. Real-world lists need companion handling: an empty state when the array is empty (`{items.length === 0 ? <Empty/> : items.map(...)}`), a loading state before data arrives, and an error state when fetching fails. Large lists should not render thousands of DOM nodes at once; techniques like pagination or windowing (react-window, react-virtualized) render only the visible rows. Every item in a list must receive a stable, unique `key` so React can track identity across updates. Nested lists and multi-column layouts are achieved by composing lists with the same `map` pattern. Filtering, sorting, and grouping are typically performed with `Array.filter`, `Array.sort`, and grouping utilities before mapping, often wrapped in `useMemo` for performance.

16. Why is key needed in list rendering?
    - **Answer:** Keys give React a stable identity for each item in a list so that during reconciliation it can match items between the old and new virtual trees. Without keys, React falls back to position-based matching: if the first item changes, React assumes the whole list changed and re-renders everything, which is both wasteful and can cause bugs such as losing the focus or internal state of an input that shifted position. With keys, React can recognize that an item moved, was inserted, or was deleted, and it updates only the affected DOM nodes. Keys must be stable, unique, and predictable across renders; the ideal key is the item's persistent identifier, such as an `id` from the backend or a database row. Using the array index as a key is generally discouraged because indices shift when items are added, removed, or reordered, which causes React to reuse DOM nodes for the wrong data and break component state and animations. Index keys are acceptable only for static lists that are never reordered or filtered. Keys only need to be unique among siblings, not globally. In React, keys also give React the information it needs to preserve component state — like an input's text — when items are reordered. The value of a key can be a string or a number, and composing multiple fields into a stable string is fine when no single id exists.

17. What is React Router?
    - **Answer:** React Router is the de facto standard library for client-side routing in React single-page applications. It maps URLs to components so that navigation between "pages" does not require a full browser reload. The core API centers on a `<BrowserRouter>` provider and `<Routes>`/`<Route>` declarations: `<Route path="/dashboard" element={<Dashboard/>} />`. Navigation is done with the `<Link>` component or programmatically with the `useNavigate` hook, and dynamic segments are captured with syntax like `path="/sensors/:id"` and read via the `useParams` hook. It supports nested routes, layout routes, redirects with `<Navigate>`, catch-all routes for 404 pages, and search-param handling via `useSearchParams`. Route guards can be implemented by wrapping protected pages in a component that checks authentication and redirects to a login route when unauthenticated. In modern React Router, route configuration can be declared as a data object and used with loaders and actions for data fetching during navigation. A key benefit is deep-linkability: users can bookmark or share a URL that points directly at a specific view, and the browser back/forward buttons work as expected because the router syncs the UI with the history stack. React Router also supports `HashRouter` for static hosts that cannot configure server-side rewrites. It integrates with React's suspension and lazy loading so route-level code splitting loads page code only when the route is visited.

18. What is RBAC in frontend?
    - **Answer:** RBAC (Role-Based Access Control) in the frontend restricts what UI a user can see or interact with based on their assigned role. The typical flow is that after login, the server returns the user's role inside a JWT, which the frontend decodes and stores in state or context. Components then gate features against that role: an `AdminPanel` is rendered only for admins, a "Delete" button is hidden for viewers, and routes are wrapped so that unauthorized roles are redirected elsewhere. The standard primitives are a role value, an allowed-roles list per feature, and a helper such as `<RoleGate roles={['admin']}>` or a `usePermission()` hook. RBAC improves usability (users are not shown actions they cannot use) and reduces clutter, but it is crucial to understand its limits: frontend checks are a UX convenience, not a security boundary, because any client-side check can be bypassed by a determined user. All sensitive operations must be enforced on the backend, which validates the role claims server-side. When permission logic becomes complex, a permissions model based on capabilities or scopes can scale better than raw role lists. The decoded JWT should also be re-validated or refreshed so that role changes take effect, and UI updates should react to role changes without a full page reload. A common production pattern combines an auth context provider with route guards and per-element gating to cover navigation, actions, and data display consistently.

19. How do you protect routes in React?
    - **Answer:** Route protection is typically implemented with a wrapper component that checks the authentication state before rendering the intended page, in combination with React Router. A `ProtectedRoute` component reads the current auth status from an AuthContext (which usually holds the decoded JWT and user profile): if the user is authenticated, it returns the requested page through `<Outlet/>` or as children; otherwise, it redirects to the login page with `<Navigate to="/login" replace/>`. The redirect should preserve the originally requested location (passed via state) so that after login the user can be sent back. Role-based variants extend the check with an allowed-roles prop: `<ProtectedRoute roles={['admin']}>` redirects to a "forbidden" page if the role does not match. The checks should also handle loading: while a token is being validated or the profile is being fetched, the wrapper should render a spinner rather than flashing a redirect or an empty page. On the backend, every protected API also enforces authentication and authorization, since client-side guards are bypassable. Token expiry is handled by catching 401 responses, clearing the session, and redirecting to login with a "session expired" message. Route protection should be applied consistently, ideally in a central route table where every protected route is wrapped once, rather than scattering checks inside individual pages. The pattern can also gate layouts, so the entire authenticated shell (header, sidebar, navigation) is only mounted for logged-in users.

20. How do you call APIs from React?
    - **Answer:** APIs are called from React by performing network requests inside effects or event handlers and then storing the result in state. The most common approach uses the browser's `fetch` API with `async/await` inside a `useEffect` that runs on mount: set loading state, `await` the response, parse the JSON, and update state. The Fetch API and alternatives like Axios are equivalent in capability, but Axios adds conveniences such as automatic JSON transformation, request/response interceptors, and cancellation via AbortController. A central API client module typically encapsulates the base URL, sets common headers (Content-Type, Authorization), and centralizes error handling, so components never duplicate URL or header logic. Requests should be cancellable on unmount to avoid setting state after the component is gone — `AbortController` passed to `fetch` and aborted in the effect's cleanup function, or a mounted flag checked before setting state. Data freshness can be achieved with `setInterval` polling, but libraries like React Query (TanStack Query) or SWR are recommended for production because they manage caching, deduplication, background refetch, and retry automatically. React Query also separates concerns nicely: the query key drives caching and invalidation, and the hook returns `{ data, isLoading, isError }` that maps directly to the UI states. POST/PUT calls happen in event handlers and update the server, after which local state or the query cache is invalidated and refetched. The key principle is that React renders from state, so every network response must eventually land in state (or a store/query cache) to trigger the corresponding UI update.

21. How do you handle loading state?
    - **Answer:** Loading state represents the period between when an async operation starts and when it resolves, and the UI must communicate that period clearly. The classic approach is a boolean state — `const [loading, setLoading] = useState(true)` — set to `true` before the request and `false` after, with the render branching into a spinner while loading, the data once loaded, or an error message if it failed. Skeleton screens are a modern upgrade over spinners: placeholder boxes matching the final layout subtly animate until the content arrives, which reduces perceived latency and prevents layout shift. Loading should be granular rather than all-or-nothing: a table that loads new rows can keep existing rows visible with an inline indicator, and an individual widget can show its own loader while the rest of the page stays interactive. Stale-while-revalidate, as implemented by React Query, shows cached data immediately and refreshes in the background, eliminating most visible loading states. Initial loads versus subsequent refreshes deserve different treatment — a page first visited shows a strong loader, but a background poll should not flash a spinner and disrupt the layout. Loading states should also cover degenerate cases: a disabled button while a submit is in flight prevents duplicate requests. Error and empty states should be distinct from loading so the user can tell whether the app is waiting, empty, or broken. The essential contract is that every async view has exactly one of three states — loading, success, or error — and the render handles all of them explicitly.

22. How do you handle errors in UI?
    - **Answer:** Error handling in the UI covers both recoverable errors (like a failed API call) and unexpected runtime errors that would otherwise crash the app. For data-fetching errors, the pattern is to catch the failure, store the error in state, and render an error view that explains what happened and offers a path forward, typically a "Retry" button that re-runs the request. Error messages should be user-friendly rather than raw stack traces, while the technical detail is logged for debugging. Network failures, 4xx/5xx responses, and malformed payloads are usually distinguished so the message can say "connection lost," "permission denied," or "server issue." For unexpected render errors, React provides error boundaries: class components that implement `componentDidCatch` and a static `getDerivedStateFromError`, used to wrap the app or major sections so that a crash in one widget shows a fallback panel instead of unmounting the entire page. Error boundaries do not catch errors in event handlers, async code, or the boundary itself, so those still need explicit `try/catch`. Global handlers like `window.onerror` and `window.onunhandledrejection` can log client-side errors to a monitoring service. Form validation errors should appear inline next to the offending field with clear guidance. A good strategy is a small, reusable error-feedback component that standardizes message styling, retry behavior, and telemetry across the app, so error UX stays consistent and is not reimplemented per feature.

23. How do you optimize React performance?
    - **Answer:** React performance optimization is about minimizing unnecessary re-renders and reducing work per render. The first line of defense is architecture: keep state as local as possible, lift it only when sharing is truly required, and split components so that frequently changing sections re-render in isolation. `React.memo` wraps pure components to skip re-rendering when props are referentially unchanged, and it must be paired with `useCallback`/`useMemo` so that function and object props stay stable across renders. Expensive derived values are cached with `useMemo` so they are not recomputed on every render. Lists of hundreds or thousands of rows should use windowing (react-window) to render only the visible slice into the DOM. Large applications use route-based code splitting with `React.lazy` and `Suspense` so initial load ships less JavaScript. The DevTools Profiler is the authoritative tool for finding actual bottlenecks — it shows which components render, how long they take, and why, so optimizations target real problems instead of guesses. Bundlers help through tree shaking, minification, and vendor chunk splitting for cache friendliness. Events that fire rapidly, like scroll or drag, should be throttled or debounced, and data arriving in high frequency should be batched in state rather than re-rendered per item. Finally, `useTransition` can mark low-priority updates as non-blocking so urgent input stays responsive even during heavy re-renders. Optimization should always be measured before and after; premature memoization adds complexity without guaranteed benefit.

24. What is lazy loading?
    - **Answer:** Lazy loading defers the loading of a module or component until it is actually needed, rather than bundling everything into the initial request. In React, it is implemented with `React.lazy`, which takes a dynamic `import()` that returns a promise resolving to the component's module, plus `Suspense`, which renders a fallback (such as a spinner) while the module loads: `const ReportsPage = React.lazy(() => import('./ReportsPage'))`. The dynamic import tells the bundler (Webpack, Vite, Rollup) to emit the code as a separate chunk fetched on demand. The most common application is route-level lazy loading, where each page's code is fetched only when the user navigates to it; combined with React Router, the page is loaded during the navigation transition and shown once ready. Lazy loading reduces the initial JavaScript payload, improving first-contentful-paint and time-to-interactive metrics, which matters most on slow networks and low-end devices. It can also be applied to heavy third-party libraries and rarely used features like export tools or admin panels. Trade-offs include a loading delay on first visit to each section, which is usually acceptable when the fallback is a good skeleton or spinner, and the need to be careful that the chunk request itself is small. Prefetching can smooth the trade-off by fetching likely-next chunks during idle time. Lazy loading and code splitting are closely related — lazy loading is the runtime behavior enabled by code splitting's build-time chunking.

25. What is code splitting?
    - **Answer:** Code splitting is the build-time technique of breaking a single monolithic JavaScript bundle into multiple smaller chunks that are downloaded on demand, so the browser never loads code the user does not need yet. Without it, an application grows into a megabyte-plus bundle that blocks initial rendering. The mechanism is the dynamic `import()` syntax, which Webpack, Vite, and other bundlers turn into separate chunk files; the runtime then requests a chunk the first time its module is imported. The most effective split point is by route — each page becomes its own chunk — because navigation is a natural boundary and users typically land on one page. Other valuable splits are vendor libraries (kept separate so their rarely-changing code is cached aggressively), large dependencies used by only one feature, and conditionally shown components like modals or editors. Benefits include faster initial load, better cache reuse (only changed chunks invalidate), and reduced memory use. The cost is a network round-trip on first visit to each section, which `React.lazy` + `Suspense` mitigates with loading fallbacks, and which prefetching can hide entirely. Analyzing the bundle with tools like `webpack-bundle-analyzer` or `source-map-explorer` reveals oversized chunks worth splitting. Code splitting can go too far — dozens of tiny chunks add HTTP overhead — so chunk size and request count must be balanced. The mental model is simple: ship only what the current screen needs, then fetch the rest just-in-time.

26. How did you build dashboards in React?
    - **Answer:** Dashboards in React are built as a composition of independent widgets arranged inside a layout shell. The architecture typically has three layers: a layout layer that positions widgets in a grid, a widget layer where each widget is a self-contained component owning its own data fetching and rendering, and a shared data layer that provides auth, formatting, and API clients. Each widget is isolated so that one widget's loading, error, or empty state does not block or crash the others — error boundaries around widgets turn failures into inline fallbacks. Widgets fetch their own data (or subscribe to a shared query cache), which decouples them and enables parallel loading. The dashboard shell holds layout configuration — grid coordinates and sizes per widget — while each widget holds its own domain state. A configurable layout, often with `react-grid-layout`, lets users drag, resize, and reorder widgets, with the layout JSON persisted to localStorage or the backend. The data layer polls the backend or subscribes to WebSocket updates so charts and KPI tiles stay live without full-page reloads, typically with polling intervals per widget and automatic cleanup on unmount. Large data sets are summarized server-side or aggregated with `useMemo` to avoid heavy client computation. Themes, responsive breakpoints, and a shared chart library keep visual consistency. The result is a modular system where adding a new widget means adding a new component and a grid entry, with no changes to the rest of the dashboard.

27. What are customizable dashboard grids?
    - **Answer:** Customizable dashboard grids let users arrange widgets freely — drag to move, drag handles to resize, and persist the result so the layout survives refreshes. The standard library is `react-grid-layout`, which provides a grid coordinate system, drag-and-drop resizing, and collision handling out of the box. The component is configured with a layout array where each entry holds an item id, position (`x`, `y`), and size (`w`, `h`): `const layout = [{ i: 'temperature', x: 0, y: 0, w: 6, h: 4 }]`. Changes are captured through `onLayoutChange`, and the resulting JSON is saved to localStorage per user or sent to the backend so different users can have different views. Responsive variants (`react-grid-responsive`) define breakpoints so widgets stack on phones and expand on wide monitors. Widgets should be designed to be resizable without breaking, which generally means fluid containers, adaptive chart libraries, and hiding optional details when space is small. Persistence often stores both the grid coordinates and per-user preferences, restored on login. The grid must handle edge cases: empty states when all widgets are removed, duplicate items, and migrating layout versions as widgets are added or removed (unknown ids are dropped safely). Customization improves usability for different roles and screen sizes, letting each user see the data that matters most. The implementation remains React-native: the grid is a component, the layout is state, and dragging merely updates that state, which flows back into the grid's props.

28. What is Three.js?
    - **Answer:** Three.js is a JavaScript library that makes 3D graphics in the browser accessible by wrapping WebGL — the browser's low-level 3D rendering API — in a high-level, scene-graph API. WebGL alone requires verbose boilerplate for shaders, buffers, and the pipeline, whereas Three.js lets developers describe a scene declaratively with a handful of objects. The core architecture is built on four pillars: a `Scene` that holds all objects, a `Camera` (typically `PerspectiveCamera`) that defines the viewpoint, a `Renderer` (`WebGLRenderer`) that draws the scene to a canvas, and `Object3D` entities like `Mesh` (geometry + material) and `Light` that populate the world. A minimal example creates a scene, adds a camera, creates a box mesh, and calls `renderer.render(scene, camera)` inside a `requestAnimationFrame` loop for animation. Three.js handles cameras, lights, shadows, materials, textures, and post-processing, and it can import models in formats like GLTF and OBJ. It is widely used for product visualizations, games, data visualization, and digital twins — 3D representations of physical assets synchronized with real data. Integration with React typically uses a wrapper library like `@react-three/fiber` or a manually managed canvas ref inside a `useEffect`. The rendering loop and React's render cycle are decoupled: React controls the component tree, while Three.js controls the canvas and animation frames. Because WebGL runs on the GPU, even scenes with thousands of objects remain interactive when rendered efficiently.

29. How did you use Three.js for digital twin visualization?
    - **Answer:** A digital twin visualization in Three.js builds an interactive 3D model of a physical asset — such as a warehouse, factory, or building — and binds it to live data so the model reflects reality in real time. The approach starts by constructing the scene's static geometry (floor plan, walls, shelving, machinery) from blueprints or imported GLTF models, laid out at real-world coordinates. Sensors and equipment are then placed as small 3D objects — spheres, boxes, or icons — positioned at their physical locations so the digital model maps one-to-one to the real one. Live data binds to the model by color and state: a sensor sphere turns green, yellow, or red based on thresholds from the latest reading, and clicking a sphere opens a detail panel with its history and alerts. Updates arrive through polling or WebSocket subscriptions in a `useEffect`, and each update only mutates the relevant object's material color rather than rebuilding the scene. Camera controls (`OrbitControls`) let users pan, zoom, and rotate to inspect any zone, and highlighting can draw attention to alarming areas. Performance matters at scale — hundreds of sensor objects share a small set of materials or use instancing to keep draw calls low. The scene is a single canvas owned by Three.js, while React manages everything around it: overlays, panels, filters, and the data layer. This pairing yields an intuitive, spatial view of operational state that is far faster to interpret than tables of numbers.

30. How do you show live sensor hotspots in UI?
    - **Answer:** Live sensor hotspots visualize temperature or other measurements as colored regions so that problem areas stand out at a glance. The standard approach renders each sensor as a colored marker on a map or 3D model — a gradient from blue through green and yellow to red encodes the value against configured thresholds, so cold zones are blue and hot zones are red. To show a continuous "hotspot" area rather than discrete dots, the values are interpolated across the space: a nearest-neighbor or inverse-distance weighting algorithm estimates values between sensor positions, and a texture or grid of colored cells is generated from those estimates. In 2D this can be drawn on a canvas overlay or as an SVG/WebGL surface; in Three.js, colors are baked into vertex data or a texture and updated as data changes. Updates come from polling or WebSocket streams inside `useEffect`; each new batch recomputes the interpolated field and updates colors without re-rendering the whole scene. Threshold alarms can additionally pulse or flash the marker, and tooltips or side panels show exact readings on hover or click. Data should be downsampled and updated no more frequently than the data arrives, typically a few times per second, to avoid wasted work. The visualization is composed of three concerns kept separate: the data stream, the interpolation/color-mapping logic, and the rendering layer. The result is an at-a-glance operational view where operators spot excursions immediately and drill into the exact sensor for details.
