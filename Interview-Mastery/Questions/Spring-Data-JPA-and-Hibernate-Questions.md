## Answers

1. What is JPA?
   - **Answer:** JPA (Java Persistence API) is a specification, not an implementation. It defines a standard set of interfaces, annotations, and rules for object-relational mapping (ORM) so that Java applications can persist plain Java objects (entities) to relational databases without hand-writing SQL. The specification is governed by the Jakarta EE (formerly Java EE) platform and includes core artifacts such as `EntityManager`, `EntityManagerFactory`, `Query`, annotations like `@Entity`, `@Table`, `@Id`, and the `persistence.xml` configuration file. Because it is only a specification, you must provide an ORM implementation on the classpath — Hibernate, EclipseLink, or OpenJPA are the common options. This abstraction provides portability: code written against JPA interfaces can run on any compliant provider, assuming database-neutral features are used. JPA also standardizes the persistence lifecycle, including persistence context management, entity state transitions, and querying via JPQL (Java Persistence Query Language). In practice, applications rarely interact with JPA directly; Spring Data JPA builds another layer of repository abstraction on top of it. JPA handles CRUD, mapping between Java types and SQL types, relationship management (`@OneToMany`, `@ManyToOne`), and transactional behavior when combined with a transaction manager. A typical usage looks like:
     ```java
     @Entity
     @Table(name = "products")
     public class Product {
         @Id
         @GeneratedValue(strategy = GenerationType.IDENTITY)
         private Long id;
         private String name;
     }
     ```
     One important nuance is that JPA by itself provides no caching beyond the first-level (persistence context) cache, no connection pooling, and no transaction management — those are typically supplied by Hibernate, a connection pool like HikariCP, and Spring's transaction abstraction. Understanding JPA as an API contract versus an engine helps clarify why switching providers rarely requires changing entity code.

2. What is Hibernate?
   - **Answer:** Hibernate is a mature, widely used ORM framework and the reference implementation of the JPA specification. It does the heavy lifting that JPA leaves undefined: translating entity state changes into SQL statements, managing the persistence context and identity map, generating DDL schema, providing a first-level session cache, and supporting optional second-level and query caches. Beyond the JPA standard, Hibernate offers its own extensions such as `@Fetch`, `@BatchSize`, `@NaturalId`, `@DynamicUpdate`, and HQL (Hibernate Query Language) which is similar to but richer than JPQL. Hibernate resolves entities by their identifier in the persistence context, so loading the same row twice within one session returns the same Java instance. It also implements lazy loading through runtime-generated proxy classes and collection wrappers. Internally, Hibernate maintains a snapshot of each loaded entity; at flush time it compares current state against that snapshot to determine which columns to update — this is dirty checking. Configuration is done through properties such as `hibernate.dialect`, `hibernate.show_sql`, `hibernate.jdbc.batch_size`, and `hibernate.cache.use_second_level_cache`. When used inside Spring Boot, Hibernate is auto-configured and surfaced through `spring.jpa.properties.hibernate.*`. A key point is that Hibernate has historically diverged from the strict JPA spec, so code that depends on Hibernate-specific annotations or HQL features is not portable to other providers — a deliberate trade-off between portability and functionality. Since Hibernate 6.x, the codebase was re-architected to be fully JPA 3.1 compliant while keeping backward-compatible extensions.

3. Difference between JPA and Hibernate.
   - **Answer:** JPA is a specification — an abstract contract — while Hibernate is one concrete implementation of that contract. The relationship is analogous to an interface and its implementing class, or JDBC versus a specific database driver. JPA defines the API surface (`EntityManager`, annotations, JPQL, configuration), and any JPA-compliant provider must honor those rules, but the internal behavior — SQL generation, caching strategies, proxy mechanics, dialect handling — is entirely up to the provider. Hibernate was actually the inspiration for JPA: JPA 1.0 was heavily based on Hibernate 3.x design, and Hibernate has remained the de facto standard JPA provider. From a developer's perspective, coding against JPA keeps the domain layer portable; for example, switching from Hibernate to EclipseLink normally requires only changing the provider dependency and possibly the dialect, not the entity code. However, Hibernate-specific features — `@BatchSize`, `@DynamicUpdate`, `@NaturalId`, `@Filter`, HQL extensions — buy real performance and convenience but permanently couple the codebase to Hibernate. Spring Data JPA abstracts this further by generating repository implementations at runtime on top of whichever JPA provider is present. One practical distinction: JPA standardizes JPQL, while Hibernate provides HQL which is a superset (e.g., HQL supports functions like `extract()`, `function()`, and named native queries more flexibly). JPA also standardizes `@EntityGraph`, caching annotations, and `LockModeType`, all of which Hibernate implements. The choice matters most in large, long-lived applications where database portability could be required; for single-database applications, using Hibernate-specific features is generally acceptable and often beneficial. Ultimately the "difference" is the interface-versus-implementation seam, and knowing where that seam sits helps in debugging and in deciding which APIs to use.

4. What is entity?
   - **Answer:** An entity is a lightweight persistent domain object that represents a row in a relational database table. In JPA, an entity is a regular Java class annotated with `@Entity` (or `@MappedSuperclass` for shared mappings), and its fields map to table columns via annotations or XML mappings. A class qualifies as an entity only if it satisfies specific JPA requirements: it must have a no-arg constructor (public or protected), cannot be `final`, and must declare a field annotated with `@Id` that identifies the row. Each entity instance maps to exactly one row, and each row maps to at most one managed instance within a given persistence context — this is the identity guarantee that makes caching and dirty checking possible. Entity relationships are expressed with `@OneToOne`, `@OneToMany`, `@ManyToOne`, and `@ManyToMany`, optionally with `mappedBy` to designate the owning side of a bidirectional association. Entities can use `@Column` to control column name, length, nullable, unique, and precision; `@Table` to set the table name and schema; and `@Transient` to mark fields that must not be persisted. There are important design guidelines: entities should expose getters/setters, avoid exposing internal collections directly (return immutable copies or unmodifiable wrappers), and override `equals()`/`hashCode()` using a stable business key rather than the database ID, because proxies and unpersisted instances can otherwise break collection semantics. An entity has a lifecycle with four states — transient/new, managed, detached, removed — and the persistence provider manages transitions automatically within a persistence context. Example:
     ```java
     @Entity
     @Table(name = "orders")
     public class Order {
         @Id
         @GeneratedValue(strategy = GenerationType.IDENTITY)
         private Long id;
         @ManyToOne(fetch = FetchType.LAZY)
         private Customer customer;
         private BigDecimal total;
     }
     ```
     Entities are not DTOs: they are stateful and usually include behavior or domain logic, whereas DTOs are stateless data carriers used to decouple the persistence layer from the API layer.

5. What is `@Id`?
   - **Answer:** `@Id` marks a field (or field of an embedded class) as the entity's primary key. JPA requires every entity to declare exactly one `@Id` so the persistence provider can assign identity, track the instance in the persistence context, and generate SQL conditions for loading, updating, and deleting the row. Without a reliable identifier, JPA cannot tell whether two objects represent the same database row, and operations like `merge()` or caching would be impossible. The `@Id` field can be a primitive or wrapper type such as `Long`, `Integer`, `String`, `UUID`, or `LocalDate`, and should ideally be immutable to avoid breaking identity semantics. When the database manages key generation, `@Id` is combined with `@GeneratedValue`, specifying a strategy (`AUTO`, `IDENTITY`, `SEQUENCE`, `TABLE`); when keys come from the application, `@Id` is used alone and the value must be assigned before `persist()`. For composite keys, JPA offers two approaches: `@IdClass` (multiple `@Id` fields plus a separate class holding the same fields) or `@EmbeddedId` (a single `@Embeddable` field annotated with `@Id`). A composite key class must implement `equals()` and `hashCode()` and be serializable. A common pitfall is assigning a generated ID to a field declared as a primitive type, which fails because the key is null before persistence. Another is using `@Id` on a mutable field, since changing it after the entity becomes managed corrupts identity tracking. Example:
     ```java
     @Entity
     public class Employee {
         @Id
         @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "emp_seq")
         @SequenceGenerator(name = "emp_seq", sequenceName = "employee_seq", allocationSize = 1)
         private Long id;
     }
     ```
     Choosing the right key type matters for performance: surrogate numeric keys are generally preferable to natural keys, and UUID keys should be stored efficiently to avoid index bloat in large tables.

6. What is generated value?
   - **Answer:** `@GeneratedValue` tells JPA that the primary key will be generated automatically rather than assigned by application code. The `strategy` attribute selects one of four generation strategies. `GenerationType.IDENTITY` delegates key generation to the database's auto-increment column, so the value is produced by the INSERT itself and the ID is known only after insertion. `GenerationType.SEQUENCE` uses a database sequence object, optionally configured through `@SequenceGenerator`; it is generally the most efficient strategy because sequence values can be pre-fetched in batches (`allocationSize`), and it does not block batching of INSERT statements. `GenerationType.TABLE` emulates a sequence with a dedicated table that is updated to track the next value; it is portable across all databases but is the slowest because every allocation requires a table update, so it is rarely recommended. `GenerationType.AUTO` lets the provider pick the best strategy for the configured database — Hibernate typically chooses SEQUENCE on modern databases and IDENTITY on MySQL — which is convenient but can lead to inconsistent behavior when the schema is shared across environments. The biggest performance consideration is the interaction with Hibernate batch inserts: with `IDENTITY`, Hibernate must execute each INSERT immediately to obtain the generated key, which silently disables `hibernate.jdbc.batch_size`. SEQUENCE with an `allocationSize` greater than 1 allows keys to be pre-fetched into the persistence context, enabling real batch inserts and UPDATE on merge. Example:
     ```java
     @Id
     @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
     @SequenceGenerator(name = "order_seq", sequenceName = "order_id_seq", allocationSize = 50)
     private Long id;
     ```
     A subtlety is the `allocationSize` mismatch with the actual database sequence increment — if they differ, IDs may be skipped or collide. Also note that with SEQUENCE, the entity ID is available before flush, whereas with IDENTITY it is only available after the INSERT.

7. What is repository?
   - **Answer:** In Spring Data, a repository is an interface-based abstraction over a data access technology that eliminates handwritten DAO code. A repository declares query methods by naming convention or annotation, and Spring Data generates the concrete implementation at application startup. The core marker interface is `Repository<T, ID>`; from it, Spring Data provides richer base interfaces. `CrudRepository<T, ID>` adds generic save, findById, existsById, findAll, count, and delete operations. `PagingAndSortingRepository` extends it with `findAll(Pageable)` and `findAll(Sort)`. `JpaRepository` adds JPA-specific methods such as `flush()`, `saveAndFlush()`, `deleteInBatch()`, and `getReferenceById()`. Repository methods can be defined three ways: derived query methods (e.g., `findByStatusAndCreatedAtAfter`), `@Query`-annotated JPQL or native SQL, and queries derived from a `@Query` name in the namespace. Spring Data applies a "query by method name" strategy at startup, parsing the method name and building a predicate tree; if the name is invalid or the property does not exist, the application fails to start, which is a desirable fail-fast behavior. Custom implementation logic is added by declaring a custom interface method and providing a class named `<Repository>Impl` — Spring Data merges the two parts. Repositories also support pagination (`Page<T>`), sorting, projections (interfaces, `DTO` classes, `@Projection`), entity graphs, locking via `@Lock`, and `@Modifying` for update/delete queries that require `clearAutomatically` and `flushAutomatically` awareness. Example:
     ```java
     public interface OrderRepository extends JpaRepository<Order, Long> {
         List<Order> findByCustomerIdAndStatus(Long customerId, String status);
         @Query("select o from Order o join fetch o.items where o.id = :id")
         Optional<Order> findWithItems(@Param("id") Long id);
     }
     ```
     The key benefit is consistency and testability: repositories are interfaces that can be mocked in unit tests, and the runtime proxies are generated once with predictable behavior.

8. What is Spring Data JPA?
   - **Answer:** Spring Data JPA is a Spring Framework module that builds a repository abstraction on top of a JPA provider (normally Hibernate), dramatically reducing the boilerplate of writing DAO classes. It automatically creates runtime implementations for repository interfaces, parses derived method names into JPQL, translates them into provider queries, and applies pagination, sorting, locking, and entity graphs transparently. Under the hood, Spring Data JPA uses the standard `EntityManager`, `EntityManagerFactory`, and `PlatformTransactionManager` beans, so a developer's code depends on Spring Data interfaces rather than on Hibernate APIs. The module also provides `@Query` for custom JPQL/native queries, `@Modifying` for DML operations, `@Procedure` for stored procedure invocation, `@EntityGraph` for fetch plans, and `Specification`/`JpaSpecificationExecutor` for dynamic criteria-based queries. Startup-time validation is a notable strength: derived method names and `@Query` strings are parsed when the context loads, so naming errors surface immediately instead of at runtime. Common settings live under `spring.jpa.*` in Spring Boot, such as `spring.jpa.hibernate.ddl-auto`, `spring.jpa.show-sql`, and `spring.jpa.properties.hibernate.*`. For bulk operations, repositories expose `deleteInBatch()`, and `@Modifying` queries run with an implicit `clearAutomatically` option that must be understood to avoid stale persistence context data. Spring Data JPA also integrates with Spring Data Commons features: audit via `@CreatedDate`, `@LastModifiedDate`, `@CreatedBy`, and `AuditorAware`, plus `Pageable`/`Slice` interfaces. The trade-off is reduced control over exactly how queries are executed compared to writing raw `EntityManager` code; for performance-sensitive paths, combining repositories with `@Query` and `JOIN FETCH` or fallback to `JdbcTemplate` is common practice.

9. What is `JpaRepository`?
   - **Answer:** `JpaRepository<T, ID>` is the richest of Spring Data's JPA base interfaces, extending `ListCrudRepository` (or `CrudRepository` and `PagingAndSortingRepository` depending on version) and adding JPA-flavored conveniences. Its extra methods include `flush()`, which synchronizes the persistence context with the database by issuing pending SQL; `saveAndFlush()`, which saves and flushes in one call so the entity's generated ID or database state is immediately visible; `saveAllAndFlush()` for bulk save-then-flush; `deleteInBatch()`, which issues a single `DELETE ... WHERE id IN (...)`; and `deleteAllInBatch()`. It also inherits `findAll(Pageable)` returning `Page<T>` and `findAll(Sort)`, plus `getReferenceById()` which returns a lazy proxy without a database round-trip. Because `JpaRepository` exposes persistence-context-touching operations, it is deliberately JPA-specific; `CrudRepository` by contrast is persistence-technology-agnostic and could theoretically back MongoDB, Redis, JDBC, or other stores. In Spring Data 3.x, the base interfaces were reorganized — `ListCrudRepository` and `ListPagingAndSortingRepository` return `List` instead of `Iterable`, and `JpaRepository` extends those. Choosing `JpaRepository` is appropriate when the application only uses a relational database and needs batching, flushing, and pagination in one interface. One caution: because methods like `deleteInBatch()` bypass the persistence context, they do not cascade and do not update managed instances, so in-memory entities can become stale. Using `JpaRepository` as the default base interface for every entity is a common, pragmatic choice in Spring Boot applications, but teams sometimes prefer `Repository` or `CrudRepository` to keep the exposed API minimal and testable.

10. Difference between `CrudRepository` and `JpaRepository`.
    - **Answer:** `CrudRepository<T, ID>` is the generic base interface for CRUD operations in Spring Data and is independent of any persistence technology, while `JpaRepository<T, ID>` extends it with JPA-specific operations. `CrudRepository` provides `save()`, `saveAll()`, `findById()`, `existsById()`, `findAll()`, `count()`, `deleteById()`, `delete()`, `deleteAll()` — enough for basic persistence. `JpaRepository` adds `flush()`, `saveAndFlush()`, `saveAllAndFlush()`, `deleteInBatch()`, `deleteAllInBatch()`, `getReferenceById()`, `findAll(Sort)`, and `findAll(Pageable)`. The most visible behavioral difference is that `CrudRepository.findAll()` returns `Iterable<T>` (or `List<T>` in Spring Data 3.x via `ListCrudRepository`), whereas `JpaRepository.findAll()` returns `List<T>` — historically, code using `CrudRepository` had to wrap results in a `List` manually. `JpaRepository` also depends on JPA types like `EntityManager`, so it cannot be used with non-JPA stores; if the persistence technology might change, depending on `CrudRepository` (or its technology-specific sibling) keeps the abstraction portable. Another subtle point: methods such as `getReferenceById()` rely on JPA proxy semantics that do not exist in other stores. In practice, most relational Spring Boot projects use `JpaRepository` for everything because pagination and flush control are routinely needed, and the JPA coupling is acceptable. The distinction is primarily about the breadth of the API surface and technology coupling: `CrudRepository` = minimal CRUD, portable; `JpaRepository` = CRUD + JPA batching/flushing/paging, JPA-bound. There is also `PagingAndSortingRepository` in between, which adds pagination/sorting without JPA-specific methods and is sometimes preferred to keep the interface minimal while still supporting `Pageable`.

11. What is derived query method?
    - **Answer:** A derived query method is a repository method whose name is parsed by Spring Data to generate a query automatically, removing the need to write JPQL or SQL. The method name follows a convention: a prefix such as `find...By`, `read...By`, `get...By`, `count...By`, `exists...By`, `delete...By` followed by a property expression chained with `And`, `Or`, and followed by operators like `Between`, `LessThan`, `GreaterThan`, `Like`, `Containing`, `In`, `IsNull`, `IsNotNull`, `After`, `Before`, `StartingWith`, `EndingWith`, `OrderBy`. Property traversal is supported through nested paths, e.g., `findByCustomerAddressCity(String city)` navigates `customer.address.city`, and `findByCustomer_Address_City` can disambiguate underscores. A subtlety is property resolution: Spring Data splits the method name at uppercase boundaries and matches against entity fields; if a path is ambiguous, it applies a "left-most" matching algorithm, and startup fails on unresolvable properties. Example:
    ```java
    List<Order> findByStatusAndCreatedAtAfterOrderByCreatedAtDesc(String status, LocalDateTime cutoff);
    long countByCustomerId(Long customerId);
    boolean existsBySerialNumber(String serialNumber);
    void deleteByStatus(String status);
    ```
    Derived queries are efficient for simple, well-known lookups and benefit from automatic count queries for pagination. The limitations are that names get unreadable beyond two or three conditions, and expressions such as complex joins, subqueries, window functions, or `GROUP BY` cannot be expressed this way — in those cases `@Query` with JPQL or native SQL is the right tool. Behind the scenes, Spring Data parses the name into a `PartTree`, builds a `Query` object, and binds parameters by name or position. It is also worth noting that `deleteBy...` and `updateBy...` derived methods issue bulk DML that bypasses the persistence context, so managed entities may be stale unless the context is cleared.

12. What is JPQL?
    - **Answer:** JPQL (Java Persistence Query Language) is the object-oriented query language defined by the JPA specification. It resembles SQL in structure — `SELECT`, `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, joins, subqueries — but operates on entity names and persistent field names rather than table and column names, and it is database-agnostic. A query like `SELECT o FROM Order o WHERE o.status = :status` selects `Order` entities where the mapped `status` field equals the bound parameter; the provider translates this into the target database's SQL at runtime. JPQL supports implicit joins through path expressions (`o.customer.name`), explicit joins (`JOIN o.items i`), `JOIN FETCH` to eagerly load associations, aggregate functions, `LIKE` patterns, `IN` lists, and `IS NULL` checks. Parameters can be positional (`?1`) or named (`:name`), with named parameters preferred for readability and for using the same query with different parameter values through query caching. Because JPQL works on entities, the result of a select is a list of managed entities (unless using constructor expressions or projections), which means result objects are tracked in the persistence context and dirty checking applies. Constructor expressions like `SELECT new com.example.dto.OrderSummary(o.id, o.total) FROM Order o` allow mapping results directly to DTOs without entity tracking. JPQL cannot express everything — database-specific window functions, CTEs, and vendor extensions are out of scope, which is where native queries and database views step in. Writing portable JPQL is a goal when the application may run against multiple databases; sticking to standard operators and avoiding provider extensions keeps queries portable. JPQL is also used under the hood by Spring Data for derived queries and `@Query` annotations, making it the lingua franca of JPA development.

13. Difference between JPQL and native query.
    - **Answer:** JPQL is a database-independent query language written against the entity model, whereas a native query is raw SQL written against actual database tables and columns. The provider translates JPQL into SQL using the configured dialect, so the same JPQL string runs on MySQL, PostgreSQL, or MSSQL without modification. Native queries give full control over the SQL — including window functions, common table expressions, database-specific functions, hints, `FOR UPDATE` clauses, and query optimizers' favorites — but at the cost of portability and of manual result mapping. In JPA, native queries are declared with `@Query(value = "SELECT ... FROM orders WHERE ...", nativeQuery = true)`, and results can be mapped to entities, to `@SqlResultSetMapping` definitions, or to constructor projections. A key behavioral difference is that JPQL selects return managed entities (subject to dirty checking and first-level caching), while native queries with entity mapping are not automatically managed unless `EntityManager` is asked for the entity reference; results from native queries are generally detached. JPQL supports entity lifecycle semantics such as `JOIN FETCH` and polymorphic queries across an inheritance hierarchy; native SQL must explicitly handle those with joins over concrete tables. Error detection differs too: JPQL errors are caught at startup when used via Spring Data `@Query`, whereas native SQL errors surface only when the query executes. Performance can also differ — hand-tuned SQL with correct index hints can outperform generated JPQL, and set-based bulk operations are easier to express natively. The pragmatic guidance is to use JPQL as the default, fall back to native queries for genuinely database-specific needs (stored procedures, window functions, complex reporting), and keep native SQL isolated so the portability cost is contained. Note also that native update/delete queries must be marked `@Modifying` so the persistence context is invalidated appropriately.

14. What is entity lifecycle?
    - **Answer:** JPA defines four entity lifecycle states: transient (new), managed (persistent), detached, and removed. A *transient* entity is a plain Java object created with `new` that is not associated with any `EntityManager` and has no representation in the database. Calling `persist()` on it makes it *managed*: the entity is associated with a persistence context, gains an identity (usually via ID generation at flush), and every subsequent change is tracked for automatic persistence. A *managed* entity is the only state where dirty checking applies — mutations are written to the database at flush time. An entity becomes *detached* when the persistence context closes (e.g., transaction ends and the `EntityManager` is closed), or explicitly via `detach()` or `clear()`. Detached entities still hold data but are no longer tracked; re-associating them requires `merge()`, which copies state onto an existing managed instance or persists a new one. A *removed* entity has been passed to `remove()`; it is scheduled for deletion and actually deleted at flush, and the entity instance becomes transient again after the transaction. The canonical transition methods are `persist()` (new → managed), `merge()` (detached → managed), `remove()` (managed → removed), `refresh()` (re-read from database), `detach()`/`clear()` (managed → detached), and `close()` of the `EntityManager`. Understanding these transitions is critical for correct behavior: calling `save()` on a detached entity with a pre-existing ID triggers `merge()`, while calling `persist()` on such an entity may throw or create a duplicate depending on provider. The lifecycle also drives `@PrePersist`, `@PostPersist`, `@PreUpdate`, `@PostUpdate`, `@PreRemove`, `@PostRemove`, and `@PostLoad` callback annotations, which allow hooking business logic to specific state changes. In Spring Data JPA, `save()` is smart enough to decide between `persist()` and `merge()` based on whether the ID is null, which conveniently hides most lifecycle management.

15. What is persistence context?
    - **Answer:** The persistence context is a JPA concept representing a set of entity instances managed within a session — effectively a first-level cache and an identity map that tracks the state of every managed entity. It is scoped to the `EntityManager` (or Hibernate `Session`), and in a typical Spring application it spans a transaction. Its core responsibilities are threefold: *identity* — within one context, loading the same row twice by ID returns the same Java instance, guaranteeing referential consistency; *caching* — repeat reads within the context hit the in-memory map instead of the database; and *change tracking* — Hibernate keeps a snapshot of each managed entity at load time, and at flush it diffs the snapshot against the current state to generate `UPDATE` statements (dirty checking). The persistence context is also what makes `getReference()` proxies, lazy loading, and cascade operations coherent, because all managed objects participate in the same identity map. Lifecycle operations that affect it: `persist()` adds an entity, `remove()` schedules deletion, `merge()` copies detached state back in, `detach()` removes an entity from tracking, `clear()` empties the context, and `flush()` synchronizes all pending changes to the database. A well-known pitfall is scope: if an entity is loaded outside a transaction and accessed later, the persistence context is gone and lazy associations fail with `LazyInitializationException`. The context is not a second-level cache — it is tied to a single transaction/session, whereas the second-level cache is shared across sessions. Understanding the persistence context is the key to answering most "why does JPA behave this way" questions, from N+1 to detached-entity issues. In Spring Data JPA, the `SimpleJpaRepository` implementation delegates to `EntityManager`, so repository methods operate within whatever persistence context the surrounding transaction provides.

16. What is dirty checking?
    - **Answer:** Dirty checking is the mechanism by which a JPA provider detects changes to managed entities and automatically persists them — the developer modifies fields on an object and the provider issues the appropriate `UPDATE` at flush time without an explicit save call. When Hibernate loads an entity, it stores a snapshot of the loaded state; at flush, it compares the snapshot against the current field values. Any difference marks the entity "dirty" and triggers an `UPDATE` for the changed columns. This comparison happens automatically at transaction commit (or on explicit `flush()`), and it is why loading an entity in a `@Transactional` method, mutating it, and returning works without calling `save()`:
    ```java
    @Transactional
    public void markPaid(Long orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.setStatus("PAID");
    }
    ```
    The default strategy compares all loaded fields, which is correct but can be wasteful for wide tables; `@DynamicUpdate` restricts the generated `UPDATE` to only the changed columns (at the cost of pre-built statement caching). Dirty checking only applies to *managed* entities — detached or transient objects are never checked, which is why re-associating a detached object with `merge()` is needed. Two performance considerations: dirty checking runs at flush time for every managed entity in the context, so huge transactions with many entities can be slow, and Hibernate optimizes by skipping the check when no `FlushModeType.AUTO` triggers it. `@PreUpdate` callbacks and version increments are also invoked as part of the flush when dirty state is detected. Understanding dirty checking clarifies common confusions: why calling `findById` then mutating persists without `save()`, why `@Modifying` bulk queries bypass it (they must be marked `clearAutomatically` to avoid stale managed state), and why read-only transactions are faster — setting `readOnly = true` tells Hibernate to skip dirty checking entirely.

17. What is first-level cache?
    - **Answer:** The first-level cache is the persistence context itself — an in-memory store scoped to a single `EntityManager`/`Session` that caches every managed entity by its type and identifier. It is always enabled and cannot be disabled, which is a deliberate JPA design decision: the cache provides repeatable reads within a session and prevents the same row from being materialized as multiple inconsistent Java objects. When an entity is loaded via `find()` or a JPQL query that returns entities, it is stored in this cache; a second lookup by the same ID within the same session returns the cached instance without hitting the database. Because the first-level cache is transaction/session-scoped, it is cleared when the transaction ends (in typical `OpenEntityManagerInView`-disabled Spring setups), so it does not share data across requests. Managing it is important for long-running operations: `entityManager.clear()` evicts all entities and detaches them, and `entityManager.detach(entity)` evicts a single one — both can reduce memory pressure when processing large result sets in a loop. There is a subtle interplay with queries: JPQL queries do not populate or read the cache the way `find()` does — a query still hits the database, though the resulting entities are then added to the cache. The first-level cache is distinct from the second-level cache, which is a SessionFactory-level cache shared across sessions and optional. A common misconception is that first-level caching means repeated queries avoid the database; in reality, only lookups by ID within the same context are served from cache, which is why N+1 problems and query-level caching are separate concerns. Recognizing that the "cache" and "identity map" are the same mechanism explains most of the caching-related behavior in Hibernate.

18. What is second-level cache?
    - **Answer:** The second-level cache is a SessionFactory-level (or `EntityManagerFactory`-level) cache shared across all sessions and transactions, and it is optional — unlike the first-level cache, it must be explicitly enabled and configured. It stores entity data, collections, and optionally query results so that multiple transactions can avoid hitting the database for the same data. In Hibernate, enabling it requires a cache provider (e.g., Ehcache, Redis, Hazelcast) plus configuration, and entities are marked cacheable with `@Cacheable` and `@Cache(usage = ...)`. The `usage` attribute selects a concurrency strategy: `READ_ONLY` for immutable data (fastest, no locking), `READ_WRITE` for mutable data where slight staleness is acceptable, `NONSTRICT_READ_WRITE` for data updated rarely with eventual consistency, and `TRANSACTIONAL` for strong transactional guarantees with a JTA-compliant provider. The second-level cache is designed for read-heavy, rarely modified data — reference data like country codes, configuration, or user profiles — and is a poor fit for frequently updated, high-contention rows. Caching collections is riskier because collection invalidation semantics are more complex, and query caching (`hibernate.cache.use_query_cache`) stores only query results plus the IDs of returned entities, which must be combined with second-level entity caching to be effective. A major caveat is distributed cache consistency: with a cluster of application instances sharing one database, a distributed cache such as Redis must invalidate entries when any node updates data, and JPA does not coordinate this automatically — stale data is possible without careful eviction logic. Because of these consistency and invalidation complexities, many teams prefer to leave the second-level cache disabled and instead optimize with targeted query optimization, read replicas, or application-level caching of DTO projections. The decision should be data-driven: measure cache hit rates and staleness tolerance before introducing it.

19. What is lazy loading?
    - **Answer:** Lazy loading defers the retrieval of an entity's associated data until the moment it is actually accessed, avoiding unnecessary database queries. JPA defaults reflect this intent: `@OneToMany` and `@ManyToMany` default to `FetchType.LAZY`, while `@ManyToOne` and `@OneToOne` default to `FetchType.EAGER`. With lazy loading, Hibernate does not join the related table in the parent query; instead, when the parent is loaded, a proxy object or a lazy collection wrapper stands in for the association. The database hit happens on first access — e.g., iterating `order.getItems()` triggers a `SELECT` for the items — and the fetched data is then stored in the persistence context. The implementation relies on proxies for single-valued associations and `PersistentBag`/`PersistentSet` wrappers for collections, all generated at runtime by the provider. The crucial constraint is that lazy loading only works while the entity is still managed within an open persistence context; accessing a lazy association after the session/transaction closed throws `LazyInitializationException`. This is why the common error message "failed to lazily initialize a collection... could not initialize proxy - no Session" appears. Solutions include keeping the operation inside `@Transactional`, eagerly fetching with `JOIN FETCH` or `@EntityGraph`, configuring `spring.jpa.open-in-view` (discouraged for production), or accessing the data before the session closes. Lazy loading is a double-edged sword: it can prevent N+1 by avoiding unnecessary joins, but naive access in loops *causes* N+1 problems (see below). Using `@BatchSize` or `@Fetch(FetchMode.SUBSELECT)` can soften the blow of lazy collections by batching the load. Understanding proxies matters for `equals()`/`hashCode()` and for type checks: `instanceof` works with proxies, but direct field access does not trigger initialization, and casting a proxy to a subclass may fail if not initialized.

20. What is eager loading?
    - **Answer:** Eager loading fetches an entity's associated data immediately when the entity itself is loaded, using a join or a subsequent query in the same load operation, so the association is available without further database round-trips. JPA's defaults make `@ManyToOne` and `@OneToOne` eager because the related row is cheaply fetched with a single join, while collections default to lazy to avoid loading entire child sets needlessly. Eager loading guarantees the data is populated even after the session closes, eliminating `LazyInitializationException` for that association, which is why it is tempting to annotate everything eager. The danger is over-fetching: an eager `@OneToMany` causes the parent query to join and load all children even when they are never used, and multiple eager collections in one entity can produce a Cartesian product — the result set explodes as the product of the collection sizes. Eager loading can also silently create N+1 behavior across a list of parents: loading 100 parents with an eager collection issues 100 extra SELECTs (or one massive join), depending on the provider's fetch strategy. JPA provides no standard way to make fetch strategy per-query; the `fetch` attribute is a static mapping default, so the recommended modern approach is to keep mappings lazy and control eager loading per query with `JOIN FETCH` or `@EntityGraph`. This gives the query author explicit control over when associations are loaded:
    ```java
    @Query("select o from Order o join fetch o.items where o.id = :id")
    Optional<Order> findWithItems(@Param("id") Long id);
    ```
    Eager loading is still appropriate for small, always-needed associations like a `Country` on a `User`, but as a general rule, lazy mappings plus explicit fetch plans balance correctness and performance. Hibernate also supports `@Fetch(FetchMode.JOIN)` and `@Fetch(FetchMode.SELECT)` to tune the loading style, but these are provider-specific.

21. What is N+1 query problem?
    - **Answer:** The N+1 problem is a classic ORM performance anti-pattern where loading a list of N parent entities triggers N additional queries — one per parent — for an associated collection, totaling N+1 queries when one would have sufficed. It typically appears with lazy-loaded collections: `repository.findAll()` issues a single `SELECT` for the parents, then code iterates and accesses each parent's lazy collection, causing the provider to fire one query per parent:
    ```java
    List<Order> orders = orderRepository.findAll();
    for (Order o : orders) {
        System.out.println(o.getItems().size());  // 1 query per order -> N+1
    }
    ```
    It also occurs with eager `@ManyToOne`/`@OneToOne` mappings when the provider issues per-row selects, and with `@BatchSize` being unset. The problem is compounded by caching: because queries do not populate the first-level cache the way ID lookups do, the same collection may be reloaded repeatedly. Detection is straightforward when SQL logging is enabled (`spring.jpa.show-sql=true` or Hibernate statistics): a log that shows one SELECT followed by hundreds of nearly identical SELECTs is the fingerprint. The cost is proportional to N and the join complexity, so lists of thousands of parents produce thousands of queries and severe latency, CPU, and connection-pool pressure. Fixes include `JOIN FETCH` (single query with joins), `@EntityGraph`, `@BatchSize` (load collections in batches, reducing N+1 to N/batch+1), `@Fetch(FetchMode.SUBSELECT)` (one query with an IN subselect), or restructuring the query to project only needed data with DTOs. The right solution depends on the access pattern: batch loading works well when the associations are used sporadically, while fetch joins work best when every parent needs its children. N+1 is the single most common cause of slow JPA applications, so it is a standard interview and production-debugging topic.

22. How do you solve N+1 query problem?
    - **Answer:** The N+1 problem is solved by reducing the number of queries that load associated data, and the main strategies are `JOIN FETCH`, `@EntityGraph`, batch fetching, and subselect fetching. `JOIN FETCH` is the most direct: writing `SELECT o FROM Order o JOIN FETCH o.items` makes Hibernate load the orders and their items in one query using a join (or two queries with distinct root in some cases to avoid duplicates). `@EntityGraph` achieves the same declaratively without changing the JPQL — the graph names which associations must be eagerly loaded for that query, which is ideal for repository methods:
    ```java
    @EntityGraph(attributePaths = "items")
    List<Order> findAllWithItems();
    ```
    Batch fetching addresses the case where the association is only sometimes accessed: `@BatchSize(size = 20)` tells Hibernate to load up to 20 lazy collections with a single `IN (...)` query, converting N+1 queries into roughly N/20+1. Alternatively, `@Fetch(FetchMode.SUBSELECT)` issues one query using a subselect on the IDs of already-loaded parents, also collapsing many queries into one. For read-only reporting, projections/DTOs loaded with a single `@Query` can avoid loading entities entirely. There is no universal best fix — the access pattern decides: if every parent always needs children, use `JOIN FETCH` or `@EntityGraph`; if children are needed rarely, `@BatchSize` is cheaper because it avoids join cartesian products; if children are always needed for a specific query, a targeted fetch query is best. It is also important to disable `spring.jpa.open-in-view` in production so that accidental lazy access fails loudly instead of silently multiplying queries. Finally, verifying with Hibernate's `hibernate.generate_statistics` or SQL logging confirms the fix reduced the query count to the expected number.

23. What is fetch join?
    - **Answer:** A fetch join is a JPQL construct (`JOIN FETCH`) that tells the persistence provider to load an association eagerly in the same query, effectively overriding the association's configured fetch type for that query. Unlike a regular join, which only filters results, a fetch join also populates the association so it is available without additional queries and without requiring an open session:
    ```java
    @Query("select o from Order o join fetch o.customer where o.status = :status")
    List<Order> findWithCustomer(@Param("status") String status);
    ```
    Because the fetched entities are managed, accessing `order.getCustomer()` afterwards does not trigger another SELECT. Two practical caveats are important. First, with a collection (`@OneToMany`), a fetch join can multiply rows — if an order has three items, the result set has three rows for the same order — and mapping them back requires `DISTINCT` or relying on Hibernate's in-memory deduplication; with multiple fetched collections the rows explode as a Cartesian product, so fetching more than one collection in a single query is discouraged. Second, `LEFT JOIN FETCH` should be used instead of `JOIN FETCH` when the association may be absent, because an inner join would silently drop parents with no children. Fetch joins do not change the entity mapping; they are a per-query concern, which keeps the domain model lazy by default while allowing hot paths to be optimized. They also interact with pagination: applying `setFirstResult`/`setMaxResults` to a query with collection fetch joins can return incorrect counts, and in many databases the pagination must be applied to the root query with a separate count query. Fetch joins are one of the primary tools against N+1, alongside `@EntityGraph`, and are generally preferred over changing global mappings to eager.

24. What is entity graph?
    - **Answer:** An entity graph is a declarative, reusable fetch plan that specifies which associations to eagerly load for a particular query, without changing the entity's static fetch mappings. There are two ways to define one: `@NamedEntityGraph` on the entity, referenced by name, or `@EntityGraph` on a Spring Data repository method, which can either reference a named graph or specify attribute paths inline. The graph is applied with one of two types: `EntityGraphType.FETCH`, which *replaces* the default fetch plan so that only the attributes listed in the graph are fetched eagerly (all others become lazy), or `EntityGraphType.LOAD`, which *adds* the listed attributes to the existing default plan. Example:
    ```java
    @NamedEntityGraph(name = "Order.details", attributeNodes = {
        @NamedAttributeNode("customer"),
        @NamedAttributeNode(value = "items", subgraph = "itemProduct")
    }, subgraphs = {
        @NamedSubgraph(name = "itemProduct", attributeNodes = @NamedAttributeNode("product"))
    })
    public class Order { ... }
    ```
    ```java
    @EntityGraph("Order.details")
    List<Order> findAllWithDetails();
    ```
    Or, more concisely, without a named graph: `@EntityGraph(attributePaths = {"customer", "items.product"})`. At execution time, the provider translates the graph into the appropriate join or select strategy (Hibernate generally uses a left join to fetch the collections eagerly). Entity graphs are the recommended, JPA-standard replacement for the old `fetch = FetchType.EAGER` global mappings because they keep the model lazy by default and make fetch behavior explicit per query. They compose with repository queries (`@Query`, derived queries) and work with `EntityManager.createEntityGraph` at runtime for fully dynamic plans. The main constraints mirror fetch joins: fetching multiple collections in one graph can produce Cartesian products, and graphs do not change the number of resulting rows, so `DISTINCT` may be needed to deduplicate roots.

25. What is pagination?
    - **Answer:** Pagination is the technique of splitting a large result set into fixed-size pages so that only one page of data is loaded, queried, and transferred at a time. In Spring Data JPA, a repository method takes a `Pageable` and returns a `Page<T>` — the page content, plus metadata such as `getTotalElements()`, `getTotalPages()`, `getNumber()`, `getSize()`, and `getSort()`:
    ```java
    Page<Order> findAllByCustomerId(Long customerId, Pageable pageable);
    Page<Order> page = repo.findAll(PageRequest.of(0, 20, Sort.by("createdAt").descending()));
    ```
    The provider translates the page size and offset into database-specific SQL (`LIMIT/OFFSET` on PostgreSQL/MySQL, `OFFSET/FETCH NEXT` on MSSQL, `ROWNUM` on Oracle), and Spring Data also runs a count query to populate the total metadata. `Slice<T>` is a lighter alternative that only knows whether another page exists, skipping the potentially expensive count query. The classic pitfall is offset-based pagination's deep-page problem: the database must scan and discard `offset + size` rows on every page, so page 100000 is costly even though only 20 rows are returned. For large datasets, keyset (seek) pagination — `WHERE createdAt > :lastSeen ORDER BY createdAt` — is O(1) per page, though it requires a stable sort key and loses the ability to jump to arbitrary pages. Another subtlety: paginating a query with collection `JOIN FETCH` can yield wrong page sizes because the join multiplies rows; the standard workaround is to paginate the root query and fetch collections with `@BatchSize` or a separate query. Pagination also interacts with sorting: user-supplied sort fields should be validated against an allowlist to prevent SQL injection via `Sort` (Spring validates property names, but custom native queries need care). For typical list endpoints, combining `Pageable` with `Page<T>` DTO projections keeps payloads small and response times stable.

26. What is sorting?
    - **Answer:** Sorting orders the rows of a query result by one or more fields in ascending or descending order. In Spring Data JPA, sorting is expressed either by passing a `Sort` object into a repository method (`findAll(Sort)`, `findAll(Pageable)`) or by using `Sort.by(...)` inside a `PageRequest`:
    ```java
    List<Order> orders = orderRepository.findAll(Sort.by(Order.asc("createdAt"), Order.desc("total")));
    Page<Order> page = orderRepository.findAll(PageRequest.of(0, 20, Sort.by("status").ascending()));
    ```
    `Sort.by("field")` maps the field name to the actual column at runtime through the entity's metadata, so `Sort.by("customer.name")` can navigate nested properties. The generated SQL appends `ORDER BY` with the correct direction and, when pagination is combined, the sort is applied before the offset/limit. Static association ordering can also be declared with `@OrderBy("createdAt DESC")` on an entity's collection field, which applies whenever the collection is loaded regardless of query. For database portability, ordering by an expression (like a case statement or a computed value) is not portable in JPQL and may require a native query or a derived order value. There is also a security angle: when sort fields come from user input, an attacker could attempt to inject into the ORDER BY clause; Spring Data validates that the property exists on the entity before building the query, which blocks arbitrary column injection for derived queries, but `Sort.unsorted()` should be used when no ordering is wanted, and custom native queries with user input must be parameterized carefully. Sorting performance depends on indexes — an `ORDER BY` on an unindexed column forces a sort after the scan, so composite indexes covering the sort fields are the primary optimization. Finally, remember that `Page` includes the `Sort` in its metadata, so clients can echo it back for consistent pagination state.

27. What is transaction management?
    - **Answer:** Transaction management is the discipline of grouping multiple database operations into a single unit of work that either commits all its changes or rolls them all back, preserving atomicity and consistency. Transactions are characterized by the ACID properties: Atomicity (all-or-nothing), Consistency (the database moves between valid states), Isolation (concurrent transactions do not interfere beyond the chosen isolation level), and Durability (committed changes survive failures). In Java, transaction management comes in two flavors: programmatic and declarative. Programmatic management uses `PlatformTransactionManager` or `TransactionTemplate` directly, giving fine-grained control inside method bodies. Declarative management uses Spring's `@Transactional` annotation or XML configuration so that transactional boundaries are defined declaratively and enforced by AOP proxies, keeping business code free of transaction plumbing. Spring provides `DataSourceTransactionManager` for plain JDBC, `JpaTransactionManager` for JPA, and `JtaTransactionManager` for distributed (JTA) transactions; with `@EnableTransactionManagement` (or Spring Boot autoconfiguration), a default transaction manager is created based on the persistence technology in use. Key concerns in transaction design are scope and duration: transactions should be short, should not hold database connections while doing slow I/O, and should not call remote services or do long computations, because long transactions hold locks and consume connection-pool resources. Transaction management also interacts with the persistence context: in Spring/JPA, the persistence context is tied to the transaction (by default), so a `@Transactional` method sees consistent, managed entities and the flush happens at commit. Distributed transactions (spanning multiple databases or queues) introduce two-phase commit and are a significant complexity; many systems avoid them by using transactional outbox patterns and sagas instead. Understanding the interplay of transactions, isolation levels, and lock durations is essential for correct and performant database applications.

28. What is `@Transactional`?
    - **Answer:** `@Transactional` is Spring's annotation for declarative transaction management. Applied to a method (or a class, which applies to all its methods), it instructs Spring to wrap the method invocation with a transaction boundary: a transaction is begun before the method runs, committed if the method completes normally, and rolled back if it throws an exception that matches the rollback rules. Its attributes configure the transaction's behavior: `propagation` controls how the method participates in an existing transaction (`REQUIRED`, `REQUIRES_NEW`, `SUPPORTS`, `MANDATORY`, `NOT_SUPPORTED`, `NEVER`, `NESTED`); `isolation` overrides the default isolation level; `timeout` aborts the transaction if it runs longer than the specified seconds; `readOnly` marks the transaction as read-only, which lets the provider skip dirty checking and issue fewer locks; `rollbackFor`/`noRollbackFor` (and their class-name variants) customize which exceptions trigger rollback. Example of a typical usage:
    ```java
    @Transactional(propagation = Propagation.REQUIRED, readOnly = true, timeout = 30)
    public List<Order> findOrders() { ... }

    @Transactional(rollbackFor = InsufficientStockException.class)
    public void reserveStock(Long orderId) { ... }
    ```
    The annotation works through a proxy — Spring generates a JDK dynamic proxy or CGLIB subclass around the bean and intercepts calls — so it only applies when the method is invoked *through* the proxy (i.e., from another bean), not on self-invocation. By default it applies only to public methods. `readOnly = true` is an optimization hint, not a strict enforcement: with JPA it makes Hibernate skip dirty checking and flush, but it does not prevent the method from writing. `@Transactional` belongs on the service (application) layer rather than the repository layer, because a use case often spans multiple repository operations and should be atomic. The default rollback behavior — rollback on `RuntimeException` and `Error`, commit on checked exceptions — is a deliberate convention and can be changed with `rollbackFor`.

29. How does `@Transactional` work internally?
    - **Answer:** `@Transactional` is implemented with Spring AOP and a proxy. At startup, Spring detects beans with transactional methods and wraps them in a proxy object (a JDK dynamic proxy if the bean implements an interface, otherwise a CGLIB-generated subclass). When another bean calls a transactional method, the call goes through the proxy, which delegates to a `TransactionInterceptor` (an `AopAlliance` advice). The interceptor obtains the `PlatformTransactionManager` bean, determines the transaction attributes from the annotation metadata, and calls `getTransaction()`, which begins or joins an existing transaction per the propagation setting. It then invokes the actual business method inside a try/catch/finally. On normal return, it calls `commit()`, which flushes the JPA persistence context (issuing pending INSERT/UPDATE/DELETE), then commits the database transaction. On exception, it checks the rollback rules — if the exception qualifies for rollback, it marks the transaction rollback-only and calls `rollback()`; otherwise it commits. The details are orchestrated by `TransactionAspectSupport.invokeWithinTransaction`, which also manages transaction synchronization (`TransactionSynchronizationManager`), exposes transaction-bound resources (the JPA `EntityManager` bound to the thread), and handles nested calls via `TransactionStatus`. Because JPA transactions are thread-bound, `@Transactional` correctly handles a single thread; the persistence context (and the connection) lives in a `ThreadLocal` for the duration of the transaction. The proxy-based nature explains the well-known limitations: self-invocation bypasses the proxy, private methods are never intercepted, and `final` methods cannot be proxied by CGLIB. This is also why calling `this.anotherTransactionalMethod()` inside a class silently loses the transaction, and why injecting the proxy into itself (via `@Lazy` self-reference) or splitting services is the fix.

30. What is transaction propagation?
    - **Answer:** Transaction propagation defines how a transactional method behaves when it is invoked while another transaction is already active — whether it joins the existing transaction, suspends it, or fails. The seven propagation levels are defined in the `Propagation` enum. `REQUIRED` (the default) joins an existing transaction or creates a new one if none exists; this is the correct choice for most business logic because all participating methods share one unit of work. `SUPPORTS` runs within an existing transaction if present, otherwise without one — useful for read helpers that work either way. `MANDATORY` requires an existing transaction and throws if none is active — a good guard for methods that must never run outside a transaction. `REQUIRES_NEW` suspends the current transaction and creates an independent one, so the inner method commits or rolls back separately; this is used for audit logging, notifications, or long-running steps that must succeed even if the outer transaction rolls back. `NOT_SUPPORTED` suspends the current transaction and runs without one — suitable for operations that must not hold a transaction open (e.g., a long report generation). `NEVER` throws if a transaction is active. `NESTED` uses a savepoint within the existing transaction, allowing the inner work to roll back to the savepoint without aborting the whole transaction (supported by JDBC `Savepoint`, but its behavior with JPA depends on the provider and database). Example:
    ```java
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveAuditLog(AuditLog log) { ... }
    ```
    Propagation is a common source of bugs: `REQUIRES_NEW` inside the same bean does not work with self-invocation (the proxy is bypassed), and a `REQUIRES_NEW` method that throws and is caught by the caller still commits its own work, which can surprise developers expecting a full rollback. Choosing propagation is about scoping the unit of work: `REQUIRED` gives atomicity across collaborators, while `REQUIRES_NEW` deliberately breaks atomicity for side effects that must survive the main transaction.

31. What is transaction isolation?
    - **Answer:** Transaction isolation determines how much a transaction can see of other concurrent transactions' uncommitted (or committed) changes, trading consistency against concurrency and lock overhead. The SQL standard defines four levels. `READ_UNCOMMITTED` is the lowest: a transaction can read rows another transaction has modified but not yet committed (dirty reads), offering maximum concurrency and minimal locking but frequently inconsistent results. `READ_COMMITTED` prevents dirty reads by making a transaction read only committed data; it is the default for many databases including PostgreSQL, Oracle, and MSSQL, and it is typically implemented with statement-level snapshots or shared locks. However, it permits non-repeatable reads — the same row read twice within one transaction can return different values if another transaction commits an update in between — and phantom reads. `REPEATABLE_READ` ensures that once a transaction reads a row, re-reading it returns the same value, because rows read are locked or the snapshot is fixed; but new rows inserted by others (phantoms) can still appear. `SERIALIZABLE` is the strictest level, preventing dirty reads, non-repeatable reads, and phantoms, effectively serializing concurrent transactions — at the price of more locking or snapshot conflicts and lower throughput. In JPA, the isolation level is set per transaction:
    ```java
    @Transactional(isolation = Isolation.REPEATABLE_READ)
    public void recalculateInventory() { ... }
    ```
    JPA does not define its own isolation semantics; it delegates the level to the underlying JDBC connection. Choosing a level is a trade-off: raising isolation reduces anomalies but increases lock contention, deadlocks, and aborts, so most applications stay at the database default and use explicit locking (`@Lock`, `SELECT ... FOR UPDATE`) for the few operations that need stronger guarantees. Also note that isolation protects only *within* a transaction — long transactions at high isolation can seriously degrade a system's concurrency.

32. What is rollback behavior?
    - **Answer:** Rollback behavior determines which exceptions cause a transaction to roll back versus commit. The Spring default is intentionally asymmetrical: the transaction rolls back on **unchecked** exceptions — subclasses of `RuntimeException` and `Error` — and commits on **checked** exceptions. This convention treats runtime exceptions as unexpected bugs (hence abort), and checked exceptions as expected business outcomes where the work should usually be preserved. This surprises many developers, so the default is worth stating explicitly: a method that catches nothing and throws `SQLException` (checked) will still commit its partial work. The behavior is customized with attributes on `@Transactional`: `rollbackFor = SomeCheckedException.class` (or `rollbackForClassName`) forces a rollback when that exception (or its subclass) propagates; `noRollbackFor = ...` declares exceptions that must *not* roll back, even if they are runtime exceptions. Example:
    ```java
    @Transactional(rollbackFor = InsufficientStockException.class)
    public void reserveStock() { ... }

    @Transactional(noRollbackFor = NoResultException.class, rollbackFor = Exception.class)
    public void transfer() { ... }
    ```
    Multiple values can be supplied in arrays. It is also worth understanding `RollbackException`: with JPA, an exception may mark the transaction rollback-only internally (e.g., `OptimisticLockException`, `ConstraintViolationException`), in which case the eventual commit throws `RollbackException` and the changes are discarded — sometimes after the method appeared to succeed. When a rollback happens, the JPA persistence context is cleared, so managed entities hold stale data afterwards. Best practice is to declare rollback rules at the method or class level, avoid swallowing exceptions that should abort the unit of work, and remember that the exception must propagate out of the transactional method for the interceptor to see it — catching it inside the method turns the abort into a commit.

33. Why does self-invocation break `@Transactional`?
    - **Answer:** Self-invocation breaks `@Transactional` because Spring enforces transactions through an AOP proxy, and a call from within the same class never passes through that proxy. When Spring wraps a bean, external callers hold a reference to the proxy, which intercepts the method, starts the transaction, invokes the real method, and commits or rolls back. But when method `a()` inside the class calls `this.b()` (where `b` is annotated `@Transactional`), the call is a plain Java method call on `this` — the actual object — so the proxy interceptor is never invoked and no transaction is created for `b`. This silently loses the transaction, and worse, it fails without any error, so the code appears correct. The same problem applies to other proxy-based features like `@Cacheable`, `@Async`, and `@Retryable`. Solutions: (1) move the transactional method into a separate Spring bean and call it through the injected reference; (2) inject the proxy into itself — `@Autowired @Lazy private OrderService self;` and call `self.b()`; (3) use programmatic transactions with `TransactionTemplate` when the method must stay internal; or (4) for simple cases, remove the annotation from the inner method if the outer method is already transactional and the inner logic should join it. The JDK-dynamic-proxy vs CGLIB distinction matters here: JDK proxies only intercept interface methods, so a concrete class relying on JDK proxy would also lose transactions for non-interface public methods — Spring Boot defaults to CGLIB proxies, which avoids that specific gap but still cannot intercept self-calls. Debugging this class of bug is tricky because nothing fails loudly; the transaction simply never opens, so the most reliable detection is enabling transaction logging and verifying that the expected transaction is created for the call in question. This is one of the most common interview and production pitfalls with Spring transactions, and the correct mental model is "transactions are only applied when the call enters the bean from outside."

34. What is optimistic locking?
    - **Answer:** Optimistic locking assumes that concurrent conflicts are rare, so instead of locking rows at read time, it detects conflicts at commit time. Each entity carries a version attribute (a number, timestamp, or UUID); when a transaction loads an entity, it reads the version. At flush/commit, the `UPDATE` statement includes `WHERE id = ? AND version = ?`. If another transaction committed a change in between, the version no longer matches, zero rows are updated, and the provider throws an `OptimisticLockException` (Hibernate: `StaleObjectStateException`). This prevents lost updates — the classic scenario where two users read the same row, both modify different fields, and the last writer silently overwrites the first. JPA enables it simply:
    ```java
    @Entity
    public class Account {
        @Id
        private Long id;
        @Version
        private long version;
        private BigDecimal balance;
    }
    ```
    The advantages are significant: no database locks are held during the transaction, so read-heavy systems keep high concurrency, and the approach works in any database. The cost is that the failure surfaces only at commit time, so the application must handle `OptimisticLockException` — typically by retrying the whole transaction, reloading the entity, or informing the user that the data changed. Version increments also affect performance in subtle ways: every update bumps the version column even if only one field changed, and with `@Version` on a `Long` the JVM-level update is fast, but concurrent writers on the same row will cause frequent conflicts and retries in hot paths. Optimistic locking is the recommended default for most web applications because it is simple and non-blocking; it pairs with `isolation = READ_COMMITTED`, since conflicts are handled by the version check rather than row locks. When using a detached entity flow, the version must travel with the entity to `merge()`, or the conflict detection is lost.

35. What is pessimistic locking?
    - **Answer:** Pessimistic locking prevents conflicts by acquiring a database lock on the row (or rows) at read time and holding it until the transaction commits or rolls back, blocking other transactions from modifying (and depending on the lock type, reading) the data. JPA exposes it through `LockModeType` in `@Lock`, `EntityManager.lock()`, or `LockModeType` in `Query` objects. The main modes are `PESSIMISTIC_READ` (a shared lock — other transactions may also read, but none may write) and `PESSIMISTIC_WRITE` (an exclusive lock — no other transaction may read or write, and they will block until the lock is released). Providers translate these into database SQL, typically `SELECT ... FOR UPDATE` (or `FOR SHARE` for read locks):
    ```java
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select a from Account a where a.id = :id")
    Optional<Account> findByIdForUpdate(@Param("id") Long id);
    ```
    Also relevant are `PESSIMISTIC_FORCE_INCREMENT`, which locks and bumps the version to force optimistic conflicts elsewhere, and `LockModeType.OPTIMISTIC`/`OPTIMISTIC_FORCE_INCREMENT` for version-based locks. The strength of pessimistic locking is *predictable* failure: the conflict is resolved up front, because the second transaction simply waits rather than failing at the end. The weaknesses are blocking, lock waiting, deadlock risk (especially when locks are acquired in different orders), and reduced concurrency — every reader/writer touches the locked row sequentially. Lock scope is tied to the transaction: the lock is released at commit/rollback, not at method return, so a long transaction holding a pessimistic lock can block the whole table. Pessimistic locking is appropriate when contention is genuinely high (e.g., a shared counter or a reservation system) or when the read-modify-write cycle is too long for optimistic retries to be practical. It is also worth noting the distinction between row locks at the database level and application-level `synchronized`/distributed locks — pessimistic locking in JPA is always database-backed.

36. What is `@Version`?
    - **Answer:** `@Version` is a JPA annotation that marks a field as the entity's version attribute, enabling optimistic locking with no extra database structures — just an extra column, usually named `version` and mapped to an integer or long:
    ```java
    @Entity
    @Table(name = "documents")
    public class Document {
        @Id
        private Long id;
        @Version
        private Long version;
        private String title;
        private String content;
    }
    ```
    The provider manages the field automatically: on the initial `INSERT`, the version is set to zero (or the initial value); on every successful `UPDATE`, it is incremented; and every update statement includes the previous version value in its `WHERE` clause. If the row's actual version differs from the value the transaction read, the update affects zero rows, the provider throws `OptimisticLockException` (Hibernate throws `StaleObjectStateException`, which is mapped to it), and the transaction is marked rollback-only. The valid field types are numeric primitives/wrappers, `Timestamp`, or `Instant` (and UUID in some providers); Hibernate also supports `@OptimisticLocking(type = OptimisticLockType.ALL)` to use all fields for conflict detection instead of a version column. Important caveats: `@Version` fields must not be set manually by application code; they should never be exposed in equals/hashCode; and in a detached-entity flow, the version must be present on the detached object so `merge()` can detect concurrent changes — otherwise the optimistic guarantee silently disappears.     Also note that a failed optimistic update with Hibernate marks the whole persistence context rollback-only, so the exception cannot simply be caught and another entity saved in the same transaction. On the concurrency side, optimistic locking never holds database locks, so read throughput is unaffected, but high-contention rows can experience frequent conflicts that force retries — the trade-off to evaluate when many writers update the same record. `@Version` is the correct, standard way to prevent lost updates, and every mutable entity in a concurrent application should typically have one.

37. What are cascade types?
    - **Answer:** Cascade types define which entity-manager operations on a parent entity automatically propagate to its associated child entities. JPA defines the following: `PERSIST` (persisting the parent also persists new children), `MERGE` (merging the parent also merges children), `REMOVE` (removing the parent also removes children), `REFRESH` (refreshing the parent re-reads children from the database), `DETACH` (detaching the parent also detaches children), and `ALL`, which is shorthand for all of the above. Cascades are configured on the association annotation:
    ```java
    @OneToMany(mappedBy = "order", cascade = CascadeType.PERSIST, orphanRemoval = true)
    private List<OrderItem> items;
    ```
    The key mental model is that cascades apply to *lifecycle operations*, not to queries: setting `cascade = PERSIST` does not affect how children are fetched or joined. Each cascade type is independent, so `CascadeType.ALL` is often overkill. A common mistake is using `CascadeType.ALL` on a `@ManyToMany` or a `@ManyToOne`; deleting a child referenced by others would try to delete rows still in use, and cascade-deleting an owner can surprise. `CascadeType.REMOVE` on `@OneToMany` is often replaced by `orphanRemoval = true`, which deletes a child as soon as it is removed from the parent's collection (they are not the same thing — see the orphan removal answer). There is also a cost: cascading `PERSIST`/`MERGE` over a deep object graph can pull many entities into the persistence context and cause wide flush, so developers should cascade only as far as the domain genuinely needs. Finally, `REMOVE` and `DETACH` on bidirectional associations require the inverse side to be maintained consistently — when a parent is removed, its children must be de-referenced or orphan-removed, otherwise dangling references or constraint violations occur.

38. What is orphan removal?
    - **Answer:** Orphan removal (`orphanRemoval = true`) makes the owning side's collection the source of truth for child lifecycle: when a child is removed from the parent's collection, JPA automatically issues a `DELETE` for that child, because it treats the child as having no owner ("orphaned"):
    ```java
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items;
    ```
    It is important to contrast this with `cascade = CascadeType.REMOVE`. Cascade `REMOVE` deletes children when the *parent* is deleted; orphan removal deletes children when they are *removed from the collection* while the parent still exists — so replacing `order.getItems().remove(item)` deletes the item from the database automatically. A further difference is semantics of the DELETE timing: both issue the delete at flush/commit, but orphan removal generates a `DELETE FROM order_items WHERE id = ?` for each removed child, while cascade remove on parent deletion deletes children via the FK cascade or individual deletes.     Requirements and pitfalls: orphan removal applies only to `@OneToMany`/`@OneToOne` (a single-valued association that becomes null also counts as orphan removal); it cannot be used with `@ManyToMany` because a many-to-many child legitimately has many owners. A common bug is to remove an item from the collection only on one side of a bidirectional association — the collection that is not the `mappedBy` owner is not the driver for orphan removal, so the deletion silently does not happen unless the owning side is updated too. The timing is also worth noting: orphan removal issues the `DELETE` at flush/commit, so the row is not removed the moment the collection is mutated. Orphan removal is the idiomatic way to implement "delete a child when it is dropped from a parent's list" semantics, especially for aggregates in DDD-style designs, and it should usually be combined with `cascade = ALL` or at least `PERSIST` so new children are saved along with the parent.

39. Difference between `save()` and `saveAndFlush()`.
    - **Answer:** `save()` (on `JpaRepository`) persists the entity and returns it, but it does not synchronously write to the database — the INSERT or UPDATE is queued in the persistence context and flushed later, typically at transaction commit (or when a query needs the data). `saveAndFlush()` calls `save()` and then immediately calls `flush()`, forcing the pending SQL statements to the database right away. The practical differences: after `save()`, the entity's generated ID may not be assigned until flush; after `saveAndFlush()`, the ID is immediately available and the row exists in the database. Why use `saveAndFlush()`? (1) when the next step needs the database state — e.g., calling a stored procedure that reads the just-inserted row, or a trigger that populates a column; (2) when a subsequent query must include the change (Hibernate flushes automatically before queries in `FlushModeType.AUTO`, so this is usually handled, but not always); (3) when catching database constraint violations early, at the known call site rather than at commit. Conversely, `save()` is preferable for performance because it allows Hibernate to batch several INSERTs/UPDATEs into one round-trip at commit. There is also a subtle interaction with ID generation: with `GenerationType.IDENTITY`, the INSERT runs immediately anyway (the ID must come from the database), so `saveAndFlush()` has no extra cost; with `SEQUENCE`, `saveAndFlush()` defeats batching for that statement. Another nuance is that `save()` in Spring Data decides between `persist()` (new entity, ID null) and `merge()` (detached, ID set), while `saveAndFlush()` does the same then flushes. For bulk operations, `saveAll()` batches more efficiently than repeated `saveAndFlush()` calls.

40. What is batch insert?
    - **Answer:** A batch insert groups many INSERT statements into a single JDBC round-trip, dramatically reducing network and database overhead for bulk loading. In Hibernate it is configured with `hibernate.jdbc.batch_size` and, for correct grouping, `hibernate.order_inserts=true` (and `hibernate.order_updates=true` for updates):
    ```yaml
    spring:
      jpa:
        properties:
          hibernate:
            jdbc.batch_size: 50
            order_inserts: true
    ```
    With a batch size of 50, inserting 10,000 entities generates roughly 200 batched round-trips instead of 10,000 individual ones — often a 5–20x throughput improvement. Critical constraints apply. First, the primary key strategy: with `GenerationType.IDENTITY`, Hibernate must issue each INSERT immediately to obtain the generated ID, which silently disables batching; `SEQUENCE` (with pre-fetchable allocationSize) or `TABLE` preserves batching. Second, statements are only batched when they are identical in structure, so inserts must not be interleaved with other operations and `order_inserts=true` is needed when entities are inserted in non-consecutive order. Third, the JDBC driver must support batch execution — for MySQL, `rewriteBatchedStatements=true` is required to actually rewrite multiple inserts into a single `VALUES` statement; PostgreSQL batches natively. Versioned entities with `@Version` batch fine, but the version increment adds a column to each statement. EntityManager-level tips: build a loop that calls `em.persist(entity)` every iteration, but periodically call `em.flush()` and `em.clear()` every `batch_size` entities to avoid unbounded growth of the persistence context (which otherwise consumes memory and slows dirty checking). For very large imports, batch inserts via JPA can still be slower than a `JdbcTemplate`/SQL `INSERT INTO ... VALUES (...), (...), (...)` or `LOAD DATA`, because Hibernate tracks each entity in the persistence context even when batched — a decision to make when data volumes reach hundreds of thousands of rows.

41. How do you improve JPA performance?
    - **Answer:** JPA performance work typically follows a few high-impact levers. First, eliminate N+1 queries, the most common cause of slow JPA applications, using `JOIN FETCH`, `@EntityGraph`, `@BatchSize`, or subselect fetching, and verify the fix with `hibernate.generate_statistics` or SQL logging. Second, enable batch inserts/updates (`hibernate.jdbc.batch_size`, `order_inserts`, `order_updates`) and prefer `SEQUENCE` over `IDENTITY` when bulk-loading. Third, avoid loading full entities when only a few columns are needed — use interface projections or DTO constructor expressions in JPQL so the provider selects only required columns. Fourth, tune lazy loading globally: keep mappings lazy (`@OneToMany`/`@ManyToMany`), use `fetch` joins only where needed, and consider `@BatchSize` on hot collections. Fifth, use the second-level cache (or an application-level cache) for genuinely read-heavy, rarely mutated reference data, with a suitable concurrency strategy. Sixth, make transactions short and `readOnly` where appropriate so Hibernate skips dirty checking and flushes. Seventh, keep an eye on the persistence context size: `flush()` + `clear()` periodically in long-running loops so memory stays bounded. Eighth, for expensive reporting, fall back to `JdbcTemplate` or native SQL/stored procedures that push set-based work into the database. Ninth, profile with `spring.jpa.show-sql`, Hibernate statistics, and `spring.jpa.properties.hibernate.use_sql_comments` to map each SQL statement back to its source. Finally, remember that indexes are the ground truth for any database — the best Hibernate configuration cannot fix a missing index on a frequently filtered column; inspect the generated SQL and execution plans. Each application is different, so the correct order is: measure (statistics/SQL logs), fix the worst queries (N+1, missing projections), then tune batching and caching.

42. When should you use JDBC instead of JPA?
    - **Answer:** JDBC (directly, or through `JdbcTemplate`) is preferable when the overhead of the JPA entity model costs more than it saves. Typical cases: (1) bulk DML — inserting or updating hundreds of thousands of rows, where JPA's per-entity persistence-context tracking and dirty checking add memory and CPU; (2) complex set-based reporting with window functions, CTEs, pivots, and heavy aggregations that are awkward or impossible in JPQL; (3) reading data that maps poorly to entities, such as flattened star-schema results, where JDBC row mapping to DTOs is direct; (4) executing stored procedures with multiple result sets or output parameters; (5) dynamic SQL built at runtime where parameterization and conditional logic are easier in raw SQL; and (6) hot paths where the difference between one well-tuned SQL statement and a generated one matters at high throughput. The classic example is a nightly batch: loading entities, mutating them, and flushing thousands of rows through Hibernate is far slower than a single `UPDATE ... WHERE ...` or `INSERT ... SELECT`. `JdbcTemplate` is the sweet spot — it keeps Spring's exception translation, connection management, and `@Transactional` integration while removing the ORM layer. A common hybrid pattern is "JPA for the interactive CRUD paths, JDBC for the reporting/batch paths." It is also reasonable to use JDBC when the team lacks JPA expertise or when the schema is legacy and irregular. Conversely, stick with JPA when the codebase is heavily entity-based, the queries are standard, or the second-level features (caching, optimistic locking, relationship management) are being used — the maintenance cost of hand-written SQL and result mapping grows with the number of queries.

43. When should you use stored procedures?
    - **Answer:** Stored procedures are appropriate when significant logic belongs in the database rather than the application. Concrete cases: complex reporting queries that combine many joins, aggregations, window functions, and conditional branching, where the whole pipeline can run server-side with one round-trip; long-running batch jobs that process millions of rows and should not stream data back to the application; operations that must execute atomically inside a database-internal transaction with exclusive access; and legacy systems where business-critical logic already lives in the database and must be reused. They also shine when the database engine can optimize set-based operations far better than an application loop — e.g., hierarchical queries, recursion, or graph traversals. Additional benefits: reduced network round-trips (one call instead of many), encapsulation of SQL so application code stays small, centralized permissions (`GRANT EXECUTE`), and the ability to tune and redeploy SQL without redeploying the application. The trade-offs are significant too: stored procedures are hard to version-control and unit-test, they tie the application to a specific database (portability is lost), debugging requires database tooling, and combining procedural logic with frameworks like JPA's optimistic locking requires discipline. In practice, most applications use stored procedures sparingly — for a handful of complex reports or batch jobs — while the interactive paths remain in JPA/JPQL. A modern alternative to consider is moving the same logic into the application with streaming (e.g., `JdbcTemplate` + pagination) or into a data warehouse, reserving stored procedures for cases where the logic is inherently database-bound. Before committing to a stored procedure, it is worth asking whether a well-indexed query with application-side aggregation would meet the requirement, since procedures remove the flexibility of adding filters or projections from the API layer. In practice, most applications use stored procedures sparingly — for a handful of complex reports or batch jobs — while the interactive paths remain in JPA/JPQL.

44. How do you call stored procedures from Spring?
    - **Answer:** Spring offers several ways to invoke stored procedures, from most declarative to most manual. The simplest is the `@Procedure` annotation on a repository method:
    ```java
    public interface ReportRepository extends JpaRepository<Report, Long> {
        @Procedure("sp_generate_report")
        List<ReportRow> generate(@Param("startDate") LocalDate start, @Param("endDate") LocalDate end);
    }
    ```
    Spring Data derives the `EntityManager` call, binds named parameters, and maps the result. For more control, use `EntityManager.createStoredProcedureQuery(...)` directly: register parameters with `registerStoredProcedureParameter(1, String.class, ParameterMode.IN)`, `ParameterMode.OUT` for outputs, and call `getResultList()` or `getOutputParameterValue(...)`. `StoredProcedureQuery` also supports `executeUpdate()` for non-SELECT procedures. The lowest-level but most flexible option is `JdbcTemplate` or `SimpleJdbcCall`, which handles result sets, output parameters, and even multiple result sets with `ResultSetExtractor`:
    ```java
    jdbcTemplate.query(
        callStatement, 
        ps -> { ps.setInt(1, partnerId); },
        rs -> { /* map multiple result sets */ }
    );
    ```
    Considerations: `@Procedure` expects the procedure name to match the method name or be given explicitly; it handles a single result set cleanly and is limited for OUT cursors and multiple result sets — use `EntityManager` or `JdbcTemplate` there. For procedures that return a cursor, PostgreSQL requires a `refcursor` parameter registered as OUT. Parameter order and names must match the database procedure, and result mapping is done by column name, not by JPA property names. When combining stored procedures with JPA transactions, the procedure's own internal transaction semantics apply, and it is common to run DDL-like or heavy procedures with `@Transactional(readOnly = false)`. The choice among the three approaches is: `@Procedure` for simple single-result-set calls, `StoredProcedureQuery` for output parameters and moderate control, `JdbcTemplate`/`SimpleJdbcCall` for complex, multi-result-set, or performance-sensitive calls.

45. How do you debug slow JPA queries?
    - **Answer:** Debugging slow JPA queries is a systematic process of making the SQL visible, mapping it to the code, and fixing the root cause. First, enable SQL logging and statistics: `spring.jpa.show-sql=true` prints each statement, `spring.jpa.properties.hibernate.format_sql=true` prettifies it, and `spring.jpa.properties.hibernate.use_sql_comments=true` prepends a comment showing which repository/entity generated the query. `spring.jpa.properties.hibernate.generate_statistics=true` outputs aggregate stats (query count, cache hits/misses, statement counts, flush time) to pinpoint overall behavior such as N+1 or excessive flushes. Second, count the queries: if a single operation triggers hundreds of similar SELECTs, it is an N+1 problem — fix with `JOIN FETCH`/`@EntityGraph`/`@BatchSize`. Third, copy a slow statement into the database's execution plan tool (`EXPLAIN` on PostgreSQL/MySQL, "Display Estimated Execution Plan" on MSSQL) to identify missing indexes, sequential scans, or expensive joins; the execution plan is the ground truth. Fourth, check Hibernate-side overhead: a query may be fast but the persistence context large (flush of many dirty entities before the query, or the query materializing thousands of entities), so measure entity count and the time spent flushing versus querying. Fifth, look at the transaction scope — a `@Transactional` method doing many queries sequentially may be correct in isolation but slow as a whole; consider batching, `readOnly = true`, or splitting. Sixth, verify index usage on filter/join/order-by columns and create composite indexes that match the query predicates. Finally, use an APM or SQL trace to see the query in production context — connection pool wait times, lock waits, and concurrent load. The output of this process should be a concrete change: an added index, a fetch join, a projection, or a move to JDBC — always re-measure after the change.

46. Why do we use the `@Transactional` annotation?
    - **Answer:** `@Transactional` is used to give a method a well-defined transaction boundary, so that all database operations inside it succeed or fail together. Without it, each repository call commits on its own, and a use case that updates several tables in a loop could leave the database half-changed if an error occurs halfway. Applying `@Transactional` makes Spring begin a transaction before the method, run the method, then commit on success or roll back on failure, giving atomicity, and it also scopes the JPA persistence context to the method so that entities loaded inside are managed, lazy loading works, and dirty checking flushes once at commit. It is the declarative alternative to writing `beginTransaction()/commit()/rollback()` boilerplate in every method. Beyond the basic boundary, the annotation carries configuration: `propagation` decides whether to join an existing transaction or create a new one; `isolation` raises or lowers the isolation level; `readOnly = true` is an optimization hint that lets Hibernate skip dirty checking and some flushes; `timeout` aborts long-running transactions; and `rollbackFor`/`noRollbackFor` control which exceptions abort the transaction. It belongs on the service/application layer rather than repositories, because a transactional unit of work is a business-level concept that often spans multiple repositories. The known limitations must be understood: the annotation only works on public methods invoked through the Spring proxy, so self-invocation and private/static methods silently lose the transaction (see the next questions). Example:
    ```java
    @Service
    public class OrderService {
        @Transactional
        public void placeOrder(OrderCommand cmd) {
            orderRepository.save(order);
            inventoryRepository.reserve(lineItems);
            auditRepository.save(audit);   // all-or-nothing
        }
    }
    ```
    In short, `@Transactional` is the primary tool for keeping multi-step writes atomic and for making JPA's managed-entity behavior predictable within a unit of work.

47. Can `@Transactional` be applied to private or static methods?
    - **Answer:** No — `@Transactional` has no effect on private or static methods. The reason is mechanical: Spring implements transactions with an AOP proxy that wraps the bean, and the proxy can only intercept calls that enter the bean from outside and go through a public method. A private method is invoked directly on `this` within the class, never through the proxy, so the interceptor never runs and no transaction is created; there is no error, which makes it a silent bug. Static methods are worse: they do not belong to an instance at all, so no instance proxy can intercept them — calling a static method annotated `@Transactional` simply runs it without any transaction, and at startup Spring does not even apply the annotation to static methods in most configurations. Spring's documentation states that only public methods are supported (and with CGLIB proxying, only non-final methods). The practical guidance: put transactional behavior in a public method of a Spring bean, and call it from another bean so the call passes through the proxy. If a private or static helper must do transactional work, options are: move the logic into a separate transactional bean and inject it; use programmatic transactions with `TransactionTemplate` (which works from anywhere); or — for the self-invocation flavor of the same problem — inject the proxy into itself with `@Lazy` self-reference. The same proxy limitation applies to other Spring annotations implemented via AOP, such as `@Async`, `@Cacheable`, and `@Retryable`, so this is a general pattern to internalize.

48. What types of exceptions trigger transaction rollback with `@Transactional`?
    - **Answer:** By default, Spring rolls back the transaction when an **unchecked** exception propagates out of the method — that is, any subclass of `RuntimeException` and any `Error` — and it *commits* when a checked exception (`Exception` subclass other than `RuntimeException`) propagates. So a method throwing `NullPointerException`, `IllegalStateException`, or a Spring `DataAccessException` triggers rollback, while one throwing a checked `SQLException` or a custom `BusinessException extends Exception` commits its partial work. This asymmetry is deliberate: runtime exceptions indicate programming errors or unexpected conditions where the partial work is unreliable, while checked exceptions often model expected business outcomes (e.g., "entity not found") where the transaction should normally persist. To override the default, use `rollbackFor` (and `rollbackForClassName`):
    ```java
    @Transactional(rollbackFor = {BusinessException.class, IOException.class})
    public void submit() { ... }

    @Transactional(noRollbackFor = NotModifiedException.class)
    public void sync() { ... }
    ```
    `rollbackFor` can be a single class or an array, and the check includes subclasses. `noRollbackFor` (and `noRollbackForClassName`) excludes matching exceptions from rollback even when they are runtime exceptions. Two subtle behaviors are worth knowing. First, the exception must *propagate* out of the transactional method for the interceptor to observe it — catching it inside the method causes a commit. Second, with JPA, certain failures mark the persistence context rollback-only internally (e.g., `OptimisticLockException`, `ConstraintViolationException`); even if the method catches them, the eventual commit throws `RollbackException` and discards changes — a source of confusing "commit failed" errors. The general guidance: default to the standard behavior, add `rollbackFor` only where a checked exception genuinely represents a failed unit of work, and never swallow exceptions that must abort the transaction.
