8. How did you reduce stored procedure execution time from 5 hours to under 12 minutes?
   - **Answer:** A strong answer should walk through the systematic diagnosis: enable `SET STATISTICS TIME ON`, capture the actual execution plan, and identify the highest-cost operators. The key concepts interviewers look for are the difference between a clustered index seek and a scan, how statistics drive cardinality estimation and plan choice, and the effect of non-SARGable predicates that force full scans. A classic culprit is an implicit type conversion or a function applied to a column, which prevents the optimizer from seeking on an index. Replacing row-by-row cursor logic with set-based operations is another major lever, because SQL Server's engine is built for set operations rather than iteration. Parameter sniffing should also be mentioned: a plan cached from one parameter value can perform badly for another, and the fix is often `OPTION (RECOMPILE)` or plan guide adjustment. This combination of changes is what explains a 5-hour to 12-minute improvement — one fixed scan eliminates millions of page reads, and removing a cursor eliminates hundreds of round trips. Each change should be measured independently and verified for correctness before moving to the next bottleneck.
9. What kind of execution plan issues did you identify?
   - **Answer:** A strong answer should name the recurring plan problems by their technical terms: table scans caused by implicit conversions, key lookups on non-covering indexes, and nested loop joins used on large inputs where a hash join would be appropriate. The candidate should be able to explain why each is expensive: a scan reads every page of the index, a key lookup adds a random page read for each returned row, and a nested loop join multiplies the cost of the outer input by the inner input. Implicit conversions are particularly insidious because the optimizer adds a warning triangle in the plan but still produces a scan when a `VARCHAR` column is compared to an `NVARCHAR` parameter. The answer should also cover the discipline of comparing estimated rows against actual rows, since gross underestimates point to stale statistics that skew plan choice. Identifying the exact operator and its cause is the first step, and choosing the targeted fix is the second. Interviewers listen for evidence that the candidate reads plans diagnostically rather than just skimming them.
10. What kind of indexes did you create or modify?
    - **Answer:** A strong answer should distinguish index types by their purpose: covering indexes that satisfy a query entirely from the index, composite indexes whose key column order follows the query's filter pattern, and filtered indexes for queries that always target a narrow subset. The order of key columns matters because SQL Server can seek on leading columns only; a filter on `Date` first and `Status` second requires an index that leads with `Date`. Adding payload columns through `INCLUDE` avoids bloating the index key while still making the index covering. The candidate should describe verifying success by checking the execution plan before and after — key lookups and scans should disappear from the plan. Over-indexing is a real risk worth mentioning, since every extra index adds write overhead and storage cost. A strong answer shows that indexes are designed from the query's access pattern rather than added blindly from the missing-index suggestions.
11. How did you validate that optimized stored procedures still returned correct results?
    - **Answer:** A strong answer should describe a side-by-side validation harness that runs the old and new procedures against the same dataset and compares outputs at multiple levels. Row counts, checksums over each result table, and aggregate values like sum, min, and max catch most discrepancies, and row-level comparisons isolate any that remain. `CHECKSUM_AGG(BINARY_CHECKSUM(*))` provides a compact fingerprint of an entire result set that can be compared between runs. Edge cases deserve explicit mention — empty inputs, duplicate rows, and NULLs in join keys — because optimizations often break under boundary conditions that happy-path data never exposes. Testing on a production-sized dataset is essential, since plan choices and performance only manifest at scale. Interviewers view this rigor as the trait that lets an engineer optimize aggressively without risking business correctness.

41. How did you handle delayed IoT messages?
    - **Answer:** A strong answer should explain the concept of event time versus ingestion time. A gateway that loses connectivity buffers readings and reconnects later, sending old messages with their original sensor timestamps. The solution is to store both timestamps — `sensor_time` for when the reading happened and `ingestion_time` for when it was received — and to write data by event time so it lands in the correct time bucket. Clock sync matters because mislabeled event times corrupt the time series; NTP sync and a clock-skew flag provide a data-quality signal. Interviewers look for an understanding that out-of-order data is inevitable in distributed systems and must be designed for. A strong answer shows the pipeline treating time as data rather than assuming arrival order.
42. How did you handle duplicate IoT messages?
    - **Answer:** A strong answer should explain why duplicates happen: MQTT QoS 1 guarantees at-least-once delivery, meaning a retransmission without acknowledgment produces the same message twice, and Lambda's delivery to Kafka can also be at-least-once. The solution is idempotency at the consumer using a unique message ID generated by the gateway. The consumer checks a Redis set keyed by that ID; if present, the message is skipped, otherwise it is added with a TTL and processed. Redis is fast enough for the write path, whereas a primary-key check against a relational database would add latency at high throughput. Interviewers look for the distinction between at-least-once delivery and exactly-once processing, which requires deduplication. A strong answer shows how the protocol's guarantee is upgraded at the application layer.
