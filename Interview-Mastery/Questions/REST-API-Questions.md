## Answers

1. What is REST?
   - **Answer:** REST (Representational State Transfer) is an architectural style for designing networked applications, introduced by Roy Fielding, that relies on stateless, cacheable client-server communication over HTTP. A REST API exposes *resources* — concepts such as users, orders, or sensors — identified by uniform resource identifiers (URIs) and manipulated using the standard HTTP methods. For example, `GET /api/sensors/{id}/readings` fetches time-series data for a specific sensor, while `POST /api/sensors` creates a new one. REST is not a protocol or a standard but a set of constraints; an API is more or less RESTful depending on how faithfully it follows them. The key benefits are simplicity, scalability through statelessness, and reuse of well-understood HTTP infrastructure (caching, proxies, load balancers). Resources are representations: the same logical resource can be served as JSON, XML, or any other format through content negotiation. REST emphasizes a uniform interface, meaning all resources are accessed through the same set of methods and conventions rather than each endpoint having bespoke operations. It contrasts with RPC-style designs where endpoints name actions rather than resources. Understanding REST means understanding that the HTTP semantics (methods, status codes, headers) carry real meaning and should not be treated as a transport detail. In practice, most production APIs claim to be RESTful but implement a pragmatic subset of the full constraints, typically skipping HATEOAS.

2. What are REST constraints?
   - **Answer:** REST is defined by six architectural constraints. (1) Client-server separation: the client and server evolve independently, with the client only knowing the resource URIs. (2) Statelessness: every request must carry all information needed to process it, with no server-side session state; this makes any server instance able to handle any request, enabling horizontal scaling. (3) Cacheability: responses must explicitly indicate whether they are cacheable (via headers like `Cache-Control` and `ETag`) so clients and intermediaries can reuse them. (4) Uniform interface: a consistent, resource-based set of operations — resource identification in requests, resource representation manipulation, self-descriptive messages, and hypermedia as the engine of application state (HATEOAS). (5) Layered system: clients cannot tell whether they are talking to the origin server or an intermediary such as a gateway, load balancer, or cache, which improves scalability and security. (6) Code on demand (optional): servers may extend client functionality by sending executable code, for example returning a JavaScript snippet. Of these, statelessness has the biggest impact on scaling because it removes session affinity requirements. Cacheability reduces latency and load but requires careful header design. The uniform interface is often the hardest constraint to enforce consistently, which is why many APIs implement it only partially.

3. Difference between REST and SOAP.
   - **Answer:** REST is an architectural style using HTTP methods over resources, usually with JSON payloads, while SOAP is a heavyweight XML-based messaging protocol with strict envelopes, schemas, and predefined operation contracts. SOAP relies on WSDL (Web Services Description Language) to describe services, making it highly standardized and tool-friendly for enterprise integrations. SOAP provides built-in error handling via SOAP faults, transactional support, and WS-Security for end-to-end encryption and signing — features that matter in banking, payments, and telecommunications. REST is simpler, lighter-weight, and human-readable, and it works naturally with browsers, mobile clients, and web infrastructure such as caching proxies and CDNs. REST payloads are typically smaller because JSON omits the envelope structure, reducing bandwidth and parsing overhead. REST is stateless by design, whereas SOAP can maintain state and supports complex workflows like WS-AtomicTransaction. REST has no formal contract unless supplemented with OpenAPI, whereas SOAP's WSDL is machine-verifiable at compile time. For greenfield web and mobile APIs, REST is nearly always the pragmatic choice; SOAP remains relevant only in legacy enterprise environments with strict compliance requirements. The essential trade-off is between SOAP's rigid, self-validating contracts and REST's flexibility, simplicity, and web-native design.

4. Difference between REST and GraphQL.
   - **Answer:** REST exposes fixed resources with predetermined response shapes per endpoint, while GraphQL is a query language that lets clients request exactly the fields and relationships they need in a single round trip. With REST, adding a new field to the client view may require a new endpoint or a version bump; with GraphQL, the client simply changes its query. GraphQL has a single endpoint (typically `/graphql`) where every operation is either a `query` (read), `mutation` (write), or `subscription` (real-time push). REST benefits from per-URL caching — since each resource has a unique URI, HTTP caches and CDNs can cache it directly; GraphQL makes response caching harder because every POST body is different. GraphQL solves the over-fetching (receiving too many fields) and under-fetching (needing multiple requests) problems common in mobile clients. However, GraphQL shifts complexity to the server: query parsing, resolver efficiency, and protecting against deeply nested or expensive queries (via depth limits or query cost analysis). REST is easier to monitor and debug because each URL is semantically meaningful in logs and metrics. REST also aligns naturally with HTTP status codes, whereas GraphQL returns 200 even when a field resolver fails and reports errors inside the response body. Many teams choose REST for simple, well-known resources and GraphQL for highly connected, client-driven data needs; the two can coexist. The core decision is whether the API should dictate the data shape (REST) or the client should (GraphQL).

5. What are HTTP methods?
   - **Answer:** HTTP defines a set of methods that express the intended action against a resource. The most important are GET (retrieve a representation without side effects), POST (create a resource or trigger processing), PUT (replace a resource in full), PATCH (apply a partial modification), DELETE (remove a resource), HEAD (return headers only, as with GET), and OPTIONS (discover supported methods, used by CORS preflight). GET, HEAD, and OPTIONS are *safe* — they must not change server state — which lets caches and prefetching use them freely. Idempotent methods (GET, PUT, DELETE, HEAD, OPTIONS) can be repeated safely, whereas POST is non-idempotent and typically creates a new resource each call. Methods should be used semantically: retrieving data with POST, or performing a destructive action with GET, confuses clients, proxies, and caching layers. For example, `GET /api/orders/42` reads order 42, while `DELETE /api/orders/42` removes it and returns 204 No Content on success. A `PUT /api/orders/42` replaces the entire order with the submitted representation, and `PATCH /api/orders/42` sends only the changed fields, such as `{"status": "shipped"}`. Using the correct method matters because intermediaries, firewalls, and API gateways may react differently to each. The semantic table — safe, idempotent, cacheable — is what lets HTTP infrastructure improve reliability without touching application code.

6. Difference between PUT and PATCH.
   - **Answer:** PUT replaces the entire resource with the representation sent in the request body, while PATCH applies a partial modification to the existing resource. If a resource has fields `{name, status, address}` and only the `status` should change, PATCH with `{"status": "active"}` is appropriate, whereas PUT requires the client to submit the complete, up-to-date object. PUT is inherently idempotent: sending the same full representation repeatedly converges to the same state. PATCH is only idempotent if the patch operation itself is designed to be (a JSON Patch `replace` on a fixed field is idempotent; an `increment` or `append` operation is not). HTTP semantics also treat PUT as a create-or-replace operation: `PUT /api/customers/7` creates customer 7 if it does not exist and replaces it if it does, so the client owns the identifier. PATCH implies the resource already exists and should return 404 if the target resource is missing, whereas PUT typically returns 201 on creation or 200 on replacement. A common pitfall is using PATCH as a looser PUT and sending entire objects anyway, which defeats the purpose. PATCH bodies are often specified by standards such as JSON Patch (RFC 6902) or JSON Merge Patch (RFC 7396), which define precise merge semantics. The choice between them comes down to payload efficiency versus full-resource semantics: PATCH minimizes bandwidth and avoids race conditions on unrelated fields, but PUT is simpler to reason about and safer for retries.

7. Difference between POST and PUT.
   - **Answer:** POST submits data to be processed, typically creating a new resource at a server-chosen URL, while PUT creates or replaces a resource at a client-specified URL. With `POST /api/customers`, the server assigns the new customer's ID and returns 201 Created with a `Location` header pointing to `GET /api/customers/{id}`. With `PUT /api/customers/42`, the client states that customer 42 should have exactly the submitted representation, and the server either creates or fully replaces it at that address. POST is not idempotent: repeating the same POST creates multiple customers, which is why payment and order endpoints need idempotency keys. PUT is idempotent — the second identical PUT changes nothing. POST is the fallback method for any action that does not fit a clean create/replace/delete model, such as submitting a search or executing an operation. Some teams use `POST /api/customers/{id}` for updates, but this loses idempotency and the semantic clarity that PUT provides. The decision rule is simple: if the client knows the resource's final URL and can supply the full representation, use PUT; if the server must allocate the identifier or process a transient action, use POST. Correctly distinguishing these methods makes API behavior predictable, retryable, and consistent with HTTP semantics.

8. What is idempotency?
   - **Answer:** An operation is idempotent if performing it once produces the same observable result as performing it multiple times. For `PUT /api/orders/42`, sending the same body twice leaves the order in the same state, so retries are harmless. This property is critical for reliability because network failures, timeouts, and client retries are unavoidable, and a retry must not cause duplicate side effects — a double-charged payment or duplicate order is unacceptable. HTTP's safe methods (GET, HEAD, OPTIONS) are trivially idempotent because they change nothing. PUT and DELETE are idempotent by definition: a second DELETE may return 404 instead of 204, but the resulting server state is identical. POST is not idempotent, which is why payment and message-sending APIs implement *idempotency keys*: the client sends a unique key in a header such as `Idempotency-Key: 3f7d...`, and the server stores the key with the response. On retry with the same key, the server returns the stored response instead of reprocessing the request. Idempotency keys are typically stored in a cache or database with a time-to-live window, scoped per client. Idempotency is about *state*, not responses — returning a different status code on a repeated DELETE is allowed as long as the server state is unchanged. Well-designed APIs assume clients will retry and make every mutating operation safe under duplication.

9. Which HTTP methods are idempotent?
   - **Answer:** GET, HEAD, OPTIONS, PUT, and DELETE are idempotent; POST and PATCH are not guaranteed to be. GET is safe (no state change) and therefore trivially idempotent. PUT is idempotent because replacing a resource with the same full representation twice yields the same final state. DELETE is idempotent at the state level: the resource is gone after the first call, and the second call leaves it gone even if it returns 404. POST is non-idempotent because each call typically creates a new resource or triggers a side effect. PATCH is conditionally idempotent — a pure value replacement is idempotent, but an operation like `{"op": "increment"}` is not. When a non-idempotent endpoint (usually POST) must tolerate retries, servers add an idempotency-key mechanism to deduplicate identical requests. HEAD and OPTIONS mirror their GET/other counterparts and are idempotent as well. Understanding this table matters for client logic: a client can safely retry a PUT or DELETE after a timeout, but a POST retry risks duplicates. Caching and HTTP infrastructure also rely on this classification — proxies may safely replay idempotent requests. The practical guideline is to use PUT for create-or-replace, reserve POST for genuinely non-idempotent actions, and add explicit idempotency-key support where POST must be retryable.

10. What are common HTTP status codes?
    - **Answer:** Status codes are grouped by class: 2xx success, 3xx redirection, 4xx client error, and 5xx server error. The most common 2xx codes are 200 OK (successful GET or general success), 201 Created (a resource was created, returned with a `Location` header), 202 Accepted (request accepted for async processing), and 204 No Content (success with an empty body, typical for DELETE). Common 3xx codes include 301 Moved Permanently and 308 Permanent Redirect (resource moved to a new URL). 4xx codes indicate the client did something wrong: 400 Bad Request (malformed request), 401 Unauthorized (missing or invalid credentials), 403 Forbidden (authenticated but not permitted), 404 Not Found (resource absent), 405 Method Not Allowed (endpoint exists but method unsupported), 409 Conflict (state conflict, such as a duplicate), 410 Gone (resource permanently removed), and 422 Unprocessable Entity (valid syntax, invalid business rules). 5xx codes indicate server-side failures: 500 Internal Server Error (unexpected exception), 502 Bad Gateway (upstream returned an invalid response), and 503 Service Unavailable (temporary overload or maintenance). Status codes should be chosen deliberately because clients, monitoring, and load balancers branch on them. Returning 200 for every successful operation and 400 for every failure destroys the diagnostic value of HTTP. A well-designed API uses the status code as the first signal of what happened and keeps the body as supplementary detail.

11. Difference between 400 and 422.
    - **Answer:** 400 Bad Request indicates the request is malformed at a syntactic level — invalid JSON, wrong content type, or unparseable parameters — so the server cannot even begin to interpret it. 422 Unprocessable Entity indicates the request parses correctly and is well-formed, but its content fails semantic or business validation — for example, an email field with an invalid format, a serial number that does not match the required pattern, or a status transition that is not allowed. In practice, malformed JSON usually triggers 400 at the framework level before application code runs, while application-level validation produces 422. Some APIs choose 400 for everything, but that forces clients to guess whether the problem is syntax or semantics. Distinguishing them improves client UX: a 422 can carry a structured `errors` array with field-level messages, whereas a 400 is typically a generic "request could not be parsed" message. REST has no strict rule mandating 422 (it comes from WebDAV), so consistency within an API matters more than the specific choice. The common convention is: 400 for transport/parsing failures, 422 for validation failures on otherwise well-formed payloads. This split lets clients render field errors directly from a 422 without special parsing.

12. Difference between 401 and 403.
    - **Answer:** 401 Unauthorized means the client is not authenticated — it provided no credentials, invalid credentials, or an expired token — so the server cannot determine who is making the request. 403 Forbidden means the client *is* authenticated but lacks permission to perform the requested action. A 401 response should include a `WWW-Authenticate` header describing the authentication scheme (for example, `WWW-Authenticate: Bearer`). Because 401 triggers browser login prompts, it should never be used when the user is merely unauthorized — that would pop up login dialogs repeatedly. Confusing the two is a very common API design mistake. A token that is well-formed but expired should return 401 (re-authentication is needed); a valid token lacking the required role should return 403. Returning 404 instead of 403 for resources the user must not know exists is a deliberate security choice that prevents information leakage. The mnemonic: 401 asks "who are you?", 403 asks "are you allowed?". OAuth2 and other authorization frameworks return 401 when the access token is missing/invalid and 403 when it is valid but scope or permission checks fail.

13. Difference between 404 and 410.
    - **Answer:** 404 Not Found means the requested resource does not exist — it never existed, the URL is wrong, or the server does not reveal its existence. 410 Gone means the resource *did* exist but was intentionally and permanently removed, and the server knows this. For example, a deleted user profile endpoint might return 410 so clients can show "this user has been removed" rather than a generic "not found". 410 is rare in practice but useful for resources that are deprecated and permanently retired, letting clients stop requesting them and update their links. Many APIs deliberately return 404 for hidden or removed resources to avoid revealing the existence of sensitive data to unauthorized callers. The distinction matters for client caching: a 404 is transient — the resource might appear later — while a 410 tells the client the resource will never come back. Both are 4xx client errors and should not be used for server-side problems. When decommissioning an endpoint permanently, a 410 (or a 301/308 redirect to the replacement) is more honest than a 404.

14. Difference between 500 and 503.
    - **Answer:** 500 Internal Server Error means an unexpected exception occurred on the server and there is no specific, meaningful status to report — the server could not fulfill the request due to a bug, unhandled exception, or misconfiguration. 503 Service Unavailable means the server is *temporarily* unable to handle the request, typically due to overload, maintenance, or a downed dependency such as a database or cache. 503 should include a `Retry-After` header telling clients how long to wait before retrying, and clients should back off and retry rather than treat it as a fatal error. 500 is an internal failure that retrying likely will not fix (the code is still broken), whereas 503 is often transient. A proxy or gateway returns 502 Bad Gateway when an upstream service sends an invalid response, and 504 Gateway Timeout when the upstream does not respond in time. Monitoring should track 5xx rates: a spike in 500s usually indicates a deployment bug; a spike in 503s usually indicates capacity or dependency issues. For maintainability, server code should catch expected dependency failures and return 503 (or 502) explicitly rather than letting them bubble up as generic 500s. Distinguishing these codes drives correct client retry behavior and accurate alerting.

15. What is request validation?
    - **Answer:** Request validation is the process of checking that incoming request data is well-formed, correctly typed, and satisfies business rules before it is processed. Validation happens in layers: schema validation (required fields, data types, size limits), format validation (regex patterns, email/phone/date formats), and business validation (unique constraints, permitted status transitions, authorization-driven rules). Frameworks provide declarative annotations — for example, Spring's `@Valid` with Bean Validation annotations like `@NotNull`, `@Size`, `@Pattern`, and `@Email` — that run automatically before the controller method executes. Failing validation should return a clear error (typically 400 for malformed input or 422 for semantic violations) with a structured list of field-level messages. Validation at the boundary protects the service layer and database from bad data, reduces debugging, and prevents injection attacks such as SQL injection via unsanitized strings. Server-side validation is mandatory even if the frontend validates too, because clients can be bypassed entirely. Validation should be centralized and reusable, not sprinkled through business logic. Whitelisting allowed values is generally safer than blacklisting. Well-designed validation fails fast, returns specific messages per field, and never trusts client-supplied data.

16. What is DTO?
    - **Answer:** A DTO (Data Transfer Object) is a plain object used to move data between process boundaries — most commonly between the API layer and the service/domain layer, and between the API and external clients. Its purpose is to decouple the API contract from the internal data model: the DTO defines exactly which fields the API exposes and in what shape, independent of how the data is stored or modeled internally. A response DTO might contain only `id`, `name`, and `status`, while the underlying entity also holds internal timestamps, audit fields, and foreign keys. Request DTOs define what a client may send, with validation annotations on the DTO fields. Using DTOs means a database schema change (renaming a column, adding a field) does not automatically break the API contract, and new API fields can be added without migrating the domain model. DTOs also prevent over-exposing sensitive data such as password hashes or internal identifiers. They reduce payload size by omitting unnecessary fields and avoid lazy-loading or infinite-serialization problems with ORM-managed bidirectional relationships. The cost is mapping boilerplate, usually handled with libraries like MapStruct or ModelMapper. The rule of thumb: the external contract (DTO) is stable, the internal model evolves freely, and the mapping between them is explicit.

17. Why not expose entity directly?
    - **Answer:** Exposing ORM or database entities directly as API responses couples the database schema to the public API contract, so any schema change forces a breaking API change. Entities often carry fields that should never leave the server — password hashes, tokens, audit columns, internal IDs — and serializing them directly risks security leaks. Bidirectional entity relationships cause infinite recursion during JSON serialization, or trigger lazy-loading errors when a serialized relationship is accessed outside an open session/transaction. Entities may load far more data than the client needs, causing performance overhead from unnecessary joins and large payloads. Direct exposure also prevents independent evolution: the API cannot add a computed field, rename a field, or flatten a nested structure without altering persistence. Entities reflect storage design (foreign keys, surrogate IDs, enums stored as integers), which is usually not what a client-facing contract should express. Using DTOs keeps the contract stable, secure, and minimal while the persistence model changes freely behind the mapper. Exposing entities is a common early-architecture mistake that becomes expensive to unwind once clients depend on the leaked shape.

18. What is global exception handling?
    - **Answer:** Global exception handling centralizes error mapping so that exceptions anywhere in the application are converted into consistent, structured HTTP responses in one place, rather than scattered `try/catch` blocks. In Spring Boot, this is typically `@ControllerAdvice` (or `@RestControllerAdvice`) with `@ExceptionHandler` methods that map specific exception types to status codes and response bodies. A handler for a "resource not found" exception returns 404, a handler for validation exceptions returns 400/422 with field-level messages, and a catch-all handler returns 500 for anything unexpected. The key benefits are uniformity — every error has the same JSON shape — and the removal of repetitive error logic from controllers. Global handlers also allow logging of every error with a request/trace ID, which links client reports to server logs. Care must be taken to never leak stack traces, SQL statements, or internal details in responses; generic messages for 5xx are safer, with full details only in logs. Global handling composes with validation frameworks, so framework-raised validation errors flow through the same formatter. This design makes the API predictable for clients and is the foundation of a well-designed error strategy.

19. How do you design error response?
    - **Answer:** An error response should be a consistent, structured JSON object so clients can handle failures programmatically. A common shape is `{"status": 400, "code": "VALIDATION_ERROR", "message": "Serial number must be alphanumeric", "timestamp": "2026-08-13T10:30:00Z"}`. The `status` mirrors the HTTP status code; `code` is a stable, machine-readable string the client can switch on; `message` is a human-readable description; and `timestamp` records when the failure occurred. For validation failures, a `details` or `errors` array with per-field objects (`{field, message, rejectedValue}`) lets clients highlight specific form fields. Every response should include a trace/request ID that can be passed to support or correlated with server logs. Error messages must be user-safe: no stack traces, no SQL, no internal paths or hostnames, and no sensitive data echoed back. Standardizing on one structure across 4xx and 5xx responses is essential — clients should not need to parse different shapes per endpoint. The error body is complementary to the status code: the code gives the class of failure, the body gives the specifics. Some teams adopt RFC 7807 (Problem Details for HTTP APIs) for a standard error format. Good error design reduces client-side branching, speeds debugging, and improves the API's overall developer experience.

20. What is API versioning?
    - **Answer:** API versioning is the practice of allowing multiple versions of an API to coexist so that existing consumers keep working while the API evolves. When breaking changes are unavoidable — renaming a field, changing a type, removing an endpoint — a new version is published and old versions are maintained for a deprecation period. Common strategies are URI versioning (`/api/v1/customers`, `/api/v2/customers`), header versioning (a custom `Accept-Version` or `X-API-Version` header), and query-parameter versioning (`/api/customers?version=2`). URI versioning is the most common because it is explicit, cacheable, and visible in logs and documentation. Header versioning keeps URLs clean but hides the version from casual inspection and is incompatible with URL-based caching. A versioned API gives consumers a migration window and a predictable upgrade path, usually announced via a deprecation header (`Deprecation: true`, `Sunset: <date>`). Breaking changes should be grouped into major versions, while additive changes (new optional fields, new endpoints) are non-breaking and can ship in the current version. Versioning has costs: duplicated code, multiple test suites, and ongoing maintenance of old routes, which is why teams should avoid over-versioning and prefer additive, backward-compatible evolution. The goal is to protect consumers from change while still allowing the API to improve.

21. URL versioning vs header versioning.
    - **Answer:** URL versioning embeds the version in the path — `/api/v1/customers` — while header versioning carries it in a request header such as `Accept: application/vnd.customers.v2+json` or a custom `X-API-Version` header. URL versioning is explicit and self-documenting: anyone looking at a request, a log line, or a bookmarked link can see the version immediately. It is trivially routable — a load balancer or gateway can route by path prefix — and it remains cacheable because each version has distinct URLs. Its downside is that the URL becomes part of the version contract, and evolving requires copying routes across versions, which can duplicate code. Header versioning keeps the URL clean and allows the same resource identifier to serve multiple representations, but it hides the version from logs and debugging tools and complicates caching, because distinct versions share a URL. Header versioning also requires client support — every request must send the header — and mistakes are easy to make when clients forget to set it. Media-type versioning (`application/vnd.api.v2+json`) is technically a form of content negotiation and is more REST-pure, but it is harder to test in a browser. For most teams, URL versioning is the pragmatic default because of its visibility and operational simplicity, with header versioning reserved for teams that prioritize clean URLs and strict media-type semantics.

22. What is pagination?
    - **Answer:** Pagination splits a large result set into smaller, sequential pages so that responses stay bounded and servers avoid transferring and serializing huge payloads. The two dominant styles are offset-based and cursor-based. Offset pagination uses `page` and `size` (or `limit`/`offset`) parameters, as in `GET /api/orders?page=2&size=50`, and returns metadata such as `totalPages`, `totalElements`, and a boolean `hasNext` for the UI. It is simple and allows jumping directly to an arbitrary page, but it is unstable under concurrent writes: new rows inserted at the front shift all pages, causing duplicates or skipped items. Cursor pagination uses an opaque token derived from the last item of the previous page — `GET /api/orders?cursor=eyJpZCI6MTAw&limit=50` — and is stable even when new records arrive, because the cursor pins a position in the data. Cursors are the preferred choice for real-time, high-write feeds such as sensor data or event streams. Responses should wrap items in an envelope: `{"items": [...], "nextCursor": "...", "hasMore": true}` so clients can page forward iteratively. Pagination parameters should have sane defaults and hard maximums to protect the server from oversized requests. Well-designed pagination also pairs with sorting and filtering, and clients should be told which style is in use. The trade-off is stability and performance (cursor) versus simplicity and random access (offset).

23. What is sorting?
    - **Answer:** Sorting lets clients order results by one or more fields, usually via query parameters such as `GET /api/orders?sort=createdAt,desc&sort=customerName,asc`. Multi-field sorting applies fields left to right, so the client expresses primary and secondary sort keys. The critical design rule is to whitelist sortable fields: user-supplied sort field names must be mapped to known, allowed columns, never interpolated directly into an ORDER BY clause, which would enable SQL injection. Unwhitelisted fields should be rejected with a 400 or 422 rather than silently ignored. Even whitelisted fields may be expensive to sort on if unindexed, so the set of sortable fields is usually limited to indexed columns. Server-side sorting keeps responses deterministic — the same query returns the same order, which is essential for stable pagination. Sorting is orthogonal to filtering and pagination: `?status=active&sort=createdAt,desc&page=1&size=50` composes them. Direction should be explicit (`asc`/`desc`) with a documented default. Some APIs support case-insensitive and locale-aware sorting via collation settings. A good sorting design prevents injection, limits cost, and gives clients predictable, composable control over result ordering.

24. What is filtering?
    - **Answer:** Filtering narrows a result set based on criteria — status, date range, category, region — rather than returning everything. The simplest form is query parameters: `GET /api/reports?status=active&from=2026-01-01&to=2026-06-30`, which maps directly onto SQL WHERE clauses or query-builder predicates. Filter fields should be whitelisted and validated, and range filters are often expressed as `min`/`max` or `from`/`to` pairs. Simple equality filters work well as query parameters; complex nested filters (AND/OR groups across multiple fields) may justify a JSON filter body sent via POST or a query-string language like OData. Backend implementation often uses a specification/query-builder pattern (for example, Spring Data JPA Specifications) to assemble dynamic WHERE clauses safely without string concatenation. Filtered columns should be indexed to avoid full-table scans on large tables. Combined with sorting and pagination, filtering lets a single endpoint serve many different client views without a proliferation of endpoints. Filter values need validation against the expected type and domain (for example, a valid date format or a known enum value). The design goal is expressive, predictable, and safe criteria that cannot bypass security constraints — for instance, tenant filtering must always be enforced server-side regardless of client filters.

25. What is HATEOAS?
    - **Answer:** HATEOAS (Hypermedia As The Engine Of Application State) is the constraint that a REST response includes links to related resources and actions, so clients navigate the API by following links rather than hard-coding URLs. A `GET /api/orders/42` response might be `{"id": 42, "status": "pending", "_links": {"self": "/api/orders/42", "cancel": "/api/orders/42/cancel", "items": "/api/orders/42/items"}}`. The server decides which links are available based on state — an already-cancelled order would not expose a `cancel` link — which is why HATEOAS is described as "the engine of application state": the available transitions are literally part of the representation. HATEOAS makes an API self-documenting and reduces coupling, because clients discover URLs dynamically instead of hard-coding them, so server URL changes do not break clients. The trade-offs are larger payloads and more complexity on both the server and client, which is why most real-world APIs implement a pragmatic subset or skip HATEOAS entirely. Some common standards are HAL (`application/hal+json`), JSON:API, and JSON-LD with link relations. Hypermedia also enables a server to evolve routes without a version bump, as long as link relations remain stable. The honest evaluation of HATEOAS is that it is theoretically elegant but operationally demanding, and most production REST APIs prefer explicit, documented URLs.

26. What is content negotiation?
    - **Answer:** Content negotiation is the HTTP mechanism by which a client and server agree on the representation format of a resource. The client expresses preferences in headers such as `Accept: application/json` (response format), `Content-Type` (request body format), `Accept-Language`, and `Accept-Encoding`. The server selects a representation it can produce, sets the corresponding `Content-Type`, and returns it; if it cannot satisfy the request, it responds with 406 Not Acceptable. A single resource URI can serve JSON, XML, or HTML depending on the `Accept` header — for example, `Accept: application/vnd.myapi+json` plus version qualifiers enables media-type-based versioning. In frameworks like Spring, controller mappings declare `produces = "application/json"` and message converters handle serialization based on the negotiated content type. Server-driven negotiation means the same logical resource is content-agnostic, while the client's preferences decide the wire format. Negotiation also covers encoding (gzip), so responses are compressed transparently when the client advertises `Accept-Encoding: gzip`. This is distinct from the outdated practice of using file extensions (`.json`, `.xml`) to pick a format. Content negotiation is a core part of a uniform interface and keeps a REST API flexible across diverse clients. The practical guideline is to set `Accept` and `Content-Type` explicitly in clients rather than relying on defaults.

27. What is CORS?
    - **Answer:** CORS (Cross-Origin Resource Sharing) is a browser-enforced security mechanism that controls whether a web page from one origin may make requests to a different origin. An origin is the combination of scheme, host, and port — so `http://localhost:3000` and `http://localhost:8080` are different origins even on the same machine. Without CORS headers, browsers block cross-origin AJAX reads, which would otherwise allow a malicious site to silently read data from another site's API. When a cross-origin request is "non-simple" (custom headers, non-simple content types like JSON, or methods other than GET/POST/POST-form), the browser first sends an OPTIONS *preflight* request, and the server must respond with the allowed origins, methods, and headers — `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`, and optionally `Access-Control-Allow-Credentials`. The server configures CORS to allow specific origins, either globally or per-route. CORS is entirely a browser policy: it does not apply to server-to-server calls, mobile apps, or curl, so it must never be treated as the security boundary — authentication and authorization still live in the API itself. Misconfigured CORS (for example, reflecting arbitrary `Origin` values, or `Allow-Origin: *` with credentials) opens the API to browser-based attacks. The right approach is to allow only trusted origins and to keep CORS configuration explicit and auditable.

28. How do you secure REST APIs?
    - **Answer:** Securing an API requires defense in depth across multiple layers. Always serve over HTTPS/TLS so credentials and payloads cannot be read in transit. Authenticate every request to establish who the caller is — common schemes are Basic auth (username/password, usually over TLS and rarely appropriate for production), API keys (simple shared secrets for service clients), bearer tokens, JWTs (stateless, self-contained tokens verified by signature), and OAuth2 flows (delegated authorization for third parties). Then authorize: map the authenticated identity to roles, scopes, or permissions and enforce least privilege on every endpoint. Input validation at the boundary prevents injection, mass-assignment, and malformed-data attacks. Rate limiting and throttling protect against abuse and brute-force credential attempts. CORS configuration restricts which browser origins may call the API, and security headers (like `Content-Security-Policy` and `Strict-Transport-Security`) harden the surface. Logging and auditing record who did what, and error responses must never leak stack traces or sensitive data. Secrets, tokens, and keys must be stored in secure storage, never in code or client-side bundles. Authorization decisions should always be server-side and resource-scoped — for example, verifying a user may access only their own records. Together these layers protect confidentiality, integrity, and availability.

29. How do you document REST APIs?
    - **Answer:** REST APIs are documented by defining the contract: endpoints, HTTP methods, request/response schemas, parameters, headers, authentication, status codes, and error formats. The modern standard is OpenAPI (formerly Swagger), written in JSON or YAML, that describes the API in a machine-readable way and can be rendered into interactive documentation. Annotation-driven tools (for example, springdoc-openapi) generate the OpenAPI document from code, which keeps the documentation in sync with the implementation — a significant advantage over manually maintained docs that drift out of date. Good documentation includes clear descriptions for every endpoint and field, realistic request/response examples, the authentication scheme, error response shapes, and pagination/sorting/filtering conventions. The generated docs expose a UI (Swagger UI or ReDoc) where developers can try endpoints live with actual authorization tokens. OpenAPI documents also power client SDK generation, contract testing, and gateway configuration. Documentation quality is part of the developer experience: it should answer "what does this endpoint do, what does it need, and what can go wrong?" for every route. Versioned documentation should match the released API versions. The goal is a single source of truth that both humans and tools consume.

30. What is OpenAPI?
    - **Answer:** OpenAPI is a vendor-neutral, machine-readable specification (formerly the Swagger specification) for describing REST APIs in JSON or YAML. A document declares the API title and version, every path and HTTP method, parameters (path, query, header, cookie), request and response bodies with typed schemas, authentication requirements, and status codes. Because it is a formal specification, OpenAPI enables powerful tooling: interactive documentation (Swagger UI, ReDoc), client SDK generation in many languages, mock servers for frontend development, contract testing, and API-gateway configuration. Frameworks with annotation support (springdoc-openapi for Spring Boot, FastAPI, etc.) can generate the document directly from code annotations, keeping docs in sync with implementation. OpenAPI also supports the `components` section to reuse schemas and the `securitySchemes` section to define API key, HTTP bearer, or OAuth2 requirements. It facilitates contract-first development, where the spec is written and agreed upon before implementation. An OpenAPI document acts as the single source of truth that the client team, the server team, and QA all reference. The main limitation is that it describes the contract, not behavior guarantees such as performance or semantics — those still require careful design and testing. OpenAPI has become the de facto industry standard for REST API description.

31. How do you test REST APIs?
    - **Answer:** REST APIs are tested at multiple levels, each catching different classes of defects. Unit tests cover service and domain logic in isolation with mocked dependencies. Controller/slice tests (for example, `@WebMvcTest`) verify serialization, validation, status codes, and error handling against mocked services. Integration tests (`@SpringBootTest`) exercise the full stack with a real database — often via Testcontainers — covering persistence, transactions, and end-to-end request flow. API-level tests send real HTTP requests and assert on status codes, headers, response bodies, and error shapes. End-to-end tests and manually executable collections (Postman/Insomnia) validate the deployed API, including authentication flows. Contract testing (with tools like Pact) verifies that the provider and consumer agree on the request/response contract, catching drift between frontend and backend teams. Performance/load tests (JMeter, Gatling, k6) validate latency and throughput under expected load and identify bottlenecks like N+1 queries. Security testing checks authorization boundaries, injection resistance, and rate limiting. Tests should be automated in the CI pipeline so regressions are caught before deployment. The key principle is layering: fast, cheap unit tests run constantly, while slow integration and load tests run on demand or before releases.

32. How do you handle long-running API requests?
    - **Answer:** Long-running operations — report generation, bulk imports, video processing — should not block an HTTP request for minutes, because clients time out, connections are held, and servers are exhausted. The standard pattern is asynchronous processing with the 202 Accepted response: the API accepts the request, validates it, enqueues a job, and immediately returns `202 Accepted` with a job/tracking ID. The client then polls a status endpoint — `GET /api/jobs/{id}` — which returns states like `queued`, `processing`, `completed`, or `failed`, along with a result URL when done. Polling can be wasteful, so a long interval or exponential backoff should be used. Alternatives include webhooks, where the server POSTs the result to a client-registered callback URL when finished, and Server-Sent Events (SSE) or WebSockets for pushing progress updates. Webhooks are push-based and efficient but require the client to expose a publicly reachable endpoint and the server to handle retries and idempotency. SSE is simpler for one-directional progress streams. The 202 pattern keeps HTTP semantics intact (the request was accepted, not completed) and lets the server scale processing via a queue independently of web capacity. Job endpoints should persist state so they survive server restarts, and results should expire after a retention window. Choosing between polling and webhooks depends on whether the client can be called back.

33. How do you handle file upload?
    - **Answer:** File uploads use the `multipart/form-data` content type, where the request body contains both the file part and ordinary form fields: `curl -F "file=@report.csv" -F "type=inventory" https://api.example.com/uploads`. The server receives the file as a stream and must validate its size (via a configured limit), MIME type, and extension against a whitelist, since filename and declared type can be forged. Files should not be trusted: contents should be inspected or virus-scanned where appropriate. Storage options include the local filesystem, object storage (S3, GCS, Azure Blob), and databases (only for very small blobs); object storage is preferred for durability and scalability. Large files should be streamed to disk or object storage rather than buffered entirely in memory, which would risk `OutOfMemoryError`. For very large files, chunked uploads or multipart upload APIs with presigned URLs let clients upload directly to object storage, bypassing the application server and reducing load. Uploads should return a location (for example, a file ID or URL) that can be referenced later. Upload endpoints need authentication, quotas, and rate limits to prevent abuse. The response typically returns 201 with metadata such as file ID, size, and download URL.

34. How do you handle large API response?
    - **Answer:** Large responses hurt latency, bandwidth, client memory, and server serialization cost, so they are controlled at multiple levels. The first line of defense is pagination — never return unbounded result sets; always page them and expose metadata about further pages. Field selection, such as sparse fieldsets (`?fields=id,name,status`), lets clients request only what they need and avoids over-fetching. Compression with gzip (or brotli) at the server or load balancer shrinks JSON dramatically for text-heavy payloads. Streaming responses lets the server write chunks incrementally so clients can begin consuming data before the entire response is generated, and avoids buffering the full payload in server memory. Projection at the query layer — selecting only needed columns, using DTOs — reduces serialization work. For extremely large datasets, endpoints that return a download file (CSV/Excel/Parquet) or trigger async generation are better than a JSON dump. Caching (with `Cache-Control` and `ETag`) prevents regenerating identical large payloads for repeated requests. The design should combine techniques: paginate by default, allow field selection, compress at the edge, and stream or offload when volumes are extreme. Each technique has a cost, so the combination should match actual client usage.

35. How do you handle backward compatibility?
    - **Answer:** Backward compatibility means existing clients keep working while the API evolves. The core rule is the robustness principle: be conservative in what you send and liberal in what you accept. Non-breaking changes — adding optional fields, adding new endpoints, expanding allowed enum values, adding response fields — can ship without a version bump, because old clients ignore unknown fields. Breaking changes — renaming or removing a field, changing a type, making a field required, changing semantics or status codes — must go through a versioning strategy (URI, header, or media-type) so old clients are unaffected. Fields should never be repurposed; adding a new field with a different meaning is safer than overloading an existing one. Deprecation should be explicit: mark deprecated endpoints or fields in documentation, set `Deprecation` and `Sunset` headers to announce when a version will be retired, and publish a migration guide. Server-side translation layers (DTO mapping) keep the wire contract stable even as internal models change. Tests should include contract tests that freeze the response shape to catch accidental breaks. When an endpoint must change behavior, prefer additive design — new endpoint alongside the old, old one deprecated — over mutation. The overall goal is a smooth migration path that never forces clients to break or lose data. Versioning is the mechanism; backward compatibility is the discipline that makes it rarely necessary.
