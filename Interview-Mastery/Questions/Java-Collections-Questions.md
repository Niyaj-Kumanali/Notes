## Answers

1. What is Java Collections Framework?
   - **Answer:** The Java Collections Framework (JCF) is a unified architecture of interfaces and implementations for storing, retrieving, and manipulating groups of objects. It sits on top of the `java.util` package and is built around core interfaces: `Collection` (the root), `List` (ordered, indexed, allows duplicates), `Set` (no duplicates), `Queue`/`Deque` (FIFO/LIFO ordering), and `Map` (key-value associations, which is *not* a subinterface of `Collection`). The framework also provides utility classes such as `Collections` and `Arrays` for sorting, searching, and creating unmodifiable views. The design separates the *abstraction* (interface) from the *implementation* (concrete class), so code can depend on `List` while the actual backing structure (e.g. `ArrayList` or `LinkedList`) can be swapped freely. Implementations cover every important data structure need: dynamic arrays, linked lists, hash tables, red-black trees, heaps, and thread-safe variants. The JCF also includes algorithms like binary search (`Collections.binarySearch`) and sorting (`Collections.sort`) that work across all implementations of an interface. Performance characteristics are documented per implementation, so choosing between them is a deliberate tradeoff between insertion cost, lookup cost, ordering guarantees, and memory overhead. Legacy classes such as `Vector`, `Stack`, and `Hashtable` remain for backward compatibility but have been superseded by the modern framework classes. Overall, the framework eliminates the need to hand-write basic data structures and promotes code reuse, type safety via generics, and predictable time-complexity guarantees.

2. Difference between `List`, `Set`, and `Map`.
   - **Answer:** `List` is an ordered collection that permits duplicates and gives positional access; elements are retrievable by index and iteration follows insertion order (for `ArrayList`). `Set` is a collection that forbids duplicates; uniqueness is determined through `equals()`/`hashCode()`, and the iteration order depends entirely on the implementation: `HashSet` is unordered, `LinkedHashSet` preserves insertion order, and `TreeSet` iterates in sorted order. `Map` is not a `Collection` at all; it stores key-value pairs where keys are unique and each key maps to at most one value, and a map can hold `null` keys and values depending on the implementation (`HashMap` allows one null key and many null values, `Hashtable` allows none). `Map.Entry` provides a view of individual pairings, and the three key views — `keySet()`, `values()`, and `entrySet()` — expose the map's contents. The core difference is the abstraction: a `List` is about *position and multiplicity*, a `Set` is about *uniqueness*, and a `Map` is about *association and fast lookup by key*. Under the hood these translate to different data structures: lists use arrays or linked nodes, sets often reuse map internals (e.g. `HashSet` is backed by a `HashMap`), and maps use hash buckets or trees. When choosing, consider the dominant operation: indexed access favors `List`, membership tests favor `Set`, and key-based retrieval favors `Map`. Null handling, ordering guarantees, and thread safety further differentiate concrete classes within each interface. The framework exposes all three through the common `Collection` (for List/Set) and `Map` hierarchies, enabling generic, implementation-agnostic code.

3. Difference between `ArrayList` and `LinkedList`.
   - **Answer:** `ArrayList` is backed by a growable Object array, giving O(1) random access by index and O(n) worst-case insertion in the middle because elements must be shifted; appends at the end are amortized O(1) thanks to geometric growth (new capacity ≈ old × 1.5 in Java). `LinkedList` is a doubly-linked list of node objects, giving O(n) access by index (it walks from whichever end is closer) but O(1) insertion and removal when the node is already located, and O(1) operations at both ends since it implements `Deque`. The memory footprint differs dramatically: `ArrayList` stores a single contiguous array plus a small header, while each `LinkedList` element requires a node object with two extra references (`prev`/`next`) plus the data reference, roughly doubling memory per element. Cache locality is another decisive factor: `ArrayList` elements are contiguous in memory, so the CPU's cache prefetcher can load many elements in one pass, while `LinkedList` nodes are scattered across the heap, causing cache misses during iteration. In practice iteration over `ArrayList` is several times faster than over `LinkedList`, which is why the Java documentation itself warns that `LinkedList` rarely outperforms `ArrayList`. `LinkedList` shines only for deque-style workloads — constant-time head/tail insertion and removal — and even there `ArrayDeque` is usually the better choice because it also has O(1) end operations with far better locality. There is no reliable way to index into a `LinkedList` efficiently, and operations like `add(index, e)` require O(n) traversal to find the insertion point. The practical rule: default to `ArrayList`; reach for `ArrayDeque` for stack/queue semantics; and treat `LinkedList` as the exception, not the rule.

4. Difference between `HashSet` and `TreeSet`.
   - **Answer:** `HashSet` is backed by a `HashMap` and offers O(1) average-time add, contains, and remove, but iteration order is unspecified and can even change across a resize. `TreeSet` is backed by a `TreeMap` (a red-black tree) and maintains elements in sorted order at all times, but every operation costs O(log n) and each element carries tree-node overhead (left/right/parent references and color flag). Because `HashSet` relies on hashing, elements must implement `equals()` and `hashCode()` consistently; `TreeSet` instead requires the element type to implement `Comparable`, or the set must be constructed with an explicit `Comparator`, and it will throw a `ClassCastException` if elements are mutually incomparable. Equality semantics differ subtly: a `HashSet` considers two elements duplicate when `equals()` returns true, whereas a `TreeSet` uses the comparator's result — if a comparator returns zero for two non-`equals()` elements, the tree set treats them as the same element and drops the second, which can silently lose data. `TreeSet` implements `NavigableSet`/`SortedSet`, exposing range operations like `subSet()`, `headSet()`, `tailSet()`, and neighbor lookups such as `ceiling()`, `floor()`, `higher()`, `lower()`, plus reverse-ordered iteration via `descendingSet()`. `HashSet` allows exactly one `null` element (the underlying map's single null key), while `TreeSet` rejects `null` because comparisons against null throw `NullPointerException`. For deduplication with no ordering requirement, `HashSet` is the fast, memory-efficient choice; sorted iteration and range queries justify the O(log n) cost of `TreeSet`. `LinkedHashSet` sits between the two, providing insertion-order iteration at O(1) cost by adding a doubly-linked list on top of the hash structure.

5. Difference between `HashMap` and `Hashtable`.
   - **Answer:** `HashMap` is not synchronized and allows one `null` key and any number of `null` values; `Hashtable` is fully synchronized (every public method is `synchronized`) and throws `NullPointerException` for any null key or value, because null cannot be hashed safely in its implementation. `Hashtable` is a legacy class from JDK 1.0 that predates the Collections Framework, while `HashMap` was introduced in JDK 1.2 as the modern replacement; both implement the `Map` interface, but `HashMap` also extends `AbstractMap` and can interoperate with the `Collections` utilities. The legacy `Hashtable` still uses the old `Dictionary` interface alongside `Map`, and its enumeration-based iteration (`keys()`/`elements()`) predates iterators. Performance-wise both have O(1) average lookup, but `Hashtable`'s coarse-grained `synchronized` methods serialize all access, making it a bottleneck in multi-threaded code, whereas `HashMap` allows full concurrent read throughput when used read-only from multiple threads. The capacity strategy differs as well: `Hashtable` uses an initial capacity of 11 and doubles-plus-one on resize, while `HashMap` uses an initial capacity of 16, a power-of-two table, and doubles the array on resize. In practice `Hashtable` should never be used in new code: for single-threaded use `HashMap` is faster and more flexible, and for concurrent use `ConcurrentHashMap` provides far better scaling through finer-grained locking and CAS-based updates. `Collections.synchronizedMap(new HashMap<>())` can mimic `Hashtable`'s external synchronization but suffers the same lock-contention problems. The takeaway is that `Hashtable` is a historical artifact — its API shape, null policy, and locking model all belong to an older generation of the platform.

6. Difference between `HashMap` and `ConcurrentHashMap`.
   - **Answer:** `HashMap` is not thread-safe: concurrent structural modification can corrupt the internal table, produce infinite loops in older JDKs, or lose entries, so access must be externally synchronized. `ConcurrentHashMap` is designed for multi-threaded access and provides thread safety without locking the entire map. In Java 7 its design used a segmented lock (`Segment extends ReentrantLock`) so only the segment being written was locked; Java 8 replaced segments with fine-grained `synchronized` on individual buckets plus CAS for empty buckets, so concurrent writers to different buckets rarely block each other and readers never block at all. Atomic per-key operations are a key differentiator: `computeIfAbsent`, `compute`, `merge`, and `putIfAbsent` execute atomically, so compound read-modify-write sequences like `map.computeIfAbsent(k, v -> expensiveLoad(k))` are safe without external synchronization. `HashMap` allows one null key and null values; `ConcurrentHashMap` forbids all null keys and values (the design relies on null as an internal sentinel to detect bucket absence, so allowing user nulls would be ambiguous). Iteration differs as well: `HashMap` iterators are fail-fast, throwing `ConcurrentModificationException` on concurrent modification, while `ConcurrentHashMap` iterators are weakly consistent — they reflect the state at some point during iteration, never throw, and are safe to use while other threads modify the map. `Collections.synchronizedMap` wraps a `HashMap` with a global lock, but that serializes every read and write, whereas `ConcurrentHashMap` allows concurrent reads and parallel writes to distinct buckets, scaling far better under contention. `ConcurrentHashMap` also pays a modest memory and per-entry overhead for its atomics and internal structures, so it should be used only when multiple threads genuinely share the map. For read-heavy workloads with occasional writes, `ConcurrentHashMap` can approach `HashMap` read performance while adding safe concurrent mutation.

7. Difference between `HashMap` and `LinkedHashMap`.
   - **Answer:** `HashMap` makes no guarantee about iteration order, and the order of keys can change whenever the map resizes. `LinkedHashMap` extends `HashMap` and adds a doubly-linked list that threads through every entry, which gives deterministic iteration order at only modest per-entry overhead (two extra references). By default `LinkedHashMap` iterates in *insertion order* — the order in which keys were first added — and re-inserting an existing key does not move it. With the access-order constructor (`new LinkedHashMap<>(capacity, loadFactor, true)`), iteration follows *access order*: every successful `get`, `put`, or `replace` moves the touched entry to the end of the list. Access-order mode is the foundation of an LRU (Least Recently Used) cache: by overriding `removeEldestEntry(Map.Entry eldest)` to return `true` when size exceeds a bound, the map automatically evicts the least-recently-accessed entry before each insertion. This makes `LinkedHashMap` the standard building block for bounded caches without pulling in a third-party caching library. Performance for lookup, insertion, and removal is still O(1) average because the linked list adds only a maintenance cost, not a search cost. Memory overhead is roughly the two extra reference fields per entry plus the list header, which is a small price for deterministic iteration. When a component needs to return entries in the exact order they were inserted — for example preserving request arrival sequence or generating deterministic serialized output — `LinkedHashMap` is the appropriate `Map` choice, while `HashMap` is preferable when ordering is irrelevant and every byte of per-entry overhead matters.

8. Difference between `HashMap` and `TreeMap`.
   - **Answer:** `HashMap` stores entries in an array of hash buckets and offers O(1) average-time `get`, `put`, and `remove`, with no defined iteration order. `TreeMap` is backed by a red-black self-balancing binary search tree, storing keys in sorted order and providing O(log n) time for every basic operation; every `put` performs tree comparisons and rebalancing rotations to keep the tree height within ~2·log(n). Because `TreeMap` keys are always ordered, the map implements `NavigableMap` and `SortedMap`, unlocking capabilities `HashMap` lacks: `firstKey()`/`lastKey()`, `floorKey()`/`ceilingKey()`/`lowerKey()`/`higherKey()` for neighbor lookups, and the view methods `subMap(fromKey, toKey)`, `headMap(toKey)`, and `tailMap(fromKey)` for range queries. Ordering in `TreeMap` comes either from the natural ordering of keys (via `Comparable`) or from a `Comparator` supplied at construction; `HashMap` instead needs proper `equals()`/`hashCode()` implementations and never compares keys for ordering. `TreeMap` does not permit a `null` key (comparison against null fails), while `HashMap` permits exactly one. Memory cost differs too: a `HashMap` entry is a node in a chain/tree inside a bucket array, whereas a `TreeMap` entry is a tree node with left/right/parent references and a color bit, so `TreeMap` uses noticeably more memory per entry. Choosing between them is a question of the access pattern: for random key-based lookup and maximum speed, `HashMap` wins; for sorted iteration, prefix/range scans, and "find nearest key" semantics, `TreeMap` is the only standard `Map` that provides them natively. If sorted ordering is needed in a concurrent context, `ConcurrentSkipListMap` offers the navigable API with thread safety.

9. How does `HashMap` work internally?
   - **Answer:** A `HashMap` is built on a `Node<K,V>[] table` — an array of buckets, each bucket being the head of a chain (linked list) or a tree. When `put(key, value)` is called, the map first computes `int hash = key.hashCode()` and then spreads the bits with a perturbation function: `(h ^ (h >>> 16))`, which mixes the high bits into the low bits so that indices depend on more of the hash. The bucket index is derived by masking with the table size minus one: `index = (table.length - 1) & hash`, which works because the table length is always a power of two. The map then scans the bucket: if it finds an existing node whose key is `equal` per the `equals()` contract (and hash matches), it replaces the value; otherwise it appends a new node to the end of the chain (Java 8) or front (Java 7). To keep buckets short, when a chain reaches 8 nodes (`TREEIFY_THRESHOLD`) *and* the table has at least 64 buckets (`MIN_TREEIFY_CAPACITY`), the chain is converted into a red-black tree (`TreeNode`), lowering worst-case lookup in that bucket from O(n) to O(log n); if the tree later shrinks below 6 nodes (`UNTREEIFY_THRESHOLD`) it is converted back to a linked list, with the 7-gap preventing thrashing between the two. The table starts at capacity 16 (default) and grows when the entry count exceeds `capacity × load factor` (default 0.75); on growth the array doubles, which triggers rehashing where entries are redistributed. On resize in Java 8, an entry's new index is either its old index or old index + old capacity, determinable from a single bit of the hash, so keys are not re-hashed, only repositioned. Lookup, insertion, and removal are O(1) average under a good hash distribution, degrading to O(log n) worst case in a bucket that has been treeified. This design is why `equals()` and `hashCode()` must be implemented consistently for keys and why immutable keys are strongly recommended.

10. What happens during hash collision?
    - **Answer:** A hash collision occurs when two distinct keys produce the same bucket index — either identical `hashCode()` values or different hashes that map to the same `index = (length - 1) & hash`. The `HashMap` does not overwrite the earlier entry; instead it stores both keys in the same bucket by chaining them, each new colliding node appended to the tail of the bucket's linked list. When `get(key)` runs, it finds the bucket by index and then uses `equals()` to walk the chain, comparing each node's key until it finds the match or reaches the end; hash comparison is done first (`key.hash == node.hash`) as a cheap filter before the potentially expensive `equals()`. Because collision lookup is linear in chain length, a badly designed `hashCode()` (for example one that returns a constant) floods every key into one bucket, degrading the map from O(1) to O(n) average. Java 8 mitigates this attack vector: once a bucket's chain exceeds 8 nodes (`TREEIFY_THRESHOLD`) and the table has at least 64 buckets, the chain is restructured into a red-black `TreeNode`, so worst-case lookup in that bucket becomes O(log n) rather than O(n); if entries are later removed and the tree drops below 6 nodes, it reverts to a linked list, and the buffer of 2 between thresholds prevents repeated flipping. When the table resizes to twice its length, colliding keys are redistributed: with the new index mask `(2·length - 1)`, each entry lands in either its old bucket or old bucket + old capacity, so previously colliding keys may separate across buckets. Collisions are an unavoidable reality of hashing, but the framework contains their cost through treeification, load-factor tuning, and the bit-spread hash function. From an interview standpoint, the key insight is that `equals()` is what ultimately disambiguates collided keys — `hashCode()` only selects the bucket.

11. What is load factor?
    - **Answer:** The load factor is the ratio `size / capacity` at which the `HashMap` decides the bucket array is too full and resizes. With the default of `0.75`, the map grows when the number of entries exceeds `capacity × 0.75` — so a table starting at capacity 16 resizes when the 13th entry is inserted. It represents a tuning knob between two opposing costs: a *lower* load factor (e.g. 0.5) keeps buckets short, cutting collision lookup time, but wastes memory because the array stays large relative to entries; a *higher* load factor (e.g. 1.0) uses memory efficiently but lengthens chains, increasing the average lookup cost. The 0.75 default is a long-standing empirical tradeoff that balances time and space; it also historically appears in the JavaDoc as an intentionally round "not precisely 0.67 or 0.75" compromise. For a known target size, the initial capacity should be chosen as `expectedSize / loadFactor + 1` so that no resize occurs during population — for example, an expected 1,000 entries with the default factor argues for an initial capacity of about 1,334, which rounds up to the next power of two. The load factor interacts directly with collisions: a fuller table has more keys hashing into the same buckets, so lookup time degrades unless the Java 8 treeify logic kicks in. It also drives resize frequency: each resize is an O(n) full copy of the table, so a load factor that is too high reduces the number of resizes but increases per-bucket chain length. In concurrent code the threshold is computed once per resize from `table.length * loadFactor`, and in Java 8 the resize loop uses per-node splitting rather than full rehashing. When constructing a map, both initial capacity and load factor can be supplied, but the load factor should rarely be changed from 0.75 unless profiling shows either excessive memory use or unacceptable collision chains.

12. What is rehashing?
    - **Answer:** Rehashing is the process of resizing the bucket array and redistributing all existing entries when the map exceeds `capacity × loadFactor`. The trigger is an insertion that pushes `size` past the threshold; the map then allocates a new array with twice the length, iterates over every bucket, and relocates each entry into the new table before the new entry is added. The total cost is O(n) — every element is touched once — which is why a single `put` that crosses the threshold can be disproportionately slow; that latency is amortized across the many cheap inserts that preceded it. The name "rehashing" is slightly historical: early implementations recomputed each key's `hashCode()` and full index during resize. Java 8 avoids that by exploiting the power-of-two sizing: since the table doubles from `n` to `2n`, the index mask gains exactly one bit, so every entry's new index is either its old index or `oldIndex + n`, determinable by inspecting a single bit of the entry's stored hash. This split-based resize is O(n) in movement but avoids recomputing hashes and enables the straightforward split of each chain into "low" and "high" sublists. The resize threshold is recomputed as `newCapacity * loadFactor`, so after doubling, the map can hold roughly twice as many entries before the next resize. Frequent resizing is a sign of a poorly chosen initial capacity; presizing to `expectedSize / loadFactor + 1` can eliminate rehashes entirely for a known workload. In Java 7 and earlier, resizing under concurrent modification could corrupt the table and create infinite loops on lookup; modern usage avoids this by never sharing a `HashMap` across threads without synchronization. Rehashing is also why iteration order of a `HashMap` is unstable — the redistribution can reorder entries across buckets.

13. Why should keys be immutable in a `HashMap`?
    - **Answer:** Immutable keys guarantee that a key's `hashCode()` can never change after it is inserted, which is a hard requirement for correct `HashMap` behavior. The map computes the bucket index once at insertion using the key's hash; all later `get`, `put` (for lookup), `remove`, and `containsKey` operations compute the index again from the same `hashCode()`. If the hash changes after insertion, lookups compute a *different* bucket index and never find the entry, even though the object is still present in the table — the entry becomes effectively unreachable and leaks in memory. `equals()` consistency is the second requirement: if a mutated object compares unequal to its former self, the map cannot identify it even within the same bucket. Using library value types such as `String`, `Integer`, `Long`, or enum constants is the simplest way to satisfy this, since they are immutable and implement `hashCode()`/`equals()` correctly. Java 16+ `record` types are designed exactly for this role: they are immutable, and their canonical constructor and `equals`/`hashCode` are derived from all components. Even a *theoretically* mutable key works fine as long as it is never mutated after insertion, but that is a fragile discipline that invites bugs; immutability makes the guarantee structural rather than behavioral. Mutable keys also break the map's invariants for `containsKey` and duplicate handling, and corrupt data can go unnoticed until production symptoms appear. Defensive copying — storing a copy of a caller-supplied key instead of the original reference — is a complementary technique when truly immutable types are not available. The principle generalizes beyond maps: any hash-based collection (`HashSet`, `LinkedHashSet`, and `HashMap` itself) depends on stable hashes and consistent equality for the entire lifetime of the stored elements.

14. What happens if a mutable object is used as a key?
    - **Answer:** If a mutable object is modified after being inserted into a `HashMap`, the object's `hashCode()` (and typically its `equals()`) changes while the entry remains stored in the bucket chosen under the *original* hash. The first symptom is a lookup failure: `get(key)` recomputes the bucket index from the new hash, searches the wrong bucket, and returns `null`, even though the key is still physically present in the map. The entry is not deleted — it is orphaned — so it continues to occupy memory and count toward the map's size while being permanently unreachable by normal lookup; this is a classic memory leak. If two keys are mutated so that their hash codes collide or swap, `get`, `remove`, and `put` may also return or replace the wrong entry, silently corrupting data. The same hazard applies to `HashSet`, since it stores elements as map keys. The failure can surface far from the mutation site, making it notoriously hard to debug: a value set through one code path becomes invisible to another code path that holds the same logical key. Mitigations include using immutable key types (`String`, `Integer`, records, value objects), defensive copying at insertion, or forbidding mutation of key fields after construction. If a key must change, the correct procedure is to `remove` the old key-value pair first, mutate the key, then `put` it again so it lands in a bucket matching its new hash. Code review rules often mandate immutable keys and re-run `hashCode()`-dependent tests under mutation to catch such bugs early. This question pairs naturally with the immutability discussion: immutability makes correctness a compile-time property instead of a runtime discipline.

15. What is fail-fast iterator?
    - **Answer:** A fail-fast iterator is one that throws `ConcurrentModificationException` the moment it detects that the underlying collection was structurally modified after the iterator was created. The mechanism is the `modCount` field: every collection that changes its structure (adding, removing, or clearing elements) increments this counter, and each iterator stores the value it captured at creation (`expectedModCount`). On every `next()` call the iterator compares the two; any mismatch signals concurrent or mid-iteration modification, and it fails fast with `ConcurrentModificationException`. "Structural modification" means a change in size or an insertion/removal, but not an in-place element replacement, which does not bump the counter. Note the exception is a *bug-detection heuristic*, not a guarantee: the check is best-effort and non-deterministic, and a modification followed by a remove in the wrong pattern can slip through or corrupt the iteration. The classic failure is mutating a `List` inside a for-each loop, which is syntactic sugar over an iterator. The safe mutation pattern is to use the iterator's own `remove()` method, which adjusts `expectedModCount` alongside `modCount`, or to collect elements for removal in a separate list and remove them after iteration. For concurrent or frequent-modification scenarios, `CopyOnWriteArrayList` and `ConcurrentHashMap` are the alternatives, as their iterators never throw. Because the guarantee is best-effort even in single-threaded code, production code should not rely on catching `ConcurrentModificationException` to handle concurrency — that is a programming error to be fixed, not a control-flow branch.

16. What is fail-safe iterator?
    - **Answer:** A fail-safe iterator operates on a snapshot of the collection rather than the live backing structure, so modifications made after the iterator is created do not throw `ConcurrentModificationException`. Strictly speaking the Java class library does not define a "fail-safe" interface; the term describes the behavior of iterators in classes like `CopyOnWriteArrayList`, `CopyOnWriteArraySet`, and `ConcurrentHashMap`. `CopyOnWriteArrayList` achieves this by copying the entire underlying array on every mutation, so an iterator holds a reference to the array as it existed at creation time and is guaranteed to see a consistent, immutable view — but it will *not* see any elements added after the iterator was created. `ConcurrentHashMap` iterators are *weakly consistent* rather than snapshot-based: they are guaranteed not to throw, reflect the state of the map at some point during traversal, and may or may not reflect concurrent updates occurring mid-iteration. The tradeoff for fail-safe behavior is cost: each write to a `CopyOnWriteArrayList` allocates a full array copy, making writes O(n), while reads remain lock-free and cheap — which is why these collections are only sensible for read-heavy, write-rare workloads. Fail-safe does not mean fully thread-safe in the sense of linearizable reads: two threads may see different snapshots at the same logical time. It is important to note that the term is informally used and can be misleading; the Java API documentation speaks of "weakly consistent iterators" and "snapshot iterators." Fail-safe behavior removes one entire class of `ConcurrentModificationException` bugs, at the price of memory overhead (retained old arrays until GC) and, for the copy-on-write types, expensive writes. Choosing between fail-fast and fail-safe is really a decision about the workload: fast, unsynchronized iteration with a clear error on mid-iteration mutation versus snapshot consistency with higher write cost.

17. Difference between `Iterator` and `ListIterator`.
    - **Answer:** `Iterator` is the universal traversal contract available on every `Collection`: it supports forward-only traversal via `hasNext()`/`next()`, removal of the last returned element via `remove()`, and since Java 8, bulk processing through `forEachRemaining()`. `ListIterator` is a subinterface of `Iterator` available only on implementations of `List` (`ArrayList`, `LinkedList`, `CopyOnWriteArrayList`, etc.), and it adds bidirectional traversal: `hasPrevious()` and `previous()` let code walk the list backwards from a given position. It also exposes index introspection with `nextIndex()` and `previousIndex()`, giving the iterator a concrete cursor position in the list. Beyond traversal, `ListIterator` supports *structural* modification during iteration: `add(e)` inserts an element at the cursor position (immediately before the element that would be returned by `next()`), and `set(e)` replaces the last element returned by `next()` or `previous()` — neither operation exists on the base `Iterator`. The directional semantics are subtle: after `next()`, `add()` inserts before the next element, while `set()` replaces the element just returned. Because the base `Iterator` is one-directional and lacks positional knowledge, it can offer only `remove()`, and that only after at least one `next()`. Set-based collections (`HashSet`, `TreeSet`) have no notion of positional index, so they expose only `Iterator`. When a traversal needs to modify a list in place, insert at a cursor, or move in both directions, `ListIterator` is the correct tool; for plain forward reads over any collection, the lighter `Iterator` (or an enhanced for-loop over it) is sufficient. The takeaway is that `ListIterator` is strictly more capable, but only meaningful where position exists.

18. Difference between `Comparable` and `Comparator`.
    - **Answer:** `Comparable` defines a type's *natural ordering* from within the class itself: the class implements `compareTo(T other)`, and only one such ordering can exist per type. `Comparator` is an external strategy object that defines ordering from outside the class, so any number of distinct comparators can be written for the same type without touching it. The natural API is `int compare(T a, T b)` (or a lambda such as `(a, b) -> a.length() - b.length()`), which is why `Comparator` supports fluent composition: `Comparator.comparing(Person::getLastName).thenComparing(Person::getFirstName)`. As a design rule, the natural `compareTo` should be consistent with `equals()` — equal objects must compare as 0 — because sorted collections like `TreeSet` and `TreeMap` decide *duplicate-ness* purely from the comparison result; a comparator that returns 0 for non-`equals()` elements will silently drop one of them. In contrast, a `Comparator` passed to a collection is authoritative, and inconsistency between a comparator and `equals()` is tolerated (with the documented consequence that elements the comparator considers equal are treated as a single element). The types that respect `Comparable` automatically include `String`, wrapper types, `Date`, enums, and `BigDecimal`; custom classes opt in by implementing it. Framework usage mirrors the distinction: `Collections.sort(list)` and `TreeSet`/`TreeMap` with no explicit comparator rely on `Comparable`, while `Collections.sort(list, comparator)`, `PriorityQueue`, and `Arrays.sort` accept a `Comparator` for custom rules. Since Java 8, `Comparator` gained helpers for null handling (`nullsFirst`, `nullsLast`), reverse order (`reversed()`), and key extractors (`comparing`, `comparingInt`, `thenComparing`). In short, `Comparable` is the single canonical ordering baked into the type; `Comparator` is a pluggable, composable ordering chosen per use-site — the latter offers far more flexibility for sorting the same class multiple ways.

19. What is priority queue?
    - **Answer:** A `PriorityQueue` is a collection that orders elements by a *priority* rather than by insertion order; the head of the queue is always the element with the least value under the natural ordering or a supplied `Comparator`. It is implemented as a binary min-heap stored in an array: the tree invariant (every parent ≤ its children) is maintained by percolating elements up on `offer()` and down on `poll()`, so both operations run in O(log n). `peek()` is O(1) because the minimum is always at index 0, while `contains` and non-head removal are O(n) linear scans, which is a notable limitation. Elements must be mutually comparable — either by implementing `Comparable` or via the comparator passed at construction — otherwise `ClassCastException` is thrown when elements are compared. The iterator does *not* traverse in priority order: it walks the internal heap array (roughly insertion order), so the only guaranteed ordering is through repeated `poll()`. `PriorityQueue` is not bounded, meaning it grows without limit, and it is not thread-safe; the concurrent counterpart is `PriorityBlockingQueue`, which adds blocking `take()` on an empty queue. Because `poll()` always returns the smallest element, repeated `poll()` yields elements in ascending order — this makes it the basis of heap sort. Common applications include scheduling tasks by deadline or severity, Dijkstra's and A* search, merging sorted streams, and top-K problems (`topK` via a size-bounded max-heap). The heap's memory overhead is low (a single backing array, doubling on demand) and it does not accept null elements, since null would break comparisons.

20. What is blocking queue?
    - **Answer:** A `BlockingQueue` is a `Queue` whose `put()` and `take()` operations block rather than fail when the queue is full or empty, respectively: `put(e)` waits until space frees up, and `take()` waits until an element is available. It is the standard building block for the producer–consumer pattern, letting producers and consumers coordinate without explicit locks, condition variables, or busy-waiting. The interface offers four families of operations: throwing variants (`add`, `remove`, `element`), returning-special-value variants (`offer`, `poll`, `peek`), timed variants (`offer(e, time, unit)`, `poll(time, unit)`), and blocking variants (`put`, `take`). Implementations differ in structure and guarantees: `ArrayBlockingQueue` is a bounded, array-backed, optionally-fair FIFO; `LinkedBlockingQueue` is a linked, optionally-bounded FIFO with two separate locks for head and tail; `SynchronousQueue` has zero capacity, so each `put` must rendezvous directly with a `take`; `PriorityBlockingQueue` is an unbounded, thread-safe heap ordered by priority; and `DelayQueue` holds elements that cannot be taken until their delay elapses. Every implementation is thread-safe, using internal locking or CAS so multiple producers and consumers can operate concurrently. Thread pools rely on this machinery internally: `ThreadPoolExecutor` keeps its pending tasks in a `BlockingQueue` (often `LinkedBlockingQueue` or `SynchronousQueue`) and uses blocking `take()` to make idle worker threads wait for work. Bounded blocking queues also provide natural backpressure: if consumers are slower than producers, producers block on `put()` and the queue size stays capped instead of exhausting memory. The interface deliberately excludes `null`, treating it as a marker for "no element" in the special-value return variants. Choosing an implementation comes down to desired bounds, ordering (FIFO vs priority vs delay), fairness, and whether zero-capacity rendezvous is required.

21. What is copy-on-write collection?
    - **Answer:** A copy-on-write collection is a thread-safe collection that mutates by copying its entire backing array on every write and swapping in the new array, rather than mutating shared state in place. `CopyOnWriteArrayList` is the canonical example; `CopyOnWriteArraySet` wraps it via `new CopyOnWriteArraySet<>(new CopyOnWriteArrayList<>())` and is the set analogue. On `add`, `remove`, or `set`, the collection takes a lock (a single `ReentrantLock`), copies the current array, applies the modification to the copy, and replaces the volatile reference to the old array. Readers are completely lock-free: they simply read the volatile array reference and traverse it, never seeing a partial write, so reads never block and never throw `ConcurrentModificationException`. Because iterators capture the array at creation time, they are snapshot iterators: they see a consistent view of the list as it was when iteration began, but they never observe elements added later, and the iterator's `remove()` method is unsupported and throws. The strategy trades write cost for read safety: every mutation is O(n) due to the full array copy and allocates a new array, so garbage collection pressure rises with write frequency. Consequently, copy-on-write collections are only appropriate for read-dominated workloads — configurations, listener/observer registries, or cache lists read by many threads and mutated rarely. Concurrent reads are fully scalable because there is no shared mutable state to contend on. The copy-on-write trick is a general concurrency technique (also used by `java.awt` and `javax.swing` event-listener lists and by functional data structures) that converts "many readers, rare writers" into a contention-free read path at the price of O(n) writes. The key mental model: writes are serialized and expensive, reads are cheap and always consistent with *some* recent snapshot.

22. When would you use `ArrayList`?
    - **Answer:** `ArrayList` is the default choice for any ordered, indexable, primarily-read collection of objects. It should be used when the dominant operations are indexed access (`get(i)`), iteration, and appending to the end, all of which are O(1) — random access is O(1), iteration benefits from contiguous memory and CPU cache prefetching, and end-appends are amortized O(1) because the backing array grows geometrically (in Java, new capacity ≈ old + old/2). Insertions or removals in the middle are O(n) due to element shifting, so `ArrayList` is wrong for workloads dominated by frequent mid-list mutation. It supports `null` elements, allows duplicates, preserves insertion order, and is not thread-safe; the concurrent alternative for read-heavy sharing is `CopyOnWriteArrayList`, and for stack/queue semantics `ArrayDeque` often fits better. Memory overhead is minimal: a single object array plus a small header, versus a node object plus two references per element for `LinkedList`. A few implementation details are worth knowing: `toArray(new T[0])` is the recommended fast conversion because the size-zero array lets the method allocate exactly the right length (the `size > 0` overload has a JVM intrinsic), `subList()` returns a live view whose modifications write through to the parent (and which invalidates on structural change of the parent), and `ensureCapacity(n)` can pre-grow the array when a large batch of appends is coming. The growth strategy is amortized: although a single `add` may trigger an O(n) array copy and reallocation, across n appends the total cost stays O(n), giving the average O(1) cost. In practice, for virtually any ordered collection in application code, `ArrayList` is the right starting point and the burden of proof lies on any alternative.

23. When would you use `LinkedList`?
    - **Answer:** `LinkedList` should be used only for workloads that genuinely require constant-time insertion and removal at *both* ends — because it implements both `List` and `Deque`, it offers `addFirst`, `addLast`, `removeFirst`, and `removeLast` at O(1). Even then, `ArrayDeque` is generally superior for pure stack/queue semantics because it provides the same O(1) end operations with a contiguous array, dramatically better cache locality, and lower per-element memory. The classic textbook justification — O(1) insertion in the middle — rarely holds in practice because `add(index, e)` first must traverse O(n) nodes to locate the insertion position; only if the node is already in hand (e.g. during a forward scan) does insertion avoid the traversal. Random access is O(n): `get(index)` walks from whichever end of the chain is nearer, so indexed loops over a `LinkedList` become accidentally quadratic. Memory overhead is heavy: each element is a node containing two references (`prev`, `next`), the payload reference, and object header padding, roughly tripling per-element storage compared to `ArrayList`. Cache behavior is poor because nodes are heap-allocated independently and scattered in memory, so sequential iteration causes a cache miss per node, typically making even iteration several times slower than `ArrayList`. Each `LinkedList` method is not thread-safe and requires external synchronization, like `ArrayList`. The honest conclusion is that in backend and application code, `LinkedList` is almost never the right answer — its O(1) end operations are better served by `ArrayDeque`, its indexed operations are dominated by `ArrayList`, and its only real niche is when a single structure must act as both a deque and an indexed list with frequent insertions at arbitrary positions while holding node references. The interview takeaway is understanding precisely *why* `LinkedList` loses: node-pointer overhead, cache misses, O(n) indexing, and the fact that modern memory hierarchy punishes pointer-chasing far more than textbook complexity analysis suggests.

24. When would you use `ConcurrentHashMap`?
    - **Answer:** `ConcurrentHashMap` is the right choice whenever a map will be read and written by multiple threads and correctness under concurrent access matters. It provides thread-safe `put`, `get`, `remove`, and atomic compound operations like `computeIfAbsent`, `compute`, `merge`, and `putIfAbsent` — so patterns such as per-key counters (`merge(k, 1, Integer::sum)`) and cache-aside loading (`computeIfAbsent(k, loader)`) are safe without external locking. Its Java 8 design uses CAS for empty-bucket insertions and `synchronized` on the head node of non-empty buckets, so writers to different buckets proceed in parallel, while readers are entirely lock-free; this scales to high core counts where a globally locked `HashMap` or `Collections.synchronizedMap` would collapse into a serialization bottleneck. It is ideal for shared caches, session stores, registries, and accumulating statistics in multi-threaded services. It forbids `null` keys and values, so pre-validation is needed if null must be representable. Iteration is weakly consistent and never throws `ConcurrentModificationException`, making it safe to iterate while other threads mutate — useful for cache eviction, reporting, and periodic snapshots — though updates made during iteration may or may not be seen. The tradeoffs: modest per-entry memory overhead for the internal nodes and atomic support, plus the fact that the default view reflects a snapshot rather than a strictly serializable ordering. When writes are extremely rare and reads dominate, a `HashMap` with external `ReadWriteLock` or an immutable map refreshed via volatile reference can be faster; when updates to the same keys are heavy, per-key contention still exists. For general multi-threaded map usage, though, `ConcurrentHashMap` is the standard, battle-tested default and the replacement for `Hashtable` and `Collections.synchronizedMap` in new code.

25. When would you use `TreeMap`?
    - **Answer:** `TreeMap` is the correct choice when keys must remain sorted at all times or when range-based, navigable queries over an ordered key space are needed. It implements `NavigableMap`/`SortedMap`, so beyond iteration it provides `firstKey()`/`lastKey()`, `floorKey()`/`ceilingKey()`/`lowerKey()`/`higherKey()` for nearest-key lookups, and the live range views `subMap(from, to)`, `headMap(to)`, and `tailMap(from)` — which make prefix scans and "all keys in a window" queries O(k + log n) instead of an O(n) filter over a full collection. Ordering is maintained by a red-black tree, so every `put`/`get`/`remove` costs O(log n), and the ordering can come from natural `Comparable` ordering or an explicit `Comparator` supplied at construction. It is the standard map for time-ordered data (events keyed by timestamp), sorted leaderboards, and any component that must present keys in sorted order repeatedly — because a `HashMap` would require an O(n log n) sort on every read, a `TreeMap` amortizes the sorting cost into each insertion. Because the map must compare keys, `null` keys are rejected, and the comparator's notion of equality governs duplicate keys. The memory cost is higher than `HashMap`: each entry is a tree node with left/right/parent references and a color bit, plus the overhead of rebalancing rotations during writes. When only final sorted output is needed — not repeated sorted access — collecting into a `HashMap` and sorting once at the end is cheaper. If a sorted map must be shared across threads, the equivalent concurrent implementation is `ConcurrentSkipListMap`, which offers the same navigable API with lock-free reads and O(log n) writes. The decision rule: needs sorted iteration, range scans, or nearest-neighbor queries → `TreeMap`; needs raw lookup speed with no ordering requirement → `HashMap`.

26. How does `HashSet` work internally?
    - **Answer:** `HashSet` is built on top of a `HashMap`; it holds a private `HashMap<E, Object> map` and every `add(e)` calls `map.put(e, PRESENT)`, where `PRESENT` is a single shared dummy `Object` constant used as the value. Because `HashMap` keys are unique, `add()` returns `true` only when the element was not already present (the underlying `put` returns `null`), and returns `false` when the element already exists — this is exactly the `boolean` contract `Set.add` promises. Uniqueness is therefore delegated entirely to the `HashMap`'s key contract: two elements are considered the same when their `hashCode()` values match *and* their `equals()` returns true; if two objects are logically equal but produce different hash codes, both will be stored. `contains(e)` is implemented as `map.containsKey(e)` and inherits the map's hashing, bucket-index masking, collision resolution (linked list, then red-black tree past 8 nodes), and amortized O(1) average lookup; `remove(e)` similarly delegates to `map.remove(e)`. All the `HashMap` tuning knobs apply: the underlying map uses the default initial capacity of 16, load factor 0.75, geometric doubling on resize, and Java 8's split-based redistribution, so a `HashSet` inherits the same performance profile and the same requirement that elements be effectively immutable in order to keep their hash stable. `Iterator` over a `HashSet` is fail-fast and reflects the backing map's iteration order, which is unspecified and unstable across resizes. The design extends naturally: `LinkedHashSet` subclasses `HashSet` by overriding the backing map with a `LinkedHashMap` (insertion-order iteration at O(1) cost), and `TreeSet` is a separate class backed by a `TreeMap` for sorted iteration at O(log n) per operation. This reuse means `HashSet` ships with zero additional hashing logic — every behavior is inherited from the map it wraps. The practical consequence for callers: correctness demands consistent, well-distributed `equals()`/`hashCode()`, and choice of set implementation is really a choice of backing map.
