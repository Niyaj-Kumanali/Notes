## Answers

1. What is Redis?
   - **Answer:** Redis is an open-source, in-memory data structure store that operates as a key-value database, cache, message broker, and stream engine. It keeps the entire dataset in RAM, which gives it sub-millisecond read and write latency, far faster than a disk-backed relational database. Because everything lives in memory, capacity planning and persistence strategy become important design decisions rather than afterthoughts. Redis supports a rich set of data structures — strings, hashes, lists, sets, sorted sets, bitmaps, hyperloglogs, geospatial indexes, and streams — each with its own specialized commands. It also provides built-in features such as key expiry with TTL, configurable eviction policies, pub/sub messaging, Lua scripting, and atomic operations that make many distributed-systems problems tractable. Data can be persisted to disk using either RDB snapshots or the AOF append-only log, or both, so Redis is not purely volatile despite being memory-resident. It typically runs as a standalone daemon, a master-replica pair for replication, a Sentinel-managed high-availability setup, or a Redis Cluster for automatic sharding. In a Java/Spring ecosystem, it is commonly wired in as the backing store behind Spring Cache and Spring Session abstractions. Redis is single-threaded for command execution, which removes locking overhead and guarantees that each individual command runs atomically. That single-threaded model, combined with event-loop-based I/O, is why simple operations execute so quickly and why the command set is carefully kept fast and non-blocking. Redis is therefore a general-purpose tool that solves caching, session sharing, distributed locking, rate limiting, and lightweight messaging, and it is one of the most widely deployed components in modern backend architectures.

2. Why use Redis?
   - **Answer:** Redis is used when an application needs extremely low latency access to frequently read data, shared state across many service instances, or a small set of distributed primitives without building them from scratch. Because data lives in memory, reads that would otherwise hit a database return in microseconds to low milliseconds, which is orders of magnitude faster than typical SQL queries. Its data structures cover many common needs directly: strings for simple cache entries, hashes for object fields, sorted sets for rankings and rate limiting, lists for queues, and streams for log-like message flows. Built-in TTL and eviction policies mean expired or memory-pressured entries are handled by the server rather than by application code. Redis also supports atomically safe operations such as `INCR`, `SETNX`, and Lua scripts, which are the foundation of distributed counters and locks. Compared with Memcached, Redis offers richer data structures, persistence, replication, and pub/sub, which makes it a better fit for anything beyond a pure key-value cache. Compared with an in-memory cache like a HashMap or Caffeine, Redis is shared across all application instances, so every node sees the same state, which is essential when sessions, locks, or cached data must be consistent cluster-wide. It also decouples the cache lifecycle from the application process, so restarts and redeploys do not wipe the cache. The trade-off is that Redis is another server to operate and monitor, and its memory footprint must be sized and managed. When a system has multiple stateless instances that need a common cache, session store, or lock, Redis is the pragmatic default choice. In short, Redis is chosen for speed, shared state, rich data structures, and battle-tested distributed features that would otherwise require significant custom engineering.

3. What data types does Redis support?
   - **Answer:** Redis supports strings, hashes, lists, sets, sorted sets, bitmaps, hyperloglogs, geospatial indexes, and streams, each designed for a distinct access pattern. Strings are byte arrays used for plain cache values, counters via `INCR`/`DECR`, and the building blocks for distributed locks. Hashes map fields to values within a single key and are ideal for storing objects — user profiles, sessions, or any record where only a few fields are read or updated at a time without serializing the whole object. Lists are ordered collections supporting push/pop on both ends, used for simple queues, recent-activity feeds, and message queues with `LPUSH`/`BRPOP`. Sets store unique, unordered strings and support fast membership checks and set algebra such as union, intersection, and difference, which suits tags, friends lists, and deduplication. Sorted sets associate each member with a score and keep members ordered by that score, enabling leaderboards, ranking systems, rate limiting, and range queries like "top N by temperature deviation". Bitmaps treat a string as an array of bits and are memory-efficient for presence tracking, such as daily-active-user flags. Hyperloglogs approximate the cardinality of a large set in constant memory, useful for counting unique visitors without storing every value. Streams are append-only log structures with consumer groups, message IDs, and acknowledgments, providing Kafka-like messaging inside Redis. The key design principle is to choose the data type that maps to the access pattern, because Redis command complexity and memory usage vary dramatically between types. For example, storing a session object as a string forces full serialize/deserialize on every touch, while a hash allows field-level reads and writes. This structural richness is one of the main reasons Redis outgrows a plain key-value cache role and is used as a general-purpose data layer.

4. What is cache?
   - **Answer:** A cache is a high-speed storage layer that holds copies of frequently accessed data so that subsequent requests can be served without recomputing or re-fetching from a slower source. The fundamental trade-off is capacity versus speed: the primary store (a database, remote API, or expensive computation) is authoritative but slow, while the cache is fast but limited in size and not authoritative. Caching exploits the observation that access patterns are skewed — a small fraction of data typically receives most of the traffic, so a relatively small cache yields a large hit-rate. A cache is useful only when data is read far more often than it changes, and when serving a slightly stale copy is acceptable for some period. In a typical web architecture, caches exist at multiple levels simultaneously: browser caches, CDN edge caches, HTTP reverse-proxy caches, application-level in-memory caches, and distributed caches like Redis or Memcached. The same logical data may exist in several of these layers, which makes consistency management the central challenge of any caching design. Key decisions when introducing a cache are the cache population strategy (lazy vs. eager), the invalidation strategy (TTL vs. explicit delete vs. write-through), the consistency requirements, and the failure behavior when the cache goes down. A cache that silently serves stale data can produce subtle bugs, so every cacheable piece of data must be evaluated for how much staleness is tolerable. Caching also introduces operational concerns such as monitoring hit rate, sizing memory, and planning for cold starts after a restart. Done well, a cache reduces database load, lowers latency, and improves throughput; done carelessly, it adds stale data, serialization overhead, and a new point of failure. The goal is always to reduce the number of expensive operations to the smallest set that still satisfies correctness.

5. What is cache-aside pattern?
   - **Answer:** In the cache-aside (lazy-loading) pattern, application code is responsible for interacting with the cache and, on a miss, loading the data from the primary store and populating the cache itself. The read path is: check the cache for the key; if present, return the value; if absent, query the database, store the result in the cache with an appropriate TTL, and return it. The write path is: update the database, then invalidate the cache key (or update it), so that the next read repopulates from fresh data. The biggest advantage is simplicity and control — the application decides exactly what gets cached, under what key, and with what TTL, with no dependency on a cache-provider abstraction. It is also resilient: if the cache is unavailable, the application simply reads from the database directly, so the cache is not a hard dependency. The main drawback is that cache misses are more expensive because two round trips occur on a miss, and if the population logic is not idempotent or protected, a burst of misses can hammer the database. Cache-aside also risks serving stale data if the invalidation step is missed, so the pattern is normally paired with TTL as a consistency backstop. It is easy to implement with Spring by annotating a service method with `@Cacheable`, which produces the same check-then-load-then-store flow. Because the cache is filled lazily, the first request after a cache flush or restart experiences the full latency of a database query. Cache-aside is the most commonly used caching strategy in application code, and most teams combine it with a write-through or explicit-invalidation step for update-heavy flows. The key discipline is ensuring that every cache update path and every invalidation path are audited, because a single missed delete leaves a stale entry until its TTL expires.

6. What is read-through cache?
   - **Answer:** In the read-through pattern, the cache itself is responsible for loading data from the database on a miss, so the application simply asks the cache for a key and never writes caching logic itself. Redis does not natively implement read-through; it is a dumb store that only serves what was explicitly written. The pattern must be layered on top, for example via Spring's `@Cacheable` abstraction, where a configured `CacheLoader` or the annotated method's logic performs the load-and-populate step transparently. From the caller's perspective, reads look identical whether the data is cached or fetched fresh — there is no branching logic in application code. This removes duplicated caching code from every read site and centralizes the caching policy in one configuration, which reduces the chance of inconsistent key naming or forgotten cache population. The downside is reduced flexibility: the cache defines how data is loaded, so it is harder to customize per-request behavior, decide which fields to store, or apply business-specific rules during population. Read-through is essentially cache-aside where the loading logic has been moved into the cache layer, so the two are often confused in interviews. Because every miss triggers a synchronous load, read-through still suffers the "thundering herd" risk if a popular key expires, unless the cache supports single-flight or locking around the load. It also requires careful sizing because the cache now holds the key structure of the dataset, and misconfigured TTLs can silently serve stale data. The pattern shines when the dataset is well-understood, the load logic is uniform, and the team wants a clean separation between data access and caching concerns. Many production systems start with cache-aside and later move to a read-through abstraction as the number of read sites grows.

7. What is write-through cache?
   - **Answer:** In the write-through pattern, data is written to both the cache and the database in the same request, so the cache entry is updated atomically alongside the authoritative write. The write path becomes: update the database, then update (or invalidate) the cache entry within the same transaction or logical operation. Because the cache is updated on every write, subsequent reads always hit fresh data, which eliminates the window of staleness that cache-aside creates between a database update and the next cache read. The trade-off is that write latency increases because every write now performs two operations, and the cache stores data that may never be read again, wasting memory. Write-through also needs careful handling of transaction rollback: if the database write succeeds but the cache update fails, the two stores diverge, so compensating logic or a background reconciler is required. In Spring, this is commonly implemented by combining `@CachePut` (which always writes to the cache) or an explicit `@CacheEvict` call inside a service method that performs the database write. Some teams prefer to invalidate on write rather than update, so that the next read lazily fetches fresh data; this is cheaper than computing and writing the new value when the entry may not be read often. Write-through is best suited to data that is written and read frequently, where staleness is unacceptable, such as configuration, account balances, or status fields that other components depend on immediately. It is a form of eager caching, meaning the cache is always warm for the data being written, at the cost of extra write-path work. A common hybrid is write-through for critical entries plus a short TTL as a final safety net against missed invalidations. The main lesson is that write-through buys consistency by moving work into the write path, so its cost must be justified by the read freshness it provides.

8. What is write-behind cache?
   - **Answer:** In the write-behind (write-back) pattern, data is written to the cache immediately and acknowledged to the caller, while the actual database persistence is deferred and batched asynchronously by a background process. This makes writes extremely fast because the caller is not blocked on disk I/O, and it allows many small updates to be coalesced into fewer, larger database writes, which dramatically reduces write load. The fundamental risk is data loss: if the cache crashes or the process dies before the deferred writes are flushed, all pending updates are lost, which is why write-behind is used only for data where loss is tolerable. It also creates a consistency window during which the cache has newer data than the database, so any process reading the database directly sees stale values. Typical use cases are counters, analytics events, activity logs, heartbeats, or sensor telemetry where dropping a small amount of recent data is acceptable and throughput matters more than durability. In a Redis-based implementation, updates are written to a Redis list or stream acting as a buffer, and a consumer drains the buffer into the database in batches. The consumer must be designed for idempotency because at-least-once delivery can reprocess the same item after a failure. Flush timing, batch size, and failure retry policies determine the durability and freshness trade-offs, and a shutdown hook should flush the pending queue on graceful stop. Write-behind is the opposite of write-through on the consistency spectrum: write-through prioritizes consistency at the cost of write latency, while write-behind prioritizes write throughput at the cost of durability. Because of the data-loss risk, regulatory or compliance-sensitive data should generally never be written via a write-behind cache. The pattern is powerful for absorbing high-frequency writes, but it shifts complexity into the flush pipeline and should only be adopted when the durability requirement is explicitly relaxed.

9. What is TTL?
   - **Answer:** TTL (Time To Live) is the duration for which a cached key is considered valid before Redis automatically deletes it, providing the standard expiration mechanism for cached data. When a key is set with an expiry, Redis removes it after the interval elapses, so the next read misses and repopulates from the source of truth. TTL is the primary consistency backstop for caching: it guarantees that even if explicit invalidation is missed, stale data eventually disappears and the cache heals itself. The choice of TTL is a business decision that balances freshness against database load — a short TTL keeps data current but causes frequent repopulation, while a long TTL reduces load but serves potentially stale values. Good TTL tuning considers how often the underlying data changes, how quickly users notice staleness, and how expensive a cache miss is. Data that changes rarely, such as reference or configuration data, may get a long TTL of hours or days, while volatile data like live sensor readings or prices gets seconds. A common technique is to add random jitter to TTLs so that keys do not expire simultaneously, which avoids an avalanche of concurrent cache rebuilds. Redis implements expiration lazily (on access) and actively (a background cycle samples expiring keys), and expired keys can be removed from memory immediately or on a time-based schedule. A key without a TTL lives forever until evicted by memory pressure or explicitly deleted, which is a common source of memory leaks in misconfigured caches. In Spring Cache with Redis, the TTL is configured globally through `RedisCacheManager` or per cache via `CacheConfiguration` / `RedisCacheWriter`. TTLs should always be set on cached data, even when explicit invalidation exists, because the TTL is the safety net that bounds how long incorrect or stale data can survive.

10. What is cache eviction?
    - **Answer:** Cache eviction is the automatic removal of keys when memory usage exceeds the configured `maxmemory` limit, governed by a `maxmemory-policy` that decides which keys to sacrifice. Because a cache is finite, eviction ensures the most valuable data stays resident while less useful entries are dropped to make room for new writes. Redis provides several eviction policies: `noeviction` (reject writes with an error when full), `allkeys-lru` / `volatile-lru` (evict least recently used keys, globally or only among keys with a TTL), `allkeys-lfu` / `volatile-lfu` (evict least frequently used keys), `allkeys-random` / `volatile-random`, and `volatile-ttl` (evict keys closest to expiry). The volatile-* policies ignore keys that have no TTL, making them safer when permanent keys must survive memory pressure. LRU approximates recency by sampling a small subset of keys (configurable with `maxmemory-samples`) rather than tracking exact access order, which keeps memory overhead low. LFU tracks access frequency and evicts rarely used keys even if they were recently accessed, which suits workloads with a stable popular set and long-lived low-use keys. Eviction is distinct from TTL expiry: expiry removes keys whose lifetime is over, while eviction removes live keys because of resource constraints. Choosing a policy requires understanding the access distribution — LRU is a good general default for caching workloads, LFU fits when a hot set persists, and `noeviction` is appropriate when Redis stores data that must never be silently dropped. Monitoring the `evicted_keys` metric reveals whether the cache is oversized or the policy is wrong, since heavy eviction degrades hit rate and causes more database traffic. The key point is that eviction is a controlled degradation mechanism: it protects the process from out-of-memory crashes by sacrificing cache quality.

11. What is LRU?
    - **Answer:** LRU (Least Recently Used) is a cache eviction policy that removes the entry whose last access was furthest in the past, on the theory that data not touched recently is least likely to be touched soon. It is a reasonable approximation of the working set because most access patterns show temporal locality: items accessed recently are likely to be accessed again. An exact LRU implementation must track access time for every entry and maintain ordering on each access, which has both CPU and memory costs. Redis avoids that by implementing an approximate LRU: it samples `maxmemory-samples` keys (default 5) when eviction is needed and evicts the least recently used among the sample, which is statistically close to true LRU at a fraction of the cost. The approximation works well in practice because the sample size and cache size are large enough that the odds of keeping a genuinely cold key are small. Redis also performs eviction from the samples of keys that are already "near" expiry when using volatile policies, further biasing toward dropping soon-to-be-invalid data. LRU can be a poor fit when access patterns are periodic or when items are accessed heavily but then become permanently cold — in those cases LFU or a long-TTL strategy may be better. Configuring LRU in Redis is just setting `maxmemory` and `maxmemory-policy allkeys-lru` in `redis.conf` or via `CONFIG SET`. The effect of LRU in a real system is that the working set stays hot, cache hit rate remains high, and the cache self-tunes to whatever data is currently popular. The main limitation is that LRU ignores frequency, so a batch of one-time accesses can push out a frequently used item that has not been touched in a moment.

12. What is cache stampede?
    - **Answer:** A cache stampede, also called a thundering herd, occurs when a popular cache key expires and a large number of concurrent requests miss the cache simultaneously, all of which fall through to the database or origin service at once. Because those requests all arrived together, one of them does not get a chance to repopulate the cache before the others begin their own expensive lookups. The result is a sudden spike in database load that can multiply response times, exhaust connection pools, and even take the database down. The scenario is most dangerous with TTL-based expiry because every request that was hitting the warm cache becomes a miss in the same instant. A stampede is not limited to a single key — if many keys expire at the same moment, the effect is amplified into a cache avalanche. The core problem is redundant work: N requests all perform the identical expensive computation when only one result is needed. It is especially severe with endpoints that compute derived data, like aggregations or reports, because each rebuild is expensive. The same failure mode can be triggered by a cache restart or a deployment that flushes the cache, since a cold cache makes the entire read path miss at once. Measuring the problem is straightforward: after a TTL boundary, database query rate and latency spike sharply. Prevention strategies include locking so only one thread rebuilds, TTL jitter to desynchronize expiry, and early recomputation to refresh the entry before it expires. The fundamental goal is to ensure that at most one request performs the expensive rebuild, and everyone else waits for or reuses its result.

13. How do you prevent cache stampede?
    - **Answer:** The standard prevention is to serialize the cache rebuild with a lock, often called single-flight or request coalescing, so only one thread performs the expensive load and the rest reuse the result. With Redis, a distributed lock can be acquired with `SET key value NX PX 3000` — the `NX` flag makes the set succeed only if the key does not exist, and `PX` gives it a short TTL as a deadlock guard if the holder crashes. On a miss, each request tries to acquire the lock; the winner loads from the database, writes the cache, and releases the lock, while the losers wait briefly and then read the cache again, now populated. A second technique is TTL jitter: add a small random offset to each key's TTL so that keys expire at slightly different times, spreading cache rebuilds and avoiding simultaneous expiry of related keys. A third is early recomputation: when serving a cached value, check whether the entry is close to expiring, and if so, trigger an asynchronous refresh in the background, so the cache never empties at all. For read-through caches, the cache layer should implement per-key locking so concurrent misses on the same key are collapsed into one load. A complementary approach is a "probabilistic early expiration" where the refresh probability grows as the entry ages, achieving the same effect without timers. In Spring Cache, the abstraction does not provide built-in stampede protection, so this is often implemented with a `CaffeineCache` backed by a manual lock or a custom `CacheLoader`. The lock's TTL is critical: too short and a slow rebuild is unprotected, too long and it blocks legitimate rebuilds after a crash. Beyond locking, reducing the cost of a rebuild (e.g., using a summary table or precomputed aggregate) shrinks the blast radius of any remaining stampede. The comprehensive defense is layered: jitter to avoid coordinated expiry, locking to collapse redundant rebuilds, and early refresh to eliminate the empty window entirely.

14. What is cache penetration?
    - **Answer:** Cache penetration happens when requests arrive for keys that do not exist in the cache and also do not exist in the underlying database, so every request falls through both layers and the cache never gets a chance to help. The cache miss is not followed by a cache population, because there is nothing to store, so the same invalid request repeats the full database lookup every time. This is different from a stampede, which involves valid data that is temporarily absent from the cache; penetration is fundamentally about requests for data that can never be found. It is often caused by user-facing APIs that accept arbitrary identifiers — a client requesting a nonexistent product ID, an out-of-range sensor ID, or a deleted record can trigger an unlimited number of identical expensive queries. In the worst case it is malicious, where an attacker deliberately generates random or invalid IDs to force the database into constant useless work. The standard mitigation is to cache negative results: store a short-lived placeholder (an empty value, a null marker, or a "not found" sentinel) so repeated requests for the same invalid key are served from the cache and never reach the database. A second approach is to pre-validate identifiers at the API boundary — reject obviously malformed or out-of-range keys before they ever reach the caching layer. A third is a Bloom filter that holds all existing keys; a query whose key is not in the filter is rejected as certainly absent without touching the database, while false positives just become normal misses. The negative-caching approach is simplest but must be paired with a short TTL so that a record created moments after an invalid check is not masked for too long. Combining input validation, negative caching, and optionally a Bloom filter makes penetration attacks largely harmless. The goal is to guarantee that the database is never queried for a key that the system already knows cannot exist.

15. What is cache avalanche?
    - **Answer:** A cache avalanche occurs when a large proportion of cache keys expire or are invalidated at roughly the same time, causing a massive burst of requests to fall through to the database simultaneously and overwhelm it. It differs from a stampede in scale: a stampede hits one popular key, while an avalanche hits many keys at once, so the load spike is aggregate rather than per-key. The most common trigger is a uniform TTL: if all keys are set with the same expiry interval at roughly the same time (for example, every entry cached with a 30-second TTL after a cache flush), they all die together and the entire read path turns into a full database rebuild at once. A scheduled batch job that refreshes the cache, a bulk deployment that restarts services, or an explicit cache flush can produce the same synchronized miss. The second common trigger is a Redis restart or failure: a warm cache suddenly becomes an empty cache, and every key misses simultaneously until the cache repopulates. The damage is visible as a latency cliff and a database CPU or connection spike that can cascade into timeouts and downtime. The primary mitigation is TTL jitter — add a random offset to each key's TTL so expiry times are spread across a window instead of clustering. Another is to warm the cache proactively after a restart, for example by a startup job that repopulates the hot keys before traffic is routed to the instance. A third is to fall back to a secondary store or a degraded mode (like serving a stale value) instead of hitting the database when the cache is empty. Replica read strategies and request queuing can also absorb the spike, but the cleanest solution is to prevent synchronized emptiness in the first place. The core principle is that cache expiry should be statistically spread out, and cache failures must degrade gracefully rather than converting all reads into database writes.

16. How do you invalidate cache?
    - **Answer:** Cache invalidation removes or refreshes a cached entry when the underlying data changes, and there are several strategies that are often combined. The simplest is TTL-based expiry, where the entry self-invalidates after a fixed duration, bounding staleness without any explicit action — but this means data can be stale for up to the full TTL. The most precise is explicit invalidation: when a write occurs, the application deletes the affected cache key (or re-populates it) so the next read fetches fresh data. In Spring this is done with `@CacheEvict(cacheNames = "products", key = "#id")` on the update method, or `@CachePut` to overwrite the entry with the new value in the same transaction. A common concern is that the cache and database can become inconsistent if the invalidation is skipped, so invalidation should happen in the same transaction or after a successful commit, and a short TTL should remain as a backstop. For bulk changes that affect many keys, individual deletion is impractical, so teams use a version prefix in the key, such as `product:123:v2`, and bump the version once to invalidate an entire generation of entries. Another approach is event-driven invalidation: publish a cache-eviction event when data changes, and let all service instances observe it and drop the affected keys, which keeps cache state consistent across a distributed deployment. There is also the pattern of invalidating on write rather than updating, which lazily repopulates only if the entry is actually read again — cheaper when writes outnumber reads. The "publish update, then delete cache" order matters: deleting before the database commit can recreate stale data if a concurrent read repopulates from the old snapshot. Because perfect invalidation is hard, mature systems rely on layered defenses: explicit eviction for known changes, TTL as a bounded-staleness guarantee, and version keys for bulk invalidation. The goal is to minimize the window during which a cached value disagrees with the source of truth, while keeping invalidation cheap and correct under concurrency.

17. What should not be cached?
    - **Answer:** Data should not be cached when staleness is unacceptable, when it is highly personalized and read only once, when it is too large to store economically, or when it is sensitive enough that retention and exposure create risk. Real-time data whose value changes constantly and where decisions depend on the latest value — like live sensor alarms, stock prices, or safety-critical state — should not be served from a cache, because even a short TTL introduces a window of incorrect behavior. Highly sensitive data such as raw passwords, cryptographic keys, personal health records, or financial details should be cached only with strict access control, encryption, and short TTLs, and often not at all, because the cache becomes an additional attack surface and a retention problem. Single-use data, such as one-time tokens, OTPs, or per-user ephemeral state, gets no benefit from caching because each item is read once, and caching it only wastes memory. Huge payloads, such as large binary files or unbounded query result sets, are usually cached poorly because they displace many small high-value entries and bloat memory; they belong in object storage or a CDN instead. Data that changes faster than the cache can refresh — where invalidation cannot keep up with writes — should be served directly or updated through write-through. Session data, volatile and user-specific, is normally kept out of a shared cache or handled specially by a dedicated session store rather than a general cache. Similarly, data governed by compliance rules around personal data access logs or right-to-erasure is awkward to cache because eviction and audit become harder. Anything whose staleness could cause financial loss, safety incidents, or compliance violations needs an explicit argument for why caching is safe, not just "it improves performance." The practical rule is to cache only data that is read often, changes rarely, is small enough to be economical, and can tolerate a bounded staleness window.

18. How do you cache API responses?
    - **Answer:** API responses are typically cached by annotating the service-layer method that produces the response with Spring's `@Cacheable`, which stores the returned object under a key derived from the method arguments. For example, `@Cacheable(cacheNames = "sensors", key = "#sensorId")` on a method that returns the latest temperature causes Spring to check the cache before executing the method body, and to store the result on a miss. The cache names in the annotation map to logical caches, which `RedisCacheManager` backs with Redis keys, so the response survives across application instances and restarts. The TTL is configured per cache or globally — in Spring Boot with `spring.cache.redis.time-to-live=30s` — so each response is automatically invalidated after the configured window. Key construction must be explicit to avoid collisions: composite keys like `#sensorId + '-' + #dateRange` separate entries for different arguments, and a version prefix can scope the whole cache generation. A critical detail is serialization: the cached object must be serializable and the chosen serializer (typically JSON via `GenericJackson2JsonRedisSerializer`) must round-trip the response type correctly. The caching boundary matters: caching at the service layer (behind controllers) keeps HTTP headers, authentication, and per-user variation out of the cache, whereas caching at the HTTP layer would store shared, unauthenticated responses. Responses that vary by user, locale, or authorization should either be excluded from the cache or cached with the varying factor in the key, otherwise one user sees another user's data. Cache-aside semantics apply automatically: the response is served from Redis until the TTL expires, and invalidation is handled by `@CacheEvict` on mutation methods. Monitoring hit rate and the origin API's load lets the team tune TTL and key coverage. The benefit is dramatic: hot responses shift from tens or hundreds of milliseconds of computation and I/O to a sub-millisecond Redis read, at the price of controlled staleness.

19. How do you cache database queries?
    - **Answer:** Database query results are cached by wrapping the repository or service call that executes the query in a cache, most idiomatically with `@Cacheable` around a repository method in Spring Data. For example, a method `findGatewayConfig()` returning rarely changing configuration can be annotated `@Cacheable(cacheNames = "configs", key = "#root.methodName")`, so repeated calls short-circuit before hitting the database. The general rule is to cache at the service layer rather than at the SQL layer, so the cache stores the assembled domain objects and the key reflects the business parameters, not the raw SQL text. Read-heavy queries with low write frequency — reference data, configuration, lookup tables, and computed summaries — are ideal candidates, because a high read-to-write ratio makes the cache's hit rate worthwhile. The TTL should be aligned with how often the underlying data changes; for stable reference data, an hour or more is reasonable, while live operational data needs seconds. The main risk is staleness: if the query result is cached for an hour and the data changes, callers see old values, so mutations must be paired with `@CacheEvict(cacheNames = "configs", allEntries = true)` (or keyed eviction) to invalidate immediately. A per-key or per-parameter invalidation is preferable when possible, and `allEntries = true` is a blunt instrument that should be used when many rows can change at once. Caching the results of aggregation queries is especially powerful because those are the most expensive to recompute, but the aggregate must be recomputed whenever any contributing row changes, which often pushes teams toward event-driven eviction. It is also important to cache only the data actually needed by the response and to avoid caching unbounded pagination results. With Redis as the backing store, query caching distributes the benefit across all instances and survives application restarts. The combination of `@Cacheable` for reads and `@CacheEvict` on writes gives an effective, low-code caching layer for a database-backed service.

20. How do you use Redis for session storage?
    - **Answer:** Redis is used for session storage by making it the backing store behind the Spring Session abstraction, so user session state lives in Redis instead of in each application instance's local memory. With the `spring-session-data-redis` dependency, the configuration is just `spring.session.store-type=redis` plus a session timeout, and Spring Session automatically routes session reads and writes through Redis. For a classic servlet stack, `@EnableRedisHttpSession` registers a filter that intercepts `HttpSession` usage and persists it; for reactive stacks, `@EnableRedisWebSession` does the equivalent. The value of external session storage is horizontal scalability: with in-memory sessions, a load balancer must pin a user to one instance (sticky sessions), and that instance dying loses every session it held. With Redis-backed sessions, any instance can serve any user, so instances can be added and removed freely and requests can be routed without affinity. Session data is stored as Redis hashes under keys like `spring:session:sessions:<id>`, and Spring Session also maintains expiry-index keys so that expired sessions are cleaned up. Serialization is a design decision: default JDK serialization works but is verbose and not cross-language, while a JSON serializer (`GenericJackson2JsonRedisSerializer`) is smaller and interoperable, at the cost of needing the session attributes to be JSON-serializable. Multi-server deployments must share one logical session store, which is naturally satisfied by Redis in front of a replica or Sentinel. The session timeout is configured separately from cache TTLs, typically minutes to hours depending on the application, and is enforced by Redis key expiry. Common pitfalls include session attribute bloat (storing large objects in session), missing serializability, and keeping long-lived sessions that hold memory long after the user leaves. Redis session storage is a standard way to make stateless application tiers truly stateless while retaining user state across the cluster.

21. How do you use Redis for distributed locking?
    - **Answer:** Redis distributed locking ensures that only one process across all instances can hold a lock for a given resource at a time, using the atomic `SET key value NX PX <ms>` command. The `NX` flag makes the set succeed only if the key is absent, which atomically claims the lock, and `PX` attaches a TTL so a crashed holder's lock expires automatically and cannot deadlock the system. A correct implementation first acquires the lock with a unique token (e.g., a UUID), performs the critical section, and then releases with a Lua script that compares the token before deleting — `if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end` — so that a holder can never delete a lock that has been re-acquired after its own lock expired. The TTL must be long enough for the critical section to finish under worst-case load, because if the lock expires early, two processes may hold it concurrently. A common pattern is the Redisson client, which implements this correctly and also supports lock renewal (watchdog), so a long-running critical section keeps refreshing the lock and avoids premature expiry. This pattern is used to prevent duplicate processing of the same event across consumer instances, to serialize a cache rebuild, to schedule a job on exactly one node, or to protect a non-atomic read-modify-write sequence. A single-node Redis lock has a failure window: if the master dies after the lock is granted, a failover can cause two nodes to believe they hold the lock. The Redlock algorithm extends this by acquiring the lock on multiple independent Redis masters and requiring a majority, which provides a stronger guarantee at the cost of complexity and more infrastructure. In practice, many systems accept single-node locking when the guarded operation is idempotent, so even a rare double-execution is harmless. Distributed locks must always be paired with a lock TTL and release logic that runs in `finally`, because a missing release leaks the lock until the TTL fires. The key takeaway is that atomic claim plus expiry plus token-checked release is the minimal correct recipe, and stronger guarantees require Redlock or a consensus-based store.

22. What is Redis pub/sub?
    - **Answer:** Redis pub/sub is a messaging pattern where publishers send messages to channels and any number of subscribers receive copies, using commands like `SUBSCRIBE channel`, `PUBLISH channel message`, and `PSUBSCRIBE pattern` for wildcard channels. A publisher never knows how many subscribers exist and does not care; the Redis server fans each published message out to every connected subscriber of that channel. The model is fire-and-forget: messages are delivered only to subscribers connected at the moment of publication, so a client that disconnects, subscribes late, or is briefly offline permanently misses everything sent in the gap. There is no persistence, no message queue backlog, no acknowledgment, and no replay, which makes pub/sub unsuitable for reliable delivery or for workloads where a lost message is unacceptable. It is well suited to ephemeral notifications where freshness matters more than completeness — a signal that data changed, a refresh trigger, a chat-like broadcast, or cache-invalidation events where every subscriber simply reloads its own data. It is extremely lightweight and low-latency, adding only the cost of the fan-out in memory, and it decouples producers from consumers cleanly. A common alternative is Redis Streams, which persists messages and supports consumer groups, acknowledgments, and replay, or a dedicated broker like Kafka when durability, partitioning, and high throughput are required. For many cache-related scenarios pub/sub works well: each instance subscribes to an "invalidate" channel, and when one node updates data it publishes, prompting all nodes to drop the affected cache key — this keeps caches consistent across a cluster without a polling loop. A limitation to note is that a slow subscriber can cause message buffering pressure, and if it disconnects, its messages are lost silently. Choosing pub/sub versus streams versus Kafka comes down to whether delivery guarantees, ordering, and replay are required.

23. What is Redis stream?
    - **Answer:** Redis Streams is an append-only, log-like data structure that supports consumer groups, message IDs, acknowledgments, and replay, effectively bringing a Kafka-style messaging model inside Redis. Each entry is stored with an auto-generated ID that encodes both a timestamp and a sequence, giving global ordering per stream and allowing range queries by time or ID. Messages are persisted in memory (and to disk with RDB/AOF), so they survive a restart, unlike pub/sub's fire-and-forget model. Consumer groups let multiple consumers divide a stream's entries among themselves, with each entry delivered to exactly one consumer in the group, and `XACK` provides explicit acknowledgment so that a consumer that crashes can re-read its unacknowledged entries after restart. This gives exactly-once-processing semantics at the group level (at-least-once delivery with idempotent consumers), which pub/sub cannot offer. Streams are a strong fit for job queues, event pipelines, and telemetry ingestion where messages must not be lost and where a bounded backlog can accumulate while consumers catch up. Compared with Kafka, Redis Streams is dramatically simpler to operate — there is no ZooKeeper, no broker cluster, no partition leadership — and latency is lower for moderate throughput. However, it lives inside Redis's single-threaded event loop and its memory footprint is bounded by the server's RAM, so very high throughput or unbounded history pushes workloads toward Kafka. The typical cutoff is that Redis Streams handles small-to-medium volumes comfortably (up to roughly tens of thousands of entries per second per stream) while Kafka scales horizontally with partitions across many brokers. Streams also support powerful features like pending-entry lists, `XCLAIM` for reassigning stuck entries, and `XREADGROUP` for blocking consumption. Choosing streams over pub/sub is essentially choosing durability and replay over simplicity and fan-out. For most cache-adjacent messaging needs where reliability matters, streams are the right Redis-native tool.

24. How do you secure Redis?
    - **Answer:** Redis security is primarily a network problem because Redis itself trusts its network and by default has no meaningful access control. The first and most important step is to never expose Redis to the public internet: place it in a private subnet or VPC, restrict access with security groups or firewalls to only the application instances that need it, and if it must be reachable outside, tunnel it over a VPN or an SSH bastion. Authentication is enabled with the `requirepass` directive (or the more granular `ACL SETUSER` in Redis 6+), which requires every client to authenticate with `AUTH` before issuing commands; production should use ACLs to grant each application only the commands and keys it actually needs. By default, a connected client can run any command, so the `rename-command` directive (or ACL command restrictions) is used to disable or rename dangerous commands like `FLUSHALL`, `FLUSHDB`, `KEYS`, `CONFIG`, and `EVAL` so that a compromised client or a malicious script cannot wipe data or expose internal state. Data in transit should be encrypted with TLS (`tls-port`, `tls-cert-file`) so passwords and payloads cannot be sniffed on the wire, and Redis 6+ supports TLS for clients and replication. Sensitive data at rest can be encrypted at the disk or volume layer, and password values should be stored in secrets managers rather than plain configuration files. The `bind` directive must be restricted to the appropriate interface instead of the default `0.0.0.0`, which listens on all interfaces. The protected-mode feature helps when no password is set, but it must not be relied on as the sole defense. Monitoring should include audit logging of authentication failures and unexpected commands, and version upgrades should be applied for security patches. It is also wise to disable dangerous commands globally if the application never uses them, since a defense-in-depth layer costs nothing at runtime. The overall posture is: private network, mandatory authentication, minimal command surface, encrypted transport, and strict ACLs — together these close the majority of real Redis attack paths.

25. How did Redis fit in your project?
    - **Answer:** Redis filled three distinct roles: a distributed cache in front of a time-series database, a shared session store for a stateless service tier, and a distributed lock for serializing operations across concurrent consumers. As a cache, it absorbed the bulk of read traffic for hot data such as latest sensor readings, gateway lists, and computed summaries, so the time-series database handled only misses and writes instead of every dashboard request. As a session store, it made user sessions available to every instance behind the load balancer, eliminating sticky-session pinning and allowing the tier to scale horizontally without losing state. As a lock, it used atomic `SET NX PX` to guarantee that a given sensor event was processed by exactly one consumer, even though multiple instances polled the same event source. The caching layer used a cache-aside pattern with TTLs tuned per data type — seconds for live readings, longer for near-static configuration — plus `@Cacheable`/`@CacheEvict` from Spring Cache to keep service code declarative. Invalidation combined explicit eviction on configuration updates with TTL as a bounded-staleness safety net, and TTL jitter prevented synchronized expiry. The measurable effect was significant: hot API responses went from a multi-millisecond database round trip to a sub-millisecond Redis read, database read volume dropped substantially, and the application instances became effectively stateless and independently disposable. The trade-offs were carefully managed — data with strict freshness or compliance requirements was deliberately excluded from the cache, and the lock design tolerated rare double-execution because the underlying processing was idempotent. Redis proved to be the highest-leverage infrastructure component in the architecture, solving caching, scaling, and concurrency with one shared, well-understood server. Its single-threaded command execution and rich data structures made these solutions both simple to reason about and easy to operate.
