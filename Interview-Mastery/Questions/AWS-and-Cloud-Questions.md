## Answers

1. What AWS services have you used?
   - **Answer:** The AWS services commonly used span the full compute, storage, networking, messaging, security, and monitoring stack. On the compute side, EC2 provides resizable virtual servers for running long-lived, stateful workloads, while Lambda offers serverless, event-driven execution for short, stateless tasks. For storage, S3 serves as scalable object storage for files and data lakes, EBS provides block storage attached to EC2 instances, and EFS offers shared file storage for multiple instances. Networking is handled through VPC with public and private subnets, internet and NAT gateways, route tables, security groups, and NACLs. AWS IoT Core manages MQTT-based device connectivity and message ingestion for IoT pipelines. IAM governs authentication and authorization through users, roles, and policies. Managed data services include RDS for relational databases and DynamoDB for key-value NoSQL workloads. Monitoring and logging are centralized in CloudWatch, while SQS and SNS provide queue-based and pub/sub messaging. These services combine to build everything from simple static websites to complex event-driven, streaming data pipelines.

2. What is EC2?
   - **Answer:** EC2 (Elastic Compute Cloud) is AWS's Infrastructure-as-a-Service offering that provides resizable virtual machines called instances. When launching an instance, several decisions must be made: the AMI (Amazon Machine Image) defines the operating system and pre-installed software, and the instance type determines the compute, memory, storage, and network capacity — families such as t3 (burstable general purpose), m5 (general purpose), c5 (compute optimized), and r5 (memory optimized) serve different workload profiles. Each instance runs in a specific availability zone and is placed inside a VPC subnet, protected by security groups that act as virtual firewalls. Access is controlled through key pairs (SSH key pairs for Linux, administrator passwords for Windows). Storage comes as either EBS volumes (persistent block storage that survives instance termination and can be snapshotted) or instance store (ephemeral, high-performance storage that is lost when the instance stops). EC2 is used for workloads that need full control over the operating system and runtime, persistent state, or sustained high utilization — situations where serverless compute would be a poor fit.

3. What is S3?
   - **Answer:** S3 (Simple Storage Service) is AWS's object storage service that stores data as objects inside buckets. Each object consists of data, a key (unique name within the bucket), and metadata, and buckets are globally unique names within a region. S3 is designed for 99.999999999% (11 nines) durability, achieved by storing each object redundantly across multiple devices and facilities. Objects are stored in different storage classes that trade cost against retrieval speed: S3 Standard for frequently accessed data, S3 Intelligent-Tiering for unknown or shifting access patterns, S3 Standard-IA and One Zone-IA for infrequently accessed data, and S3 Glacier Instant/Glacier Flexible/Glacier Deep Archive for archival data with retrieval times from minutes to hours. Versioning keeps every version of an object so accidental overwrites or deletes can be recovered, and lifecycle policies automate transitions between storage classes and eventual deletion based on age rules. Buckets support static website hosting, and access is controlled through bucket policies, IAM policies, and pre-signed URLs. S3 differs fundamentally from EBS (a single-instance block device) and EFS (a shared, POSIX-compliant file system for many instances): S3 is an object store accessed over HTTP, ideal for backups, static assets, data lakes, and file storage at any scale.

4. What is Lambda?
   - **Answer:** Lambda is AWS's serverless compute service that runs code in response to events without any server management. A function is packaged with its runtime (Node.js, Python, Java, etc.) and triggered by event sources such as S3 uploads, DynamoDB changes, API Gateway requests, or custom integrations. AWS handles the underlying infrastructure, including provisioning, scaling, patching, and high availability. Execution is limited by configurable memory (128 MB up to 10 GB), a timeout (up to 15 minutes), and ephemeral storage (up to 10 GB); the billed cost is based on execution duration and provisioned memory, which means idle functions cost nothing. Concurrency is managed per function, with AWS automatically scaling up to a default account-level limit of 1000 concurrent executions; each new execution environment incurs a cold start while the runtime initializes, though techniques like provisioned concurrency can warm environments in advance. Lambda integrates tightly with the AWS ecosystem and is the natural compute layer in event-driven and serverless architectures. It is not suited to long-running processes, stateful workloads, or consistently high-utilization tasks where running an EC2 instance would be cheaper.

5. What is AWS IoT Core?
   - **Answer:** AWS IoT Core is a managed cloud service that lets IoT devices connect securely to the AWS cloud and exchange data with other services. It acts as a highly available, scalable MQTT message broker — devices authenticate using X.509 certificates or AWS credentials, and publish messages to named topics. A device registry organizes and tracks each device's metadata, and the thing shadow (device shadow) maintains the last known reported and desired state so applications can inspect device status even when the device is offline. Rules evaluate inbound messages and route them to downstream services such as Lambda, Kinesis, DynamoDB, or S3, which enables serverless ingestion pipelines without running any broker infrastructure. The service scales automatically with the number of connected devices and integrates with IoT Policies for per-device authorization. It also supports LoRaWAN and MQTT over WebSocket, and provides fleet provisioning and certificate management. Because the broker and device management are fully managed, teams avoid the operational burden of running and scaling a self-hosted MQTT broker.

6. Why use AWS IoT Core?
   - **Answer:** AWS IoT Core is chosen because it removes the operational complexity of running a highly available MQTT broker at scale. Self-managing a broker like Mosquitto on EC2 means handling clustering, replication, TLS termination, certificate revocation, and capacity planning for peak device concurrency — all of which a managed service handles automatically. It provides a built-in device registry, device shadows, and a policy engine for per-device authorization, features that would otherwise have to be built from scratch. Device onboarding is simplified through fleet provisioning APIs that can issue certificates and register devices programmatically. Message routing via rules offloads the transformation and dispatch logic from devices to the cloud, letting MQTT payloads flow directly into Lambda, Kinesis, DynamoDB, or S3. The service integrates with CloudWatch for metrics and alarms, and its pricing is based on the number of connected minutes and messages, so cost tracks actual device activity. For an IoT pipeline, the alternative would require building and maintaining a broker fleet, implementing device authentication, and engineering for scale — all substantial efforts that IoT Core eliminates.

7. How does MQTT work with AWS IoT Core?
   - **Answer:** MQTT is a lightweight pub/sub messaging protocol designed for constrained networks and low-power devices, built on top of TCP. Devices connect to the AWS IoT Core broker over TLS on port 8883, authenticating with X.509 certificates and often a client ID. Once connected, a device publishes messages to a hierarchical topic, for example `sensors/gateway-1/temperature`, and other devices or services subscribe to topics or topic patterns. Topic filters support wildcards — the single-level `+` and the multi-level `#` — so a subscriber can match `sensors/+/temperature` to receive temperature readings from every gateway. MQTT provides three QoS (Quality of Service) levels: QoS 0 is fire-and-forget with at-most-once delivery, QoS 1 guarantees at-least-once delivery with acknowledgements and possible duplicates, and QoS 2 guarantees exactly-once delivery at the cost of more round trips. AWS IoT Core rules then listen to topics and match inbound messages against SQL-like rule statements, forwarding matched payloads to services like Lambda. A common ingestion pattern is devices publishing telemetry to a wildcarded topic, a rule parsing the JSON payload, and Lambda or Kinesis persisting and transforming the data downstream.

8. Difference between EC2 and Lambda.
   - **Answer:** EC2 and Lambda represent opposite ends of the compute spectrum. EC2 gives full control over the operating system, runtime, libraries, and instance configuration, and runs workloads continuously — it is a good fit for stateful services, long-running processes, and applications with predictable, sustained load. Lambda is ephemeral and event-driven: code runs in a managed runtime, is invoked only when an event arrives, scales automatically, and bills per invocation, but has hard limits — a 15-minute timeout, up to 10 GB of ephemeral storage, and limited execution environments. EC2 supports any language and arbitrary binaries, while Lambda is restricted to supported runtimes and package size limits. Pricing diverges accordingly: EC2 bills per second of running instance regardless of utilization, so idle capacity costs money, whereas Lambda bills only for actual execution time and is expensive for high-utilization workloads. Cold start latency is a concern with Lambda but irrelevant on EC2. The practical rule is that EC2 is preferred for Kafka brokers, databases, and long-lived services needing persistent storage and sustained throughput, while Lambda is preferred for request-driven transformations, API backends, and glue code between AWS services.

9. When would you use Lambda?
   - **Answer:** Lambda is the right choice for event-driven, short-lived, stateless tasks. Common use cases include transforming data as it moves between services, resizing images or processing uploads on S3 object-created events, building REST backends with API Gateway, processing messages from SQS or DynamoDB streams, running scheduled cron-style jobs, and serving as the glue layer in IoT pipelines that transform device payloads before forwarding them to storage or streaming services. It excels when workloads are intermittent or bursty, because there is no idle-cost and scaling is instantaneous and automatic. Lambda also suits scenarios where teams want zero infrastructure management, as AWS handles patching, availability, and concurrency. Cost is favorable when utilization is low or variable because billing is per invocation and duration. It should be used when the work fits within its limits — under 15 minutes, modest memory and storage, and no requirement for persistent state or dedicated hardware.

10. When would you avoid Lambda?
    - **Answer:** Lambda should be avoided for workloads that exceed its limits or don't fit its execution model. Long-running processes that exceed the 15-minute timeout, such as large batch transformations or legacy batch jobs, cannot run there. Stateful workloads that need persistent connections, in-memory state, or sticky sessions are a poor fit because execution environments are recycled between invocations. Sustained, high-throughput workloads like Kafka consumers processing thousands of messages per second can run in Lambda but often become expensive and hit concurrency limits, and the per-GB-second billing makes high utilization costlier than a continuously running EC2 instance. Low-latency requirements can be undermined by cold starts, especially in real-time or interactive paths. Workloads requiring specialized hardware, GPUs, particular kernels, or arbitrary native binaries are also excluded. Finally, applications needing fine-grained control over networking, instance sizing, or a specific OS version are better served by EC2, containers (ECS/EKS), or bare metal.

11. What is serverless?
    - **Answer:** Serverless is a cloud computing model where the provider manages the servers entirely, and the developer focuses on code and configuration. The name does not mean there are no servers — it means there is no server to provision, patch, scale, or pay for while idle. AWS Lambda is the canonical example, but the model also covers managed services like S3, DynamoDB, API Gateway, and SQS, where scaling and availability are handled by the provider. The defining benefits are automatic scaling, zero idle cost (billing is per use), and reduced operational overhead. The trade-offs are limited control over the runtime environment, potential cold-start latency, unpredictable cost when usage spikes, and difficulty debugging distributed execution. Serverless fits event-driven architectures, IoT ingestion, web APIs with variable traffic, and batch-style data processing. A hybrid architecture is common: serverless for the ingestion and transformation layer where load is spiky, and long-running EC2 or containerized services for the persistent processing tier that needs sustained throughput. The decision ultimately balances operational simplicity and elastic scaling against control, predictability, and cost at high utilization.

12. What is IAM?
    - **Answer:** IAM (Identity and Access Management) is AWS's service for controlling authentication and authorization across the account. It answers two questions: who can access AWS resources, and what can they do. IAM identities come in three forms: users represent people or applications with long-term credentials, roles are identities assumed by AWS services or federated entities for temporary credentials, and groups are collections of users that make permission administration easier. Permissions are expressed as JSON policies that are attached to identities or to resources, and an effective permission set is the union of allowed actions minus any explicit denies. IAM policies reference AWS services and actions, resource ARNs, and conditions such as source IP or time of day. The guiding principle is least privilege — granting only the permissions required for a job. IAM is global (not region-scoped) and provides federation with corporate identity providers, multi-factor authentication, and a credential report. CloudTrail logs every IAM-authorized API call, which is essential for auditing and troubleshooting "Access Denied" errors.

13. What is IAM role?
    - **Answer:** An IAM role is an identity with permissions that is assumed rather than logged into — it carries no long-term credentials. Roles are designed for AWS services and federated identities to gain temporary, time-limited credentials that AWS rotates automatically. A role consists of two policy documents: a trust policy that defines which principals (an AWS service such as Lambda or EC2, or a federated user) are allowed to assume it, and permission policies that define what the role holder may do. For example, an EC2 instance can be launched with an instance profile role that grants read access to S3, and a Lambda function can assume a role granting permission to write to DynamoDB. Because credentials are temporary and generated on demand through the STS (Security Token Service), there is no static secret to leak, rotate, or embed in code. Roles scale permission management: one role can be shared by many resources, and its policies can be updated once to affect all of them. Roles also enable cross-account access and are central to securing serverless and instance-based workloads with least privilege.

14. What is IAM policy?
    - **Answer:** An IAM policy is a JSON document that defines permissions by listing allowed or denied actions against specific AWS resources. A policy contains a Version, and one or more Statements, each with an Effect (Allow or Deny), an Action list (such as `s3:PutObject` or `dynamodb:Query`), a Resource ARN, and optional Conditions. Policies can be identity-based, attached to users, groups, or roles, or resource-based, attached to services like S3 buckets or SQS queues. AWS-managed policies cover common scenarios, while customer-managed policies let teams encode specific requirements. The evaluation model is explicit deny overrides any allow, so a deny on a resource always wins. Conditions allow fine-grained control — restricting access to certain IP ranges, requiring TLS, or limiting access to objects under a specific key prefix. The principle of least privilege guides policy design: grant only the actions needed on only the resources needed. The IAM Policy Simulator can validate a policy before production use, and CloudTrail logs the effective decisions to debug access denials.

15. What is VPC?
    - **Answer:** A VPC (Virtual Private Cloud) is a logically isolated, software-defined network within AWS where resources like EC2 instances, RDS databases, and Lambda functions are launched. Each VPC has an IP address space defined with CIDR blocks (for example 10.0.0.0/16) and is scoped to a single region. Inside it, subnets divide the address space across availability zones, and route tables determine how traffic flows between subnets, the internet gateway, and other network services. An internet gateway provides public connectivity to and from the internet, while a NAT gateway allows instances in private subnets to make outbound connections without being reachable from outside. Security is enforced at two layers: security groups act as stateful, instance-level firewalls, and network ACLs act as stateless, subnet-level firewalls. The default VPC is convenient, but a well-designed custom VPC typically places the load balancer and bastion in public subnets and application and database tiers in private subnets. VPC endpoints allow private access to services like S3 and DynamoDB without traversing the public internet. The VPC is the foundation of network isolation, security, and high availability for nearly every AWS workload.

16. What is subnet?
    - **Answer:** A subnet is a range of IP addresses carved out of a VPC's CIDR block, and it is associated with exactly one availability zone — a subnet cannot span zones. Subnets are categorized as public or private based on their route table: a public subnet has a route to an internet gateway so resources in it can receive inbound internet traffic, while a private subnet has no such route and therefore cannot be reached from the internet. Private subnets typically route outbound traffic through a NAT gateway in a public subnet, allowing instances to reach the internet for updates and API calls without being externally reachable. A common three-tier design places the load balancer in public subnets, application servers in private subnets, and databases in separate private subnets, with security groups restricting traffic between tiers. Distributing subnets across multiple availability zones is essential for high availability, because a design that places everything in one zone fails when that zone fails. Subnet CIDR planning should reserve enough address space for growth and for future per-zone expansion.

17. What is security group?
    - **Answer:** A security group is a virtual firewall that controls inbound and outbound traffic for EC2 instances, and more broadly for resources like load balancers, RDS databases, and Lambda functions inside a VPC. Security groups are stateful: if an inbound rule allows a request, the return traffic is automatically permitted, and the same applies to outbound. Rules are specified by protocol, port, and source or destination — a source can be an IP CIDR, a range of addresses, or another security group, and referencing another security group enables micro-segmentation where one tier only accepts traffic from the specific group protecting another tier. Security groups are evaluated as an allowlist with an implicit deny-all default, so any traffic not explicitly permitted is blocked. Unlike NACLs, security groups cannot have deny rules and are associated with instances, not subnets, which makes them per-resource. By default, security groups allow all outbound traffic and no inbound traffic. A standard hardened pattern is to allow SSH only from a bastion or corporate IP range, and to allow application traffic only from the load balancer's security group, so even misconfigured clients cannot reach the application tier directly.

18. What is load balancer?
    - **Answer:** A load balancer distributes incoming client traffic across a group of backend targets — typically EC2 instances or containers — to improve availability, scalability, and fault tolerance. AWS offers the Application Load Balancer (ALB) for HTTP/HTTPS traffic with path-based and host-based routing, the Network Load Balancer (NLB) for TCP/UDP traffic requiring very high throughput, and the Gateway Load Balancer for virtual appliances. The load balancer sits in public subnets, accepts traffic, and forwards it to a target group of registered instances based on listener rules. It performs health checks against configurable endpoints (for example an application's `/actuator/health`), and only routes to targets that pass; unhealthy targets are deregistered automatically. TLS/SSL termination can be offloaded to the load balancer, freeing backends from certificate handling. Sticky sessions can pin a client to a target, though stateless designs that keep session state in tokens avoid the need. Cross-zone load balancing and placement across availability zones ensure traffic is spread and failures are tolerated. By decoupling clients from the underlying instances, the load balancer enables auto scaling and rolling deployments without downtime.

19. What is auto scaling?
    - **Answer:** Auto Scaling automatically adjusts the number of running instances in response to demand, so capacity tracks load rather than being over- or under-provisioned. An Auto Scaling Group (ASG) is defined by a launch template (AMI, instance type, security groups, user data), a minimum, a desired, and a maximum instance count, and a set of subnets across availability zones. Scaling can be reactive, driven by CloudWatch metrics such as average CPU utilization or request count per target, or scheduled, such as scaling up before a known traffic peak. When a scale-out policy triggers, the ASG launches a new instance from the template and registers it with the load balancer; when load drops, scale-in policies terminate instances. Warm-up and cooldown periods prevent thrashing, and health checks automatically replace instances that become unhealthy. Placement across multiple availability zones means a failed zone doesn't take down the entire fleet. The desired capacity can be set manually for maintenance windows. The result is a fleet that grows elastically, stays healthy, and does not pay for idle capacity during quiet periods.

20. What is CloudWatch?
    - **Answer:** CloudWatch is AWS's centralized monitoring and observability service, collecting metrics, logs, and events from across the account. It ingests standard infrastructure metrics like CPU utilization and network traffic for EC2, plus service metrics for RDS, DynamoDB, Lambda, and others. Custom metrics can be published via the CloudWatch agent or the AWS SDK, allowing application-level signals like queue depth, consumer lag, or processing rate to be tracked. CloudWatch Logs centralizes log streams from EC2 instances, Lambda functions, and containers, with log groups organizing streams and retention policies controlling storage cost and log search. Alarms evaluate metrics on a fixed interval and transition through states (OK, INSUFFICIENT_DATA, ALARM), triggering actions like Auto Scaling policies or SNS notifications to email and SMS. Dashboards aggregate metrics into visual views across accounts and regions. CloudWatch Events (EventBridge) routes operational events — instance state changes, scheduled cron jobs, and service events — to targets such as Lambda. Together these features form the primary operational control plane for detecting problems, alerting on them, and scaling in response.

21. How do you monitor AWS applications?
    - **Answer:** Monitoring AWS applications combines infrastructure metrics, application metrics, logging, and alerting. CloudWatch provides default infrastructure metrics — basic monitoring for EC2 samples every five minutes, and detailed monitoring samples every minute. The CloudWatch agent adds in-guest metrics like memory and disk usage, which are not visible from outside the instance. Application-level signals are published as custom metrics, such as processing rate, error count, or consumer lag, so dashboards reflect business health rather than just CPU. All logs are centralized in CloudWatch Logs with structured JSON output and appropriate retention, and CloudWatch Logs Insights enables ad-hoc querying. Alarms are created on meaningful thresholds and can be combined into composite alarms that require multiple conditions before firing, reducing alert fatigue. Alarms trigger actions through SNS — email, SMS, or pager integrations. Tracing distributed flows, such as MQTT → Lambda → Kafka, often requires X-Ray or application-level correlation IDs. The monitoring strategy should cover the full request path: load balancer health, instance metrics, application metrics, log errors, and end-to-end latency.

22. How do you store files in S3?
    - **Answer:** Storing files in S3 is done by uploading objects to a bucket through the AWS console, CLI, SDK, or infrastructure-as-code tools. Programmatically, the AWS SDK provides operations like `PutObject` and `UploadPart` (for multipart uploads of large files) with parameters for the bucket, object key, content type, metadata, and storage class. Object keys form a flat namespace where slashes are just characters, so folder-like organization is achieved with key prefixes such as `reports/2026/08/summary.csv`. Large files should use multipart upload to parallelize transfer and allow resuming. Server-side encryption can be enforced with SSE-S3, SSE-KMS, or SSE-C, and access is controlled by IAM, bucket policies, and pre-signed URLs. Pre-signed URLs grant temporary, time-limited access to upload or download a specific object without exposing credentials. A typical reporting flow generates a file in an application, uploads it to S3 with the SDK, and returns a pre-signed URL so authorized users can retrieve it. Lifecycle rules can then transition the object to cheaper storage classes and eventually delete it automatically.

23. What is S3 bucket policy?
    - **Answer:** An S3 bucket policy is a resource-based IAM policy attached to a bucket that defines who may perform which actions on the bucket and its objects. Unlike identity-based policies attached to users or roles, a bucket policy is evaluated for any principal accessing the bucket, and it can grant access to principals outside the account, such as other AWS accounts or public internet users. Typical uses include allowing a specific role to put objects, restricting the bucket to a corporate IP range, forcing `aws:SecureTransport` to require HTTPS, and denying all public access. Bucket policies work together with identity-based policies: a request is permitted if either allows it and no policy denies it. Modern hardening practice combines bucket policies with the "Block Public Access" settings, which override and prevent any accidental public exposure. Lifecycle configuration, versioning, and replication are configured separately from policies but are often applied together. A well-designed bucket policy is a primary control for enforcing security, compliance, and least-privilege access on object storage.

24. How do you secure S3?
    - **Answer:** Securing S3 follows a defense-in-depth approach across access control, encryption, and monitoring. First, the S3 Block Public Access settings should be enabled to prevent any object or bucket from becoming public, and access should be granted only through IAM and bucket policies following least privilege. Server-side encryption should be enforced on all objects — SSE-S3 for default encryption or SSE-KMS when key management and audit trails are required — and the bucket policy can mandate `aws:SecureTransport` so objects are only served over HTTPS. For time-limited, controlled sharing, pre-signed URLs are preferable to making objects public. Versioning should be enabled so accidental overwrites or deletions can be restored, and MFA delete can protect against malicious deletions. S3 access logs or CloudTrail data events record who accessed which objects, and Lifecycle policies reduce both cost and exposure by expiring sensitive data on schedule. Cross-account replication can mirror data to a compliant region. Finally, testing with tools like the IAM policy simulator and reviewing the bucket permission report helps catch misconfigurations before they become incidents.

25. How do you deploy Spring Boot on EC2?
    - **Answer:** A typical deployment pipeline builds a Spring Boot application into a deployable artifact, packages it, and runs it on EC2 instances. The application is compiled with Maven or Gradle into a fat JAR, and commonly wrapped in a Docker image so the runtime, JVM version, and configuration are identical across environments. The image is pushed to a registry, and the EC2 instance pulls and runs it with `docker run`, mapping ports and injecting environment variables and secrets. Alternatively, the JAR can be run directly with `java -jar` on an instance with the JRE installed, optionally behind a reverse proxy like Nginx. Instance provisioning uses a launch template with user data — a bootstrap script that installs the runtime, pulls the latest artifact, and starts the service. The instance belongs to an Auto Scaling Group behind a load balancer, and health checks against the application's health endpoint determine readiness and routing. Configuration lives in environment variables, Parameter Store, or Secrets Manager rather than in the image, so the same image runs across environments. A deployment therefore becomes: build image, push image, trigger rollout, and verify health.

26. How do you run Kafka on EC2?
    - **Answer:** Running Kafka on EC2 means self-managing the cluster's installation, configuration, monitoring, and scaling. A typical cluster has three or more brokers in separate availability zones for fault tolerance, with ZooKeeper (or KRaft in modern versions) handling coordination and metadata. Kafka is installed on each instance, and `server.properties` is configured with the broker ID, log directories, and both advertised and listener addresses pointing to the instance's private IP so clients inside the VPC connect correctly. Replication factor of 3 with `min.insync.replicas=2` and producer `acks=all` provides durability against broker failure. Storage is provisioned as EBS volumes — gp3 for balanced I/O, or provisioned IOPS for high-throughput — and partitions are distributed across brokers by partition count and replication factor. OS tuning matters: page cache behavior, `vm.swappiness`, and file descriptor limits affect Kafka's disk I/O patterns. Security groups restrict broker traffic to the application tier. Monitoring is essential, with consumer lag, broker disk usage, and request metrics published to CloudWatch. Zookeeper/KRaft nodes, log retention, and disk capacity must be planned and operated manually, which is the core operational burden versus using a managed service like MSK.

27. What are the challenges of running Kafka on EC2?
    - **Answer:** Self-managing Kafka on EC2 shifts substantial operational burden onto the team. Disk management is the first challenge: Kafka is I/O and page-cache intensive, so EBS volumes must be sized for throughput and IOPS, and brokers can fail when disks fill up because log retention and consumers falling behind increase storage pressure. Network is second: inter-broker replication traffic and client traffic compete for bandwidth, and latency between brokers in different availability zones affects replication and leader election. The control plane adds complexity — ZooKeeper (or KRaft) must be deployed, sized, and monitored as a separate stateful component, and its failure can destabilize the whole cluster. Operating system tuning for file descriptors, `vm.swappiness`, and page cache is required for performance and stability. Upgrades and rolling restarts must be orchestrated carefully to avoid downtime. Capacity planning for partition count, replication, and disk growth is manual, and scaling brokers is not just additive because throughput per partition depends on the instance. Monitoring must cover consumer lag, disk, CPU, and network, with alerting tuned to avoid outages. Finally, cost is higher than a managed service because over-provisioning and operational time are included.

28. How do you manage environment variables in AWS?
    - **Answer:** Environment-specific configuration should be separated from code and managed through dedicated AWS services. AWS Systems Manager Parameter Store stores configuration values in a hierarchical namespace (such as `/app/prod/db/url`) with types including String, StringList, and SecureString for encrypted values, and it is free up to a quota of parameters. AWS Secrets Manager stores secrets — database passwords, API keys — with automatic rotation, fine-grained access via IAM, and tight integration with services like RDS. Applications retrieve values at startup or on demand through the AWS SDK, so the same artifact runs in any environment by selecting the right parameter path. For containerized workloads, ECS supports injecting values as environment variables, and Lambda supports environment variables stored encrypted and surfaced at runtime. EC2 user data scripts can export values to the environment at boot, though this is less flexible. IAM roles control which components can read which parameters, keeping secrets out of repositories, build logs, and images. The rule is: never hardcode configuration in code; always externalize it and control access per environment.

29. How do you handle secrets?
    - **Answer:** Secrets are handled by storing them outside of code and artifacts and retrieving them at runtime through a secure, access-controlled service. AWS Secrets Manager is the standard choice for database credentials, API keys, and other sensitive values, offering encryption with KMS, fine-grained IAM policies, versioning, and automatic rotation for services like RDS and Redshift. An application obtains the secret at startup via the SDK, caches it in memory, and refreshes it on rotation. Secrets should never appear in source control, property files, environment variable defaults, Docker images, or CI logs. IAM roles, rather than static credentials, grant applications the permission to read the specific secrets they need — least privilege applies to secrets just as to compute. For infrastructure and CI/CD, secrets can also live in the CI system's credential store. Rotation must be planned: when a password rotates, running applications need to refresh it, so the retrieval and caching logic should handle transient failures and re-fetch. Auditing access to secrets through CloudTrail and monitoring helps detect misuse.

30. What is CI/CD deployment to AWS?
    - **Answer:** CI/CD to AWS is the automated pipeline that builds, tests, and ships code to AWS environments with minimal manual involvement. Continuous Integration merges developer changes frequently and runs automated build and test on every push; Continuous Delivery automates deployment of verified artifacts to staging and production. A typical pipeline for an application deployed on EC2 has stages: source checkout, dependency resolution and compile, unit and integration tests, static analysis, building a container image, pushing the image to a registry, and deploying to the target environment — for example by updating an Auto Scaling Group's launch template and rolling instances, or by SSH-triggered pull-and-restart on existing instances. Deployment verification runs health checks against a load balancer endpoint, and rollback can revert to the previous artifact if verification fails. The pipeline can be implemented with Jenkins, GitHub Actions, GitLab CI, or native services like CodePipeline, CodeBuild, and CodeDeploy. Environment configuration (parameter paths, secrets) is injected at deploy time rather than baked in, so the same artifact promotes across environments. The value is repeatability, speed, and reduced risk of human error.

31. How did Jenkins deploy to EC2 in your project?
    - **Answer:** A Jenkins pipeline deploying to EC2 typically follows a multi-stage flow: checkout the source from the repository, run the Maven or Gradle build with unit tests, build a Docker image containing the application JAR, push that image to a container registry, and then deploy to the target EC2 instances. The deployment stage connects to the instances over SSH using credentials stored securely in Jenkins — never inline in the script — and executes a script that pulls the new image, stops the running container, starts the new one, and removes the old image to reclaim disk. A health check stage runs `curl` against the application's health endpoint on the load balancer to confirm readiness before marking the build successful. Blue-green or rolling strategies can be encoded by updating Auto Scaling Group launch configurations and cycling instances. Jenkins credentials (registry login, SSH keys, VPC endpoints) are managed as scoped credential objects. Failure at any stage stops the pipeline, preserving the last good deployment. The pipeline itself is defined as code (a Jenkinsfile) so the process is versioned and reviewable.

32. How do you debug AWS deployment failure?
    - **Answer:** Debugging a failed deployment starts by identifying which stage failed — build, image creation, push, or deploy. The CI pipeline's console output shows compilation errors, test failures, or Docker build issues directly. If the build succeeded and deployment failed, the next source of truth is the instance's logs: CloudWatch Logs captures application stdout, startup exceptions, and configuration errors, and `journalctl` or `docker logs` on the instance gives immediate feedback. Common root causes are missing or wrong environment variables, incorrect IAM permissions causing access-denied errors when the application calls AWS APIs, ports or security groups blocking traffic, insufficient disk space from accumulating old images and logs, and unhealthy health checks that prevent the load balancer from routing traffic. Deployment scripts should be idempotent and output each step, and a failed deploy should trigger rollback to the previous known-good artifact. Comparing environment configuration between the last successful and the failed deployment often isolates the change. Temporary fixes — like a cleanup step that prunes old Docker images — should then be made permanent in the pipeline.

33. What is high availability?
    - **Answer:** High availability (HA) is the property of a system remaining operational and accessible despite individual component failures, typically expressed as a percentage of uptime. HA is achieved through redundancy and automatic failover rather than through making components infallible. At the infrastructure level, resources are distributed across multiple availability zones so that a datacenter-level failure does not take down the whole system — running application instances in at least two zones behind a load balancer, whose health checks automatically route around failed instances, is the canonical pattern. Data services use replication: RDS Multi-AZ maintains a synchronous standby replica that fails over automatically, Kafka uses ISR-based replication with automatic leader election, and S3 is inherently replicated for 99.999999999% durability. The architecture must remove single points of failure at every tier — compute, storage, messaging, and configuration. Design targets like "99.99% availability" translate to about 52 minutes of downtime per year, which guides how much redundancy is justified. HA is measured by uptime; a related but distinct concept, fault tolerance, concerns correct operation despite failures. Achieving HA also requires operational practices: health checks, automated replacement, backups, and failure drills.

34. What is fault tolerance?
    - **Answer:** Fault tolerance is a system's ability to continue operating correctly in the presence of failures, ideally without any interruption or data loss. Whereas high availability emphasizes minimizing downtime, fault tolerance emphasizes correctness and continuity under failure — the system keeps serving requests and preserves its data. Fault tolerance is achieved through redundancy with automatic failover: Kafka with a replication factor of 3 and `min.insync.replicas=2` tolerates the loss of a broker while continuing to serve consumers with no data loss; an Auto Scaling Group with instances across zones replaces failed capacity; a load balancer's target group deregisters unhealthy instances and keeps traffic flowing to healthy ones. Databases provide fault tolerance through replication and Multi-AZ standby. Design principles include eliminating single points of failure, detecting failures quickly through health checks and heartbeats, and reacting automatically rather than requiring human intervention. A system can be highly available yet not fully fault tolerant, for example if failover involves a brief outage. True fault tolerance requires duplicated state and idempotent processing so that retries after partial failure are safe. The cost of full fault tolerance is higher redundancy, so it is applied where data integrity and continuous operation matter most.

35. What is horizontal scaling?
    - **Answer:** Horizontal scaling means increasing capacity by adding more instances or nodes to a pool, rather than making existing ones bigger. Stateless application tiers scale this way naturally: an Auto Scaling Group adds instances behind a load balancer as load rises, and each new instance shares the work equally. Distributed systems like Kafka scale horizontally by adding brokers and rebalancing partitions across them, which increases overall throughput, and Kafka consumers scale by adding consumer instances up to the number of partitions. Horizontal scaling provides elasticity — capacity can grow and shrink with demand — and improves fault tolerance, because more instances mean any single failure affects a smaller fraction of capacity. It is not without complexity: state must be externalized (in databases or caches), load must be distributed evenly, and some systems have ceilings, such as Kafka where per-partition throughput is bounded by a single broker. Horizontal scaling is the preferred approach for web tiers, stateless APIs, and streaming consumers. The infrastructure can be costlier than scaling up one machine, but it delivers near-unlimited capacity with better resilience.

36. What is vertical scaling?
    - **Answer:** Vertical scaling (scaling up) increases capacity by upgrading the resources of an existing server — more vCPUs, more memory, faster storage — such as moving an instance from m5.large to m5.xlarge. It is the simplest form of scaling because no code or architecture changes are required; the same application just runs on a bigger machine. Vertical scaling is often the right choice for stateful systems where horizontal scaling is hard, such as relational databases with strong consistency requirements, and for Kafka brokers, where adding brokers does not increase throughput per partition and the whole topic partition set must be rebalanced. The fundamental limitation is the ceiling: an instance can only be as large as the largest available type, and at some point capacity cannot grow further. Scaling up requires downtime in most cases, as the instance must stop and restart to change size. Vertical scaling is also less resilient — one large machine is a bigger single point of failure than several smaller ones. A common strategy uses vertical scaling for stateful tiers and horizontal scaling for stateless tiers, combining simplicity where it fits with elasticity where it is needed.

37. What is Databricks?
    - **Answer:** Databricks is a unified data analytics platform built on open-source Apache Spark, designed for data engineering, data science, machine learning, and business analytics on a single lakehouse architecture. It provides managed clusters that spin up Spark workers on demand, an interactive notebook environment for collaboration across data engineers and data scientists, and Delta Lake for ACID transactions on data stored in object storage like S3. The platform handles cluster provisioning, autoscaling, and tuning, removing much of the operational burden of running Spark. It integrates with streaming sources like Kafka and Kinesis to run Structured Streaming jobs, and with a data lake in S3 to query and transform both batch and streaming data. Databricks also offers managed MLflow for experiment tracking and model lifecycle management, and a SQL warehouse for BI-style queries. Its value is consolidating the whole data pipeline — ingestion, transformation, training, and serving — in one governed environment. In a predictive analytics context, Databricks reads historical telemetry, trains models on patterns, and publishes predictions back to downstream systems.

38. How did Databricks help in predictive analytics?
    - **Answer:** Databricks powers predictive analytics by giving a distributed compute platform where large volumes of historical data can be processed, transformed, and used to train models at scale. Spark clusters in Databricks consume streaming or batch data — for example telemetry from a Kafka topic — and Structured Streaming applies the same DataFrame APIs to continuous streams as to batch data, enabling near-real-time feature computation. Historical data stored in a data lake (Parquet in S3) is loaded, cleaned, and joined into feature tables, and distributed ML training via MLlib or custom Spark pipelines produces models that learn failure or excursion patterns from temperature and sensor histories. Databricks' notebook environment makes the process reproducible, and MLflow tracks experiments, parameters, and metrics so the best model is promoted. Trained models can be registered and used for batch scoring or served to score each incoming record, with predictions written back to Kafka or a database to trigger downstream alerts. The benefit is that analysis scales with data size, runs without standing up bespoke Spark infrastructure, and shortens the cycle between data collection and actionable predictions — enabling preventive maintenance before failures occur.

39. What is data lake?
    - **Answer:** A data lake is a storage repository that holds raw data in its native format at any scale, without requiring the data to be transformed or structured before storage. Unlike a data warehouse, which enforces a schema and stores processed, relational data optimized for BI queries, a data lake stores everything — structured, semi-structured, and unstructured — so it can be explored and processed later for many purposes. On AWS, S3 is the natural data lake foundation, with objects organized by prefixes and formats like Parquet, ORC, and JSON; tools like Spark, Athena, and Glue query the raw data in place. The core advantage is flexibility and fidelity: raw data is never discarded, so new algorithms and business questions can be answered by reprocessing historical data without re-acquiring it. This is why a common architecture keeps raw IoT or event data in a data lake, then transforms it into curated layers for analytics and machine learning. Data lakes require governance to avoid becoming "data swamps" — cataloging schemas, managing access, and versioning data are essential. The lakehouse model (as in Delta Lake on S3) combines data lake scale with warehouse-style ACID transactions and performance.

40. What is cloud cost optimization?
    - **Answer:** Cloud cost optimization is the practice of minimizing cloud spending while preserving performance, reliability, and capacity — avoiding waste rather than merely cutting budgets. Key levers include right-sizing instances to match actual utilization (often discovered through CloudWatch metrics or tools like Compute Optimizer), replacing on-demand pricing with reserved instances or savings plans for predictable, always-on workloads, and using Spot instances for interruptible batch and stateless workloads. Storage costs are reduced by lifecycle rules that transition rarely accessed objects to cheaper classes like S3-IA and Glacier and by expiring unnecessary data. Unused resources are the biggest source of waste — stopping idle EC2 instances, terminating unattached EBS volumes, and deleting stale snapshots. Auto scaling and serverless architectures align spend with demand, eliminating over-provisioning for peak load. Monitoring is essential: Cost Explorer identifies the largest spend categories and trends, budgets and anomaly detection trigger alerts when spend deviates, and tags allocate costs to teams and projects for accountability. Optimization is a continuous loop of measuring, identifying waste, and applying the right pricing and sizing strategy — not a one-time cleanup.
