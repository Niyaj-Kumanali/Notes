## Answers

1. A stored procedure suddenly becomes slow in production. How do you debug it?
   - **Answer:** Start by confirming the performance regression is real: capture the current elapsed time, CPU, and logical reads, then compare them against a known-good baseline so the investigation targets a change rather than a one-off spike. Next, capture the actual execution plan that production is using, because a plan that worked yesterday can change today for many reasons. The most common root causes are parameter sniffing (the plan was built for one parameter value and is poor for others), stale or missing statistics after large data loads, newly introduced blocking or lock waits, plan cache eviction, and changes to data volume or schema. Use Query Store or dynamic management views such as `sys.dm_exec_query_stats` and `sys.dm_exec_requests` to see the plan and waits in real time, and inspect wait stats to separate CPU, I/O, and blocking problems. If parameter sniffing is suspected, test with `OPTION (RECOMPILE)` or `OPTION (OPTIMIZE FOR UNKNOWN)` to see whether performance changes, and verify that parameter data types match the column types. If statistics are the issue, update them and schedule an index/statistics maintenance job. For I/O-bound queries, check for missing or fragmented indexes and look at logical reads; for blocking, identify the blocker with `sys.dm_exec_requests` and `sys.dm_exec_connections` and review transaction durations. Once a fix is applied, compare against the baseline and monitor for a few days to confirm stability. Prevention means running Query Store, keeping maintenance jobs current, monitoring plan changes, and reviewing any schema or data changes that preceded the regression. Interviewers look for a structured, evidence-based approach that separates measurement from speculation and proves the fix with before-and-after numbers rather than guessing at the cause.

2. A query uses an index in testing but not in production. What could be the reason?
   - **Answer:** The optimizer chooses an execution plan based on cost, and cost is driven by row estimates built from statistics, so the first place to look is the difference in data distribution between environments. Production typically has far more rows, a different cardinality of the indexed column, and different NULL distribution, which can make a scan cheaper than a seek. A classic example is a column that is mostly NULL in production: a non-clustered index does not index NULL values, so the optimizer estimates a scan as cheaper than a seek that would touch the clustered index for every row. Check the actual versus estimated row counts in both execution plans and compare the statistics histograms; also confirm the index actually exists in production, because schema drift between environments is common. Parameter sniffing can also differ if the same query is executed with different parameter values in each environment. Stale statistics in production after a large data load cause estimates to be wildly off. Verify that the data types in the query match the index key types, since implicit conversions force a scan even when an index exists. The correct fix is not usually a query hint but aligning the environments: refresh statistics, maintain indexes, and copy schema via a controlled migration process. Interviewers look for an understanding that the optimizer is cost-based, an appreciation of environment drift, and a preference for fixing the root cause (statistics, data, schema parity) over hard-coding hints.

3. A database job takes 5 hours. How would you reduce it?
   - **Answer:** Approach this as a profiling exercise rather than a blind rewrite: capture the execution plan and use `SET STATISTICS TIME, IO` to identify which steps consume most of the elapsed time and logical reads, then focus effort on the top cost drivers. Common wins are missing or fragmented indexes, correlated subqueries that run once per row instead of once per set, and unnecessary round-trips caused by row-by-row (cursor) processing. Rewrite set-based operations to use joins instead of scalar subqueries, and pre-aggregate intermediate results into temp tables rather than repeatedly scanning large source tables. For very large volumes, switch to batch processing: commit in chunks of a few thousand rows so log growth, locks, and memory pressure stay bounded, and consider table partitioning so each batch touches only its own partition. Evaluate whether parts of the job can run in parallel across independent units of work, but weigh that against lock contention and system load. Check whether the job can use `TRUNCATE` instead of `DELETE`, minimize index fragmentation created during the run, and look for unnecessary full scans caused by functions on indexed columns or implicit conversions. After each change, re-measure elapsed time and reads so improvements are proven, and track the job duration over time to detect regressions early. Interviewers look for a systematic, data-driven tuning methodology, an instinct to convert row-by-row logic into set operations, and an awareness that the biggest wins come from eliminating work rather than making existing work slightly faster.

4. A report has incorrect data after ETL. How do you investigate?
   - **Answer:** Treat ETL as a pipeline of handoffs and validate at every stage so the fault can be isolated to extraction, transformation, or loading. Start by comparing source counts and sums against what the report shows, then check staging tables to see whether the raw data arrived intact or was truncated or duplicated on the way in. Row-count and checksum comparisons between consecutive stages narrow the problem to the exact step where data diverges. Common causes are JOINs that multiply rows (fan-out), missed NULL handling that drops or double-counts records, incorrect aggregation keys, timezone or date-boundary mismatches, and changes to source data formats that break parsing logic. Reproduce the pipeline on a small, known sample and hand-verify the expected output for that sample to confirm the transformation logic. Check whether duplicates exist in the source itself and whether the ETL deduplicates or propagates them. Validate the full ETL end to end on a subset of real data, not just synthetic test data, because real data contains the edge cases. Prevention includes adding automated data-quality checks at each stage (row counts, key uniqueness, range checks), asserting referential integrity, and alerting whenever a stage fails its validation before downstream consumers see the data. Interviewers look for a methodical, stage-by-stage trace, a strong grasp of SQL join and aggregation semantics, and a data-quality mindset that treats validation as a first-class part of the pipeline.

5. Duplicate serial records are entering inventory. How do you prevent it?
   - **Answer:** Enforce uniqueness at the database layer as the source of truth, because application-level checks alone are vulnerable to race conditions when two requests check simultaneously and both pass. Add a unique constraint or unique index on the serial number so the database rejects a second insert with the same value, which converts a silent data-quality bug into a visible, catchable error. Layer a friendly validation on top so users or integrations get a clear "serial already exists" message rather than an obscure constraint violation. If the check-then-insert pattern is required (for example, when a serial must be verified against a separate baseline before insertion), protect it with an appropriate isolation level or a serialized locking mechanism so concurrent requests cannot both pass the check. Design for re-entrancy: if the same batch or API call retries after a timeout, it should not create duplicates, so use a natural key or idempotency key on the insert path. Log rejected attempts with the serial and source channel to make it easy to reconcile and audit. Put a reconciliation job in place that periodically flags serial numbers appearing more than once, even if only in a transaction log, to catch legacy or edge-case duplicates. Interviewers look for a defense-in-depth mindset (database constraint plus application validation), an understanding of race conditions around check-then-insert, and awareness that idempotent ingestion prevents duplicates caused by retries.

6. Inventory data is delayed from some channels. How do you handle it?
   - **Answer:** Begin by mapping each channel's full data path from submission to a visible inventory update, because "delayed" can mean late at the source, stuck in ETL, or processed but not yet reflected in the UI. Instrument each channel with timestamps at submission, extraction, transformation, and load so you can measure where time is lost and compare channels against each other. Delays frequently come from partners sending non-standard or malformed formats that fail validation and get retried or rejected, from downstream services being slower for certain channel volumes, or from processing being sequential when channels are independent. Fix the systemic issues by standardizing the ingestion contract (schema, field formats, expected cadence) and by parallelizing per-channel pipelines so one slow channel does not back up the rest. Establish a service-level objective per channel, such as "visible within 15 minutes of submission," and monitor the time to reflect against that target with alerts when the window is missed. Acknowledge that some upstream delay is outside the system's control, and design a stale-data policy: after a grace period, mark inventory as stale and communicate that state to consumers rather than presenting outdated data as fresh. Interviewers look for measurable, per-channel monitoring, a willingness to fix both contract and processing issues, and an understanding that graceful degradation beats silent staleness.

7. Kafka consumer lag is increasing. How do you debug it?
   - **Answer:** Lag is the gap between the latest produced offset and the offset a consumer has committed, and it tells you producers are outpacing consumers; the goal is to find where the bottleneck is. Check consumer lag metrics per partition and per consumer group first, because a spike in one partition points at a hot-key problem while uniform lag points at global throughput limits. Determine whether the consumer is CPU-bound, I/O-bound, or blocked on a downstream call such as a database write or HTTP request, which usually shows up in the consumer's logs and profiling. Inspect the processing code for slow operations like per-message synchronous database writes that could be batched, and look for poison-pill messages that repeatedly fail and retry. If the consumer uses manual or per-record commit, an exception can cause re-processing or rebalancing that wastes capacity. Verify the number of partitions versus consumer instances: if consumers outnumber partitions, idle consumers do no work, and if load is high, the topic needs more partitions or the consumer needs more concurrency. Also check the produce side: if the producer is sending very large messages or an upstream source is hammering the topic, consumption capacity is being consumed by volume rather than useful work. Reduce lag by increasing consumer instances to match partitions, batching writes to downstream systems, and adding backpressure-aware rate limiting if the source is bursty. Prevention is constant lag monitoring with thresholds so a rising trend triggers a response before data staleness affects users. Interviewers look for a clear mental model of offsets and lag, the ability to isolate a partition-level vs global bottleneck, and practical throughput fixes rather than blind horizontal scaling.

8. Kafka messages are duplicated. How do you handle it?
   - **Answer:** Duplication is an inherent property of at-least-once delivery, which Kafka guarantees, so the system must be designed to tolerate it rather than hope it never happens. Producers can duplicate on retry after a network timeout, and consumers can reprocess messages after a crash or rebalance before their offsets are committed, so both ends can introduce duplicates. The core solution is idempotency: the consumer must be able to process the same logical event twice and produce the same end state. That is achieved by deriving a stable key (such as a serial number, reading ID, or event ID) and enforcing uniqueness in the destination, for example a unique constraint or a primary key with `INSERT ... ON CONFLICT DO NOTHING`, so a second write is a no-op instead of a duplicate row. When the destination cannot enforce uniqueness, track processed message IDs in a datastore such as Redis with a TTL, and skip messages whose ID was already seen. Enable the idempotent producer setting so the broker itself detects and drops duplicate produces for a given producer session. Choose the delivery semantics deliberately: exactly-once is expensive and rarely needed, so document the at-least-once model and design business logic that is commutative or naturally deduplicable. Add monitoring that counts duplicates per topic so a rise in the duplicate rate surfaces as an upstream problem. Interviewers look for the insight that "handle duplicates" means "be idempotent," a correct understanding of Kafka delivery semantics, and practical patterns like unique keys and deduplication stores.

9. Kafka messages are out of order. How do you handle it?
   - **Answer:** Ordering in Kafka is guaranteed only within a single partition, so the answer always starts with how messages are partitioned. If strict per-entity ordering matters, derive a partition key from the entity (such as sensor ID or order ID) so all messages for that entity land in the same partition and are processed in order by the consumer. Understand that a producer that enables retries can resend an older message after a newer one, and in-flight ordering depends on the max in-flight requests setting, so order-sensitive producers should set `max.in.flight.requests.per.connection=1` or use the idempotent producer, which preserves ordering. Out-of-order also appears at the application layer if the consumer is multi-threaded and processes messages within a partition concurrently, so per-partition sequential processing must be preserved if order matters. For data that carries its own timestamp or sequence number, design the sink to handle late-arriving data with a tolerance window: record the latest seen event time per entity, and decide whether to ignore, reorder, or correct earlier writes. Recognize the trade-off between ordering and parallelism: strict global ordering serializes throughput, so scoping ordering to the entity level is usually the right balance. Document the ordering guarantee consumers can rely on, and reject or flag messages that fall outside the allowed skew window. Interviewers look for a precise understanding of partition-level ordering guarantees, a correct partition-key design, and an appreciation that ordering and parallelism are a deliberate trade-off.

10. A Kafka consumer keeps failing on one message. What do you do?
    - **Answer:** A single message that permanently fails is the classic poison-pill pattern, where a consumer group can get stuck in a retry loop, stall the whole partition, or crash repeatedly on startup. First inspect the consumer logs and the payload itself to understand why it fails: schema mismatches, invalid or truncated data, missing required fields, or downstream errors triggered only by that record. If the error is transient, retry with backoff for a bounded number of attempts; if it is permanent, retrying is wasted work. Route the failed message to a dead-letter topic after the retries are exhausted, and record the original topic, partition, offset, and the failure reason alongside the payload so it can be analyzed and replayed after a fix. Keep the error-handling strategy in the consumer configuration so a poison pill does not loop indefinitely or block the rest of the partition. Alerts should fire when messages land in the DLQ, since a steady stream indicates an upstream data-quality problem. Fix the root cause at the source where possible, and build a replay tool that lets an operator repair the message and re-submit it after the schema or data issue is corrected. Interviewers look for a bounded retry strategy, correct use of a dead-letter queue, and the operational discipline to alert on and permanently resolve the underlying data problem rather than silently skipping records.

11. AWS Lambda is timing out. How do you debug it?
    - **Answer:** Timeouts happen when the function does not finish inside its configured duration, so the investigation starts with confirming what the function is actually waiting on. Check CloudWatch Logs for the invocation's timestamps and any logged steps to see whether time is spent in initialization, external calls, or computation. Pull the function's CloudWatch metrics for duration and concurrency to see whether timeouts are isolated to specific payloads or correlated with load. Common causes are synchronous calls to slow downstream services such as a broker or database without an appropriate timeout, cold starts, an undersized memory setting (which also caps CPU), and initialization work that runs on every invocation instead of outside the handler. Look for connection creation per invocation that should be reused, and for payload sizes that are too large for a request-response flow. Verify the timeout value is set deliberately rather than left at a default that does not match the workload, and consider decoupling long work with an async invocation or SQS so the function does not need to complete before responding. Use Lambda power tuning to find the memory level that minimizes cost and duration, and enable X-Ray or structured logging to trace where the time goes. Interviewers look for the ability to read Lambda-specific metrics and logs, a habit of isolating external call latency from compute time, and knowledge of the memory-versus-CPU relationship and async invocation options.

12. EC2 deployment failed after Jenkins pipeline ran successfully. What do you check?
    - **Answer:** A green pipeline followed by a failed deployment points at a gap between what the pipeline validated and the conditions on the target instance, so treat the two as separate problems. Start with the instance itself: connect to EC2 and inspect application and container logs for startup errors, then check basic resources like disk space, memory, and CPU, because full disks are a frequent cause of failed startups. Verify that the artifact or image referenced by the deployment actually exists and is reachable from EC2, including the correct image tag, and confirm the Docker daemon or service manager is running. Compare the environment on the instance with the one the pipeline tested: environment variables, secrets, mounted volumes, file permissions, and the OS architecture can all differ and break startup. Check security group and network rules, since an instance that cannot reach the database, registry, or other services will fail at runtime even though the build succeeded. Look at recent instance-level changes such as a new AMI, updated configuration, or resource limits, and check cloud-init or user data logs that may show configuration errors. Decide between fixing forward and rolling back the image to the previous known-good version, then redeploy with smoke tests. Interviewers look for an organized troubleshooting sequence that separates build from runtime, checks environment drift, and validates resources and connectivity before assuming code is at fault.

13. API response time increased suddenly. How do you debug it?
    - **Answer:** A sudden regression is almost always caused by a change, so start by correlating the spike with deployments, configuration changes, and data growth, and use APM or request logs to pinpoint which endpoint is slow and whether the time is spent in the application, the database, or an external call. Look for the classic culprits: a query whose plan changed or stopped using an index, a cache with a poor hit ratio suddenly falling back to the database, thread-pool exhaustion from slow upstream calls, and growing payloads. Check whether the slowdown affects all requests or only a subset, because that distinguishes a global capacity problem from a single hot path. Use percentiles rather than averages, since p95 and p99 reveal slow tail requests that averages hide. Sample slow requests and inspect their stack traces and the SQL or external calls they issued. Verify the dependency direction: a slow third-party API or a database under load can back up the application through thread starvation even when the application code is unchanged. Mitigate immediately by scaling, failing fast, or reducing work per request, then fix the root cause and add alerting on latency percentiles so the next regression is caught automatically. Interviewers look for the correlation-first instinct, use of percentiles and tracing, and the ability to separate application, database, and network contributions to latency.

14. Database connections are exhausted. How do you debug it?
    - **Answer:** Connection exhaustion means the pool is empty and new requests are queuing or failing, so the investigation targets two questions: who is holding connections, and why are they not being released. On the database side, query the active connection and session list to group by user, application, and host, and look for connections idle in transaction or with very long-running queries. On the application side, check the connection pool metrics (active, idle, pending, and timeout counts) to see whether the pool is legitimately saturated or leaking connections. The most common causes are code that opens a connection and never closes it, a long-running query or slow upstream call that holds a pooled connection for minutes, a pool size that is too small for peak concurrency, and blocked queries waiting on locks that tie up sessions. If leaks are suspected, enable leak detection in the pool, review transaction boundaries, and scan for manually opened connections not closed in a finally block or try-with-resources. If capacity is the issue, configure the pool deliberately with a maximum size that fits the database's limits, and set connection and idle timeouts so slow or broken connections do not accumulate. Also check for connection-count multiplication: several services each opening large pools against one database can exhaust it collectively. Prevention includes pool and database-side monitoring with alerts on active-connection thresholds and long-held connections. Interviewers look for the ability to read both pool metrics and database session lists, the discipline to distinguish leaks from saturation, and correct pool configuration rather than just raising the maximum.

15. Redis cache has stale data. How do you fix it?
    - **Answer:** Stale data means the cache returned a value that no longer matches the source of truth, which is a design issue in the invalidation strategy rather than a Redis bug. Decide which consistency model the application needs: cache-aside with TTL accepts bounded staleness, while write-through or explicit invalidation gives stronger consistency. The quickest mitigation is shortening the TTL so stale entries expire sooner, but that trades cache hit rate for freshness and does not fix the underlying cause. The durable fix is invalidating the cache when the underlying data changes: either invalidate the keys involved in the write transaction, or publish an invalidation event (for example, through Redis Pub/Sub or the application event bus) that all cache nodes honor. Be careful with distributed systems where multiple instances can write, because deleting a key is safer than updating it, since updating concurrently can race and reintroduce stale values. Versioning keys (cache key includes a data version or timestamp) prevents stale reads across asynchronous pipelines. Monitor cache hit ratio and staleness together, and treat TTL as the safety net rather than the primary correctness mechanism. Interviewers look for an explicit consistency model, correct invalidation design, and an understanding that TTLs mask staleness problems while invalidation solves them.

16. A scheduled job runs on all pods and sends duplicate emails. How do you solve it?
    - **Answer:** The problem is that a scheduler triggers the same job on every instance, so the goal is to guarantee single-instance execution using a coordination mechanism. The standard solution is a distributed lock: the first instance to acquire the lock runs the job, and the others skip that run. A Redis-based lock such as Redisson, or a database lock table with a unique row per job, both work; the key is that acquisition must be atomic so two instances cannot both acquire simultaneously. Configure a lease or lock TTL that is longer than the longest possible job run so the lock does not expire mid-run (which would let a second instance start a duplicate), but short enough that a crashed instance does not block future runs forever. Handle lock-acquisition failure gracefully by logging and skipping rather than failing the whole pod. Prefer scheduler libraries that natively support this, like a `@SchedulerLock`-style wrapper around the cron trigger, so the coordination is part of the job declaration rather than ad hoc code. Record which instance executed each run, and monitor lock status, so skipped runs and unexpected lock holders are visible. Interviewers look for knowledge of distributed locking, the atomicity requirement behind it, and awareness of the lease-time versus crash-recovery trade-off.

17. A scheduled job is missing executions. How do you monitor it?
    - **Answer:** Missing executions are a monitoring gap, so the fix is to make the job's execution observable and verifiable rather than only logging output that nobody reads. Add clear start and end logging with timestamps and any relevant result counts, and write a heartbeat or "last executed at" marker that can be checked independently of the job's own logs. Expose execution metrics (last success time, last duration, success/failure counts) through a health endpoint or metrics system so the scheduler state is visible to dashboards and alerting. The important alert is on absence, not failure: set up a watchdog that fires if a job that should run hourly has not recorded a successful execution within its expected window, because a job that silently never ran is harder to detect than one that logs an error. Track reasons for misses, which include nodes being down or scaled to zero during the window, the scheduler being paused, overlapping runs that exceed the interval, and timezone or DST issues with cron expressions. Consider whether the job should be pushed through a queue or deduplicated so a miss can be retried instead of simply lost. Interviewers look for alerting on expected presence rather than just errors, observability of scheduled work, and an understanding of the operational modes in which jobs silently do not run.

18. JWT works locally but fails behind load balancer. What do you do?
    - **Answer:** The difference between the local environment and the load balancer is usually the terminating proxy, so compare the headers and connection context that the application receives in each case. The most common causes are the load balancer stripping or modifying the Authorization header, SSL termination that changes the scheme from HTTPS to HTTP, and settings like the `Secure` flag on cookies that are invalid when the app thinks it is on a plain HTTP connection. Check the `X-Forwarded-Proto`, `X-Forwarded-Host`, and `X-Forwarded-For` headers that the load balancer inserts, and ensure the application is configured to trust them and reconstruct the original scheme. If the token is carried in a cookie, verify that the cookie `Secure` flag, `SameSite` attribute, and domain/path match the actual production URL, since a mismatch makes the browser silently drop the cookie. If the token is in the Authorization header, confirm the load balancer is not inspecting, rewriting, or stripping headers, and confirm any request-size limits do not reject large tokens. Also check whether the load balancer or its TLS layer is modifying the request such that the token's signature validation or issuer/audience validation fails against a different base URL. Interviewers look for a systematic comparison of the request path in both environments, knowledge of proxy header semantics, and the ability to check token transport (header vs cookie) settings.

19. Users get 403 after enabling CSRF. How do you fix it?
    - **Answer:** Understand what CSRF protection is for before disabling or adjusting it: it prevents a malicious website from triggering state-changing requests by exploiting cookies that a browser sends automatically. Applications that authenticate with a bearer token in the Authorization header are not vulnerable to classic CSRF because browsers do not automatically attach that header to cross-origin requests, so CSRF protection is unnecessary and only adds friction. For a token-based API, the correct fix is to disable CSRF for the stateless endpoints while keeping it enabled where cookie-based authentication is used, so state-changing requests from a cookie-authenticated browser are still protected. If CSRF is genuinely required, the proper approach is a token: the server issues a synchronizer token that the client echoes in a header or body field, and the server rejects requests without a valid token. Validate that the CSRF token is actually being sent by the client: frameworks such as Spring require the token to be included in every state-changing request, and a missing or mismatched token produces the 403. Also check that cookie settings (SameSite) and the CSRF token repository match the SPA's setup. The answer should show an understanding of the threat model rather than a reflex to disable protection. Interviewers look for a correct mental model of when CSRF applies, the distinction between cookie-based and token-based authentication, and the ability to configure rather than blindly disable security.

20. Admin role update is not reflected immediately. How do you design it?
    - **Answer:** The delay is a consequence of where authorization data lives: if roles are embedded in a signed token such as a JWT, they cannot change until the token is reissued, whereas checking the database on every request gives immediate effect but costs a lookup. The design starts by defining the freshness requirement and choosing the right trade-off. For roles that must take effect immediately, perform the authorization check against the database or a near-realtime cache keyed by the user and role on each request, invalidating the cache when a role changes. For roles where minutes of delay are acceptable, short-lived tokens (for example, five to fifteen minutes) bound the staleness, and forcing re-login or proactively refreshing the token after a role change provides immediate effect for the affected user. A hybrid approach uses short-lived tokens for common requests and a database-backed check for sensitive operations such as admin actions. Whatever the choice, centralize the decision in an authorization service so role changes propagate consistently, and add a per-user role version that is compared on each request to trigger token refresh. Log role changes and the time they became effective to make behavior explainable. Interviewers look for an explicit freshness-versus-latency trade-off, knowledge of the token staleness property, and a design that is consistent and testable rather than an accidental behavior.

21. Production API returns 500 but logs are unclear. How do you improve observability?
    - **Answer:** Unclear logs are an observability debt that must be paid in the middle of an incident, so the improvement plan focuses on making every failure diagnosable from data that already exists. Adopt structured logging with JSON so every entry has machine-parseable fields, and include a correlation or trace ID that is generated at the edge and propagated through the request chain so all logs for one request can be grouped. Ensure exceptions are logged with the full stack trace, the request path, method, and the parameters that triggered the failure, but be careful about logging sensitive data. Add request and response logging with timing at the API boundary to correlate status codes with latency. Publish error-rate metrics and alert on spikes rather than relying on someone opening a log viewer. Use a distributed tracing system to connect the failing request across services, and an APM tool to link a 500 to the exact span and stack trace. Instrument the application health endpoint with dependency status so failing downstream calls are visible. Log correlation IDs in the response headers so a reported 500 can be tied directly to server logs. Interviewers look for a concrete observability stack (structured logs, trace IDs, metrics, alerting), an understanding that unclear logs are a design failure, and the ability to prioritize instrumentation that pays off during incidents.

22. A service dependency is down. How should your service behave?
    - **Answer:** A well-designed service assumes dependencies fail and plans for that state rather than treating availability as guaranteed. The first requirement is bounded failure: every call to a dependency must have a timeout, otherwise a slow or hung dependency consumes threads and drags down the whole service. Add a circuit breaker so that after a dependency fails repeatedly, the service fails fast on subsequent calls instead of hammering a dead endpoint. The service should degrade gracefully by serving cached or last-known data when the dependency is down, and it must mark that data as stale so consumers do not mistake it for fresh. When no fallback exists, return a meaningful, structured error that tells the caller what is unavailable, rather than an ambiguous 500. Protect the rest of the system with bulkheads so that a failing dependency's retry storm does not exhaust the thread pool shared with healthy dependencies. Consider queuing work that can be retried once the dependency returns, so no data is lost during the outage. Monitor the dependency's health, circuit-breaker state, and the proportion of requests served from fallback, and alert on degraded mode. Interviewers look for resilience patterns (timeout, retry with backoff, circuit breaker, fallback, bulkhead) and a bias toward predictable degradation over heroic attempts to keep everything working.

23. A dashboard becomes slow with live data. How do you optimize it?
    - **Answer:** Live dashboards degrade when both the data pipeline and the frontend are doing more work than they need to, so optimize both ends together. On the backend, reduce the amount of data crossing the wire by pre-aggregating in the database: store downsampled or summarized series for the time ranges the dashboard displays rather than returning raw points. Add caching for hot queries and paginate or cap the number of rows returned so a single render never pulls a huge dataset. Use push-based delivery such as WebSocket or Server-Sent Events instead of aggressive polling, and push only deltas or batch updates on a schedule (for example, every few seconds) rather than on every event, so the browser is not re-rendering thousands of times. On the frontend, virtualize long lists so only visible rows render, memoize components to skip unnecessary re-renders, and debounce interactions such as window resizing. Simplify what the browser computes: compute derived values on the server or pre-compute them, and avoid re-running expensive selectors on every state change. Measure the slow endpoint's query time, payload size, and frontend render time separately so optimization targets the actual bottleneck. Interviewers look for end-to-end thinking from database to render loop, an understanding of aggregation and push vs poll trade-offs, and a habit of measuring before optimizing.

24. IoT sensor sends invalid readings. How do you validate them?
    - **Answer:** Validation for IoT data needs layers, because a reading can be invalid in different ways: malformed, out of range, physically impossible, or indicative of a failing sensor. Start with format validation at the ingestion edge: confirm the payload parses, has the required fields with correct types, and carries a valid device ID and timestamp. Apply physical plausibility checks, such as a plausible temperature range for the sensor type and a maximum rate of change (a temperature jump of 20 degrees in one minute is suspicious even if each value is in range). Classify failures instead of rejecting everything: reject malformed data, flag or quarantine data that fails plausibility checks for review, and interpolate or ignore small gaps caused by transient communication errors. Detect sensor malfunction patterns such as a constant value over a long period, which passes range checks but indicates a frozen sensor, and mark the device itself unhealthy rather than just the reading. Include a device-level watchdog that alerts when a sensor stops reporting or reports constant values, since missing data is as important as bad data. Store raw data separately from validated data so bad input can be re-analyzed after a rule change. Interviewers look for a layered validation model, the distinction between rejection and flagging, and awareness that validation rules must handle both bad values and bad behavior over time.

25. IoT gateway sends data in bursts. How do you handle backpressure?
    - **Answer:** Bursts are the normal behavior of IoT gateways, which reconnect after network outages and catch up on buffered data, so the architecture must absorb bursts without loss or overload. The right tool is an unbounded buffer with a consumer that drains at its own rate, and a message queue such as Kafka is a natural fit because producers publish at their own speed while consumers commit at theirs. When the burst arrives, the queue grows and consumer lag increases temporarily, but as long as the drain rate eventually exceeds the sustained arrival rate, the backlog clears without dropping data. Monitor lag as the key signal, and distinguish acceptable transient lag from sustained growth that means the consumer is the bottleneck. If bursts routinely exceed capacity, add consumer instances up to the partition count, then increase partitions for more parallelism, and batch writes downstream so the consumer's throughput rises. At the ingestion edge, rate-limit or negotiate with gateways if sustained rates exceed what the platform can handle, and design for drop-then-reconcile semantics if data loss is acceptable for some telemetry. Persist buffered data on the gateway itself so a long outage does not create an unbounded replay. Interviewers look for a clear grasp of queues as shock absorbers, lag as the diagnostic signal, and the distinction between transient backpressure and a genuine throughput shortfall.

26. A database migration causes backlog. How do you recover safely?
    - **Answer:** A migration that falls behind creates a two-part problem: the backlog must drain, and the migration must not cause further damage or data loss. First stop the bleeding by pausing or rate-limiting new writes to the affected table if they are compounding the backlog, and assess how large the backlog and the migration's error rate actually are. Identify whether the backlog comes from the migration being too slow, from failures causing retries, or from lock contention, because each has a different remedy. If the migration is safe to continue, speed it up by batching: process in chunks with bounded commit sizes and index maintenance, or run batches in parallel if the schema permits. If the migration is unsafe or has produced inconsistent data, the safe recovery is to restore from a backup with point-in-time recovery, then re-run a corrected migration. Before re-running, fix the root cause in the script, test it on staging with production-sized data, and have a rollback script ready. Prefer backward-compatible migrations (additive columns, new tables) so old code can continue while the migration progresses, and keep migration and rollback in the same versioned change. Add monitoring on migration progress, error rate, and backlog size so recovery is data-driven rather than guesswork. Interviewers look for calm, ordered triage, the discipline to restore rather than patch when data integrity is at risk, and a migration process designed to be reversible from the start.

27. A deployment needs rollback. What is your process?
    - **Answer:** A reliable rollback is planned before the deployment, not improvised during the incident, so the process starts with keeping deployable artifacts immutable and versioned. Retain the previous image or artifact so rollback is a one-step action: point the deployment back at the last known-good version and redeploy, which should be fast because the artifact already exists. The critical constraint is database compatibility: if the new code changed the schema, rolling back the code while the database stays at the new version breaks, so the database change must be backward-compatible or the database must be rolled back too. Prefer expand-contract migrations (additive first, drop later) so both old and new code can run against the same schema. After rolling back, run smoke tests on the critical paths to verify the previous version is actually healthy. Decide between rollback and fix-forward: for data or irreversible changes, shipping a forward fix is often safer than reverting. Escalate according to the runbook, communicate status to stakeholders, and hold a postmortem to determine why the deployment failed and what guardrails should catch it earlier. Interviewers look for pre-planned reversibility, an understanding of the code-versus-database coupling, and the judgment to choose between rollback and forward fix.

28. A Docker container works locally but fails on EC2. What do you check?
    - **Answer:** Local-versus-production container failures are almost always environment drift, so the investigation is a systematic comparison of everything the container depends on. Compare environment variables and secrets: a missing variable or an empty value that existed locally changes the runtime completely. Check resources, because an instance with less memory or a memory limit will let the container start and then get OOM-killed, while local Docker with abundant RAM never hits the limit. Inspect container logs and `docker inspect` for the exit code and restart policy to see whether it crashed at startup or was killed. Verify the image: the instance may be pulling a different tag, an older cached image, or an image built for a different architecture, so confirm the exact digest is the same one that ran locally. Check mounted volumes and permissions: a missing or read-only mount, or a file owned by a different UID, breaks applications that write files. Check network: security group rules, a VPC that cannot reach the database, or a registry that is unreachable from the instance. Also compare the host OS and Docker version for subtle incompatibilities. Interviewers look for a disciplined checklist that compares image, config, resources, storage, and network, plus the understanding that "works locally" only proves the code, not the environment.

29. A REST API has inconsistent error responses. How do you standardize it?
    - **Answer:** Inconsistent errors are a contract problem, and fixing them means enforcing one shape at one choke point instead of scattering error handling across controllers. Implement a global exception handler that catches every unhandled exception and maps it to a single, documented error format, for example a body with a timestamp, an HTTP status, an error code, a message, and a path or correlation ID. Use HTTP status codes meaningfully: 400 for validation failures, 401 for unauthenticated, 403 for forbidden, 404 for missing resources, 409 for conflicts, and 429 for rate limits, with 500 reserved for unexpected server errors. For validation errors, return the list of offending fields in a consistent sub-structure so the frontend can render them generically. Document the error schema in the OpenAPI specification, including each error code's meaning and when it occurs, so clients and backend evolve against the same contract. Ensure that even unexpected exceptions produce the standard shape rather than a framework default page, and log the full details server-side while exposing only safe information to the client. Add tests that assert every endpoint returns the documented error format. Interviewers look for a single source of truth for error handling, correct and deliberate status-code usage, and the contract-first thinking that treats errors as part of the API surface.

30. A frontend user sees pages they should not access. How do you fix RBAC?
    - **Answer:** The failure usually comes from relying on frontend-only protection, which is a usability convenience, not a security boundary. Hiding a button or blocking a route in the browser does not protect data, because an attacker can call the API directly, so the fix is to enforce authorization on the server and treat the frontend as purely cosmetic. Confirm the backend enforces role-based checks on every API endpoint, for example method-level authorization, and that these checks cannot be bypassed by calling a sibling endpoint that lacks the guard. On the frontend, align route guards and conditional rendering with the same role model so users do not see controls they cannot use, but never rely on those guards as the security control. Check how roles are obtained and whether they are current: a token with stale roles, or a client that trusts its own claims, produces both false negatives and false positives. Ensure default-deny behavior so an unlisted role or endpoint is denied rather than allowed. Add tests that verify authorization at the API level, including negative tests asserting that users without the role get 403. Interviewers look for the core principle that authorization is server-side truth, an understanding of defense in depth, and the ability to align UX and security without confusing the two.

31. A stored procedure returns correct results but is slow. What metrics do you check?
    - **Answer:** Correctness rules out a logic error and points the investigation at resource usage and plan quality, which are best quantified with measured metrics. Capture the actual execution plan and examine it for scans, key lookups, sort and spool operators, and large discrepancies between estimated and actual rows. Use `SET STATISTICS IO` to read logical reads, which directly reflects how many pages the query touches and is the most reliable indicator of inefficiency, and `SET STATISTICS TIME` for CPU and elapsed time. Inspect wait stats for the session to classify the bottleneck as CPU, I/O, or blocking: `CXPACKET` and `SOS_SCHEDULER_YIELD` point at parallelism issues, `PAGEIOLATCH` at I/O, and blocking waits at locks. Compare execution plans and stats for the same query under different parameter values to expose parameter sniffing, and with `OPTION (RECOMPILE)` to see whether a stale cached plan is the problem. Check index usage and fragmentation, and whether functions or implicit conversions on indexed columns force scans. Combine the numbers into a story: high reads with scans means index or query-shape work, high waits with low CPU means contention or I/O, and plan instability means statistics or sniffing. Interviewers look for concrete, measurable diagnostics (reads, waits, elapsed, plans) and the ability to attribute slowness to a class of problem before prescribing a fix.

32. A query is fast for one parameter but slow for another. What could be wrong?
    - **Answer:** This is the signature of parameter sniffing: the optimizer compiles the plan using the statistics for the first parameter value it sees, and that plan is poor for other values. A parameter with a selective, narrow filter produces a seek plan that is terrible when the same query is later called with a broad filter that should scan. It can also be caused by data skew, where one parameter value matches a huge fraction of rows and another matches almost none, so no single plan suits both. Check that the parameter's data type matches the column's data type, because an implicit conversion can prevent the optimizer from using the index for some values. Confirm statistics are current, since stale stats mislead the optimizer regardless of the parameter. Test the diagnosis with `OPTION (RECOMPILE)` to see if forcing a fresh compile fixes the slow case. The durable fix depends on the pattern: `OPTION (OPTIMIZE FOR UNKNOWN)` makes the optimizer use generic averages, splitting the query into a fast path for the selective case and a scan path for the broad case can serve both well, and keeping plans in Query Store with plan forcing stabilizes behavior. Document why the chosen strategy works for the data distribution. Interviewers look for the ability to name parameter sniffing, reason about selectivity and data skew, and choose a targeted fix rather than disabling plan caching entirely.

33. A microservice is receiving duplicate requests. How do you make it idempotent?
    - **Answer:** Idempotency means the effect of processing a request twice is identical to processing it once, and it is achieved by keying the operation to a stable identifier the client supplies. Have the client generate an idempotency key, typically a UUID, for each logical operation and send it in a header, then have the server check whether it has already seen that key before performing the work. Persist the key together with the operation's result in a store that enforces uniqueness, such as a database table with the key as a primary key or a unique index, or Redis with a TTL for a bounded window. On a duplicate request, return the previously stored result instead of executing the operation again, so retries after timeouts do not double-charge or double-insert. Choose the scope of the key carefully: it should represent the logical operation, and reusing one key for different payloads would be a bug. Ensure the idempotency check and the operation are atomic, otherwise two racing requests can both pass the check; a unique constraint converts the race into a handled duplicate. Decide the retention window for keys (hours to days) and clean them up. Interviewers look for the client-supplied key pattern, atomicity of the check-and-execute, and the understanding that idempotency keys convert retries from a correctness risk into a no-op.

34. A payment-like operation succeeds but client times out. How do you handle retry?
    - **Answer:** The scenario is the classic double-payment hazard: the server completed the operation, but the client never saw the response, so a naive retry would execute it again. The core requirement is idempotency, so the operation is keyed by a unique transaction or request ID that the client generates and reuses across retries; the server detects the same ID and returns the stored outcome instead of reprocessing. Give the client an explicit way to query status: a `GET /transactions/{id}` endpoint that returns the outcome of an in-flight or completed operation, so the retry logic first checks status before resubmitting. On the server side, write the intent and the outcome atomically so the recorded result survives the timeout, and ensure the write is committed before the response is sent, because an early commit is better than an ambiguous one. Use idempotent semantics in the payment provider integration too, since provider-level idempotency keys protect against retries at that layer. Distinguish the timeout phases: a request that never arrived is safe to retry, while an unknown outcome must be resolved by status lookup rather than blind resubmission. Add appropriate retry with backoff and jitter, and cap retries so the system gives up and surfaces the uncertainty to an operator or user. Interviewers look for the idempotency-key pattern, a status-check-first retry strategy, and recognition that the dangerous case is an unknown outcome, not a failed request.

35. A report must be generated exactly once across multiple servers. How do you design it?
    - **Answer:** Exactly-once execution across multiple servers is a distributed coordination problem, and the standard solution is a lock that only one server can hold. Acquire a distributed lock on a unique key identifying the report run (for example, the report name and run date), so the first server to acquire it performs the generation and the others skip the run. The lock can live in Redis, where a SETNX with an expiry guarantees a single holder, or in a database table with a unique key on the run identifier, which gives atomicity through the constraint. Set a lease that is longer than the longest plausible generation time so a slow run does not release the lock while still running, but bounded so a crashed server's lock expires and lets another instance retry. Complement the lock with a status table tracking the report lifecycle (submitted, in-progress, completed, failed), written transactionally so a crashed run leaves a visible in-progress or failed state. A scheduled cleanup job should reclaim abandoned in-progress entries after the lease expires, and the generator should write the output atomically (for example, to a temp file or temp table, then rename or commit) so consumers never observe a partial report. Interviewers look for the lock-plus-status combination, correct lease handling, and an understanding of how crash recovery interacts with the exactly-once guarantee.

36. An API must process 10,000 records. Do you process synchronously or asynchronously?
    - **Answer:** Ten thousand records is far beyond what a synchronous request-response flow should do, because the HTTP connection would be held open for minutes, risking timeouts, proxy limits, and a client that gives up. The correct pattern is asynchronous: accept the request, return 202 Accepted with a job ID immediately, and process the records in the background. The background work can be driven by a queue such as Kafka or a message queue, or by a job/worker pool, which lets the work scale independently of the API tier and gives natural retry and ordering semantics. The client then polls a status endpoint or receives a notification when the job completes, and can fetch results or an error summary. Use the job ID for idempotency so a resubmitted request does not duplicate work. Consider the trade-off explicitly: asynchronous adds components (queue, job store, status API, retries) but prevents timeouts, decouples load, and enables horizontal scaling; for small batches under a hundred records where latency is short, synchronous is simpler and fine. Interviewers look for a grasp of the volume threshold, the 202 + job ID pattern, and an honest cost-benefit analysis rather than an automatic "async always" answer.

37. A customer asks for near real-time dashboard updates. What architecture would you choose?
    - **Answer:** Near real-time means the data flow must be event-driven rather than pull-based, so the architecture moves data as it arrives and pushes it to the browser. The ingestion layer takes events and lands them in a message bus such as Kafka, which decouples producers from the consumers that prepare data for the dashboard. A backend service consumes those events, writes them to a fast time-series store, and pushes updates to connected clients over WebSocket or Server-Sent Events, which avoids the latency and load of polling. When the backend runs multiple instances, use a coordination channel such as Redis Pub/Sub so an event received by one instance is broadcast to clients connected to all instances. The frontend maintains a live connection and renders updates incrementally, applying a throttling or batching window (for example, refresh at most every few seconds) so a high event rate does not cause re-renders on every single event. Decide freshness granularity deliberately: true sub-second push has a cost, so define "near real-time" as the requirement, often seconds, and batch accordingly. Choose SSE over WebSocket when only server-to-client push is needed, since it is simpler and reconnects automatically. Interviewers look for the event pipeline concept, the choice between push and poll, multi-instance broadcast, and the discipline to define the actual latency target before designing.

38. A database table is growing very large. How do you manage performance?
    - **Answer:** Manage growth with a strategy that reduces the data the queries must touch rather than just buying more hardware. Partition the table by a natural axis such as date, so queries that filter by time access only the relevant partition and old partitions can be archived or dropped cheaply. Add a retention policy that moves cold data to cheaper storage or a separate archive table, keeping the hot working set small. Keep indexes narrow and aligned with the query patterns, drop unused indexes (each costs writes and space), and periodically rebuild or reorganize to control fragmentation. Review statistics maintenance so the optimizer's estimates stay accurate as the table grows. For time-series data specifically, downsampling or aggregation tables can serve long-range queries at a fraction of the storage cost. Consider read replicas to move reporting and analytical queries off the primary write path, and ensure application queries are paginated and selective instead of scanning the whole table. Avoid functions or wildcard patterns that defeat index usage on the largest tables. Interviewers look for partitioning, retention, and index hygiene as a coherent strategy, an understanding that the goal is shrinking the scanned data, and a willingness to trade storage for query performance deliberately.

39. A third-party API is slow. How do you protect your application?
    - **Answer:** A slow external dependency is a reliability risk because it can back up the application's threads even when the application code is fine, so the protection strategy is isolation and fallback. Give every third-party call an explicit timeout covering both connection and read, so a hung endpoint cannot hold a thread indefinitely. Add a circuit breaker that watches the dependency's error and latency rates and, after a threshold, fails fast on subsequent calls instead of waiting for the timeout every time, and opens again when the dependency recovers. Apply bulkhead isolation so the slow dependency is bounded to its own thread pool and cannot consume the resources of the rest of the application. When the dependency is unavailable or slow, serve a graceful fallback: cached or last-known data clearly marked stale, or a structured error telling the caller what is degraded. Use retries with exponential backoff and jitter only for transient failures, and cap them so a dead dependency does not cause a retry storm. Process non-critical third-party work asynchronously with a queue so interactive requests are not blocked on it. Monitor the dependency's health, timeout rates, and circuit state, and alert on degradation. Interviewers look for the timeout-circuit-breaker-bulkhead-fallback combination, an understanding of failure contagion, and explicit monitoring of external dependency health.

40. A production issue happens at midnight. How do you approach debugging?
    - **Answer:** Start by contextualizing the time window, because midnight is when scheduled work dominates: batch jobs, ETL pipelines, backups, maintenance windows, and key rotations all collide and compete for the same CPU, memory, I/O, and database capacity. Check the schedule of everything that runs at midnight and correlate the incident with the start or end of a job, then examine job logs and the database's active sessions and wait stats during the window to see which process was consuming resources. Review recent deployments or configuration changes that happened within the hours before midnight, since a new job or a changed schedule is a prime suspect. Use monitoring dashboards scoped to the exact time range to reconstruct CPU, memory, I/O, network, and error-rate timelines rather than reasoning from a single screenshot. Reproduce the behavior in staging with similar load and concurrent jobs to confirm the mechanism. If the incident is an alert, triage by impact first: is data being corrupted or lost, or is this a performance blip, and act accordingly. After mitigation, add runbook coverage for the recurring window so the next midnight incident has a documented investigation path. Interviewers look for time-correlation thinking, awareness of scheduled-work contention, the discipline to reconstruct from metrics and logs, and calm prioritization of impact over root cause.
