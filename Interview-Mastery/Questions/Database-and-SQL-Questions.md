## Answers

1. What is DBMS?
   - **Answer:** A Database Management System (DBMS) is software that defines, stores, manages, retrieves, and administers data in an organized, structured way. It sits between the application layer and the physical storage, providing an interface for users and applications to interact with data while hiding the complexities of file storage, concurrency, and recovery. A DBMS typically provides a data definition language (DDL) to create and alter schema objects, a data manipulation language (DML) to insert, update, delete, and query data, and a data control language (DCL) to manage permissions. It also handles critical internal responsibilities such as transaction logging, buffer/cache management, locking and isolation, crash recovery, and query optimization. Common examples include Microsoft SQL Server, PostgreSQL, MySQL, Oracle, and SQLite. The core value of a DBMS is that multiple users and applications can read and write the same data concurrently without corrupting it, because the engine enforces consistency and integrity rules. Modern DBMSs also expose metadata catalogs that let administrators inspect table definitions, indexes, statistics, and execution plans. Choosing a DBMS involves trade-offs around ACID guarantees, scalability model (vertical versus horizontal), licensing, and ecosystem tooling. A DBMS is distinct from a simple file system because it guarantees structured access, constraints, and transactional semantics rather than raw byte reads and writes.

2. What is RDBMS?
   - **Answer:** A Relational Database Management System (RDBMS) is a DBMS that stores data in two-dimensional tables (relations) with rows and columns, and manages the relationships between those tables using keys and referential integrity. Data is modeled relationally, so a fact about an entity lives in exactly one place and is referenced by other tables rather than duplicated. The RDBMS is built on the relational model introduced by E. F. Codd, and it exposes SQL as the standard language for querying and manipulation. Key features include primary keys to uniquely identify rows, foreign keys to link tables, and constraints (NOT NULL, UNIQUE, CHECK) that enforce data quality at the engine level. RDBMSs guarantee ACID transactions, which makes them the default choice for OLTP systems such as banking, e-commerce, and inventory management where data accuracy is non-negotiable. Compared with NoSQL stores, an RDBMS provides strong consistency, ad-hoc queryability via JOINs, and mature tooling, at the cost of less flexible schemas and more complex horizontal scaling. The relational design is normalized to remove redundancy, and query performance is enabled by indexes created on frequently filtered or joined columns.

3. What is primary key?
   - **Answer:** A primary key is a column or set of columns that uniquely identifies each row in a table and cannot contain NULL values. Every table should have exactly one primary key, and its value must be unique for every row for the entire lifetime of that row. The primary key is backed by a unique index that enforces the uniqueness constraint and makes point lookups by that key fast. In SQL Server, creating a primary key automatically creates a clustered index by default, which physically orders the table data by that key. The primary key is also the natural target for foreign key references from other tables, forming the backbone of referential integrity. Choosing a good primary key matters: surrogate keys like an auto-incrementing integer (`IDENTITY`) or a `GUID` are preferred over natural keys because they are stable, narrow, and never change. A wide or volatile primary key can degrade the clustered index and bloat every non-clustered index that references it, since non-clustered indexes store the clustered key as the row locator. The declaration `ALTER TABLE Customers ADD CONSTRAINT PK_Customers PRIMARY KEY (CustomerId);` both constrains the data and creates the underlying index.

4. What is foreign key?
   - **Answer:** A foreign key is a column or set of columns in one table that references the primary key (or a unique key) of another table, creating a relationship between the two. It enforces referential integrity: a value inserted into the foreign key column must already exist in the referenced table, or the insert is rejected. Foreign keys can also define cascading behaviors such as `ON DELETE CASCADE` or `ON UPDATE CASCADE` to propagate changes, though cascades should be used carefully because they can silently delete large amounts of data. There are three common relationship types: one-to-many (an order header referencing a customer), one-to-one (a user profile referencing a user account), and many-to-many (implemented with a junction table holding two foreign keys). A subtle but important performance point: creating a foreign key does not automatically create an index on the foreign key column, so queries that join on that column, or deletes that check child rows, can cause table scans. Adding an index on foreign key columns is a standard optimization for join-heavy workloads. Foreign keys also help the query optimizer make better cardinality estimates, and they prevent orphan rows that would otherwise produce incorrect or inconsistent query results.

5. What is unique key?
   - **Answer:** A unique key (or unique constraint) guarantees that every value in a column or combination of columns is distinct across the table. Unlike a primary key, a unique key allows NULL values (in most databases, multiple NULLs are permitted), and a table can have many unique keys while it can have only one primary key. A unique constraint is implemented with a unique index, which both enforces the rule and makes lookups on that column fast. Unique keys are typically used for business-level uniqueness that is not the identity of the row — for example, an `Email` column or a `(PartnerId, SerialNumber)` pair must be unique even though a surrogate integer is the primary key. Declaring uniqueness at the engine level is always preferable to checking in application code, because it is race-condition-proof: two concurrent inserts cannot both slip past an application-level check. A unique index also provides a useful optimization target for queries that filter by those columns. In SQL Server, a filtered unique index can enforce uniqueness on only a subset of rows, such as a single active record per group, which is otherwise impossible with a standard constraint. The syntax `CREATE UNIQUE INDEX UX_Employees_Email ON Employees(Email);` demonstrates the combined constraint and index.

6. Difference between primary key and unique key.
   - **Answer:** Both enforce uniqueness, but they differ in several important ways. A table can have only one primary key, but multiple unique keys. A primary key cannot contain NULL values, whereas a unique key typically allows NULLs (usually multiple NULLs), though the exact behavior varies by database. The primary key represents the identity of the row and is the natural reference target for foreign keys, while a unique key guards a business column that must not repeat. In SQL Server, a primary key is clustered by default, meaning the data pages are physically ordered by that key; a unique key creates a non-clustered index unless it is explicitly made clustered. Because the clustered index is the base table in SQL Server, every non-clustered index stores the clustered key as the row locator, so a wide or volatile primary key inflates every secondary index. The primary key is part of the relational design that defines how tables reference each other, whereas unique keys protect data quality. Choosing the right clustered key — narrow, stable, monotonically increasing — is one of the most impactful physical-design decisions for write-heavy tables.

7. What is index?
   - **Answer:** An index is a database structure that speeds up data retrieval by providing a fast lookup path for the values in one or more columns. The most common implementation is a balanced tree (B-tree), where the leaves at each level are sorted and linked, allowing the engine to find a value in logarithmic time instead of scanning the whole table linearly. Each index key column is a copy of the indexed column values, stored in sorted order, plus a reference (row locator) pointing back to the actual data row. When a query filters, joins, or sorts on an indexed column, the optimizer can use the index to read only the relevant pages. Indexes are separate objects from the table: they occupy disk space, consume memory for caching, and must be maintained on every INSERT, UPDATE, and DELETE. Multiple index types exist — clustered, non-clustered, composite, covering, filtered, and columnstore — each tuned for a different access pattern. An index does not change query results; it only changes how efficiently the engine can produce them. Over-indexing is a real risk, so each index should justify its maintenance cost by serving one or more frequent, expensive queries.

8. How does indexing improve performance?
   - **Answer:** Indexing improves performance by converting expensive linear scans into logarithmic or near-constant-time lookups. A B-tree index lets the engine navigate from the root through intermediate levels to the leaf node containing the target key, so finding a row among a million rows costs only a handful of page reads. Without an index, the engine must read every data page to evaluate a predicate; with an index it reads only the pages that can possibly match. Indexes also benefit JOINs: when both sides of a join predicate are indexed, the engine can use an index seek per probe (nested loop) or merge the two sorted structures (merge join) instead of hashing entire tables. Sorted index keys allow ORDER BY and range scans (BETWEEN, >, <) to be served in index order without a separate sort operation. A covering index, which includes all columns referenced by a query, allows the query to be answered entirely from the index pages, avoiding a trip to the clustered table. The query optimizer chooses between scan and seek based on index structure and column statistics: if the predicate is highly selective, the seek wins. Indexing works best when queries use sargable predicates — comparisons on the raw column value — because wrapping the column in a function like `YEAR(OrderDate)` makes the index unusable.

9. What are the disadvantages of indexes?
   - **Answer:** Every index costs write performance: each INSERT, UPDATE, or DELETE must also update every index that covers the affected columns, so more indexes mean slower and more expensive writes. Indexes consume disk space, often several times the size of the indexed data when many wide or covering indexes exist, and they compete for buffer-pool memory when accessed. Heavy update patterns can cause page splits when an index page fills up and must be divided, leading to fragmentation that degrades reads over time until the index is rebuilt or reorganized. The query optimizer must also spend time choosing among the available indexes; with many overlapping indexes, it can pick a suboptimal one, and maintaining statistics for many indexes adds overhead. Indexes can even be counterproductive on small tables, where a full table scan is cheaper than traversing index levels and then performing lookups. Finally, indexes are not a substitute for good query design — a poorly written non-sargable query will scan an index just as expensively as it scans the table. The practical rule is to index the columns that appear in frequent WHERE, JOIN, and ORDER BY clauses, and to remove redundant or unused indexes periodically based on actual usage statistics.

10. What is clustered index?
    - **Answer:** A clustered index determines the physical storage order of the data rows in a table, which means a table can have at most one clustered index because the rows can be physically sorted in only one way. In SQL Server the clustered index is effectively the table itself — the leaf level of the clustered index contains the actual data rows, not pointers to them. Because lookups via a clustered index reach the full row immediately, it is the fastest way to retrieve data. When a primary key is created in SQL Server, it becomes the clustered index by default. The clustered key is also embedded in every non-clustered index as the row locator, so a narrow, stable clustered key keeps all secondary indexes small. A good clustered key is monotonically increasing (like an identity column) because random inserts cause page splits, fragmentation, and poor fill rates. Range scans are especially efficient on a clustered index because the data is already physically ordered by the key, so an ORDER BY on that column needs no sort. Choosing a clustered index is a design decision: OLTP tables favor narrow surrogate keys, while large analytical fact tables sometimes cluster on a date or partition key to speed range-based reporting.

11. What is non-clustered index?
    - **Answer:** A non-clustered index is a separate structure that contains a sorted copy of the indexed key columns plus a row locator pointing to the actual data. Unlike a clustered index, a table can have many non-clustered indexes, each tuned for a different query pattern. In SQL Server, the row locator is the clustered index key when a clustered index exists, otherwise it is a physical row identifier. Because the index is physically separate, querying through a non-clustered index typically requires two steps: navigating the index B-tree to find the matching key entries, then fetching the actual rows from the clustered table. When many rows match and the index does not cover the query, those per-row fetches become random I/O, which can make a scan cheaper than a seek. Non-clustered indexes are the workhorses of query tuning: they are created on foreign key columns to speed joins, on WHERE clause columns to speed filters, and with INCLUDE columns to become covering. A key lookup (or "bookmark lookup") in the execution plan signals that the non-clustered index lacked the columns the query needed. Adding INCLUDE columns to the index can eliminate lookups entirely for the most frequent queries, at the price of a larger, more expensive-to-maintain index.

12. What is composite index?
    - **Answer:** A composite index is an index defined on two or more columns, such as `CREATE INDEX IX_Orders ON Orders(CustomerId, OrderDate);`. The column order is the most important design decision: the index can satisfy predicates on a leading prefix of its columns, but not on later columns alone. In other words, an index on `(A, B)` helps `WHERE A = ?` and `WHERE A = ? AND B = ?`, but does not help `WHERE B = ?`. The leftmost-prefix rule means the most selective column, or the column filtered most frequently, should lead, because it prunes the tree fastest and preserves range-search capability on the remaining columns. A range condition on the leading column stops the range optimization for subsequent columns. Composite indexes also help sort elimination: an index on `(A, B)` can serve `ORDER BY A, B` without sorting. When designing a composite index, the analysis should start with the actual workload — the columns used in equality predicates first, then range predicates, then sort columns — rather than simply listing columns in the order they appear in the query. The same set of columns can be reordered into several candidate indexes, and the estimated plan cost can be compared to choose the best one.

13. What is covering index?
    - **Answer:** A covering index is an index that contains all the columns a query needs, so the engine can answer the query entirely from the index pages without touching the base table. This eliminates the key lookup, which is the most expensive part of a non-clustered index access path because it performs random I/O per matching row. In SQL Server, a non-clustered index can have INCLUDE columns that are stored at the leaf level for exactly this purpose without being part of the key: `CREATE INDEX IX_Orders_OrderDate ON Orders(OrderDate) INCLUDE (Total, Status);`. The key columns are used for seek and range predicates, while the included columns are carried along so the SELECT list and any residual filter can be satisfied from the index. Covering indexes dramatically reduce I/O for read-heavy queries and are a first-line fix for reported "key lookup" operators. The trade-off is size: every included column is stored once per row in the index, inflating disk usage and write cost. A covering index should be designed for the exact, frequently executed query rather than built generically, because a wide index covering many queries can become nearly as large as the table itself and start to lose its benefit.

14. What is filtered index?
    - **Answer:** A filtered index is an index created on a subset of rows, defined by a WHERE clause at creation time. For example, `CREATE INDEX IX_Orders_Active ON Orders(OrderId) WHERE Status = 'Active';` indexes only active orders. Filtering makes the index physically smaller, so it uses less disk and memory, is cheaper to maintain, and can be scanned faster. Filtered indexes shine when a large share of rows in a column share the same low-cardinality value (like historical, completed rows) and only a small active subset is queried frequently. They also provide functionality ordinary constraints cannot: a filtered unique index can enforce uniqueness on only the active subset, which is a common pattern for "one active record per entity" rules. Statistics are created only for the filtered subset, giving the optimizer more accurate cardinality estimates for queries restricted to that subset than a full-column statistic would. The trade-off is that the optimizer uses the filtered index only when the query predicate is provably a subset of the filter condition, which requires the optimizer to reason about predicate implication. The filter must also be deterministic — functions like GETDATE() are not allowed in the filter definition.

15. What is index selectivity?
    - **Answer:** Selectivity measures what fraction of the rows in a table satisfy a predicate; high selectivity means few rows match (a filter ratio near zero), and low selectivity means many rows match. It is usually approximated by the ratio of distinct values to total rows in a column, the cardinality ratio. High-selectivity columns are the best index candidates because an index seek returns few rows and random I/O for the lookups stays low. Low-selectivity columns, such as a gender or boolean flag, produce indexes that return a large fraction of the table, and the optimizer will likely ignore them in favor of a scan because seeking then fetching half the table is slower than a sequential scan. Selectivity also determines composite index column order — the most selective column leads so the tree is pruned fastest. The optimizer relies on column statistics (histograms) to estimate selectivity at compile time, which is why accurate, up-to-date statistics are vital: stale statistics lead to bad row estimates, wrong operator choices, and poor plans. A value that was selective when statistics were sampled can become common later, so automatic or scheduled statistics updates are a standard maintenance task.

16. What is query execution plan?
    - **Answer:** An execution plan is the detailed step-by-step roadmap the database engine produces for how it will execute a query: which tables it reads, in what order, via which access methods (seek, scan, lookup), which join algorithms it uses (nested loop, hash match, merge join), and how it filters, sorts, and aggregates. The optimizer generates the plan from the query text, schema metadata, indexes, and statistics, choosing among a space of candidate plans the one with the lowest estimated cost. Plans can be examined in two forms: the estimated plan, produced at compile time without running the query, and the actual plan, produced at runtime and annotated with real row counts and elapsed times. Reading a plan correctly is a core tuning skill: the most expensive operator is usually the best starting point, and discrepancies between estimated and actual row counts are the strongest signal of a problem. Plans reveal missing or ineffective indexes, non-sargable predicates, redundant sorts, and accidental Cartesian products. SQL Server caches plans to avoid recompiling identical queries, which is fast but can reuse a bad plan for a different parameter value — the root of parameter sniffing problems. Tools like `SET SHOWPLAN_ALL ON`, `SET STATISTICS PROFILE ON`, and the graphical plan in SSMS expose this information.

17. How do you analyze an execution plan?
    - **Answer:** The analysis should start with the actual plan, not the estimated one, so that real row counts are available for comparison. The workflow is: enable the actual plan, look at the most expensive operator by percentage cost, check whether it is a seek or a scan, and then compare estimated rows to actual rows for that operator. A large discrepancy indicates stale statistics, parameter sniffing, or a bad cardinality estimate, and the plan hint `OPTION (RECOMPILE)` is a quick test to see whether fresh estimates fix it. Missing-index suggestions in the plan provide hints, though they must be validated against the whole workload rather than applied blindly. Additional metrics from `SET STATISTICS IO ON` (logical/physical reads, scan counts) and `SET STATISTICS TIME ON` (CPU, elapsed) quantify the cost in I/O terms. The plan should then be read left to right for the join order and join types: a hash join with a large row count may indicate a missing predicate or poor estimates, while many nested-loop iterations indicate a small driving side. Suspicious operators to search for include table scans on large tables, key lookups with high row counts, sorts not explained by an ORDER BY, and spools. After a change, the plan should be compared before and after to confirm the operator disappeared and the reads dropped.

18. What is table scan?
    - **Answer:** A table scan is an access method in which the database engine reads every row in the table to evaluate the query predicate, because no usable index exists. In a heap table, the scan reads every data page in allocation order; in a table with a clustered index, the scan reads the clustered index leaf level, which is the whole table. A table scan is optimal when the query returns a large fraction of the rows, because a sequential read of all pages is cheaper than seeking for each row individually, and the optimizer intentionally chooses scans for low-selectivity predicates. For small tables, scans are perfectly fine because the entire table fits in a few pages. The problem is when a scan hits a large table for a selective predicate — the query reads millions of rows to return a handful, wasting huge amounts of I/O. Scans on big tables in a hot query path are the first symptom to look for in an execution plan. The fix is usually an index on the filtered or joined columns, which turns the scan into an index seek. A scan should never be treated as automatically wrong; it is only wrong when the plan does not reflect the true selectivity of the query.

19. What is index seek?
    - **Answer:** An index seek is an access method that navigates the B-tree from the root down to the leaf level to find the specific rows that satisfy a predicate, touching only the relevant pages. Because each tree level reduces the search space, a seek on a large index costs only a handful of page reads regardless of table size, giving roughly logarithmic performance. For this to work, the predicate must be sargable — it must compare the raw index column to a constant or parameter, as in `WHERE OrderDate >= @from`, rather than wrapping the column in a function like `WHERE YEAR(OrderDate) = 2024`, which forces a scan because the engine cannot use the index order. A seek can also satisfy range predicates and equality predicates on a leading prefix of a composite index. A seek is the sign of a well-indexed query, but the number of rows returned matters: if the predicate is not selective, the seek returns many row locators, and the subsequent key lookups can be slower than a scan. The plan's actual row count at the seek operator should be checked to confirm the predicate is truly selective. Non-sargable rewrites, such as converting `WHERE YEAR(OrderDate) = 2024` to `WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'`, are among the highest-leverage query fixes.

20. What is index scan?
    - **Answer:** An index scan reads every entry in an index (rather than every row of the table), in index order, evaluating each row against the predicate. Because the index contains only its key and included columns, it is usually much narrower than the table, so an index scan reads fewer pages than a table scan and can still serve the query without touching the base table — that is why the optimizer sometimes chooses an index scan over a table scan. An index scan is still a scan: it reads all rows in the structure and its cost grows linearly with the index size, so on large indexes it can be nearly as expensive as a table scan. It is the correct choice when a large fraction of rows match, when the query needs a full ordered pass for sorting, or when a narrower covering index can answer the query even without a selective predicate. The plan shape is the same (scan operator), but the pages touched differ, so `STATISTICS IO` page counts are needed to tell an index scan from a table scan. A scan operator on a big index with a selective predicate is a tuning target: a better index or a sargable rewrite should convert it to a seek.

21. What is key lookup?
    - **Answer:** A key lookup occurs when the optimizer uses a non-clustered index to find the matching key entries but the index does not contain every column the query needs, so the engine must fetch the remaining columns from the clustered index (or heap). For each matching row in the non-clustered index, a separate random read is issued to the base table using the row locator, so the cost scales with the number of rows returned. This is the classic performance problem: the optimizer chose the narrow index because the seek looked cheap, but the hidden lookup makes the total cost high. The execution plan shows a key lookup operator feeding the remaining predicate and output columns, and `STATISTICS IO` shows a high number of logical reads. The standard fix is to make the index covering by adding the missing columns as INCLUDE columns, converting the lookup to a simple index scan or seek. Alternatively, a selective predicate that reduces the number of matched rows lowers the lookup count. In SQL Server, lookup operators can be nested (clustered index lookup from an index seek), and the same pattern appears in PostgreSQL as an index scan with a bitmap or repeated heap access. The number of lookups, not just their presence, determines whether they matter.

22. What are joins?
    - **Answer:** A join combines rows from two or more tables based on a relationship between their columns, allowing data spread across normalized tables to be assembled into a single result. The join condition typically compares a foreign key in one table to a primary key in another, expressed with the ON clause: `SELECT c.Name, o.OrderId FROM Customers c INNER JOIN Orders o ON c.CustomerId = o.CustomerId;`. Logically there are inner joins (only matching rows), left/right outer joins (preserve one side), full outer joins (preserve both), and cross joins (Cartesian product). Physically, the optimizer implements joins with one of three algorithms chosen by cost: nested loop join, which probes the inner side once per outer row and is best when one side is small; merge join, which requires both inputs sorted and is best for large sorted inputs; and hash join, which builds a hash table on one input and probes it with the other, best for large unsorted inputs. The choice depends on row estimates, existing indexes, and sort availability, so accurate statistics strongly influence join quality. Missing join predicates cause accidental Cartesian products, which the optimizer happily executes as expensive nested loops or hash joins. The result of a join is a virtual table whose columns come from both sides, and the optimizer freely reorders and rewrites joins to find a cheaper plan as long as the result is unchanged.

23. Difference between inner join and left join.
    - **Answer:** An inner join returns only the rows where the join predicate matches on both sides; any row in either table without a match is omitted from the result. A left outer join returns every row from the left table regardless of whether it has a match, filling the right-side columns with NULL when no match exists. The difference is visible immediately in the row counts and in the NULL-filled columns of unmatched left rows. Semantically, inner join answers "which pairs exist," while left join answers "all left rows, plus their matches if any." When the requirement is to find records present on one side but missing on the other, a left join with a `WHERE right_table.key IS NULL` filter is the standard idiom. Using a left join where an inner join suffices changes the result set and can inflate counts when the ON clause produces multiple matches per left row; using an inner join where a left join is needed silently drops rows. In practice, the join type should be driven by the business question: exclusive matching, inclusive reporting from one side, or full comparison of both sides.

24. Difference between left join and right join.
    - **Answer:** A left join preserves every row from the left table and matches against the right, whereas a right join preserves every row from the right table and matches against the left — they are mirror images of each other. `A LEFT JOIN B` is logically equivalent to `B RIGHT JOIN A` with the same ON clause, so a query can always be rewritten between the two by swapping the table order. The difference matters only for readability and convention: most teams standardize on left joins and write the driving table first, because the left-to-right reading order matches how the query is composed. A right join requires the reader to mentally reverse the table order, which becomes error-prone in complex queries with multiple joins and subqueries. Using both in one query makes the join order ambiguous and hard to reason about. The practical guidance is to pick a convention, usually left joins, and rewrite any right joins into their left-join equivalents so every join reads naturally in a single direction.

25. Difference between full join and cross join.
    - **Answer:** A full outer join returns all rows from both tables, matching rows where the join predicate holds and filling the non-matching side with NULLs, so nothing from either side is lost. A cross join returns the Cartesian product of the two tables: every row of the first combined with every row of the second, with no predicate at all, so the result has `m × n` rows. Full join is used for complete comparisons, such as reconciling a source table against a target table to find rows present in either but not both. Cross join is occasionally intentional, such as generating all combinations of a dimension and a measure, but most Cartesian products in production are accidents caused by omitting the ON clause or joining on a non-unique column. An accidental cross join is one of the most destructive bugs possible, because a query expected to return thousands of rows can suddenly produce billions and consume enormous I/O and memory. The optimizer will happily build the huge plan, so the actual execution plan should always be inspected when a query returns far more rows than expected. A full join is expensive by nature because it must track both unmatched sets, and it is worth verifying that it cannot be replaced by two anti-joins or an EXCEPT-based approach.

26. What is normalization?
    - **Answer:** Normalization is the systematic process of organizing a relational schema to reduce data redundancy and eliminate update anomalies by splitting tables into smaller, related tables. Redundancy is bad not just for storage but because it creates the risk of inconsistency: the same fact stored in two places can be updated in one and not the other. Update anomalies come in three forms: insertion anomalies (cannot insert a valid row because it depends on a not-yet-existing row), update anomalies (changing one fact requires changing many rows), and deletion anomalies (deleting a row also deletes unrelated facts it happened to carry). Normalization works by decomposing a table so each fact is stored exactly once, connected to the rest of the data through keys and foreign keys. The process is applied in steps called normal forms (1NF, 2NF, 3NF, BCNF, and beyond), each removing a specific class of dependency. A normalized schema maximizes data integrity and makes constraints expressible, but it spreads related data across many tables, so queries must join more tables. For OLTP systems where correctness is paramount, normalization to at least 3NF is the standard target; the performance cost of joins is then mitigated with indexes. Normalization is a logical design discipline, while denormalization and indexing are physical or practical adjustments layered on top of it.

27. What are normal forms?
    - **Answer:** Normal forms are a sequence of increasingly strict rules for eliminating redundancy and dependency problems from a relational schema. First normal form (1NF) requires that each column hold atomic values and that each row be uniquely identifiable, meaning no repeating groups or arrays of values within a cell. Second normal form (2NF) additionally requires that every non-key column depend on the entire primary key, not just part of it — this only matters for composite keys, and it removes partial dependencies. Third normal form (3NF) further requires that no non-key column depend transitively on another non-key column; every non-key column must depend on the key, the whole key, and nothing but the key. Boyce-Codd normal form (BCNF) is a slightly stronger version of 3NF that also resolves dependencies where the determinant is not a candidate key, a case 3NF misses. The typical practice is to normalize to 3NF or BCNF for transactional tables, because that removes the most damaging update anomalies while remaining practical to query. The normalization steps should be verified per table rather than applied dogmatically, because over-splitting a table that genuinely models a single entity adds join cost without removing real redundancy. Each higher normal form fixes a narrower class of problem, and the trade-off against join complexity and query performance grows with every split.

28. What is denormalization?
    - **Answer:** Denormalization is the deliberate introduction of controlled redundancy into a schema to improve read performance, usually after the schema has been normalized. The most common techniques are storing a column that could be derived (like a precomputed total), duplicating a column across tables to avoid a join, and keeping pre-aggregated summary tables. The gain is that frequent read queries avoid expensive joins and aggregations over large volumes of data; the cost is that the redundant data must be kept consistent, either by application logic, triggers, or scheduled refresh jobs, which makes writes slower and more complex. Denormalization is an optimization decision based on measured workload, not a substitute for normalization, and it should be applied only where a specific slow query is identified. Reporting and analytics systems are the classic targets because they are read-heavy and tolerate slight latency in data freshness; transactional systems are usually kept normalized because write integrity matters more. Designers should be explicit about who owns the truth for each column and how divergence is detected and repaired. A middle path is an indexed view or a separate aggregate table refreshed by the ETL process, which keeps the operational schema clean while serving reads fast.

29. When should you denormalize?
    - **Answer:** Denormalization is justified when read performance is a measured bottleneck, the redundant data is relatively stable, and the consistency risk can be managed. Common triggers are analytical dashboards that repeatedly aggregate millions of rows, joins across many tables in the hot path of a frequent query, and reference values that change rarely but are fetched constantly. Pre-aggregated summary tables are the cleanest form: compute monthly totals once in the ETL and let reports read the small summary instead of scanning the raw fact table every time. Denormalizing volatile transactional data is riskier because keeping several copies synchronized under concurrent writes invites inconsistency, so the write path must be carefully controlled. Another guideline is to denormalize only what the workload actually needs — one copied column or one summary table per proven bottleneck — rather than redesigning the whole schema speculatively. The denormalized structures should also be versioned and reconciled, for example by periodic checks against the normalized source, so drift is caught early. If the normalized source can be kept as the authoritative store and the denormalized copy rebuilt on demand, the design stays safe even as requirements change.

30. What is stored procedure?
    - **Answer:** A stored procedure is a named, pre-compiled collection of SQL statements and control-flow logic stored in the database and executed as a single unit, such as `EXEC sp_GetOrders @CustomerId = 42;`. Procedures can contain multiple statements, conditionals (IF/ELSE), loops, error handling (TRY/CATCH), and can accept input and output parameters, returning result sets, output values, or a status code. They centralize business and data-access logic in the database layer, so the same transformation is executed consistently by every application that calls it. On first execution the optimizer compiles the procedure and caches the plan, so subsequent calls can reuse the plan without recompilation, reducing both parse cost and network round trips — the client sends only the procedure call and parameters, not the whole SQL text. Procedures also provide a security boundary: applications can be granted permission to execute a procedure without direct access to the underlying tables. In practice, procedures are the natural home for ETL steps, complex reporting logic, and multi-statement transactions that must run atomically. Their main drawbacks are that version control, testing, and debugging tooling for database code is weaker than for application code, and that a cached plan can become stale as data distribution changes, a problem addressed with plan recompiles or `OPTION (RECOMPILE)`.

31. Advantages and disadvantages of stored procedures.
    - **Answer:** The advantages are reduced network traffic (only the call and parameters travel between app and database), plan reuse through the plan cache, centralized logic enforced identically across all callers, a security layer that can expose data through procedure permissions alone, and the ability to run multi-statement logic atomically inside a transaction. Disadvantages include harder version control and diffing compared to application code, more limited testability and debugging, tighter coupling between the application and a specific database engine (reducing portability), and a risk of performance surprises: parameter sniffing can lock a procedure onto one bad plan, and logic embedded in the database can be more difficult to review than application-level SQL. Procedures also encourage mixing logic into the database, which some teams prefer to keep in the service layer for portability and testing. The balanced approach is to put set-based, data-intensive operations in procedures where they run efficiently, and to keep business validation and orchestration in application code where it is unit-testable. Procedures should be reviewed like any other code, with schema-bound versioning and change scripts. Using `SET NOCOUNT ON` and avoiding unnecessary dynamic SQL inside procedures keeps their plans stable and efficient.

32. What is function in SQL?
    - **Answer:** A function in SQL is a reusable, deterministic routine that takes parameters and returns a single scalar value or a table, and it is always invoked as part of an expression or query rather than being executed standalone. Scalar functions like `SELECT dbo.FormatDate(OrderDate) FROM Orders;` return one value and can be used in SELECT lists, WHERE clauses, and computed columns. Table-valued functions (TVFs) return a result set and can appear in the FROM clause like a table or view. Inline TVFs are the important performance case: their body is a single SELECT that the optimizer expands inline, so they are optimized exactly like a view and can benefit from indexes on the underlying tables. Multi-statement TVFs, by contrast, build and return a temporary table and carry a fixed row estimate (often a small guess), which can produce poor plans. The critical caution is scalar functions in WHERE clauses: a scalar function applied to a column makes the predicate non-sargable, forcing a scan, and in many engines it also executes row by row, which is why scalar functions are a top cause of slow queries. Functions cannot modify data, which makes them unsuitable for operations with side effects. For shared logic that must stay fast, inline TVFs or computed columns are usually better tools than scalar functions.

33. Difference between stored procedure and function.
    - **Answer:** The essential differences are what they return and what they may do. A function must return a value (scalar or table) and cannot modify database state — no INSERT, UPDATE, DELETE, or DDL — and it is used inside a query as an expression or a table source. A stored procedure may return zero, one, or many result sets, can perform data modification and transaction control, and is executed with `EXEC`, not referenced inside a SELECT. Functions can be used in computed columns, CHECK constraints, and directly inside other queries, which procedures cannot; procedures can return output parameters and status codes, which functions cannot. From a performance standpoint, inline table-valued functions can be expanded and optimized by the query optimizer, while scalar functions tend to be executed per row, and procedures get plan caching and are the right vehicle for batch and transactional work. Functions are therefore the right tool for pure, reusable transformations and lookups, while procedures are right for operations, ETL steps, and complex multi-statement business flows. The optimizer's treatment of the two also differs, so a function that is slow as a scalar routine may be fast as an inline TVF, and procedures are the better place for logic that needs error handling.

34. What is trigger?
    - **Answer:** A trigger is a special type of stored code that runs automatically in response to a DML event (INSERT, UPDATE, DELETE) on a table or view, without the application having to invoke it explicitly. There are AFTER (or FOR) triggers, which run after the DML statement completes and can inspect the affected rows through the inserted and deleted virtual tables, and INSTEAD OF triggers, which replace the operation entirely and are used mainly to enforce complex rules on views. Triggers are useful for auditing changes, maintaining derived or denormalized data, enforcing business rules that cannot be expressed as constraints, and automatically updating "last modified" columns. Their dangers are real: they add hidden work to every DML statement, they execute within the same transaction, so a trigger failure rolls back the whole statement, and they can cascade — a trigger that updates another table fires that table's trigger, producing chains that are hard to trace and easy to turn into locking and performance problems. Triggers also complicate debugging because their behavior is implicit. The guidance is to keep triggers small, set-based, and side-effect-light, and to prefer declarative constraints for rules they can express. During bulk operations, triggers must be examined carefully, since each row batch passes through the trigger once, and large batches mean large inserted/deleted tables.

35. What is view?
    - **Answer:** A view is a saved query that behaves like a table to the user; it has a name, a column set, and can be queried with SELECT, joined to other tables, and secured with permissions, but it stores no data of its own — it is just a definition that expands at query time. Views hide complexity by encapsulating join logic, column lists, and filters, so report writers see a simple named object instead of a 10-table join. They also provide a security and abstraction layer: columns can be exposed or hidden, and row-level restrictions can be embedded in the view's WHERE clause. A view adds no performance penalty or benefit by itself, because the optimizer expands it into the underlying query and optimizes the whole thing — which is exactly the caveat: a view joining many tables looks cheap but runs like the join it contains, so performance problems of the underlying query are simply hidden behind a clean name. Indexed views (materialized) change this by physically storing results, but standard views are pure definitions. Views can also be updated in limited cases (single-table views on key columns), and INSTEAD OF triggers can make complex views updatable. Because views are schema objects, they participate in permissions and can be dropped and replaced without touching application code, making them a common abstraction boundary.

36. What is materialized view?
    - **Answer:** A materialized view physically stores the result of a query, precomputing the expensive joins and aggregations so that reads of the view return from stored data instead of recomputing against the base tables. In SQL Server this is implemented as an indexed view, which requires schemabinding, a unique clustered index, and specific restrictions such as `COUNT_BIG` instead of `COUNT` and no DISTINCT in aggregate expressions. The stored results are maintained by the engine: when base tables change, the view is updated automatically as part of the same transaction (in SQL Server and Oracle), or refreshed on demand (in PostgreSQL and some data warehouses). The payoff is dramatic for repeated aggregation queries over large tables — the query becomes a small index scan instead of a full aggregation — but the maintenance cost lands on every write to the base tables, which is why indexed views suit read-mostly data. The optimizer can also match queries against indexed views automatically even when the query text does not name the view, depending on the engine and settings. Materialized views are effectively a declarative form of denormalization: the engine maintains the redundancy instead of application code. In data warehouse workloads they are often preferred over manually maintained summary tables because they cannot drift out of sync.

37. What is transaction?
    - **Answer:** A transaction is a logical unit of work consisting of one or more database operations that must succeed or fail together, so the database is never left in a partially updated state. The standard control statements are `BEGIN TRANSACTION`, `COMMIT`, and `ROLLBACK`: a commit makes all the changes durable and visible, while a rollback discards them all, restoring the pre-transaction state. Transactions are essential whenever a single business operation spans multiple writes, such as moving money between accounts or inserting an order header plus its line items, where writing only half would corrupt the data. The engine implements this by logging every change to a transaction log and applying locks or row versioning to isolate concurrent transactions. A critical practical rule is to keep transactions short: holding locks for the duration of long transactions (including slow application round trips) increases blocking and deadlock probability, so transactions should cover only the statements that must be atomic. Transactions can also be nested or chained in application frameworks, and their default behavior and isolation can be configured per transaction. Every property of a transaction is summarized by the ACID acronym: atomicity, consistency, isolation, and durability.

38. What are ACID properties?
    - **Answer:** ACID is the set of guarantees a database engine provides for transactions. Atomicity means the transaction is all-or-nothing: if any statement fails, the entire transaction rolls back, and no partial effects survive. Consistency means the transaction transforms the database from one valid state to another, preserving all constraints, keys, and rules — the engine enforces the constraints, while the application is responsible for the business rules. Isolation means concurrent transactions behave as if they ran one after another, not interleaved, with the strength of that guarantee determined by the isolation level: weaker levels allow dirty, non-repeatable, or phantom reads, while stronger levels prevent them at the cost of concurrency. Durability means that once a transaction commits, its changes survive any subsequent crash or power failure, because the commit record is written to a durable transaction log before the transaction is acknowledged. These four properties are what distinguish a relational database from a simple file store and are the reason OLTP systems trust them with money, inventory, and user data. The engine implements ACID with the transaction log, lock manager (or version store), and recovery mechanism, and the tuning question is always where to trade strictness (isolation) against performance. Distributed systems weaken these guarantees deliberately (CAP theorem, eventual consistency), which is why ACID is a selling point for relational databases.

39. What is isolation level?
    - **Answer:** An isolation level is a per-transaction configuration that controls how much of another transaction's uncommitted work is visible, and therefore which anomalies a transaction may experience. The SQL standard defines four levels. READ UNCOMMITTED allows dirty reads: a transaction can see another transaction's uncommitted changes. READ COMMITTED prevents dirty reads but allows non-repeatable and phantom reads, because each statement sees a fresh snapshot. REPEATABLE READ prevents dirty and non-repeatable reads by holding shared locks until the transaction ends, so rows read twice are stable, but new rows can still appear (phantoms). SERIALIZABLE is the strongest level: it holds range locks that also prevent phantoms, effectively serializing concurrent transactions. Databases implement these with either locking or row versioning; for example, SQL Server uses locks for READ COMMITTED and REPEATABLE READ, and a version store for SNAPSHOT isolation, which gives repeatable-read semantics without blocking writers. The choice is a trade-off between consistency and concurrency: the stronger the isolation, the more blocking and the lower the throughput. Practical guidance is to start at READ COMMITTED (the default in most engines), raise the level only for operations that genuinely need stable reads, and use snapshot isolation for long read-only reporting against busy OLTP tables.

40. Difference between read committed and repeatable read.
    - **Answer:** Both prevent dirty reads, but they differ on whether a value read twice within the same transaction can change. Under READ COMMITTED, each statement reads a fresh snapshot of committed data, so another transaction that commits a change between two statements in the same transaction can cause the second read to return a different value — a non-repeatable read. Under REPEATABLE READ, shared locks on the read rows are held until the transaction ends, so rows already read are guaranteed to return the same value on subsequent reads, but new rows matching the predicate can still be inserted by others (phantom reads remain). The practical cost difference is locking scope: READ COMMITTED releases shared locks after each statement, allowing other transactions to update the read rows promptly, while REPEATABLE READ holds those locks for the whole transaction and therefore blocks concurrent writers and increases deadlock risk. REPEATABLE READ is the right choice for operations that must compare two snapshots, such as a reconciliation that reads a baseline, does work, and reads again. For most workloads, READ COMMITTED offers adequate consistency with much better concurrency, and snapshot isolation is a non-blocking alternative when stable reads are needed.

41. What is dirty read?
    - **Answer:** A dirty read occurs when a transaction reads a row that another transaction has modified but not yet committed, meaning the data may later be rolled back. The reading transaction sees data that may never exist in the committed history of the database, and any decisions made from it can be wrong. Dirty reads are possible only at the READ UNCOMMITTED isolation level (or via NOLOCK hints), where reads take no shared locks and ignore locks held by writers. They are also unsafe in a different way: under READ UNCOMMITTED, a reader can read rows while pages are being split during an index update, potentially seeing a row twice or missing it entirely. Most databases default to READ COMMITTED or stronger precisely to prevent dirty reads. NOLOCK hints are sometimes used on reporting queries against busy tables to avoid blocking, but they trade correctness for availability and are unacceptable for anything that feeds counts, totals, or decisions. The safer substitute is snapshot isolation, which gives consistent reads without ever blocking writers. Detecting a dirty read is hard because the wrong value looks plausible; the isolation level is the only reliable guard.

42. What is non-repeatable read?
    - **Answer:** A non-repeatable read happens when, within a single transaction, the same row is read twice and returns different values because another transaction committed an UPDATE (or DELETE) in between. This is possible at the READ COMMITTED isolation level because each statement takes a fresh snapshot of committed data, so the second read reflects changes committed after the first. It is called non-repeatable because re-running the same SELECT does not reproduce the earlier result. The standard prevention is REPEATABLE READ, which holds shared locks on the read rows until the transaction ends so no other transaction can modify them, or snapshot isolation, which presents a consistent version of the data from the transaction start. This anomaly matters when a transaction performs logic across multiple reads and assumes stability, such as reading a balance, computing something, and reading it again. Under locking-based REPEATABLE READ, the cost is that writers to those rows are blocked for the whole transaction, which is why it is applied selectively. Applications that need repeatable reads across multiple statements but cannot afford blocking use snapshot isolation, trading some storage overhead for no reader-writer blocking.

43. What is phantom read?
    - **Answer:** A phantom read occurs when, within a single transaction, two executions of the same query return a different set of rows because another transaction inserted (or deleted) rows that match the query predicate between the two executions. The new rows "appear out of thin air" — they are phantoms. REPEATABLE READ prevents non-repeatable reads by locking the rows that were read, but it does not lock the range, so a concurrent insert into that range still slips through, producing a phantom. Only SERIALIZABLE prevents phantoms, by acquiring range locks (key-range locks in SQL Server) that block inserts into the scanned range, and snapshot isolation also prevents them because it reads from a fixed point-in-time version. Phantoms matter most for aggregate queries: a COUNT or SUM run twice in the same transaction can differ if rows are inserted in between, which can corrupt reconciliations and balance checks. Range locks are expensive and limit concurrency, which is why SERIALIZABLE is rarely the default. In practice, phantoms are the subtle anomaly most teams discover only when a transaction that must be deterministic — like an inventory snapshot or a summary computation — produces different totals on consecutive runs.

44. What is deadlock?
    - **Answer:** A deadlock is a situation where two or more transactions are blocked forever because each holds a lock the other needs and neither will release what it holds. A classic example: transaction A locks table X and waits for table Y, while transaction B locks table Y and waits for table X, so each waits on the other with no path to progress. The database engine detects this cycle (SQL Server does so with a lock monitor thread and deadlock graph; other engines use lock timeouts) and breaks it by choosing a victim — usually the transaction with the lower rollback cost — and rolling it back with error 1205, leaving the other to complete. From the application's perspective a deadlock appears as a random query failure, but the root cause is almost always a design pattern: inconsistent resource-access order, overly long transactions holding locks while doing slow work, or an isolation level that holds more locks than needed. Deadlocks are not always a bug; under high concurrency they are a normal symptom that should be minimized and handled with retry logic. The diagnostics are deadlock graphs (SQL Server Profiler or Extended Events) showing the objects and lock types involved. Fixes include enforcing a consistent object-access order across all transactions, keeping transactions short, using lower or snapshot isolation, and reducing lock footprint through indexing.

45. How do you prevent deadlocks?
    - **Answer:** The most reliable prevention is to make every transaction acquire locks in the same global order — if all code accesses tables in alphabetical or hierarchical order, a lock cycle cannot form because every transaction waits in the same direction. Keeping transactions short reduces the window during which locks are held, which lowers both the chance of collision and the duration of any wait; this means committing as soon as the work is done and avoiding application round trips inside a transaction. Choosing a weaker or non-blocking isolation level such as READ COMMITTED or SNAPSHOT dramatically reduces lock contention, because snapshot isolation uses row versioning and readers never block writers. Correct indexing also helps: a seek that touches a few rows locks far fewer resources than a scan, so a missing index that turns a seek into a scan can be the hidden cause of a deadlock. When deadlocks still occur, the application should retry the victimized transaction, because a single retry succeeds in the vast majority of cases. Deadlock graphs should be captured and analyzed to confirm the pattern and verify the fix actually removed the cycle. Finally, update statements should target rows explicitly and in a consistent order rather than relying on scans.

46. What is locking?
    - **Answer:** Locking is the mechanism a database uses to coordinate concurrent access to data, ensuring that transactions cannot interfere with each other's reads and writes. When a transaction reads or writes a resource, it acquires a lock of the appropriate mode — shared locks for reads, exclusive locks for writes — and the lock manager ensures that incompatible modes are never granted to two transactions at once, forcing the second to wait. Locks exist at multiple granularities: row, key/range, page, and table, and the engine escalates to coarser granularity when the number of fine-grained locks exceeds a threshold, which reduces lock-manager overhead but increases blocking. Exclusive locks block both readers and writers; shared locks block writers but not other readers; update and intent locks coordinate upgrades and escalation. Locking directly implements the isolation level: weaker levels release locks sooner and block less, stronger levels hold them longer. The downside of locking is contention — one slow transaction holding a lock can stall every other transaction that needs the same data. Monitoring views like `sys.dm_tran_locks` reveal who holds what and what is waiting. The design goal is to minimize lock duration and footprint so that concurrency stays high without sacrificing the correctness the isolation level promises.

47. What is row lock?
    - **Answer:** A row lock locks a single row of a table, allowing maximum concurrency because transactions touching different rows never block each other. Row-level locking is the default in most modern databases: an UPDATE or DELETE locks exactly the rows it touches, and a SELECT at a locking isolation level takes shared locks on the rows it reads. The advantage is granularity — under high concurrency, many transactions can work on different rows of the same table simultaneously. The costs are memory (each lock is a lock-manager entry, so many row locks consume memory) and overhead (the engine must track and release many fine-grained locks), which is why the engine escalates to page or table locks when a single transaction locks a large fraction of the table. Row locks are what make OLTP concurrency work, but their effectiveness depends on the access path: if a query scans and locks every row to find the few it needs, it effectively locks most of the table. An index seek that touches only the target rows keeps the lock footprint small. Wait statistics showing row-lock waits indicate either hot rows contended by many transactions or access paths that lock too broadly.

48. What is table lock?
    - **Answer:** A table lock locks the entire table, preventing all conflicting concurrent access to it, whether that means blocking all writers or blocking both readers and writers depending on the lock mode. Exclusive table locks allow nothing else to touch the table; shared table locks allow concurrent readers but block writers. The engine escalates to table locks when a transaction locks a large percentage of a table's rows — lock escalation in SQL Server triggers around 5,000 locks — because managing thousands of individual row locks is more expensive than one table lock. Table locks are also taken directly by DDL statements and by bulk operations like `TRUNCATE` or large `INSERT ... SELECT`. While escalation reduces overhead, it devastates concurrency: a long-running bulk load that escalates to a table lock blocks every other query against that table until it completes, which in production appears as mysterious hangs and timeouts. Prevention techniques include breaking large operations into smaller batches that stay under the escalation threshold, partitioning the table so escalation is scoped to a partition, and, in SQL Server, setting `LOCK_ESCALATION = DISABLE` or `AUTO` with careful monitoring. A table lock is not inherently wrong — full-table reads and batch loads are legitimate uses — but it must be deliberate, not an accidental side effect.

49. What is optimistic locking?
    - **Answer:** Optimistic locking is a concurrency control strategy that assumes conflicts are rare and therefore holds no locks during the transaction; instead it verifies, at commit or update time, that the data has not changed since it was read. The typical implementation adds a version column (rowversion/timestamp in SQL Server, a version integer or a timestamp in others) that is incremented on every update, and the UPDATE includes the original version in the WHERE clause: `UPDATE Orders SET Status = 'Shipped', Version = Version + 1 WHERE OrderId = @id AND Version = @expected;`. If the row was modified concurrently, the version no longer matches, zero rows are updated, and the application detects the conflict and decides how to react — usually by refreshing the data and retrying, or by informing the user. Optimistic locking is ideal for low-contention workloads and long-lived conversations like web forms, because it imposes no locking overhead and never blocks other transactions. The cost is that the conflict is discovered late, after the work is done, and the application must handle the failed update gracefully. It also requires discipline: every write path must maintain the version column consistently, or the protection silently disappears.

50. What is pessimistic locking?
    - **Answer:** Pessimistic locking assumes conflicts are likely and acquires the necessary locks up front, before doing the work, so that no other transaction can modify the data until the operation finishes. The classic technique is locking a row during read so it cannot change before the update: `SELECT * FROM Inventory WHERE SerialId = @id WITH (UPDLOCK)` or `SELECT ... FOR UPDATE` in other engines. This guarantees correctness under high contention, because a transaction that reads the row is guaranteed to be able to update it, and no lost updates can occur. The price is throughput: the locks are held from the read until the transaction ends, so other transactions wait, and the wait time grows with transaction duration, increasing the risk of deadlock and blocking cascades. Pessimistic locking suits critical, low-concurrency sections where correctness outweighs concurrency — for example, allocating a scarce resource or updating a running balance. Choosing between optimistic and pessimistic locking is a workload judgment: pessimistic protects correctness but serializes, while optimistic allows concurrency but relies on retries. Both require transactions to be kept as short as possible to limit their blast radius.

51. What is connection pooling?
    - **Answer:** Connection pooling is a technique in which a set of database connections is created once and reused across many requests, avoiding the high cost of establishing a connection (network handshake, authentication, session setup) on every request. When an application asks for a connection, the pool returns an idle one if available, and when the application is done, the connection returns to the pool instead of being closed. Configuring the pool size is a balance: too small and requests queue waiting for a connection (timeouts), too large and the database spends its resources on idle connections and lock contention, so the size should roughly match the concurrency the database can actually service. HikariCP (Java), pgbouncer (PostgreSQL), and SQL Server's built-in pooling (ADO.NET) are common implementations, and all share the same key parameters: maximum pool size, minimum idle connections, connection timeout, and maximum lifetime. The classic failure mode is connection exhaustion, where the pool maxes out because of a connection leak — code that opens a connection and never closes or disposes it. Connection leak detection and metrics monitoring (active connections, pool wait time) are the standard tools for diagnosing it. A connection in use is not pooled — pooled means idle — so a single application with many threads may need a pool sized to the number of simultaneous database operations.

52. How do you optimize a slow query?
    - **Answer:** The optimization process should follow the evidence rather than guessing. First, capture the actual execution plan and run the query with `SET STATISTICS IO ON` and `SET STATISTICS TIME ON` to get logical reads, scan counts, and elapsed time as a baseline. Then find the most expensive operator in the plan and ask three questions: is it a seek or a scan, are the estimated rows close to the actual rows, and is a missing-index hint present? A scan on a large table with a selective predicate points to a missing index; a large estimated-versus-actual discrepancy points to stale statistics, parameter sniffing, or a poorly modeled predicate. Filtering must also be examined: predicates should be sargable, filters that belong in a WHERE clause (reducing rows before aggregation) should not be in a HAVING clause, and functions on indexed columns should be rewritten as ranges. The query structure itself matters — unnecessary subqueries, functions called per row, and accidental Cartesian products should be removed, and SELECT * should be narrowed to needed columns so covering indexes can serve the query. After a change, the plan and the I/O metrics are re-measured to confirm a real improvement, and the change is checked against the workload as a whole so one query is not optimized at the expense of others. Statistics should be updated and reviewed as part of the process, because a query can be perfectly written and still run badly on wrong statistics.

53. How do you optimize a stored procedure?
    - **Answer:** The procedure should first be profiled as a whole to see where time actually goes: `SET STATISTICS TIME ON`, `SET STATISTICS IO ON`, and capturing the actual plan isolate the most expensive statements inside the body. Each expensive statement is then optimized with the same technique as a standalone slow query — indexing, sargability, join order, statistics — because optimizing statements one by one and re-running the whole procedure is the reliable way to reduce the cumulative cost. Two procedure-specific risks deserve attention. The first is parameter sniffing: the plan cached from the first execution may be poor for later parameter values, detectable when a procedure runs fast with some parameters and slowly with others, and testable with `OPTION (RECOMPILE)` or `OPTION (OPTIMIZE FOR ...)`; the fix is chosen per procedure based on whether parameter distribution is skewed. The second is non-set-based logic: cursors, row-by-row loops, and repeated singleton queries inside procedures should be converted to set-based operations, which are almost always an order of magnitude faster. `SET NOCOUNT ON` reduces network chatter, and explicit transactions should wrap only the statements that need atomicity, kept short to avoid lock escalation and blocking. After changes, the plan cache entry for the procedure should be cleared and the procedure re-executed with the original parameters to verify the improvement is real and consistent.

54. How do you handle large data processing?
    - **Answer:** Large data processing should favor set-based operations over row-by-row processing, because the engine is optimized to operate on whole sets; cursors and per-row loops should be replaced with a single INSERT/UPDATE/SELECT or window-function expression whenever possible. Work should be broken into batches: processing a million rows as 1,000 batches of 1,000 rows keeps transactions short, keeps locks small and escalatable-safe, and lets progress and errors be tracked per batch rather than failing the entire load. Each batch should be filtered by a stable, indexed key such as `WHERE Id BETWEEN @batchStart AND @batchEnd`, or by an IDENTITY/date range, rather than by `TOP` with repeated offsets, which degrades as the scan restarts. Proper indexing on the filter and join columns is prerequisite, and the load should avoid competing with the online workload by running in a maintenance window or against a replica. Logging per-batch row counts and error counts turns a monolithic load into a diagnosable pipeline where a failure at batch 900 restarts only at batch 900. Memory-intensive operations like large sorts and hashes should be watched, and a heap or staging table with `TABLOCK` and minimal logging can speed initial ingestion before the data is indexed and validated. The same principles apply to parallelism: the engine's degree of parallelism should be verified rather than assumed, because skewed data can make parallel plans slower than serial ones.

55. What is pagination in SQL?
    - **Answer:** Pagination splits a large result set into fixed-size pages so applications can display data in chunks instead of transferring everything at once. The standard SQL method is OFFSET/FETCH: `SELECT ... ORDER BY OrderId OFFSET @page * @pageSize ROWS FETCH NEXT @pageSize ROWS ONLY;`, which is supported in SQL Server 2012+, PostgreSQL, and DB2. An ORDER BY is mandatory for pagination to be deterministic — without it the engine may return pages in any order and rows can repeat or vanish across pages. The main drawback of offset pagination is that the engine must scan and discard all skipped rows on every request, so the cost grows with the page number; page 10,000 is as expensive as reading all 10,000 pages of rows, because OFFSET cannot be optimized to "jump" into the middle of an index. Keyset pagination avoids this by using a predicate on the ordering column. Pagination is usually paired with a total-count query (`COUNT(*)`), which itself scans the table unless an index or approximation strategy exists. For deep pages or large datasets, keyset pagination is the performance-correct choice, while offset pagination is fine for shallow pages.

56. Difference between offset pagination and keyset pagination.
    - **Answer:** Offset pagination uses `OFFSET n ROWS FETCH NEXT m ROWS` to skip the first n rows, while keyset pagination uses a WHERE predicate on the ordering column to fetch rows beyond the last row seen: `WHERE OrderId > @lastId ORDER BY OrderId FETCH NEXT 50 ROWS ONLY`. The performance difference is fundamental: offset pagination must read, sort, and discard all n skipped rows on every request, so each page costs O(n) work and deep pages are catastrophically slow; keyset pagination seeks directly to `@lastId` via the index and always reads only one page, so every page costs O(page size) regardless of depth. Offset pagination also drifts if new rows are inserted before the current page, because the same rows appear on multiple pages; keyset pagination is stable because it is anchored to the actual last row. Keyset pagination cannot jump to an arbitrary page number, since there is no OFFSET, so it fits infinite scroll and "load more" patterns rather than numbered page links. It also requires a unique, orderable key (an IDENTITY column or similar) so the tie-breaking is deterministic. The practical rule: use OFFSET for small tables and shallow pages where simplicity matters, and keyset for large datasets, deep navigation, or live tables with frequent inserts.

57. What is query parameterization?
    - **Answer:** Query parameterization replaces literal values in SQL with named placeholders that are bound separately from the statement text, so the database sees the same SQL for every different value. In application code this means `WHERE OrderId = @id` with the value passed as a parameter, via a prepared statement or an ORM, rather than embedding the value directly into the string. The two benefits are security and performance. Security: parameterized queries are immune to SQL injection because the input is never parsed as SQL syntax. Performance: the same parameterized statement can reuse one cached execution plan across all parameter values, avoiding repeated parsing and compilation, which matters for queries executed frequently. Without parameterization, every distinct literal produces a distinct query string and pollutes the plan cache with many near-identical plans. The database can also force parameterization at the database level to rewrite literal queries into parameterized form, though this can prevent the optimizer from using literal-specific cardinality estimates. The caveat is that a single shared plan can be suboptimal for some parameter values — the parameter sniffing problem — which is addressed with RECOMPILE, OPTIMIZE FOR, or plan guides. ORMs and data access libraries parameterize automatically, and developers should avoid constructing SQL by string concatenation.

58. What is SQL injection?
    - **Answer:** SQL injection is an attack in which malicious SQL is inserted into a query through unsanitized user input, changing the meaning of the query the application intended to run. It happens when user input is concatenated directly into SQL text: for input `' OR '1'='1`, the query `SELECT * FROM Users WHERE Name = '` + input + `'` becomes `SELECT * FROM Users WHERE Name = '' OR '1'='1'`, which returns every user. Attackers can extend the technique to dump tables via UNION SELECT, modify or delete data, call stored procedures, and in severe cases gain database-level access, especially if the database account has elevated privileges. The root cause is treating input as code instead of data, and the damage depends on the privileges of the compromised connection and how much the attacker can learn about the schema. Injection is possible not only in SELECT statements but in INSERT, UPDATE, DELETE, and even in dynamic SQL built inside stored procedures. The defense is to never concatenate input into SQL and instead use parameterized queries, prepared statements, or ORM parameter binding, which guarantee input is treated as data. Defense in depth adds least-privilege database accounts, input validation, and removing dangerous stored procedures like xp_cmdshell, but parameterization is the primary and complete defense for this specific vulnerability.

59. How do you prevent SQL injection?
    - **Answer:** The primary defense is parameterization: every user-supplied value is passed as a query parameter (`WHERE Name = @name`) or through an ORM's parameter binding, so the database treats the value as data and it can never alter the statement's structure. This alone eliminates the injection class of attack, because there is no string containing user input that gets parsed as SQL. Beyond parameterization, the defense-in-depth layers are: least-privilege database accounts (application accounts should not be sysadmin or have access to tables they do not need), input validation at the application boundary (type, length, and format checks, which also improve data quality), and never building dynamic SQL — and this includes inside stored procedures, where concatenating input and running it with `EXEC()` is a common but fully vulnerable pattern. Output should also be encoded or treated as data by tools that render it, guarding against stored-XSS that complements the injection. If dynamic SQL is genuinely unavoidable, it should be constructed from a fixed allow-list of identifiers and use parameters for all values. Escaping functions exist but are a weaker, error-prone fallback and should not be relied on as the sole control. Regular scanning of codebases for string-concatenated SQL and periodic penetration testing keep the defense verified.

60. What is ETL?
    - **Answer:** ETL — Extract, Transform, Load — is the process of moving data from source systems into a target database or data warehouse, usually on a schedule, to support reporting and analytics. Extraction reads data from heterogeneous sources such as relational databases, flat files, APIs, and spreadsheets; transformation cleans, validates, standardizes, joins, deduplicates, aggregates, and reshapes the data so it fits the target schema and business rules; loading writes the transformed result into the target. The design separates the three phases so each is independently testable and restartable, and it usually involves a staging area where raw data lands before transformation, which provides recoverability and an audit trail. ETL is the classic architecture for batch data integration, contrasted with ELT (extract, load, transform), where raw data is loaded first and transformed in the warehouse with SQL, which suits cloud-scale warehouses where transformation compute is cheap and cheap to parallelize. The important operational properties are idempotency (re-running the pipeline produces the same result), restartability (a failure resumes from the last good state), and observability (row counts and error counts logged per run). ETL is not just about moving bytes — the transformation stage is where data quality rules are actually enforced, which is why validation belongs to the pipeline and not just to the consumers.

61. What is SSIS?
    - **Answer:** SSIS (SQL Server Integration Services) is Microsoft's ETL platform, part of the SQL Server product family, used to build data integration and workflow solutions. An SSIS package is composed of a control flow and one or more data flows: the control flow orchestrates the package with containers, precedence constraints, and tasks (Execute SQL, File System, Send Mail, For Each Loop), while the data flow moves data from a source through transformations into a destination using an in-memory pipeline. The data flow transformations cover the standard ETL toolkit — lookups against reference tables, conditional splits, derived column computations, data conversions, merge and sort, and error outputs that redirect bad rows to a separate destination instead of failing the whole package. SSIS packages are developed in Visual Studio, deployed to the SSISDB catalog (or the legacy msdb), and executed on a schedule via SQL Server Agent, with built-in logging and package configuration for environments. The typical architecture is a staging area: source files land in staging tables, are validated and transformed, and then loaded into the dimensional reporting tables. SSIS has competition from cloud pipelines and ELT tools, but it remains widely deployed for on-premises SQL Server integration workloads, and its value is the mature tooling for error handling and restartability.

62. What is data validation in ETL?
    - **Answer:** Data validation in ETL is the set of checks that guarantee the data reaching the target is correct, complete, and consistent with the business rules, applied before or during the load rather than discovered later by consumers. Validation layers are typically three: schema validation (columns exist, types match, required fields are present, lengths are within bounds), business-rule validation (codes must exist in reference tables, dates must be plausible, values must fall in allowed ranges), and referential integrity (foreign keys resolve to existing parents). The pipeline design should treat validation as an explicit stage with defined behavior per rule: fail the load, reject and log the offending rows to an error table, or correct the data deterministically. Each failure should be classified and counted so the report on a run is meaningful — for example, how many rows failed format checks versus referential checks — because that tells the data owners where the source quality is breaking down. Validation at the earliest stage is cheapest, because a bad value detected after transformation has already consumed processing and may have propagated into derived data. Edge cases deserve specific attention: NULLs, empty strings versus NULL, leading/trailing whitespace, duplicate keys, and data types that pass the schema check but violate meaning, like a future-dated birth date. The validation stage is also where the target's constraints (unique keys, foreign keys, CHECK constraints) act as a safety net for rules the pipeline missed.

63. How do you handle duplicate records?
    - **Answer:** The first step is to define what a duplicate is for the data at hand, because "duplicate" means a business key collision, not identical rows: for a serial-number table the key might be SerialNumber, while for an order it might be OrderId plus a source system. Duplicates are then detected with a window function that ranks rows within each business key: `SELECT ..., ROW_NUMBER() OVER (PARTITION BY SerialNumber ORDER BY LoadTimestamp DESC) AS rn FROM Staging;`, keeping `rn = 1` as the survivor and sending the rest to a rejection table. The choice of which row survives — earliest, latest, highest source priority, most complete — is a business decision and should be logged so it is auditable. After deciding, the pipeline can either reject the duplicates outright (when the key must be unique, like serial numbers) or merge them (when the same entity was submitted multiple times), and the merge logic must be explicit about which fields win. Both GROUP BY and DISTINCT have their roles: DISTINCT removes fully identical rows, while GROUP BY aggregates the non-key columns of duplicates, and neither alone preserves the "keep one, reject the rest" semantics that ROW_NUMBER provides. The deduplication should run before uniqueness constraints are enforced at load time, so the target's unique index never has to reject a batch. Logging the duplicate counts per key and per source gives the source owners the evidence to fix the root cause at origin.

64. How do you handle missing data?
    - **Answer:** Missing data should be handled explicitly and per column, because the right treatment depends on why the value is missing and how the column is used downstream. The first question is whether the field is truly required: a required field that is missing is a rejection reason, because guessing ownership or identity fabricates data; an optional field can be defaulted. The available strategies are: reject the row to an error table (required data missing), default the value with COALESCE or ISNULL to a business-accepted fallback such as zero, 'N/A', or a date bound, impute a value from other rows when the data distribution justifies it, or leave NULL and let the consumers handle it with IS NULL semantics. NULL must be treated deliberately in queries, because NULL is not equal to anything, including NULL, so comparisons need `IS NULL`, aggregates like SUM and COUNT ignore NULLs, and `COUNT(*)` versus `COUNT(col)` count differently. A NULL in a join column prevents the match silently, which is a common source of "missing" joined rows. Whatever strategy is chosen, it should be recorded — a data dictionary entry saying "NULL means not provided, defaulted to zero" — because downstream analysts cannot guess the rule. Missing data patterns should also be monitored over time, because a growing missing rate usually signals a source-side problem, not a pipeline one.

65. How do you reconcile source and target data?
    - **Answer:** Reconciliation verifies after the load that the target accurately reflects the source, combining row counts, key sets, and value-level checks. The first level is row-count reconciliation: compare the number of source rows to loaded rows, and the discrepancy must match exactly the documented number of rejected or transformed rows. The second level is key-set reconciliation, which finds which keys are missing on either side using set operations: `SELECT ... FROM Source EXCEPT SELECT ... FROM Target` returns rows in the source not in the target, and `INTERSECT` returns the common set. The third level compares values for the common keys by joining on the business key and checking each field, often with a hash of the full row, so a single differing column is detected without writing a comparison per column. Each reconciliation step produces a mismatch count and, when the count is above zero, the mismatching keys, so the pipeline can fail loudly or alert instead of shipping a silently corrupt dataset downstream. Reconciliation should be the last step of the ETL run and automated, with the results stored or emailed so a mismatch is investigated before any downstream report is consumed. The checks must also cover the transformation rules, not just the rows: if deduplication or aggregation is part of the pipeline, the reconciler should verify the aggregate totals against an independent computation. Idempotent pipelines make reconciliation meaningful, because a re-run after fixing a bug produces a verifiably consistent result.
