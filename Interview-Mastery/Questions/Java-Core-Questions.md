## Answers

1. What are the main features of Java?
   - **Answer:** Java is a statically typed, object-oriented programming language designed for portability, security, and robustness. Its defining feature is platform independence: source code compiles to bytecode that runs on any Java Virtual Machine, following the "write once, run anywhere" principle. The language is built around the four pillars of OOP — encapsulation, inheritance, polymorphism, and abstraction — which support modular, maintainable design. Automatic memory management through garbage collection removes the burden of manual allocation and deallocation that exists in languages like C and C++. Java provides strong static typing, which catches many errors at compile time rather than at runtime. It has built-in multithreading and concurrency primitives (`Thread`, `synchronized`, the `java.util.concurrent` package) for writing parallel code. Exception handling with checked and unchecked exceptions gives structured control over error conditions. The extensive standard library covers collections, I/O, networking, and reflection, reducing the need for external dependencies. The JVM enforces security through bytecode verification and a managed runtime that controls access to system resources. Java 8 added lambdas, streams, and functional-style programming, and the language continues to evolve with a six-month release cadence, introducing records, sealed classes, and pattern matching. Java is widely used in enterprise backends via the Spring ecosystem, in Android development, and in large-scale distributed systems, with strong community and vendor support.

2. What is platform independence in Java?
   - **Answer:** Platform independence means a Java program runs on any operating system and hardware combination that provides a JVM, without needing recompilation for each platform. This is achieved because the `javac` compiler translates Java source into platform-neutral bytecode rather than native machine code. The bytecode lives in `.class` files and is executed by the JVM, which is itself platform-specific — each OS ships its own JVM implementation that interprets or compiles the bytecode for that platform's CPU and OS interfaces. The same `.jar` or `.class` artifact therefore runs unchanged on Windows, Linux, macOS, and other architectures, as long as a compatible JVM exists. The JVM abstracts away platform differences such as file systems, memory layout, and hardware instruction sets. True portability still requires discipline: code should avoid platform-specific native calls and must handle differences like file path separators and line endings. The Java standard library normalizes many of these concerns, including consistent Unicode handling across platforms. The cost of this portability is a layer of indirection between the code and the hardware, which can affect raw performance; the Just-In-Time (JIT) compiler mitigates this by compiling hot methods into native code at runtime. Portability also depends on the JVM version: bytecode produced by a newer compiler fails on older JVMs because of incompatible class file versions. This combination of a neutral intermediate format plus a per-platform runtime makes Java a common choice for applications that must be deployed across heterogeneous environments, from developer laptops to cloud containers.

3. What is JVM, JRE, and JDK?
   - **Answer:** The JVM (Java Virtual Machine) is the runtime engine that executes Java bytecode; it loads classes via the classloader subsystem, verifies bytecode for safety, manages runtime memory (stack, heap, method area), and executes code through an interpreter plus a Just-In-Time compiler that translates hot methods into native code. The JRE (Java Runtime Environment) is the package needed to run compiled Java programs: it contains the JVM plus the core class libraries (`java.lang`, `java.util`, `java.io`, and others) and supporting runtime files. The JDK (Java Development Kit) is the full development environment: everything in the JRE plus development tools such as `javac` (compiler), `javap` (bytecode disassembler), `jar`, `javadoc`, and debugging/profiling utilities. The relationship is a containment hierarchy: JDK ⊇ JRE ⊇ JVM. Developers need the JDK to compile source code, while end users only need a JRE to run a compiled application. Since Java 9, Oracle and other vendors stopped shipping a standalone JRE, distributing full JDKs instead, so most deployments simply use a JVM inside a runtime image. The JVM's responsibilities extend beyond execution: it also handles thread scheduling, synchronization, garbage collection, and interaction with native code through the Java Native Interface. The JVM enforces safety by verifying bytecode before it executes, rejecting invalid or type-unsafe instructions. Choosing a JVM implementation (HotSpot, OpenJ9, GraalVM) affects startup time, peak throughput, and memory footprint.

4. What is bytecode?
   - **Answer:** Bytecode is the intermediate, platform-neutral instruction set produced when `javac` compiles Java source code. Each `.java` file is compiled into a `.class` file containing bytecode instructions plus metadata such as a constant pool, field and method signatures, and line-number tables used for debugging. The JVM is a stack-based machine, so bytecode instructions mostly push values onto an operand stack, pop them off, or manipulate local variables and the heap. Because bytecode is platform-neutral, the same `.class` file runs on any JVM regardless of the underlying hardware or operating system. Before execution, the classloader loads the file and the bytecode verifier checks it for type safety and illegal operations, forming a core part of Java's security model. The execution engine starts by interpreting bytecode and then uses the JIT compiler to translate frequently executed methods into optimized native code, giving near-native performance over time. Bytecode can be inspected with tools like `javap -c`, which is useful for understanding compiler transformations such as lambda desugaring and string concatenation. Libraries such as ASM and Byte Buddy can generate or modify bytecode at runtime, which is how frameworks like Spring, Hibernate, and mocking libraries implement proxies and bytecode enhancement. Because generics are erased during compilation, bytecode generally contains no generic type information. Each `.class` file carries a major version number tied to the Java release (for example, 61 for Java 17), which is why bytecode compiled with a newer JDK throws an `UnsupportedClassVersionError` on an older JVM.

5. What is the difference between stack and heap memory?
   - **Answer:** Stack memory is a per-thread, LIFO structure that stores local variables, method arguments, and references to objects; every method invocation pushes a frame onto the stack and the frame is popped when the method returns. Stack allocation is fast and deterministic because memory is reclaimed simply by unwinding frames. Heap memory is a shared pool that stores all objects created with `new`, plus their fields, and is managed by the garbage collector; allocation is slower and reclamation is non-deterministic. Primitive local variables live entirely on the stack, whereas objects always live on the heap even though the references to them sit on the stack. The stack is not shared between threads, giving each thread naturally isolated method-local state; the heap is shared, so concurrent access to the same objects requires synchronization. Each thread has a fixed-size stack, so deep or unbounded recursion produces a `StackOverflowError`. Insufficient heap produces an `OutOfMemoryError: Java heap space`. The heap is divided into generations for garbage collection efficiency — the young generation (Eden plus survivor spaces) and the old generation. The JVM flags `-Xss`, `-Xms`, and `-Xmx` control stack size, initial heap, and maximum heap respectively. Understanding which data lives where matters when tuning memory, diagnosing crashes, and reasoning about thread safety.

6. What is a class?
   - **Answer:** A class is a blueprint or template that defines the structure and behavior of objects, declared with the `class` keyword. It can contain fields (instance variables), static fields, constructors, methods, initializer blocks, and nested types. A class is a user-defined reference type: creating an instance with `new` allocates heap memory and runs the constructor to initialize that instance's state. Classes define an encapsulation boundary — fields are typically private and behavior is exposed through public methods that validate and control state changes. A class can extend exactly one superclass and implement any number of interfaces, participating in inheritance and polymorphism. Classes can also be abstract, meaning they cannot be instantiated and are intended as bases for subclasses. The compiler turns each class into a `.class` bytecode file, which the classloader loads into the JVM's method area when the class is first referenced. Instance fields are stored in each object; static fields belong to the class and exist once in the method area, shared by all instances. The structure of a class determines its instances' memory layout, and good design follows principles like single responsibility and high cohesion. Classes are the primary unit of organization and reuse in Java applications, from small value types to large service components.

7. What is an object?
   - **Answer:** An object is a runtime instance of a class, created with the `new` keyword, and it occupies heap memory that holds its own set of field values. Objects combine state (fields) with behavior (methods), and each instance has distinct state — two objects of the same class can hold completely different data. When `new` runs, the JVM allocates memory, invokes a constructor to initialize fields, and returns a reference to the object, which is stored in a stack variable or inside another object. Objects are always accessed through references; the reference value itself lives on the stack or in other objects, never in the object's own memory. Every object in Java inherits from `java.lang.Object`, which provides foundational methods such as `equals()`, `hashCode()`, `toString()`, `getClass()`, and `clone()`. An object's lifetime is determined by reachability: once no live reference points to it, it becomes eligible for garbage collection and its memory is eventually reclaimed. Objects are the unit of runtime method dispatch, so invoking a method on a reference uses the object's actual runtime type — this is what enables runtime polymorphism. Identity (the reference value) is different from equality (defined by `equals()`), and both matter for collections. Objects are the concrete manifestation of the OOP pillars of state, behavior, and identity, and are what the JVM's heap and garbage collector manage.

8. What are constructors?
   - **Answer:** Constructors are special methods invoked at object creation time to initialize a new object's state. They share the class's name and declare no return type, not even `void`. If a class declares no constructors, the compiler inserts a default no-argument constructor that simply calls the superclass's no-argument constructor. Constructors can be overloaded, providing multiple initialization paths for objects created in different ways. The first statement of a constructor must be either `this(...)` (delegating to a sibling constructor) or `super(...)` (invoking a parent constructor); if neither appears, the compiler inserts `super()` implicitly. If a superclass has no accessible no-argument constructor, subclasses must explicitly call a parameterized super constructor, otherwise compilation fails. Constructors are not inherited, so they cannot be overridden; they also cannot be `abstract`, `static`, or `final`. Access modifiers apply to constructors, so a `private` constructor can enforce a singleton pattern or restrict creation to static factory methods. Constructors ensure objects start in a valid state by forcing callers to supply required values. Records and dependency-injection containers invoke constructors automatically, and constructor injection is generally preferred over field injection because it produces immutable, easily testable dependencies.

9. What is constructor overloading?
   - **Answer:** Constructor overloading means defining multiple constructors in the same class with the same name but different parameter lists — differing in the number, types, or order of parameters. The compiler selects the matching constructor at compile time based on the arguments supplied at the call site. This is a form of compile-time polymorphism and provides flexibility in how an object can be constructed: a full-parameter constructor plus convenience constructors that supply sensible defaults. To avoid code duplication, overloaded constructors usually delegate to one another with `this(...)`, which must be the first statement of the constructor. The return type plays no role because constructors have no return type, so overloads are distinguished purely by their signatures. Overload resolution considers widening conversions, autoboxing, and varargs in later phases, which can occasionally produce surprising or ambiguous selections. Constructor overloading is distinct from the builder pattern: overloading suits a small number of optional parameters, while a builder improves readability when there are many optional fields. It is commonly used for DTOs, entities, and value objects that support multiple construction styles. Overloading also keeps call sites concise and self-documenting.

10. What is method overloading?
   - **Answer:** Method overloading is defining multiple methods in the same class that share a name but have different parameter lists — differing in count, type, or order of parameters. The correct method is chosen at compile time based on the static types of the arguments, so overloading is a form of compile-time polymorphism. The return type alone cannot distinguish overloads; the parameter list must differ, otherwise the compiler reports a duplicate method. Resolution proceeds in phases: exact match first, then widening primitive conversion, then autoboxing, then varargs, picking the most specific applicable method. Overloaded methods can be static or instance and may have different access modifiers and return types. Overloading is commonly used for convenience variants, such as `findById(long id)` and `findById(long id, boolean eager)`, or `add(int)` and `add(int, int)`. It interacts subtly with inheritance and autoboxing, which can lead to ambiguous or unexpected choices when a call matches multiple signatures. Unlike overriding, overloading does not participate in runtime dynamic dispatch; the binding is fixed at compile time. Overloading improves readability by grouping related operations that differ only in arguments under one name. It is a language-level convenience that has no runtime cost.

11. What is method overriding?
   - **Answer:** Method overriding is redefining an inherited method in a subclass to provide a subclass-specific implementation. The overriding method must have the same signature (name and parameter types) as the parent method and a compatible return type — covariant return types are allowed, so a subclass can narrow the return type. The access modifier cannot be more restrictive than the parent's, though it may be widened (for example, `protected` to `public`). Method selection happens at runtime based on the object's actual type, through a mechanism called dynamic dispatch, which is the foundation of runtime polymorphism. The `@Override` annotation is strongly recommended because it causes a compile error if the method does not actually override anything, catching typos and signature mismatches. A method cannot override a `static`, `final`, or `private` method: `static` redeclaration is called method hiding, and `private` methods are not inherited at all. Overriding methods can call the parent implementation using `super.method()`. The overriding method may not declare broader checked exceptions than the parent throws, though it may omit them. Invoking a method on a supertype variable that refers to a subclass instance runs the subclass's version, which is exactly how frameworks like Spring implement proxy-based interception. Correct overriding of `equals()` and `hashCode()` together is essential for objects used in hash-based collections.

12. What is inheritance?
   - **Answer:** Inheritance is an OOP mechanism where a class (the subclass) acquires fields and methods from another class (the superclass) using the `extends` keyword, establishing an "is-a" relationship and enabling code reuse. Java supports single inheritance for classes: a class can extend only one superclass, forming a hierarchy rooted at `java.lang.Object`. A subclass inherits all `public` and `protected` members, plus package-private members if it is in the same package; `private` members are not inherited, though they still occupy memory within the instance. Constructors are not inherited, but every subclass constructor implicitly or explicitly invokes a superclass constructor, ensuring the parent's state is initialized first. Inheritance enables method overriding and runtime polymorphism: code written against the supertype works with any subtype. The superclass constructor always executes before the subclass constructor. Inheritance increases coupling, because changes to a superclass can ripple into subclasses, so it should model a genuine is-a relationship and follow the Liskov substitution principle — a subclass must be usable anywhere its superclass is. Composition (holding references to other objects) is often preferable to inheritance for flexibility and is a common refactoring target. Abstract classes and interfaces complement inheritance: interfaces define contracts and support multiple inheritance of type, while abstract classes provide partial implementations. Java avoids the diamond problem entirely for classes through single inheritance.

13. What is encapsulation?
   - **Answer:** Encapsulation is the OOP principle of bundling data and the methods that operate on that data together while restricting direct external access to the internal state. In Java, it is implemented with access modifiers: fields are typically `private`, and controlled access goes through public getters, setters, or behavior methods. This information hiding ensures the object's state cannot be corrupted from outside, because every mutation passes through validated methods that can enforce invariants — for example, an `Account` class can reject a transfer that would make the balance negative. Encapsulation allows an implementation to change internally (swapping a `HashMap` for a sorted map) without affecting callers, as long as the public API stays stable. Getters for mutable fields should return defensive copies so callers cannot mutate internal collections directly. Encapsulation reduces coupling, because clients depend on the public API rather than internals, and it supports maintainability and testing. It is a foundational principle of layered architectures, where service classes encapsulate persistence details behind behavior-oriented methods. Encapsulation is achieved not just through access modifiers but through deliberate design choices about what to expose and what to hide. Along with inheritance, polymorphism, and abstraction, it is one of the four pillars of OOP.

14. What is abstraction?
   - **Answer:** Abstraction is the OOP principle of exposing only the essential, high-level behavior of an object while hiding the complexity of its implementation. In Java it is expressed primarily through abstract classes and interfaces, which define method signatures as contracts without necessarily providing implementations. Callers program against the abstraction — for example, a `PaymentProcessor` interface — without caring whether the concrete implementation talks to a database, an external API, or an in-memory structure. This decoupling supports the dependency inversion principle, dependency injection, polymorphism, and easy testing with mocks. Abstraction also operates at the method level: a caller cares about what a method does, not how it does it. Good abstractions are stable, focused, and model the "what" rather than the "how," so they survive underlying implementation changes. The concrete details of persistence, networking, and algorithms stay hidden behind the abstraction boundary. Over-abstraction — interfaces with a single trivial implementation added speculatively — adds ceremony without real benefit. Abstraction complements encapsulation: encapsulation hides state, while abstraction hides implementation complexity. It is one of the four pillars of OOP and a key driver of maintainable, extensible systems.

15. What is polymorphism?
   - **Answer:** Polymorphism, meaning "many forms," is the ability of an object to take multiple forms so that the same interface or method call behaves differently depending on the object's actual runtime type. Java provides two kinds: compile-time polymorphism through method overloading, and runtime polymorphism through method overriding. Runtime polymorphism is enabled by inheritance and interfaces: a reference of a supertype or interface type can point to any subtype, and the JVM selects the appropriate overriding method based on the object's actual class at invocation time using dynamic dispatch. This allows code to be written against a general abstraction while concrete behaviors vary — for example, a `Shape` reference invoking `area()` computes the correct result for a circle or a rectangle depending on the actual instance. Polymorphism promotes extensibility because new subtypes can be added without modifying existing code, satisfying the open/closed principle. Frameworks like Spring depend on polymorphism for dependency injection: beans are injected by interface type, and proxy-based interception works through dynamic dispatch. Polymorphism relies on the is-a relationship established by inheritance or interface implementation. Along with encapsulation, inheritance, and abstraction, it is one of the four pillars of OOP.

16. What is the difference between compile-time and runtime polymorphism?
   - **Answer:** Compile-time polymorphism, implemented as method overloading, is resolved by the compiler based on the static types of the arguments; the decision about which method runs is fixed before the program executes. Runtime polymorphism, implemented as method overriding, is resolved by the JVM at runtime based on the actual type of the object, through a mechanism called dynamic dispatch (vtable or method-table lookup). In overloading, the reference type determines which method is called; in overriding, the object type determines it. Overloaded methods may differ in parameter lists, while overridden methods must keep the same signature. Compile-time resolution incurs no runtime lookup overhead because the call is bound statically, whereas runtime dispatch involves a vtable indirection — though modern JIT compilers often inline or devirtualize virtual calls. Overloading is primarily a convenience and readability feature; overriding is what enables polymorphic behavior and substitutability. Both can coexist in one class, which can override an inherited method while also providing overloaded variants. For example, `List.remove(int)` and `List.remove(Object)` are overloads selected by argument type, while `toString()` is overridden and dispatched at runtime. Runtime polymorphism is what makes interface-based frameworks and dependency injection work.

17. What is an interface?
   - **Answer:** An interface is a reference type that defines a contract — a set of method signatures, constants, and, since Java 8, default and static methods — without holding instance state. A class declares that it follows the contract with the `implements` keyword and must provide implementations for all inherited abstract methods unless it is abstract itself. Interfaces support multiple inheritance of type: a class can implement many interfaces, unlike the single-inheritance limit for classes. Since Java 8, interfaces can declare default methods with bodies for backward-compatible API evolution and static methods for utility functions; Java 9 added private methods to share code between default and static methods. All interface fields are implicitly `public static final` constants, and interface methods are implicitly `public`. Interfaces enable programming to abstractions: clients depend on the interface, and any implementation can be substituted, which supports decoupling, testability with mocks, and polymorphism. A functional interface — one with exactly one abstract method — can be implemented with a lambda expression. Common examples include `Comparable`, `Runnable`, `List`, and Spring's `Repository` interfaces. Interfaces define behavior ("what"), while classes provide the state and implementation ("how").

18. What is an abstract class?
   - **Answer:** An abstract class is a class declared with the `abstract` keyword that cannot be instantiated; it may contain abstract methods (signatures without bodies) and concrete methods with full implementations, as well as fields and constructors. Subclasses must implement all inherited abstract methods, or they must also be declared abstract. Abstract classes are used to share common state and behavior among closely related classes while leaving some details to subclasses. Unlike interfaces, abstract classes can have instance fields, constructors (invoked during subclass construction), and members with any access modifier such as `protected`. They support the template method pattern: a concrete method defines the algorithm skeleton and calls abstract methods that subclasses implement. Because of single class inheritance, a subclass can extend only one abstract class, which limits their flexibility relative to interfaces. Abstract classes are a good fit when related classes share substantial implementation and state; interfaces fit when unrelated classes share only a contract. For example, an abstract `ReportGenerator` can provide a final `generate()` template that calls an abstract `buildBody()`. Abstract classes also allow partial implementation, so they are valuable for framework base classes that provide common plumbing.

19. Difference between abstract class and interface.
   - **Answer:** Abstract classes can contain instance fields, constructors, and concrete method implementations, while interfaces traditionally contain only method signatures and constants, though Java 8+ added default, static, and (Java 9+) private methods with bodies. A class can extend only one abstract class but can implement many interfaces, giving interfaces the advantage of multiple inheritance of type. Abstract class members can have any access modifier, whereas interface members are implicitly `public` and interface fields are implicitly `static final`. Abstract classes support shared state and shared implementation, making them suitable for closely related classes in a hierarchy; interfaces define a contract usable across unrelated classes. Abstract classes allow partial implementation and template methods; interfaces define a pure contract and enable polymorphism across diverse types. Java 8's default methods blurred the distinction by letting interfaces carry implementation for backward compatibility, but interfaces still cannot hold instance state or constructors. Design guidance: use abstract classes for internal shared implementation among related classes, and interfaces for public contracts. Records and sealed classes add further modeling options. The choice affects coupling, extensibility, and how the code composes with frameworks like Spring.

20. Can an interface have default methods?
   - **Answer:** Yes — since Java 8, an interface can declare default methods with a body using the `default` keyword. Default methods were introduced primarily for backward compatibility: adding a method to an interface would otherwise break every existing implementer, so the Streams API and collections used default methods (for example, `Collection.stream()` and `Iterator.remove()`) to evolve interfaces without breaking existing code. A default method is inherited by implementing classes unless they override it with their own implementation. If a class implements two interfaces that declare conflicting default methods with the same signature, the class must override the conflicting method or compilation fails, reintroducing a limited form of the diamond problem. An interface can also redeclare an inherited default method as abstract to force implementers to provide it. Default methods cannot access instance fields because interfaces have none, but they can call other interface methods, enabling a lightweight template pattern directly on the contract. A default method can be overridden by a class, and a more specific interface's default takes precedence over a superinterface's. This mechanism allows API owners to add capabilities without source or binary incompatibility.

21. Can an interface have static methods?
   - **Answer:** Yes — since Java 8, interfaces can declare static methods with a body. They are invoked through the interface name, for example `Comparator.comparing(...)` or `List.of(...)`, and cannot be called on instances of implementing classes. Static interface methods are not inherited, so implementing classes cannot access them as instance methods and cannot override them; they are effectively utility methods that belong to the interface's namespace. They behave like static methods in classes except for this inheritance restriction. Java 9 additionally introduced private methods in interfaces, which can be used by default and static methods to share helper logic without exposing it. Static interface methods are commonly used for factory methods and combinators — `Comparator` provides `naturalOrder()`, `comparing()`, and `reversed()` as static helpers. They help group related utility functions near the type they serve, improving discoverability. Like default methods, static interface methods cannot access instance state. They are a convenient way to attach cohesive, type-related utilities directly to the contract rather than to a separate utility class.

22. What is the diamond problem?
   - **Answer:** The diamond problem is an ambiguity that arises in multiple inheritance when a class inherits the same method from two supertypes that provide conflicting implementations. Java avoids it for classes entirely through single inheritance: a class can extend only one superclass, so there is never a conflict between two parent class implementations. However, Java 8 reintroduced a limited version of the problem with default methods: if a class implements two interfaces that both declare a default method with the same signature, the class must override the method or the compiler rejects the code. The class can resolve the conflict by providing its own implementation or by delegating to a specific default using `InterfaceName.super.method()`. If one interface declares the method abstract while the other provides a default, the abstract declaration wins and the class must implement the method. Interface hierarchy also matters: a default method from a more specific subinterface overrides a default from a superinterface. C++ allows true multiple inheritance and faces the diamond problem directly; Java sidesteps it by design, guaranteeing unambiguous method resolution in the JVM. This is one reason interfaces, not multiple class inheritance, are Java's mechanism for sharing contracts across types.

23. What is the difference between `==` and `.equals()`?
   - **Answer:** `==` compares values for primitives and compares references for objects: for two primitives it checks whether the values are equal, while for two object references it checks whether they point to the exact same object in memory. `.equals()` is a method defined on `Object` whose default implementation behaves like `==`, but it is designed to be overridden to compare logical content. Two distinct String objects containing the same text compare equal with `.equals()` but not with `==`. Because String literals are interned, two literals with the same text are the same object, so `==` returns true and can mislead developers into using it incorrectly. Wrapper classes cache values in a limited range — `Integer` caches −128 to 127 — so `Integer a = 100; Integer b = 100; a == b` is true but fails for values outside that range; comparing wrappers with `==` is a classic bug. In practice, `==` is used for primitives and for identity checks such as `obj == null` or comparing enum constants, while `.equals()` is used for content comparison of objects. An overridden `equals()` should be reflexive, symmetric, transitive, and consistent, and must return false when compared to `null`. Overriding `equals()` always requires overriding `hashCode()` consistently, or hash-based collections break.

24. What is the contract between `equals()` and `hashCode()`?
   - **Answer:** The contract states that if two objects are equal according to `equals()`, they MUST return the same value from `hashCode()`. The reverse is not required — unequal objects may legitimately share a hash code. This rule exists because hash-based collections (`HashMap`, `HashSet`, `Hashtable`) use the hash code to pick a bucket and then use `equals()` to distinguish entries within that bucket. If equal objects produce different hash codes, they land in different buckets, breaking lookups, deduplication, and removal: a `HashSet` can contain logical duplicates, and `map.get(key)` can return `null` for a key that was inserted. `hashCode()` must also be consistent — it must return the same value as long as the fields used by `equals()` are unchanged. A good implementation distributes values evenly to reduce collisions; a typical approach multiplies by a prime and accumulates the hash codes of significant fields, or uses `Objects.hash(...)`. IDEs generate both methods together, and Lombok's `@EqualsAndHashCode` automates them. Only stable, non-mutable fields should participate, because a key whose hash changes after insertion becomes unreachable in its bucket. Overriding one method without the other silently breaks collection behavior.

25. What happens if `hashCode()` is not overridden?
   - **Answer:** If `hashCode()` is not overridden, the default `Object` implementation derives the hash code from an identity-based value that is different for distinct objects, even when they are logically equal. Because equal objects then return different hash codes, the `equals()`/`hashCode()` contract is violated and every hash-based collection misbehaves. Two equal objects are placed in different buckets, so a `HashMap` lookup by an equal key fails to find the stored entry, a `HashSet` allows both copies as if they were distinct, and `remove()` cannot find the object to delete. The failure manifests as confusing runtime bugs: `contains()` returns `false` for an element that appears to be in the set, and `map.get(key)` returns `null` even though the key was inserted. Because identity-based hashes can vary across runs, the behavior is non-deterministic and hard to reproduce. The fix is to override both `equals()` and `hashCode()` consistently using the same significant fields. IDE code generation, `Objects.hash(...)`, and Lombok's `@EqualsAndHashCode` reduce the risk of manual errors. Keys in hash-based collections should also be immutable, because a mutable key whose hash changes after insertion becomes permanently lost in its bucket. This is one of the most common correctness bugs in Java and a frequent focus of code review.

26. What is immutable class?
   - **Answer:** An immutable class is a class whose instances cannot be modified after construction — every field's value is fixed for the lifetime of the object. Immutability provides thread safety for free, because a state that never changes can be shared and read concurrently without synchronization. Immutable objects are safe to use as `HashMap` keys, safe to publish across threads, and easy to reason about because they cannot enter inconsistent states. The JDK's `String` and all wrapper classes are immutable, and records provide a concise way to create immutable data carriers. The requirements are: declare the class `final` (or seal it) so it cannot be subclassed; make all fields `private` and `final`; initialize all fields in the constructor; provide no setters or mutating methods; and for mutable field types, store defensive copies of constructor arguments and return defensive copies from getters so internal state can never be leaked through references. The main cost is allocation churn when frequent updates are needed, since every change creates a new object rather than modifying an existing one. Immutable objects also support safe publication under the Java memory model: a properly constructed immutable object is visible in its final state to all threads. Value objects, DTOs, and configuration are natural candidates for immutability. Immutability reduces a whole class of concurrency and aliasing bugs in large systems.

27. How do you create an immutable class?
   - **Answer:** The steps are: (1) declare the class `final` so it cannot be subclassed, because a subclass could override methods or add mutable state; (2) make all fields `private` and `final`; (3) initialize all fields in the constructor; (4) provide only getters and no setters; (5) for mutable field types such as collections and arrays, store defensive copies of constructor parameters and return defensive copies from getters so the internal state cannot be mutated through exposed references; (6) ensure methods cannot be overridden — the `final` class already guarantees this. An example:
     ```java
     public final class ImmutablePoint {
         private final int x;
         private final int y;
         private final List<String> tags;

         public ImmutablePoint(int x, int y, List<String> tags) {
             this.x = x;
             this.y = y;
             this.tags = List.copyOf(tags); // defensive, unmodifiable copy
         }

         public int getX() { return x; }
         public List<String> getTags() { return tags; }
     }
     ```
     Returning the reference is safe here only because `List.copyOf` produces an unmodifiable list; otherwise a copy must be returned. Records (Java 14+) generate this structure automatically for data-carrying types. A subtle risk is serialization: deserialization can create instances without invoking constructors, so an immutable class implementing `Serializable` may need `readResolve()` to preserve its invariants. The builder pattern is a useful alternative when the class has many fields.

28. Why is `String` immutable?
   - **Answer:** String immutability serves several design goals. Security: Strings carry class names, file paths, URLs, database connection strings, and credentials, so a mutable String could be altered by malicious code after a security check, enabling attacks; immutability makes a String's value tamper-proof once created. Caching and pooling: because Strings are immutable, the JVM can safely share literals in the string constant pool, and equal strings can reuse the same object, saving memory. Hash-code caching: String caches its hash code on first computation, and because the value never changes, that cached value is always valid — since Strings are the most common `HashMap` keys, this makes lookups fast. Thread safety: an immutable String can be shared freely across threads without synchronization. Class loading and other JVM metadata rely on Strings whose values must never change while referenced. The `String` class is also `final`, so it cannot be subclassed to add mutable behavior. The trade-off is that concatenation creates new objects, so building strings in loops requires `StringBuilder`. Since Java 7, `substring()` copies the backing array rather than sharing memory with the original, avoiding accidental retention of large strings. These properties make String uniquely safe and efficient as a universal value type.

29. Difference between `String`, `StringBuilder`, and `StringBuffer`.
   - **Answer:** `String` is immutable — every operation that appears to modify it actually produces a new object, so concatenating inside a loop creates many intermediate objects and is inefficient. `StringBuilder` is a mutable character sequence with no synchronization, making it the recommended choice for building strings through concatenation in single-threaded code; it mutates an internal backing array that grows as needed. `StringBuffer` is also mutable but synchronizes its mutating methods, making it thread-safe at the cost of performance; it was the only mutable option before Java 5, when `StringBuilder` was added because the synchronization was rarely needed. The compiler itself rewrites simple string concatenations using `+` into `StringBuilder.append` chains, so small concatenations are already optimized. Strings provide special behavior that the buffers lack, including interning in the constant pool and cached hash codes. `String.format` and `MessageFormat` are alternatives for formatted output. The practical rule: use `String` for fixed or shared values, use `StringBuilder` for loops and dynamic construction in a single thread, and avoid `StringBuffer` unless a legacy API or genuine multi-threaded mutation requires it. Choosing correctly prevents both memory churn and unnecessary synchronization overhead.

30. What is the String constant pool?
   - **Answer:** The string constant pool is a dedicated region of JVM memory that caches String literals so identical literals share a single object, saving memory and enabling fast identity checks. When a literal like `"partner"` appears in code, the JVM looks it up in the pool and reuses the existing instance if one is present. Before Java 7 the pool lived in the method area (PermGen); since Java 7 it resides on the heap, so it is subject to garbage collection and is bounded by heap size rather than the fixed PermGen limit. Strings created with `new String("x")` are not pooled automatically: the literal `"x"` is pooled, but the `new` expression creates a distinct object, so `new String("x") == "x"` is false while `new String("x").equals("x")` is true. The `intern()` method explicitly adds a string to the pool and returns the pooled instance, which can reduce memory when many equal dynamic strings are created — but careless use of `intern()` grows the pool and can cause memory pressure. Constant expressions like `"a" + "b"` are folded to `"ab"` at compile time and pooled. The G1 garbage collector supports String deduplication, letting equal strings share their backing character arrays. Understanding the pool matters when reasoning about `==` comparisons and memory usage in string-heavy applications.

31. What is exception handling?
   - **Answer:** Exception handling is the mechanism Java provides for detecting and recovering from runtime error conditions without crashing the program. Errors are represented by exceptions — objects descended from `Throwable`, whose two main branches are `Exception` (recoverable problems) and `Error` (serious JVM-level problems such as `OutOfMemoryError`). Code that may fail goes inside a `try` block; `catch` blocks handle specific exception types; a `finally` block always executes for cleanup; and try-with-resources (Java 7+) closes `AutoCloseable` resources automatically. When an exception is thrown, the JVM unwinds the call stack looking for a matching handler; if none exists, the thread terminates and the exception is reported. Checked exceptions must be declared or handled at compile time, while unchecked `RuntimeException` subclasses propagate freely. Good practices include catching the narrowest meaningful type, never swallowing exceptions, logging with context, and translating low-level exceptions into meaningful domain or HTTP responses — Spring's `@ControllerAdvice` with `@ExceptionHandler` does this declaratively. Business failures are often modeled as custom exceptions. The `Error` branch indicates JVM-level failures that applications normally should not try to catch. Effective exception handling separates error reporting from normal control flow, making systems more robust and diagnosable.

32. Difference between checked and unchecked exceptions.
   - **Answer:** Checked exceptions are validated by the compiler: a method that can throw one must either handle it with a `try`/`catch` or declare it in its `throws` clause, otherwise compilation fails. They extend `Exception` but not `RuntimeException`, and they are intended for recoverable, foreseeable conditions such as a missing file, malformed input, or a failed network call, where the caller can reasonably react. Unchecked exceptions extend `RuntimeException` and are not verified by the compiler; they can be thrown and propagated without any declaration. They typically represent programming errors or conditions the caller cannot meaningfully recover from — `NullPointerException`, `IllegalArgumentException`, `IndexOutOfBoundsException`. An overriding method may not declare broader checked exceptions than the method it overrides, though it may omit them. In modern frameworks like Spring, unchecked exceptions are preferred because the transaction machinery rolls back automatically on `RuntimeException`, and checked exceptions force `try`/`catch`/`throws` boilerplate through every layer. Many teams standardize on runtime exceptions for domain errors and rely on a global exception handler to map them to HTTP responses. The classic guidance is to use checked exceptions only when the caller is genuinely expected to handle the condition; otherwise use unchecked exceptions.

33. Difference between `throw` and `throws`.
   - **Answer:** `throw` is a statement that actually creates and raises an exception at runtime, for example `throw new IllegalArgumentException("...")`; it is written inside a method body and accepts any `Throwable` instance. `throws` is a clause in a method signature that declares which checked exceptions the method may propagate, for example `public void read() throws IOException`; it tells callers they must handle or further declare those exceptions, and it performs no action itself at runtime. A method body may `throw` zero, one, or many exceptions on different paths, and its signature must declare all the checked ones it can propagate (unchecked ones need not be declared). The two are complementary: `throw` raises an exception, while `throws` advertises that a method is a potential source of checked exceptions. Example:
     ```java
     public void save(Data d) throws IOException {
         if (d == null) throw new IllegalArgumentException("Data required");
         Files.write(Paths.get("out.txt"), d.bytes()); // may throw IOException
     }
     ```
     Exception chaining attaches a cause to a new exception using `initCause` or the `Throwable(cause)` constructor. Declaring an overly broad exception like `throws Exception` hides information and forces callers to handle everything, so signatures should name the specific exceptions. `throws` also appears in overriding rules: overriding methods may not widen the set of declared checked exceptions.

34. Difference between `final`, `finally`, and `finalize`.
   - **Answer:** These three constructs share a prefix but are unrelated. `final` is a keyword that prevents modification: a `final` variable can be assigned only once (making it a constant), a `final` method cannot be overridden, and a `final` class cannot be extended. `finally` is a block used with `try`/`catch` that always executes — whether the try block completes normally, returns, or throws — and is traditionally used for cleanup such as closing resources. If a `finally` block itself throws, it can mask the original exception. `finalize()` is an instance method of `Object`, deprecated since Java 9 and removed in later versions, that the garbage collector used to call before reclaiming an object's memory; it was intended for cleanup but is unreliable because invocation timing is unspecified and GC may never run, so code must never depend on it. Modern alternatives are try-with-resources with `AutoCloseable` and `java.lang.ref.Cleaner` for post-lifetime cleanup. Example:
     ```java
     final int LIMIT = 10;
     try { risky(); } finally { release(); }
     ```
     `final` and `finally` are compile-time and runtime language constructs, while `finalize` was a JVM lifecycle callback. Only `final` and `finally` remain relevant in modern Java.

35. What is try-with-resources?
   - **Answer:** try-with-resources (introduced in Java 7) automatically closes one or more resources declared in the `try` header when the block completes, whether it finishes normally or throws an exception, eliminating the need for a manual `finally` block. It works with any type implementing `AutoCloseable` or its subtype `Closeable`, which includes streams, readers, writers, and JDBC connections. The compiler generates the closing logic, closing resources in the reverse order of their declaration. If both the `try` body and the resource-close operation throw, the close exception is added as a *suppressed* exception on the primary one, retrievable with `Throwable.getSuppressed()`. Example:
     ```java
     try (BufferedReader reader = Files.newBufferedReader(path);
          BufferedWriter writer = Files.newBufferedWriter(out)) {
         writer.write(reader.readLine());
     }
     ```
     This pattern guarantees resources are closed even on early returns and exceptions, preventing file-handle, socket, and connection leaks. Custom resources can participate simply by implementing `AutoCloseable`. Since Java 9, a resource variable that was declared before the `try` can be referenced in the header as long as it is effectively final. try-with-resources is strongly preferred over manual `close()` in `finally` because it cannot be forgotten and it preserves the primary exception.

36. What is a custom exception?
   - **Answer:** A custom exception is a user-defined class extending `Exception` (checked) or `RuntimeException` (unchecked) that represents a specific, named failure condition in a domain, carrying contextual information beyond a generic message. It is created by extending a suitable base class and providing constructors that delegate to `super` with a message and cause, optionally adding custom fields such as an error code. Example:
     ```java
     public class InsufficientBalanceException extends RuntimeException {
         private final String accountId;

         public InsufficientBalanceException(String accountId, double balance) {
             super("Insufficient balance on account " + accountId + ": " + balance);
             this.accountId = accountId;
         }

         public String getAccountId() { return accountId; }
     }
     ```
     Custom exceptions make code more readable and enable precise `catch` blocks, exact logging, and fine-grained mapping to HTTP status codes in a global exception handler. If the exception may be serialized across JVMs or stored, declare a `serialVersionUID`. For domain errors in transactional frameworks, extending `RuntimeException` is usually preferable so that the transaction infrastructure rolls back automatically. A custom exception should add genuine information or behavior beyond a generic exception — creating a new type for every edge case adds ceremony without value. Good design includes a descriptive message and the ability to chain the root cause.

37. What are access modifiers in Java?
   - **Answer:** Access modifiers control the visibility of classes, methods, fields, and constructors. `private` restricts access to the declaring class only; this is the most restrictive and is used to protect internal state. The default (package-private) modifier — no keyword at all — allows access only within the same package. `protected` allows access within the same package plus subclasses in any package. `public` allows access from anywhere and defines the class's external API. These levels implement encapsulation by keeping fields `private` and exposing behavior through controlled `public` methods. Inheritance rules: an overriding method cannot reduce the visibility of the method it overrides — for example, a `public` method cannot be overridden as `private`. Top-level classes can be `public` or package-private only; nested classes and members can use all four levels. Access is checked at compile time, though reflection can bypass it, subject to Java module restrictions since Java 9. A common subtlety is that `protected` members of a superclass are accessible from a subclass only through that subclass's own instances, not through a superclass reference. Choosing the correct access level is part of defining a clean, maintainable API surface.

38. What is static keyword?
   - **Answer:** The `static` keyword indicates that a member belongs to the class itself rather than to any particular instance. Static fields exist once in the JVM's method area and are shared by all instances of the class. Static methods can be invoked without creating an instance and cannot directly access instance fields or methods, because there is no `this`. Static initializer blocks run once when the class is first loaded, useful for one-time setup. Static nested classes are simply nested types without a reference to the enclosing instance. `static` is used for constants (`static final`), utility methods (like those in `Math` and `Collections`), factory methods, and shared configuration. Static methods are not polymorphic: they are bound to the reference type at compile time, so declaring a static method with the same signature in a subclass is method hiding, not overriding, and calling it through a supertype reference invokes the supertype's version. Mutable static state is a common source of concurrency bugs and memory leaks, especially static collections that grow unbounded, so it should be managed with care. Static members initialize in declaration order at class-load time. Because static state belongs to the class, it is naturally application-scoped and survives for the lifetime of the classloader.

39. What is final keyword?
   - **Answer:** `final` prevents modification at several levels. A `final` variable can be assigned only once: for primitives it fixes the value, and for references it fixes which object is referenced (the referenced object itself can still change). A `final` parameter cannot be reassigned inside the method. A blank `final` field — declared without an initializer — must be assigned exactly once, in every constructor or an initializer, giving instance-level constants. A `final` method cannot be overridden by subclasses, locking in its behavior; this can also enable safe initialization and JIT optimizations such as inlining. A `final` class cannot be extended — examples include `String`, the wrapper classes, and record types. `final` fields contribute to thread safety through safe publication: under the Java memory model, an object whose `final` fields are set in its constructor is guaranteed to be fully visible to other threads. Local variables used inside lambdas or anonymous classes must be effectively final. `final` is not a synonym for immutability — a `final` reference to a mutable object still allows mutation through that reference. Combined with `static`, `final` declares constants.

40. What is transient keyword?
   - **Answer:** `transient` marks an instance field to be skipped during default Java serialization, so its value is not written to the byte stream and on deserialization it receives the type's default value (`null`, `0`, `false`). It is used for fields that are derived, cache-like, or should not be persisted for security or size reasons — for example, a password, a live connection, or computed state that can be rebuilt. `transient` affects only the native Java serialization mechanism (`ObjectOutputStream`/`ObjectInputStream`); it has no effect on JSON serialization with Jackson or other serializers, which use their own annotations such as `@JsonIgnore`. For classes implementing `Externalizable`, the class fully controls what is written, so `transient` is irrelevant. When a transient field is needed after deserialization, it must be recomputed in a `readObject()` method. The class's `serialVersionUID` must remain consistent between serialization and deserialization, or an `InvalidClassException` is thrown. Best practice is to mark truly non-serializable or sensitive data as `transient` and never persist credentials. This keyword directly addresses both security and correctness concerns in persistence scenarios.

41. What is volatile keyword?
   - **Answer:** `volatile` is a field modifier that guarantees visibility and ordering of reads and writes to that field across threads. Each read or write of a `volatile` variable operates on main memory rather than a thread's private cache, and the Java memory model establishes a happens-before relationship: a write to a `volatile` field happens-before any subsequent read of it. This prevents threads from seeing stale values, so `volatile` is ideal for flags that signal state changes, such as a shutdown flag checked by worker threads. It does not provide atomicity: compound operations like `count++` involve a read-modify-write cycle and are still racy, so they require `AtomicInteger`, `AtomicLong`, or `synchronized`. The classic double-checked locking pattern uses a `volatile` field for the singleton instance to prevent publication of a partially constructed object. `volatile` has lower overhead than `synchronized` because it does not acquire a monitor or block threads, but it still acts as a memory barrier, preventing some compiler and CPU reorderings at a small performance cost. It fits single-writer, multiple-reader scenarios well. A `volatile` reference only makes the reference itself visible; it does not make the referenced object's fields volatile.

42. What is serialization?
   - **Answer:** Serialization converts an object's state into a byte stream so it can be persisted to storage or transmitted across a network, and deserialization reconstructs an equivalent object from those bytes. Java's native mechanism requires the class to implement `java.io.Serializable`, a marker interface; `ObjectOutputStream.writeObject` writes the object graph (including nested objects and shared references), and `ObjectInputStream.readObject` rebuilds it. `serialVersionUID` is a version fingerprint that must stay consistent: if it changes, deserialization throws `InvalidClassException`, so it should be declared explicitly. Fields marked `transient` are skipped during serialization. Native serialization is a security concern — deserializing untrusted data can enable code execution via gadget chains — so modern guidance is to prefer safe, cross-language formats such as JSON (Jackson, Gson) or binary formats like Protobuf/Avro, or to use `ObjectInputFilter` allowlists. Customization is possible through `writeObject`/`readObject`, `readResolve`, and the `Externalizable` interface. Deserialization does not invoke constructors for `Serializable` classes; state is restored directly, which can bypass constructor invariants. Alternative serializers (Jackson, Protobuf, Avro) map to field or record structures rather than JVM internals and are preferred for integration and security reasons.

43. What is marker interface?
   - **Answer:** A marker interface is an interface with no methods that exists purely to signal to the JVM or a framework that a class has a certain capability. The classic examples are `java.io.Serializable` and `java.lang.Cloneable`: the runtime checks whether an object implements them — `ObjectOutputStream` checks for `Serializable`, and `clone()` checks for `Cloneable` — and throws an exception otherwise. The marker interface pattern is a form of type-level metadata that the JVM can verify with `instanceof`. Its limitation is that it communicates nothing about behavior and cannot be validated: a class can implement `Cloneable` without overriding `clone()` and still fail at runtime. Modern Java largely prefers annotations as a richer marker mechanism, since annotations can carry attributes, specify targets, and be processed reflectively; frameworks like Spring and JPA rely on annotations. The trade-off is that marker interfaces are enforced by the type system and checked with `instanceof`, while annotations are metadata inspected reflectively and are easy to add but also easy to forget. In framework design, annotations have largely replaced marker interfaces. Since Java 8, default methods allow a marker interface to optionally carry behavior too.

44. What is cloning?
   - **Answer:** Cloning creates a copy of an object. The canonical mechanism is `Object.clone()`, a protected native method that performs a shallow copy — it copies the field values, so reference fields still point to the same objects as the original. For `clone()` to be usable, the class must implement the `Cloneable` marker interface; otherwise `clone()` throws `CloneNotSupportedException`. The class should also override `clone()` and widen its visibility to `public`, typically calling `super.clone()` to obtain the shallow copy and then manually deep-copying any mutable fields. A critical subtlety is that `clone()` bypasses constructors — `Object.clone` allocates memory and copies fields directly — so constructor invariants may not hold on the clone. Because of these complications (protected access, the checked exception, shallow semantics, and no constructor invocation), many developers prefer copy constructors or static factory methods (for example, a `copyOf(...)` method) for explicit, safe copying. Serialization can also copy an object by writing and reading it, though that is slow and fragile. Records and immutable objects make copying trivial or unnecessary. For deep copying, explicit recursive copying or a library is used, since `clone()` alone is shallow.

45. What is shallow copy and deep copy?
   - **Answer:** A shallow copy duplicates the top-level object but shares references to any mutable objects it contains, so the copy and the original refer to the same nested objects; mutating a nested object through either reference affects both. A deep copy recursively duplicates all referenced objects, producing a fully independent object graph in which the copy shares nothing mutable with the original. `Object.clone()` produces a shallow copy by default; converting it to a deep copy requires explicitly copying every mutable field. Shallow copies are cheap and are perfectly fine when fields are primitives, immutable, or when sharing is intentional. Deep copies are required when a copy must be fully isolated — for example, editing a draft, taking a snapshot of configuration, or defensively copying state to protect invariants. Deep copying can be implemented manually with recursive copying, via a serialization round-trip, or with libraries, and manual copying is preferred for clarity and performance. For example:
     ```java
     List<String> tags = new ArrayList<>(List.of("a"));
     Record original = new Record(tags);
     Record shallow = new Record(tags);                // shares the list
     Record deep = new Record(new ArrayList<>(tags));  // independent list
     ```
     A copy is equal under `equals()` but is a distinct identity. The cost of a deep copy grows with the size of the object graph.

46. What are wrapper classes?
   - **Answer:** Wrapper classes provide object forms of the eight primitives: `Boolean`, `Byte`, `Character`, `Short`, `Integer`, `Long`, `Float`, and `Double`. They exist because Java generics and collections work only with objects — `List<int>` is illegal, so `List<Integer>` is used — and because primitives cannot be `null` or passed where an object is required. Wrappers are immutable, override `equals()` and `hashCode()`, implement `Comparable`, and provide static utilities such as `Integer.parseInt()`, `Integer.valueOf()`, and `Integer.MAX_VALUE`. The compiler performs autoboxing and unboxing transparently, but boxing outside the cached ranges allocates new objects. The value caches are significant: `Integer`, `Short`, `Long`, `Byte`, `Character`, and `Boolean` cache common values (`Integer` −128 to 127, `Character` 0 to 127, booleans always), so `Integer a = 100; Integer b = 100; a == b` is true but fails at 128 and beyond. Because of this, wrappers should always be compared with `.equals()`, never `==`. Unboxing a `null` wrapper throws a `NullPointerException`. Prefer `OptionalInt`/`OptionalLong`/`OptionalDouble` over `Optional<Integer>` to avoid boxing, and use primitives or primitive streams (`IntStream`) in performance-critical loops.

47. What is autoboxing and unboxing?
   - **Answer:** Autoboxing is the compiler's automatic conversion of a primitive to its wrapper object — for example, `int` to `Integer` — when a wrapper is required; unboxing is the reverse conversion from wrapper to primitive. The compiler inserts the equivalent of `Integer.valueOf(...)` for boxing and `intValue()`/`doubleValue()` for unboxing. For instance, putting an `int` into a `List<Integer>` boxes it, and reading it back unboxes it. `Integer.valueOf` consults the value cache for −128 to 127, so boxed small values may reuse existing instances. The pitfalls matter in practice: unboxing a `null` wrapper throws `NullPointerException`; comparing wrappers with `==` compares references rather than values, which only works inside the cached range; and heavy boxing in loops allocates many temporary objects, hurting performance. Example:
     ```java
     Integer i = 5;       // autobox: Integer.valueOf(5)
     int x = i + 1;       // unbox i, add, then assign int
     i = i + 1;           // unbox, add, and re-box
     ```
     In mixed comparisons such as `wrapper == int`, the wrapper is unboxed. Modern JITs mitigate some of the overhead, but tight loops should use primitives or primitive streams. Autoboxing also affects overload resolution, because boxing is only considered in a later phase of method selection.

48. What are annotations?
   - **Answer:** Annotations are metadata attached to code elements — types, methods, fields, parameters, and so on — that provide structured, machine-readable information to compilers, tools, and frameworks. They are not part of the program's runtime logic but can influence behavior through processing. Built-in annotations include `@Override` (compile-time validation), `@Deprecated`, `@SuppressWarnings`, and `@FunctionalInterface`. Custom annotations are defined with the `@interface` keyword and can have elements (attributes) with default values, a `@Target` restricting where they apply, and a `@Retention` controlling their lifecycle: `SOURCE` (kept only at compile time, like `@Override`), `CLASS` (kept in the `.class` file but not loaded reflectively), or `RUNTIME` (available via reflection). Example:
     ```java
     @Retention(RetentionPolicy.RUNTIME)
     @Target(ElementType.METHOD)
     public @interface Audited {
         String value() default "";
     }
     ```
     Frameworks process `RUNTIME` annotations reflectively — Spring's `@Component`, `@Service`, `@RestController`, `@Transactional`, and `@Cacheable` declaratively drive dependency injection, transaction management, and AOP. Annotations replaced much XML configuration and centralize cross-cutting declarations next to the code they affect. Repeatable annotations and meta-annotations (annotations applied to other annotations, such as `@Component` on `@Service`) add further expressiveness.

49. What is reflection?
   - **Answer:** Reflection is the ability to inspect and manipulate classes, interfaces, fields, methods, and constructors at runtime. It is powered by the `Class` object: `Class.forName("...")` or `obj.getClass()` provides metadata, and APIs like `getMethod()`, `getFields()`, `getDeclaredConstructor()`, `setAccessible()`, and `Method.invoke()` enable dynamic behavior — loading classes by name, invoking methods, and reading or writing private fields. Frameworks rely heavily on it: Spring's dependency injection scans annotated classes and invokes their constructors, JPA/Hibernate maps entities reflectively, serialization libraries introspect objects, and mocking frameworks create dynamic proxies. The trade-offs are real: reflection is slower than direct calls (mitigated by caching metadata and by `MethodHandles`), it sacrifices compile-time type safety because errors surface at runtime, and it can expose internals, which is why the module system (Java 9+) restricts deep reflection on non-open modules. Example:
     ```java
     Class<?> c = Class.forName("com.example.Account");
     Method m = c.getMethod("balance");
     Object result = m.invoke(instance);
     ```
     Reflection should be used sparingly in application code; interfaces, generics, and lambdas are safer alternatives. Modern frameworks prefer `MethodHandles` and `invokedynamic` for better performance.

50. What are generics?
   - **Answer:** Generics allow classes, interfaces, and methods to operate on type parameters, providing compile-time type safety so that casts and runtime type errors are eliminated. For example, `List<String>` can hold only `String` objects: the compiler checks every assignment, and elements are retrieved as `String` without explicit casting. Type parameters like `T`, `E`, `K`, and `V` are placeholders substituted at compile time. Generic classes (such as `ArrayList<E>` and `HashMap<K,V>`), generic interfaces (such as `Comparable<T>` and Spring's `JpaRepository<T, ID>`), and generic methods (`<T> T identity(T t)`) all parameterize types. Wildcards express flexibility: `? extends T` is an upper bound for reading (a "producer"), and `? super T` is a lower bound for writing (a "consumer") — the PECS rule guides their use. Bounded type parameters like `<T extends Number>` restrict what types are allowed. Because of type erasure, generic type information is unavailable at runtime — there is no `instanceof List<String>` — and primitives cannot be type arguments, so wrappers are used. Generics make the Collections framework robust and enable type-safe, reusable APIs, catching many bugs at compile time.

51. What is type erasure?
   - **Answer:** Type erasure is the compiler's removal of generic type information, so at runtime the JVM sees only raw types. `List<String>` and `List<Integer>` both compile to a plain `List`; each type parameter is replaced with its bound, or with `Object` if unbounded. This keeps generics a purely compile-time feature and preserves backward compatibility with pre-generics bytecode, but it means generic type information is unavailable at runtime: `list instanceof List<String>` is a compile error, `new T()` is illegal because `T` is erased to `Object`, and casts involving generics produce unchecked warnings. To keep the code safe, the compiler inserts casts where needed — for example, when reading an element from a raw list it inserts a `checkcast`. When a subclass overrides a generic method, the compiler may generate bridge methods to preserve polymorphism at the raw level. Workarounds for runtime type information include passing a `Class<T>` parameter explicitly or using a `TypeToken`/`Gson`-style approach to capture the generic signature, which is optionally retained in class files. Erasure also affects overloading: two methods differing only in generic parameter types clash. Mixing raw types with generics can cause heap pollution.

52. What is varargs?
   - **Answer:** Varargs (variable-length arguments) let a method accept zero or more arguments of a given type using the `...` syntax in the signature, for example `public static int sum(int... nums)`. Inside the method, the arguments are accessed as an array. The compiler transforms each call into array construction, so `sum(1, 2, 3)` compiles to something like `sum(new int[]{1, 2, 3})`. An array can also be passed directly, since the varargs parameter is an array. The varargs parameter must be the last parameter in the signature, and there can be only one. Calling a varargs method with no arguments passes an empty array, not `null`. A subtle pitfall is heap pollution: a generic varargs method such as `<T> void f(T... ts)` receives an array whose runtime type is `T[]` after erasure, which can hold values of the wrong type and produces a compiler warning. Overload resolution prefers a fixed-arity method over a varargs one. Varargs are common in logging, formatting, and utility methods, but they should be used only when a method genuinely accepts a variable count of homogeneous values; overuse reduces readability.

53. What is enum?
   - **Answer:** An enum is a special class type that defines a fixed, named set of constants, for example `enum Day { MON, TUE, WED }`. Every enum constant is a `static final` instance of the enum class, and enums are full classes: they can have fields, private constructors, methods, and can implement interfaces. Enum constructors run once at class-load time, which guarantees a fixed, ordered set of instances. Enums support `switch` statements, including the enhanced `switch` expression form; iteration with `values()`; lookup by name with `valueOf()` (which throws `IllegalArgumentException` for an unknown name); and `ordinal()` for the declaration index — which should not be relied on for persisted values. `EnumSet` and `EnumMap` are highly optimized collections for enum keys. An enum with a single constant is a robust singleton, because the JVM prevents cloning, ordinary serialization, and reflection-based instantiation of enum instances. Example:
     ```java
     public enum Severity {
         LOW(1), MEDIUM(5), HIGH(10);

         private final int threshold;

         Severity(int threshold) { this.threshold = threshold; }

         public int threshold() { return threshold; }
     }
     ```
     Enums provide type safety that plain integer or string constants cannot, and they can carry behavior, making them the preferred way to model a closed set of values.

54. What is garbage collection?
   - **Answer:** Garbage collection (GC) is Java's automatic memory management: the JVM identifies objects that are no longer reachable and reclaims their memory, freeing developers from manual deallocation as required in C/C++. Reachability is determined by tracing from GC roots — objects still referenced from active thread stacks, static fields, JNI handles, and so on — and any object not reachable from a root is a candidate for collection. The dominant design is generational: most objects die young, so the heap is split into a young generation (Eden plus survivor spaces, collected frequently by minor GCs using copying) and an old generation (collected by major/full GCs using mark-sweep-compact or concurrent algorithms). Common collectors include the Serial collector (single-threaded, small heaps), the Parallel collector (throughput-oriented), G1 (the default since Java 9; region-based with bounded pause times and concurrent marking), and low-pause collectors like ZGC and Shenandoah that aim for sub-millisecond pauses. Tuning balances throughput, pause time, and footprint through flags such as `-Xms`, `-Xmx`, `-XX:NewRatio`, and `-XX:MaxGCPauseMillis`. GC activity is observable via `-verbose:gc`, `-Xlog:gc`, and tools like `jstat`, JFR, and visual profilers. Understanding GC is essential for diagnosing `OutOfMemoryError`, long pauses, and heap sizing in long-running services.

55. What are GC roots?
   - **Answer:** GC roots are the anchor points from which the garbage collector traces object reachability; any object not reachable from a root is garbage and eligible for collection. The main categories of roots are: local variables and arguments in active thread stack frames; static (class) variables; objects held by JNI global and local references; objects referenced by active monitors (locks); live thread objects and system classes; and special references registered with the JVM, such as the finalization queue. A minor GC considers a subset of roots, including references from the old generation into the young generation, tracked via remembered sets. Root scanning contributes to GC pause times because the collector must capture a consistent snapshot of all threads' stacks. In heap dump analysis with tools like Eclipse MAT, the "GC roots" view shows which roots keep a given object alive, which is the starting point for memory-leak diagnosis: an object that is logically dead but still referenced from a static cache appears reachable and therefore leaks. Weak, soft, and phantom references are collected only when the object is reachable solely through such references.

56. What is memory leak in Java?
   - **Answer:** A memory leak in Java occurs when objects are no longer needed by the application but remain reachable from GC roots, so the garbage collector cannot reclaim them and heap usage grows without bound. Unlike leaks in C/C++ (memory that was never freed), Java leaks are logical: the reference graph keeps dead objects alive. Common symptoms are heap usage creeping upward over time, more frequent and longer full GCs, and eventually an `OutOfMemoryError`. Detection involves monitoring the heap with `-Xlog:gc`, JFR, `jstat`, or VisualVM, and capturing heap dumps with `jmap` or `-XX:+HeapDumpOnOutOfMemoryError`, then analyzing them with tools like Eclipse MAT or JProfiler — the dominator tree and GC-root path analysis show what retains memory. Typical sources are unbounded static collections (caches keyed by short-lived objects), `ThreadLocal` values never removed, unclosed streams and connections, listener registrations that are never unregistered, inner classes capturing their outer instance, and long-lived collections accumulating entries. Fixes include bounded caches (`WeakHashMap` or an eviction-based cache like Caffeine), try-with-resources, explicit deregistration, and code review. Leaks are particularly dangerous in long-running server applications where they accumulate over time.

57. How can memory leaks happen in Java?
   - **Answer:** The common mechanisms are: objects kept alive by static collections — a `static` `HashMap` used as a cache that is never cleared or keyed by objects that never die; `ThreadLocal` values not removed, since each thread's `ThreadLocalMap` retains its value for the thread's entire lifetime, which is dangerous in thread pools; unclosed resources such as JDBC connections, sockets, and streams that hold onto native memory or object graphs; unregistered listeners and callbacks that keep strong references to the observer object; non-static inner classes holding an implicit reference to their enclosing instance, so the outer object stays alive as long as the inner does; unbounded caches without eviction; and overuse of `String.intern()` growing the string pool. In every case, objects that are logically dead remain reachable from a root. Preventative patterns include using `WeakHashMap` or a cache library with size/time eviction, always closing resources with try-with-resources, removing `ThreadLocal` entries in a `finally` block, preferring static nested classes where the outer instance is not needed, and unregistering listeners when components are destroyed. Detection starts with heap dumps and reference-path analysis to identify which roots pin the leaked objects. Long-lived containers and thread pools amplify these problems because their lifetime far exceeds that of the leaked data.

58. What are strong, weak, soft, and phantom references?
   - **Answer:** Java defines four reference strengths controlling how aggressively the garbage collector treats an object. A strong reference is the normal one — `Object o = new Object()` — and the object is never collected while any strong reference exists. A `SoftReference` keeps its referent as long as memory pressure is low; it is cleared only when the JVM is close to throwing `OutOfMemoryError`, making it suitable for memory-sensitive caches. A `WeakReference` does not keep its referent alive: the object is collected at the next GC if it is only weakly reachable, and it cannot prevent collection. `WeakHashMap` exploits this so entries vanish when their keys are otherwise unreachable, preventing leaks in canonical mappings. A `PhantomReference` is the weakest kind: `get()` always returns `null`, and the reference is enqueued to a `ReferenceQueue` after the referent is finalized and deemed unreclaimable, enabling post-mortem notification and cleanup without resurrection. `ReferenceQueue` lets code observe when references are enqueued after their referents are collected. Note that accessing a soft- or weak-referenced object can re-strengthen it, which changes GC behavior. Libraries like Guava's cache layer on top of weak and soft references. Choosing the right strength balances memory reclamation against retention policy.

59. What is classloader?
   - **Answer:** The classloader subsystem loads `.class` files into the JVM at runtime, converting bytecode into class representations in the method area, and also performs linking (verification, preparation, resolution) and initialization. The default delegation model is parent-first: when asked to load a class, a loader first delegates to its parent, and only if the parent fails does it try itself — this guarantees that core classes like `java.lang.String` come from the bootstrap loader and are never shadowed. The three built-in loaders are the Bootstrap loader (core JDK modules), the Platform loader (previously called the Extension loader), and the System/Application loader, which loads from the classpath or module path — and for Spring Boot, from the fat JAR's `BOOT-INF/lib`. Custom classloaders enable hot deployment, plugin systems, and per-webapp class isolation (Tomcat gives each webapp its own loader so conflicting library versions do not clash). Class loading is lazy — it happens on first use — which is why `ClassNotFoundException` and `NoClassDefFoundError` surface at runtime, usually from missing dependencies or a wrong loader context. The classloader also participates in type identity: the same class loaded by two different loaders is treated as two distinct types, affecting `instanceof` and casts. Understanding loaders is essential for debugging `ClassNotFoundException`, `NoClassDefFoundError`, and framework weaving issues.

60. What are Java records?
   - **Answer:** Records (previewed in Java 14, finalized in Java 16) are a concise syntax for immutable data carriers. A record declares a name and a component list, and the compiler automatically generates the canonical constructor, accessor methods, `equals()`, `hashCode()`, and `toString()`. Records are implicitly `final`, their fields are `private final`, and they cannot extend any class, though they can implement interfaces. Example:
     ```java
     public record Point(int x, int y) { }

     Point p = new Point(3, 4);
     p.x();   // accessor — not getX()
     ```
     Records can declare a compact constructor for validation and normalization:
     ```java
     public record Range(int from, int to) {
         public Range {
             if (from > to) throw new IllegalArgumentException("from > to");
         }
     }
     ```
     Records are ideal for DTOs, API responses, and value objects where immutability and data-focused behavior matter. Caveats: JPA and other ORM frameworks need no-arg constructors and setters, so records do not map directly to entities; Java serialization of records is supported, but the component names become part of the wire format. Records can override accessors, add static members, or add additional instance methods, but they cannot declare extra instance fields beyond the components. They reduce boilerplate dramatically and encourage immutable, value-based design.
