## Answers

1. What is microservices architecture?
   - **Answer:** Microservices architecture is a software design approach where an application is structured as a collection of small, loosely coupled, independently deployable services. Each service is built around a specific business capability, owns its own data store, and communicates with other services over a network using lightweight protocols such as HTTP/REST, gRPC, or asynchronous messaging. Services can be written in different languages, scaled independently, and deployed on their own release cadence, which decouples teams from a shared monolith release train. The key principles are single responsibility, decentralized data management, and automation-first operations. Compared to a monolith, where every change requires rebuilding and redeploying the whole application, microservices allow a single service to be updated without affecting others. However, this distribution comes at a cost: the system becomes distributed, which introduces network latency, partial failures, and the need for sophisticated service discovery, observability, and deployment tooling. Teams gain organizational alignment because each service can be owned by a small autonomous team. The trade-off is that what was once an in-process function call becomes a remote call that can fail, time out, or return out-of-order data. A well-designed microservices system is a composition of capabilities with well-defined contracts, so the boundaries between services must be chosen carefully to minimize cross-service coupling. This architecture is most beneficial for large, complex systems with multiple teams and high scalability requirements; for smaller applications it often adds overhead without proportional benefit.

2. Difference between monolith and microservices.
   - **Answer:** A monolith is a single application where all features share one codebase, one deployment unit, and usually one database schema, with modules calling each other through in-process method invocations. A microservices architecture decomposes that application into separate processes, each owning its own database and exposing an API. Deployment differs fundamentally: in a monolith, a small change requires rebuilding, testing, and redeploying the entire application, while in microservices each service ships independently. Scalability also differs: a monolith can only scale as a whole unit, whereas microservices scale only the service that is under load, which is more resource-efficient. Technology stack flexibility is another differentiator: a monolith locks the organization into one language and runtime, while each microservice can use the most appropriate technology. Development speed initially favors the monolith because there is no inter-service communication, distributed transaction handling, or network debugging; the cost grows as the codebase and team expand. Microservices shine when the organization has multiple teams that can each own a service end-to-end, reducing merge conflicts and coordination overhead. The biggest costs of microservices are operational complexity, distributed data consistency, and observability — every cross-service interaction can fail in ways a monolith never experiences. For many systems a modular monolith is a sensible middle ground: it keeps deployment simplicity while enforcing clear module boundaries. The choice is not about which is objectively better but about the size, team structure, and scaling needs of the organization.

3. Advantages of microservices.
   - **Answer:** The primary advantage is independent deployability: each service can be built, tested, released, and rolled back on its own cadence, which shortens release cycles and reduces the blast radius of a change. Independent scaling lets resources be allocated only where they are needed — a read-heavy service can run many instances while a write-heavy one stays small, improving cost efficiency. Technology diversity allows each service to pick the best language, framework, and database for its job, such as a time-series store for telemetry and a relational database for transactional data. Fault isolation is a significant benefit: a memory leak or crash in one service degrades only that capability instead of taking the entire application down. Team autonomy follows naturally because ownership of a service end-to-end (code, data, deployment) enables a team to move without waiting on others. Microservices also promote a clear contract-based design, forcing teams to define stable APIs and think explicitly about data ownership and consistency boundaries. Reusability improves because a well-designed service can be consumed by many different clients and even by other teams' features. The architecture supports gradual, partial adoption — legacy features can remain in a monolith while new capabilities are added as services. Faster recovery is possible since a failed service can be redeployed or rolled back in isolation. The payoff only materializes when the operational maturity (CI/CD, monitoring, automation) is in place to handle the added complexity.

4. Disadvantages of microservices.
   - **Answer:** The dominant disadvantage is distributed complexity: every inter-service call introduces network latency, can time out, and can fail in ways an in-process call cannot, so the design must handle partial failures everywhere. Data consistency becomes harder because a business workflow that once ran in a single ACID transaction now spans multiple services, each with its own database, forcing eventual consistency and distributed transaction patterns. Operational overhead grows substantially — many services mean many deployments, containers, log streams, dashboards, and alerting rules, requiring mature CI/CD, observability, and on-call tooling. Debugging and tracing become more difficult because a single user request fans out across multiple services, so correlation IDs, distributed tracing, and centralized logging become mandatory rather than optional. Development complexity rises for simple features that must coordinate multiple services, with orchestration, versioning, and contract management adding to the cost. Resource overhead is higher because each service runs its own process, memory, and infrastructure even if it is small. Testing becomes harder: integration testing across service boundaries requires test doubles, consumer-driven contract tests, and shared environments, all of which add effort. There is also a coordination cost for API changes, schema changes, and feature deprecations, since consumers must be migrated before breaking changes. For small teams or small applications, the infrastructure and operational burden can outweigh the benefits. These disadvantages explain why many organizations start with a monolith or modular monolith and decompose into services only when the pain points justify it.

5. How do services communicate?
   - **Answer:** Services communicate over a network using two broad categories: synchronous request/response protocols and asynchronous messaging. Synchronous communication uses protocols like REST over HTTP/HTTPS, gRPC, or GraphQL, where a client sends a request and blocks waiting for the response; this is intuitive, easy to debug, and well suited to queries and command flows that need an immediate result. Asynchronous communication uses message brokers or event streaming platforms such as Kafka, RabbitMQ, or AWS SQS, where the producer publishes a message and continues immediately while the consumer processes it later; this decouples the producer from the consumer and buffers bursts of load. The two styles can be combined in one system: for example, commands that need acknowledgment use REST, while high-throughput events and background processing flow through a broker. Communication payloads should be versioned and validated through shared contracts, typically defined with OpenAPI, Protobuf, or JSON Schema, so services can evolve without breaking each other. Synchronous chains should be kept shallow because each hop adds latency and failure risk; long request/response flows are better broken into asynchronous steps. Delivery semantics matter: messaging is usually at-least-once, so consumers must be idempotent, while REST can be made retry-safe with idempotency keys. Service-to-service authentication (mTLS, tokens) must be applied so communication is secure even on the internal network. Regardless of protocol choice, every interaction should have timeouts, retries with backoff, and circuit breakers so a slow dependency does not stall the caller. The right choice depends on whether the caller needs an immediate answer, whether the operation is a command or an event, and the required throughput and latency characteristics.

6. REST vs messaging.
   - **Answer:** REST is a synchronous, request/response style where the client sends a request and waits for a reply; it is simple, widely understood, cacheable, and easy to debug, making it ideal for CRUD APIs and query operations where the caller needs an immediate, deterministic answer. Messaging is asynchronous: the producer publishes a message to a broker or topic and moves on, while one or more consumers process it later, so the producer never blocks on the consumer's speed or availability. The key difference is coupling: REST couples the caller to the callee's availability and latency, while messaging decouples them both in time and space, allowing the producer to keep working even if the consumer is down or slow. Messaging naturally absorbs traffic spikes because the broker acts as a buffer, whereas REST requires load shedding and backpressure to survive bursts. Delivery semantics differ — REST can be retried by the client, while messaging is typically at-least-once, requiring idempotent consumers to prevent duplicate side effects. REST is appropriate for low-volume, interactive operations such as fetching a user profile or placing an order, where the response is needed synchronously. Messaging is appropriate for high-throughput, fire-and-forget workloads such as telemetry ingestion, email notifications, and event-driven pipelines, where immediate response is irrelevant. Reliability and ordering: a broker provides durability and partitioning, while REST depends on the server's uptime and the client's retry logic. Many mature systems use both — REST at the edge for interactive clients and messaging internally for decoupled workflows. The decision rule is simple: if the client needs the result now, use REST; if the work can proceed asynchronously, use messaging.

7. What is API gateway?
   - **Answer:** An API gateway is a single, well-known entry point that sits in front of a set of backend services and routes client requests to the appropriate service. It centralizes cross-cutting concerns so they are implemented once instead of in every service: authentication and authorization, rate limiting, request validation, response aggregation, request/response transformation, and TLS termination. A common pattern is the "backend for frontend" (BFF), where separate gateways are tailored to each client type (mobile, web, third party), each aggregating data into the shape that client needs and thereby avoiding chatty, fine-grained round trips. The gateway also hides the internal service topology from clients, so services can be split, merged, or moved without changing client contracts. Beyond routing, gateways enforce security policies — validating JWT tokens, checking scopes, and blocking abusive clients — making them the natural place for a WAF and rate limiting. The gateway can also implement resilience patterns such as timeouts, retries, and circuit breaking against backend services, protecting clients from downstream failures. Two routing styles exist: proxy routing passes the request unchanged to one service, while aggregation fetches from multiple services and combines the responses. The main trade-off is that the gateway is a critical infrastructure component and a potential bottleneck and single point of failure, so it must be stateless, horizontally scalable, and deployed redundantly. It must not become a dumping ground for business logic, or it risks becoming a distributed monolith. A gateway is most valuable when there are many clients and services; with few services and one client, it may be unnecessary overhead.

8. What is service discovery?
   - **Answer:** Service discovery is the mechanism by which a service locates the network address of another service at runtime, instead of relying on hardcoded URLs or configuration that breaks when instances come and go. It is essential in dynamic environments where instances scale up and down, fail, or are redeployed, so their IP addresses and ports change frequently. There are two main patterns: client-side discovery and server-side discovery. In client-side discovery, the client queries a service registry (such as Eureka or Consul), gets the list of available instances, and picks one using a load-balancing algorithm, so the registry is a direct dependency of every caller. In server-side discovery, the client calls a well-known address such as a load balancer or Kubernetes Service, and that component queries the registry and routes the request to a healthy instance, which keeps the discovery logic out of the client. The service registry is populated by instances registering themselves on startup (self-registration) or by a third-party registrar that detects and registers instances (such as registrator or the Kubernetes controller). To stay accurate, the registry relies on heartbeats: instances send periodic lease renewals, and the registry evicts instances that stop sending them. Modern platforms like Kubernetes implement discovery natively with DNS and the Service abstraction, where a stable DNS name resolves to a virtual IP that load balances across pods, making discovery largely automatic. Health checking is an integral part of discovery, because a registry that routes traffic to dead instances is worse than no registry at all. Service discovery must itself be highly available and replicated, since it is a critical path for every inter-service call. Choosing between the patterns depends on platform capabilities: in a Kubernetes world, server-side discovery via Services is the default; on bare infrastructure, a registry like Consul with client-side discovery is common.

9. What is circuit breaker?
   - **Answer:** The circuit breaker pattern prevents cascading failures by failing fast when a downstream service is unhealthy, instead of letting every caller wait on timeouts and exhaust resources. It works like an electrical circuit breaker with three states. In the closed state, calls pass through normally; the breaker tracks the failure rate over a rolling window. When the failure rate crosses a configured threshold, the breaker opens and rejects all calls immediately, typically returning a fallback value, a cached response, or a clear error without touching the failing service. This protects the failing service from further load and, crucially, protects the caller's resources from being consumed by calls that are doomed to fail. After a cooldown period, the breaker transitions to the half-open state, where it allows a small, probe number of trial calls through; if those succeed, the breaker closes and traffic resumes, and if they fail, it reopens. The half-open state is what enables automatic recovery without manual intervention. The pattern should be combined with timeouts — the circuit breaker measures actual failures and timeouts, so a fast-failing call counts as a failure while a hang does not. Implementing circuit breakers is common in service frameworks such as Resilience4j in the JVM ecosystem and Hystrix historically, and at the network layer in service meshes like Istio and Linkerd. Configuration matters: the failure rate threshold, the window size, and the cooldown must be tuned per dependency because a dependency that is intermittently slow behaves differently from one that is fully down. The pattern gives the system graceful degradation: non-critical features fail fast with a fallback while critical features continue working.

10. What is retry pattern?
    - **Answer:** The retry pattern automatically re-attempts a failed operation when the failure is likely to be transient, such as a network blip, a momentarily busy database, or a connection reset. The simplest form retries a fixed number of times, but a robust implementation uses exponential backoff: the delay between attempts doubles each time (for example, 100 ms, 200 ms, 400 ms) so that a recovering dependency is not hammered by retries. Adding jitter (a small random component to the delay) prevents the "thundering herd" problem where many clients retry at the same instant and re-overload the dependency. Retries are only effective if the failure is idempotent-safe; a retried write must not create duplicates, which is why retrying is coupled with idempotency keys or an idempotent operation such as a PUT. The number of attempts and the total time budget must be bounded so a pathological dependency does not tie up threads for too long. It is also important to distinguish which errors are retryable — connection refused, timeouts, and 5xx errors are typically retryable, while 4xx client errors (except 429) are not and should fail immediately. The retry pattern is frequently combined with the circuit breaker: retry handles short-lived transient failures, while the circuit breaker stops the stream of attempts when the dependency is persistently failing. Retrying inside a queue consumer is different: a failed message can be delivered again through a dead-letter queue with exponential retry tiers rather than a synchronous loop. In a distributed system, retries must respect the request's overall deadline so that multiple layers of retry do not multiply each other's delays. Used correctly, retries dramatically improve perceived reliability; used without bound, they amplify load and can take down a struggling service.

11. What is timeout?
    - **Answer:** A timeout is a maximum duration a caller is willing to wait for an operation to complete; when exceeded, the call is aborted so resources are not held indefinitely. Timeouts are the fundamental defense against a slow or hung dependency, because without them a single unresponsive service can accumulate threads, connections, and memory until the caller itself fails. There are several distinct types: connection timeout bounds how long establishing a connection may take; read timeout bounds how long the caller waits between bytes of a response; and write timeout bounds how long sending data may take. Different layers need their own timeouts — the HTTP client, the database driver, the messaging producer, and the network stack each have defaults that should be reviewed and set explicitly. Timeout values must be chosen carefully: too short causes false failures on legitimate slow operations, and too long keeps resources tied up when the dependency is gone. A common pattern is a deadline at the edge: the total budget for a request is set at the entry point, and each nested call gets a portion of that budget, preventing a chain of services from each adding its own generous timeout. Timeouts should also be combined with circuit breakers and retries: the timeout bounds a single attempt, the retry gives a few bounded attempts, and the circuit breaker stops all attempts once the dependency is confirmed failing. The client should also register a fallback or error path so the user receives a fast, clear failure instead of a hang. Modern libraries such as Java's HttpClient, Spring's WebClient, and gRPC deadlines all provide first-class timeout support. Observability of timeouts matters, because a high timeout rate is an early signal of a degrading dependency.

12. What is bulkhead pattern?
    - **Answer:** The bulkhead pattern isolates the resources of different consumers or subsystems so that a failure or slowdown in one cannot deplete resources needed by others, borrowing its name from the compartments in a ship's hull. The classic implementation is thread pool isolation: each dependency or service gets its own pool of threads with a bounded size, so if one dependency saturates its pool, only the calls to that dependency are affected and other dependencies keep their capacity. Without bulkheads, a shared thread pool can be exhausted by slow calls to one backend, and then every request to every backend fails even though the other backends are healthy. The pattern is applied to other resources as well: connection pools, message queues, database connections, and even memory can be partitioned per consumer or per dependency. A related implementation is semaphore isolation, where instead of a dedicated thread pool a shared pool is used but the number of concurrent calls per dependency is capped with a semaphore; this has lower overhead but less isolation. Bulkheads also apply to infrastructure design: separate message queues or database instances for critical and non-critical paths ensure that a flood of non-critical work does not starve critical work. The trade-off is that partitioning resources by dependency reduces overall resource utilization because each pool must be sized for its own peak, leaving headroom idle. Pool sizes must be tuned based on the expected concurrency, latency, and throughput of each dependency. This pattern is a core resilience technique in libraries like Resilience4j and is often combined with timeouts, retries, and circuit breakers. It is particularly valuable when a system has a mix of critical and non-critical workloads, because it guarantees that a degradation in one area degrades only that area.

13. What is rate limiting?
    - **Answer:** Rate limiting controls how many requests a client, user, or source can make within a time window, protecting backend resources from overload, abuse, and cascading failure. Common algorithms include the fixed window counter, sliding window log, sliding window counter, token bucket, and leaky bucket. The token bucket algorithm is popular: a bucket holds a number of tokens, each request consumes one token, tokens are replenished at a fixed rate, and requests that find an empty bucket are rejected or queued — this allows short bursts up to the bucket capacity while capping the sustained rate. The sliding window counter combines the memory efficiency of a counter with the smoothness of a sliding window by weighting counts from the current and previous windows. Rate limiting can be enforced at different layers: at the API gateway or edge proxy for all traffic, inside individual services, or within a single function for a hot code path. In distributed systems the counter must be shared across instances, typically stored in a fast in-memory data store like Redis with a TTL, which introduces considerations of atomicity and accuracy. Limits are usually applied per client identity (API key, IP address, authenticated user) and may be tiered — free tier, standard, premium — each with its own quota. When a limit is exceeded, the standard response is HTTP 429 Too Many Requests, ideally with Retry-After header and rate-limit headers so clients can self-throttle. Rate limiting also protects downstream systems, because a gateway can cap the aggregate traffic forwarded to a fragile backend. It is a fundamental component of any public API, and it also prevents accidental spikes and slow-leak DoS attacks.

14. What is load balancing?
    - **Answer:** Load balancing distributes incoming traffic across a group of backend instances so that no single instance is overwhelmed, while also providing high availability by routing around failures. A load balancer sits in front of the backend pool, exposes a stable virtual IP or DNS name, and forwards each request to one healthy instance according to a scheduling algorithm. Common algorithms are round-robin (sequential distribution), weighted round-robin (proportional to instance capacity), least-connections (prefer the instance with fewest active connections), and consistent hashing (route a given key to the same instance, useful for session affinity or caching). Critical to correctness is health checking: the load balancer periodically probes each instance with a health endpoint, and instances that fail are removed from rotation while instances that recover are re-added automatically. Load balancing works at several layers: L4 balancing operates on TCP/UDP connections, while L7 balancing operates on HTTP, allowing path-based or header-based routing, URL rewriting, and request/response inspection. In cloud and Kubernetes environments, load balancing is largely platform-managed — an AWS ALB, a Kubernetes Service with a load balancer, or an ingress controller routes traffic to pods. Horizontal scaling relies on the load balancer: instances are added and removed dynamically, and the balancer redistributes traffic without downtime. For stateful workloads, sticky sessions (session affinity) pin a client to a consistent instance, though stateless designs that keep session data in a shared store like Redis are generally preferred. Load balancers are themselves a single point of failure and must run in a redundant, active-active or active-passive configuration. Effective use of load balancing also requires that instances be designed to be horizontally scalable and not hold critical state locally.

15. What is distributed tracing?
    - **Answer:** Distributed tracing is a technique for observing a single request or workflow as it travels across multiple services, reconstructing the complete path, timing, and failure points. It is built on a standard data model: every request gets a globally unique trace ID, and each unit of work within a service (such as handling an incoming request or calling a downstream service) is represented as a span with its own span ID, parent span ID, start time, duration, and tags. The trace ID is propagated end-to-end through headers — for HTTP via standard headers like W3C Trace-Context, and through message headers in Kafka and other brokers — so that every service along the path contributes spans to the same trace. Spans are emitted by instrumented frameworks (Spring Cloud Sleuth or Micrometer Tracing in the JVM world, OpenTelemetry SDKs generally) and shipped to a tracing backend such as Jaeger, Zipkin, or Tempo, which stores them and correlates them by trace ID. A trace view shows a waterfall diagram: the overall latency at the top, then each service's contribution, making it obvious where time is spent and which service is the bottleneck. Distributed tracing is essential for debugging latency and failures in microservices because a single user action can fan out to dozens of services, and logs alone cannot show the causal chain. Traces also power critical-path analysis, service dependency graphs, and capacity planning. Sampling is necessary because recording every span is expensive; common strategies record 100% for a small percentage of requests or 100% of requests that are slow or errored. Tracing works best when combined with logging and metrics: the trace ID should also be recorded in logs so logs and traces can be cross-referenced, forming the third pillar of observability.

16. What is centralized logging?
    - **Answer:** Centralized logging aggregates log output from all services and instances into a single, searchable platform so that engineers can inspect any part of the system from one place instead of SSHing into individual servers. In a distributed system, logs are scattered across thousands of containers and instances; when something goes wrong, the relevant entries are spread across multiple sources and must be correlated by request or by time. The typical pipeline is: applications emit logs to stdout or a local agent, a shipper (Fluentd, Fluent Bit, Filebeat) collects them, a broker buffers them (Kafka), and a search and analytics engine (Elasticsearch, Loki, or a managed service like CloudWatch Logs) stores them with a UI (Kibana, Grafana) for querying and alerting. Structured logging is a key practice: emitting logs as JSON with well-defined fields (timestamp, level, service, instance, trace ID, message) instead of free-form text makes them machine-parseable, filterable, and aggregatable. Log levels (DEBUG, INFO, WARN, ERROR) should be used consistently, with ERROR reserved for actionable problems and sensitive data never logged. Correlation is what makes centralized logging powerful: when every service logs the trace or correlation ID from the incoming request, a single search groups all log entries for one user action across all services. Retention and cost management matter because high-volume systems generate enormous log data, so hot storage for recent logs, cold archival for compliance, and sampling for DEBUG logs are standard. Centralized logging enables alerting on error patterns, like a spike in a specific exception. It is a prerequisite for effective debugging, on-call response, and audit compliance in any distributed architecture.

17. What is correlation id?
    - **Answer:** A correlation ID is a unique identifier assigned to a request or workflow at its entry point and propagated through every service, message, and database call it touches, so that all related log entries can be linked together. Its purpose is to answer the question "which pieces of this distributed workflow belong together?" When a user action fans out across several services, each service writes its own logs with its own context, and without a shared key those entries cannot be reassembled. The ID is typically a UUID generated once, attached as an HTTP header (such as X-Request-ID) for sync calls, carried in message headers for async flows, and echoed into every log line by the logging framework. It should also be passed to downstream external calls and returned to the client so that a support ticket can reference a single ID that maps to the full server-side trace. In practice, tracing tools build on this idea: the correlation (trace) ID is combined with per-hop span IDs to produce a hierarchical view, but even without a full tracing stack, correlation IDs in logs give a linear, chronological reconstruction of one flow. The implementation is largely mechanical — a filter or interceptor generates or reads the header at the edge, stores it in thread-local or context-local storage, and the logging framework appends it automatically. A good correlation ID strategy also covers async paths: Kafka consumers should read the ID from the message header and propagate it into subsequent operations and outbound calls. Without correlation IDs, debugging in a distributed system means manually stitching together timestamps and hoping for the best. The pattern is cheap to implement and returns disproportionate value in debugging and support.

18. What is eventual consistency?
    - **Answer:** Eventual consistency is a consistency model where, after a write, replicas or dependent services are allowed to hold temporarily divergent views of the data, with the guarantee that they will converge to the same value once writes stop and sufficient time passes. It is the model that distributed systems converge on because the CAP theorem states that in the presence of a network partition, a system must choose between availability and strong consistency, and most large-scale systems choose availability. Strong consistency requires coordinating replicas before returning, which adds latency and reduces availability during partitions; eventual consistency trades a short window of stale reads for better performance and availability. It arises naturally in microservices because each service owns its own database, so a business entity may be duplicated across services (an order in the order service and a denormalized copy in the analytics service), updated through events with inherent propagation delay. Designers must make this latency explicit: document the maximum staleness (e.g., data reflects state within seconds), and design APIs and UX so consumers know they might read slightly stale data. Because duplicates and reorderings are possible in the asynchronous pipeline, the system must be built for idempotency — applying the same update twice should not corrupt state. Practical techniques include versioning events, last-write-wins timestamps, and reconciliation jobs that periodically fix drift. Eventual consistency should not be used where strong guarantees are legally or financially required, such as money transfer debits, without compensating safeguards. The model is a deliberate trade-off: the developer gives up immediate read-your-writes semantics within a bounded window, and in exchange gets a system that keeps serving during failures and scales horizontally.

19. What is distributed transaction?
    - **Answer:** A distributed transaction is a business operation that spans multiple services or databases, where all participants must commit or all must roll back to preserve data integrity. In a monolith with one database, an ACID transaction handles this atomically with BEGIN/COMMIT/ROLLBACK. When the operation spans services, each owning a separate database, there is no single transaction manager, so atomicity must be achieved across the network. The classic mechanism is two-phase commit (2PC): a coordinator asks all participants to prepare (phase 1); each participant locks its resources and votes; if all vote yes, the coordinator tells them all to commit, otherwise all abort. 2PC provides atomicity but has serious drawbacks in distributed systems: it holds locks and resources during the entire prepare phase (high latency), it reduces availability because a single unresponsive participant blocks the whole transaction, and if the coordinator fails during the window between prepare and commit, participants can be left uncertain — blocked between commit and abort. Because of these problems, modern distributed systems mostly avoid 2PC and replace global atomicity with the saga pattern or with a careful application of eventual consistency. The practical approach is to shrink the atomicity boundary: keep related data in one database or one service where a single ACID transaction is possible, and treat cross-service steps as compensatable local transactions. Distributed transactions are a design smell in microservices — they signal that the service boundary may be in the wrong place. When cross-service atomicity is truly unavoidable, sagas and idempotent, compensating operations are the standard solution.

20. What is saga pattern?
    - **Answer:** A saga is a sequence of local transactions, one per participating service, that together accomplish a distributed business operation without a global ACID transaction. Each step in the saga commits its own local transaction and publishes an event or message to trigger the next step; if a step fails, the saga executes compensating transactions in reverse order to undo the effects of the already-completed steps. For example, a travel booking saga might reserve a flight, reserve a hotel, and charge a card; if the hotel booking fails, the saga cancels the flight reservation and reverses the payment. Compensation must be business-meaningful: canceling a reservation is not the same as a database rollback, and it may be asynchronous or even require manual intervention if the compensation fails. There are two coordination styles. Choreography uses events: each service reacts to events and publishes the next event, with no central controller, so the flow is decentralized and the services are loosely coupled, but the flow is implicit and hard to monitor. Orchestration uses a central coordinator (a state machine or workflow engine such as Temporal, Cadence, or a custom orchestrator) that tells each service what to do and manages the saga state and compensations, making the flow explicit and observable but introducing a coordination component. Sagas work with at-least-once messaging, so each step must be idempotent to survive duplicate or reordered events. The saga pattern accepts eventual consistency: intermediate states of the business operation are visible to the outside world until the saga completes. It is the standard modern answer to distributed transactions and the recommended pattern whenever a workflow spans multiple services.

21. What is CQRS?
    - **Answer:** CQRS (Command Query Responsibility Segregation) is a pattern that separates the model and infrastructure used to read data from those used to write data, instead of using one model for both. A command represents an intent to change state and is written in imperative form ("increase stock by 5"); a query is a read that returns data without side effects. The two paths can use completely different storage technologies — a normalized relational database optimized for writes on the write side, and a read-optimized store such as a denormalized table, a search index, or a cache on the read side. This makes sense when read and write workloads are asymmetric, such as a system with high-frequency writes and complex, aggregation-heavy reads. The read model is typically kept in sync with the write model asynchronously: writes are published as events, and a projection component updates the read model, which means read data is eventually consistent with written data. CQRS also naturally combines with event sourcing, where the write side stores the sequence of events rather than current state, and the read models are projections of those events. Benefits include independent scaling (the read side can have many replicas, the write side fewer), independent optimization of each side's schema and index strategy, and simpler write logic because writes no longer need to answer arbitrary queries. Costs include increased complexity, eventual consistency visible to consumers, and duplicate data that must be synchronized. CQRS is not appropriate for simple CRUD systems where read and write models are similar; it pays off when reads and writes are genuinely divergent. In microservices, CQRS is often used per-service, with a service's command API and query API backed by different stores.

22. What is event-driven architecture?
    - **Answer:** Event-driven architecture is a style where the components of a system communicate by producing and consuming events, which are records of something that happened ("order placed", "temperature exceeded threshold"), rather than by sending imperative commands that demand a specific action. Producers publish events to a broker or event stream without knowing who consumes them, and consumers subscribe to the events they care about, creating loose coupling in both time and space: producers and consumers do not need to be available at the same moment, and adding a new consumer does not require changing the producer. Events are immutable facts and are typically persisted, which gives the system a durable, replayable log of everything that occurred, enabling auditability, debugging, and rebuilding of state. Event streaming platforms like Kafka make this practical with partitioned logs that preserve order per key and support at-least-once delivery. There is an important distinction between event notification (a bare signal that something happened), event-carried state transfer (the event carries the relevant data), and event sourcing (events are the primary store of truth). Event-driven systems excel at handling bursts, decoupling teams, and enabling real-time reactions, but they trade away the simplicity of request/response, introducing challenges around tracing, ordering, exactly-once semantics, and replay. Because consumers can lag, the system must handle out-of-order and duplicate events, usually through idempotency and key-based partitioning. Event-driven architecture is the natural substrate for sagas in choreography style, CQRS read model projections, and IoT telemetry pipelines. A mature event-driven system needs good event schemas, schema versioning, and governance, since events become long-lived contracts across teams.

23. What is idempotency?
    - **Answer:** Idempotency means that performing the same operation multiple times produces exactly the same result and has the same side effects as performing it once. Mathematically, an operation is idempotent if applying it twice yields the same state as applying it once — for example, setting a value to 5 is idempotent, while incrementing a counter is not. In HTTP, GET, PUT, and DELETE are naturally idempotent: fetching a resource repeatedly is harmless, replacing a resource with the same representation has no additional effect, and deleting a resource that no longer exists is a no-op. POST is not idempotent because it creates a new resource each time, which is precisely why network retries of a POST can create duplicates. Idempotency is achieved in practice through idempotency keys: the client generates a unique key (often a UUID) for each business operation and sends it with the request; the server stores the key and the response, and if the same key arrives again it returns the stored response without re-executing the operation. On the server side, idempotency can also be enforced with unique constraints in the database — a unique index on a natural business key causes the second insert to be rejected or skipped rather than duplicated. Messaging systems rely on this heavily because brokers typically deliver at-least-once, so consumers must be idempotent to avoid double-processing a message. Designing idempotent operations is a foundation of reliable distributed systems because it makes retries safe, and retries are how systems recover from transient failures.

24. Why is idempotency important?
    - **Answer:** Idempotency is important because network communication is unreliable, and retries are an unavoidable part of any distributed system; without idempotency, a single retry can corrupt data or cause duplicated side effects. Consider an order placement or a payment charge: a network timeout before the client receives the response leads the client to retry, and if the operation is not idempotent, the customer is charged twice or a duplicate order is created. Message brokers typically provide at-least-once delivery, meaning a message can be redelivered after a consumer crash or network partition, so every consumer must tolerate processing the same message more than once. Beyond correctness, idempotency enables the retry pattern, the circuit breaker, and client-side retries to be used safely — the system can automatically recover from transient failures instead of requiring a human to detect and fix duplicates. Idempotency also simplifies the user experience: a user double-clicking a "submit" button, a mobile app resending a request after a dropped connection, or a client replaying a batch are all harmless instead of producing duplicates. For inventory and financial systems, a duplicated write has direct business impact — inflated counts, double debits, reconciliation failures — making idempotency a hard requirement rather than a nice-to-have. It reduces the need for manual intervention, because the compensation for a duplicate is complex to execute reliably. Fundamentally, idempotency turns the unreliable, at-least-once semantics of the real network into the exactly-once effect that business operations require.

25. How do you design idempotent APIs?
    - **Answer:** The standard design is the idempotency key pattern: the client sends a unique key with the request, typically in a header such as Idempotency-Key, and the server guarantees that requests sharing the same key within a validity window produce the same result and execute only once. On the server, the flow is: check whether the key has already been processed; if it has, return the stored response for that key (with a status indicating replay); if it has not, process the operation and atomically store both the key and the resulting response before returning. The storage of the key must be atomic with the business operation, or a crash between the two leaves a window for duplicates — the cleanest way is a unique constraint on the key column in the same database and transaction as the business write. Idempotency keys are typically stored in a fast store with a TTL, such as Redis or a dedicated database table, and the validity window is usually hours to days to cover the full duration over which clients may retry. The key should be generated by the client per logical operation — retrying the same logical operation reuses the key, while a genuinely new operation gets a new key. Concurrency must be handled: if two identical requests arrive at the same time, the server must serialize them so only one executes, often with a database lock or atomic insert. GET, PUT, and DELETE are inherently idempotent and need no keys; POST endpoints that create or mutate state are the ones that require them. The stored response also makes replays efficient, because the second request does not re-run expensive work. Finally, the API contract should document the idempotency guarantee, the key format, and the behavior on replay, so clients can rely on it.

26. How do you handle duplicate requests?
    - **Answer:** Duplicate requests are handled by making the system detect and suppress them at the layer where the side effect occurs. The strongest defense is a database-level uniqueness constraint on a natural business key: for example, a unique index on order reference or batch ID causes the second insert to fail, and the code catches that specific conflict and returns the already-successful result. For non-idempotent operations that have no natural key, the client-supplied idempotency key (typically in a header) is stored with the response, and any request carrying an already-seen key short-circuits to the cached response without re-executing. Deduplication needs a time dimension: a duplicate is only a duplicate within a reasonable window, because the same payload arriving much later is likely a legitimate new request, so idempotency records should expire (TTL) and dedup logic should not be applied across days without explicit rules. In asynchronous and event-driven flows, duplicates come from at-least-once messaging, so the consumer applies the same approach: a deduplication table or an upsert keyed on a unique message or business ID makes redelivery harmless. Content-based deduplication (hashing the payload) is less reliable than key-based deduplication because legitimate different requests can share payloads, so explicit keys are preferred. The response on a detected duplicate should be consistent with the original response so the caller cannot tell the difference, and no new side effects should be generated. Distributed systems must also handle concurrent duplicates: two identical requests arriving simultaneously should be serialized so only one executes, using a unique constraint or a lock, because a check-then-write race can slip both through. A layered approach — client keys, server dedup storage, and database constraints — provides defense in depth.

27. How do you handle API versioning?
    - **Answer:** API versioning gives consumers a stable contract while the underlying implementation evolves, and the main approaches are URI path versioning, query parameter versioning, header versioning, and media-type (content negotiation) versioning. URI versioning (`/v1/orders`, `/v2/orders`) is the most common because it is explicit, easy to route at the load balancer or gateway, discoverable in documentation, and cacheable; its downside is that the version is part of the URL and can be copied into shared links or bookmarks. Query parameter versioning (`?version=1`) and header versioning (`Accept-Version: 1`) keep the URL clean but make the version invisible and easier to get wrong in caching and in client code. Media-type versioning uses the Accept header with vendor-specific types, which is elegant but harder to manage in practice. Regardless of the mechanism, the rules of safe evolution matter more: never remove or change the meaning of an existing field, only add new optional fields, and keep old endpoints working until consumers migrate. Backward compatibility is the priority, because breaking changes ripple through every consumer and force coordinated deployments. Deprecation is a process, not an event: mark the old version deprecated in documentation and response headers, announce a timeline, and give consumers a migration window before removal. Internally, versioned handlers can share the same domain logic with adapters translating between versions, so the cost of supporting multiple versions is mostly at the boundary. The gateway is a convenient place to map old routes to new service versions. A disciplined versioning strategy — explicit, deprecation-managed, and backward-compatible — is what allows a platform to evolve without breaking its consumers.

28. How do you design pagination?
    - **Answer:** Pagination splits a large result set into pages so that a single request returns a bounded amount of data, protecting both database and client from huge payloads. There are two main styles: offset-based and cursor-based. Offset-based pagination (`?page=2&size=50`) is simple and allows jumping to any page, but it is inefficient for deep pages (large OFFSET means scanning and discarding many rows) and inconsistent — when new rows are inserted or deleted between requests, items shift across page boundaries and the client sees duplicates or gaps. Cursor-based pagination returns an opaque cursor (often the last-seen ID or timestamp, base64-encoded) that the client passes back to fetch the next page; it is efficient because the query is a range lookup on an indexed column (`WHERE id > cursor ORDER BY id LIMIT 50`), and it is consistent under concurrent inserts because the cursor pins the position in the ordered key space. Cursor pagination cannot jump to arbitrary pages, which is fine for infinite-scroll UIs but a limitation for "page 5" links. Page size should be capped (for example, max 100 per request) and validated, with the total count either omitted (it is expensive to compute on every request and often unnecessary) or cached separately. The response envelope should include the next cursor, a has-more flag, and possibly the current data, so clients can paginate without guessing. Keyset ordering requires a stable, indexed sort key; timestamps are not always unique, so a composite cursor (timestamp plus ID) is safer. For very large or real-time datasets, cursor-based pagination is almost always the right choice, while offset-based works acceptably for small, static administrative lists.

29. How do you design search APIs?
    - **Answer:** A search API is designed around three concerns: filtering, sorting, and pagination, layered over a queryable data source. Filtering is expressed with query parameters that map to indexed fields (`?status=active&region=eu`), with date ranges (`?createdFrom=...&createdTo=...`) and exact-match or IN-list semantics; the parameter set should be explicit and validated rather than accepting arbitrary predicates, both for security and for index utilization. Sorting should be restricted to whitelisted, indexed columns so that arbitrary sort keys do not cause full scans or require filesorts. Pagination should use cursor-based or capped offset pagination as the underlying data grows, as described by the pagination pattern. For simple filter-on-fields search over a relational database, parameterized queries and composite indexes cover the common cases, with query building kept in a safe layer to prevent SQL injection. When the search includes full-text, fuzzy matching, relevance ranking, faceting, or it must scale to very large collections, a dedicated search engine like Elasticsearch or OpenSearch is the standard choice: documents are indexed with a chosen analyzer (tokenization, stemming, synonyms), and the API translates query parameters into the engine's query DSL with relevance scoring and aggregations for facets. Text search supports phrase matching, prefix queries, and typo tolerance via fuzzy matching, with results ordered by relevance score rather than by an arbitrary field. Autocomplete and typeahead can be served from a dedicated index built for fast prefix or edge-ngram matching. A search API should support faceted navigation (counts per filter value) so clients can build filter-driven UIs, and it must apply the same security and authorization filters as the main API. The design process is the same regardless of engine: define the query capabilities, enforce bounded result sets, and return a consistent envelope for results, facets, and next-page cursor.

30. How do you design notification system?
    - **Answer:** A notification system is designed as an event-driven pipeline: events are produced by business logic, routed to a notification service, and delivered through multiple channels such as email, SMS, push, and in-app. The core components are a producer, a messaging layer, a notification service, a delivery layer, and a database of notification state. When an event occurs (order shipped, temperature exceeded), the producer publishes a domain event to a broker; the notification service consumes it, determines which users should be notified and via which channels (preference resolution, throttling, scheduling), and creates a notification record with a unique ID. Delivery is delegated to channel adapters — an email provider, an SMS gateway, a push notification service like FCM or APNs — each with its own adapter abstraction so channels can be added without changing the core. Delivery semantics are at-least-once, so the pipeline must be idempotent: the notification ID prevents duplicate sends, and consumers track delivery status (queued, delivered, failed, expired) per channel. Retries handle transient channel failures with exponential backoff, and messages that fail permanently go to a dead-letter queue for investigation. Rate limiting and batching are essential to avoid flooding recipients — a single event that affects thousands of users should produce batched or throttled notifications, with preferences letting users opt out or choose a digest. Ordering and prioritization matter: critical alerts should bypass queues or have a priority channel, while promotional notifications can be deferred. Observability requires tracking per-channel delivery rates, failure rates, and latency, because notification delivery is a system whose health is measured end-to-end to the external provider. The design scales horizontally because each stage is stateless and buffered by the messaging layer.

31. How do you design rate limiter?
    - **Answer:** A rate limiter is designed as a component that decides, for each incoming request, whether it is allowed or rejected based on the client's consumption of its quota within a time window, and it returns 429 Too Many Requests with a Retry-After header when rejected. The first decision is the algorithm: token bucket allows controlled bursts and is simple to implement in memory; sliding window log is exact but memory-hungry; sliding window counter approximates a sliding window with two counters and is a good memory/accuracy trade-off; fixed window is simplest but allows double traffic at window boundaries. The second decision is where the limiter lives: it is typically deployed at the API gateway or edge so it protects all services uniformly, and it can also be applied inside a specific service for fine-grained control over a single hot endpoint. In a single-instance deployment, an in-memory counter is sufficient; in a distributed deployment, the counter must be shared across instances, and Redis is the standard choice — a Lua script on a Redis key per client per window performs the check-and-increment atomically, avoiding race conditions. Limits are usually defined per client identity (API key, user ID, IP) and can be tiered (free, standard, premium), each tier having a different quota; combining identity with IP prevents key sharing abuse. The limiter must be fast (sub-millisecond) because it sits on the hot path, and it should be fail-open in an emergency — if Redis is down, allow traffic rather than block everything, since availability usually matters more than perfect enforcement. It also needs observability: metrics for allowed/rejected requests per client, and alerts on clients that are frequently throttled. Rate limiting protects backend capacity, enforces fair use, and provides the backpressure mechanism that keeps the whole platform stable under load.

32. How do you design URL shortener?
    - **Answer:** A URL shortener maps a long URL to a short, shareable key (such as `xyz.com/Ab3x9`) and resolves that key back to the original URL with a redirect. The core is the key-generation strategy. Hashing the URL (MD5/SHA) and taking a prefix of the digest, or using a base62 encoding of an incrementing counter, both produce short keys; a counter-based approach is simplest because a single global sequence guarantees uniqueness, while a hash-based approach must handle collisions by appending a salt or retrying with a different input. The length of the key determines capacity — base62 with 7 characters offers roughly 62^7 ≈ 3.5 trillion combinations, plenty for realistic use. The read path is the performance-critical one: a redirect happens for every click, so the key-to-URL mapping is cached aggressively in Redis with a TTL, falling back to the database (PostgreSQL or DynamoDB) on a cache miss, with the cache-aside pattern. Clicks should not hit the database synchronously — click events are written to a queue or message broker and processed asynchronously into an analytics store, so the redirect path stays fast. The write path takes the original URL, validates it, generates a key, and stores the row; if the same URL is submitted again, the system can either return the existing key or generate a new one depending on the product decision. Redirection uses HTTP 301 (permanent, cached by browsers) or 302 (temporary, allows click tracking), with 301 being common for shorteners. The system is trivially horizontally scalable because the mapping is a simple key-value lookup and the cache absorbs read spikes. Capacity planning is straightforward: throughput is dominated by redirects, and the design must ensure cache hit ratios stay high and the database never becomes the bottleneck.

33. How do you design distributed cache?
    - **Answer:** A distributed cache is a shared, in-memory data store that sits in front of slower storage (databases, remote APIs) to serve reads with microsecond-to-millisecond latency and to reduce load on the backend. The canonical pattern is cache-aside (lazy loading): on a read, check the cache first; on a miss, read from the database, write the value into the cache with a TTL, and return it; on a write, update the database and invalidate or update the cache. Redis is the standard implementation, chosen for its low latency, atomic operations, TTL support, and rich data structures. Keys are usually composite and versioned (`orders:123:items`) to avoid collisions, and TTLs are mandatory to prevent stale data from living forever and to let hot data naturally rotate out. Stale data is controlled by choosing TTLs aligned with how fresh the data must be; where stronger guarantees are needed, the cache can be invalidated on writes, though invalidation across many instances adds coordination complexity. Two classic failure modes must be engineered around: cache stampede (many concurrent requests all miss at once and hammer the database — mitigated with locking, single-flight, early re-expiration, or stochastic TTLs) and cache penetration (requests for keys that do not exist in cache or database — mitigated with short-lived negative caching). For datasets larger than one node, the cache is partitioned using consistent hashing so that keys distribute across shards and node additions/removals only move a fraction of keys; consistent hashing also underpins Redis Cluster. Cache topology also matters: a read-through or write-through cache can be layered, and high-availability deployments add replicas. Metrics such as hit ratio, miss latency, and eviction rate are the essential operational signals. The cache is a powerful lever, but it must never be the source of truth — the database remains authoritative and the cache can be rebuilt at any time.

34. How do you design chat system?
    - **Answer:** A chat system is designed around three flows — message send/receive, presence, and history — with real-time delivery as the defining requirement. For real-time bidirectional communication, WebSockets (or modern alternatives such as server-sent events or HTTP/2 streaming) establish a persistent connection from client to server; with multiple servers, clients connect to an edge that maintains their socket, and a pub/sub layer (Redis pub/sub, or a streaming broker like Kafka with partitions per chat room) routes messages between servers so the receiving client's server can push the message. Each message carries a sender ID, conversation/message ordering key, timestamp, and a client-generated ID so the client can deduplicate. Ordering is guaranteed per conversation by partitioning on conversation ID, since a single consumer handles each partition sequentially. Durability comes from a message store (a relational database or a time-ordered store like Cassandra) written by a separate consumer of the same stream, so delivery and persistence are decoupled. Delivery semantics are at-least-once, so clients deduplicate by message ID, and offline users receive messages on reconnect by fetching from the cursor of the last delivered message. Presence is tracked with heartbeats and socket state — online, offline, or idle — with a presence service in a shared store (Redis with TTL) so any edge server can answer "who is online." Read receipts and typing indicators are best-effort, ephemeral signals broadcast over the pub/sub layer. Scaling: stateless edge servers hold the sockets, the pub/sub layer scales horizontally, and the history store is partitioned by conversation ID. Unread counts are derived asynchronously from message offsets. This design delivers a chat system whose latency is dominated by the network round trip, with history and presence handled independently.

35. How do you design inventory system?
    - **Answer:** An inventory system is designed around the core operations of receiving stock data, validating it, updating counts, and serving accurate queries, with correctness as the dominant constraint. The write path is typically batch-driven: partners submit batches of serial records; each batch gets a unique batch ID that doubles as an idempotency key; records are validated against a baseline (duplicate serials, invalid serials, unknown products) using set operations that are efficient in a relational database. Validation and the resulting state change should happen inside a single ACID transaction per batch so partial failures cannot leave the inventory in an inconsistent state. Accepted records update the inventory count; rejected records are flagged with reasons for reconciliation. Stock levels are stored per product (and per location if multi-warehouse), and changes are recorded in a ledger of movements so any count can be explained and audited. Reads serve different consumers: real-time queries for dashboards can use optimized, denormalized count tables or a cache, while reporting and reconciliation use the ledger. Concurrency is a key risk: two batches touching overlapping stock must not race, so updates are serialized through row locks or optimistic concurrency with version columns, and over-commit is prevented by enforcing non-negative stock in the data model. If the system grows across services, the counts become eventually consistent: writes publish events, and projection services maintain read models, with reconciliation jobs detecting and fixing drift. The design must also handle idempotent resubmission, because partners will retry failed batches. Performance for batch validation is achieved by batching in bulk (set-based SQL rather than row-by-row), which keeps high-volume validations in seconds.

36. How do you design IoT monitoring system?
    - **Answer:** An IoT monitoring system is an end-to-end pipeline from physical sensors to a monitoring dashboard, and the design is dominated by the ingestion side: potentially millions of devices producing telemetry continuously. On the device side, lightweight protocols like MQTT over TCP/TLS (or CoAP for constrained devices) connect sensors to a broker such as AWS IoT Core, Mosquitto, or EMQX; devices publish readings on topics organized by device or site, which gives natural routing and access control. The ingest path terminates at a highly available ingestion layer that must absorb bursts and never drop data — telemetry is written to a durable message broker or streaming platform such as Kafka, which decouples the rate of production from the rate of processing. Stream processors (Kafka Streams, Flink, or consumer applications) transform and enrich the data, perform threshold detection for alerts, and write to a time-series database such as InfluxDB or TimescaleDB that is purpose-built for append-heavy, timestamped data with downsampling and retention policies. Alerts are a separate concern: threshold crossings are evaluated in the stream layer and routed to an alerting service that deduplicates, throttles, and delivers via email/SMS/push so that a fleet-wide excursion does not create a flood of notifications. Dashboards and APIs read from the time-series store, with pre-aggregated rollups (1-minute, 5-minute, hourly) for fast historical queries and caching for hot data. Ordering per device matters for trend analysis, so partitions are keyed by device ID. The key metrics are ingestion lag, end-to-end latency, drop rate, and consumer lag, since a monitoring system that silently loses data is worse than none. Scalability comes from horizontal partitioning at every stage, and reliability from duplicate-tolerant, idempotent writes and replayable streams.

37. How do you design real-time dashboard?
    - **Answer:** A real-time dashboard continuously displays fresh data to users, and the design centers on how data moves from the backend to the browser. The data path starts with a backend API backed by a fast query layer, and "real-time" is a spectrum: near-real-time polling is often sufficient, while truly sub-second updates require push. The simplest reliable approach is polling with a configurable interval (for example, every 10–30 seconds), where the frontend fetches the latest aggregation; it is easy to implement, cacheable, and resilient to disconnects. WebSockets or Server-Sent Events provide push when updates must appear immediately — the backend pushes changes as they occur, avoiding the latency and wasted requests of polling. The backend must make queries cheap, because dashboards issue repeated, expensive aggregation queries: pre-aggregation (rollups computed by stream processing at 1-minute or 5-minute granularity), time-series databases with downsampling, materialized views, and caching of hot results in Redis are the standard techniques. To avoid stampede on a refresh, the query layer should be read-only, cached, and served from replicas. The API should return bounded windows (latest N points, or a date range with a resolution) so payloads stay small, and it should paginate or stream large history. Real-time dashboards must also tolerate momentary backend slowness — the UI should degrade gracefully by showing stale data with a freshness indicator rather than erroring. The refresh architecture should avoid every browser client hammering the backend: use a shared cache with TTL, or push via a gateway so the computation happens once and is fanned out. Metrics to watch are query latency percentiles, cache hit ratio, and staleness. The design goal is consistent, sub-second perceived freshness without pushing query load onto the primary database.

38. How do you handle high throughput ingestion?
    - **Answer:** High-throughput ingestion is handled by inserting a durable buffer between producers and consumers, and by making every stage horizontally scalable, so that no component is forced to match the peak production rate. The standard tool is a partitioned log like Kafka: producers write to topics partitioned by key (device ID, tenant, order ID), which preserves per-key ordering and distributes write load across brokers; consumers read in parallel from partitions, so throughput scales with the number of partitions and consumers. The buffer absorbs bursts and spikes, letting consumers process at their own pace, and it provides durability — a consumer crash loses nothing because offsets track progress and replay is possible. Backpressure is the essential principle: if consumers cannot keep up, the right response is not to drop data but to scale consumers out, to alert on consumer lag, and, in the worst case, to apply load shedding at the edge with explicit, logged rejection of excess. Batch writes are far more efficient than one-record-at-a-time writes: producers batch (Kafka's linger), and consumers write to storage in bulk transactions. The downstream storage is chosen for the write pattern — a time-series database or a log-structured store with append-friendly writes rather than an OLTP database that requires updates and locking. Idempotency must be built into consumers because at-least-once delivery means duplicates are possible; deduplication keys and upserts make redelivery harmless. Partition count must be planned up front because adding partitions later is disruptive, and it is sized from expected peak throughput per key times the target parallelism. The design goal is linear scalability: doubling the producers, brokers, and consumers should roughly double sustained throughput.

39. How do you handle data consistency?
    - **Answer:** Data consistency is handled by choosing the strongest guarantee each workflow actually needs and designing the architecture around that boundary. Within a single service and its own database, full ACID transactions give strong consistency — atomicity, isolation, and durability — and this is where writes that must be atomic together (a batch validation that updates counts) belong. The key design rule is to minimize the amount of data that needs cross-service atomicity: keep related, frequently co-updated data in the same service or same database so a single transaction suffices. Across service boundaries, global ACID is not achievable at scale (the CAP theorem forces a choice under partitions), so the standard approach is eventual consistency with explicit, bounded staleness: writes are published as events, dependent services consume them and update their own views, and applications are written to tolerate reading slightly stale data. The CAP theorem frames the trade-off: partition tolerance is mandatory in distributed systems, so the real choice is between consistency and availability, and most distributed systems choose availability with eventual consistency for non-critical paths. Patterns that preserve correctness under eventual consistency are idempotent operations, versioned writes, last-write-wins or compare-and-set conflict resolution, outbox pattern for reliable event publication (write the event to the same database transaction as the business change, then publish to the broker from the outbox), and reconciliation jobs that periodically detect and repair drift. Compensation mechanisms such as sagas provide cross-service rollback in business terms. The consistent picture is layered: strong consistency where it is cheap and required (money, inventory counts), eventual consistency where the business tolerates it (analytics, notifications, read models), and reconciliation to guarantee convergence. The design always documents the staleness bound and makes the consistency choice deliberate rather than accidental.

40. How do you handle failure in downstream services?
    - **Answer:** Downstream failures are handled with a layered resilience strategy so that a failing dependency degrades only its own functionality instead of cascading through the caller. The first layer is timeouts on every outbound call, because a hung dependency that never returns will otherwise consume threads and connections indefinitely. The second layer is retries with exponential backoff and jitter for transient failures, bounded by a budget so a persistently failing dependency is not hammered. The third layer is the circuit breaker, which stops all attempts once the failure rate crosses a threshold, gives the dependency time to recover, and re-probes in the half-open state. Fallbacks provide graceful degradation: if a call fails, the caller returns a stale cached value, a default, or a simplified response instead of an error, so the user-facing feature partially works. Bulkheads isolate resource pools so that a saturated dependency cannot starve calls to healthy dependencies. Asynchronous decoupling is itself a resilience technique: when the call can be made async, the request is queued and processed later, so a downstream outage does not block the caller at all. Idempotency makes retries safe. Beyond the caller side, the whole system should be designed so that no single dependency is on the critical path of unrelated features — feature independence, redundant instances, and multi-AZ deployment reduce the chance of a single failure taking out a whole capability. Monitoring completes the loop: failure rates, fallback activations, and circuit-breaker state changes are surfaced as alerts. The guiding principle is fail fast, degrade gracefully, and recover automatically.

41. How do you choose between sync and async communication?
    - **Answer:** The choice between synchronous and asynchronous communication is driven by whether the client needs the result immediately and whether the operation must complete within the request. Use synchronous communication (REST, gRPC) when the caller needs an immediate, deterministic answer — a query for current state, an operation whose result determines the response (create an order and return its ID) — and when the operation is fast enough to complete within a reasonable request budget. Use asynchronous communication (message brokers, event streams) when the operation can proceed independently of the caller's wait — background processing, notification dispatch, telemetry ingestion, or any high-throughput flow where the producer must not be slowed by the consumer. Asynchrony also shines when the call must be decoupled in time (the consumer can be offline and catch up later) or when the workload is bursty, because the broker buffers the spike. The error-handling model differs fundamentally: synchronous calls surface failures inline and can be retried immediately, while asynchronous flows need dead-letter queues, retry tiers, and monitoring for stuck messages. Tracing and debugging are easier with synchronous calls; asynchronous flows need correlation IDs propagated through message headers. A pragmatic hybrid is common: synchronous at the edge for interactive clients, asynchronous internally for event-driven workflows and cross-service state propagation. The decision also depends on consistency requirements — if the business requires an immediate, strongly consistent outcome, async makes it harder. The general rule: if the client blocks on the result, keep it synchronous and fast; if the work is decoupled, background, or bursty, make it asynchronous.

42. How do you secure microservices?
    - **Answer:** Microservices security follows a defense-in-depth model: authenticate every request at the boundary, authorize at each service, encrypt in transit, validate input everywhere, and protect inter-service communication. The standard for end-user authentication is OAuth 2.0 with OpenID Connect, where an identity provider issues short-lived JWT access tokens; the API gateway or edge validates the token's signature, expiry, and issuer, and passes the claims downstream. Authorization (what the user can do) is enforced in each service based on claims — roles and scopes in the token — rather than trusting only the gateway, so every service enforces its own access rules. For service-to-service calls, the same JWT pattern can be used with a machine identity, or mutual TLS (mTLS) verifies both endpoints and encrypts traffic; service meshes such as Istio or Linkerd implement mTLS automatically. Secrets — database passwords, API keys, tokens — must never be in code or configuration files; they are stored in a vault (HashiCorp Vault, cloud secret managers) and injected at runtime. Input validation and parameterized queries at every service prevent injection attacks, and the gateway applies rate limiting and payload validation to mitigate abuse. HTTPS/TLS is mandatory on every boundary, with TLS termination at the gateway and again internally where data sensitivity warrants. Additional layers include network segmentation (services only reachable within a private network or service mesh), security logging and audit trails, and dependency scanning plus CVE patching as part of CI/CD. The threat model must consider compromised services — a breached service should be contained by least-privilege credentials and per-service keys. Security in microservices is distributed: every service is a trust boundary, and the design must assume any single component can be compromised.

43. How do you monitor microservices?
    - **Answer:** Monitoring microservices is built on the three pillars of observability — logs, metrics, and traces — applied uniformly across every service, so that the health and behavior of the whole system can be understood from centralized views. Logs provide event-level detail: every service emits structured logs to a centralized log platform, tagged with service name, instance, and correlation/trace ID so errors can be traced across services. Metrics provide time-series signals: request rate, latency percentiles, error rate, and resource utilization per service, scraped by a system like Prometheus and visualized in Grafana. Distributed tracing connects the two for individual requests, showing the path, timing, and failures across service boundaries, which is indispensable for debugging latency and error propagation. Health checks are the operational baseline: each service exposes a health endpoint (Spring Boot Actuator, Kubernetes liveness/readiness probes) so load balancers and orchestrators route around unhealthy instances automatically. Alerting turns signals into action: thresholds on error rate, latency, and consumer lag trigger pages, with alert rules tied to service-level objectives so alerts fire when the user-visible promise is at risk. Infrastructure metrics (CPU, memory, network, disk) are collected per node or pod, and business metrics (records processed, messages consumed, jobs completed) matter because they detect silent failures that generic metrics miss. Every new service should come with a standard observability package — health check, metrics endpoint, structured logging, trace instrumentation — as a requirement of deployment, not an afterthought. The goal is a single pane of glass: an engineer can find the request, its logs, its trace, and the metrics of every service it touched in seconds.

44. What metrics would you track for backend services?
    - **Answer:** Backend service metrics fall into the RED method for service health and the USE method for infrastructure. RED stands for Rate, Errors, and Duration: request rate (requests per second, per endpoint), error rate (percentage and count of 5xx and 4xx responses, and unhandled exceptions), and duration (latency percentiles — p50, p95, p99 — because averages hide tail latency that users actually experience). Latency percentiles are the most important signal: p99 is a good proxy for the worst-case user experience, and a p99 that drifts while p50 stays flat signals resource contention or GC or lock pressure. USE stands for Utilization, Saturation, and Errors applied to each resource (CPU, memory, disk, network, connections, thread pools): utilization is how busy a resource is, saturation is how much queued or extra work is waiting, and errors are device-level failures. Beyond the generic RED/USE sets, services track dependency metrics: downstream latency and error rate per dependency, circuit-breaker state, and retry counts — this is what detects degradation before it reaches the user. Message-driven services track consumer lag (how far the consumer is behind the latest message), which is the leading indicator of ingestion problems. Thread pool and connection pool usage reveal capacity pressure; queue depth and dead-letter counts reveal processing failures. Business metrics complete the picture: throughput of business operations (orders, records processed), so that a pipeline that is "healthy" by infrastructure metrics but silently dropping work is still caught. Every metric should be labeled with service, endpoint, and instance so it can be sliced by any dimension.

45. What is SLA?
    - **Answer:** An SLA (Service Level Agreement) is a formal contract between a service provider and a customer that defines the expected level of service and the consequences if it is not met, typically including availability and performance commitments. The most common commitment is uptime as a percentage, such as 99.5% or 99.9% — the fraction of a period (usually a month) during which the service is available. Availability percentiles translate into concrete budgets: 99.9% allows about 43 minutes of downtime per month, and 99.99% allows about 4 minutes, which shows how quickly the margin shrinks as the target tightens. SLAs also cover performance (latency thresholds, e.g., "95% of requests complete within 300 ms"), support response times, and other service attributes, and they define credits or penalties paid to the customer when targets are missed. An SLA is a business contract, not just a technical target, and it should be set based on what the business can actually achieve and afford, because meeting a stricter SLA requires redundancy, monitoring, and engineering investment. Hitting a high SLA is a design problem: 99.9% requires multi-AZ deployment, redundant instances, automated failover, and careful change management, while 99% can be met with simpler single-region design. The SLA also drives monitoring: the measurement method must be agreed on, because "availability" can be measured as uptime of the infrastructure, successful health checks, or user-visible request success rates. The relationship between SLA and SLO is that the SLA is the externally visible commitment, while SLOs are the internal engineering targets set to make sure the SLA is met with a margin. Realistic SLAs also anticipate shared responsibility — network and cloud-provider outages are typically excluded or shared.

46. What is SLO?
    - **Answer:** An SLO (Service Level Objective) is an internal, engineering target for how reliable a service must be, expressed as a measurable objective such as "99% of requests complete in under 500 ms" or "error rate below 0.1% over a rolling month." SLOs are chosen to be stricter than the externally committed SLA, so that engineering teams operate with a buffer: if the SLO is 99.9% but the SLA promises 99.5%, there is headroom, and internal issues are caught and fixed before customers are affected. An SLO has three parts: a metric (what is being measured), a threshold (the value that must be met), and a window (the period over which it is evaluated, such as a rolling 30 days). Because an SLO is a percentage over a window, short blips do not necessarily breach it — what matters is the cumulative performance over the window, which is why SLO-based alerting looks at burn rate rather than instantaneous spikes. SLOs drive alerting: alerts should fire not just when the SLO is breached but when the burn rate indicates it will be breached soon, and each alert is tied to a user-visible consequence. Choosing the right SLO is a product decision, not just a technical one — it reflects how reliable users expect the service to be and what the team can realistically maintain, and over-strict SLOs create noise and alert fatigue while over-loose ones let real problems pass unnoticed. SLOs also guide operational and release decisions through the error budget. A good SLO program makes reliability measurable, gives on-call a clear definition of "broken," and turns vague goals like "be reliable" into a specific number the whole organization can track.

47. What is error budget?
    - **Answer:** An error budget is the acceptable amount of failure over a period, derived directly from the SLO: if the SLO promises 99.9% availability, the error budget is the remaining 0.1% (about 43 minutes per month) of allowed downtime or failure. The error budget turns reliability into a measurable quantity that engineering and product can manage like a resource. When the budget is unspent (service is performing better than the SLO), the team has permission to ship changes, release features, and take engineering risk, because the service is safely above its reliability target. When the budget is exhausted (failures have consumed all allowed downtime), the team must prioritize stability: pause risky releases, focus on fixing the underlying issues, and reduce change velocity until the budget is replenished. This inverts the traditional dynamic where every outage is treated as a crisis and releases are always gated by fear — the error budget makes the trade-off between velocity and reliability explicit and rational. The concept comes from Google's SRE practice and is closely tied to the fact that error budgets should be aligned between product teams and platform teams, because one team's changes can consume another team's budget. Error budgets also force honesty about measurement: the budget is consumed based on the same metric as the SLO (request success, latency), so the team knows in near-real time how close they are to the edge. Monitoring burn rate — the rate at which the budget is consumed — enables early alerts, so the team reacts to a fast burn well before the budget is actually exhausted. The error budget gives a concrete, data-driven answer to the question "when is the system too unstable to release?"

48. How do you design for scalability?
    - **Answer:** Scalability design starts with finding the bottleneck — the component that limits throughput — because scaling everything else while the bottleneck remains is wasted effort; the classic candidates are the database, a single-threaded worker, or a stateful service. The two axes are vertical scaling (bigger machines) and horizontal scaling (more instances); horizontal scaling is preferred because it is elastic and failure-tolerant, but it requires that instances be stateless — session and cache state must live in a shared store like Redis or a database rather than in the instance's memory. Stateless services are scaled by putting them behind a load balancer and adding or removing instances based on load; orchestration platforms like Kubernetes automate this with autoscaling based on CPU, memory, or custom metrics. The database is almost always the hard part: read-heavy systems scale with read replicas and caching; write-heavy systems need sharding (partitioning data by key so each shard holds a subset) or event-sourced, append-only designs, and every query must be indexed and bound in size. Message brokers in the ingestion path absorb bursts so consumers scale independently of producers, and queue consumers scale horizontally per partition. Asynchronous, queue-based processing lets workloads that can be delayed (reports, notifications, enrichment) be smoothed over time instead of paid for at the peak. Capacity planning is part of the design: estimate peak load from usage data, size partitions and instance counts for that peak with headroom, and test with load testing to confirm the design scales linearly. Caching and data locality reduce load at the source, and pagination, aggregation, and read models keep queries cheap. Every scaling design should be verified against the metrics — latency, throughput, and consumer lag — because a system that is not measured cannot be scaled effectively.

49. How do you design for reliability?
    - **Answer:** Reliability design aims to keep the service delivering its function despite failures, and it starts by eliminating single points of failure: every critical component — load balancer, application instance, database, message broker — should have redundant, independent replicas, ideally across availability zones so a facility failure does not take the system down. Stateless application instances behind a load balancer fail over seamlessly; state requires replication — databases with primary/replica failover, and brokers with replication factor so no node holds the only copy of a message. The application layer uses the resilience patterns (timeouts, retries, circuit breakers, bulkheads, fallbacks) so that a failing dependency degrades only its own feature. Graceful degradation is the goal: the system should keep providing partial service under stress — showing cached data when the database is slow, serving reads when writes fail — rather than failing entirely. Deployment reliability requires automated, repeatable releases with health checks, canary or blue-green deployment, and rollback capability, because most outages are caused by change. Automated failover and self-healing (orchestration restarts crashed pods, health checks remove unhealthy instances) reduce mean time to recovery, and since failures are inevitable, the design optimizes for fast recovery and minimal impact. Monitoring and alerting on SLO burn rates detect degradation early, and post-incident reviews turn each outage into system improvements. Backups and tested restores protect against data loss, and chaos engineering deliberately introduces failures to verify the design handles them. Reliability is designed in at every layer — redundancy, isolation, graceful degradation, and fast recovery — and validated continuously rather than assumed.

50. How do you design for maintainability?
    - **Answer:** Maintainability design makes a system cheap to understand, change, and extend over time, and it starts with the structure of the code and services: clear boundaries, single responsibility per module or service, and consistent, predictable patterns so that any engineer can navigate the system. Services should be named by business capability with well-defined, versioned contracts between them, so the architecture itself communicates the domain model. Code quality practices — meaningful names, small functions, and absence of duplication — make change safe, and comments explain the "why" that code cannot, such as the reason an index or a workaround exists. Automated tests are the safety net that makes change affordable: unit tests for logic, integration tests across boundaries, and contract tests so that services can evolve independently without breaking consumers. Deployment and operations are maintained through automation: infrastructure as code, CI/CD pipelines, and runbooks so that deploying and diagnosing are repeatable, not manual rituals. Documentation that lives with the code — API specifications, architecture decision records, and runbooks — keeps knowledge from concentrating in a few people. Observability (structured logs, metrics, traces) makes diagnosing issues fast, which is a large part of day-to-day maintenance. Dependency hygiene matters: keep libraries and platforms reasonably current to avoid expensive migration spikes, and keep the number of technologies small enough that specialists are not required for every component. Simplest-adequate design is a maintainability principle: adding unnecessary abstraction or premature generalization costs more to understand than it saves. The measure of maintainability is the time for a new engineer to make a safe, small change, and the design constantly optimizes for that.
