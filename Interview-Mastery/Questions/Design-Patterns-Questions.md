# Design Patterns Questions

## Questions

1. What are design principles and design patterns?
2. Explain the SOLID principles.
3. What are the DRY and KISS principles?
4. Explain the Factory design pattern.
5. Explain the Singleton design pattern.
6. Explain the Strategy design pattern.
7. Explain the Observer design pattern.
8. Explain the Adapter design pattern.

---

## Answers

1. What are design principles and design patterns?
   - **Answer:** Design principles are broad, language-agnostic guidelines for writing clean, maintainable software. They describe *how to think* about a design problem rather than prescribing a concrete structure. Examples include SOLID, DRY, KISS, YAGNI, and the Law of Demeter. A principle such as "program to an interface, not an implementation" tells a developer what quality the code should have, but it does not dictate exactly how to achieve it. Design patterns, by contrast, are proven, reusable templates for solving specific recurring problems in object-oriented design. Each pattern has a well-defined structure — named participants, their responsibilities, and their relationships — and is categorized by intent. The three families are creational patterns, which control object creation (Factory, Singleton, Abstract Factory); structural patterns, which arrange objects and classes into larger structures (Adapter, Decorator, Facade, Proxy); and behavioral patterns, which define how objects communicate and distribute responsibility (Strategy, Observer, Command, Template Method). The relationship between the two is hierarchical: principles motivate patterns, and patterns are concrete manifestations of principles. A Factory embodies the Open/Closed and Dependency Inversion principles; an Observer embodies the principle of loose coupling. Patterns should be applied when the problem genuinely matches the pattern's intent — not forced into every class just because a pattern exists. Over-applying patterns produces the very complexity they are meant to reduce, which violates KISS and YAGNI. A practical approach is to let repeated pain points in the design reveal where a pattern is needed, and to prefer a plain, direct solution when a pattern would add indirection without adding value. Finally, a working knowledge of patterns provides a shared vocabulary: saying "this is a Strategy" or "this needs an Adapter" communicates a design decision far faster than re-explaining it.

2. Explain the SOLID principles.
   - **Answer:** SOLID is an acronym for five object-oriented design principles introduced by Robert C. Martin, each addressing a specific source of rigidity and fragility in code. **S**ingle Responsibility Principle (SRP) states that a class should have exactly one reason to change — one cohesive responsibility. Concretely, if two responsibilities change for different reasons, they should live in separate classes. For example, a `ReportGenerator` should not also perform `FilePersistence`; a change to the storage format should not force a change to the report layout logic. **O**pen/Closed Principle (OCP) states that classes should be open for extension but closed for modification: new behavior should be added by writing new code, not by editing existing, tested code. This is typically achieved with polymorphism — a dispatcher that holds a `PaymentProcessor` interface can accept a new `PayPalProcessor` without any change to the dispatcher itself. **L**iskov Substitution Principle (LSP) states that subtypes must be substitutable for their base type without altering the correctness of the program. A classic violation is a `Square` extending `Rectangle` and overriding width/height in a way that breaks the invariant that the rectangle's area equals width times height; callers that rely on `Rectangle` semantics will silently produce wrong results. **I**nterface Segregation Principle (ISP) states that clients should not be forced to depend on methods they do not use. Instead of one fat `UserService` interface with persistence, email, and auth methods, split it into `UserReader`, `UserWriter`, and `UserNotifier` so each client only sees the contract it needs. **D**ependency Inversion Principle (DIP) states that high-level modules should not depend on low-level modules; both should depend on abstractions, and abstractions should not depend on details. In practice this means injecting interfaces — `class OrderService { OrderService(OrderRepository repo) { ... } }` — rather than calling `new JdbcOrderRepository()`, so the high-level logic depends on the contract, not the concrete technology. The principles are mutually reinforcing: SRP keeps classes focused, which makes them easier to extend per OCP; LSP protects polymorphism, which is what OCP relies on; ISP keeps contracts minimal so substitution is realistic; and DIP inverts dependency flow so the whole system can be composed and tested. Violations surface as code that is hard to test (tight coupling makes mocking impossible), hard to extend (every new feature edits existing classes), and prone to surprising behavior. In practice, applying SOLID well is about identifying the axes of change in a system and letting each class sit on exactly one axis. A code example of OCP and DIP together: `interface PaymentProcessor { void pay(BigDecimal amount); }` with `class CardProcessor implements PaymentProcessor` and `class PaymentService { private final PaymentProcessor processor; }` — adding Stripe support means adding a class, not touching `PaymentService`. SOLID is not a checklist to apply mechanically; it is a lens for judging whether a design separates concerns and inverts dependencies in a way that keeps the system malleable.

3. What are the DRY and KISS principles?
   - **Answer:** DRY — Don't Repeat Yourself — states that every piece of knowledge in a system should have a single, unambiguous, authoritative representation. When the same logic appears in multiple places, a change must be replicated everywhere, which guarantees that eventually one copy will be missed and the copies will drift apart. DRY is applied by extracting duplicated logic into a method, class, or constant and reusing it — for example, putting tax calculation or validation rules in one helper instead of inlining the same code in controllers, services, and mappers. DRY applies to logic and knowledge, not to incidental text: two methods that both happen to read a file are not necessarily a DRY violation unless the *rule* they encode is the same. KISS — Keep It Simple, Stupid — states that the simplest solution that correctly solves the problem is the best solution. Simpler code has fewer places to hide bugs, is easier to read and review, and costs less to maintain. KISS argues against speculative generality: do not build an abstraction layer, a configurable framework, or a caching system for requirements that have not arrived. The two principles exist in tension and must be balanced. Forcing DRY too aggressively leads to premature abstraction — a shared base class or a heavily parameterized utility that is hard to follow, which then violates KISS. Conversely, copy-pasting the same logic everywhere is a maintenance hazard that no amount of simplicity justifies. A good heuristic is the "rule of three": allow a duplication to appear twice, and only extract the shared logic when a third occurrence reveals the true shape of the abstraction. A second heuristic is that DRY should be applied along the axis of change — extract what is genuinely one concept, and leave alone what only looks similar. The classic counterexample is two unrelated places that coincidentally use the same literal; forcing them to share a constant couples unrelated code and violates KISS. In review, the question is always whether a change now touches one place or many: DRY optimizes for that, KISS optimizes for immediate comprehensibility, and good engineering picks the point where both are best served.

4. Explain the Factory design pattern.
   - **Answer:** Factory is a creational design pattern that decouples client code from the concrete classes it instantiates by delegating object creation to a dedicated factory. The core problem it solves is that using `new ConcreteClass()` directly hard-codes a dependency into client code: adding a new type means finding and editing every call site, and the client must know details of construction (which arguments, which setup steps) that are none of its business. The factory centralizes creation logic and returns instances through a common interface, so clients depend on the abstraction instead. There are three main variants. **Simple Factory** is not strictly a GoF pattern: a single class with a `create(type)` method that uses a switch or map to pick the concrete type — often implemented as a static method. **Factory Method** is the classic GoF form: a base class or interface declares a creation method, and each subclass overrides it to instantiate the product it knows about, letting a framework define the algorithm while subclasses decide the objects. **Abstract Factory** creates *families* of related objects — a `UIFactory` that produces a matching set of `Button`, `Checkbox`, and `ScrollBar` for Windows or macOS so the pieces stay consistent. The structure has three participants: the Product interface, the ConcreteProduct implementations, and the Creator that exposes the factory method. A Java example of Factory Method: `public interface Document { void open(); }`, `public class PdfDocument implements Document { ... }`, and `public abstract class DocumentCreator { public abstract Document create(); public void deliver() { Document d = create(); d.open(); } }` with `public class PdfCreator extends DocumentCreator { public Document create() { return new PdfDocument(); } }`. In frameworks, Spring's `BeanFactory` and `ApplicationContext` are object factories that produce beans from configuration, and `java.util.Calendar.getInstance()` and `NumberFormat.getInstance()` are library-level factories that pick a locale-appropriate implementation. The main benefit is Open/Closed compliance: introducing a new product means adding a product class and registering it in the factory, without changing client code. It also centralizes complex construction, supports caching or pooling of instances, and enables mocking in tests because clients consume an interface. Factory should NOT be used when there is only one implementation and construction is trivial — there, `new` is clearer and a factory is indirection with no payoff. It also should not be used when the client genuinely needs to pass different constructor arguments to different types, because a factory signature tends to flatten those differences. Factory is closely related to other patterns: a Factory often produces Strategies or Observers, an Abstract Factory is frequently a Singleton, and in Spring the entire dependency-injection container is, in a broad sense, a factory that configures and assembles objects declared in configuration.

5. Explain the Singleton design pattern.
   - **Answer:** Singleton is a creational pattern that guarantees a class has exactly one instance in the JVM and provides a single global access point to it. The problem it solves is managing shared resources or shared state — such as a connection pool, a configuration reader, a thread pool, or a logging facility — where multiple instances would be wasteful or inconsistent. The classic implementation enforces this with a private constructor (so nobody can call `new`) and a static accessor. There are several thread-safety strategies. The simplest is **eager initialization**: `public final class Config { private static final Config INSTANCE = new Config(); private Config() { } public static Config getInstance() { return INSTANCE; } }` — the instance is created at class-load time, so thread safety is guaranteed by the JVM class-loading mechanism. The drawback is that the instance is created even if it is never used. The **Bill Pugh static holder** variant keeps laziness without synchronization: `public final class Config { private Config() { } private static class Holder { static final Config INSTANCE = new Config(); } public static Config getInstance() { return Holder.INSTANCE; } }` — the nested class is not loaded until `getInstance()` is first called, and class loading is inherently thread-safe. The naive **lazy synchronized** approach `public static synchronized Config getInstance()` is correct but serializes every access under contention; **double-checked locking** mitigates that but requires the field to be `volatile` and is easy to get subtly wrong. Since Java 5, an even cleaner option is an `enum` with one constant: `public enum Config { INSTANCE }`, which provides serialization safety and reflection protection for free. The pattern has well-documented costs. A hand-rolled Singleton is essentially global mutable state: it hides dependencies (any class can reach `Config.getInstance()` from anywhere), makes unit testing harder because the shared instance is hard to replace or reset, and complicates lifecycle management. The GoF book itself warns against overusing it. In a Spring application this criticism is the reason the framework offers **singleton scope**: by default the container creates exactly one bean instance per bean definition and injects it everywhere, but the object is a plain POJO with a public constructor and injected dependencies — so the same guarantee is achieved without the hidden global access. The recommended modern practice is therefore to rely on the IoC container for singletons, or to use the enum/holder approach only for genuinely framework-free, stateless utilities. Singleton also relates to other patterns: it is commonly used to access factories, registries, and configuration objects, and it pairs naturally with the Factory pattern when a single factory instance must be shared. The decision criterion is whether the single-instance guarantee genuinely matters for the resource's correctness or efficiency — otherwise a regular object with dependency injection is simpler and more testable.

6. Explain the Strategy design pattern.
   - **Answer:** Strategy is a behavioral pattern that defines a family of interchangeable algorithms, encapsulates each one in its own class, and lets the client select among them at runtime without changing the client's code. The problem it solves is that conditional logic — long `if-else` or `switch` chains selecting between algorithms — grows with every new algorithm, is hard to read, and violates the Open/Closed principle because adding an algorithm means editing the dispatcher. Strategy replaces that branching with polymorphism: the client holds a reference to an interface, and the actual behavior is chosen by which implementation is plugged in. The structure has three participants: the **Context**, which holds a reference to the strategy and delegates the algorithm call to it; the **Strategy** interface, which declares the algorithm contract; and the **ConcreteStrategy** classes, each implementing one variation. A Java example: `public interface PricingStrategy { double calculate(double base); }`, `public class DiscountedStrategy implements PricingStrategy { public double calculate(double base) { return base * 0.9; } }`, `public class StandardStrategy implements PricingStrategy { public double calculate(double base) { return base; } }`, and `public class Checkout { private PricingStrategy strategy; public void setStrategy(PricingStrategy s) { this.strategy = s; } public double total(double base) { return strategy.calculate(base); } }`. The Context can also accept the strategy in its constructor, making it immutable. The core benefit is that adding a new algorithm means writing a new class and injecting it — the Context and existing strategies remain untouched, which satisfies OCP. It also isolates each algorithm for focused unit testing, removes the mutation-style thinking of branch chains, and allows behavior to be switched at runtime, which is often necessary in interactive or event-driven systems. In frameworks, Strategy appears throughout the JDK: `Comparator<T>` is a strategy for ordering, `Executor` and `ExecutorService` are strategies for how tasks run, and `PathMatcher` strategies drive file matching; Spring's `ResourceLoader`, `MessageSource`, and various `*Strategy` beans are configured strategy objects assembled by the container. In Java 8+, a functional interface with one method can be supplied as a lambda — `checkout.setStrategy(base -> base * 0.9)` — which turns a single-method strategy into a lightweight, anonymous implementation without the ceremony of a class. Strategy should NOT be used when there is only one algorithm or the variants never change, because the pattern adds classes and indirection for no benefit; a plain method call is then simpler. It also requires the client to understand the alternatives to make an informed choice, which is fine when selection is driven by configuration or input. Strategy combines naturally with other patterns: a Factory is often used to produce the correct strategy from configuration, and Strategy is the behavioral counterpart of the State pattern — State changes behavior automatically as internal state changes, whereas Strategy is chosen explicitly by the caller. The deciding question is whether the algorithm varies independently of the clients that use it; if it does, Strategy is the clean way to let both evolve independently.

7. Explain the Observer design pattern.
   - **Answer:** Observer is a behavioral pattern that establishes a one-to-many dependency between objects: when one object — the **subject** (also called the observable) — changes state, all its registered **observers** are notified and updated automatically. The problem it solves is tight coupling between the source of a change and the code that must react to it. Without Observer, the sensor code would have to know about every consumer — the alert service, the dashboard, the audit logger — and each new consumer would mean editing the sensor. Observer inverts that: the subject knows only the `Observer` interface and maintains a list of dependents, so consumers register and unregister without the subject knowing their concrete types. The structure has three participants: the **Subject**, which keeps the observer list and offers `attach(observer)` / `detach(observer)` and calls `notify()` when state changes; the **Observer** interface, declaring the `update()` method; and the **ConcreteObserver** classes, each implementing `update()` to react in its own way. A Java example: `public interface Observer { void update(double temperature); }`, `public class Subject { private final List<Observer> observers = new ArrayList<>(); private double temperature; public void attach(Observer o) { observers.add(o); } public void setTemperature(double t) { this.temperature = t; notifyObservers(); } private void notifyObservers() { for (Observer o : observers) o.update(temperature); } }`, and `public class AlertService implements Observer { public void update(double t) { if (t > 30) System.out.println("High temperature alert"); } }`. The pattern guarantees loose coupling: the subject and observers can evolve independently, observers are added at runtime, and the subject does not know what its observers do with the state. The main costs are that naive observers hold references that must be cleaned up (otherwise memory leaks), and notification order is generally unspecified. Java historically shipped `java.util.Observable` and `java.util.Observer`, but they were deprecated in Java 9 because the API leaked state, was awkward to use, and could not support events with clean typing. The pattern's conceptual descendants are everywhere: Swing/AWT event listeners and `EventListener` interfaces are observers; Spring publishes `ApplicationEvent` objects through `ApplicationEventPublisher` to registered `@EventListener` methods; and message-driven components, RxJava reactive streams, and publish-subscribe messaging systems are all the same idea pushed to larger scale. The distinction between Observer and publish-subscribe is one of infrastructure: classic Observer is in-process and synchronous — `notifyObservers()` blocks the subject until every observer finishes — while pub/sub usually routes through an intermediary broker that decouples producer and consumer across threads, processes, or machines, and often delivers asynchronously. A practical consideration is that synchronous notification can make the subject slow if an observer does heavy work; moving notification to a separate thread or queue is the standard remedy. Observer should be used when multiple unrelated parts of a system must react consistently to a state change, and should be avoided when the reaction is always the same — then a direct call or a simple listener suffices. It relates to the Mediator pattern (Mediator centralizes interactions, Observer decentralizes them) and is frequently combined with Strategy, since each observer may apply its own strategy when reacting to the notification.

8. Explain the Adapter design pattern.
   - **Answer:** Adapter is a structural pattern that lets two incompatible interfaces work together by converting one interface into the other. The problem it solves is integration: a client is written against one contract, while an existing class or third-party library exposes a different one, and neither side can be changed. Rather than modifying the vendor class or rewriting the client, the adapter sits between them, implementing the interface the client expects and delegating the actual work to the adaptee's own interface, translating calls as needed. The structure has four participants: the **Target** interface (the contract the client already uses), the **Adaptee** (the existing class with the incompatible interface), the **Client** (which calls through the Target), and the **Adapter**, which implements the Target and wraps or inherits from the Adaptee. There are two forms. The **object adapter** uses composition: the adapter holds an instance of the adaptee and forwards each call. This is generally preferred because it does not couple the adapter to a specific adaptee subclass, it works even when the adaptee is final, and it keeps the adapter's interface explicit. The **class adapter** uses inheritance — `class Adapter extends Adaptee implements Target` — which requires multiple inheritance in Java and is therefore only usable through a trick (extending one class and implementing the other), making the object adapter the idiomatic Java choice. A Java example of an object adapter: `public interface CustomerService { Customer getById(int id); }`, `public class LegacyCustomerClient { public Map<String,String> fetch(String id) { ... } }`, and `public class CustomerServiceAdapter implements CustomerService { private final LegacyCustomerClient client; public CustomerServiceAdapter(LegacyCustomerClient c) { this.client = c; } public Customer getById(int id) { Map<String,String> raw = client.fetch(String.valueOf(id)); return new Customer(raw.get("name")); } }`. The adapter pattern is pervasive in the JDK and frameworks: `Arrays.asList(T... a)` adapts an array into the `List` interface; `InputStreamReader` adapts an `InputStream` (bytes) to a `Reader` (chars); Spring's `MessageConverter` and `Adapter` interfaces bridge heterogeneous message formats, and logging-interface adapters like SLF4J bind to `log4j`, `java.util.logging`, or `logback` behind one API. Real-world use cases include bridging a legacy LDAP client into a modern `AuthenticationService` contract, making a third-party reporting library conform to an internal reporting interface, and uniting multiple vendors behind a single repository abstraction. Adapter should be used when the mismatch is purely an interface-conversion problem; it should NOT be used to wrap a class merely to rename methods for cosmetics, because that adds indirection without changing behavior. It is also important not to add behavior inside the adapter — that turns it into a Decorator, a different pattern with a different intent. Adapter is often confused with Facade: both wrap an existing class, but an Adapter changes the interface to *match* what the client expects, while a Facade *simplifies* a subsystem by exposing a reduced, higher-level API; an Adapter is usually one-on-one with a pre-existing contract, whereas a Facade is a deliberately new, convenience-oriented entry point. Adapter complements the Dependency Inversion principle: placing an adapter behind a stable interface lets high-level code depend on an abstraction while the concrete, foreign implementation remains swappable at the boundary.
