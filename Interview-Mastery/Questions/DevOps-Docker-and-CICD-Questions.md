## Answers

1. What is Git?
   - **Answer:** Git is a distributed version control system that tracks source code changes over time, enabling parallel collaboration, history audit, and rollback. Unlike centralized systems like SVN, every clone contains the full repository history, so work continues offline and every machine is a full backup. Files move between three states: working directory, staging area (index), and the local repository. Commits are content-addressed snapshots linked into a DAG of parent references, and branches are lightweight movable pointers into that graph. Git enables feature development on isolated branches, code review through pull requests, and safe reverts through `git revert` or `git reset`. The system is fast because operations like diffing and branching are local and do not require a server round-trip. Remote workflows synchronize commits through `push`, `pull`, and `fetch`, which makes distributed teams effective. Git also forms the backbone of modern CI/CD because pipeline triggers are typically tied to push, pull request, and tag events. Tagging releases, using `git blame` for accountability, and leveraging `git bisect` to locate the commit that introduced a regression are common advanced practices. Adopting a consistent branching and commit-message convention keeps history readable and supports automation. Overall, Git provides the safety net that makes continuous integration and frequent, small releases practical.

2. What is Git branch?
   - **Answer:** A Git branch is a movable pointer to a specific commit, representing an independent line of development that diverges from the main history. Branching allows multiple developers or features to evolve in parallel without interfering with each other, because each branch has its own working tree and commit sequence. When a commit is created on a branch, the pointer advances, and other branches remain untouched. The default branch (commonly `main` or `master`) represents the stable integration line, while feature branches isolate work until it is reviewed and merged. Branches are cheap to create and discard, encouraging short-lived branches for each logical change. Common workflows include GitFlow with long-lived `develop` and `release` branches, and trunk-based development with short-lived branches merged quickly into `main`. Good practice keeps feature branches short-lived to minimize merge conflicts and stale code. Once merged, branches are typically deleted to keep the repository tidy. Branch naming conventions such as `feature/`, `bugfix/`, and `hotfix/` make history self-describing. Branching is what makes Git suited to teams because work happens in isolation and integration is explicit, reviewable, and reversible.

3. Difference between merge and rebase.
   - **Answer:** Merge and rebase are two ways to integrate changes from one branch into another, and they differ fundamentally in how history is recorded. Merge creates a new merge commit that joins two histories, preserving the exact timeline and branch topology; this is non-destructive and shows exactly when integration happened. Rebase re-applies the commits of the current branch on top of the target branch, producing a linear history where the branch commits look like they were written after the target. Rebase rewrites commit metadata (new hashes, parents, timestamps) and can be forced through `git rebase --continue` after resolving conflicts at each replayed commit. The main benefit of merge is history preservation and safety on shared branches; the benefit of rebase is a clean, linear log that is easier to bisect and review. A common workflow merges or rebases `main` into a feature branch to keep it up to date, then creates a single merge (or squash merge) when integrating back. The golden rule is never to rebase a branch that others have based their own work on, because rewritten history breaks their references and forces force-pushes. Interactive rebase (`git rebase -i`) also enables squashing, reordering, and rephrasing local commits before sharing. Squash merges offer a middle ground: they keep a single integration commit while discarding granular history. Choosing between merge and rebase is a team policy decision, but both keep the working tree in the same state—only the recorded history differs.

4. What is pull request?
   - **Answer:** A pull request (PR) is a review mechanism that proposes merging changes from one branch into another, typically the main integration branch. It wraps the diff, its commit history, and metadata into a reviewable unit with description, comments, approvals, and status checks. PRs gate the main branch so that code is reviewed for correctness, style, security, and performance before it is merged. Modern PR tooling is tightly coupled with CI: every PR triggers a pipeline that runs tests, linting, and builds, and the merge is blocked until checks pass. Best practices include keeping PRs small and focused on a single concern, writing a clear description of the change and its motivation, and linking related issues or tickets. Reviewers look for logic errors, missing tests, edge cases, and unintended side effects, using inline comments for specific feedback. Requiring at least one approval, plus passing checks, provides the branch protection that maintains main-branch stability. Draft PRs allow early feedback while work is still in progress. Merging strategies—merge commit, squash, or rebase—are chosen by team convention. Beyond code review, PRs serve as a durable audit trail and a documented record of why each change was made, which is invaluable for on-boarding and debugging later.

5. How do you resolve merge conflict?
   - **Answer:** A merge conflict occurs when Git cannot automatically combine changes to the same lines of the same file from two branches, and it must be resolved manually. The resolution workflow starts by fetching and merging or rebasing the target branch into the feature branch so conflicts surface in the working tree. Git marks conflicting regions with conflict markers—`<<<<<<<`, `=======`, and `>>>>>>>`—showing the local version versus the incoming version. Each conflicting hunk must be edited to the correct final content, keeping the intended semantics rather than blindly combining both sides. Git diff or a merge tool with side-by-side comparison makes it easier to see which lines belong to which branch. After editing, `git add` marks files resolved, and the merge or rebase continues to completion. Any related callers, configuration, or tests must be updated to match the resolved logic, since conflicts often reveal coupled changes. Re-running the test suite after resolution is essential because conflict resolution can silently break behavior. If the conflict touches unfamiliar code, communicating with the other developer prevents misinterpretation of intent. To minimize future conflicts, teams keep branches short-lived, pull the target branch frequently, and make smaller, more focused changes. A clean, tested resolution is committed so the integration point stays green.

6. What is CI/CD?
   - **Answer:** CI/CD is the practice of automating the building, testing, and delivery of software through a pipeline that runs on every change. Continuous Integration (CI) means developers merge code into a shared branch frequently, where each merge triggers an automated build and test run, catching integration problems early. Continuous Delivery (CD) extends CI by automatically packaging the validated code and making it ready to deploy to any environment at the push of a button. Continuous Deployment goes further, automatically deploying every passing change to production without manual approval. A typical pipeline runs stages such as checkout, compile, unit tests, static analysis, integration tests, artifact build, image build, and deployment. CI provides fast feedback: a failed build stops the flow and is the team's top priority, since the main branch must stay green. CD removes error-prone manual release steps, making releases frequent, repeatable, and low-risk. Automation also produces a consistent audit trail of what was built, tested, and deployed, which simplifies troubleshooting and rollback. Environments (dev, staging, production) receive promotion only after the previous stage passes, so code proven in lower environments reaches production. CI/CD shifts the team's focus from "will this deploy?" to "shipping features," because the mechanical work is handled by the pipeline.

7. What is Jenkins?
   - **Answer:** Jenkins is an open-source automation server used to build, test, and deploy software through CI/CD pipelines. It runs as a standalone Java application and exposes a web UI plus a REST API for configuration and monitoring. Jobs can be defined as freestyle projects (web-configured steps) or, preferably, as pipelines-as-code using a Jenkinsfile committed to the repository. Pipelines are written either in declarative syntax with a structured `pipeline { }` block or in scripted Groovy for maximum flexibility. Jenkins supports master/agent architecture: the controller (master) schedules and orchestrates, while agents (nodes) execute jobs, enabling parallel builds and distributing load across machines. The plugin ecosystem is one of Jenkins' biggest strengths, providing hundreds of integrations for source control (Git), build tools (Maven, Gradle), containers (Docker), artifact repositories, and notification systems. Credentials such as SSH keys and registry tokens are stored in the credential store and referenced safely by ID. Build history, logs, test reports, and artifacts are retained for audit and debugging. Triggers range from SCM polling and webhooks to cron schedules, upstream job completion, and manual/parameterized execution. While newer tools like GitHub Actions and GitLab CI are cloud-native competitors, Jenkins remains widely used because it is self-hostable, free, extensible, and runs anywhere.

8. How do you create Jenkins pipeline?
   - **Answer:** A Jenkins pipeline is best created as a Jenkinsfile committed to the repository so that the definition itself is versioned, reviewed, and reproducible. Declarative pipelines use a `pipeline` block containing an agent, stages, and post sections. A minimal pipeline might check out code, build it, run tests, package an artifact, build a Docker image, and deploy. The `agent` directive selects where the job runs—e.g., `agent any`, a labeled node, or a Docker container. Stages are sequential by default but can use `parallel` to run independent work simultaneously, such as unit tests and static analysis. Environment variables and credentials are injected through the `environment` block and `credentials()` binding to keep secrets out of source. Parameters enable manual or parameterized runs, and triggers like `pollSCM`, `webhook`, or upstream `build` calls automate execution. The `post` section defines always/success/failure behavior such as archiving artifacts, sending notifications, and cleaning up the workspace. Build steps call external tools (`sh` on Unix, `bat` on Windows) or plugin steps, and failures propagate to mark the stage and build red. Stage views and logs make it clear exactly where a failure happened, and retained test reports provide a visual trend. Options like build-timeout, retries, and discard-old-builds make pipelines robust and keep the controller clean. Source-controlled Jenkinsfiles let infrastructure review and rollback apply to the pipeline itself.

9. What are Jenkins stages?
   - **Answer:** Stages are the logical building blocks of a Jenkins declarative pipeline that group related steps and make the pipeline's phases visible. Each stage is declared inside the `pipeline` block and typically represents one phase such as Checkout, Build, Test, Package, Deploy. Stages execute sequentially by default; parallel branches can be declared within a stage using the `parallel` directive to reduce wall-clock time. The stage view renders each stage as a block on the build status page, turning pipeline execution into a visual, color-coded timeline that is easy to scan. A typical pipeline might define Checkout, Compile, Unit Tests, Static Analysis, Docker Build, Docker Push, Deploy to Staging, Smoke Test, and Deploy to Production. Stages can gate progress: the pipeline stops at the first failing stage, and `input` steps can pause for manual approval—for example, before a production deploy. Each stage can use `when` conditions to run only for certain branches, tags, or parameter values. Failure messages, timestamps, and logs are scoped per stage, which pinpoints problems quickly. Stages can also share results by stashing files or recording artifacts between them. Good pipeline design keeps stages small, single-purpose, and quick to fail so feedback is fast and diagnosable.

10. How do you manage Jenkins credentials?
    - **Answer:** Secrets are managed through Jenkins' built-in credential store rather than hardcoded in pipelines or repository files. The store supports several kinds of credentials: username/password, SSH private keys, secret text, and certificate files. Credentials are stored encrypted in the controller's configuration and exposed to pipelines only through the `credentials()` binding or the `withCredentials` step. In a declarative pipeline, the environment block can map a credential ID to an environment variable, e.g., `DOCKER_PASSWORD = credentials('dockerhub-creds')`. Best practice limits credential scope to the jobs and folders that need them, and the `Manage Jenkins > Credentials` area lets admins control create/update/delete permissions. Sensitive values should never be printed to logs; the `maskPasswords` plugin and careful echo hygiene prevent leakage. Pipeline steps like `withCredentials([sshUserPrivateKey(...)])` make the key available only within the block's scope and scrub it from console output. SSH keys are preferred over passwords for automation because they support passphrases and fine-grained authorization. Separating non-sensitive configuration into environment variables keeps secrets out of the repo entirely. Credential rotation and periodic audits reduce the risk of stale or exposed tokens. Centralized secret management—whether in Jenkins, a Vault, or a cloud secrets manager—prevents the common failure of credentials committed to source control.

11. How do you deploy Spring Boot using Jenkins?
    - **Answer:** Deploying a Spring Boot application with Jenkins follows a pipeline that builds, packages, containerizes, and ships the artifact to the target runtime. The pipeline checks out the source, then runs a Maven or Gradle build that executes tests and produces the executable JAR. The JAR is placed into a Docker image built from a multi-stage Dockerfile: a builder stage compiles with the JDK and Maven, and the final stage runs the JAR on a slim JRE base to keep the image small. The image is tagged with the build number or commit SHA and pushed to a registry such as Docker Hub or an internal Artifactory/ECR. The deploy stage connects to the target host over SSH and pulls the new image, then restarts the container via `docker compose up -d` or `docker run`. Health verification after deploy runs a smoke test against an Actuator endpoint to confirm the application is actually serving traffic. Rolling back is simple because the registry retains prior tags and the host can restart the previous image. Environment-specific values such as datasource URLs and JWT secrets are injected as environment variables or secrets, not baked into the image. Automated deployment removes the risk of manually copying JARs and misconfiguring the runtime. For higher scale, the same image can be rolled out to ECS, Kubernetes, or a load-balanced fleet with the pipeline only changing the deploy plugin.

12. How did Jenkins reduce deployment time in your project?
    - **Answer:** The reduction in deployment time came from replacing a manual, error-prone release procedure with an automated, triggered pipeline. Previously, deployments required developers to build locally, transfer JARs to servers by hand, stop services, and restart them—each step subject to version mismatch, config drift, and human error. With Jenkins, a code push (webhook or SCM polling) automatically runs build, test, Docker image creation, push, and deployment, cutting the cycle from tens of minutes of hands-on work to a few minutes with zero human involvement. Automation also runs the exact same steps every time, so results are reproducible and consistent across environments. Parallel test and build stages compress the timeline further, while caching of dependencies and Docker layers avoids repeated work. Deployments become small and frequent rather than large and risky, because the friction of releasing drops dramatically. Failures happen earlier and more visibly: a broken build stops the pipeline before anything is deployed. When issues do occur, rollback is a single re-run against the previous image tag, which previously meant digging out an old artifact. The measurable outcome is shorter lead time from commit to production, higher release frequency, and fewer incidents caused by deployment mistakes.

13. What is Docker?
    - **Answer:** Docker is a platform for packaging applications and their dependencies into lightweight, isolated containers that run consistently on any host. A container is an OS-level virtualization mechanism: processes share the host kernel but are isolated via namespaces (process, network, PID, mount) and constrained by cgroups (CPU, memory, I/O). This isolation means a containerized application sees only its own filesystem, environment, and network, independent of what else runs on the host. Docker's components include the Docker Engine (client + daemon), images as immutable templates, registries for distributing images, and a network/volume layer for connectivity and persistent data. The developer experience is built around a Dockerfile, which declares how an image is assembled from base images and instructions. Docker solves the classic "works on my machine" problem because the container packages the runtime, libraries, and configuration alongside the code. It also improves resource utilization compared to virtual machines, since containers do not each carry a full guest operating system. Docker Compose orchestrates multi-container applications on a single host, while Kubernetes and Swarm extend orchestration to clusters. Common usage spans local development, CI pipelines, and production deployment, with the same artifact moving through every environment. For Linux-based workloads, Docker has become the de facto packaging and distribution standard.

14. Why use Docker?
    - **Answer:** Docker provides environment consistency, isolation, portability, and fast, repeatable delivery. Because the image contains the runtime and all dependencies, the same artifact runs identically on a developer laptop, a CI agent, and a production server, eliminating environment drift. Containers isolate applications from each other: each has its own filesystem, process tree, and network namespace, so a dependency upgrade in one service cannot break another. Startup and teardown are near-instantaneous because there is no guest OS to boot, which makes containers ideal for CI, horizontal scaling, and ephemeral workloads. The image registry workflow enables immutable releases: a built image is pushed once and pulled anywhere, and every tag is a reproducible, auditable artifact. Docker also simplifies toolchains—databases, message brokers, and caches run as single-command containers during development, removing manual installation. Resource efficiency is higher than VMs because containers share the host kernel and consume only what they need, allowing more services per host. Developers gain the ability to replicate production-like environments locally via Compose, reducing surprises at deploy time. Security improves through smaller images, non-root users, and immutable infrastructure practices. Overall, Docker makes software delivery faster, more consistent, and more portable across the entire lifecycle.

15. What is Docker image?
    - **Answer:** A Docker image is an immutable, read-only template that contains everything needed to run an application: code, runtime, libraries, environment variables, and configuration. Images are assembled from a Dockerfile where each instruction (FROM, RUN, COPY, ENV, CMD) creates a new layer on top of the previous one. Because layers are cached, unchanged instructions are reused in later builds, dramatically speeding up rebuilds when only the code changes. Images are built with `docker build` and stored either locally or in a registry (Docker Hub, ECR, GCR) from which they can be pulled by any Docker host. Every image has a unique digest, and tags like `latest`, version numbers, or commit SHAs provide named references to specific builds. Images are structured as a stack of layers in a union filesystem (overlayfs), so pulls and pushes transfer only changed layers. A single base image can be shared by many applications, saving disk and bandwidth because identical layers are deduplicated. Images are versioned and immutable once built, which makes them reliable release artifacts: the exact bytes that were tested are the exact bytes deployed. Building best practices—small base images, multi-stage builds, `.dockerignore`, and running as a non-root user—reduce size and attack surface. The image/container relationship is analogous to a class/object or template/instance: many containers can be created from one image, each with its own writable state.

16. What is Docker container?
    - **Answer:** A Docker container is a running instance of a Docker image—an isolated process (or set of processes) with its own filesystem, network stack, and process tree. When a container starts, Docker gives it a writable layer on top of the image's read-only layers, so writes never modify the image itself. Each container is isolated through Linux namespaces and resource-limited through cgroups, so it cannot see or exhaust the host's other processes. Containers are created, started, stopped, restarted, and removed through commands like `docker run`, `docker stop`, and `docker rm`. The container lifecycle is short and repeatable: since the image is the source of truth, a container can be discarded and recreated at any moment. Configuration flows into containers via environment variables, mounted files, and arguments rather than by editing files inside the running instance. Ports are published to the host with `-p host:container`, and containers on a user-defined network can discover each other by name. Health checks can be attached so the orchestrator or engine knows whether the container is actually serving traffic, not merely running. Container state intended to survive restarts must be stored in a volume, because the container's writable layer disappears with it. By running each service in its own container, teams get process-level isolation, predictable behavior, and a uniform operational model across all environments.

17. What is Dockerfile?
    - **Answer:** A Dockerfile is a text file containing the instructions that define how to build a Docker image. Each instruction—FROM, RUN, COPY, ADD, ENV, WORKDIR, EXPOSE, CMD, ENTRYPOINT—adds a layer and transforms the image being assembled. The FROM instruction selects the base image, which should be as small and minimal as the application allows (for example, `eclipse-temurin:17-jre-alpine` for a JVM app). RUN executes commands such as installing packages or compiling code, and COPY copies files from the build context into the image. Best practices include ordering instructions from least to most frequently changing so Docker's layer cache is reused, combining related RUN commands to reduce layers, and using `.dockerignore` to keep large unnecessary files out of the build context. A typical Spring Boot Dockerfile uses a multi-stage build: one stage with the JDK and Maven to compile and package, and a final stage that only copies the JAR onto a slim JRE, keeping the production image small. The CMD or ENTRYPOINT declares how the container starts, e.g., `ENTRYPOINT ["java", "-jar", "app.jar"]`. EXPOSE documents the port the app listens on, though the actual binding happens at run time. Metadata like LABEL and maintainer can be added for documentation and automation. The result is a declarative, versionable description of the runtime environment, turning infrastructure into code that is reviewed and tested like application code.

18. What is Docker Compose?
    - **Answer:** Docker Compose defines and runs multi-container applications from a single YAML file, replacing long chains of `docker run` commands. The compose file declares services, their images or builds, ports, volumes, environment variables, networks, dependencies, and restart policies. One `docker compose up` command starts all services in dependency order, and `docker compose down` tears them down, which makes local development of a microservice stack trivial. The `depends_on` field orders startup, though it only waits for the container to start, so applications should still retry connections to databases and brokers. Named volumes persist data across container recreation, and bind mounts enable live code reload during development. Compose creates a private network per project where services reach each other by service name, abstracting away IP addresses. Environment-specific settings can be layered through multiple override files (e.g., `docker-compose.override.yml`) or `.env` files for different contexts. Health checks in the compose file allow dependent services to wait for readiness and enable auto-restart of unhealthy containers. Compose works well for single-host production, but for multi-host and self-healing workloads Kubernetes becomes the next step. As a form of basic infrastructure as code, Compose makes the entire stack reproducible and reviewable in version control.

19. Difference between image and container.
    - **Answer:** An image is a static, immutable, read-only template, while a container is a live, mutable, running instance of that template. The image is the definition—code, runtime, dependencies, and default configuration—while the container is that definition in motion, with a process, an isolated filesystem, and its own network identity. Images are stored in registries, versioned with tags, and pulled once to start many containers; containers are ephemeral and created/destroyed freely. Multiple containers can run from the same image simultaneously, each with independent state because each gets its own writable layer. Changes made inside a running container do not affect the image or other containers derived from it. A useful analogy is the class/object pair: the image is the class, the container is an instantiated object. Another framing: the image is a recipe, and the container is the meal cooked from it. Images are identified by digest and tag, containers by ID and name. Deleting an image does not affect already-running containers, and stopping a container does not alter the image. The distinction matters operationally because it implies immutability of artifacts and reproducibility of runtime: build once, run anywhere, discard freely.

20. What is multi-stage Docker build?
    - **Answer:** A multi-stage build is a Dockerfile technique that uses multiple FROM statements to separate the build environment from the runtime environment. Each stage has its own base image and can have a name, e.g., `FROM maven:3.9-eclipse-temurin-17 AS build`. The first stage contains the heavy toolchain (compilers, build tools, package managers) and performs compilation and packaging, such as `mvn clean package`. Subsequent stages copy only the needed artifacts from earlier stages using `COPY --from=build`, so build tools never end up in the final image. This dramatically reduces image size—for a Spring Boot application, from a multi-hundred-MB full-JDK image to a ~150MB slim JRE image containing only the JAR. Smaller images pull faster, start quicker, and present a smaller attack surface because compilers and debuggers are excluded. Multi-stage builds also unify the build process: the same Dockerfile both compiles and packages, so CI does not need a separate compilation job. A canonical example: stage one builds the artifact with Maven, stage two runs it with `FROM eclipse-temurin:17-jre-alpine`, `COPY --from=build /target/app.jar app.jar`, and `ENTRYPOINT ["java", "-jar", "app.jar"]`. Intermediate stages are discarded at the end, though `--target` lets a developer build a specific stage for debugging. The technique keeps the pipeline simple, the artifact lean, and the production environment minimal.

21. How do you reduce Docker image size?
    - **Answer:** Image size is reduced primarily by using multi-stage builds, choosing small base images, and minimizing what is copied into the final image. The runtime stage should use a slim variant such as `eclipse-temurin:17-jre-alpine` instead of a full JDK image, since only the JRE is needed to run the JAR. Multi-stage builds keep compilers, build tools, and intermediate artifacts out of the final image by copying only the packaged artifact across stages. Combining related RUN commands (`RUN apt-get update && apt-get install -y ... && rm -rf /var/lib/apt/lists/*`) avoids orphaned layer caches and cleans package-manager state in the same layer. A `.dockerignore` file excludes logs, `.git`, `target`, and other unnecessary files from the build context, shrinking the context and preventing cache invalidation. Every RUN, COPY, or ADD instruction adds a layer, so consolidating instructions reduces layer count and metadata overhead. Distroless images provide an even smaller surface by omitting the shell and package manager entirely. Compressing the JAR with `-Djarmode=tools` (Spring Boot's layered-jar tool) or building native images with GraalVM can shrink Java artifacts substantially. Tools like `dive` analyze per-layer content and reveal files that were added then deleted but still occupy space. The measurable results are faster pulls, less storage cost, quicker cold starts, and a smaller attack surface, all of which matter in production.

22. How do you pass environment variables to Docker?
    - **Answer:** Environment variables are passed to containers through the Dockerfile, the CLI, or Compose, and they follow the 12-factor principle that configuration lives outside code. At build time, `ARG` declares build arguments and `ENV` sets defaults baked into the image. At run time, `docker run -e KEY=value` passes variables to the container process, and the `--env-file` flag reads many values from a file. In Docker Compose, the `environment` block sets variables directly and the `env_file` directive loads them from a file, while `$VAR` interpolation in the compose file pulls values from the host environment or a `.env` file. Sensitive values should come from secrets and credential stores rather than plain text in `environment` blocks. Spring Boot maps conventional env vars to properties automatically: `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, and `JWT_SECRET` override the corresponding `application.properties` entries without code changes. Injecting configuration this way keeps the image generic and environment-agnostic: the same image runs in dev, staging, and production with different variable sets. Secrets can be mounted as files or passed through Docker secrets and later referenced by the app. Best practice forbids baking secrets into images because images are distributed and auditable. The result is portable images whose behavior is fully controlled at deployment time, not build time.

23. How do you debug container startup failure?
    - **Answer:** Debugging a container that fails to start follows a systematic, top-down approach. The first step is `docker logs <container>` (or `docker compose logs`) to read stdout/stderr, where most failures announce themselves with an exception, a missing-config error, or a connection refused. Next, `docker inspect` shows the container's state, exit code, env, mounts, and network settings, revealing issues like a wrong entrypoint or a missing volume. If the container exits immediately, the exit code indicates the cause: 0 with a short run may mean the command finished, non-zero means the process crashed. Environment variables are a frequent culprit—a missing `SPRING_DATASOURCE_URL` or a wrong secret causes Spring Boot to fail during context initialization. Dependencies matter too: an application that starts before its database or broker is ready fails on connection, so retry logic or `depends_on` with health checks should be in place. The image itself can be inspected by running it with an overridden entrypoint, e.g., `docker run --entrypoint sh <image>`, to poke around without executing the app. Port conflicts on the host (`docker ps -a` to see existing binds) and exhausted resources (disk full, memory limits) also cause startup failures. For a non-running-but-alive container, `docker exec -it <container> sh` opens a shell for diagnostics like checking processes, network, and files. Health checks and startup logs aggregated in a log system make these symptoms visible before users are affected. A disciplined sequence of logs → inspect → environment → dependencies → host resources resolves the vast majority of startup failures.

24. What is logging in Docker?
    - **Answer:** Docker logging treats the container as a 12-factor application: it writes logs to stdout/stderr, and the logging driver collects and forwards those streams. The default `json-file` driver stores logs as JSON on the host and is what `docker logs` reads; it must be configured with rotation (`--log-opt max-size=10m --log-opt max-file=3`) so log files do not fill the disk. Other drivers forward logs to external systems: `syslog`, `fluentd`, `gelf` (Graylog), and `awslogs` (CloudWatch) allow centralized aggregation and retention. Centralized logging matters because containers are ephemeral—logs stored only inside a container disappear with it, so forwarding is essential for production. Applications should emit structured logs (JSON key/value) rather than free text so that aggregators can filter, search, and alert on fields. In Compose and orchestration, each service's logs are labeled by container/service, and tools like Loki or the ELK stack (Elasticsearch, Logstash, Kibana) provide queryable dashboards. Log rotation and retention policies prevent disk exhaustion on hosts and cost overruns in cloud log stores. Troubleshooting workflows start with `docker logs` for the most recent error, then pivot to the aggregated store for trends and correlation across services. Good practice also avoids logging secrets, tokens, or sensitive data, and uses log levels consistently (DEBUG/INFO/WARN/ERROR). The key principle is: applications write to stdout, infrastructure handles collection, retention, and search.

25. What is health check?
    - **Answer:** A health check verifies that a container is not just running but actually functioning, by periodically probing an endpoint or command. Docker supports a built-in `HEALTHCHECK` instruction in the Dockerfile or the `--health-cmd` run option, which returns `healthy`, `unhealthy`, or `starting` states. Compose and orchestrators can act on these states—restarting unhealthy containers, withholding traffic, or blocking dependent services until readiness is confirmed. For a Spring Boot application, the Actuator health endpoint (`/actuator/health`) exposes liveness and readiness separately: readiness reflects whether the app can serve requests (DB, messaging, external dependencies available), and liveness reflects whether the process is stuck or dead. The distinction matters because a process that is alive but unable to serve traffic should be removed from the load balancer, not killed and restarted in a crash loop. Orchestrators implement this with probes: Kubernetes `livenessProbe` restarts a deadlocked container, while `readinessProbe` gates traffic and `startupProbe` handles slow-starting applications. Health checks must test something real—an HTTP GET to the health endpoint or an actual dependency query—not merely process existence. Load balancers use the same endpoint to register and deregister instances, preventing requests from hitting a failing backend. Health checks enable automated self-healing, accurate scaling, and safer deployments because unhealthy nodes are detected and ejected quickly.

26. What is deployment rollback?
    - **Answer:** Deployment rollback is the process of reverting a running application to a previously known-good version after a deployment causes problems. Because modern releases are immutable artifacts—versioned images or JARs in a registry—rollback means redeploying the prior version rather than editing files on a live server. The mechanics depend on the strategy: for a containerized single host, pull the previous image tag and restart; for Kubernetes, `kubectl rollout undo` reverts a Deployment to the prior ReplicaSet; for blue-green, switch the router back to the still-running old environment. Speed matters: a fast, well-rehearsed rollback limits user impact and downtime. Rollback is safest when releases are backward-compatible at the data layer—if a migration changed the database schema irreversibly, the code cannot simply be reverted without a compensating fix. Versioning by unique tag or commit SHA ensures the exact previous artifact is recoverable and reproducible. Keeping the last N versions in the registry and automating the revert in the pipeline or runbook removes guesswork under pressure. Monitoring drives the decision: alerts on error rate, latency, or business metrics trigger rollback quickly rather than debugging in production. Combining strategies—blue-green for instant traffic switching, canary for measured rollout, and retained artifacts for full revert—creates a layered safety net. The goal is that a bad release degrades to a minor, quickly-recovered event rather than a long outage.

27. What is blue-green deployment?
    - **Answer:** Blue-green deployment runs two identical production environments—blue (current) and green (new)—and switches traffic between them. The new version is fully deployed and tested in the green environment while blue still serves users; when green passes verification, traffic is switched over, typically through a load balancer or router change. This makes deployment effectively an instant router flip, and the old environment stays warm for immediate rollback by switching traffic back. Downtime is limited to the traffic-switch moment, and the new version is validated against production-like conditions before any user traffic touches it. The main cost is infrastructure: two full environments must be provisioned, which is expensive at scale, though cloud environments can share the database if migrations are backward-compatible. Database changes are the tricky part—schema must work for both versions during the switch, or migration must be handled separately and carefully. Rollback is trivial and fast because the old environment is still running and untouched. Deployments become routine, frequent, and low-risk because each one is reversible. The strategy pairs well with infrastructure as code: both environments are defined and rebuilt from the same templates. For single hosts the concept can be approximated with multiple containers behind a proxy, but a load-balanced target group switch is the cleanest implementation.

28. What is canary deployment?
    - **Answer:** Canary deployment rolls out a new version gradually by routing a small percentage of traffic to it while the majority continues on the stable version. This is commonly implemented with weighted load balancing, where, for example, 10% of requests go to the new instances and 90% to the old ones. As the canary version is monitored—error rates, latency, throughput, and business metrics—the traffic share is increased in steps (10% → 25% → 50% → 100%) until the full rollout completes. If the canary shows elevated errors or degraded metrics, the rollout halts and traffic is redirected back to the stable version with minimal user impact. Canary deployments reduce the blast radius of a bad release, because only a small, monitored population is affected at any time. Unlike blue-green, no full duplicate environment is required; new instances can run alongside old ones within the same fleet. Success requires meaningful metrics and automated thresholds so the pipeline or operator knows when to progress or abort. Kubernetes supports this natively with multiple Deployments and traffic splitting via ingress/service mesh (e.g., Istio), while cloud load balancers offer weighted target groups. The technique is well suited to high-traffic systems where an untested edge case could otherwise reach every user. Canary is the most common gradual-release strategy because it combines safety, low cost, and empirical validation.

29. What is infrastructure as code?
    - **Answer:** Infrastructure as Code (IaC) manages infrastructure through versioned, reviewable configuration files instead of manual, click-driven setup. The core idea is that servers, networks, load balancers, databases, and security rules are defined declaratively, and a tool converges the real environment toward that definition. Terraform is a leading IaC tool: it uses HCL (HashiCorp Configuration Language) to declare resources like EC2 instances, VPCs, security groups, and RDS databases, then builds and applies a plan that shows exactly what will change. Configuration management tools like Ansible, Chef, and Puppet focus on configuring machines, while Terraform and CloudFormation focus on provisioning cloud resources; Docker Compose and Kubernetes manifests are container-level IaC. Benefits include repeatability (the same files produce the same environment), versioning and code review for infrastructure changes, auditability of who changed what, and elimination of configuration drift. Environments become reproducible: staging can be created and destroyed on demand, exactly mirroring production. Rollback of infrastructure changes is possible by reapplying a previous state. Idempotency and state management (Terraform's state file) let the tool track existing resources and make incremental, safe changes. Infrastructure as code converts provisioning from a fragile manual task into a fast, testable engineering process, enabling ephemeral environments and self-service provisioning.

30. What are common deployment issues?
    - **Answer:** Common deployment issues cluster around configuration, data, dependencies, resources, and verification. Environment-specific misconfiguration tops the list—missing or wrong environment variables, incorrect service URLs, or mismatched secrets between environments—so 12-factor configuration and secret management prevent most of them. Database schema mismatches break running applications when code expects columns that migrations have not yet added; backward-compatible, phased migrations and expand/contract patterns avoid this. Dependency version conflicts occur when the same library resolves differently between build and runtime, which containerized, immutable artifacts eliminate. Resource exhaustion—disk full from unrotated logs, memory leaks, or insufficient CPU—causes crashes and unhealthy instances, mitigated by log rotation, resource limits, and monitoring. Health check and load-balancer misconfiguration can route traffic to not-ready instances, producing intermittent errors. Deployment-tool failures themselves (SSH flakiness, registry outages, image pull failures) interrupt releases, so retries and idempotent deploy scripts are essential. Smoke tests that are too shallow let a broken app pass the pipeline and reach users; robust verification covers endpoints, critical user flows, and data paths. Race conditions during rollout—such as the new version serving before the database migration completes—cause transient failures. Each of these is addressed by a combination of immutable artifacts, configuration management, comprehensive tests, observability, and a rehearsed rollback procedure. The common thread is that most deployment incidents are preventable through automation, verification, and preparation.
