## Answers

1. What are Java 8 features?
   - **Answer:** Java 8 was a landmark release that shifted the language toward functional programming. Its headline feature is lambda expressions, which allow behavior to be passed as data and remove the ceremony of anonymous inner classes. Lambdas are built on functional interfaces such as `Predicate`, `Function`, `Consumer`, and `Supplier`, which are single-abstract-method contracts that the compiler can implement implicitly. The Stream API provides a declarative pipeline for processing collections — `filter`, `map`, `sorted`, `collect` — with lazy intermediate operations and eager terminal operations, plus built-in parallel support. `Optional` was introduced to model the possible absence of a value explicitly and reduce null-pointer exceptions. Default and static methods allow interfaces to carry implementations, which let the JDK add methods to existing interfaces like `Collection` without breaking every implementer. `CompletableFuture` brought a modern asynchronous programming model with chainable callbacks, replacing the limited `Future` interface. The new `java.time` API (`LocalDate`, `LocalDateTime`, `Instant`, `ZoneId`) replaced the mutable and error-prone `Date`/`Calendar` classes. Other additions include method references, `Collectors`, `StringJoiner`, and improvements to the `ConcurrentHashMap` and `CompletableFuture` infrastructure. Together these features promote a more declarative, immutable, and composable style of coding.

2. What is lambda expression?
   - **Answer:** A lambda expression is an anonymous function that can be passed around as a value and used where a functional interface is expected. Its syntax has three parts: a parameter list, an arrow (`->`), and a body that is either a single expression or a block of statements. For example, `(a, b) -> a + b` is a `BinaryOperator`, and `s -> s.length()` is a `Function`. The compiler infers the parameter types from the target type, so `(a, b) -> a + b` compiles as an `IntBinaryOperator` or a `BinaryOperator<Integer>` depending on context. Lambdas can capture variables from the enclosing scope, but only if those variables are effectively final — reassigning a captured variable is a compile error. Under the hood, lambdas are compiled with `invokedynamic` rather than creating a new class per lambda, which avoids the anonymous-class overhead and enables lambdas to be cached and reused. The key benefit is treating behavior as a first-class value: instead of writing a loop with branching logic, the logic is passed into a method such as `filter` or `map`. This enables functional composition and makes pipelines shorter and more readable. Lambdas can reference existing methods through method references (`Class::method`) for even more concise syntax.

3. What is functional interface?
   - **Answer:** A functional interface is an interface that declares exactly one abstract method. Because there is precisely one abstract method, a lambda or method reference can serve as its implementation, which is what makes lambdas type-safe. The `java.util.function` package provides the standard set: `Predicate<T>` (`test`), `Function<T,R>` (`apply`), `Consumer<T>` (`accept`), `Supplier<T>` (`get`), `UnaryOperator<T>`, `BinaryOperator<T>`, and primitive-specialized variants like `IntPredicate` and `ToIntFunction`. A functional interface may contain any number of default and static methods without losing its status, because those are not abstract. It may also redeclare methods from `Object` such as `equals`, `toString`, and `hashCode`; those do not count toward the single abstract method rule either. Custom functional interfaces can be defined with the `@FunctionalInterface` annotation to have the compiler verify the contract. A common use is defining a small callback contract: `@FunctionalInterface interface Validator<T> { boolean isValid(T input); }`, which can then be implemented inline. The practical consequence is that any API that accepts a functional interface can receive behavior instead of data, enabling the pluggable, composable design at the heart of the Stream API.

4. What is `@FunctionalInterface`?
   - **Answer:** `@FunctionalInterface` is an informational annotation that declares an interface is intended to be a functional interface — one with a single abstract method. It is optional, but when present the compiler enforces the rule: if more than one abstract method is declared, a compilation error results. The annotation also guards against accidental changes, because adding a second abstract method later will fail the build instead of silently breaking lambda usage. Some methods do not count toward the single abstract method requirement: default methods and static methods are concrete, and any abstract methods that redeclare public methods from `java.lang.Object` (like `equals`, `hashCode`, `toString`) are excluded. For example, `Comparator<T>` is annotated with `@FunctionalInterface` yet declares many default and static methods plus a single abstract `compare` method, and it also redeclares `equals`. The annotation communicates intent to other developers and to the compiler. Notable built-in examples are `Runnable`, `Callable`, `Comparator`, and the entire `java.util.function` package. Marking custom interfaces with `@FunctionalInterface` is best practice when the interface is designed to be implemented by a lambda. If the annotation is omitted, the interface still works as a functional interface, but the safety and clarity of the explicit contract are lost.

5. What is Stream API?
   - **Answer:** The Stream API processes sequences of elements declaratively through a pipeline of functional operations, replacing manual loops with `filter`, `map`, `sorted`, `reduce`, and `collect`. A stream pipeline consists of a source, zero or more intermediate operations, and one terminal operation. Sources include collections via `stream()`, arrays via `Arrays.stream`, ranges like `IntStream.range`, and the generators `Stream.iterate` and `Stream.generate`. Intermediate operations such as `filter`, `map`, `sorted`, and `distinct` return a new stream and are lazy; the terminal operation such as `collect`, `forEach`, or `count` triggers execution. Streams do not store data and never modify the source collection — they are a view over the data that produces results on demand. A stream can be traversed only once; after a terminal operation it is consumed and cannot be reused, requiring a new stream from the source. The `Collectors` utility provides `toList()`, `toMap()`, `groupingBy()`, `joining()`, and `partitioningBy()` for aggregating results. Because operations are composable and stateless by design, the same pipeline can run in parallel with `.parallelStream()`, letting the framework split work across threads. The API also supports primitive streams (`IntStream`, `LongStream`, `DoubleStream`) to avoid boxing. Overall, streams express the *what* of data processing while the runtime decides the *how*, making code shorter and less error-prone than imperative loops.

6. Difference between collection and stream.
   - **Answer:** A collection is an in-memory data structure that holds all its elements, whereas a stream is a sequence of values computed on demand and not stored anywhere. Collections are about *data*: they support direct access, iteration, and can be traversed multiple times. Streams are about *computation*: they describe operations on data and are consumed once after a terminal operation. Collections use external iteration — the client drives the loop with an iterator or enhanced for — while streams use internal iteration, where the pipeline decides how elements are pulled through. Because iteration is internal, the runtime can optimize by fusing operations and can easily parallelize execution; external loops cannot be parallelized without explicit thread management. A stream is lazy and may short-circuit, for example `limit(5)` stops producing elements once five are found, which a collection cannot do because it already holds everything. Streams do not store elements or modify the source; they produce a new result through `collect`. Collections provide random access (in the case of `List`) and are mutable, while streams are immutable views. In practice, a collection is the source of a stream and a stream produces a new collection or side effect as its result.

7. Difference between intermediate and terminal operations.
   - **Answer:** Intermediate operations return a new stream and are lazy, while terminal operations produce a result or side effect and trigger the actual execution. Examples of intermediate operations are `filter`, `map`, `flatMap`, `sorted`, `distinct`, `peek`, and `limit`. Examples of terminal operations are `collect`, `forEach`, `count`, `reduce`, `anyMatch`, `allMatch`, `noneMatch`, `findFirst`, and `findAny`. The crucial consequence is that a pipeline of intermediate operations does no work at all until a terminal operation is attached — building the pipeline is cheap, and executing it is what loops through the source. This laziness enables optimizations such as operation fusion, where `filter`, `map`, and `sorted` are combined into a single pass, and short-circuiting, where `findFirst` or `limit(3)` stops pulling elements as soon as the answer is known. Intermediate operations are composable and can be chained indefinitely, but only a terminal operation signals the end of the chain. Order matters: placing a cheap `filter` before an expensive `map` reduces the amount of work the `map` performs. A stream is considered consumed after a terminal operation executes and cannot be reused. `peek` is a debugging intermediate operation that performs an action on each element without ending the pipeline, unlike `forEach`, which is terminal.

8. What is lazy evaluation in streams?
   - **Answer:** Lazy evaluation means stream elements are processed only as needed and intermediate operations do not execute until a terminal operation demands results. When a pipeline like `stream.filter(...).map(...).sorted()` is constructed, nothing is computed; the operations are merely recorded. Execution begins only when `collect()`, `forEach()`, `count()`, or another terminal operation is called. This laziness is what allows infinite streams to exist — `Stream.iterate(1, n -> n * 2)` or `Stream.generate(Math::random)` are unbounded, but a terminal operation like `limit(5)` or `findFirst()` pulls only the needed elements and terminates. Laziness also enables short-circuiting: `anyMatch`, `findFirst`, and `limit` stop pulling elements the moment a result is produced, so a filter over millions of records may process only a few. Because the whole pipeline is known up front, the runtime can fuse intermediate operations into a single pass, avoiding multiple materialized intermediate collections that eager processing would create. Operation order directly affects performance under laziness — filtering first reduces the number of elements that reach downstream transformations. Streams are one-shot, so after the terminal operation consumes the stream, a fresh stream must be created from the source for further processing. Lazy evaluation is a core reason streams scale: cost is proportional to what is actually requested, not to the entire source.

9. Difference between `map()` and `flatMap()`.
   - **Answer:** `map` applies a function to each element and returns a stream of the same length where every element is transformed one-to-one; `flatMap` maps each element to a stream and then concatenates those streams, giving a one-to-many result. For example, `list.stream().map(String::toUpperCase)` changes each string, while `list.stream().flatMap(s -> Arrays.stream(s.split(" ")))` explodes each string into multiple words and flattens them into a single stream. Without `flatMap`, applying a function that returns a collection yields a `Stream<List<T>>`, a nested structure that requires a second flattening pass; `flatMap` does both in one operation. The transformation function of `flatMap` must return a stream (`Stream<R>`), and the runtime merges all produced streams in encounter order. `flatMap` is also the standard way to flatten nested collections: `List<List<Integer>>` can become `Stream<Integer>` with `listOfLists.stream().flatMap(List::stream)`. The same idea appears in `Optional`: `Optional.flatMap` chains an operation that itself returns an `Optional`, preventing the nested `Optional<Optional<T>>` that `map` would create. In `CompletableFuture`, `thenCompose` is the async equivalent of `flatMap` and `thenApply` of `map`. In short, `map` transforms the shape of each element, while `flatMap` both transforms and collapses a level of nesting.

10. Difference between `filter()` and `map()`.
    - **Answer:** `filter` is a selection operation that retains or discards elements based on a `Predicate`, leaving the elements themselves unchanged; `map` is a transformation operation that converts every element into something else using a `Function`. `filter` narrows the stream — `numbers.filter(n -> n > 0)` keeps only positive numbers, and the element type does not change. `map` changes the element type and the stream length stays the same — `names.map(String::length)` produces a `Stream<Integer>`. The two are frequently combined, and the idiomatic pattern is to `filter` before `map` so the more expensive transformation runs only on the elements that survive. For example, filtering valid records and then mapping them to DTOs avoids constructing DTOs for discarded elements. `filter` works with a predicate that returns `true` for kept elements, while `map` works with a function that returns the new element; neither is a substitute for the other. In terms of short-circuiting, `filter` participates in lazy evaluation — an early `findFirst` after a filter may examine very few elements. `map` is commonly used for DTO conversion, field extraction, or applying formatting, while `filter` is used for validation and preconditions. Both are intermediate operations and can be chained any number of times.

11. Difference between `findFirst()` and `findAny()`.
    - **Answer:** `findFirst` returns the first element of the stream in encounter order, while `findAny` returns any element without guaranteeing which one. In a sequential stream both behave identically for ordered sources, so the difference is invisible there; the distinction matters for parallel streams. `findAny` is optimized for parallelism because it does not enforce ordering — any thread that locates a match can complete immediately, which minimizes coordination. `findFirst`, by contrast, must respect encounter order, which may require waiting for earlier segments to be processed even if a match is found later, adding overhead in parallel execution. Encounter order depends on the source: a `List` has a defined order, a `HashSet` does not, and `sorted()` or `distinct()` can establish or disturb ordering. Both operations return an `Optional`, and both are short-circuiting terminal operations — they stop pulling elements once a result is produced. If the stream is empty, both return an empty `Optional`, typically handled with `orElseThrow`, `orElse`, or `ifPresent`. A practical rule is to use `findFirst` when the earliest match matters (earliest alert, first record) and `findAny` when any valid match is acceptable. For most sequential code, either works; for parallel pipelines, `findAny` is the better performer.

12. Difference between sequential and parallel streams.
    - **Answer:** A sequential stream processes elements one at a time in a single thread, whereas a parallel stream splits the source into chunks and processes them concurrently using a shared `ForkJoinPool`. Parallelism is enabled simply by calling `.parallelStream()` or `.parallel()`, and the framework handles splitting via the `Spliterator`, scheduling sub-tasks onto worker threads, and recombining results. The runtime automatically merges results, so the pipeline code is identical regardless of mode — the API hides the concurrency. Parallel streams shine on large datasets with CPU-intensive, stateless operations where the parallelization gain outweighs splitting and coordination overhead. They are counterproductive for small datasets, for I/O-bound work where threads mostly wait, and for stateful operations like `sorted()` or `distinct()` that require buffering and merging ordered results. Correctness is also at risk: lambdas that mutate shared state or capture non-thread-safe objects behave differently in parallel mode and can corrupt data. The common pool is shared across the whole JVM, so a long-running parallel stream can starve other tasks; a custom `ForkJoinPool` can isolate workloads. In practice the decision is empirical — the data must be large (typically well over a hundred thousand elements) and the operation CPU-bound for a parallel stream to pay off. A sequential stream has deterministic ordering and low overhead and remains the default choice unless measurement justifies parallelism.

13. When should you avoid parallel streams?
    - **Answer:** Parallel streams should be avoided when the dataset is small, because the cost of splitting the source, scheduling sub-tasks, and merging results can exceed the savings — the work per element is not enough to amortize the coordination overhead. They should also be avoided for I/O-bound operations like database queries, HTTP calls, or file access, because parallel threads spend most of their time blocked, and increasing concurrency does not reduce latency and can saturate the underlying resource. Operations that depend on shared mutable state are unsafe in parallel: lambdas that increment a shared counter or add to a shared list introduce data races that a sequential stream never has. Streams with expensive ordering requirements — `sorted()`, `distinct()`, or those relying on encounter order for `findFirst` — incur additional merge costs in parallel mode. Tasks that are inherently sequential or that have a fixed common pool (the shared `ForkJoinPool`) risk starving other parts of the application. Operations with very small per-element work benefit little even on large inputs, since thread switching and contention eat the gains. If the ordering of results matters and cannot tolerate reordering, parallel adds no value. The correct approach is to benchmark with representative data and use parallel streams only when a measurable speedup is observed and the operations are stateless, independent, and CPU-bound.

14. What is `Optional`?
    - **Answer:** `Optional` is a container object that either holds a non-null value or is empty, used to explicitly model the possible absence of a result and to avoid null-pointer exceptions. Its purpose is to force callers to acknowledge and handle the empty case instead of silently dereferencing null. `Optional` is intended primarily as a *return type* for methods that may not produce a value — for example, a repository method that might find no record; it is discouraged for fields, method parameters, and collections. An `Optional` is created with `Optional.of(value)` (throws if null), `Optional.ofNullable(value)`, or `Optional.empty()`. The API provides safe consumption methods: `ifPresent` performs an action only when a value exists, `orElse` and `orElseGet` supply fallback values, and `orElseThrow` throws a specified exception when empty. Functional transformation is supported through `map`, which transforms a present value while preserving emptiness, and `flatMap`, which chains operations that themselves return `Optional` without nesting. `filter` keeps the value only if it satisfies a predicate. Chaining is the real strength: `repo.findById(id).map(User::getEmail).map(String::toLowerCase).orElse("unknown")` handles absence at every step without explicit null checks. `Optional` does not replace null — it is a convention that makes the contract visible and forces correct handling.

15. Why should we not use `Optional.get()` directly?
    - **Answer:** `Optional.get()` throws `NoSuchElementException` if the `Optional` is empty, which defeats the entire purpose of using `Optional` in the first place. Calling `get()` without a guard reintroduces the same class of runtime failure that `Optional` was designed to prevent, except the failure is now a misleading exception at the call site rather than a null pointer. The safe alternatives encode the empty case explicitly: `orElse(defaultValue)` returns a fallback, `orElseGet(supplier)` computes a fallback lazily, and `orElseThrow(() -> new NotFoundException(...))` raises a domain-meaningful exception. The classic anti-pattern `if (optional.isPresent()) { return optional.get(); }` should be replaced with `optional.orElse(...)`, `optional.map(...).orElse(...)`, or `ifPresent`. Using `orElseThrow` conveys intent better: it states that a missing value is an error and should surface as an exception with context, rather than a bare `NoSuchElementException`. `get()` also signals nothing about how emptiness should be handled, so it makes code review harder and encourages hidden assumptions. Static analysis tools and IDEs typically flag direct calls to `get()` on an `Optional` as a code-smell warning. In short, every legitimate use of `Optional` has a method that expresses the intended behavior; `get()` is only safe after an `isPresent()` check, and even then those two calls are better replaced by a single `orElseThrow`.

16. Difference between `orElse()` and `orElseGet()`.
    - **Answer:** `orElse` eagerly evaluates its argument even when the `Optional` is present, whereas `orElseGet` accepts a `Supplier` whose body runs only when the `Optional` is empty. The difference is best seen with a method call: `optional.orElse(computeDefault())` invokes `computeDefault()` unconditionally, wasting work on every call where a value already exists; `optional.orElseGet(() -> computeDefault())` invokes the method only when the value is missing. For cheap or constant fallbacks — `orElse("N/A")` — the eager form is fine and idiomatic. The eager form becomes a bug when the default is expensive: building a large object, hitting a database, or calling a remote service inside `orElse` executes on every invocation regardless of need. `orElseGet` is the correct choice whenever the fallback involves computation, I/O, or object creation, and it is also the form that avoids eager evaluation surprises during debugging. The two return the same value when the `Optional` is empty; they differ only in when the fallback is produced. A related method, `orElseThrow`, takes a `Supplier` for the exception and is the right tool when an empty value should raise an error rather than fall back. Choosing between them is a matter of cost: constant values go to `orElse`, anything computed goes to `orElseGet`.

17. What are method references?
    - **Answer:** A method reference is a compact lambda that refers to an existing method by name, using the syntax `ClassName::methodName`, and it can be used anywhere a lambda or functional interface is expected. There are four categories. A static method reference, `Integer::parseInt`, is equivalent to `s -> Integer.parseInt(s)`. A bound instance method reference, `logger::info`, calls a method on a captured object. An unbound instance method reference, `String::toUpperCase`, uses an element of the stream as the receiver, equivalent to `s -> s.toUpperCase()`. A constructor reference, `ArrayList::new` or `Employee::new`, supplies the constructor matching the functional interface's signature. Method references are particularly common inside stream pipelines: `.map(String::trim)`, `.filter(Objects::nonNull)`, `.map(User::getEmail)`, and `.forEach(System.out::println)`. Constructor references appear with `Collectors.toList()`-style factories or when mapping entities to DTOs. The compiler infers the target type from context, so the referenced method must match the expected signature and return type. Method references are generally more concise and readable than equivalent lambdas, and they can be extracted from existing utility methods to encourage reuse. They are not a separate feature but a syntactic shorthand: anything written as a method reference can be written as a lambda, so the choice is purely about clarity.

18. What are default methods?
    - **Answer:** Default methods let an interface provide a concrete implementation for a method, marked with the `default` keyword, so implementing classes inherit behavior without being forced to override it. They were introduced in Java 8 primarily to let the JDK evolve: adding `forEach` to `Collection` and `stream()` to the `Collection` hierarchy would otherwise have broken every existing implementation, but default methods made the additions backward compatible. A class that implements an interface can use the default implementation as-is or override it. Conflict resolution follows fixed rules: a class's own method wins over any interface default, a more specific interface wins over a more general one, and if two unrelated interfaces both provide a default for the same signature, the implementing class must override the method to disambiguate (or the code will not compile). This creates a potential diamond-problem where a class inherits conflicting defaults from different branches of an interface hierarchy; Java resolves it deterministically rather than allowing ambiguous resolution. Default methods are also what allow functional interfaces to accumulate convenience methods — `Comparator` has many default methods like `reversed()` and `thenComparing()` while keeping its single abstract method. Static methods in interfaces are related but belong to the interface itself, not to instances. Default methods are a tool for API evolution and trait-like composition, letting shared behavior live in interfaces without forcing it on implementers.

19. What is `CompletableFuture`?
    - **Answer:** `CompletableFuture` is a `Future` that can be completed explicitly and supports building complex asynchronous pipelines through chained callbacks. Unlike the plain `Future`, whose only operation is a blocking `get()`, a `CompletableFuture` registers callbacks that run when the task finishes, so the calling thread never blocks. Async tasks are created with `supplyAsync(() -> result)` for a value-producing task or `runAsync(() -> { ... })` for a side effect, and both can take a custom `Executor` to control the thread pool. Completion is decoupled from the task: `complete(value)` and `completeExceptionally(ex)` let another thread finish the future, which is how async APIs integrate. Dependent stages are composed with `thenApply` (transform result), `thenCompose` (chain to another async task), `thenAccept` (consume result), `thenRun` (run after completion), and `thenCombine`/`allOf`/`anyOf` for combining multiple futures. Error handling is part of the model: `exceptionally`, `handle`, and `whenComplete` recover from or observe failures, and exceptions propagate through the chain automatically. Each stage is itself a `CompletableFuture`, so composition is uniform and nesting is avoided by design. The main advantage over callbacks is readability — an asynchronous sequence reads top-down instead of nesting. A common pattern is gathering data from several independent services with `allOf` plus `join()`, or fan-out/fan-in processing. `CompletableFuture` is a foundation of non-blocking and reactive-style programs in plain Java.

20. Difference between `thenApply()` and `thenCompose()`.
    - **Answer:** `thenApply` transforms the result of a `CompletableFuture` with a function and returns a new future holding the transformed value, while `thenCompose` takes a function that itself returns a `CompletableFuture` and flattens it, so the result is a single future, not a nested one. The distinction is analogous to `map` vs `flatMap` in streams: if the function passed to `thenApply` returns a `CompletableFuture`, the result is `CompletableFuture<CompletableFuture<T>>`, a nested future that requires an extra `thenCompose` or `join` to unwrap. `thenCompose` avoids this nesting because it expects the function to return a future and merges the outer and inner futures into one. The practical difference is about dependency: `thenApply` is for synchronous transformation of an already-produced value, while `thenCompose` is for chaining a second asynchronous operation that depends on the first result. For example, after fetching a user, looking up the user's orders is an async call, so `thenCompose(user -> orderService.getOrders(user.getId()))` produces a `CompletableFuture<List<Order>>` directly. Using `thenApply` for that same chained call would yield a nested future and an extra unwrapping step. `thenCompose` is the tool that keeps asynchronous chains flat and readable, preventing callback-style nesting. It is sometimes described as the async version of `flatMap` — map, then flatten.

21. Difference between `thenApply()` and `thenAccept()`.
    - **Answer:** `thenApply` takes a `Function` that transforms the future's result into a new value and returns a `CompletableFuture` holding that value; `thenAccept` takes a `Consumer` that processes the result but returns nothing, so it yields a `CompletableFuture<Void>`. The choice comes down to whether the stage produces a value to continue the chain or performs a side effect. `thenApply` is used when the result feeds another stage: `future.thenApply(order -> order.total())` produces a future of the total. `thenAccept` is used at the end of a chain for side effects such as writing to a log, updating a cache, or sending a notification: `future.thenAccept(order -> emailService.send(order))`. Because `thenAccept` returns `CompletableFuture<Void>`, it is usually a terminal stage, and attempting to transform its result afterwards loses the value. There is a third variant, `thenRun`, which takes a `Runnable` and ignores the result entirely — used when only completion matters, not the value. All three inherit the thread pool semantics: without an explicit executor, they run on the thread that completed the future (or the common pool). Exception handling still applies: if an upstream stage failed, `thenAccept` runs nothing and the exception propagates to downstream handlers. In summary, `thenApply` continues the data flow, `thenAccept` consumes the data and stops the flow.

22. How do you handle exceptions in `CompletableFuture`?
    - **Answer:** Exceptions in a `CompletableFuture` are propagated along the chain: when one stage fails, all dependent stages are skipped and the exception flows to the nearest exception handler. The recovery method is `exceptionally`, which takes a `Function<Throwable, T>` and converts a failure into a fallback value, effectively recovering the chain. For example, `future.exceptionally(ex -> 0)` turns a failed fetch into a default result. `handle` is a stronger variant: its function receives both the result (or null) and the throwable, and it runs in all cases, letting the code either recover, transform, or rethrow. `whenComplete` observes the outcome with a `BiConsumer` for side effects like logging or cleanup but does not modify the result, and it passes the original outcome through. To fail a future explicitly, `completeExceptionally(ex)` marks it failed so downstream handlers react — this is how async APIs surface errors. The exception object given to `exceptionally` and `handle` is the cause that triggered the failure, and it can be rethrown after logging if recovery is not appropriate. Unchecked exceptions thrown inside callbacks are captured by the future machinery rather than crashing the calling thread, which makes silent failures possible unless handlers are attached. A robust pattern is combining `whenComplete` for logging with `exceptionally` for fallback, or using `handle` when both success and failure need a unified result. There is no checked-exception support, so checked exceptions must be wrapped in unchecked ones when working inside `supplyAsync` or callback lambdas.

23. What is Java Date and Time API?
    - **Answer:** The Date and Time API in `java.time`, introduced in Java 8 and based on Joda-Time, provides a comprehensive model of dates, times, and instants built on immutable, thread-safe value classes. It replaced the legacy `java.util.Date`, `Calendar`, and `SimpleDateFormat`, which were mutable, confusingly indexed (January was month 0), and not thread-safe. The core classes are `LocalDate` (a calendar date), `LocalTime` (a time without date or zone), `LocalDateTime` (both, without a zone), `ZonedDateTime` (with a zone and full daylight-saving rules), `Instant` (a UTC point on the timeline), `OffsetDateTime`/`OffsetTime` (with a fixed offset), and `Duration`/`Period` for measuring elapsed time. Every operation returns a new instance instead of mutating, which removes an entire class of concurrency bugs. Formatting and parsing use the thread-safe `DateTimeFormatter` with patterns or predefined formats, replacing `SimpleDateFormat`. Time-zone handling is centralized in `ZoneId` and `ZoneOffset`, with `ZonedDateTime` applying daylight-saving transitions automatically. `TemporalAdjusters` provides convenient adjustments like "next working day" or "last day of month". Chaining is natural: `date.plusMonths(2).minusDays(5)` reads as a sentence and returns a new value. The API also supports comparison (`isAfter`, `isBefore`), conversion to and from legacy types via `toInstant()` and `Date.from(...)`, and works cleanly with modern database drivers and JSON libraries. It is now the standard choice for any date and time modeling.

24. Difference between `LocalDateTime`, `ZonedDateTime`, and `Instant`.
    - **Answer:** `Instant` is a single point on the UTC timeline — a count of seconds and nanoseconds since the epoch — with no notion of calendar, so it is the right type for timestamps that must be comparable across time zones. `LocalDateTime` is a date plus time with no time-zone information at all; it describes "2026-08-13T10:30" but does not say where that time is, so it cannot be converted to an `Instant` without a zone. `ZonedDateTime` is a date, time, zone, and the offset rules for that zone — including daylight-saving transitions — so it fully identifies a moment in a specific region. The practical rule: store and transmit timestamps as `Instant` (or as `OffsetDateTime` UTC), and use `ZonedDateTime` for display in a user's local zone, because it knows about DST shifts. `LocalDateTime` should not be stored or compared globally because the same value means different instants in different zones; it suits local, zone-less contexts like scheduling logic that is time-zone agnostic. Conversions are explicit: `instant.atZone(ZoneId.of("Asia/Kolkata"))` produces a `ZonedDateTime`, `zonedDateTime.toInstant()` produces an `Instant`, and `localDateTime.atZone(zone)` is required before any instant conversion. `ZonedDateTime` correctly handles ambiguous times around DST fall-back and gaps in spring-forward, whereas arithmetic on `LocalDateTime` ignores such transitions. `OffsetDateTime` is a lighter alternative to `ZonedDateTime`: it carries a fixed offset but no zone rules, useful for APIs that must send an explicit offset.

25. What are records in Java?
    - **Answer:** A record is a concise, immutable data carrier that declares data as a list of components and gets the constructor, accessors, `equals`, `hashCode`, and `toString` generated by the compiler. Introduced as a preview in Java 14 and finalized in Java 16, it is written as `record Point(int x, int y) {}` and replaces verbose POJOs that only hold data. Records are implicitly final, extend `java.lang.Record`, and their fields are private and final, so instances cannot be mutated after creation. The generated accessors match the component names — `point.x()` rather than `getX()` — and the canonical constructor validates and assigns every component. A compact constructor can add validation without redeclaring the parameter list: `record Employee(String name, double salary) { Employee { if (salary < 0) throw new IllegalArgumentException(...); } }`. Extra static methods, instance methods, and even a custom accessor can be added, but no additional instance fields beyond the components. Because `equals` and `hashCode` are derived from the components, records are ideal as map keys, DTOs, and immutable value objects. Pattern matching works naturally with records, allowing deconstruction via type patterns in `instanceof` and switch. Records are serializable, though mutable serialization concerns exist and a record's serialized form binds to its components. Records have limitations — they are final, cannot extend a class, and their absence of a no-arg constructor complicates JPA entity use, so they are best suited for DTOs and transfer objects rather than ORM-managed entities.

26. What are sealed classes?
    - **Answer:** Sealed classes restrict which other classes or interfaces may extend or implement them, giving controlled, exhaustive inheritance. A sealed class declares its permitted subtypes in a `permits` clause: `sealed interface Shape permits Circle, Rectangle, Triangle`. Every permitted type must be in the same module or the same package, and each must declare itself `final`, `sealed`, or `non-sealed`. `final` ends the hierarchy for that subtype, `sealed` continues the restriction, and `non-sealed` reopens the hierarchy to arbitrary subclassing. Sealing is finalized in Java 17 and works for classes and interfaces. The main benefit is domain modeling: when the set of possible variants is fixed, sealing encodes that constraint in the type system instead of relying on convention. Combined with pattern matching, sealed types enable exhaustive switches — the compiler verifies that every permitted subtype is covered, so adding a new variant forces all switches to be updated and missing cases become compile errors rather than runtime surprises. This is ideal for modeling domain events, algebraic data types, and result hierarchies like `sealed interface Result permits Success, Failure`. Sealed classes communicate intent to future maintainers that new subtypes must be deliberate and explicit. They also enable more precise analysis by the JIT and provide a middle ground between `final` classes (no extension) and open classes (unlimited extension).

27. What is pattern matching?
    - **Answer:** Pattern matching lets a single construct both test a value's type and bind a variable, combining the classic `instanceof` check and cast into one step. In Java 16+, `if (obj instanceof String s)` checks the type and, if it matches, declares `s` already cast to `String`, eliminating the separate cast line and its scope pitfalls. The pattern variable is in scope only where the type is guaranteed, which the compiler enforces — using `s` after the `if` block outside the negated branch is a compile error. From Java 17, pattern matching extends to switch: `switch (obj) { case String s -> s.length(); case Integer i -> i + 1; default -> 0; }`, and with switch expressions this becomes an expression returning a value. Guard conditions can refine a pattern: `case String s when s.length() > 5 -> ...`. Record patterns (Java 19+) deconstruct records in the match itself: `case Point(int x, int y) -> ...` binds the components. Combined with sealed classes, switch patterns can be exhaustive, so the compiler checks that every subtype is handled and the `default` branch becomes optional. The result is dramatically less boilerplate than chains of `instanceof`/cast/`else` and fewer opportunities for `ClassCastException`. Pattern matching is being incrementally enhanced across Java versions and is a cornerstone of the modern, declarative style.

28. What are switch expressions?
    - **Answer:** A switch expression is a form of `switch` that yields a value and can be assigned, introduced as a standard feature in Java 14. The arrow syntax `case X -> value` replaces the colon, `break`, and fall-through of the old statement form; with arrows, only the matched arm executes and no fall-through occurs. Each arm can produce a value either directly or through a block that ends with `yield`: `case SUCCESS -> 200; case ERROR -> { log(...); yield 500; }`. Because every arm produces a value, the compiler requires the expression to be exhaustive — every possible value must be covered or a `default` provided, otherwise it will not compile. The statement form of `switch` is still valid but no longer needed in most cases. Since Java 17, switch expressions also support pattern matching: `case String s when s.length() > 10 -> "long"; case Integer n -> "number";`, which is evaluated top-down. They are particularly useful for mapping enums to values or behaviors, replacing multi-branch if-else chains. The exhaustiveness rule is a safety improvement: the compiler enforces completeness for enums and sealed types, so adding an enum constant breaks the build until all switches are updated. Overall, switch expressions turn a statement-oriented, error-prone construct into a clean, value-oriented expression.

29. What are text blocks?
    - **Answer:** A text block is a multi-line string literal delimited by three double quotes (`"""`), finalized as a standard feature in Java 15. It lets developers write strings that span lines exactly as they appear in source, without concatenation operators or `\n` escape sequences. For example:
    ```java
    String json = """
        {
          "name": "employee",
          "active": true
        }
        """;
    ```
    The opening delimiter is followed by a newline, and incidental leading whitespace is stripped automatically based on the indentation of the closing delimiter, so the block aligns with the surrounding code while the content keeps its relative indentation. This makes SQL, JSON, HTML, XML, and regex far more readable than escaped single-line strings. Escape sequences still work inside text blocks — `\n`, `\"`, and `\\` — and Java 15 added `\` (line continuation) and `\s` (explicit space) for finer control. A text block is a regular `String`, so all `String` methods, `String.format`, and comparisons behave normally. Text blocks do not support runtime interpolation like Python's f-strings; formatting is done with `String.format` or `StringBuilder`. They remove the two biggest maintenance pains of multi-line content in code: unreadable escape soup and concatenation errors. The compiler strips trailing whitespace on each line, keeping the content clean. Text blocks are the idiomatic way to embed structured text in Java source.

30. What are virtual threads?
    - **Answer:** Virtual threads are lightweight threads introduced in Java 21 (Project Loom) that are managed by the JVM rather than the operating system, enabling applications to create millions of concurrent tasks at a fraction of the memory cost of platform threads. A platform thread is backed by an OS thread with a large stack, and each costs on the order of a megabyte, limiting an application to a few thousand. A virtual thread is scheduled by the JVM on a small set of platform threads (the carrier threads), and it blocks efficiently: when a virtual thread performs a blocking operation such as I/O or `synchronized` waiting, the JVM unmounts it and runs another one on the same carrier thread, so blocking no longer wastes an OS thread. This makes the thread-per-request model viable again — each request can be handled by a virtual thread without the traditional thread pool sizing and backpressure gymnastics. Virtual threads are created with `Thread.ofVirtual()`, `Executors.newVirtualThreadPerTaskExecutor()`, or by running a `Callable` directly, and they integrate with existing code because they are instances of `Thread`. The rule of thumb is to use virtual threads for I/O-bound work with many concurrent tasks and to keep platform threads (or CPU-bound parallelism via the common pool) for CPU-intensive computation that would not benefit from blocking-style concurrency. `synchronized` blocks can pin the carrier thread, a known caveat that is being improved; other limitations include no `Thread.stop`, and careful use with thread-local variables because millions of threads multiply their cost. Virtual threads preserve the familiar blocking programming model while achieving the scalability of reactive or async approaches.

31. Given a `List<Employee>` where each employee has Name, ID, Salary, and Experience, filter employees based on experience and salary criteria, then print the results in ascending or descending order. Write the Java code.
    - **Answer:** This can be solved declaratively with the Stream API: `filter` selects elements matching the criteria, `sorted` orders them with a `Comparator`, and a terminal `collect` or `forEach` produces the output. Below, the pipeline keeps employees with at least five years of experience and a salary greater than 50,000, sorts them by salary in ascending order, and prints each one. Assume `Employee` is a class with accessors `getName()`, `getId()`, `getSalary()`, and `getExperience()`.
    ```java
    import java.util.Comparator;
    import java.util.List;
    import java.util.stream.Collectors;

    List<Employee> result = employees.stream()
        .filter(e -> e.getExperience() >= 5)          // keep experienced employees
        .filter(e -> e.getSalary() > 50000)           // keep higher-paid employees
        .sorted(Comparator.comparing(Employee::getSalary)) // ascending by salary
        .collect(Collectors.toList());                // terminal operation

    result.forEach(System.out::println);              // print each employee
    ```
    The two `filter` calls can be combined into a single predicate for marginally less overhead: `filter(e -> e.getExperience() >= 5 && e.getSalary() > 50000)`. For descending order, reverse the comparator: `.sorted(Comparator.comparing(Employee::getSalary).reversed())`, and since salary is a double, `Comparator.comparingDouble(Employee::getSalary).reversed()` avoids boxing. To break ties, chain comparators: `.sorted(Comparator.comparing(Employee::getSalary).thenComparing(Employee::getExperience))` sorts by salary and then by experience within equal salaries. For null-safe sorting, `Comparator.nullsLast(Comparator.comparing(...))` places employees with null fields at the end. `filter` and `sorted` are lazy intermediate operations; nothing runs until the terminal `collect` executes. To skip the intermediate list, the pipeline can end directly with a terminal `forEach`: `employees.stream().filter(...).sorted(...).forEach(System.out::println)`. The alternative imperative approach — a plain loop with a hand-written `Comparator` passed to `Collections.sort` — is more verbose and does not compose as cleanly. The Stream version is preferred because it states the intent, keeps the data immutable, and can be switched to a parallel stream by replacing `.stream()` with `.parallelStream()` if the dataset is large enough to justify it.
