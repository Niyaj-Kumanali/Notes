11. How did you reduce Loan Listing API latency from 100 seconds to 30 seconds?
    - **Answer:** I started by identifying where the time was being spent. Since the Loan Listing API depended heavily on SQL Server stored procedures, I analyzed the database side first. I reviewed stored procedure logic, checked execution plans, looked for table scans, expensive joins, missing indexes, and unnecessary data processing. 12. What were the bottlenecks in the Loan Listing API?
    - **Answer:** The main bottlenecks were in the stored procedures. Some procedures had table scans instead of index seeks because the indexes were missing or poorly designed. There were expensive joins across large tables without proper filtering. Some procedures were also processing unnecessary columns and doing redundant calculations. Additionally, the data volume was growing, and the queries were not designed to scale. All of these combined to cause the high latency.

13. How did you identify slow stored procedures in DRMS?
    - **Answer:** I used SQL Server Management Studio to check the execution plans and identify high-cost operations. I also looked at the duration and logical reads for each procedure using the system DMVs. I profiled the API calls to see which endpoint was slow, then traced it back to the specific stored procedure. Once I identified the high-impact procedures, I analyzed them one by one.

14. What changes did you make in the 11 legacy stored procedures?
    - **Answer:** I made several types of changes. I added missing indexes to avoid table scans. I rewrote inefficient joins and added proper filtering conditions. I removed unnecessary columns from SELECT statements. I also simplified some complex queries that were doing redundant subqueries or calculations. In some cases, I broke down large monolithic procedures into smaller focused queries. The goal was to reduce logical reads and execution time while keeping the business logic intact.

15. How did you validate that stored procedure changes did not break business logic?
    - **Answer:** I ran the old and new versions of the procedures side by side with the same input parameters and compared the output. I also checked edge cases like empty results, single results, and large result sets. In addition, I had xUnit tests in the API layer that tested the business logic. After the changes, I ran those tests to make sure nothing was broken. I also tested the complete API flow through the Angular frontend to confirm the behavior was correct.

19. What approval stages existed in DRMS?

20. How did multi-tier approval work in DRMS?
    - **Answer:** In multi-tier approval, a request had to be approved at multiple levels before it was finalized. For example, a request might first go to a team lead, then to a manager, and then to a director for high-value items. Each tier had its own set of approvers. The system tracked the current stage and only allowed the appropriate approver for that stage to take action. If approved at one stage, it moved to the next. If rejected at any stage, the entire request was rejected.

21. What is the mid-approval cancellation feature?
    - **Answer:** Mid-approval cancellation allows the requestor to cancel a demo request even after it has been submitted and is in the middle of the approval workflow. For example, if a requestor realizes they no longer need the demo, they can cancel it instead of waiting for the full approval process to complete. This saves time for both the requestor and the approvers. However, cancellation is only allowed under certain conditions, such as when the request is not yet finalized.

22. What edge cases did you handle in mid-approval cancellation?
    - **Answer:** I handled cases like cancellation when the request is at different stages, cancellation after one approver has already approved, and cancellation attempts by users who are not authorized. I also handled the scenario where a cancellation request comes in at the same time as an approval action to prevent race conditions. Additionally, I made sure that the audit history clearly shows who cancelled and at what stage the request was.

23. How did you prevent unauthorized cancellation?
    - **Answer:** I enforced authorization checks in the API. Only the original requestor or an authorized administrator could cancel a request. The cancellation endpoint checked the current user's identity against the request owner. The RBAC layer also ensured that approvers could not cancel requests unless they had special permission. Additionally, I added validation to check the current stage of the request, because cancellation might not be allowed at certain stages.

24. How did you maintain audit history during cancellation?
    - **Answer:** I used Serilog to capture audit logs for all cancellation actions. The log included who cancelled, when it was cancelled, the current stage at the time of cancellation, and any additional context. The database also stored the cancellation event as part of the request history, so the full timeline of the request was preserved. This made it possible to trace what happened even if the cancellation was performed in the middle of the workflow.

25. What are Outlook Actionable Messages?
    - **Answer:** Outlook Actionable Messages allow users to take actions directly from their email inbox without opening the application. In DRMS, when an approver received an approval request email, they could see Approve or Reject buttons directly in the email. Clicking the button would send a request to the backend API, and the approval action would be processed. This eliminated the need to log in to the application for simple approval actions.

26. How did email-based approval work in DRMS?
    - **Answer:** When a demo request reached a stage requiring approval, the system sent an email to the approver with an Outlook Actionable Message card. The card contained details about the request and buttons for Approve and Reject. When the approver clicked a button, it sent an HTTP request to a secure endpoint in the ASP.NET Core API. The API validated the action token, checked permissions, and processed the approval or rejection. The user did not need to log in to the application for this.

27. How did you secure email-based approvals?
    - **Answer:** I used token-based security for Outlook Actionable Messages. Each email contained a unique validation token that was generated server-side and tied to a specific request and action. ## C# Core Questions

1. What is the difference between `value` and `reference` types in C#?
   - **Answer:** Value types (structs, int, bool, DateTime) store data directly on the stack and are copied on assignment. Reference types (classes, strings, arrays) store a reference (pointer) on the stack pointing to the heap object; assignment copies the reference, not the object. In PROXPERT, we used records (reference types) for DTOs and structs for lightweight value-objects like `Money` or `Percentage` to reduce heap pressure in high-throughput API calls.

2. Explain boxing and unboxing with an example.
   - **Answer:** Boxing converts a value type to `object` or an interface type, wrapping it on the heap. Unboxing extracts the value type back. Example: `int x = 42; object obj = x;` (boxing); `int y = (int)obj;` (unboxing). In DRMS, we avoided boxing in hot paths like logging loops by using generic overloads in Serilog (`Log.Information("{Count}", count)`) instead of `string.Format` which boxes.

3. What is the difference between `String` and `StringBuilder`?
   - **Answer:** `string` is immutable – every concatenation creates a new string object. `StringBuilder` uses a mutable buffer, appending without allocations. In DRMS, when building dynamic SQL queries for report generation with hundreds of parameters, we used `StringBuilder` to avoid O(n²) string allocations. For fixed strings or simple concats, plain `string` is fine.

4. Explain the `using` statement. What is `IAsyncDisposable`?
   - **Answer:** `using` ensures `IDisposable.Dispose()` is called when the block exits, even on exceptions. `IAsyncDisposable` (C# 8) adds `DisposeAsync()` for async cleanup like closing network streams. In PROXPERT, we used `await using` for our `RedisConnection` and `DbConnection` instances to ensure connections are returned to the pool without blocking threads.

5. What are extension methods and how do they work?
   - **Answer:** Static methods in a static class where `this` prefixes the first parameter. They appear as instance methods on the target type. In EUV, we created `IQueryableExtensions.WhereIf(condition, predicate)` to conditionally apply filters in our compliance APIs without cluttering LINQ expressions.

6. Explain the difference between `IEnumerable<T>`, `ICollection<T>`, `IList<T>`, and `IQueryable<T>`.
   - **Answer:** `IEnumerable<T>` – forward-only iteration over an in-memory collection. `ICollection<T>` adds Count, Add, Remove. `IList<T>` adds indexed access. `IQueryable<T>` represents a queryable data source (e.g., SQL) with expression trees; execution is deferred and translated to the provider's language. In EUV, compliance validation APIs used `IQueryable<T>` with EF Core so filters compiled to SQL; once materialized with `.ToListAsync()`, we returned `IEnumerable<T>` to controllers.

7. What is the difference between `First()`, `FirstOrDefault()`, `Single()`, and `SingleOrDefault()`?
   - **Answer:** `First()` returns the first element or throws if empty. `FirstOrDefault()` returns `default` if empty. `Single()` returns the only element or throws if zero or many. `SingleOrDefault()` returns `default` if empty but throws if more than one. In DRMS, I used `SingleOrDefault()` when expecting exactly one approval record from a stored procedure; more than one was an integrity violation worth throwing on.

8. Explain `async` and `await`. What happens under the hood?
   - **Answer:** `async` marks a method to allow `await`. The compiler generates a state machine that yields control to the caller at each `await` point. When the awaited task completes, execution resumes on the captured `SynchronizationContext`. In all three projects, we used `ConfigureAwait(false)` in library code to avoid marshaling back to the request context, improving throughput under load.

9. What is the difference between `Task`, `Task<T>`, `ValueTask`, and `ValueTask<T>`?
   - **Answer:** `Task`/`Task<T>` are reference types representing async operations, always heap-allocated. `ValueTask`/`ValueTask<T>` (C# 7) are value types that can avoid allocation when the result is synchronously available. In PROXPERT, we used `ValueTask<int>` for Redis cache lookups that often hit synchronously, reducing allocations by ~40% on cache-hit paths.

10. Explain the `lock` statement and thread safety.
    - **Answer:** `lock(obj)` acquires a mutual-exclusion lock on the given reference object, ensuring only one thread executes the critical section. In DRMS, we used `ConcurrentDictionary` for in-memory rate-limiting counters instead of manual locking. For PROXPERT's background job status tracking, we used `SemaphoreSlim` for finer-grained async-compatible synchronization.

11. What is a delegate? What is the difference between `Action`, `Func`, and `Predicate`?
    - **Answer:** A delegate is a type-safe function pointer. `Action<T>` returns void. `Func<T, TResult>` returns a value. `Predicate<T>` is equivalent to `Func<T, bool>`. In EUV, I used `Func<DateTime, bool>` as a parameter for date-range filtering strategies in compliance validation, allowing testability without mocking the full service.

12. Explain events vs delegates.
    - **Answer:** An event is a wrapper around a delegate that only allows `+=` and `-=` from outside the declaring class – it prevents subscribers from clearing or invoking the delegate list. In DRMS, we used events for the email notification system: the `ApprovalService` raised `ApprovalProcessed`, and the `EmailService` subscribed; this decoupled the approval logic from the email infrastructure.

13. What are anonymous methods and lambda expressions?
    - **Answer:** Anonymous methods (`delegate(int x) { return x > 0; }`) are C# 2.0 inline methods. Lambda expressions (`x => x > 0`) are C# 3.0 syntactic sugar that can be compiled to delegates or expression trees. In PROXPERT, we used expression lambdas for EF Core queries (`context.Users.Where(u => u.Role == "Admin")`) and statement lambdas for in-memory operations.

14. Explain Expression Trees. When would you use them?
    - **Answer:** Expression trees represent code as data – a tree of `Expression` nodes that can be inspected, modified, and compiled at runtime. In EUV, we built dynamic filtering expressions for the compliance validation engine: user-selected criteria were composed into `Expression<Func<T, bool>>` trees that EF Core translated to parameterized SQL.

15. What is the difference between `var`, `object`, and `dynamic`?
    - **Answer:** `var` is statically typed – the type is inferred at compile time. `object` is the universal base type requiring boxing for value types. `dynamic` bypasses compile-time checking, resolved at runtime via DLR. In PROXPERT, we used `var` by convention, `object` only in legacy interop, and `dynamic` once for JSON deserialization of loosely-typed webhook payloads.

16. Explain the `yield` keyword and its use cases.
    - **Answer:** `yield return` creates an iterator state machine – elements are produced lazily without allocating an intermediate collection. In DRMS, we used `yield return` in a method that paginated through stored procedure results, streaming records without loading thousands into memory at once.

17. What are nullable value types? What is `Nullable<T>`?
    - **Answer:** `Nullable<T>` (also `T?`) allows value types to represent `null`. It's a struct with `HasValue` and `Value` properties. In EUV, we mapped nullable SQL columns (like `ApprovedDate datetime null`) to `DateTime?` in our entity models, using `??` or `.GetValueOrDefault()` in business logic.

18. Explain the `null-conditional` operator (`?.`) and `null-coalescing` operator (`??`).
    - **Answer:** `?.` short-circuits to `null` if the left side is null. `??` provides a fallback value when the left side is null. In PROXPERT: `var role = user?.Role?.Name ?? "Guest"`. We also used `??=` (C# 8) to lazy-initialize cached configurations: `_config ??= await LoadConfigAsync()`.

19. What are Records? How are they different from Classes?
    - **Answer:** Records (C# 9) are reference or value types with value-based equality, a compiler-generated `ToString()`, `Deconstruct`, and `With` expressions. Classes have reference equality. In PROXPERT, we used records for DTOs and API contracts because immutable by default (`init` setters) and structural equality made unit testing predictable.

20. Explain `readonly` vs `const` vs `static readonly`.
    - **Answer:** `const` is a compile-time constant, inlined by the compiler. `readonly` is a runtime constant set in the constructor. `static readonly` is shared across all instances, initialized once. In DRMS, we used `const` for SQL query fragments, `readonly` for per-request injected services, and `static readonly` for configuration-loaded values like `ConnectionString`.

21. What is the `sealed` keyword for? When should you use it?
    - **Answer:** `sealed` prevents a class from being inherited or a method from being overridden. In PROXPERT, we sealed our `BaseRepository<T>` because it was designed for composition, not extension; this also enables runtime JIT devirtualization for performance-critical hot paths.

22. Explain the `is` and `as` keywords. Difference from casting?
    - **Answer:** `is` checks type compatibility (returns bool). `as` attempts a cast, returning `null` on failure instead of throwing. In EUV: `if (result is IValidationResult vr)` for pattern matching; `var handler = service as IEmailHandler` for optional interface detection.

23. What is the difference between `Exception` and `SystemException`?
    - **Answer:** `SystemException` is the base for framework-defined exceptions (e.g., `NullReferenceException`, `InvalidOperationException`). `Exception` is the ultimate base class. Custom exceptions should derive from `Exception`, not `SystemException`. In all projects, we created custom exceptions like `DomainException` inheriting from `Exception`.

24. Explain `IDisposable` and the Dispose pattern.
    - **Answer:** `IDisposable` provides `Dispose()` for releasing unmanaged resources. The full pattern includes a `protected virtual void Dispose(bool disposing)` overload to handle both manual and finalizer cleanup. In DRMS, our `DbContext` subclasses used `Dispose` to close DB connections properly; we also implemented `IAsyncDisposable` for Serilog sinks that flush asynchronously.

25. What is the Global Using feature? (C# 10)
    - **Answer:** `global using` imports a namespace across all files in the project. In PROXPERT, we had a `GlobalUsings.cs` with `global using System;`, `global using System.Threading.Tasks;`, and our domain namespaces, eliminating repetitive `using` statements across 80+ files.

26. Explain `file-scoped namespaces` (C# 10).
    - **Answer:** Instead of a block with braces, you write `namespace MyApp.Services;` at the top of the file – everything in that file belongs to the namespace. Every C# file in PROXPERT used this, reducing indentation and diff noise in PRs.

27. What is the difference between `abstract class` and `interface`? Have interfaces changed in recent versions?
    - **Answer:** Abstract classes can have state (fields, constructors), concrete methods, and protected members. Interfaces (pre-C# 8) could only have declarations. Since C# 8, interfaces can have default implementations, static members, and `private` methods. In EUV, we preferred interfaces for service contracts (`IComplianceService`) and abstract classes only when sharing constructor-injected dependencies across implementations.

28. Explain covariance and contravariance in generics.
    - **Answer:** Covariance (`out T`) allows using a more derived type where a base type is expected (e.g., `IEnumerable<Dog>` as `IEnumerable<Animal>`). Contravariance (`in T`) allows using a less derived type (e.g., `Action<Animal>` as `Action<Dog>`). In PROXPERT, we used `IReadOnlyCollection<out T>` for API response DTO lists and `IComparer<in T>` for custom sorting.

29. What is the `ref` return and `ref` local?
    - **Answer:** A method can return a reference to a variable with `ref return`, and callers can store it with `ref local` to modify the original. In DRMS, we used `ref` returns in our custom `ObjectPool<T>` for byte arrays used during Serilog log batching, avoiding array copy overhead.

30. Explain the `Span<T>` and `Memory<T>` types.
    - **Answer:** `Span<T>` is a stack-allocated, ref-struct view over contiguous memory (arrays, unmanaged memory). `Memory<T>` is a heap-allocable version not limited to stack scope. In PROXPERT, we used `Span<byte>` for parsing fixed-width protocol buffers in IoT telemetry ingestion, achieving zero-allocation parsing.

31. What is the difference between `Array.CopyTo()` and `Array.Clone()`?
    - **Answer:** `Clone()` creates a shallow copy as `object`, requiring a cast. `CopyTo()` copies elements into an existing array at a specified index. Both do shallow copies of reference types. In EUV, we preferred `CopyTo` when reusing a pre-allocated buffer for batch compliance result processing.

32. Explain the `Index` and `Range` types (C# 8).
    - **Answer:** `^` (Hat operator) creates an `Index` from the end: `^1` is the last element. `..` creates a `Range`: `array[1..^1]` skips first and last. In PROXPERT, we used ranges for pagination on cached result slices: `cacheResults[skip..(skip + take)]`.

33. What are `init`-only setters?
    - **Answer:** `init` allows a property to be set only during object initialization. In PROXPERT, all API request DTOs used `init` setters to prevent mutation after the object was created by the model binder.

34. Explain `pattern matching` enhancements (switch expressions, positional patterns, property patterns).
    - **Answer:** C# 7+ added switch expressions (`x switch { 1 => "one", _ => "other" }`), positional patterns (matching on `Deconstruct`), and property patterns (`{ Name: "Admin" }`). In DRMS's authorization service, we used property patterns on the `UserPrincipal` object to match role and permission combinations for RBAC decisions.

35. What is `LINQ`? Explain deferred execution and eager execution.
    - **Answer:** LINQ is a set of methods for querying data. Deferred execution means the query is not evaluated until the result is enumerated (e.g., `Where`, `Select`). Eager execution materializes immediately (e.g., `ToList()`, `Count()`, `First()`). In EUV, we carefully deferred filtering until all conditions were applied, then called `ToListAsync()` once to execute a single SQL query.

36. Explain `Select` vs `SelectMany`.
    - **Answer:** `Select` projects each element to a single element. `SelectMany` flattens nested collections – each element projects to an `IEnumerable<T>` and the results are concatenated. In DRMS, `SelectMany` was used to flatten user-role-permission mappings: `users.SelectMany(u => u.Roles.SelectMany(r => r.Permissions))`.

37. What is `ExceptionFiltering`? Give an example.
    - **Answer:** `catch (InvalidOperationException ex) when (LogException(ex))` – the `when` clause filters the catch block without unwinding the stack if the condition is false. In DRMS, we used this to only catch DB concurrency exceptions for specific error codes: `catch (DbUpdateConcurrencyException ex) when (ex.Entries.Any(e => e.Entity is Approval))`.

38. Explain the `nameof` expression.
    - **Answer:** `nameof` returns the compile-time string name of a variable, type, or member. In PROXPERT, we used it for argument validation guards: `Guard.Against.Null(id, nameof(id))` and for Serilog property names: `Log.Information("{@User} logged in", user)` – safe against refactoring.

39. What is the difference between `throw` and `throw ex`?
    - **Answer:** `throw` re-throws the original exception preserving the original stack trace. `throw ex` re-throws with a reset stack trace pointing to the catch block, losing the original call site. In all my projects, we always used `throw` in catch blocks for logging-and-rethrow patterns.

40. Explain the `CallerMemberName`, `CallerFilePath`, `CallerLineNumber` attributes.
    - **Answer:** Compiler-provided parameter values for the calling method's name, file, and line. In DRMS, we used `[CallerMemberName]` in a base `LoggableService` class so every derived service method automatically logged its name without manual strings.

41. What is the `ThreadPool` and how does it relate to `Task`?
    - **Answer:** `ThreadPool` manages a pool of worker threads. `Task` uses the `ThreadPool` by default via `TaskScheduler.Default`. Long-running CPU-bound tasks can use `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning)` to get a dedicated thread. In PROXPERT, background job processing used `Task.Run` which queued to the `ThreadPool`.

42. Explain `CancellationToken` and cooperative cancellation.
    - **Answer:** `CancellationToken` is a struct that signals cancellation via `IsCancellationRequested` or throws `OperationCanceledException` on `ThrowIfCancellationRequested()`. In all projects, every async endpoint accepted `CancellationToken` and passed it to EF Core methods and `HttpClient` calls, ensuring graceful shutdown under load.

43. What is the difference between `ToList()` and `ToArray()`?
    - **Answer:** Both materialize a collection. `ToList()` returns `List<T>` with an internal array that may be oversized. `ToArray()` returns `T[]` which is trimmed to exact size. For immutable returns in PROXPERT, we used `ToArray()`; for mutable collections where elements would be added later, we used `ToList()`.

44. Explain the `AsNoTracking()` method in LINQ to Entities.
    - **Answer:** `AsNoTracking()` returns entities without change tracking, which is faster and uses less memory. In EUV, all read-only compliance queries used `AsNoTracking()` since no updates were performed, reducing EF Core overhead by ~30% in query processing.

45. What is `StringComparison` and why is it important?
    - **Answer:** Specifies culture and case rules for string comparisons. In EUV, Malaysian compliance user lookups required ordinal case-insensitive comparisons (`StringComparison.OrdinalIgnoreCase`) for identity numbers, avoiding cultural quirks of the default `CurrentCulture`.

46. Explain `CultureInfo` and `InvariantCulture`.
    - **Answer:** `CultureInfo` defines locale-specific formatting for dates, numbers, and strings. `InvariantCulture` is culture-insensitive. In DRMS, we serialized all API dates as `"yyyy-MM-ddTHH:mm:ssZ"` using `InvariantCulture` to avoid locale-dependent parsing issues between Malaysian and US systems.

47. What is `Assembly`? How do you load and inspect assemblies at runtime?
    - **Answer:** `Assembly` represents a compiled .NET assembly (DLL/EXE). You can load with `Assembly.LoadFrom("path")` and inspect with reflection: `assembly.GetTypes()`, `GetCustomAttributes()`. In PROXPERT, we used assembly scanning for DI registration via Scrutor: `services.Scan(s => s.FromAssemblies(Assembly.GetExecutingAssembly())...)`.

48. Explain `Reflection`. When would you use it? What are the downsides?
    - **Answer:** Reflection inspects and invokes types, methods, and properties at runtime. We used it sparingly: for attribute-based authorization in DRMS, for generic repository pattern in EUV. Downsides: slow (no JIT optimization), no compile-time safety, and brittle to refactoring.

49. What is `dynamic` type and how does the DLR work?
    - **Answer:** `dynamic` defers type resolution to runtime via the Dynamic Language Runtime. In PROXPERT, we used it only for JSON deserialization of third-party webhooks where the schema was unpredictable. We avoided it in internal code due to the lack of IntelliSense and runtime performance cost.

50. Explain `source generators`. Have you used them?
    - **Answer:** Source generators run during compilation, analyzing attributes and generating additional source files. In PROXPERT, we used the `MediatR` source generator to auto-register handlers, and a custom generator that produced `IValidator` boilerplate from record definitions.

51. What are the different types of classes in C#? (static, abstract, sealed, partial, etc.)
    - **Answer:** `static` – cannot be instantiated, only static members. `abstract` – cannot be instantiated, may have abstract methods. `sealed` – cannot be inherited. `partial` – class definition split across files. In PROXPERT, we used `partial` classes for EF Core entity configurations, `static` for helper classes, and `sealed` for repositories.

52. Explain `WeakReference<T>`.
    - **Answer:** A weak reference allows the GC to collect the object while still holding a reference. In DRMS, we used `WeakReference<T>` in our caching layer for large, recreatable objects (like compiled report templates) to avoid memory pressure while keeping a cache-aside strategy.

53. What is `ConcurrentDictionary<TKey, TValue>` and when would you use it?
    - **Answer:** A thread-safe dictionary using fine-grained locking and lock-free reads. In PROXPERT, we used `ConcurrentDictionary` for the in-memory rate-limiting store, mapping API keys to request counts with `AddOrUpdate` and `GetOrAdd` atomic operations.

54. Explain `Interlocked` operations.
    - **Answer:** `Interlocked` provides atomic operations (`Increment`, `Decrement`, `Exchange`, `CompareExchange`) without locks. In EUV, we used `Interlocked.Increment(ref _requestCount)` for lightweight, lock-free request counters in the compliance auditing middleware.

55. What is the difference between `is null` and `== null`?
    - **Answer:** `is null` uses pattern matching and cannot be overloaded, making it always reliable. `== null` uses the overloaded `==` operator; user-defined types can override it. In all projects, we used `is null` for null checks to avoid surprises with custom equality operators.

56. Explain `struct` vs `class` – when would you choose a struct?
    - **Answer:** Structs are value types, allocated on the stack or inline, more efficient for small, immutable data (≤ 16 bytes). In EUV, we used structs for `ComplianceResultCode` (a small enum-like value) and for coordinates in our geofencing module. Avoid structs for large mutable objects due to copy overhead.

57. What are tuples? ValueTuple vs Tuple?
    - **Answer:** `Tuple<T1, T2>` (class, heap-allocated) was pre-C# 7. `ValueTuple<T1, T2>` (struct, C# 7) supports named elements, deconstruction, and better performance. In PROXPERT, we used named value tuples for internal method returns: `(bool Success, string Role)` instead of creating single-use DTOs.

58. Explain `async void` vs `async Task`. When is `async void` acceptable?
    - **Answer:** `async void` cannot be awaited and exceptions crash the process. `async Task` is awaitable with proper exception handling. `async void` is only acceptable for event handlers (e.g., button clicks, `IAsyncDisposable.DisposeAsync`). In all projects, we enforced via Roslyn analyzers that only event handlers used `async void`.

59. What is `StackOverflowException` and how do you prevent it?
    - **Answer:** Thrown when the call stack overflows, typically from infinite recursion. In DRMS, we prevented it by ensuring recursive tree traversals (e.g., org hierarchy loading) had a max-depth parameter: `LoadHierarchy(maxDepth: 5)`. StackOverflowException cannot be caught since .NET 2.0.

60. Explain `default` keyword and `default literal` (C# 7.1).
    - **Answer:** `default(T)` returns the zero-initialized value for type T (null for ref types, zero for numeric, etc.). Since C# 7.1, `default` can infer the type: `var result = Method() ?? default;`. In EUV, we used `default` in generic repository methods for `FindByIdOrDefaultAsync`.

## ASP.NET Core Web API Questions

1. What is the ASP.NET Core request pipeline?
   - **Answer:** A pipeline of middleware components configured in `Program.cs` via `app.Use*()` methods. Each middleware can handle the request, pass it to the next, or short-circuit. In DRMS, the pipeline was: ExceptionHandler → Serilog → Authentication → Authorization → CORS → EndpointMiddleware (controllers). Order matters – auth must come before endpoints.

2. Explain middleware. How do you create custom middleware?
   - **Answer:** Middleware is a class with a `RequestDelegate next` parameter and an `InvokeAsync(HttpContext context)` method. In EUV, we created `ComplianceAuditMiddleware` that logged request/response payloads for audit trails:
   ```csharp
   public class ComplianceAuditMiddleware
   {
       private readonly RequestDelegate _next;
       public async Task InvokeAsync(HttpContext context)
       {
           // log request
           await _next(context);
           // log response
       }
   }
   ```

3. What is the difference between `app.Use()` and `app.Run()`?
   - **Answer:** `app.Use()` adds middleware that can call `next` to pass to the next component. `app.Run()` is terminal middleware – it never calls `next`, short-circuiting the pipeline. In PROXPERT, `app.Run()` was used at the end of the pipeline for static file fallback in SPA hosting.

4. How does dependency injection work in ASP.NET Core? Explain service lifetimes.
   - **Answer:** Built-in DI container with three lifetimes: **Singleton** (one instance for the app lifetime – Redis cache), **Scoped** (one per HTTP request – DbContext), **Transient** (new instance every injection – lightweight services). In PROXPERT, repositories were scoped, `IMediator` was scoped, and `IOptions<T>` was singleton.

5. Explain `AddScoped`, `AddTransient`, `AddSingleton` – when to use each?
   - **Answer:** `AddSingleton` for stateless services and configuration (Redis client, logger). `AddScoped` for state-per-request services (DbContext, UnitOfWork). `AddTransient` for lightweight, stateless, and thread-safe services (validators, mappers). In DRMS, `IEmailService` was scoped because it used request-scoped Serilog enrichers.

6. What are the different ways to register services? Examples.
   - **Answer:** `services.AddScoped<IMyService, MyService>()`, `services.AddTransient<IMyService>(sp => new MyService(...))`, `services.AddSingleton(typeof(IMyService), typeof(MyService))`, and assembly scanning via Scrutor: `services.Scan(s => s.FromCallingAssembly().AddClasses(c => c.AssignableTo<IValidator>()).AsImplementedInterfaces())`. Used assembly scanning in PROXPERT to auto-register all MediatR handlers and FluentValidation validators.

7. How would you configure CORS in an ASP.NET Core API?
   - **Answer:** In `Program.cs`:
   ```csharp
   services.AddCors(o => o.AddPolicy("AllowFE", b => b.WithOrigins("https://app.lenovo.com.my").AllowAnyHeader().AllowAnyMethod()));
   app.UseCors("AllowFE");
   ```
   In DRMS (Lenovo), we restricted origins to specific corporate domains and allowed credentials for cookie-based auth.

8. Explain `Endpoint Routing` vs conventional routing.
   - **Answer:** Endpoint routing (introduced in ASP.NET Core 3.0) maps requests to endpoints using `app.UseRouting()` and `app.UseEndpoints()`. Conventional routing uses `{controller}/{action}/{id?}` patterns. Attribute routing (`[Route("api/approvals")]`) is the preferred approach in all my projects. Endpoint routing integrates with middleware like auth and CORS between routing and endpoint execution.

9. What is the purpose of `appsettings.json`? How does environment-specific config work?
   - **Answer:** `appsettings.json` is the base configuration file, overridden by `appsettings.{Environment}.json` (e.g., `appsettings.Development.json`, `appsettings.Production.json`). Environment is set via `ASPNETCORE_ENVIRONMENT`. In PROXPERT, we had `appsettings.json` (shared) + `appsettings.Development.json` (local Redis/DB) + `appsettings.Production.json` (Azure Key Vault references).

10. How do you read configuration from `appsettings.json`?
    - **Answer:** Via the `IOptions<T>` pattern:
    ```csharp
    services.Configure<RedisSettings>(configuration.GetSection("Redis"));
    // Inject: IOptions<RedisSettings> or IOptionsSnapshot<RedisSettings>
    ```
    In PROXPERT, we used `IOptionsSnapshot<T>` for settings that reload when the source file changes, and `IOptionsMonitor<T>` for singleton services needing reactive updates.

11. Explain `IOptions`, `IOptionsSnapshot`, `IOptionsMonitor`.
    - **Answer:** `IOptions<T>` – singleton, reads once. `IOptionsSnapshot<T>` – scoped, reads per request, supports reload. `IOptionsMonitor<T>` – singleton but subscribes to changes. In EUV, compliance rules were configured per customer via `IOptionsSnapshot`, ensuring changes took effect without app restart.

12. How does model binding work? How would you bind a complex object?
    - **Answer:** Model binding maps HTTP request data (route, query, body, form) to action method parameters. Complex objects are deserialized from the body using `[FromBody]`. In DRMS, we used `[FromQuery]` for filtering parameters and `[FromRoute]` for IDs. Custom model binders were used for encrypted query parameters in the approval flow.

13. What is model validation? How do you use FluentValidation?
    - **Answer:** Model validation checks incoming data against rules. Data Annotations (`[Required]`, `[EmailAddress]`) work but FluentValidation is more expressive. In PROXPERT:
    ```csharp
    public class CreateProjectValidator : AbstractValidator<CreateProjectRequest>
    {
        public CreateProjectValidator() { RuleFor(x => x.Name).NotEmpty().MaximumLength(100); }
    }
    ```
    Registered with `services.AddValidatorsFromAssemblyContaining<CreateProjectValidator>()`.

14. What are Action Filters? How do they differ from middleware?
    - **Answer:** Action filters run in the MVC pipeline, after routing but before and after the action method. They have access to the action context (parameters, model state). Middleware is broader – it wraps the entire pipeline. In DRMS, we used an `ValidationFilterAttribute` that auto-returned 400 if `ModelState.IsValid` was false, centralizing validation.

15. Explain `IAsyncActionFilter` with an example.
    - **Answer:**
    ```csharp
    public class LoggingActionFilter : IAsyncActionFilter
    {
        public async Task OnActionExecutionAsync(ActionExecutingContext context, ActionExecutionDelegate next)
        {
            // before
            var result = await next();
            // after – result.Result has the IActionResult
        }
    }
    ```
    In PROXPERT, we used this to log request/response times per endpoint.

16. What is the difference between `IExceptionFilter` and the `ExceptionHandlerMiddleware`?
    - **Answer:** Middleware catches exceptions from the entire pipeline; filters only catch from MVC action execution. In DRMS, we used `ExceptionHandlerMiddleware` for global error handling (consistent JSON error responses) and `IExceptionFilter` was added only for controller-specific fallback logic.

17. Explain rate limiting in ASP.NET Core 7+? Have you implemented it?
    - **Answer:** Built-in rate limiting with `AddRateLimiter()` supporting fixed window, sliding window, token bucket, and concurrency policies. In PROXPERT, we implemented a fixed-window policy per API key:
    ```csharp
    services.AddRateLimiter(o => o.AddFixedWindowLimiter("ApiKey", opt => { opt.PermitLimit = 100; opt.Window = TimeSpan.FromMinutes(1); }));
    ```

18. How do you implement JWT authentication in ASP.NET Core?
    - **Answer:**
    ```csharp
    services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
        .AddJwtBearer(o => { o.TokenValidationParameters = new TokenValidationParameters
            { ValidateIssuer = true, ValidateAudience = true, ValidateLifetime = true, IssuerSigningKey = key }; });
    ```
    In PROXPERT, we used OAuth2 with Azure AD, validating the issuer, audience, and signing key from Azure AD metadata. Role claims were extracted for RBAC.

19. What is `[Authorize]` and how do you use role-based and policy-based auth?
    - **Answer:** `[Authorize(Roles = "Admin")]` checks role claims. Policy-based: `services.AddAuthorization(o => o.AddPolicy("RequireAdmin", p => p.RequireRole("Admin").RequireClaim("Permission", "CanApprove")))`; then `[Authorize(Policy = "RequireAdmin")]`. In DRMS, our RBAC had 5 roles and 20+ permission policies.

20. How does `ClaimsPrincipal` work in ASP.NET Core?
    - **Answer:** `HttpContext.User` is a `ClaimsPrincipal` containing one or more `ClaimsIdentity` instances, each with `Claim` objects (Type, Value). In DRMS (LDAP SSO), the authenticated user's `ClaimsPrincipal` was populated with `cn`, `mail`, `memberOf` (AD groups) which we mapped to application roles.

21. Explain the difference between authentication and authorization.
    - **Answer:** Authentication verifies identity ("who you are") – done by middleware like JWT or cookie auth. Authorization determines access ("what you can do") – done by `[Authorize]` and policies. In DRMS, LDAP SSO handled auth; RBAC middleware handled authorization based on the authenticated claims.

22. How do you design RESTful endpoints? What are best practices?
    - **Answer:** Use nouns (not verbs) for resources, HTTP methods for operations (GET for read, POST for create, PUT for replace, PATCH for partial, DELETE), version via URL prefix (`/api/v1/`), use plurals (`/api/approvals`), return proper status codes (200, 201, 204, 400, 404, 500). In EUV, compliance API followed RESTful conventions with query parameters for filtering/sorting.

23. What status codes does a REST API commonly return?
    - **Answer:** 200 (OK) – GET/PUT success. 201 (Created) – POST. 204 (No Content) – DELETE. 400 (Bad Request) – validation errors. 401 (Unauthorized) – not authenticated. 403 (Forbidden) – not authorized. 404 (Not Found). 409 (Conflict) – duplicate/invalid state. 500 (Internal Server Error). We returned Problem Details (RFC 7807) in all projects.

24. Explain content negotiation.
    - **Answer:** The client specifies the expected response format via `Accept` header. ASP.NET Core uses `AddNewtonsoftJson()` or `AddXmlSerializerFormatters()`. The framework selects a formatter based on `Accept` header and available formatters. In all projects, we only supported `application/json` and removed XML formatters.

25. What is the difference between `AddControllers()` and `AddControllersWithViews()`?
    - **Answer:** `AddControllers()` registers services for API-only controllers (no views, no Razor). `AddControllersWithViews()` also registers view/Page-related services. In all my projects (SPA backends), we used `AddControllers()` with `AddJsonOptions()`.

26. Explain the repository pattern in ASP.NET Core. Did you use it?
    - **Answer:** Repository pattern abstracts data access behind an interface, making business logic testable. In PROXPERT, we used a generic `IRepository<T>` with methods like `GetByIdAsync`, `FindAsync(Expression<Func<T, bool>>)`, `AddAsync`, `Update`, `Delete`. EF Core's `DbSet<T>` already implements the repository pattern; we wrapped it for unit testing and added cross-cutting concerns like caching.

27. What is the Unit of Work pattern? How did you implement it?
    - **Answer:** Tracks changes across multiple repositories and commits them in a single transaction. In PROXPERT, `IUnitOfWork` exposed `IProjectRepository`, `ITaskRepository`, and `SaveChangesAsync()`. A scoped unit of work ensured all repositories shared the same `DbContext`, so a single `SaveChangesAsync()` committed all changes atomically.

In PROXPERT, we had Solution folders with each layer as a separate project, enforcing dependency direction: API → Application → Domain, Infrastructure → Application → Domain.

## Entity Framework Core Questions

1. What is Entity Framework Core? How does it differ from EF6?
   - **Answer:** EF Core is a lightweight, cross-platform ORM. Key differences from EF6: lighter footprint, no EDMX (code-first only), supports Cosmos DB, better async, value conversions, owned entities, global query filters. In all my projects, we used EF Core for code-first migrations and LINQ-to-SQL translation.

2. Explain the database-first vs code-first approach. Which do you prefer?
   - **Answer:** Database-first generates models from an existing DB (good for legacy); code-first defines models in C# and generates migrations. In DRMS (legacy with many stored procedures), we started database-first for the existing SQL Server schema. In EUV and PROXPERT, we used code-first for full control over the model.

3. What is a `DbContext`? How do you configure it?
   - **Answer:** `DbContext` represents a session with the database, managing entity instances, change tracking, and database operations. Configured in `Program.cs`:
   ```csharp
   services.AddDbContext<AppDbContext>(o => o.UseSqlServer(connectionString, sql => sql.CommandTimeout(30)));
   ```

4. How do you configure entities using Fluent API vs Data Annotations?
   - **Answer:** Data Annotations use attributes directly on properties (`[Required]`, `[MaxLength(50)]`, `[ForeignKey("UserId")]`). Fluent API uses `IEntityTypeConfiguration<T>` classes with `builder.Property(x => x.Name).HasMaxLength(50).IsRequired()`. In PROXPERT, we preferred Fluent API in separate configuration classes for cleaner entities.

5. Explain migrations in EF Core. How do you roll back a migration?
   - **Answer:** `Add-Migration` creates migration files (Up/Down methods). `Update-Database` applies pending migrations. Rollback: `Update-Database LastGoodMigration` applies the Down() of all later migrations. In PROXPERT, we used `dotnet ef migrations script` for SQL scripts delivered via CI/CD.

6. What is the difference between `DbSet<T>` and `IQueryable<T>`?
   - **Answer:** `DbSet<T>` represents a table/entity collection with change tracking, and implements `IQueryable<T>`. `IQueryable<T>` is the queryable interface used for building LINQ expressions that translate to SQL. In EUV, we exposed `IQueryable<T>` from repositories for composable queries, while `DbSet<T>` was internal.

7. Explain the different loading strategies: Eager, Lazy, Explicit.
   - **Answer:** Eager loading (`.Include(x => x.Roles)`) loads related data upfront in one query. Lazy loading (virtual navigation properties + `UseLazyLoadingProxies()`) loads on access – each access triggers a SQL query (N+1 risk). Explicit loading (`.Entry(user).Collection(x => x.Roles).LoadAsync()`) loads on demand after the query. In all projects, we used eager loading and disabled lazy loading to prevent accidental N+1 queries.

8. What is the `Include` and `ThenInclude` method?
   - **Answer:** `Include()` loads related entities; `ThenInclude()` chains deeper:
   ```csharp
   context.Users.Include(u => u.Department).ThenInclude(d => d.Manager)
   ```
   In DRMS, approval queries eagerly loaded `Approval.Workflow.Steps.Approver` using Include chains.

9. How does Change Tracking work in EF Core?
   - **Answer:** EF Core's `ChangeTracker` detects changes to entities by comparing the original and current values. It tracks entity states: `Added`, `Unchanged`, `Modified`, `Deleted`, `Detached`. When `SaveChangesAsync()` is called, it generates SQL for all tracked changes. In PROXPERT, we used `AsNoTracking()` for read-only queries to bypass change tracking overhead.

10. Explain `AsNoTracking()` and its performance implications.
    - **Answer:** `AsNoTracking()` disables change tracking, meaning entities are not cached in the `ChangeTracker`. This reduces memory usage and speeds up queries by ~30-50%. In EUV, all GET endpoints used `AsNoTracking()` since read data was never updated back through the same context.

11. What is `AutoDetectChanges` and when would you disable it?
    - **Answer:** `DbContext.ChangeTracker.AutoDetectChangesEnabled = false` prevents automatic detection of property changes. Useful when bulk-adding many entities to avoid O(n²) detection overhead. In PROXPERT, we disabled it during batch imports of 10,000+ project tasks and called `DetectChanges()` manually before `SaveChangesAsync()`.

12. How do you handle concurrency conflicts in EF Core?
    - **Answer:** Use `[ConcurrencyCheck]` or `[Timestamp]` (rowversion) attributes. When `SaveChangesAsync()` detects that a row was modified since it was loaded, it throws `DbUpdateConcurrencyException`. In DRMS, we handled this with retry logic (3 attempts) and user-friendly "modification conflict" messages in the approval flow.

13. Explain `Shadow Properties`.
    - **Answer:** Properties not defined in the entity class but tracked by the context. Example: `builder.Property<DateTime>("CreatedAt")`. Useful for audit fields without polluting entities. In all projects, we used shadow properties for `CreatedAt`, `UpdatedAt`, and `IsDeleted` via a base `IEntity` interface.

14. What are `Navigation Properties`?
    - **Answer:** Properties that represent relationships between entities (e.g., `User.Roles`). They can be collection (`ICollection<Role>`) or reference (`User Department`). Configured with `HasOne`, `HasMany`, `WithOne`, `WithMany`. In PROXPERT, navigation properties were virtual only when using explicit loading.

15. Explain the relationship types: One-to-One, One-to-Many, Many-to-Many.
    - **Answer:** One-to-One: `User` ↔ `UserProfile` (`.HasOne(u => u.Profile).WithOne(p => p.User)`). One-to-Many: `Department` → `Users` (`.HasMany(d => d.Users).WithOne(u => u.Department)`). Many-to-Many (EF Core 5+): `User` ↔ `Role` (`.HasMany(u => u.Roles).WithMany(r => r.Users)`). In DRMS, the approval workflow had a complex many-to-many between Approvers and ApprovalGroups.

16. What is a `Joining Table` in Many-to-Many? How is it configured?
    - **Answer:** EF Core 5+ auto-creates a join table for many-to-many. Before EF Core 5, you had to explicitly model the join entity. In PROXPERT, `UserRole` join table was auto-configured; for the `OrderProduct` join (with extra `Quantity` column), we modeled it as an explicit entity.

17. Explain `Owned Entity Types`.
    - **Answer:** Owned types are part of the parent entity and are mapped to the same table (table splitting) or to a separate table. In EUV, `Address` was an owned type in `Customer`:
    ```csharp
    builder.OwnsOne(c => c.Address, a => { a.Property(p => p.City).HasMaxLength(50); });
    ```

18. What are `Global Query Filters`?
    - **Answer:** Filters automatically applied to all queries for an entity:
    ```csharp
    builder.HasQueryFilter(e => !e.IsDeleted);
    ```
    In PROXPERT, all entities had `IsDeleted` with a global filter. In DRMS, approvals were filtered by the current user's department via `HasQueryFilter`.

19. How do you handle soft deletes in EF Core?
    - **Answer:** Add an `IsDeleted` bool property and a global query filter. Override `SaveChangesAsync` to set `IsDeleted = true` and change state to `Modified` instead of `Deleted`. In DRMS, soft deletes preserved audit trails for compliance purposes.

20. Explain `Migration Bundles` (EF Core 6+).
    - **Answer:** A self-contained executable that applies migrations without needing .NET SDK: `dotnet ef migrations bundle`. In PROXPERT, we bundled migrations as part of the CI/CD pipeline, deploying the bundle to on-prem servers that lacked the SDK.

21. What is `EnsureCreated()` vs `Migrate()`?
    - **Answer:** `EnsureCreated()` creates the database if it doesn't exist (no migrations, no version tracking). `Migrate()` applies pending migrations and tracks which ones were applied. In development, we used `EnsureCreated()` for ephemeral test databases; `Migrate()` for production.

22. How does EF Core translate LINQ queries to SQL?
    - **Answer:** EF Core's query pipeline compiles the LINQ expression tree into a SQL statement via a database provider. It translates supported methods to SQL (e.g., `.Where(u => u.Name == "abc")` → `WHERE [u].[Name] = @p0`). Unsupported methods throw at runtime. In EUV, we verified SQL translation by logging queries with `EnableDetailedErrors` during testing.

23. Explain the `Database.Log` equivalent in EF Core.
    - **Answer:** Configure logging in `OnConfiguring` or `Program.cs`:
    ```csharp
    optionsBuilder.LogTo(Console.WriteLine, LogLevel.Information).EnableSensitiveDataLogging();
    ```
    In DRMS, we logged SQL to Serilog at `Debug` level with `LogTo(msg => Log.Debug(msg))` for debugging stored procedure calls.

24. How do you execute raw SQL queries in EF Core?
    - **Answer:** `context.Database.ExecuteSqlRawAsync("UPDATE Users SET Active=1 WHERE Id={0}", id)` for non-query. `context.Users.FromSqlRaw("SELECT * FROM Users WHERE Role={0}", role)` for querying. In DRMS, we used `FromSqlRaw` to call legacy stored procedures that were not yet migrated to LINQ.

25. What is the difference between `FromSqlRaw` and `FromSqlInterpolated`?
    - **Answer:** `FromSqlRaw` takes a raw string and separate parameters; you must handle SQL injection yourself. `FromSqlInterpolated` uses interpolated strings that are parameterized automatically: `FromSqlInterpolated($"SELECT * FROM Users WHERE Id = {id}")`. In DRMS, we used `FromSqlInterpolated` for safety.

26. Explain `Value Conversions`.
    - **Answer:** Convert between property types and database column types:
    ```csharp
    builder.Property(u => u.Status).HasConversion<string>().HasMaxLength(20);
    ```
    In PROXPERT, we stored enums as strings in the DB for readability. We also converted `string[]` to a comma-separated column for simple list storage.

27. What is the difference between `AddDbContext` and `AddDbContextPool`?
    - **Answer:** `AddDbContextPool<T>` creates a pool of `DbContext` instances, reusing them across requests to avoid repeated initialization (which is relatively cheap but still avoidable). In PROXPERT, we used `AddDbContextPool` with pool size = 128, which improved throughput by ~10% under load.

28. How do you use transactions in EF Core?
    - **Answer:**
    ```csharp
    using var transaction = await context.Database.BeginTransactionAsync();
    try { /* operations */ await context.SaveChangesAsync(); await transaction.CommitAsync(); }
    catch { await transaction.RollbackAsync(); }
    ```
    In DRMS, approval processing required atomic updates to multiple tables, all wrapped in a single transaction.

29. Explain `ExecuteUpdate` and `ExecuteDelete` (EF Core 7+).
    - **Answer:** Bulk update/delete without loading entities:
    ```csharp
    await context.Users.Where(u => u.IsInactive).ExecuteDeleteAsync();
    await context.Users.Where(u => u.IsActive).ExecuteUpdateAsync(s => s.SetProperty(u => u.LastLogin, DateTime.UtcNow));
    ```
    In PROXPERT, bulk status updates in background jobs used `ExecuteUpdateAsync`, reducing DB round-trips from 10,000+ to 1.

30. What is `SaveChangesInterceptor`?
    - **Answer:** Hook into `SaveChanges` to modify or audit entities before/after they're persisted. In PROXPERT, we implemented `AuditInterceptor` that auto-set `CreatedAt`, `UpdatedAt`, and `CreatedBy` on tracked entities before save.

31. Explain `IDbContextFactory<T>`.
    - **Answer:** A factory that creates new `DbContext` instances, useful in Blazor or long-running services where scoped lifetime doesn't apply:
    ```csharp
    services.AddDbContextFactory<AppDbContext>(o => o.UseSqlServer(connection));
    ```
    In PROXPERT's `BackgroundService`, we used `IDbContextFactory<T>` because the service outlived a single request scope.

32. How do you handle table-per-type (TPT), table-per-hierarchy (TPH), and table-per-concrete (TPC) inheritance?
    - **Answer:** TPH (default): single table with discriminator column. TPT: separate table per type with joins. TPC (EF Core 7+): separate table per type, no joins (each table has all columns). In EUV, we used TPH for a `ComplianceDocument` base with two derived types, adding a discriminator column.

33. What is the difference between `FindAsync` and `FirstOrDefaultAsync`?
    - **Answer:** `FindAsync(id)` first checks the change tracker cache; if not found, queries the DB by primary key. `FirstOrDefaultAsync(predicate)` always queries the DB. In DRMS, `FindAsync` was ideal for lookup endpoints where recently queried entities might be cached in the context.

34. Explain `Compiled Queries` (EF Core 6+).
    - **Answer:** Pre-compile LINQ queries to avoid recompilation:
    ```csharp
    static private Func<AppDbContext, int, Task<User?>> GetUserById = EF.CompileAsyncQuery((AppDbContext ctx, int id) => ctx.Users.FirstOrDefault(u => u.Id == id));
    ```
    In PROXPERT, we compiled three hot-path queries, reducing CPU time for those endpoints by ~15%.

35. How do you seed data in EF Core?
    - **Answer:** Override `OnModelCreating` with `builder.Entity<User>().HasData(new User { Id = 1, Name = "Admin" })` or use an `IEntityTypeConfiguration<T>` with `HasData()`. In PROXPERT, seed data (initial roles, admin user) was part of migrations.

36. Explain `Complex Types` in EF Core (EF Core 8+).
    - **Answer:** Similar to owned entities but cannot be null and are always inline in the same table. In EUV, we used complex types for `Money` (Amount + Currency) values in compliance fee structures.

37. What is `Temporal Tables` support in EF Core 6+?
    - **Answer:** EF Core supports SQL Server temporal tables for point-in-time queries:
    ```csharp
    builder.ToTable(tb => tb.IsTemporal());
    ```
    In DRMS, approval records used temporal tables so auditors could query the state of an approval at any historical date.

38. How do you handle large datasets in EF Core?
    - **Answer:** Streaming with `AsAsyncEnumerable()`, batching with `Take`/`Skip`, `AsNoTracking()` for read-only, `ExecuteDelete`/`ExecuteUpdate` for bulk operations. In EUV, compliance reports used `AsAsyncEnumerable()` with `System.Threading.Channels` for producer-consumer processing.

39. Explain `Disconnected Entities` and how to update them.
    - **Answer:** Entities that were created/modified outside the current `DbContext`. To update: attach and set state:
    ```csharp
    context.Entry(entity).State = EntityState.Modified;
    ```
    In PROXPERT, when updating a project from an API request, we fetched the existing entity, applied property changes from the DTO (via AutoMapper), and saved.

40. What is `EF Core Power Tools`?
    - **Answer:** A VS extension for reverse-engineering databases, viewing EF Core logs, generating migrations, and visualizing the model. In DRMS, we used it to scaffold the legacy database into entities when migrating from stored procedures to EF Core.

41. How does `ModelBuilder` work? What is the fluent API?
    - **Answer:** `ModelBuilder` is the object used in `OnCreateModel` to configure the model. The fluent API calls like `.HasKey()`, `.Property()`, `.HasForeignKey()` define schema behavior. In all projects, we separated configuration into `IEntityTypeConfiguration<T>` classes called via `modelBuilder.ApplyConfigurationsFromAssembly()`.

42. Explain `Database View` mapping in EF Core.
    - **Answer:** Map entities to database views using `ToView("ViewName")`. The entity is keyless (`.HasNoKey()`) and read-only. In EUV, we mapped a compliance summary view to a keyless entity for efficient reporting without duplicating business logic in C#.

43. How do you handle multiple DbContexts in one application?
    - **Answer:** Register each: `services.AddDbContext<ReadDbContext>(...)` and `services.AddDbContext<WriteDbContext>(...)`. In PROXPERT, we split into `CqrsDbContext` (read-optimized with `AsNoTracking` default) and `CommandDbContext` (write-optimized with full change tracking).

44. What is `Cosmos DB Provider` for EF Core?
    - **Answer:** EF Core can target Azure Cosmos DB (NoSQL API) with the same LINQ abstractions. In PROXPERT, we considered it for the telemetry store but chose the SQL provider for transactional consistency requirements.

45. How do you debug and optimize EF Core queries?
    - **Answer:** Enable `EnableSensitiveDataLogging`, log SQL with `LogTo(Console.WriteLine, LogLevel.Information)`, use `ToQueryString()` to preview the SQL, analyze with SQL Server Profiler, add indexes based on query patterns. In EUV, we identified a missing index on the compliance audit table via logged queries, which reduced query time from 8s to 200ms.

## Dapper Questions

1. What is Dapper? How is it different from EF Core?
   - **Answer:** Dapper is a lightweight micro-ORM by Stack Overflow that extends `IDbConnection` with extension methods. Unlike EF Core, Dapper has no change tracking, no LINQ-to-SQL translation, and no migrations. It executes raw SQL and maps results directly. In DRMS, we used Dapper alongside EF Core for performance-critical stored procedure calls and complex reporting queries.

2. When would you choose Dapper over EF Core?
   - **Answer:** When you need maximum performance with minimal overhead, have complex SQL that LINQ cannot express cleanly, or work with legacy stored procedures. In DRMS, we used Dapper for the stored procedures that performed 30+ table joins with pivots – EF Core's LINQ translation would have been unwieldy and slower.

3. What are the key extension methods in Dapper?
   - **Answer:** `QueryAsync<T>`, `QueryFirstOrDefaultAsync<T>`, `QueryMultipleAsync`, `ExecuteAsync`, `ExecuteScalarAsync`. In DRMS, we used `QueryAsync<ApprovalDto>` to map stored procedure results to DTOs, and `ExecuteAsync` for INSERT/UPDATE/DELETE operations.

4. How does Dapper map query results to objects?
   - **Answer:** Dapper uses `SqlMapper` with implicit type mapping: column names match property names (case-insensitive by default). It uses `FastMember` internally for high-performance property setters. In DRMS, we sometimes used custom column-to-property mapping with `[Column("db_name")]` or anonymous type splits for multi-result queries.

5. Explain `QueryAsync` vs `QueryFirstOrDefaultAsync` vs `QueryMultipleAsync`.
   - **Answer:** `QueryAsync<T>` returns all rows as `IEnumerable<T>`. `QueryFirstOrDefaultAsync<T>` returns the first row or default. `QueryMultipleAsync` handles multiple result sets from a single command. In DRMS, we used `QueryMultipleAsync` for a dashboard endpoint that returned approval counts, pending items, and recent activity in one database round-trip.

6. How do you handle parameters in Dapper? SQL injection prevention?
   - **Answer:** Dapper extends `IDbConnection` with parameterized queries via anonymous types:
   ```csharp
   connection.QueryAsync<Approval>("SELECT * FROM Approvals WHERE Status = @Status", new { Status = "Pending" });
   ```
   This ensures parameters are always parameterized, preventing SQL injection. In DRMS, we never concatenated user input into SQL strings.

7. Explain `DynamicParameters` in Dapper.
   - **Answer:** For advanced parameter scenarios (output params, table-valued parameters, direction):
   ```csharp
   var p = new DynamicParameters();
   p.Add("@Id", id, DbType.Int32, ParameterDirection.Input);
   p.Add("@Count", dbType: DbType.Int32, direction: ParameterDirection.Output);
   connection.Execute("sp_GetCount", p, commandType: CommandType.StoredProcedure);
   int count = p.Get<int>("@Count");
   ```
   In DRMS, we used DynamicParameters for stored procedures with multiple output parameters and return values.

8. How do you call stored procedures with Dapper?
   - **Answer:**
   ```csharp
   var result = await connection.QueryAsync<Approval>("usp_GetApprovalsByUser",
       new { UserId = userId, Status = "Pending" },
       commandType: CommandType.StoredProcedure, commandTimeout: 60);
   ```
   In DRMS, I refactored 15+ stored procedures to be called via Dapper, replacing the legacy `SqlCommand`/`SqlDataReader` boilerplate.

9. How does Dapper handle transactions?
   - **Answer:** Create a `DbTransaction` and pass it to each Dapper call:
   ```csharp
   using var transaction = connection.BeginTransaction();
   await connection.ExecuteAsync("UPDATE ...", new { Id = 1 }, transaction: transaction);
   await connection.ExecuteAsync("INSERT ...", new { Name = "x" }, transaction: transaction);
   transaction.Commit();
   ```
   In DRMS, multi-step approval processing used transaction-scoped Dapper calls for atomicity.

10. Explain `buffered vs unbuffered` queries in Dapper.
    - **Answer:** Buffered (default `buffered: true`) reads all rows into memory at once. Unbuffered (`buffered: false`) streams rows one at a time, keeping the connection busy until enumeration completes. In DRMS, we used buffered for small result sets and unbuffered for large report exports (10,000+ rows) to avoid memory spikes.

11. How do you map multi-mapping (one-to-many) results in Dapper?
    - **Answer:** Use the `splitOn` parameter:
    ```csharp
    var lookup = new Dictionary<int, Order>();
    connection.Query<Order, OrderItem, Order>("SELECT * FROM Orders o JOIN OrderItems i ON o.Id = i.OrderId",
        (order, item) => { if (!lookup.TryGetValue(order.Id, out var o)) lookup.Add(order.Id, o = order); o.Items.Add(item); return o; },
        splitOn: "Id").AsQueryable();
    ```
    In DRMS, I used this pattern to map approval workflows with their step history in a single query.

12. What is `SqlMapper.GridReader` and when would you use it?
    - **Answer:** Returned by `QueryMultipleAsync`, it provides sequential access to multiple result sets:
    ```csharp
    using var grid = await connection.QueryMultipleAsync("sp_GetUserDashboard", new { userId });
    var profile = await grid.ReadFirstAsync<UserProfile>();
    var recentActivity = await grid.ReadAsync<Activity>();
    ```
    In DRMS, this replaced 3 separate DB calls with 1, reducing dashboard load time from 1.2s to 400ms.

13. How do you handle large result sets efficiently with Dapper?
    - **Answer:** Use unbuffered queries, streaming via `await foreach` (C# 8), and `CommandBehavior.SequentialAccess` for large BLOB columns. In EUV, compliance data exports of 100K+ rows used unbuffered streaming directly to CSV response, keeping memory under 50MB.

14. What is the performance advantage of Dapper over EF Core?
    - **Answer:** Dapper is ~2-10x faster than EF Core for read operations because it bypasses change tracking, identity resolution, and LINQ compilation. In DRMS benchmarks, the stored procedure dashboard returned in 50ms with Dapper vs 180ms with EF Core for the same query.

15. How do you integrate Dapper with ASP.NET Core DI?
    - **Answer:**
    ```csharp
    services.AddSingleton<IDbConnection>(sp =>
    {
        var config = sp.GetRequiredService<IConfiguration>();
        return new SqlConnection(config.GetConnectionString("DefaultConnection"));
    });
    ```
    In DRMS, we registered `SqlConnection` as scoped, injected `IDbConnection` into repositories alongside the EF `DbContext`.

16. Explain `Dapper.Contrib` and its attributes.
    - **Answer:** A NuGet package adding CRUD helpers (`InsertAsync`, `GetAsync`, `UpdateAsync`, `DeleteAsync`) and attributes (`[Table]`, `[Key]`, `[ExplicitKey]`, `[Computed]`, `[Write]`). In DRMS, we used `Dapper.Contrib` for simple CRUD on reference tables but avoided it for the complex approval workflow logic.

17. How do you test Dapper code?
    - **Answer:** Abstract `IDbConnection` behind a repository interface and mock it in unit tests. For integration tests, use a real SQL Server or LocalDB instance. In DRMS, we used xUnit with `FakeDbConnection` (from a library like Effort) but preferred integration tests against a test database spun up per test run.

18. How do you map column names that differ from property names?
    - **Answer:** Use column aliases in SQL:
    ```csharp
    connection.QueryAsync<Approval>("SELECT ApprovalId AS Id, ApproverName AS Name FROM ...")
    ```
    Or use Dapper's `CustomPropertyTypeMap` or `[Column("db_column")]` attribute from Dapper.Contrib. In DRMS, we consistently used SQL aliases for clarity.

19. What is `ExecuteAsync` and how does it differ from `QueryAsync`?
    - **Answer:** `ExecuteAsync` returns the number of affected rows, used for INSERT/UPDATE/DELETE. `QueryAsync` returns rows as objects, used for SELECT. In DRMS:
    ```csharp
    var rows = await connection.ExecuteAsync("UPDATE Approvals SET Status = @Status WHERE Id = @Id", new { Status = "Approved", Id = 42 });
    ```

20. What are some common pitfalls when using Dapper?
    - **Answer:** (1) Forgetting `buffered: false` for large datasets causes high memory. (2) Connection still open when enumerating unbuffered results. (3) Case sensitivity? No, Dapper ignores case. (4) No compile-time SQL validation. (5) N+1 queries from manual loops. (6) Parameter name mismatches ("@name" vs "name"). In DRMS, we mitigated these with code reviews, consistent SQL conventions, and a Dapper wrapper that enforced buffered/unbuffered defaults.

## SQL Server and Database Optimization Questions

1. How did you optimize the Loan Listing API from 100s to 30s?

- **Answer:** I refactored 11 legacy stored procedures in the DRMS project. The main bottleneck was a procedure joining 14 tables with nested subqueries and scalar UDFs in WHERE clauses. I replaced scalar UDFs with inline expressions, added filtered indexes for the most common status filter (`WHERE Status IN ('Active', 'Pending')` which covered 80% of queries), and converted cursor-based row-by-row processing to set-based operations with CTEs. I also broke one monolithic procedure into two: one for quick list metadata, another for detail drill-down.

- **If asked more:** The original procedure had a scalar UDF `fn_GetLoanStatus()` called per row that did a separate lookup. SQL Server couldn't optimize it because UDFs are black boxes. I inlined the logic using `CASE` and moved the lookup into a LEFT JOIN. That alone shaved ~40s. The cursor was iterating over 50K+ rows to calculate running balances — I replaced it with a windowed SUM running total, which brought it down to under 10s. The filtered indexes on `IsActive = 1` and `Status IN ('Active', 'Pending')` were the final tweak.

2. How did you tune 14 stored procedures for 57% peak-hour capacity improvement in EUV?

- **Answer:** I analyzed the query plans using `sys.dm_exec_query_stats` and `sys.dm_db_index_usage_stats`. Key changes: (1) Rewrote OR conditions as UNION ALL when both branches had selective predicates, (2) added covering indexes with included columns to eliminate key lookups, (3) broke a large procedure with multiple optional filters into dynamic SQL with `OPTION(RECOMPILE)` to avoid parameter sniffing. Monitoring showed query waits dropped from 340ms avg to 120ms, and concurrent session capacity went from ~350 to ~550 during peak.

- **If asked more:** The EUV compliance checks involved 200+ high-value transactions daily. Each check ran 4-7 stored procedures. One critical procedure had a parameter-sniffing issue: the initial compile used a large client's dataset (50K rows), but 90% of calls were small clients (<500 rows). `OPTION(RECOMPILE)` forced fresh plans. I also used `sys.dm_exec_query_stats` to find the top-5 most expensive queries and added missing indexes on foreign key columns that were implicitly converted (varchar vs nvarchar mismatch — fixed by aligning data types).

3. What's your approach to analyzing slow queries?

- **Answer:** I start with `sp_whoisactive` or `sys.dm_exec_requests` for real-time blocking. Then I capture the actual execution plan from `sys.dm_exec_query_stats` sorted by `total_worker_time`. I look for scans on large tables, key lookups, implicit conversions (red warnings in the plan), and spills to tempdb. In DRMS, I found a clustered index scan on a 2M-row table caused by a `WHERE CAST(Column AS DATE) = @date` — adding a computed persisted column with date-only resolved it.

- **If asked more:** I also check wait stats with `sys.dm_os_wait_stats`. The top wait type at DRMS was PAGEIOLATCH_SH — confirmed disk bottleneck. We moved the most-accessed indexes to a faster SSD filegroup. Another common issue is parameter sniffing: I use `OPTIMIZE FOR UNKNOWN` when a single plan suits all, or `OPTION(RECOMPILE)` when queries are highly variable. In EUV, I used Query Store to track plan regressions after an index change.

4. Explain index types and when you'd use each.

- **Answer:** Clustered index defines physical sort order — one per table, best on narrow, ever-increasing keys like identity columns. Non-clustered indexes are lookup structures; I use covering indexes (with INCLUDE columns) to eliminate key lookups. Filtered indexes are great for high-query, low-modification subsets — I used one in DRMS for active loans only. Columnstore indexes for large DW-style aggregation queries. The main trade-off: indexes speed reads but slow writes, so I monitor `user_seeks` vs `user_updates` in `sys.dm_db_index_usage_stats`.

- **If asked more:** In EUV, I created a filtered index `WHERE Status IN ('Pending', 'Processing')` — that status combo covered 90%+ of the compliance check queries and the index was 80% smaller than a full index on Status. For the DRMS listing page, I added a covering index on `(Status, CreatedDate DESC) INCLUDE (LoanAmount, BorrowerName)` to serve the most common sort/filter combo without touching the clustered index.

5. What causes index fragmentation and how do you handle it?

- **Answer:** Fragmentation happens when INSERT/UPDATE/DELETE operations cause page splits — especially on GUID clustered indexes or indexes with random inserts. I check fragmentation with `sys.dm_db_index_physical_stats`. If avg_fragmentation > 30%, I do REBUILD (offline for clustered, online in Enterprise). If between 5-30%, REORGANIZE. In DRMS, one lookup table had a NEWSEQUENTIALID() clustered key that was fine, but a non-clustered index on a uniqueidentifier column with random GUIDs was 67% fragmented — I changed to sequential GUID generation.

- **If asked more:** Fragmentation hurts range scans more than singleton seeks. A SELECT * with 67% fragmentation caused 3x more reads. For large tables, I schedule REBUILD during maintenance windows. I also track fill factor — 90% is a good default for read-heavy workloads. In EUV, I set fill factor to 80% on high-insert tables to leave room for updates without immediate page splits.

6. What is parameter sniffing and how do you mitigate it?

- **Answer:** Parameter sniffing occurs when SQL Server caches a plan optimized for the first parameter value, which performs poorly for different values. In DRMS, a procedure filtering by `LoanStatus` would get a scan-heavy plan cached for a rare status but then run terribly for a common status. Fixes: (1) `OPTION(RECOMPILE)` for infrequent calls, (2) `OPTIMIZE FOR UNKNOWN` for reasonably uniform distributions, (3) local variable assignment to disable sniffing, (4) dynamic SQL with specific params.

- **If asked more:** For EUV's compliance procedure, I used `OPTION(RECOMPILE)` because each call had vastly different parameter combinations — the 2ms compilation cost was negligible compared to the 3s gain. I also split the procedure: one path for single-record checks, another for batch checks, each with its own cached plan.

7. Compare CTEs, subqueries, temp tables, and table variables.

- **Answer:** CTEs are non-indexed, optimized inline — good for readability and recursive queries. Subqueries are similar but can cause correlated execution if not written carefully. Temp tables support indexes and statistics — best for multi-step processing with large intermediate results. Table variables have no statistics and limited scope — good for small result sets (<100 rows) or passing to TVP in .NET. In DRMS, I replaced a temp table (1M+ rows with two index rebuilds) with a CTE + window function, eliminating the intermediate storage entirely.

- **If asked more:** The original DRMS procedure wrote cursor results to a temp table with an identity column, then joined it. I rewrote with `ROW_NUMBER() OVER (ORDER BY ...)` CTE and a direct self-join. Also, temp tables force recompiles; table variables mostly don't. For EUV batch processing (200 transactions per run), a temp table with a clustered index on BatchId was perfect because we needed to update rows across multiple steps.

8. What is a deadlock and how do you resolve it?

- **Answer:** Deadlocks occur when two sessions hold locks the other needs. I use `SET DEADLOCK_PRIORITY` and trace flags 1222/1204 to capture deadlock graphs. Fixes: (1) access objects in the same order in all procedures, (2) keep transactions short, (3) use READ COMMITTED SNAPSHOT ISOLATION for read-heavy workloads, (4) add covering indexes to reduce lock duration. In DRMS, two procedures updated the same two tables in opposite order — aligning to TableA → TableB eliminated the deadlock.

- **If asked more:** I've also used `sp_getapplock` for application-level serialization around a critical loan disbursement workflow. The deadlock graph showed a key-range lock conflict on an insert-heavy table. Adding an index on the foreign key allowed row-level locks instead of page-level.

9. Explain transaction isolation levels.

- **Answer:** READ UNCOMMITTED (dirty reads), READ COMMITTED (default — no dirty reads, but non-repeatable reads), REPEATABLE READ (no dirty/non-repeatable reads, but phantom reads), SERIALIZABLE (fully isolated, but concurrency killer), SNAPSHOT (row versioning — no locks for reads). For PROXPERT's caching layer, we didn't need high isolation — most reads used READ UNCOMMITTED (or NOLOCK hints) since stale data was acceptable due to TTL expiration. For DRMS financial transactions, we used READ COMMITTED with SNAPSHOT for reporting queries to avoid blocking.

- **If asked more:** SNAPSHOT isolation uses tempdb version store, so I monitor version store cleanup and size. In DRMS, a long-running report with READ COMMITTED was blocking loan application inserts. Switching to RCSI resolved the blocking with no application code changes. The trade-off is 14-byte overhead per row in the version store.

10. What is a covering index and how do you design one?

- **Answer:** A covering index contains all columns needed by a query in either the key or INCLUDEd columns, so SQL Server doesn't need to touch the clustered index (no key lookup). I analyze the SELECT, WHERE, JOIN, and ORDER BY columns. In DRMS, I created: `CREATE INDEX IX_Loans_StatusDate ON Loans(Status, CreatedDate DESC) INCLUDE (LoanAmount, BorrowerName, BranchId)` — this served 90% of listing queries without touching the base table.

- **If asked more:** Key columns go in the index key (for seek/predicate pushdown), non-key columns go in INCLUDE. I keep key columns narrow. SQL Server's index usage stats (`user_lookups`) tell you if your covering index is effective. In EUV, I found a 12-column covering index that was overkill — split it into two narrower indexes for different query patterns.

11. How do you handle large data deletion without blocking production?

- **Answer:** I batch deletes in small chunks (e.g., 1000-5000 rows per batch) with a WAITFOR DELAY between batches. I use a WHILE loop with `DELETE TOP (@BatchSize)` and check `@@ROWCOUNT`. In DRMS, we had a loan archival job that needed to delete 2-year-old records from a 50M-row table — directly deleting would lock the table for minutes. I batched 5000 rows per iteration with a 1-second delay, running during off-peak.

- **If asked more:** I also considered partition switching: create a staging table, SWITCH out the old partition, then TRUNCATE (a metadata-only operation). For EUV compliance logs, we used partition switching with monthly partitions. Another pattern: delete into a "deleted" table for audit, then batch delete from the audit table when space is needed.

12. What is a recursive CTE and give a use case?

- **Answer:** A recursive CTE has an anchor member (base result) and a recursive member (references the CTE itself) with a UNION ALL. Typical use: employee hierarchy, BOM explosion, or category tree. In DRMS, loan officer hierarchy for approval routing used a recursive CTE: find the reporting chain from a given officer up to the branch manager for escalation approval.

- **If asked more:** I set `MAXRECURSION 0` (no limit) but with a depth guard column to avoid infinite loops. The DRMS hierarchy had max 5 levels: Officer → Sr. Officer → Manager → Branch Head → Regional Head. The CTE also calculated approval limits by summing cumulative authority at each level.

13. Explain statistics and why they matter.

- **Answer:** Statistics are histogram data on index key columns that SQL Server's optimizer uses to estimate row counts for plan choices (index seek vs scan, join type, etc.). Stale or missing statistics cause bad plans. I use `sp_updatestats` or set `AUTO_UPDATE_STATISTICS ON` but for large tables, I schedule manual updates. In DRMS, a 50M-row Loans table had outdated stats after bulk inserts — a query doing an equality seek chose a scan because it estimated 1 row but found 500K.

- **If asked more:** I check stats freshness with `STATS_DATE()`. For EUV, I used fullscan sampling on critical tables and default sampling for others. Ascending key columns (like date-based IDs) benefit from incremental statistics or trace flag 2371 to trigger update sooner. I also use filtered statistics on filtered indexes.

14. What's the difference between DELETE and TRUNCATE?

- **Answer:** DELETE is DML, logs each row, can have WHERE clause, triggers fire, and doesn't reset identity counter. TRUNCATE is DDL, deallocates data pages (minimally logged), can't filter, doesn't fire triggers, resets identity. In DRMS archival, we used DELETE with batching for selective cleanup. In EUV, we used TRUNCATE for staging tables after batch processing completed.

- **If asked more:** TRUNCATE requires higher permissions (ALTER table) and can't be used on tables referenced by FK. In a transaction, TRUNCATE can be rolled back but still uses fewer log resources. For PROXPERT's token cache cleanup, we used DELETE with batching to avoid blocking concurrent reads.

15. What is NOLOCK and when is it appropriate?

- **Answer:** NOLOCK (READ UNCOMMITTED) reads data without acquiring shared locks — no blocking but can read uncommitted (dirty) data, non-repeatable reads, and phantoms. Appropriate for reporting or dashboard queries where slight inconsistency is acceptable. In DRMS, I used NOLOCK on the loan listing page — showing a loan 2 seconds before it was fully committed was fine since the user would refresh. Never use it on financial calculations where accuracy matters.

- **If asked more:** Actually, NOLOCK can cause allocation-order scans that skip or double-count rows during page splits. For PROXPERT's token cache reads, NOLOCK was fine because TTL expiration provided eventual consistency. An alternative is READ COMMITTED SNAPSHOT which gives consistency without locks — we used that for DRMS reports.

16. How do you diagnose blocking chains?

- **Answer:** I use `sp_whoisactive` by Adam Machanic — it shows blocking_session_id, wait_info, and the actual query text. For deeper analysis: `sys.dm_exec_requests` joined with `sys.dm_exec_sessions` and `sys.dm_os_waiting_tasks`. I output the blocking chain by recursively following `blocking_session_id`. In DRMS, a nightly ETL was blocking user-facing loan lookups — we added NOLOCK hints to the ETL queries.

- **If asked more:** I also configure `BLOCKED_PROCESS_THRESHOLD` to fire an alert when a block exceeds 5 seconds. For persistent blockers, I capture deadlock graphs with trace flag 1222. In EUV, a long-running compliance update was blocking validation API calls — we moved the update to a background job with snapshot isolation.

17. What are wait statistics and how do you interpret them?

- **Answer:** `sys.dm_os_wait_stats` aggregates waits by type. Top wait types: PAGEIOLATCH_SH (disk I/O bottleneck — need index or hardware fix), LCK_M_XX (locking contention — need isolation or query tuning), CXPACKET (parallelism skew — need index or MAXDOP tuning), SOS_SCHEDULER_YIELD (CPU pressure). At DRMS, IORT_COMPLETION and PAGEIOLATCH_SH were >50% of waits — we moved hot indexes to SSD.

- **If asked more:** I take a baseline snapshot (`SELECT * INTO WaitStats_Base FROM sys.dm_os_wait_stats`), let it run during peak, then compare. I focus on waits that aren't benign (e.g., WAITFOR, BROKER_XXX). I also use `sp_BlitzFirst` for a quick health check. In EUV after index tuning, PAGEIOLATCH_SH dropped from 45% to 18%.

18. Explain the difference between clustered and non-clustered indexes.

- **Answer:** Clustered index determines physical row order — table data is the leaf level. One per table. Fastest for range scans. Non-clustered index is a separate structure with key values pointing to the clustered key (or RID for heaps). Multiple allowed. In DRMS, the Loans table had a clustered index on LoanId (identity, narrow, sequential — ideal). I added non-clustered indexes on Status, CreatedDate, and BorrowerId for different query patterns.

- **If asked more:** The leaf of a non-clustered index contains the clustered key (inclusive of all key columns). That's why narrow clustered keys are important — they're duplicated in every non-clustered index. In DRMS, I avoided turning a 50-byte composite key into the clustered index precisely because it would bloat all non-clustered indexes.

19. What is an execution plan and how do you read it?

- **Answer:** An execution plan shows the operations SQL Server performs (seeks, scans, joins, sorts) with operator costs. I read right-to-left, top-to-bottom (expensive operators first). I look for: table scans on large tables, key lookups, spools, hash matches (on non-equi joins), lazy spools. The actual plan (vs estimated) shows actual rows vs estimated — huge discrepancy means stale stats. In DRMS, the actual plan showed 100K rows estimated vs 2M actual — updated stats fixed it.

- **If asked more:** In SSMS, I hover over operators to see details: actual rows, estimated rows, I/O cost, CPU cost, number of executions. A nested loops join executing 50K times with a seek each time is often worse than a hash match that scans once. In EUV, I found a nested loops join repeating 14,000 times — replaced with a merge join after sorting the inputs.

20. What are common join types and when does SQL Server use each?

- **Answer:** Nested Loops: best for one small input (outer) and an index on the inner. Hash Match: best for large, unsorted inputs when no useful index exists. Merge Join: best for large, pre-sorted inputs (e.g., clustered index on join columns). At DRMS, most joins were Nested Loops with seek because indexes were properly designed. For the unsorted compliance batch in EUV, a Hash Match was the correct choice.

- **If asked more:** You can force join hints with `INNER LOOP JOIN`, `INNER HASH JOIN`, etc., but I prefer letting the optimizer choose with good indexes and stats. A Nested Loops join with 10 seek operations per row is catastrophic — that's when I check for missing indexes. In DRMS, one join had no index on the inner table's join column, causing a table scan per iteration — adding an index switched it to a seek.

21. What are window functions and give examples?

- **Answer:** Window functions perform calculations across a set of rows related to the current row without collapsing them. Common ones: `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `SUM() OVER`, `LAG()`, `LEAD()`. In DRMS, I used `ROW_NUMBER()` to deduplicate loan applications (pick the latest submission per borrower), and `SUM(Amount) OVER (PARTITION BY BorrowerId ORDER BY DueDate)` for running balance in the cursor replacement.

- **If asked more:** The `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` frame is default for ORDER BY in window aggregates. I used `LAG(Status)` to compare previous vs current status for audit trail generation. Window functions are generally faster than self-joins or cursors because they read the data once.

22. How do you optimize queries with multiple OR conditions?

- **Answer:** Multiple OR conditions often cause scans because the optimizer can't use a single index seek. Fixes: (1) rewrite as UNION ALL with separate queries per branch, (2) use IN clause (SQL Server can convert to OR but may still be better), (3) create individual indexes per condition and let optimizer choose, (4) use a full-text index for text searches. In EUV, a compliance query with `WHERE Status = 'A' OR Amount > 10000` was scanning — I rewrote as UNION ALL.

- **If asked more:** SQL Server can use an index union strategy (IndexOR) in some cases, but it's not guaranteed. The UNION ALL approach lets each subquery use its own best index. I also consider `IN` vs `OR` — SQL Server treats them the same, but IN is more readable. For DRMS's multi-status filter, `WHERE Status IN ('Active', 'Pending', 'UnderReview')` used a filtered index on those three values.

23. Explain the difference between WHERE and HAVING.

- **Answer:** WHERE filters rows before aggregation (per-row), HAVING filters after aggregation (group-level). WHERE is more efficient because it reduces rows entering the aggregate. In DRMS, `WHERE Status = 'Active' GROUP BY BranchId HAVING COUNT(*) > 100` — filtering active loans first, then showing branches with more than 100 active loans.

- **If asked more:** HAVING without GROUP BY works on the entire result as one group. Performance tip: push as much filtering into WHERE as possible. SQL Server can use indexes on WHERE columns but not on HAVING columns (post-aggregation).

24. How do you handle pagination efficiently in SQL Server?

- **Answer:** Avoid `OFFSET/FETCH` with large offsets — it still scans all skipped rows. Better: keyset pagination (seek method) using `WHERE Id > @LastId ORDER BY Id FETCH NEXT 50 ROWS ONLY`. For DRMS's loan listing, I used the seek method with the clustered index key — consistent and fast regardless of page number for the default sort. For custom sorts, I used a composite index matching the ORDER BY.

- **If asked more:** Keyset pagination requires a stable, unique sort column. I used `WHERE (CreatedDate, LoanId) < (@LastDate, @LastId)` for multi-column pagination. The old row_number approach with `WHERE rn BETWEEN 1 AND 50` scans the entire result before skipping — terrible for deep pages. PROXPERT's token audit pagination used keyset with the token creation timestamp.

25. What is a computed column and when would you use it?

- **Answer:** A computed column is derived from an expression on other columns. It can be PERSISTED (stored physically) or virtual (calculated on read). Good for: (1) indexed computed columns for queries that filter on expressions, (2) denormalizing derived values, (3) exposing calculated fields without application logic. In DRMS, I added a persisted computed column `AS CAST(CreatedDate AS DATE)` to enable efficient date-only grouping/indexing.

- **If asked more:** The computed column can be indexed if it's deterministic and precise. Indexing `CAST(CreatedDate AS DATE)` let me seek on date-only queries without wrapping the column in a function (which blocks index usage). In EUV, I used a computed column for `TotalAmount AS (Principal + Interest)` — persisted and indexed for the compliance listing page.

26. Explain execution plan caching and plan reuse.

- **Answer:** SQL Server caches execution plans in the plan cache to avoid recompilation. Plans are identified by the query hash of the batch. Ad-hoc queries with different literals don't reuse plans — that's why parameterized queries or `sp_executesql` are better. Simple parameterization auto-parameterizes some queries. In DRMS, all stored procedures used parameters, guaranteeing plan reuse. For ad-hoc reporting, I enabled forced parameterization.

- **If asked more:** Plan cache bloat can cause memory pressure. I monitor `sys.dm_exec_cached_plans` and use `DBCC FREEPROCCACHE` selectively (with plan handle, not globally). Single-use plans are the biggest waste — I identify them with `SELECT objtype, COUNT(*) FROM sys.dm_exec_cached_plans GROUP BY objtype` and look for high ad-hoc counts.

27. What is a scalar UDF and why is it problematic?

- **Answer:** A scalar UDF returns a single value per call. The problem: it's a black box to the optimizer — it can't estimate cost, inline it, or use parallelism. It executes row-by-row (RBAR). In DRMS, `fn_GetLoanStatus()` was called in a WHERE clause on a 2M-row table, effectively running 2M separate queries. I replaced it with an inline table-valued function or direct expression.

- **If asked more:** SQL Server 2019 introduced F_ID (Froid) that can inline some scalar UDFs, but it's not always safe. I prefer inline TVFs (returns a table, optimizer can inline the definition) or CTEs. For DRMS, the UDF contained a simple lookup — `LEFT JOIN` on the lookup table was the correct replacement and ran in a single set operation.

28. What is the difference between CHAR and VARCHAR?

- **Answer:** CHAR is fixed-length (padded with spaces), VARCHAR is variable-length (2-byte overhead for length). CHAR is slightly faster for fixed-length data (no length byte processing) but wastes space if values vary. VARCHAR saves space but has a tiny overhead. In DRMS, I used CHAR(6) for loan application codes (always alphanumeric, fixed format), VARCHAR for borrower names (variable length).

- **If asked more:** For performance, CHAR can be faster for short, fixed-length strings because SQL Server knows exact size. But disk/memory savings of VARCHAR usually win for variable data. A VARCHAR column with average length 10 but max 255 wastes more space than expected if values are near max. In EUV, status codes (1-3 chars) used CHAR(3) — waste minimal, performance edge.

29. Explain the difference between VARCHAR and NVARCHAR.

- **Answer:** VARCHAR stores non-Unicode (1 byte per char), NVARCHAR stores Unicode (2 bytes per char). Use VARCHAR unless you need to support international characters (Arabic, Chinese, etc.). NVARCHAR doubles storage and reduces page density, hurting performance. In DRMS, borrower names used NVARCHAR (supporting Arabic names). Internal status codes used VARCHAR.

- **If asked more:** Implicit conversion between VARCHAR and NVARCHAR blocks index usage (the conversion on the column side). In EUV, I found an NVARCHAR column being compared to a VARCHAR parameter — adding "N" prefix or aligning data types fixed a scan-to-seek conversion.

30. What are the different types of keys in SQL Server?

- **Answer:** Primary Key (unique, clustered by default, identifies each row), Foreign Key (referential integrity), Unique Key (unique non-clustered by default, allows one NULL), Composite Key (multiple columns). In DRMS, LoanId was PK, BorrowerId and BranchId were FKs referencing their tables. The approval table had a composite PK on (LoanId, ApprovalLevel).

- **If asked more:** Surrogate keys (identity column) vs natural keys (business-meaningful). I prefer surrogate PKs for stability (business keys can change) with unique constraints on natural keys. In DRMS, loan application codes were the natural key but could be reused after archiving — so a surrogate LoanId identity column was the PK.

31. Explain the benefits of database normalization and when to denormalize.

- **Answer:** Normalization (up to 3NF) eliminates data redundancy, ensures consistency, and simplifies updates. Denormalization reduces JOINs for read-heavy queries. In DRMS, the loan listing schema was normalized (Loans, Borrowers, Branches, LoanOfficers). I denormalized LoanStatusName into the Loans table (from a lookup table) because the listing page joined it 100% of the time and status names rarely changed.

- **If asked more:** I followed 3NF for transactional tables (loan applications, disbursements) to maintain integrity. For reporting/listing views, I used indexed views or denormalized summary tables. In EUV, compliance check results were denormalized into a single flat table for fast queries — but the source data remained normalized.

32. What is the difference between a primary key and a unique key?

- **Answer:** Primary Key: unique, non-null, one per table, clustered by default. Unique Key: unique, allows one NULL, creates a non-clustered index by default. In DRMS, LoanId (PK) guaranteed every loan had a unique identifier. Email (Unique Key) on Users table ensured unique login but allowed one system account with NULL email.

- **If asked more:** Both enforce uniqueness at the constraint level. The PK is the row identifier — FK references point to PKs. Unique keys can be referenced by FKs too but less common. In PROXPERT, the token cache used a PK on TokenId and a Unique Key on (UserId, TokenType) to prevent duplicate sessions.

33. How do you monitor and detect long-running queries?

- **Answer:** I use a combination: `sys.dm_exec_requests` for current long-running queries, `sys.dm_exec_query_stats` for historical patterns, and alerts via SQL Agent jobs that check thresholds (e.g., `WHERE total_elapsed_time > 30000`). In DRMS, I created a dashboard query showing top-10 queries by average duration from the last hour. I also set up extended events to capture queries exceeding 5 seconds.

- **If asked more:** The DRMS alerting job sent an email when a loan listing query exceeded 60 seconds — that's how I caught the regression after a schema change. In EUV, I used Query Store to track query performance over time, which made it easy to compare before/after index changes.

34. What is a key lookup and how do you eliminate it?

- **Answer:** A key lookup occurs when a non-clustered index doesn't cover all columns in the query — SQL Server has to fetch the missing columns from the clustered index. It shows as a "Key Lookup" operator in the plan with a 99.9% cost. Eliminate by making it a covering index (INCLUDE missing columns) or creating a new non-clustered index. In DRMS, I added INCLUDE columns to existing indexes to eliminate lookups.

- **If asked more:** Key lookups are per-row operations. If a non-clustered index returns 50K rows, that's 50K separate lookups — each seemingly small but cumulatively expensive. The INCLUDE clause adds columns at the leaf level without enlarging the index tree. In EUV, I added `INCLUDE (ComplianceResult, ReviewedBy)` to eliminate lookups on the compliance check index.

35. Explain the concept of SARGability.

- **Answer:** SARGable (Search ARGument-able) means a query predicate can use an index seek rather than scan. Wrapping columns in functions breaks SARGability: `WHERE YEAR(CreatedDate) = 2024` is not SARGable, `WHERE CreatedDate >= '2024-01-01' AND CreatedDate < '2025-01-01'` is. In DRMS, `WHERE DATEDIFF(day, CreatedDate, GETDATE()) > 30` was scanning — rewrote to `WHERE CreatedDate < DATEADD(day, -30, GETDATE())` which used the index.

- **If asked more:** Other non-SARGable patterns: `WHERE LEFT(Name, 3) = 'ABC'`, `WHERE Column + 1 = @val`, `WHERE Column LIKE '%pattern'` (leading wildcard). Implicit conversions also break SARGability (varchar to nvarchar). In EUV, I fixed `WHERE CAST(ComplianceDate AS DATE) = '2024-01-01'` by comparing with a range.

36. What's the difference between HAVING and WHERE in a GROUP BY query?

- **Answer:** WHERE filters rows before group/aggregate, HAVING filters groups after. In DRMS: `SELECT BranchId, COUNT(*) FROM Loans WHERE Status = 'Active' GROUP BY BranchId HAVING COUNT(*) > 100` — WHERE reduces input to active loans, HAVING filters branches with >100 active loans.

- **If asked more:** HAVING without GROUP BY treats the whole result as one group. Query optimizer can't push HAVING predicates to WHERE because HAVING might reference aggregates. For performance, maximize WHERE filtering.

37. What is a trigger and what are its downsides?

- **Answer:** A trigger is a special stored procedure that fires automatically on INSERT/UPDATE/DELETE. Downsides: (1) invisible logic — devs forget it exists, (2) multi-table triggers compound, (3) they execute in the same transaction (locking issues), (4) can cause unexpected recursion, (5) hard to debug. In DRMS, I replaced an audit trail trigger with explicit logging in the application layer for better transparency.

- **If asked more:** If triggers are necessary, I make them simple — one action, no cursor, no cross-database calls. I use `DISABLE TRIGGER` during bulk operations and re-enable. An INSTEAD OF trigger on a view can be useful for making complex views updateable. In EUV, I used an AFTER INSERT trigger on compliance logs to update a summary table — simpler than scheduling an ETL job.

38. What are the different types of joins in SQL Server?

- **Answer:** INNER JOIN (matching rows only), LEFT JOIN (all left rows, NULL on right if no match), RIGHT JOIN (opposite), FULL OUTER JOIN (all rows from both), CROSS JOIN (Cartesian product). In DRMS, the Loan Listing used LEFT JOIN on Borrower — a loan should show even if borrower data was incomplete.

- **If asked more:** Performance ordering (roughly): INNER JOIN fastest with good indexes, then LEFT JOIN (same if index seek), then FULL OUTER JOIN (often requires hash match). CROSS JOIN is useful for test data generation. I avoid RIGHT JOIN — I always flip to LEFT JOIN for readability. In EUV, I used CROSS APPLY to get the latest compliance check per transaction (similar to join but with a correlated subquery).

39. Explain the difference between UNION and UNION ALL.

- **Answer:** UNION removes duplicates (adds a DISTINCT sort), UNION ALL keeps all rows. UNION ALL is faster because it skips the dedup. In DRMS, a report combining active and pending loans used UNION ALL because the two sets were mutually exclusive by definition. If duplicates are possible, I first evaluate whether they matter — often they don't, and UNION ALL is the right choice.

- **If asked more:** UNION performs a Sort or Hash Match to remove duplicates — on large datasets, that's significant overhead. For DRMS quarterly reports, switching from UNION to UNION ALL reduced report generation time from 45s to 28s. Use UNION only when deduplication is semantically required.

40. What is the difference between clustered columnstore and rowstore?

- **Answer:** Rowstore stores data row-by-row (good for OLTP — point lookups, small writes). Columnstore stores column-by-column (good for OLAP — compression, aggregation, large scans). Columnstore can have 10x compression. In DRMS, transaction tables used rowstore. For EUV's compliance analytics dashboard, I considered a clustered columnstore index on the audit table — but the table also had point lookups, so I used a non-clustered columnstore index (NCCI) instead.

- **If asked more:** Clustered columnstore is the primary storage — best for tables where all queries are analytical. NCCI (non-clustered) sits alongside rowstore — updates go to the rowstore portion (delta store) and eventually compressed. SQL Server 2019+ has batch mode on rowstore, narrowing the gap. For DRMS, the 50M-row loan archive table would benefit from columnstore for archival reports.

41. How do you configure and manage SQL Server Agent jobs?

- **Answer:** SQL Server Agent handles scheduled jobs (backups, index maintenance, stat updates, ETL). I create job steps with proper error handling — `ON FAILURE GO TO NEXT STEP` for retries, notification on failure. DRMS had a nightly job: step 1 — updatestats, step 2 — reorg indexes if fragmentation >10%, step 3 — archive old audit records, with email alerts on failure.

- **If asked more:** I use operators (email profiles) for notifications, and set up job schedules carefully to avoid overlapping. For critical jobs, I add a step checking if the previous run is still active and exit if so. PROXPERT had a Redis cache refresh job that ran every 6 hours — with alerts if it took >5 minutes.

42. Explain backup types and your recovery strategy.

- **Answer:** Full backup (complete database), Differential (changes since last full), Transaction Log (point-in-time recovery). My strategy: Full weekly, Differential daily, Log every 15-30 minutes for critical systems. DRMS was a financial system — RPO of 15 minutes, RTO of 4 hours. We used Ola Hallengren's maintenance scripts for consistency. I test restores quarterly.

- **If asked more:** Recovery model: SIMPLE (no log backups, minimal logging), FULL (point-in-time recovery, log grows). DRMS used FULL with regular log backups to prevent log explosion — a critical concern after a developer ran a 200M-row update without proper batching. BULK_LOGGED during large ETL operations (index rebuilds, bulk inserts) then back to FULL.

43. What is database mirroring and Always On Availability Groups?

- **Answer:** Database Mirroring: two servers (principal + mirror), automatic failover with witness, no readable secondary. Always On AG: up to 9 replicas, readable secondaries (good for reporting offload), listener for transparent failover, supports multiple databases per group. DRMS used Always On AG with one primary for writes and two readable secondaries for reporting queries.

- **If asked more:** AG requires Windows Failover Cluster and domain-joined servers. I configured read-only routing on the listener to direct reporting queries to secondaries. Synchronous commit for zero data loss (primary + one sync secondary), async for remote DR. In DRMS, we used SQL Agent alerts for AG health monitoring.

44. How do you handle data encryption in SQL Server?

- **Answer:** Options: TDE (transparent data encryption — encrypts data at rest, no app changes), Always Encrypted (column-level, client-side encryption — data is never in plaintext to SQL Server), SSL/TLS for connections. DRMS used TDE for the entire database (regulatory requirement for financial data) and Always Encrypted for sensitive PII columns (PAN, SSN).

- **If asked more:** TDE uses a DEK (Database Encryption Key) protected by certificate stored in master db. Performance overhead is ~3-5% with modern hardware. Always Encrypted has more overhead — only use for truly sensitive columns. I managed key rotation with Azure Key Vault integration. For PROXPERT, JWT tokens were encrypted at rest using TDE on the token audit table.

45. What is Query Store and how do you use it?

- **Answer:** Query Store captures query plans, runtime stats, and wait stats per query. I use it for: (1) identifying regressions with "Tracked Queries" view, (2) forcing a good plan when parameter sniffing causes a bad one, (3) analyzing top resource-consuming queries over time. In EUV, Query Store helped me catch a plan regression after a stat update — the new plan switched from seek to scan.

- **If asked more:** I set `QUERY_CAPTURE_MODE = AUTO` to avoid capturing one-off queries. `MAX_STORAGE_SIZE_MB = 500` on DRMS with `DATA_FLUSH_INTERVAL_SECONDS = 900`. When a plan regresses, I use `sp_query_store_force_plan` to pin the known-good plan. I also run the "Overall Resource Consumption" report weekly.

46. Explain static vs dynamic data masking.

- **Answer:** Static Data Masking (SDM) creates a masked copy of the database (for dev/test). Dynamic Data Masking (DDM) masks data at query time based on user permissions — no copy needed. In DRMS, DDM was applied on PAN numbers and borrower phone numbers — unauthorized users see masked values (e.g., `XXXX-XXXX-1234`), authorized users see full data.

- **If asked more:** DDM is not encryption — privileged users (db_owner) see unmasked data. It's a compliance layer to prevent accidental exposure. The masking functions: default (filler), email (mask format), partial (expose first/last N chars), random. It doesn't affect indexing — the full value is indexed. In DRMS, DDM was part of our multi-layer data protection strategy.

47. What are the different types of SQL Server indexes?

- **Answer:** Clustered, Non-clustered, Unique, Filtered, Columnstore, Full-text, Spatial, XML, Hash (memory-optimized). Each for different use cases. In DRMS: clustered (LoanId), non-clustered (Status, CreatedDate), filtered (active loans), full-text (borrower name search). In EUV: columnstore (considering for compliance analytics), spatial (not needed).

- **If asked more:** Filtered indexes are underutilized — they're great for query predicates that filter on a specific status or boolean. In DRMS, a filtered index on `WHERE IsArchived = 0` served the active loan listing perfectly and was much smaller than a full index. Hash indexes are for in-memory OLTP — not used in our projects.

48. How do you implement row-level security in SQL Server?

- **Answer:** Row-Level Security (RLS) uses a security policy with a predicate function that filters rows based on `SESSION_CONTEXT()` or `USER_NAME()`. In DRMS, a loan officer could only see loans assigned to their branch. The predicate function checked the user's branch ID from `SESSION_CONTEXT()` set by the application after authentication:

```sql
CREATE FUNCTION dbo.fn_BranchFilter(@BranchId INT) RETURNS TABLE
RETURN SELECT 1 AS Access WHERE @BranchId = CAST(SESSION_CONTEXT(N'BranchId') AS INT)
```

- **If asked more:** RLS eliminates the need to add WHERE clauses to every query for multi-tenant security. It's enforced regardless of the query tool (SSMS, Excel). In PROXPERT, RLS was used with the dynamic RBAC system — each role had different row visibility rules. Performance impact is minimal when predicates are simple.

49. How do you manage schema changes in production?

- **Answer:** I use versioned deployment scripts (Flyway or custom) with checksums to track applied migrations. Each script is additive (no destructive changes without migration step). For DRMS: (1) deploy new columns/indexes as nullable/default first, (2) deploy application code using them, (3) backfill data in batches, (4) make column NOT NULL or drop old. I always test rollback scripts.

- **If asked more:** For the DRMS schema migration that added a new approval_status column, we: added column NULL, deployed app code (writes new, reads old/new), backfilled 500K rows in 5K batches, then altered to NOT NULL with a default. A schema change that requires table rebuild (ALTER TABLE ALTER COLUMN) was scheduled during maintenance windows with replication failover.

50. What tools do you use for SQL Server monitoring and optimization?

- **Answer:** Built-in: `sp_whoisactive`, `sys.dm_exec_query_stats`, `sys.dm_db_index_usage_stats`, Query Store, Extended Events. Third-party: SentryOne (now SolarWinds DPA) for historical analysis, SQL Monitor (Redgate) for alerting. In DRMS, I set up a PowerShell script that ran `sp_whoisactive` every 30 seconds during peak hours, logging to a table for later analysis. For EUV, I used the built-in reports heavily.

- **If asked more:** Extended Events are lighter than Profiler — I use them to capture deadlock graphs, long-running queries, and login failures. For index tuning, I use `sys.dm_db_missing_index_details` as a starting point but verify with actual workload patterns. In DRMS, the missing index DMV suggested an index on a low-selectivity column (bit) — I ignored it because the scan cost was acceptable.

## Authentication, Authorization, RBAC, OAuth2 and JWT Questions

1. Explain how you implemented LDAP-based SSO in DRMS.

- **Answer:** I integrated LDAP SSO using `System.DirectoryServices.Protocols` in .NET. When a user accesses DRMS, they're redirected to the corporate IdP. Successful auth returns a SAML token, which I validate against the enterprise LDAP store. I extract user attributes (employee ID, name, email, department, branch, role group) from the LDAP response, sync them to the DRMS user table, and generate a local session. This eliminated separate login credentials — 2,100+ users authenticate through their existing Windows AD credentials.

- **If asked more:** The SSO flow: user → DRMS → redirect to ADFS → LDAP bind → SAML response → DRMS validates signature → checks user exists in local DB (auto-create if new) → issues session token → redirects to landing page. I handled the case where a user is disabled in AD by checking `userAccountControl` flags. For logout, I implemented both local session clearing and IdP-initiated logout (SLO). The challenge was syncing LDAP group membership changes — I used a background job that updates role assignments every 15 minutes from AD.

2. How did you design multi-tier RBAC for 2,100+ users?

- **Answer:** I designed a three-tier RBAC: (1) **System-Level**: IT admin, Auditor, Read-Only — global roles with no domain restrictions. (2) **Branch-Level**: Branch Manager, Loan Officer, Operations — scoped to one or more branches. (3) **Function-Level**: Approver levels (L1, L2, L3) with specific permission bits — CreateLoan, ApproveLoan, DisburseLoan, CancelLoan, ViewReports. Permissions were stored as bitmask flags in a `Roles` table, assigned via `UserRoleAssignments` with branch scope. A user could have multiple role assignments — the effective permission was the union of all roles.

- **If asked more:** The permissions table: `CREATE TABLE Permissions (PermissionId INT, PermissionName VARCHAR(50), PermissionBit INT, Module VARCHAR(50))`. Role-Permission mapping used bitwise AND at query time (fastest). For 2,100+ users with average 2.5 role assignments each, the query was a single JOIN with a bitwise check. The permission check was executed at the API filter level using a custom `[AuthorizePermission(Permission.ApproveLoan)]` attribute. For the mid-approval cancellation feature, I added a special `CancelInProgress` permission that only L3 approvers had — with audit trail of who cancelled and why.

3. Compare OAuth2 and JWT — how did you use them in PROXPERT?

- **Answer:** OAuth2 is the authorization **framework** (four grant types for token issuance), JWT is the **token format** (self-contained, JSON payload, cryptographically signed). In PROXPERT, I implemented OAuth2 with authorization code grant + PKCE for the web app and client credentials for machine-to-machine integrations. The access token was a JWT containing user claims (UserId, Roles, Permissions bitmask, BranchIds). The token was signed with RS256 (asymmetric) using a private key on the auth server, public key on resource servers for offline validation.

- **If asked more:** The JWT structure: header (alg=RS256, typ=JWT), payload (sub=UserId, roles=[], permissions_bitmask=0x..., branch_ids=[], exp, iat, jti, iss), signature. I set access token TTL to 15 minutes and refresh token TTL to 7 days (rotated on use). The OAuth2 flow: frontend redirects to auth endpoint → user logs in → auth code returned → frontend exchanges code + PKCE verifier for token → token stored in memory (not localStorage) → attached as `Authorization: Bearer <token>` on all API calls. The STS (Security Token Service) was a separate .NET Core service with its own database.

4. Explain the OAuth2 authorization code grant flow with PKCE.

- **Answer:** (1) Client generates a `code_verifier` (random string) and `code_challenge` (SHA256 hash of verifier, Base64URL encoded). (2) Browser redirects to auth server with `response_type=code&code_challenge=<hash>`. (3) User authenticates and consents. (4) Auth server returns auth code to redirect URI. (5) Client sends auth code + original `code_verifier` to token endpoint. (6) Auth server verifies verifier matches challenge hash, returns JWT access token + refresh token. PKCE prevents auth code interception even without client secret — I used this in PROXPERT for the SPA frontend.

- **If asked more:** The `code_challenge_method` was S256 (SHA256), not `plain` (which sends the verifier as-is). I also set `code_challenge` to expire after 10 minutes. The SPA never saw the client secret — only the `client_id`. For the PROXPERT mobile app, I used the same flow with AppAuth library. The refresh token was stored in the keychain and rotated on each use (old token invalidated, new one issued) to prevent replay attacks.

5. How do JWT signatures work and which algorithm did you use?

- **Answer:** JWT has three parts: header.payload.signature. I used RS256 (RSA with SHA-256, asymmetric). The auth server signs with its private key, resource servers verify with the public key — no shared secret, no need for resource servers to call auth server on every request. The signature is computed on `base64UrlEncode(header) + "." + base64UrlEncode(payload)`. Verification: decode header to get `kid` (key ID), fetch corresponding public key from the JWKS endpoint, verify signature using RSA.

- **If asked more:** HS256 (HMAC with shared secret) is simpler but requires the resource server to know the secret — breaking the OAuth2 separation of concerns. With RS256, any service can validate tokens without talking to the auth server. I rotated signing keys quarterly — keeping the previous public key in the JWKS during overlap so tokens signed with the old key still validate until expiration. I also implemented a token revocation list (check `jti` against a Redis set) for immediate invalidation of compromised tokens.

6. How did you secure the email-based approval with Outlook Actionable Messages?

- **Answer:** Outlook Actionable Messages allow users to take actions (Approve/Reject) directly from email. I registered a "Actionable Email" connector with Microsoft via the Developer Dashboard. Each approval email contained a `card` with actions that posted to a secure endpoint in DRMS. The security: (1) Microsoft sends a signed JWT in the `activity` payload (validated against Microsoft's public keys — RS256), (2) the originator email (sender) was verified against the loan application's assigned approver, (3) I checked the action timestamp against the approval window (24-hour expiry), (4) the action had a nonce (`approvalId`) preventing replay.

- **If asked more:** The Actionable Message card was JSON within the email's `X-Microsoft-ActionableMessages` header. Validation: `https://api.actions.microsoft.com/` provided the signing keys via JWKS. The card also included target context (loan ID, status) so the backend could validate that the action was still applicable. For mid-approval cancellation, the email included a "Cancel This Request" action visible only to the originator and L3 approvers — clicking it would trigger the cancellation workflow with audit trail.

7. What's the difference between Authentication and Authorization?

- **Answer:** Authentication (AuthN) verifies **who** you are — "Are you who you claim to be?" Authorization (AuthZ) verifies **what** you can do — "Do you have permission to perform this action?" In DRMS, authentication was handled by LDAP SSO (proving identity). Authorization was the RBAC system (checking if the authenticated user with role X can approve loans > $50K). In PROXPERT, authentication was OAuth2 + JWT, authorization was the dynamic RBAC with permission bitmasks.

- **If asked more:** They're two separate concerns. A user can be authenticated (valid JWT) but unauthorized for a specific endpoint (returns 403). In the DRMS API pipeline: the authentication middleware validates the JWT/LDAP session and populates `HttpContext.User`, then the authorization middleware checks permission requirements. I always return 401 for unauthenticated (no token/missing/invalid) and 403 for unauthorized (valid token but insufficient permissions).

8. Explain refresh token rotation and why it matters.

- **Answer:** Refresh token rotation means every time a refresh token is used, the auth server issues a new refresh token and invalidates the old one. This limits the window of exposure — if a refresh token is stolen, the attacker can use it only until the legitimate user (or the attacker) refreshes next. In PROXPERT, I implemented rotation: on each `/token` call with a refresh token, the server validates it, issues new access + refresh tokens, and sets the old refresh token's status to "Used". If a used refresh token is presented again, all tokens for that user are revoked (assuming breach).

- **If asked more:** The detection of "used" token replay triggers an immediate revocation of all user sessions and forces re-authentication. I stored refresh tokens in a database table with columns: `UserId`, `RefreshToken` (hashed), `ExpiresAt`, `Status` (Active/Used/Revoked), `DeviceInfo`, `CreatedAt`. This also enabled "log out all devices" functionality. My refresh token TTL was 7 days — relatively short for financial systems.

9. How do you prevent JWT token theft?

- **Answer:** (1) Short-lived access tokens (15 minutes) — limited window of exposure. (2) Store tokens in memory or httpOnly cookies, never localStorage (XSS vulnerability). (3) Use token binding (optional in JWT: include `cnf` claim with a public key hash of the client). (4) Refresh token rotation with reuse detection. (5) Implement a token revocation list for critical events (password change, logout, suspected breach). (6) Use HTTPS-only — no token over unencrypted connections. In PROXPERT, the SPA stored access tokens in JavaScript memory (variable), refresh tokens in httpOnly secure sameSite=Strict cookies.

- **If asked more:** Token binding ties the token to the TLS session — even if stolen, it can't be used from a different connection. I considered it but the complexity of managing client key material was high. Instead, I relied on short TTL, rotation, and strict CORS. For the email approval system, each `activity` JWT had an `iat` claim checked against the current time ± 5 minutes to prevent replay.

10. What claims should a JWT contain and what shouldn't it contain?

- **Answer:** Should contain: `sub` (user ID), `iat` (issued at), `exp` (expiration), `jti` (unique token ID — for revocation), `iss` (issuer), `aud` (audience). Custom claims: `roles`, `permissions_bitmask`, `name`, `email` — but only what's needed for authorization decisions. Should NOT contain: passwords, secrets, full profile data, or anything that changes frequently (DB hits for data not needed on every request). In PROXPERT, the JWT contained `sub`, `roles[]`, `permissions`, `branch_ids`, `exp`, `iat`, `jti` — enough for offline authorization without DB calls.

- **If asked more:** JWT payload is base64-encoded, not encrypted (unless using JWE). Anyone with the token can decode and read claims — that's why sensitive data should never be there. For the DRMS email approval JWT, I included the `approvalId` and `loanId` in the claims so the backend could validate without a separate lookup. The JWT size matters too — large payloads cause HTTP header overhead.

11. How did you implement dynamic RBAC in PROXPERT?

- **Answer:** Dynamic RBAC means roles and permissions can be created/modified at runtime without code changes. I designed: `Roles (Id, Name, Description)`, `Permissions (Id, Name, PermissionBit)`, `RolePermissions (RoleId, PermissionId)` with a bitmask cached in Redis. `UserRoles (UserId, RoleId, ScopeBranchId)`. Permissions were bit flags (32-bit int for up to 32 permissions), making authorization checks a simple bitwise AND. The CMS allowed admins to create new roles, assign any combination of permissions, and scope them to branches. This served 6+ roles (IT Admin, Branch Manager, Sr. Loan Officer, Loan Officer, Operations, Auditor) with no code changes.

- **If asked more:** The bitmask approach: `int.MaxValue = 2,147,483,647` — 32 permission slots. The permission constant: `[Flags] public enum Permissions { CreateLoan = 1, ApproveLoan = 2, DisburseLoan = 4, CancelLoan = 8, ... }`. The check: `(user.PermissionBitmask & Permission.ApproveLoan) == Permission.ApproveLoan`. For more than 32 permissions, I could switch to 64-bit long or use the bitmask in a BigInteger. The dynamic part: when admin creates a new permission in the CMS, the enum is not updated — actually, it's stored as a DB row and the client-facing permission name is mapped. The enum is only for the C# code — both approaches coexist.

12. Explain the difference between RBAC and ABAC.

- **Answer:** RBAC (Role-Based Access Control) grants permissions based on a user's role(s). Simple, predictable, widely used. ABAC (Attribute-Based Access Control) evaluates policies based on user, resource, action, and environment attributes (time of day, location, risk score, etc.). More flexible but complex. DRMS used RBAC — sufficient for the loan lifecycle with well-defined roles. ABAC would be needed if we had policies like "approvals over $100K need two L2 approvers AND cannot be done between 10 PM and 6 AM."

- **If asked more:** ABAC policy example: `PERMIT access TO LoanOfficer TO ApproveLoan IF loan.Amount < 50000 AND currentTime BETWEEN '06:00' AND '22:00' AND branch.region NOT IN ('Restricted')`. I'd use a policy engine like PolicyServer or OPA for this. For PROXPERT, I considered ABAC for the token security processing but RBAC was simpler and met all requirements. The audit trail recorded the attributes at the time of decision — enabling retrospective ABAC compliance checks.

13. What is a claims-based identity model?

- **Answer:** Claims-based identity means the identity provider (IdP) issues claims — statements about the user — into a token. The application trusts these claims for authorization decisions instead of querying a user store on every request. In DRMS, the LDAP SSO issued claims: `employeeId`, `department`, `branch`, `groupMembership`. In PROXPERT, the JWT contained claims: `sub`, `roles`, `permissions`. The application makes decisions based on claim values, not database lookups.

- **If asked more:** Claims are more flexible than roles alone. Two users with role "LoanOfficer" might have different claim scopes (`branch_id: 101` vs `branch_id: 102`). In .NET, `ClaimsPrincipal` is the foundation — `User.FindFirst("branch_id")?.Value`. Claims transformations (custom middleware) can enrich or transform claims from external providers. For DRMS, I added a claims transformer that enriched the LDAP-issued identity with local role assignments from the DRMS database.

14. How do you handle token expiration and silent refresh in SPAs?

- **Answer:** In the PROXPERT SPA (React), I set up an Axios interceptor: on 401 response (expired token), it calls the `/token` endpoint with the refresh token (stored in httpOnly cookie). If successful, the new access token is stored in memory and the original request is retried. If refresh fails (refresh expired or revoked), redirect to login. I used `if (originalRequest && !originalRequest._retry)` flag to avoid infinite loops. The refresh call itself excluded from the interceptor.

- **If asked more:** Silent refresh happens automatically — no user interaction needed. The challenge is race conditions: multiple API calls failing simultaneously with 401. I used a promise queue: the first 401 triggers the refresh, subsequent 401s wait for the same refresh promise, then all retry with the new token. The pattern:

```javascript
let refreshPromise = null;
axios.interceptors.response.use(resp => resp, async error => {
  if (error.response?.status === 401 && !error.config._retry) {
    if (!refreshPromise) refreshPromise = refreshToken();
    const newToken = await refreshPromise;
    error.config.headers.Authorization = `Bearer ${newToken}`;
    return axios(error.config);
  }
});
```

15. What is the Principle of Least Privilege and how did you apply it?

- **Answer:** Every user/process should have the minimum permissions necessary to perform their function. In DRMS: Loan Officers could only create and view their own branch's loans (not modify or approve). Approvers could only approve loans within their authority limit ($50K for L1, $200K for L2, unlimited for L3). The IT admin had no loan access — only system configuration. Auditors had read-only access to all loans. Branch Managers could view all loans in their branch but not approve their own created loans (segregation of duties).

- **If asked more:** Least privilege reduces blast radius. A compromised Loan Officer account couldn't approve a loan or access other branches' data. In PROXPERT, the token processing service had a separate service account with only `token:validate` permission — not `token:revoke` or `token:create`. For the email approval system, the Actionable Messages endpoint only accepted approvals from the designated approver's email — not from anyone with the link.

16. Explain OAuth2 scopes and how they differ from roles.

- **Answer:** Scopes define **what** the access token can do on behalf of the user — they're granular permission boundaries for APIs. Roles define **who** the user is in the system. A scope might be `loans:read` or `loans:write`. A role might be "LoanOfficer". In PROXPERT, a user with role "LoanOfficer" might request a token with scope `loans:read` (for read-only dashboard) or `loans:read loans:write` (for full operations). Scopes are enforced at the API level — the user can only request scopes their role allows.

- **If asked more:** Scope names follow `resource:action` convention. In the OAuth2 flow, the client requests specific scopes during authorization. The user sees a consent screen: "Allow App to Read your loans and Write your loans." The resulting JWT has a `scope` claim: `"loans:read loans:write"`. My API middleware checks both: (1) does the token have the required scope? (2) does the user have the required role/permission? This adds a layer of protection — even if a role is compromised, the token scope restricts what the token can do.

17. How do you implement MFA in a .NET application?

- **Answer:** I implemented TOTP-based MFA using `Otp.NET` library. Flow: (1) User authenticates with username/password (or LDAP SSO). (2) If MFA is enabled, a one-time code is sent to the user's registered authenticator app (Google Authenticator, Microsoft Authenticator). (3) The generated TOTP code (30-second window, 6 digits) is validated server-side against the user's secret key (stored encrypted in DB). (4) On successful validation, the JWT is issued with a `mfa_verified` claim. For SMS/email OTP, I used a random 6-digit code stored in Redis with 5-minute TTL.

- **If asked more:** The registration flow: admin generates a QR code (provisioning URI) containing the secret, user scans with authenticator app, then provides a TOTP code to verify setup. The secret is encrypted using `DataProtectionProvider` before storing. For rate limiting OTP attempts, I used a Redis-based counter — max 5 attempts per 15 minutes. For DRMS, MFA was mandatory for L2 and L3 approvers — high-value transactions required MFA-verifed JWT.

18. What is CSRF and how do you prevent it?

- **Answer:** CSRF (Cross-Site Request Forgery) tricks a user into submitting requests from another site while authenticated. Prevention: (1) Anti-CSRF tokens (synchronizer token pattern), (2) SameSite cookies (Strict/Lax), (3) Custom headers (require `X-CSRF-TOKEN` header checked server-side), (4) Origin/Referer headers validation. In PROXPERT, I used SameSite=Strict cookies for the refresh token and anti-forgery tokens for POST/PUT/DELETE endpoints using the built-in `[AutoValidateAntiforgeryToken]` attribute.

- **If asked more:** For the API (not MVC), the SPA sent the anti-CSRF token in a custom header. .NET Core's Anti-Forgery middleware generates a cookie + hidden request token that must match. For the OAuth2 flow, CSRF is prevented by the `state` parameter — a random value stored in session before redirect, verified on callback. This was critical for the DRMS SSO login — the `state` parameter ensured the callback matched the original request.

19. Explain XSS and how you mitigated it in PROXPERT.

- **Answer:** XSS (Cross-Site Scripting) injects malicious scripts into web pages viewed by others. Mitigations: (1) Output encoding — Razor auto-encodes, React's JSX prevents injection by default. (2) Content-Security-Policy headers — `script-src 'self'` blocks inline scripts. (3) httpOnly cookies — prevents JavaScript access to session cookies. (4) Input sanitization — for user-generated content in the CMS, I used `HtmlSanitizer` library to strip dangerous tags. (5) Avoid `dangerouslySetInnerHTML` in React.

- **If asked more:** In PROXPERT's CMS (which allowed rich text for loan notices), sanitization was critical. I used AngleSharp's HTML Sanitizer — it strips `<script>`, `on*` handlers, `javascript:` URLs, and allows only a whitelist of safe tags (`<b>`, `<i>`, `<u>`, `<p>`, `<a>`). The CSP header was: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'` (inline styles allowed for the CMS editor). The refresh token was stored in an httpOnly, secure, SameSite cookie — immune to XSS.

20. How do you implement rate limiting on authentication endpoints?

- **Answer:** I used a sliding window counter approach with Redis. For each identifier (IP, username, or a combination), I increment a counter with a TTL equal to the window. When the counter exceeds the threshold, requests are rejected with 429 Too Many Requests. In PROXPERT: `/token` endpoint — 5 attempts per minute per IP per username. `/forgot-password` — 3 attempts per hour per email. The response included `Retry-After` header.

- **If asked more:** The Redis key pattern: `ratelimit:{endpoint}:{identifier}` with `INCR` and `EXPIRE`. For distributed rate limiting across multiple instances, Redis is ideal. I used a Lua script for atomic increment + EXPIRE. For DRMS SSO login, I added a delay after 3 failed attempts (increasing: 1s, 5s, 30s, 5min) to slow down brute force without locking out legitimate users.

21. What is the difference between access token and ID token in OIDC?

- **Answer:** Access token (JWT) is for API authorization — contains scopes, permissions, and is sent to resource servers. ID token (JWT) is for client-side authentication — contains user identity claims (name, email) and is consumed by the client only. In OpenID Connect (OIDC), the ID token confirms the user's authentication; the access token authorizes API calls. In PROXPERT, we used OAuth2 (no ID token needed) — identity came from the `/userinfo` endpoint called with the access token.

- **If asked more:** The ID token must be validated by the client (verify signature, `aud`, `iss`, `nonce`). The access token's audience (`aud`) is the API (resource server), while the ID token's audience is the client (`client_id`). The ID token contains a `nonce` claim matching the one sent in the auth request (prevents replay). In a typical OIDC flow, the client gets both tokens but only uses the access token for API calls.

22. Explain how you handled user impersonation for audit purposes.

- **Answer:** I implemented a "support admin" feature where a super admin could impersonate a user without knowing their password. The impersonator's identity was preserved in the audit trail. The JWT contained both `sub` (impersonated user) and `impersonator` (admin's user ID). All audit logs recorded the impersonator. Actions taken during impersonation were flagged with an `isImpersonated=true` column. The support admin had a "Stop Impersonating" button that cleared the impersonation session.

- **If asked more:** The impersonation was scoped — the admin could only impersonate users within their own branch hierarchy. Audit events logged: `AdminId`, `AdminName`, `UserId` (impersonated), `Action`, `Timestamp`, `IP Address`. In DRMS, this was used for debugging loan approval issues — an L3 admin could see exactly what a Loan Officer saw without needing their credentials. The `impersonator` claim was validated by the authorization middleware — permissions were still from the impersonated user's role.

23. What is a security token service (STS) and how did you build one?

- **Answer:** An STS is a service that issues, validates, and revokes security tokens (JWT). In PROXPERT, I built the STS as a separate ASP.NET Core Web API with its own database and Redis cache. Endpoints: `POST /connect/token` (issue token — password grant for first-party, client credentials for third-party), `POST /connect/refresh` (rotate refresh token), `POST /connect/revoke` (revoke token), `GET /.well-known/jwks.json` (public keys for JWT validation). The STS was deployed as a separate microservice for security isolation.

- **If asked more:** The STS never stored access tokens (stateless JWT validation) — only refresh tokens (hashed) and revocation entries (in Redis for fast lookup). The STS used a signing certificate from Azure Key Vault, refreshed periodically from the JWKS endpoint. For DRMS, the STS was simpler — just a session store backed by SQL Server (no JWT — we used opaque session tokens stored in Redis, validated by the web app). For PROXPERT's API-first architecture, true JWT STS was necessary.

24. How do you implement password policies securely?

- **Answer:** (1) Minimum length (12+ characters) — not complexity chaos (length > complexity). (2) Password hashing with bcrypt (cost factor 12) or Argon2id — never plain SHA. (3) Salt per user (bcrypt handles this). (4) Check against breached password lists (Have I Been Pwned API). (5) Rate-limit password attempts. (6) No password hints or security questions (weak). (7) Force reset on first login and periodically (90 days). In DRMS, LDAP handled password policy on the enterprise side — we just enforced password sync.

- **If asked more:** For PROXPERT's local accounts (used only for initial setup and admin recovery), I used ASP.NET Core Identity with Argon2id. I disabled insecure features: password hints, email-based password reset without verified identity. For password reset, I used time-limited, single-use tokens (not links — tokens sent in email body to prevent MITM on the link). The token expired after 15 minutes and was invalidated after use.

25. Explain how you handle token revocation.

- **Answer:** JWT is stateless — can't be revoked by itself (until expiration). I implemented a token revocation list (Redis set of `jti` values with TTL equal to token's remaining lifetime). On each API request, middleware checks if the token's `jti` is in the revocation set. Refresh tokens were revoked by setting status = "Revoked" in the database (and deleting from Redis cache). Revocation triggers: user changes password, admin force-logout, "log out all devices", suspected token theft (detected by refresh token replay).

- **If asked more:** The revocation check introduced a Redis call per request — acceptable latency (~1ms). For DRMS (non-JWT, session-based), revocation was instant — just delete the session from the session store. For PROXPERT with 500+ concurrent users, the revocation set was checked on every API call but added negligible overhead (Redis GET by `jti` with O(1) lookup). I also implemented a blacklist bloom filter as a fast pre-check before the Redis lookup.

26. What is a bearer token and how do you secure it?

- **Answer:** A bearer token means "bearer of this token has the rights granted by it" — anyone presenting the token is authenticated. Security: (1) Always use HTTPS (token over HTTP is game over). (2) Short expiry. (3) Store securely — never in URL, never in localStorage (XSS vulnerable). (4) Validate `aud`, `iss`, `exp`, signature on every request. (5) Use token binding or rotate refresh tokens. In PROXPERT, the `Authorization: Bearer <token>` header was validated by middleware that checked signature (RS256), expiry, issuer, audience, and revocation list.

- **If asked more:** The term "bearer" comes from the legal principle of "bearer instruments." There's no built-in proof-of-possession mechanism. Token binding (RFC 8471) solves this but hasn't seen wide adoption. I considered DPoP (Demonstration of Proof of Possession) for PROXPERT's highest-security endpoints (loan disbursement) — the client adds a `DPoP` header proving possession of a private key tied to the token. We didn't implement it due to complexity, but the refresh token reuse detection handled the practical threat.

27. How do you audit authentication and authorization events?

- **Answer:** I log to a dedicated `AuditLog` table with columns: `EventType` (Login, Logout, AccessDenied, PermissionChanged, etc.), `UserId`, `Timestamp`, `IPAddress`, `UserAgent`, `Resource`, `Action`, `Result` (Success/Denied/Error), `Details` (JSON with context). Successful logins, failed logins, permission denials, role changes — all logged. In DRMS, the audit log was immutable (append-only, no UPDATE, no DELETE) with a quarterly archival job. In PROXPERT, I added an alert for >5 failed logins on any account within 10 minutes.

- **If asked more:** The audit events were written asynchronously (queue → batch insert) to avoid impacting the request. For the email approval system, every approval/rejection/cancellation event was logged with the full payload: approver email, loan ID, action, timestamp, JWT activity ID. The audit trail was critical for regulatory compliance — we could reconstruct exactly who did what, when. I also built a simple audit viewer for the admin panel with search and export.

28. Explain how you used CORS to secure the API.

- **Answer:** CORS (Cross-Origin Resource Sharing) controls which origins can access the API. In PROXPERT, the API had strict CORS policy: `AllowOrigins("https://app.proxpert.com")`, allowed methods GET/POST/PUT/DELETE, allowed headers Authorization, Content-Type, X-CSRF-TOKEN. No wildcard origins, no `AllowAnyOrigin()` in production. Credentials (cookies for refresh tokens) required `WithCredentials()` on the client and specific origin (not wildcard) on the server.

- **If asked more:** Preflight requests (OPTIONS) were cached with `Access-Control-Max-Age: 3600` to reduce overhead. CORS is a browser-only protection — API calls from curl/Python have no CORS restrictions. That's why server-side authentication (JWT validation) is also required. For the STS, CORS was more restrictive — only the SPA origin was allowed to call the token endpoint.

29. What is OpenID Connect and how does it extend OAuth2?

- **Answer:** OpenID Connect (OIDC) is an identity layer on top of OAuth2. While OAuth2 provides delegated authorization (access token for APIs), OIDC adds authentication (ID token with user identity). OIDC adds: `userinfo` endpoint (get user claims with access token), ID token (JWT with identity claims, signed), `nonce` (replay prevention), standard scopes (`openid`, `profile`, `email`). DRMS SSO used a custom LDAP-based solution, not OIDC. PROXPERT used plain OAuth2 (no OIDC) because identity was resolved through the JWT claims.

- **If asked more:** OIDC flow: client sends `scope=openid profile` → authorization server authenticates user → returns both ID token (authentication proof) and access token (API authorization) → client can optionally call `/userinfo` with access token for additional claims. The ID token's `aud` is the client ID (not the API). In practice, many implementations (like ours) embed user claims in the access token and skip OIDC entirely.

30. How do you handle session management in a distributed system?

- **Answer:** I use a centralized session store (Redis) accessible by all application instances. Each request reads session state from Redis by session ID (stored in httpOnly cookie or JWT subject). In DRMS, the web farm used Redis-backed sessions (`AddDistributedRedisCache`). In PROXPERT, sessions were JWT-based (stateless) — no server-side session needed. For cases where server-side state was needed (e.g., multi-step approval flow), I stored it in Redis with a TTL matching the flow duration.

- **If asked more:** Sticky sessions (load balancer affinity) are a workaround, not a solution — if a server fails, the session is lost. Centralized session store is the correct approach. Redis provides sub-millisecond reads. I set sane session timeouts (20 minutes idle, 8 hours absolute in DRMS) and clean up expired sessions. For PROXPERT JWT, the stateless approach eliminated the session store entirely for authentication — just validate the token.

31. What is the difference between symmetric and asymmetric JWT signing?

- **Answer:** Symmetric (HS256): same key for signing and verification. Fast, simple — but the shared secret must be distributed to all verifiers (any verifier can also sign). Asymmetric (RS256, ES256): private key signs, public key verifies. Slower but secure — resource servers can validate without being able to sign new tokens. In PROXPERT, I used RS256 because multiple microservices needed to validate tokens without trust of a shared secret.

- **If asked more:** HS256 is fine for a monolithic app (one verifier = one signer). For distributed systems, RS256 is the standard. ES256 (ECDSA) is faster than RSA with equivalent security — I'd use it for new implementations. Key rotation: with RS256, I add the new public key to the JWKS while keeping the old one until all tokens signed with it expire. The `kid` header in the JWT tells verifiers which key to use.

32. How do you handle API key authentication for machine-to-machine communication?

- **Answer:** API keys are long, random strings sent as `X-API-Key` header. I hash the key (SHA256) before storing in the database — never store the plain key. The application hashes the incoming key and looks it up in the DB. Each key has scopes and an expiry. In PROXPERT, the compliance check API used API keys for integration with external systems — the key was scoped to `compliance:write` only.

- **If asked more:** API keys are less secure than OAuth2 client credentials (no short-lived tokens, no rotation easily). I implemented the pattern: API key → generate a JWT (via an internal STS) → use the JWT for subsequent calls. This way, the API key is used only for the initial authentication, and all subsequent authorization uses short-lived JWT. The API key itself was rotated quarterly.

33. Explain the concept of "just-in-time" provisioning for SSO.

- **Answer:** JIT provisioning means when a user authenticates via SSO for the first time, the system automatically creates their local account with default roles rather than requiring an admin to pre-create it. In DRMS, when an LDAP-authenticated user logged in for the first time, my code checked if their `employeeId` existed in the local users table. If not, it created the user with default role "Loan Officer" and auto-assigned them to the branch derived from their LDAP department attribute.

- **If asked more:** The JIT-created user had read-only access until a branch admin assigned specific roles. This prevented unauthorized access from users who shouldn't have system access. I also added a toggle: during provisioning, an email was sent to the user's manager for approval. The attribute mapping from LDAP was configurable in a settings table: `{ "displayName" -> "FullName", "mail" -> "Email", "department" -> "Branch", "title" -> "Designation" }`.

34. How do you handle logout in a JWT-based system?

- **Answer:** Logout requires two steps: (1) Clear client-side token (frontend deletes it from memory). (2) Revoke the token on the server side (add `jti` to revocation list in Redis). The refresh token cookie is also cleared (set empty with expired date). For the SSO logout (DRMS), I implemented single logout: the local session is cleared, and the user is redirected to the IdP's logout endpoint which clears all sessions across the enterprise.

- **If asked more:** "Logout all devices" feature: on password change, all refresh tokens for the user are revoked (set status = 'Revoked' in DB), and all access tokens' `jti` values are added to the revocation set with their remaining TTL. The user has to re-authenticate everywhere. For PROXPERT, I also sent a WebSocket message to all active sessions to force client-side logout.

35. What is a nonce in OAuth2/OIDC and why is it needed?

- **Answer:** A nonce (number used once) is a random value sent by the client in the authorization request and included in the ID token. The client verifies the nonce matches to prevent token replay attacks — ensuring the token was generated in response to this specific request, not replayed from a previous one. In DRMS's SSO flow, I included a `state` parameter (analogous to nonce) in the SAML request and verified it matched on callback. In PROXPERT's OAuth2 authorization code flow, the PKCE `code_challenge` served a similar purpose (bundling the auth code to the specific client session).

- **If asked more:** Without a nonce/state, an attacker could intercept a previous auth code (man-in-the-middle) and replay it. The nonce must be unguessable (cryptographically random). In OIDC, the nonce is in the ID token for client verification. In OAuth2, the state parameter is used in the authorization request/response pair. I always used both state and PKCE for the PROXPERT authorization code flow.

## Redis and Caching Questions

1. How did you use Redis in PROXPERT?

- **Answer:** I implemented Redis for security token caching — 500+ active sessions with automated TTL management. The token cache stored hashed session tokens with a configurable TTL (default 30 minutes, refreshed on activity). This eliminated SQL Server round trips for every request. I also used Redis for: (1) RBAC permission bitmask cache (user ID → permissions), (2) rate limiting counters (sliding window), (3) token revocation list (jti → revoked), (4) distributed session state (when needed), (5) hot data from the CMS (menus, roles, permissions config).

- **If asked more:** The token validation flow: incoming JWT → validate signature (offline, using cached public key from JWKS) → check `jti` against Redis revocation set → check TTL from `exp` claim → fetch user permissions from Redis (key: `user_perms:{userId}`). If missing in Redis, compute from database and cache with 15-minute TTL. Average token validation: ~3ms (signature + 2 Redis GETs). The baseline (before Redis caching) was ~50ms (DB round trip for permissions). Cache hit rate: ~98%.

2. What data structures in Redis did you use and why?

- **Answer:** Strings (key-value) for token cache and permissions cache — simple, O(1) get/set, TTL via EXPIRE. Sorted Sets for rate limiting (timestamp scores, ZREMRANGEBYSCORE to clean old entries, ZCARD for count). Sets for token revocation list (SISMEMBER check, TTL via EXPIRE on the key). Hash for user session metadata (HSET/HGETALL for multiple fields in one cache entry). Pub/Sub for cache invalidation messages across instances.

- **If asked more:** I also used Lua scripts for atomic operations: rate limiting (increment + set TTL atomically) and token cache update (SET if not exists with expiry). The rate limiting Sorted Set approach: each request adds `ZADD ratelimit:{endpoint}:{ip} timestamp uniqueId`, then `ZREMRANGEBYSCORE` to remove old entries, then `ZCARD` to count current window. This gives sliding window precision.

3. Explain cache-aside pattern and how you implemented it.

- **Answer:** Cache-aside (lazy loading): (1) On read, check cache first. (2) If cache hit, return data. (3) If cache miss, load from database, populate cache with TTL, return data. (4) On write, invalidate cache (delete key — consistency over hitting DB + cache writes). In PROXPERT, my token validation middleware followed cache-aside: check `user_perms:{userId}` in Redis → if miss, query SQL Server for role-permission mappings → store in Redis with 15-minute TTL. The cache was invalidated when an admin changed role permissions (delete key so it reloads on next request).

- **If asked more:** I avoided write-through (write to cache + DB simultaneously) because it doubles write latency and adds complexity. With cache-aside, writes go to DB only, cache is invalidated. Trade-off: a brief inconsistency window where a stale cache is served. For RBAC, a 15-minute delay is acceptable (permission changes aren't time-critical). For the token cache, I used read-through with shorter TTL (30 minutes) and passive expiration.

4. How did you manage TTL (Time-To-Live) values?

- **Answer:** I set TTL per data type based on staleness tolerance: (1) Token cache: 30 minutes (matching JWT access token expiry), refreshed on activity. (2) Permission cache: 15 minutes (changes are admin actions, not time-critical). (3) Rate limiting counters: 1 minute (matching the window). (4) Token revocation entries: TTL = remaining token lifetime (so they auto-clean). (5) Session metadata: 8 hours (matching the workday). I used `EXPIRE` on SET operations and sometimes `SET key value EX seconds` for atomicity.

- **If asked more:** TTL tuning was based on access patterns. The permission cache was the hardest — too short (5 min) meant 12 DB hits/user/day even if no changes. Too long (60 min) meant stale permissions. 15 minutes was the sweet spot. For the token cache, I used sliding expiration: `EXPIRE` on every cache hit (access token validation extends the session). I monitored cache hit rate and memory usage via Redis `INFO` stats to validate TTL settings.

5. What is cache invalidation and what strategies did you use?

- **Answer:** Cache invalidation is removing or updating cached data when the underlying data changes. Strategies: (1) **TTL-based** (passive — data expires automatically) — used for permissions and tokens. (2) **Write-invalidate** (on update, delete cache key) — used for RBAC changes. (3) **Pub/Sub invalidation** — when an admin changes roles on one server, publish a message; all servers delete the affected cache keys. (4) **Manual** (admin can force-clear specific cache via admin panel).

- **If asked more:** The invalidation flow for RBAC changes: Admin changes role permissions via CMS → API deletes `user_perms:{userId}` for affected users → publishes `invalidate:perms:{userId}` via Redis Pub/Sub → all instances subscribed to that channel delete the key. Without Pub/Sub, a user could hit a different server after a role change and still get stale permissions for up to 15 minutes (TTL). For the token cache, I relied on TTL only — no active invalidation needed because tokens expire naturally.

6. How did you eliminate SQL Server disk I/O using Redis?

- **Answer:** By caching frequently accessed data that previously required SQL Server queries. In PROXPERT, each API request needed: (1) token validation (permissions, user metadata), (2) RBAC checks (role → permissions). These were on every request path. Before caching, each request made 2-3 SQL Server queries. After Redis caching, the SQL Server query count dropped to 0 for most requests (only write paths touched the DB). This reduced SQL Server load from ~500 queries/second to ~50, and peak-hour capacity improved significantly (the 57% boost in EUV came from index tuning + Redis caching in PROXPERT).

- **If asked more:** The trade-off: memory cost vs SQL Server licensing cost. Redis saved CPU/disk on SQL Server, delaying the need for a SQL Server upgrade. I monitored `INFO commandstats` to see Redis throughput (~2000 ops/sec peak). The cache footprint: 500 user sessions × ~2KB each = ~1MB for tokens, plus ~500KB for permissions cache — negligible compared to the 4GB Redis instance.

7. Explain Redis persistence options and which you used.

- **Answer:** RDB (snapshot at intervals) — good for backup but can lose data since the last snapshot. AOF (append-only file, replay commands) — more durable but slower. In PROXPERT, I used RDB with 60-second save interval because the cache was ephemeral — all data could be regenerated from the database. Losing a few seconds of rate-limit counters or a few minutes of cached permissions was acceptable — the system would degrade gracefully (cache miss → DB load).

- **If asked more:** For production, I used RDB (`save 60 1000` — at least 1000 changes in 60 seconds, trigger save). No AOF — I prioritized performance over durability for a cache layer. If Redis restarted, the cache would warm up naturally as users made requests (cache-aside). The only concern was a "thundering herd" at startup — mitigated by setting `lazyfree-lazy-eviction yes` and pre-warming the most critical cache keys. For DRMS, we didn't use Redis (session state was SQL Server-backed).

8. How did you handle Redis high availability?

- **Answer:** I used Redis Sentinel for high availability: one master, two replicas. Sentinel monitors the master and performs automatic failover if it goes down. The application used `StackExchange.Redis` with connection multiplexing and automatic failover handling. Connection string: `mymaster.redis.cache.windows.net:6380,password=...,ssl=true,abortConnect=false`. `abortConnect=false` — application stays up even if Redis is temporarily unreachable (degrade to DB reads with a circuit breaker).

- **If asked more:** The application had a fallback: if Redis is down, queries go directly to SQL Server (with a local in-memory cache as a second layer). I used a circuit breaker pattern via Polly: if Redis fails 5 times within 30 seconds, break the circuit for 60 seconds, then try again. This prevented cascading failures. For PROXPERT, we never actually hit this fallback in production — Sentinel handled failures transparently within 10-15 seconds.

9. Explain Redis eviction policies and which you chose.

- **Answer:** Eviction policies control what happens when Redis reaches `maxmemory`. Options: `noeviction` (return errors), `allkeys-lru` (evict least recently used keys), `volatile-lru` (LRU among keys with TTL), `allkeys-lfu` (least frequently used), `volatile-ttl` (evict keys with shortest TTL). I chose `allkeys-lru` for PROXPERT — the cache was best-effort, and LRU ensures hot data stays in memory. Less active sessions would be evicted first, causing a cache miss (graceful degradation to DB).

- **If asked more:** LFU (Least Frequently Used) could be better for our access pattern (a session that's used 100 times/day should survive over one used 10 times/day), but LRU was sufficient. I set `maxmemory` to 75% of available Redis memory (3GB of 4GB) to leave headroom for spikes. I monitored `evicted_keys` via Redis INFO — it stayed at zero, meaning the cache never hit the limit. The eviction policy was more of a safety net.

10. What Redis commands did you use most frequently?

- **Answer:** `GET/SET` (token cache, permission cache — 80% of operations), `EXPIRE` (TTL management), `SISMEMBER/SADD` (revocation set), `INCR/EXPIRE` (rate limiting atomic), `HSET/HGETALL` (user session metadata), `PUBLISH/SUBSCRIBE` (cache invalidation across instances), `DEL` (explicit cache invalidation), `KEYS` (admin panel — only on non-production), `SCAN` (iterate cache keys for monitoring).

- **If asked more:** I avoided `KEYS` in production (blocks Redis for large key spaces) — used `SCAN 0 MATCH user_perms:* COUNT 100` for admin cache inspection. For the token cache, the command pipeline was: receive JWT → `GET jti:{jti}` (revocation check) → `GET user_perms:{sub}` (permissions) → if hit, `EXPIRE user_perms:{sub} 900` (sliding TTL). Used `MULTI/EXEC` for atomic operations where needed (e.g., setting cache + TTL).

11. How do you monitor Redis performance?

- **Answer:** I used `INFO` command for key metrics: `used_memory`, `hit_rate` (keyspace_hits / (keyspace_hits + keyspace_misses)), `connected_clients`, `evicted_keys`, `total_commands_processed`, `instantaneous_ops_per_sec`. For PROXPERT, I exposed these via a `/health/redis` endpoint and set up Grafana dashboards. I also set up alerts: hit rate < 90%, memory > 80%, evicted_keys > 0, and `connected_clients` approaching the max.

- **If asked more:** Latency monitoring: `redis-cli --latency -h <host> -p <port>` for baseline. For per-command latency, I used `SLOWLOG GET 100` to find slow commands (threshold: 10ms). The `SLOWLOG` showed zero entries — Redis was consistently sub-millisecond. I also used StackExchange.Redis's built-in profiling to trace individual command timing in the application logs.

12. How do you secure Redis in production?

- **Answer:** (1) Set a strong password via `requirepass`. (2) Bind to internal/private IP only (`bind 127.0.0.1` for same-host, or `bind <private-ip>` for network). (3) Enable SSL/TLS for in-transit encryption. (4) Rename dangerous commands: `rename-command FLUSHALL ""`, `rename-command FLUSHDB ""`, `rename-command CONFIG ""`. (5) Network security groups restrict access to only application servers. (6) Use Redis Enterprise or Azure Redis for managed security. In PROXPERT, Redis ran on a private subnet with a firewall rule allowing only the application tier.

- **If asked more:** For Azure Redis (used in PROXPERT production), I enabled: non-TLS port disabled, Azure Private Link (VNet integration), managed identity for keyless authentication. The connection string was stored in Azure Key Vault, not appsettings.json. I also set `maxclients 5000` to handle peak load and set up diagnostic logging for failed authentication attempts.

13. What is a Redis pipeline and when did you use it?

- **Answer:** A pipeline batches multiple commands into one network round trip (reduces latency from N RTTs to 1). In PROXPERT, I used pipelining during warm-up: when the application starts, it loads all permission cache entries in one batch — 500 commands in a single pipeline vs 500 individual round trips. Also used during rate limit cleanup (batch delete expired entries) and when updating the revocation list with multiple entries.

- **If asked more:** Pipeline commands are non-transactional (by default) — they're executed sequentially but errors in one don't affect others. For atomicity, I used `MULTI/EXEC` transactions. In StackExchange.Redis, pipelining is automatic for fire-and-forget operations (`flags: CommandFlags.FireAndForget`). I used it for cache invalidation deletes where we didn't need the response — just "fire and forget."

14. Explain the difference between Redis and in-memory cache (MemoryCache).

- **Answer:** MemoryCache is local to each application instance — no coordination across instances. Redis is a centralized cache accessible by all instances. MemoryCache: fastest (zero network), no serialization overhead, but duplicate data per instance and cache coherency issues on updates. Redis: slightly slower (network RTT ~0.5ms), shared across instances, supports advanced data structures, persistence, Pub/Sub. In PROXPERT, I used both: MemoryCache for the JWKS public keys (same on all instances, 1-hour TTL), Redis for everything shared (permissions, tokens, rate limiting).

- **If asked more:** For DRMS (single server), in-memory cache would have worked — but we didn't implement it. The choice depends on deployment topology. With multiple load-balanced instances, local caches have N copies of the same data — stale data differs per instance after an update. Redis centralizes the cache: one version of truth. The extra ~0.5ms network latency is negligible compared to the 20-50ms SQL Server query it replaces.

15. How do you handle cache stampede (thundering herd)?

- **Answer:** Cache stampede occurs when many requests simultaneously miss the cache and all query the database before the cache is populated. Solutions: (1) **Locking** — only one request populates the cache, others wait. (2) **Early expiration** — serve stale data briefly while refreshing in the background. (3) **Probabilistic expiration** — set random % of TTL jitter so not everything expires at once. In PROXPERT, I used a distributed Redis lock via `SETNX` (SET if Not Exists) for the permissions cache — only the first request that misses loads from DB, others wait for the lock to release.

- **If asked more:** The locking approach: `SETNX cache_lock:{key} timestamp EX 5` — if returns 1, this instance loads from DB and sets the cache. Other instances `WAIT` with retry (spin, 10ms delay, max 50ms) or immediately fall back to stale data. I also added random jitter to all TTL values (`TTL = base_TTL * (0.8 + random * 0.4)` — 80-120% of base) to stagger expiration times. For the token cache, the refresh-on-activity pattern (extend TTL on every read) naturally prevented stampedes.

16. How did you design the Redis key naming convention?

- **Answer:** I used `{entity}:{identifier}[:subresource]` format with colons — Redis groups keys with same prefix in the keyspace, and it clusters them in a hash slot if using curly braces for hash tags. Examples: `token:{jti}` (token validation cache), `user_perms:{userId}` (permission bitmask), `ratelimit:{endpoint}:{ip}` (rate limiting), `revoke_set:tokens` (revocation set), `session:{userId}` (session metadata). Hash tags: `{token}:{jti}` forced same hash slot for token operations.

- **If asked more:** Consistent naming made monitoring easier — `SCAN 0 MATCH user_perms:*` for permission cache inspection. I avoided spaces, kept ASCII, used lower-case. For PROXPERT, I also prefixed keys with the environment: `prod:user_perms:123`, `staging:user_perms:123` when the same Redis instance was shared across environments (not recommended, but acceptable for non-prod).

17. Explain Redis transactions and how you used them.

- **Answer:** Redis transactions via `MULTI/EXEC` (or `WATCH` for optimistic locking). All commands between MULTI and EXEC are queued and executed atomically. No rollback — if one command fails, others still execute. I used transactions for: (1) Token cache update with TTL: `MULTI; SET token:{jti} "{...}"; EXPIRE token:{jti} 1800; EXEC`. (2) Rate limiting with atomic increment and expiry: `MULTI; INCR rate:{ip}:{endpoint}; EXPIRE rate:{ip}:{endpoint} 60; EXEC`. (3) Cache invalidation + Pub/Sub notification in a transaction.

- **If asked more:** `WATCH` implements optimistic locking: watch a key, execute commands, if the watched key changed, the transaction fails. I used this for the revocation set: `WATCH revoke_set; SISMEMBER revoke_set token_jti; if not member, MULTI; SADD ...; EXEC`. If another instance added to the set between WATCH and EXEC, the transaction retried. In practice, conflicts were rare.

18. What is Redis Pub/Sub and how did you use it?

- **Answer:** Pub/Sub is a messaging pattern: publishers send messages to channels, subscribers receive them in real-time. In PROXPERT, I used Pub/Sub for cross-instance cache invalidation: when an admin updates permissions on one web server, it publishes `invalidate:perms:{userId}` on a channel. All server instances subscribed to that channel delete the affected cache keys from their local memory cache and mark the Redis cache key for refresh. This kept the cache coherent across the cluster.

- **If asked more:** The subscriber was a `BackgroundService` in .NET Core that listens on `__keyspace@0__:*` (Redis keyspace notifications) and custom channels. Keyspace notifications could serve the same purpose (listen for DEL/SET events on specific key patterns) but Pub/Sub gave more control. Drawback: Pub/Sub messages are fire-and-forget — if a subscriber is disconnected, the message is lost. For cache invalidation, that's acceptable because the next request will miss and reload. For critical data, I'd use Redis Streams (persistent messaging).

19. How do you estimate Redis memory requirements?

- **Answer:** I estimate: `sum(data_size + overhead)` per cached entry. For a string key-value: ~50 bytes overhead per key, plus value size. For a hash: ~100 bytes overhead + field overhead. For a set: ~50 bytes per member. In PROXPERT: 500 token cache entries × (50 + 500 bytes) ≈ 275KB. 500 permission entries × (50 + 200 bytes) ≈ 125KB. Rate limiting sets: 1000 entries × ~100 bytes ≈ 100KB. Total: ~500KB — with 2x safety margin = 1MB for actual data. I allocated 4GB for headroom and future growth.

- **If asked more:** Use `redis-cli --bigkeys` to scan and estimate memory per data type. For production, I monitored `used_memory` over time and set alerts at 80% of `maxmemory`. Redis memory overhead can be significant — a 10-byte value in a key still costs ~70+ bytes (key structure, dict entry). For the token cache, I serialized to JSON and compressed with GZip for values >1KB.

20. Explain the difference between Redis and SQL Server for caching.

- **Answer:** Redis is in-memory, key-value, sub-millisecond reads, has built-in TTL and eviction policies — purpose-built for caching. SQL Server can be used as a cache but: (1) row-based storage is slower (5-50ms reads vs <1ms for Redis), (2) no automatic TTL (requires scheduled cleanup jobs), (3) heavier connection overhead, (4) costs more per GB. In PROXPERT, we used Redis for low-latency, high-throughput caching. SQL Server remained the source of truth — the system-of-record.

- **If asked more:** Before Redis, PROXPERT considered SQL Server's In-Memory OLTP tables for caching. Benchmarks showed Redis was 3-5x faster for simple key-value lookups and easier to manage (no schema changes, automatic eviction). SQL Server's in-memory tables are better for hybrid workloads (data that's both cached and transactional). For our pure caching needs, Redis was the clear winner.

21. What is a cache hit ratio and what was yours?

- **Answer:** Cache hit ratio = `keyspace_hits / (keyspace_hits + keyspace_misses)` × 100. In PROXPERT, the permission cache had ~98% hit rate (most users repeat requests within their TTL window). The token cache had ~95% hit rate (some tokens expire between requests). Rate limiting had ~100% (always accessed after write). I monitored this via Redis `INFO stats` and set an alert if hit rate dropped below 90% — that would indicate a misconfigured TTL or cache eviction pressure.

- **If asked more:** When hit rate drops, I check: (1) Is memory full and evicting cache entries? Check `evicted_keys`. (2) Are TTLs too short? (3) Is there a pattern change (new feature rollout, traffic spike)? The permission cache miss was 10ms extra (DB query) — acceptable. But a sustained low hit rate means you're paying the latency cost of cache miss without the memory benefit of cache hits — time to tune.

22. How do you implement distributed locking with Redis?

- **Answer:** Using `SETNX` (SET if Not eXists) with expiry: `SET lock_key unique_id EX 10 NX`. If returns OK, lock acquired. Release with a Lua script that deletes only if the value matches (prevent deleting someone else's lock). In PROXPERT, I used RedLock algorithm via the `RedLock.net` library for distributed locks around the permission cache population and the multi-instance cache invalidation flow.

- **If asked more:** The Lua script: `if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end`. The `unique_id` (Guid) prevents a thread from deleting another thread's lock (e.g., if a lock expired and another thread acquired it). I set lock TTL to 10 seconds — much longer than the expected lock hold time (~500ms for DB query). For RedLock, I used 3 Redis instances (quorum of 2) — though for PROXPERT's deployment, a single master with Sentinel was sufficient.

23. What is Redis Cluster and did you consider it?

- **Answer:** Redis Cluster is a distributed topology where data is sharded across multiple nodes (automatic partitioning). Each node holds a subset of hash slots. It provides high availability and horizontal scalability. For PROXPERT, I didn't need Cluster — a single instance with Sentinel (replication + failover) handled our ~2000 ops/sec easily. Cluster adds complexity: (1) multi-key operations only within same hash slot, (2) transactions restricted to same node, (3) clients must handle MOVED redirects. The performance gain didn't justify the overhead.

- **If asked more:** The decision criteria: single-instance throughput (~100K ops/sec for small values) >> PROXPERT's requirement (~2K ops/sec). Memory usage (~2GB) << instance capacity. I'd consider Cluster if: (1) memory needs exceed a single node (100GB+), (2) write throughput needs to scale beyond one node's capacity, (3) data needs to be partitioned for geographic distribution. For DRMS (no Redis), there was no consideration.

24. How do you handle cache warm-up after a deployment?

- **Answer:** Cache warm-up pre-populates critical cache entries before receiving user traffic — avoiding a cold start thundering herd. In PROXPERT, my deployment script: (1) after new instances are healthy, it runs a warm-up job that loads the top-N active users' permission caches. (2) For the token cache, the warm-up loads all active non-expired session tokens from the database. (3) For rate limiting — no warm-up needed (counters reset on deployment, which is acceptable). The warm-up job ran within 30 seconds on a background thread, non-blocking.

- **If asked more:** The warm-up ran only on the first instance of a new deployment (to avoid N instances all doing the same work simultaneously). It used a distributed lock (Redis SETNX) to coordinate. The candidate data: last-24-hours active users (filtered from application logs). This covered ~80% of the next day's users. Without warm-up, the first few minutes post-deployment would have 100% cache miss rate and spike the database.

25. What is the difference between Redis Strings and Hashes for storing objects?

- **Answer:** Strings store the entire object as a serialized blob (JSON/protobuf) — simple, single GET/SET. Hashes store fields individually — you can read/update specific fields without deserializing the entire object. Strings: simpler code, larger network payload for partial updates. Hashes: more granular, smaller network for partial access, but overhead per field. In PROXPERT, I used Strings for the token cache (always read the full token), and Hashes for session metadata (we read/wrote individual fields: last_activity, ip_address, user_agent).

- **If asked more:** Memory comparison: Hashes can be more memory-efficient for small objects because Redis encodes them as ziplists (`hash-max-ziplist-entries 512`, `hash-max-ziplist-value 64`). For the session metadata hash (<10 fields, <50 bytes each), ziplist encoding saved ~50% memory vs a flat String. For larger objects (~500 bytes+), the overhead difference is negligible. I tested both approaches — Hashes won for session metadata due to partial access patterns.

26. Explain the concept of Redis replication and Sentinel.

- **Answer:** Replication creates read replicas of the master — asynchronous by default (eventually consistent). Sentinel monitors the master, performs automatic failover when the master fails, and acts as a service discovery (client asks Sentinel for the current master). In PROXPERT, I had one master, two read replicas, and three Sentinel instances. Reads could go to replicas (read scaling), but I kept all operations on the master for consistency (PROXPERT's read volume didn't need replica offloading).

- **If asked more:** Replication lag was typically <1ms — acceptable for cache data. Sentinel was configured with `quorum: 2` (at least 2 Sentinels must agree the master is down). The client (StackExchange.Redis) supported Sentinel natively: `ConnectionMultiplexer.Connect(new ConfigurationOptions { ServiceName = "mymaster", TieBreaker = "", CommandMap = ... })`. The application reconnected transparently after failover. I tested failover scenarios: ~12 seconds for detection + failover + client reconnection.

27. How do you back up Redis data?

- **Answer:** RDB snapshots (scheduled via `save` config) — I saved every 5 minutes if at least 100 keys changed. For disaster recovery: I also scheduled an external backup script that runs `BGSAVE` and copies the RDB file to Azure Blob Storage daily. I kept 7 days of backups. For cross-region DR, the backup was copied to a secondary region. In PROXPERT, we never needed to restore from Redis backup — cache data can always be regenerated from the source of truth (SQL Server).

- **If asked more:** The backup strategy: local RDB (quick recovery if Redis restarts) + cloud backup (DR scenario). Restoration: copy RDB to Redis data directory and restart. For Azure Redis, managed backups were built-in. I didn't use AOF persistence (better durability, but performance overhead). The RDB snapshot process (fork + write) was fine for our 2GB dataset — completed within 200ms and the fork overhead was negligible.

28. How do you handle large objects in Redis?

- **Answer:** Redis is single-threaded — commands on large objects block the event loop. A GET on a 10MB value blocks Redis for ~10ms, impacting all other operations. Solutions: (1) Split large objects into smaller chunks (e.g., a user's full profile → separate keys for permissions, preferences, metadata). (2) Compress values (GZip, Snappy). (3) Store large objects in Blob Storage, only cache metadata in Redis. In PROXPERT, all cached objects were <5KB — no large object issues. I set a `max-value-size` warning at the application level (log a warning for SET with value > 10KB).

- **If asked more:** If I had to cache larger payloads, I'd use the split approach: hash the object key, create N shard keys (e.g., `user_profile:{userId}:0`, ..., `user_profile:{userId}:3`), pipeline MGET them, reassemble. Or I'd evaluate whether that data truly needs Redis caching. In PROXPERT, CMS content (menus, role definitions) was the largest cached data — still under 5KB in serialized JSON.

29. Explain the trade-off between cache freshness and performance.

- **Answer:** Longer TTL → fewer cache misses → better performance (lower DB load, lower latency) but stale data. Shorter TTL → fresher data but more cache misses (higher DB load, higher latency). In PROXPERT: the permission cache had 15-minute TTL — accepting the risk that a newly promoted user might not have updated permissions for 15 minutes. The trade-off was acceptable because role changes were infrequent admin actions. For the token cache, 30-minute TTL matched the JWT expiry — the token would expire anyway.

- **If asked more:** I also used "stale-while-revalidate": serve cached data even if slightly expired, but trigger a background refresh. For example: permission cache TTL = 15 minutes, but I serve up to 30 minutes old data if the background refresh fails. This prevents a cache miss spike during temporary Redis/DB issues. In practice, I didn't implement this — the simple TTL-based approach was adequate for PROXPERT's use case.

(2) Integration tests with a local Docker Redis instance (spin up in test container, run tests, tear down). ## Testing, xUnit and NUnit Questions

1. How do you unit test a controller action that uses EF Core?
   - **Answer:** I don't mock EF Core directly. Instead, I use the actual EF Core in-memory provider or SQLite in-memory database. For example, in PROXPERT's NUnit tests, I'd create a `DbContextFixture` that seeds the in-memory database with test data, inject it into the repository, and verify the controller returns the expected `IActionResult`. This tests the actual query logic.
   - **If asked more:** The in-memory provider has limitations (no relational features), so for more complex queries, I used SQLite in-memory mode which supports relationships better. I also tested the `IQueryable` filtering directly.

2. How did you test stored procedure changes in DRMS?
   - **Answer:** I wrote xUnit integration tests that used a real SQL Server LocalDB instance. Each test would: 1) Run a setup SQL script to create test tables and data. 2) Execute the stored procedure via EF Core's `FromSqlRaw`. 3) Assert on the returned results. After refactoring 11 stored procedures, I ran all tests before and after to verify the same results were produced.
   - **If asked more:** I also created benchmark tests using `Stopwatch` to verify that the refactored procedures completed in under 30 seconds compared to the original 100s+ performance. The test database was seeded with realistic data volumes to catch regression issues.

3. What's your approach to testing CQRS handlers?
   - **Answer:** In PROXPERT, I'd unit test each command/query handler in isolation using NUnit. I mocked `IMediator` (or used the actual mediator with registered handlers for integration tests), created in-memory repositories, and verified that the handler produces the expected result or side effect. For example, testing a `CreateDocumentCommandHandler` would verify the document is saved and the appropriate event is published.
   - **If asked more:** I also tested validation behavior using FluentValidation — verifying that invalid input returns the correct `ValidationException` with the right error messages. I used `AutoFixture` to generate test data with sensible defaults.

4. How did you achieve high code coverage in PROXPERT?
   - **Answer:** We targeted 80%+ coverage. I wrote unit tests for all business logic in the Domain layer, all command/query handlers in Application layer, and controller actions in the API layer. We used `Coverlet` for coverage collection and `ReportGenerator` for readable reports. The CI pipeline enforced the coverage gate via SonarQube.
   - **If asked more:** We excluded infrastructure code (EF Core migrations, Program.cs, DTOs) and generated proxy code from the coverage threshold. I also encouraged TDD for new features — writing the test first made it natural to hit coverage targets.

5. How do you test ASP.NET Core middleware?
   - **Answer:** I use the `WebApplicationFactory<T>` from `Microsoft.AspNetCore.Mvc.Testing` to create a test server. In NUnit, I'd add a custom `WebApplicationFactory` with a mocked service registration (replacing real services with test doubles), then send HTTP requests using `HttpClient` and assert on the response. This tests the full middleware pipeline including auth, CORS, and custom middleware.
   - **If asked more:** For custom middleware specifically (like our tenant resolution middleware), I'd also write a pure unit test by creating a `DefaultHttpContext`, invoking the middleware with `RequestDelegate`, and asserting on the context items.

6. How do you test authentication and authorization in your API?
   - **Answer:** I use the `WebApplicationFactory` with a custom `AuthenticationHandler` that simulates an authenticated user with specific claims. I created a helper method: `client.AsUser("admin")` that adds the Authorization header with a test JWT. For authorization, I verify that endpoints return 200 for authorized roles and 403 for unauthorized.
   - **If asked more:** In PROXPERT, I had test cases for each RBAC permission: "admin can create user", "viewer cannot delete document", etc. The test user setup was parameterized so I could test across all roles systematically. I also tested the OAuth2 token validation middleware by sending expired/invalid tokens.

7. How did you test the caching logic in PROXPERT?
   - **Answer:** I wrote integration tests that ran against a local Redis container (using `Testcontainers` NuGet). The test would: 1) Assert an empty cache. 2) Call the service method. 3) Assert the result is cached. 4) Verify the second call returns from cache (verify by monitoring cache hit metrics or by asserting the same object reference). I also tested cache expiration and eviction scenarios.
   - **If asked more:** I also unit tested the cache-aside pattern by mocking `IDistributedCache`. The mock verified that cache was checked first, and on miss, the data was fetched from the repository and stored in cache. I tested the circuit breaker behavior by making Redis throw an exception and asserting graceful fallback.

8. How do you test database migrations?
   - **Answer:** I wrote an xUnit test in DRMS that ran `Database.Migrate()` on a fresh test database (SQLite in-memory). The test asserted that all migrations applied successfully without errors. For PROXPERT, I had a similar test that applied migrations to a test SQL Server container, then ran a smoke query against each table to verify schema correctness.
   - **If asked more:** We also had a "downgrade" test that rolled back the last migration and re-applied it, ensuring downgrade scripts were correct. Seed data migration tests verified that the production seed data could be inserted without conflicts.

9. How do you test background jobs or scheduled tasks?
   - **Answer:** In PROXPERT, we had a few `IHostedService` implementations. I tested them by: 1) Instantiating the service with mocked dependencies. 2) Calling the `ExecuteAsync` or the main method directly. 3) Verifying the expected side effects. For integration tests, I used a `TestServer` with a custom `TestBackgroundJobScheduler` that ran the job immediately instead of on a schedule.
   - **If asked more:** I also tested error handling — what happens when the background job throws? We used a retry policy (Polly), so the test verified retry counts and fallback behavior. We logged failures to Application Insights, and the test verified the logger received the correct error.

10. How do you approach testing in a legacy codebase?
    - **Answer:** In DRMS, the codebase was not originally testable. I started by adding integration tests for the stored procedures (the most critical and fragile part). Then, I introduced the "Seam" pattern — extracting interfaces from concrete classes to make them testable. Every time I touched a file for a bug fix or feature, I'd add at least a basic test around the changed code.
    - **If asked more:** I used characterization tests — writing tests that capture the current behavior before making changes, so I know what I broke. Over time, we increased coverage from ~10% to ~65%. The key was making testing part of the definition of done for every story.

11. What's your preferred mocking framework and why?
    - **Answer:** I use Moq with xUnit (DRMS) and NSubstitute with NUnit (PROXPERT — team preference). Both work well. Moq has a cleaner API for setup/verify patterns. NSubstitute's Arrange-Act-Assert syntax is more readable with `sub.Received(1).Method()`. I avoid mocking too much — I prefer fakes or in-memory implementations when possible.
    - **If asked more:** I strongly avoid over-mocking. If a test has more than 3-4 mocks, that's a code smell that the class has too many dependencies. I'd refactor to reduce dependencies rather than add more mocks.

12. How did you use xUnit vs NUnit? Why both?
    - **Answer:** DRMS used xUnit because it was the project's initial choice — xUnit is lighter, has better extensibility with `ITestCollectionOrderer`, and its `IAsyncLifetime` was useful for database setup. PROXPERT used NUnit because the team was more familiar with it, and NUnit's `[TestCase]` parameterized tests and `[Retry]` attribute were useful for our integration tests.
    - **If asked more:** Both frameworks are essentially equivalent. xUnit's `Fact` and `Theory` vs NUnit's `Test` and `TestCase` are semantically the same. The bigger difference is the assertion library — we used FluentAssertions in PROXPERT and the built-in xUnit asserts in DRMS.

13. How do you test exception handling in your code?
    - **Answer:** I use the Arrange-Act-Assert pattern. I set up the dependency to throw a specific exception (e.g., repository throws `DbUpdateException`), call the method under test, and assert that the correct exception is thrown or that the global exception handler returns the expected HTTP status code. I also test the error logging — verifying `ILogger` received the error message.
    - **If asked more:** In PROXPERT, we had a global exception middleware that caught all exceptions and returned structured error responses. I tested this middleware by throwing various exception types (ValidationException, NotFoundException, UnauthorizedAccessException) and asserting on the returned JSON body, status code, and ProblemDetails format.

14. How do you write maintainable tests?
    - **Answer:** I follow the AAA pattern strictly. Test names follow the pattern: `MethodName_Scenario_ExpectedResult`. Each test asserts one logical concept (one assert per test when possible). I use test data builders or `AutoFixture` to reduce boilerplate. Tests don't depend on other tests or test order. I avoid test logic (if/else/loops) — tests should be declarative.
    - **If asked more:** I also believe in test code review. Tests that are hard to read are a sign of design problems in the production code. I'm not religious about one-assert-per-test — multiple asserts on the same logical concern (e.g., asserting multiple properties of a response) is fine.

15. How do you test stored procedures in isolation from the application?
    - **Answer:** I created a test database that was restored from a backup of a sanitized production snapshot. The xUnit test would: 1) Execute the stored procedure with test parameters. 2) Capture the result set. 3) Assert on the returned data. I also had tests that verified error handling — passing nulls, missing data, or invalid IDs to ensure the procedure threw the correct error.
    - **If asked more:** I also tested performance. Each stored procedure test recorded execution time and compared against a baseline. If a refactored procedure was slower than the original, the test would fail. The test database was sized to match production row counts for meaningful benchmarks.

16. How did you test the RBAC system in PROXPERT?
    - **Answer:** I wrote parameterized NUnit tests for every role-permission combination. The test matrix included: Admin, Manager, Editor, Viewer, and Custom roles. Each test case authenticated as a specific role, called an endpoint with a specific resource, and asserted the expected HTTP status code (200, 403). This gave us confidence in the permission enforcement.
    - **If asked more:** I also tested the dynamic RBAC — where a user's permissions could change mid-session. I verified that the permission cache was invalidated correctly and the next request reflected the updated permissions. I tested edge cases: user with no roles, deleted user's token, expired permissions, and overlapping roles with conflicting permissions.

17. How do you test SQL injection vulnerabilities?
    - **Answer:** I wrote security tests that passed malicious SQL strings (e.g., `' OR 1=1 --`, `'; DROP TABLE Users --`) to all API endpoints that accepted string inputs. The test verified that the operation returned an appropriate validation error or empty result, and crucially, did not cause any database schema changes or data leaks. Since we used EF Core with parameterized queries and never raw SQL in PROXPERT, these tests passed consistently.
    - **If asked more:** For DRMS, where stored procedures used dynamic SQL in a few cases, I verified that parameters were properly sanitized by examining the procedure code and running tests with SQL injection payloads. I proposed converting dynamic SQL to parameterized queries in the procedures.

18. How did you test email sending in DRMS?
    - **Answer:** I mocked `ISmtpClient` or `IEmailService` using Moq in xUnit tests. The test verified that the correct email content was constructed and the send method was called with the right parameters (to, subject, body) when an approval was triggered. For integration tests, I used a local SMTP server (Papercut or smtp4dev) to verify emails were actually sent without spamming real users.
    - **If asked more:** I also tested the email template rendering — seeding the template with test data and verifying the output HTML contained the expected placeholders replaced with correct values. We tested all email types: approval request, approval notification, rejection notification, and mid-approval cancellation.

19. How do you test async code in .NET?
    - **Answer:** Both xUnit and NUnit support async test methods natively. I simply mark the test method as `async Task` and await the async method under test. I'm careful to avoid mixing sync and async (no `.Result` or `.Wait()` which can cause deadlocks). For mocking async methods, I use `.ReturnsAsync()` in Moq or `.Returns(Task.FromResult())` in NSubstitute.
    - **If asked more:** I also test `Task.WhenAll` scenarios and cancellation tokens. I test that passing a cancelled `CancellationToken` throws `OperationCanceledException` and that the method doesn't proceed with the operation. I've also tested timeout scenarios by using a mock that delays beyond the expected timeout.

20. How do you test the Angular frontend in DRMS?
    - **Answer:** I wrote Jasmine/Karma unit tests for the Angular components and services. I'd mock the HTTP service using `HttpClientTestingModule` and `HttpTestingController` to simulate API responses. For routing, I used `RouterTestingModule`. I tested: component rendering with various data states, form validation, error handling, and RBAC-based menu visibility.
    - **If asked more:** I didn't achieve full Angular test coverage — about 60% — focusing on critical components: login, approval workflow forms, and the dashboard. I also used Protractor for a few end-to-end tests that verified the full login flow and approval workflow. E2E tests were run manually before releases, not in CI.

21. How do you test React components in PROXPERT?
    - **Answer:** We used React Testing Library with Jest. Tests focused on user-facing behavior rather than implementation details. For example, testing that: clicking "Save" calls the onSave prop, error messages appear when validation fails, and the correct menu items render based on the user's role from the auth context. We mocked the API layer using `msw` (Mock Service Worker) for integration-like tests.
    - **If asked more:** We had about 70% frontend coverage. Key patterns: `render` with `ThemeProvider` and `AuthContext.Provider` wrappers, `screen.getByRole`/`getByText` for queries, `userEvent` for interactions, and `waitFor` for async assertions. We avoided testing internal state — testing that the component renders correctly for given props was sufficient.

22. How did you test file upload functionality?
    - **Answer:** I wrote integration tests that created a test file in memory, used `MultipartFormDataContent` to send it in an HTTP request, and verified the file was saved correctly. I tested: valid file types, file size limits (too large should be rejected), empty files, and files with malicious content (script injection). The test verified the response contained the expected file URL or ID.
    - **If asked more:** In DRMS, document upload was a critical feature. I tested concurrent uploads (multiple files simultaneously), upload cancellation (mid-approval cancellation), and the scan for virus rejection scenario (simulated by the anti-virus service returning a positive result).

23. How do you ensure tests are fast?
    - **Answer:** I categorize tests into unit (fast, <100ms), integration (moderate, <5s), and end-to-end (slow, minutes). Unit tests don't touch the database or network — they run in milliseconds. Integration tests use in-memory databases or test containers. E2E tests are minimal and run only on demand. We ran unit and integration tests in CI, and E2E tests on nightly builds or before releases.
    - **If asked more:** I also use "shared test fixtures" for expensive setup (like database seeding) so it's done once per test class, not per test. In PROXPERT, we had about 1,200 unit tests that ran in under 30 seconds. The 200 integration tests took about 3 minutes using SQLite in-memory.

24. How do you test the API endpoint performance?
    - **Answer:** I wrote a "performance test" that called the API endpoint 100 times with different parameters and recorded the average, p50, p95, and p99 response times. If the p95 exceeded 2 seconds, the test would fail. For stored procedures in DRMS, I had similar tests that measured execution time before and after refactoring, with a threshold of < 30 seconds.
    - **If asked more:** These weren't strict CI gates — more as informative metrics that we tracked. We used `BenchmarkDotNet` for critical code paths and wrote those as separate benchmark projects. The CI performance tests were simpler — just verifying no regression occurred compared to the baseline.

25. How did you test the LDAP SSO integration in DRMS?
    - **Answer:** I couldn't test against the real LDAP server in CI, so I created a fake LDAP authentication service that implemented the same interface. The fake would accept known test credentials and reject others. The xUnit tests verified: successful login with correct credentials, failed login with incorrect credentials, locked account handling, and the fallback to local authentication when LDAP was unreachable.
    - **If asked more:** For manual testing, we had a test LDAP server in staging that mirrored the production configuration. The integration tests were configurable via app settings to point to either the fake or the real LDAP server. I also tested the token creation after LDAP authentication — verifying the correct claims were populated.

26. How do you test the CQRS event publishing?
    - **Answer:** In PROXPERT, I used a test spy — an in-memory event collector that implements the same event handler interface. After executing a command, I'd assert that the correct events were published with the expected data. For integration tests, I used the real mediator and an in-process event bus, verifying that side effects (like sending an email or updating a read model) actually happened.
    - **If asked more:** I also tested the event ordering and idempotency — if the same command was executed twice, the events should be published correctly both times with no duplicate side effects. We used MediatR's `INotification` with multiple handlers, and I tested that all handlers were invoked.

27. How do you handle flaky tests?
    - **Answer:** First, I investigate the root cause — most flaky tests are due to: 1) Shared mutable state between tests, 2) Timing/race conditions in async tests, 3) Tests that depend on external services being available. I fix the root cause by: isolating test state, using `CountdownEvent` or proper async synchronization, and mocking external dependencies. If a test is genuinely timing-dependent, I use Polly retries or the NUnit `[Retry]` attribute as a last resort.
    - **If asked more:** In CI, we had a Flaky Test Detector — if a test failed once but passed on retry, it was flagged and reported. We'd investigate and fix it within the same sprint. Flaky tests erode trust, so we took them seriously.

28. How did you test the approval workflow mid-approval cancellation in DRMS?
    - **Answer:** This was a complex scenario. I wrote an integration test that: 1) Created a document and submitted for approval. 2) Started the approval process (first approver approved). 3) Cancelled the request mid-flow (before the second approver acted). 4) Verified that: the document status changed to "Cancelled", no further approval emails were sent, the cancellation notification went to all involved parties, and the document was unlocked for editing.
    - **If asked more:** I also tested edge cases: cancellation when no approvers had acted yet, cancellation when all approvals were already complete (should be rejected — can't cancel a fully approved document), and cancellation by a non-owner (should be rejected with 403).

29. How do you test the `Serilog` logging configuration?
    - **Answer:** I wrote a test that: 1) Captured log output using `Serilog.Sinks.XUnit` (for xUnit) or a custom `TestSink`. 2) Executed the code path that should log. 3) Asserted that the expected log message was written at the correct level. This was especially important for verifying that sensitive data was not logged and that structured properties were attached correctly.
    - **If asked more:** I also tested the logging enrichment — verifying that the correlation ID, user context, and tenant ID were automatically attached to every log entry. For DRMS, I tested the SQL Server sink by checking that logs were written to the expected table with the correct schema.

30. What's your philosophy on test-driven development?
    - **Answer:** I practice pragmatic TDD. For new features with clear requirements, I write the test first — it forces me to think about the API design before implementation. For bug fixes, I write a test that reproduces the bug before fixing it (so I know the fix works and it won't regress). For exploratory or UI-heavy work, I sometimes write the implementation first and add tests after.
    - **If asked more:** The biggest benefit of TDD for me is the improved design — testable code tends to be loosely coupled and follows the Single Responsibility Principle. I don't aim for 100% TDD coverage. What matters is that the critical business logic is tested. I've had too many experiences where untested refactoring broke production, so testing is non-negotiable for me.

## React, Angular and Frontend Questions

   - **If asked more:** We also had a `useAuth` hook that exposed the current user, login/logout, and token state. The `PrivateRoute` component used this hook to protect routes. The axios interceptor was configured in a `apiClient` module that was imported by all service files.

## Full-Stack and Architecture Questions

1. Can you explain the CQRS implementation in PROXPERT?
   - **Answer:** We used the MediatR library to implement a simple CQRS (Command Query Responsibility Segregation) pattern. Commands (writes) and Queries (reads) were separate C# records. Each had a handler class. Commands went through a validation pipeline (FluentValidation via MediatR's `IPipelineBehavior`) and published events after execution. Queries bypassed the validation pipeline for performance. The read side used the same database but with optimized queries.
   - **If asked more:** We didn't use separate read/write databases (eventual consistency felt unnecessary for our scale). The separation was at the code level — commands changed state, queries returned data. This made the code easier to reason about and test. The pipeline behaviors also handled: logging, transaction wrapping, and performance monitoring.

2. How did you implement the dynamic RBAC system?
   - **Answer:** The RBAC system had three layers: Users, Roles, and Permissions. A user could have multiple roles, and each role had a set of permissions (e.g., "Document.View", "Document.Approve", "Admin.Access"). Permissions were stored in the database and cacheed in Redis. The API middleware resolved the user's permissions from the JWT claims (which contained the user ID, not the full permission list) and fetched permissions from cache on each request.
   - **If asked more:** The admin panel allowed CRUD on roles and permissions. Permissions were grouped by module (Documents, Users, CMS, Settings). The permission check was done in the API via a custom `[RequirePermission("Document.Approve")]` attribute that used a policy-based authorization handler. The cache key was `permissions:{userId}`, invalidated when the user's roles changed.

3. How did you implement the dynamic CMS system?
   - **Answer:** The CMS was a key-value store with additional metadata. Content pages were stored with a `slug` (URL path), `title`, `body` (HTML from the WYSIWYG editor), `meta` fields (SEO), and `version` number. When a user requested `/api/cms/{slug}`, we returned the latest published version. The admin panel could create new versions, preview unpublished versions, and publish.
   - **If asked more:** The CMS also supported: content templates (reusable sections with placeholders), scheduling (publish on a future date), and content localization (language-specific slugs). The navigation menu was stored as an array of menu items with `parentId`, `title`, `slug`, `order`, and `target` (_self vs _blank).

4. How did you design the approval workflow in DRMS?
   - **Answer:** The workflow was: 1) A user creates a document and submits it for approval. 2) The system determines the approval chain based on the document type and the user's department (configurable rules). 3) The first approver gets an email notification with a link to approve/reject. 4) Once the first approver acts, the next approver is notified. 5) If all approvers approve, the document is approved. 6) The submitter can cancel mid-flow.
   - **If asked more:** The approval chain was stored as a `WorkflowInstance` table with `WorkflowStep` rows (approver ID, status, sequence). The workflow engine was state-machine-based with states: Pending, InProgress, Approved, Rejected, Cancelled. The email approval link used a signed token so the approver didn't need to log in (if using the email link). The mid-approval cancellation checked that no steps beyond the current one had been acted upon.

5. How did you handle the mid-approval cancellation feature?
   - **Answer:** When a user clicked "Cancel Request", the API: 1) Verified the user was the document owner. 2) Checked that at least one step hadn't been acted on (i.e., the workflow wasn't fully approved or rejected). 3) Updated the `WorkflowInstance` status to "Cancelled". 4) Marked all pending steps as "Cancelled". 5) Sent cancellation notification emails to all approvers who had already acted or were in the pending queue. 6) Unlocked the document for editing.
   - **If asked more:** If approver A had approved and approver B was pending, cancelling set A's step to "Cancelled" (rollback) and B's step to "Cancelled". A notification was sent to A saying the request was cancelled. The document's status changed back to "Draft", and the submitter could edit and resubmit, which created a new workflow instance.

6. How did you structure the modular services in PROXPERT?
   - **Answer:** The application followed Clean Architecture: Domain layer (entities, enums, interfaces), Application layer (CQRS commands/queries, DTOs, interfaces), Infrastructure layer (EF Core, Redis, external services), and API layer (controllers, middleware). Each layer was a separate .NET project. Dependencies pointed inward — the API depended on Application, which depended on Domain, and Infrastructure implemented Application's interfaces.
   - **If asked more:** We used dependency injection throughout. The `Program.cs` had extension methods like `AddApplicationServices()`, `AddInfrastructureServices()`, and `AddApiServices()`. The Domain layer had zero external dependencies. The Application layer depended only on Domain and MediatR/FluentValidation. This separation made testing easy (mock Infrastructure, test Application).

7. How did you design the database schema for RBAC?
   - **Answer:** Normalized tables: `Users` (Id, Name, Email, etc.), `Roles` (Id, Name, Description), `Permissions` (Id, Name, Group, Description), `UserRoles` (UserId, RoleId), `RolePermissions` (RoleId, PermissionId). We also had a `UserPermissions` table for direct user-specific overrides. All tables used integer IDs and had audit columns (CreatedAt, CreatedBy, UpdatedAt, UpdatedBy).
   - **If asked more:** We used EF Core's `HasMany`/`WithMany` relationships for the many-to-many joins. Permission names followed the convention `{Module}.{Action}` (e.g., "Document.Create"). The `UserPermissions` table allowed granting or denying specific permissions to individual users without creating a custom role. A denied permission (via a boolean `IsDenied` column) always took precedence.

8. How did you implement the stored procedure refactoring in DRMS?
   - **Answer:** The 11 stored procedures were monolithic — each handled multiple concerns (filtering, sorting, pagination, aggregations) in one query, some with unnecessary `.WRITE()` clauses and cursor-based logic. I rewrote them as modular procedures: each handled one operation (GetDocuments, GetDocumentById, CreateDocument, etc.). I used set-based operations, proper indexing, and `WITH (NOLOCK)` where appropriate. The refactoring reduced execution times from 100+ seconds to under 30 seconds.
   - **If asked more:** I also: removed deprecated `TEXT`/`NTEXT` types in favor of `VARCHAR(MAX)`, converted `SELECT *` to explicit column lists, added `@offset`/`@fetch` parameters for server-side pagination, and created covering indexes for the most common query patterns. Performance was validated by running the same inputs against both old and new procedures.

9. How did you design the email notification system in DRMS?
   - **Answer:** I created a background service (`IHostedService`) that polled an `EmailQueue` table every 30 seconds. When an approval action was taken (submitted, approved, rejected, cancelled), a record was inserted into the `EmailQueue` table with the email type, recipients, and template data. The background service processed the queue, rendered the email using a Razor template, and sent via SMTP. Failed emails were retried 3 times, then logged.
   - **If asked more:** The email templates were stored as files in the application and used `RazorEngine` for rendering (later migrated to `RazorLight`). Each email type (ApprovalRequest, Approved, Rejected, Cancelled) had its own template. The approval request email included a unique signed link that allowed the approver to approve/reject without logging in. The signature was an HMAC of the workflow step ID and a server secret.

10. How did you handle concurrency and optimistic locking?
    - **Answer:** In PROXPERT, I added a `RowVersion` (byte array) column to all entities that could be concurrently modified. EF Core's `IsRowVersion()` fluent API enabled optimistic concurrency checking. On a `DbUpdateConcurrencyException`, the API returned a 409 Conflict response with details about the conflict. The frontend would prompt the user to refresh and retry.
    - **If asked more:** For the approval workflow in DRMS, we handled the specific case where two approvers tried to approve simultaneously. The stored procedure used `UPDATE ... WHERE Status = 'Pending' AND @@ROWCOUNT = 1` to ensure only one approval succeeded. The second would get a "This step has already been processed" error. We logged all concurrency conflicts for monitoring.

11. How did you implement the LDAP SSO integration in DRMS?
    - **Answer:** On login, the user entered their credentials. The API attempted to authenticate against the LDAP server using `System.DirectoryServices.Protocols` (for portability) or `System.DirectoryServices.AccountManagement` (when on Windows). If LDAP authentication succeeded, the user's info (name, email, groups) was retrieved from LDAP attributes. If the user didn't exist in our local `Users` table, they were auto-provisioned. If LDAP was unreachable, we fell back to local authentication.
    - **If asked more:** LDAP groups were mapped to application roles via configuration. For example, LDAP group "CN=DRMS-Admins,OU=Groups,DC=company,DC=com" mapped to the "Admin" role. The mapping was stored in a `RoleMappings` table. The LDAP server URL, base DN, and other settings were configurable in `appsettings.json`. We supported both LDAP and LDAPS (port 636).

12. How did you handle API versioning?
    - **Answer:** In PROXPERT, we used URL path versioning (`/api/v1/`, `/api/v2/`) with the `Asp.Versioning.Mvc` package. New endpoints were added to the latest version. When breaking changes were necessary, we incremented the version and kept the old version running for a deprecation period. Deprecated versions returned a `Sunset` header and logged warnings. The `ApiVersion` attribute was applied to controllers.
    - **If asked more:** We also supported media type versioning (`Accept: application/json;v=1.0`) as an alternative. The versioning strategy was documented in our API contract. We only had v1 during my tenure — v2 never materialized. Internal services didn't use versioning (we controlled both ends), only the public-facing API was versioned.

13. How did you design the error handling strategy?
    - **Answer:** I implemented a global exception handling middleware that caught all unhandled exceptions. It returned a structured response using the `ProblemDetails` RFC 7807 format. Different exception types mapped to different status codes: `ValidationException` → 400, `NotFoundException` → 404, `UnauthorizedAccessException` → 403, `DbUpdateConcurrencyException` → 409, and generic exceptions → 500.
    - **If asked more:** The middleware also logged the full exception details (including stack trace) to Serilog/Application Insights but only sent a generic error message to the client in production. In development, the full exception details were included. We also had a `FluentValidation` middleware that automatically returned 400 with all validation errors in the response body.

14. How did you handle logging across the application?
    - **Answer:** I used Serilog with structured logging. Every log entry included: `CorrelationId` (from the HTTP request), `UserId`, `TenantId`, `RequestPath`, and `ElapsedMilliseconds`. The `ILogger<T>` was injected via DI in all services and controllers. We used different sinks per environment: Console + File in development, Application Insights in production, and SQL Server for audit-specific logs in DRMS.
    - **If asked more:** The correlation ID was generated by middleware at the start of each request and stored in `HttpContext.Items`. It was also sent to the frontend via a response header so client-side errors could be correlated with server logs. We used Serilog's `Destructure` policy to avoid logging sensitive data (passwords, tokens).

15. How did you handle feature flags?
    - **Answer:** In PROXPERT, we used a simple database-backed feature flag system. The `FeatureFlags` table had: `Name`, `Enabled`, `AccountId` (for tenant-specific flags), and `LastModified`. A `FeatureFlagService` cached flags in Redis with 5-minute TTL. Controllers and views used `[FeatureGate("NewDashboard")]` attribute or `_featureFlagService.IsEnabled("NewDashboard")` to conditionally enable features.
    - **If asked more:** This allowed us to gradually roll out features to specific tenants. The admin panel had a feature flag management page. We also had "gradual rollout" flags that were enabled for a percentage of users based on the user ID hash. This was simpler than using Azure App Configuration's feature flags, though we considered migrating.

16. How did you design the API for the React frontend?
    - **Answer:** The API followed RESTful conventions: `GET /api/documents`, `POST /api/documents`, `PUT /api/documents/{id}`, `DELETE /api/documents/{id}`. Collections supported query parameters for filtering, sorting (`?sort=createdAt:desc`), and pagination (`?page=1&pageSize=20`). Responses included pagination metadata (total count, page, pageSize) in the response headers or body. Error responses used the ProblemDetails format.
    - **If asked more:** We also had a `GET /api/documents/{id}/approvals` endpoint for fetching the approval workflow state. The API was designed to be consumed by the React SPA, but also by potential mobile clients (though that never materialized). We documented the API using Swagger/OpenAPI with `Swashbuckle`.

17. How did you handle the separation of concerns between frontend and backend?
    - **Answer:** The frontend and backend were completely separate projects with their own CI pipelines and deployment. The API was the contract — defined by OpenAPI/Swagger. The frontend consumed the API and didn't know anything about the backend's internal structure. The backend was built independently and served JSON. We never used server-side rendering (SSR) or any View engines.
    - **If asked more:** This separation allowed frontend and backend teams to work independently. The React team could run the app against a stub/mock API (using MSW) while the backend was being developed. In DRMS, since I was solo, the separation was less critical but still maintained — the Angular app was in a separate folder with its own `package.json`.

18. How did you handle data validation (client and server side)?
    - **Answer:** Validation was enforced on both sides. Client-side: Angular Reactive Forms validators (DRMS) or React Hook Form + Zod (PROXPERT) for immediate user feedback. Server-side: FluentValidation validators that checked all inputs before the handler executed. The server was the source of truth — client-side validation was purely for UX, never for security.
    - **If asked more:** FluentValidation validators were registered in the DI container and applied via MediatR's `IPipelineBehavior`. A `ValidationException` would be thrown with a list of errors, which the global middleware would return as a 400 response with field-level error messages. The frontend would map these back to the form fields.

19. How did you handle transactions across multiple database operations?
    - **Answer:** In EF Core, I used `IDbContextTransaction` for explicit transactions when an operation involved multiple `SaveChanges` calls. For the CQRS pattern in PROXPERT, I had a `TransactionPipelineBehavior` that automatically wrapped command handlers in a transaction. If the handler succeeded, the transaction was committed. If any exception occurred, it was rolled back. This was transparent to the handler code.
    - **If asked more:** For DRMS stored procedures, transactions were handled inside the procedures (`BEGIN TRANSACTION`/`COMMIT`/`ROLLBACK`). The refactored procedures used atomic operations and avoided nested transactions. For cross-database operations (which we didn't have), I'd have used the distributed transaction coordinator or a saga pattern.

20. How did you approach the performance optimization of the stored procedures?
    - **Answer:** The process was: 1) Identify slow procedures via SQL Server Profiler or `sys.dm_exec_query_stats`. 2) Analyze the execution plan — look for table scans, key lookups, and sort operations. 3) Rewrite the query using set-based operations instead of cursors. 4) Add missing indexes. 5) Parameterize all inputs to avoid plan cache bloat. 6) Test with production-like data volumes. The key changes were: adding covering indexes, converting cursors to joins, and removing `SELECT *`.
    - **If asked more:** One specific example: a procedure that joined 7 tables with multiple `OR` conditions was refactored into a `UNION ALL` of simpler queries, each using a different index. Another had a `WHILE` loop that processed rows one by one — replaced with a single `UPDATE` statement with a `JOIN`. The execution time dropped from 45 seconds to 2 seconds.

21. How did you handle search functionality in your applications?
    - **Answer:** For DRMS, search was implemented as stored procedures with `LIKE '%searchTerm%'` and `FULLTEXT` indexes for better performance. For PROXPERT, we used EF Core's `Contains` method which generated `LIKE '%term%'` queries. For high-performance search, we planned to implement Elasticsearch but it wasn't deployed during my tenure.
    - **If asked more:** The search supported: multiple field search (document title, description, creator name), date range filtering, status filtering, and sorting by any column. The search results were paginated server-side. We also had "advanced search" with field-specific criteria and boolean operators.

22. How did you design the audit logging system?
    - **Answer:** I implemented audit logging via EF Core's `SaveChangesInterceptor` (for PROXPERT) and database triggers (for DRMS stored procedures). The audit log captured: who made the change, what entity was changed, the old and new values, the timestamp, and the IP address. The data was stored in a separate `AuditLogs` table that was never modified or deleted — it was append-only.
    - **If asked more:** In PROXPERT, the `AuditInterceptor` inherited from `SaveChangesInterceptor` and processed entries with `EntityState.Added`, `Modified`, or `Deleted`. Sensitive fields (passwords, tokens) were excluded via a `[SkipAudit]` attribute. The audit logs were viewable in the admin panel and were kept for 7 years per compliance requirements.

23. How did you handle license plate or serial number tracking in the applications?
    - **Answer:** In DRMS, documents could be associated with license plates. This was implemented as a many-to-many relationship between Documents and LicensePlates tables. The license plate data was imported via a batch process (stored procedure that parsed uploaded files). Validation rules ensured: format compliance (regex pattern matching), uniqueness, and active status verification.
    - **If asked more:** The license plate search was critical — users needed to find all documents associated with a plate. I created a covering index on the join table for fast lookups. The stored procedure used index hints to force the correct index. We also had a "quick search" box on the dashboard that searched across document IDs, plate numbers, and customer names.

24. How did you handle the migration from .NET Framework to .NET Core (or version upgrades)?
    - **Answer:** DRMS started on .NET Core 3.1 and was upgraded to .NET 6 during my tenure. The upgrade involved: updating target framework, replacing deprecated APIs (e.g., `IWebHostEnvironment` changes), updating NuGet packages, and re-running all tests. It was surprisingly smooth — Microsoft's upgrade assistant tool helped identify breaking changes. PROXPERT started on .NET 8.
    - **If asked more:** The key challenges were: third-party library compatibility (we had to replace one that didn't support .NET 6), and some minor EF Core query behavior differences (a few queries returned different SQL, which we fixed by adding `AsSplitQuery()` where needed). The Angular app was upgraded from v10 to v12 during the same period.

25. How did you handle the separation between development and production configurations?
    - **Answer:** I used the standard ASP.NET Core approach: `appsettings.Development.json` for local overrides (local SQL Server, verbose logging, Swagger enabled) and `appsettings.Production.json` for production settings. Environment variables and Azure App Settings overrode these at runtime. The `IHostEnvironment.EnvironmentName` was set to "Production" by Azure App Service and "Development" when running locally via `ASPNETCORE_ENVIRONMENT`.
    - **If asked more:** I also had `appsettings.Staging.json` for the staging environment. The Docker builds used the `Release` configuration and the staging/production settings were injected at deployment time via environment variables. We never built environment-specific Docker images — the same image could run in any environment with different config.

26. How did you handle migration from one database to another?
    - **Answer:** I haven't done a major database migration (e.g., SQL Server to PostgreSQL) in these projects. For moving from SQL Server on-prem to Azure SQL Database for DRMS, the process was: 1) Use the Azure Database Migration Service to assess compatibility. 2) Export the database as a `.bacpac` file. 3) Import to Azure SQL. 4) Update the connection string in `appsettings.Production.json`. 5) Test all functionality. The migration was straightforward with no schema changes needed.
    - **If asked more:** The main issues were: firewall rules (Azure SQL requires firewall exceptions), connection string format differences, and performance differences (we needed to adjust some indexes for Azure SQL's performance characteristics). 27. How did you handle API rate limiting?
    - **Answer:** In PROXPERT, I implemented rate limiting using ASP.NET Core 8's built-in rate limiting middleware. I configured a fixed window policy: 100 requests per minute per IP address for general endpoints and 10 requests per minute for authentication endpoints. The middleware returned a 429 Too Many Requests response with a `Retry-After` header. Rate limit exceeded events were logged for analysis.
    - **If asked more:** We considered per-user rate limiting (using the JWT subject claim) but kept it IP-based for simplicity. The rate limiting limits were generous since the app was internal. We also had a "burst" allowance of 20 requests in 10 seconds before the per-minute limit kicked in.

28. How did you handle user session management?
    - **Answer:** We used JWT tokens — no server-side session state. The access token (15-minute expiry) was stored in `sessionStorage` on the frontend. The refresh token (7-day expiry) was stored in an HTTP-only secure cookie. When the access token expired, the client's 401 interceptor triggered a refresh request. The backend validated the refresh token and issued a new access token.
    - **If asked more:** If the refresh token was expired or invalid, the user was logged out. The refresh token was rotated (a new refresh token was issued with each access token refresh) and the old one was invalidated. This prevented replay attacks. For LDAP SSO in DRMS, the session duration was controlled by the LDAP server's settings.

29. How did you handle Tenant-based isolation in PROXPERT?
    - **Answer:** PROXPERT was a multi-tenant application with shared database, shared schema. Each table had a `TenantId` column (a GUID). A `TenantResolutionMiddleware` extracted the tenant ID from the JWT claims (the `tid` claim). All queries included `.Where(e => e.TenantId == currentTenantId)` via a `ITenantProvider` that was injected into all services. We used EF Core's global query filters (`HasQueryFilter`) to automatically add this condition to all queries.
    - **If asked more:** The global query filter prevented accidental cross-tenant data leaks. Filtering was applied at the database level, so no amount of application-level logic issues could expose another tenant's data. The tenant resolution was based on the authenticated user's tenant — one user could only access one tenant. We also had a `TenantAdmin` role that could access multiple tenants for support purposes.

30. How did you approach security in your API design?
    - **Answer:** 1) Authentication: JWT tokens with OAuth2/Entra ID for PROXPERT, LDAP SSO for DRMS. 2) Authorization: RBAC with `[RequirePermission]` attribute. 3) Input validation: FluentValidation on the server, client-side validation on the frontend. 4) Output encoding: Auto by ASP.NET Core and the frontend framework. 5) CSRF: Anti-forgery tokens for state-changing operations. 6) Rate limiting. 7) HTTPS enforced everywhere. 8) Sensitive data: Never logged. 9) SQL injection: EF Core or parameterized queries only. 10) XSS: Content Security Policy headers.
    - **If asked more:** We also had: security headers (X-Content-Type-Options, X-Frame-Options, CSP), dependency scanning with OWASP Dependency Check in CI, and regular penetration testing by an external vendor. Secrets were stored in Azure Key Vault. The frontend never stored sensitive data (no tokens in localStorage).

31. How did you handle pagination in your APIs?
    - **Answer:** I used cursor-based pagination for the most common use case (infinite scroll in the frontend) and offset-based pagination for the admin panel (traditional page numbers). The API returned: `data` (the records), `cursor` (next cursor value), and `hasMore` (boolean). For offset-based: `data`, `page`, `pageSize`, `totalCount`, and `totalPages`. The frontend used React Query's `getNextPageParam` for cursor-based infinite queries.
    - **If asked more:** Cursor-based pagination is more performant for large datasets because it doesn't require `OFFSET` which degrades on deep pages. The cursor was usually the last record's ID (an indexed, sequential column). For the Angular app in DRMS, we used traditional offset-based pagination since the data was limited (documents were around 10K total).

    - **Answer:** The contract was the OpenAPI/Swagger specification. The backend generated the `swagger.json` automatically via `Swashbuckle`. For Angular, I used `NSwag` to generate TypeScript client code from the Swagger spec. For React, we didn't use code generation — we manually typed the API responses but referenced the Swagger spec as the source of truth. Any API change required updating the spec first.

33. How did you handle the integration between Search and Filtering?
    - **Answer:** The API accepted a `search` query parameter for full-text search and individual filter parameters (e.g., `status=Pending`, `dateFrom=2024-01-01`). All filters were combined with AND logic. The backend query built an expression tree that combined the conditions. Filters were validated for allowed values and SQL injection was prevented by using parameterized queries.
    - **If asked more:** The stored procedure in DRMS used a dynamic SQL builder that constructed the WHERE clause based on which parameters were provided. I was careful to use `sp_executesql` with parameters to avoid SQL injection. The procedure also had a `@SearchMode` parameter ('All' or 'Any') for the search keywords.     - **Answer:** The document lifecycle had these statuses: Draft (not yet submitted), PendingApproval (submitted, waiting for approvers), InReview (currently being reviewed by an approver), Approved (all approvers approved), Rejected (an approver rejected), Cancelled (submitter cancelled mid-flow), and Archived (old, read-only). The EF Core configuration used `HasConversion<string>()` to store the string name for readability in the database. The frontend showed different actions and UI based on the current status — Draft showed "Submit" button, PendingApproval showed "Cancel Request" button, Approved showed a green badge.

    - **Answer:** Notifications were both in-app and email. The email system used a queue table processed by a background service. ## Scenario-Based Questions

1. A user reports that after the recent deployment, the "Approve Document" button is not showing for approvers even though they have the correct role. How do you debug?
   - **Answer:** First, I'd check the browser DevTools Network tab to see if the permissions API call returns the expected permissions for the user. Then, I'd check the React/Angular component that conditionally renders the button — was the permission key recently renamed? I'd check the `PermissionGuard`/`*appIfPermission` directive. Then I'd look at the API endpoint to ensure it's returning the user's permissions correctly. Finally, check the database `RolePermissions` table for the user's role. I'd also check if the RBAC cache was cleared after the deployment. In PROXPERT, I'd check Redis for stale cached permissions.

2. You deploy a new version of the API to Azure, but the health check endpoint starts returning unhealthy. What do you do?
   - **Answer:** I'd first check the App Service's Diagnose and Solve Problems blade and the Application Insights live metrics for errors. I'd look at the Serilog logs in Kudu or Azure Blob storage. Common causes: database connection string changed, Redis is unreachable, or a new dependency failed to register. I'd check the `appsettings` in the Azure portal to ensure they're correct. I'd also check the deployment slot's configuration — sometimes settings don't swap correctly. If it's a startup issue, I'd temporarily disable the custom health check and investigate the startup logs.

3. A stored procedure that used to run in 2 seconds is now taking 2 minutes after the latest release. What's your approach?
   - **Answer:** First, I'd check if the execution plan changed by running `EXEC sp_updatestats` and then checking the actual execution plan. Common causes: parameter sniffing (cached plan for atypical parameters), missing indexes after schema changes, or increased data volume. I'd look at `sys.dm_exec_query_stats` for the procedure. I'd use `WITH RECOMPILE` temporarily to see if it's a parameter sniffing issue. If it was my refactored procedure from DRMS, I'd compare the old and new execution plans, check if the new procedure has proper indexes, and verify the `WHERE` clause is sargable. I'd also check if any blocking or deadlocking is occurring.

4. A user says they approved a document, but the system shows it's still pending. Another approver says they also approved it. What happened?
   - **Answer:** This sounds like a concurrency issue. I'd check the `WorkflowSteps` table to see both approvals. If both approvers had the same step (e.g., both are level-1 approvers), they might have both clicked approve at the same time. Our stored procedure used `UPDATE ... WHERE Status = 'Pending' AND @@ROWCOUNT = 1`, so only one should succeed. I'd check if the second one got a "already processed" error that wasn't shown to the user. I'd also check if the frontend handled the 409 Conflict response correctly — maybe the error was silently swallowed. If both approvals succeeded, there's a bug in the concurrency guard that I'd need to fix. I'd then write a test that reproduces the race condition.

5. The API is returning 500 errors sporadically — about 1 in 100 requests. How do you find the cause?
   - **Answer:** I'd look at Application Insights' failed requests and exception telemetry. Since it's intermittent, I'd look for patterns: does it happen for specific endpoints, specific times of day, or specific users? I'd check the exception details and stack trace. Common causes: thread safety issues in static/shared state, race conditions, database deadlocks (error 1205), or transient network failures. I'd check if there's a missing null check or an unobserved task exception. If the error is a database deadlock, I'd add retry logic with Polly. I'd also check the IIS/Azure logs for request timing — maybe a timeout during peak load.

6. A feature that works perfectly in the development environment fails in production. What's your debugging process?
   - **Answer:** First, I'd check the differences: database data (production has more data, different data patterns), configuration (different API URLs, connection strings), and environment (production is HTTPS, behind a load balancer). Common issues: hardcoded environment-specific values, missing CORS configuration, different time zones, or culture-specific formatting (e.g., decimal separators). I'd enable verbose logging in production for that specific feature (via Serilog's minimum level override) and reproduce the issue. I'd also check if the issue is a race condition that only manifests under production load. In DRMS, a common issue was that production had larger datasets that exposed inefficient query patterns.

7. The CI pipeline is failing at the "Run Tests" stage, but all tests pass locally. What do you check?
   - **Answer:** This is usually an environment mismatch. I'd check: 1) The test database — does the CI have a test database? Is it seeded with the right data? 2) Are environment variables or connection strings set in CI? 3) Is the .NET SDK version the same? 4) Are there any flaky tests that pass locally but fail under CI's parallelism? 5) Is the build agent out of disk space? 6) For Docker-based tests, is the Docker daemon running? I'd look at the CI logs for the specific test failure. If it's a timing issue, I'd increase timeouts. If it's a seeding issue, I'd make the test setup idempotent.

8. A user reports that the search feature returns results, but clicking on result number 3 always shows the wrong document. What's the bug?
   - **Answer:** This sounds like a pagination indexing issue. The most common cause: the "TotalCount" returned by the API doesn't match the actual number of results after filtering, or the OFFSET calculation is off. For example, if the stored procedure calculates total count before applying filters, the page numbers don't align. Or if the `ORDER BY` clause doesn't produce a stable sort (duplicate values in the sort column, records are inserted between page loads). I'd check the SQL query to ensure `OFFSET/FETCH` is correct and the `ORDER BY` is on a unique column combination. For cursor-based pagination, I'd check if the cursor encoding/decoding has a bug.

9. After deploying the Angular SPA, users on IE11 get a blank page. What do you do?
   - **Answer:** First, I'd check the browser console for errors. Angular doesn't support IE11 after v13, so if we upgraded Angular, the solution would be to inform the client that IE11 is no longer supported. If we must support IE11, I'd check the `browserslist` configuration and `polyfills.ts` — ensure we're including the right polyfills for ES6 features. I'd also check if the deployment is sending the right `Content-Type` for JS bundles. In DRMS, we only supported modern browsers (Chrome, Edge, Firefox) so IE11 wasn't a concern.

10. The "Forgot Password" email sometimes arrives hours later. What's the issue?
    - **Answer:** This sounds like an email queue processing issue. In DRMS, the background service polled the `EmailQueue` table every 30 seconds. If the queue is backing up, either: 1) The SMTP server is slow or rate-limited. 2) A failed email with retries is blocking the queue (if processing fails and retries are immediate, it could delay other emails). 3) The background service is crashing and restarting. I'd check the `EmailQueue` table for pending emails with old timestamps, check the SMTP server logs for delays, and check the application logs for any email sending errors. I'd also consider using a dedicated email service like SendGrid or Azure Communication Services for better deliverability.

11. Two users are editing the same document simultaneously. User A saves their changes, then User B saves. User A's changes are lost. How do you fix this?
    - **Answer:** This is a lost update problem. The solution is optimistic concurrency. I'd add a `RowVersion` column to the document table. When User A loads the document, they get the current version. When they save, the update is `UPDATE ... WHERE Id = @Id AND RowVersion = @OriginalVersion`. If User B saved first, A's update would affect zero rows, and EF Core would throw a `DbUpdateConcurrencyException`. The API would return a 409 Conflict, and the frontend would show "This document was modified by another user. Please refresh and try again." In DRMS, the mid-approval cancellation also needed this — if the document was being edited and submitted for approval simultaneously, the concurrency check prevented race conditions.

12. A deployment process that used to take 10 minutes now takes 45 minutes. What changed?
    - **Answer:** I'd investigate by checking the Azure DevOps pipeline execution logs for the timed-out stage. Common causes: 1) Docker image size increased (check if `node_modules` or build artifacts are being included). 2) NuGet packages are taking longer to restore (maybe a private feed is slow). 3) Database migration is running (if we changed the migration strategy). 4) The build agent is running low on resources. 5) A new SonarQube analysis is running and slowing things down. I'd also check if the deployment to Azure is slower — maybe the slot swap warm-up is taking longer. I'd benchmark each stage separately and optimize the bottleneck.

13. An API endpoint that returns a list of documents is suddenly returning empty results. The database has data. What's wrong?
    - **Answer:** I'd check: 1) Is the tenant ID filter working correctly? Maybe the user's JWT has a different tenant ID. 2) Did a recent deployment change a filter condition (e.g., status filter added)? 3) Is there a caching issue — stale data being returned (or not returned)? 4) Is the SQL query generating the correct WHERE clause? I'd run the actual SQL query generated by EF Core against the database to see if it returns data. 5) Did a schema change break the mapping? I'd check the EF Core entity configuration and migrations. 6) Is the connection string pointing to the right database? In PROXPERT, we had an incident where a slot swap changed the database connection string unintentionally.

14. After adding a new index to improve performance, some operations start failing with deadlock errors. What happened?
    - **Answer:** The new index changed the execution plan for some queries, and they're now accessing tables in a different order, causing a deadlock with other concurrent operations. I'd analyze the deadlock graph from SQL Server's `system_health` session or via Azure SQL's deadlock logging. The fix options: 1) Add `WITH (NOLOCK)` hints for read operations (if dirty reads are acceptable). 2) Reorder operations in the application to acquire locks in a consistent order. 3) Use `READ COMMITTED SNAPSHOT` isolation level to reduce locking. 4) Create covering indexes that eliminate key lookups (reducing lock duration). 5) For the specific deadlocked queries, add `INDEX` hints to force the old execution plan temporarily while investigating.

15. A user logs in and sees another user's dashboard data for a split second before their own data loads. What's the issue?
    - **Answer:** This is an auth state issue — probably the previous user's data is cached and shown before the new user's data loads. In the frontend, on logout, we need to clear all cached state: React Query cache, context state, and `sessionStorage`. On login, we should show a loading state until the new user's data is fully fetched. The fix: in the `AuthContext` logout function, call `queryClient.clear()` (React Query) or reset all services' `BehaviorSubject` (Angular). Also, ensure the API doesn't cache responses across users (check if any HTTP caching is happening). We might also need to add a "Loading..." screen during the initial data fetch after login.

16. A stored procedure that runs fine in SSMS returns incorrect data when called from the application. What's the difference?
    - **Answer:** This is a classic parameter sniffing issue or SET options difference. SSMS and the application might have different `SET` options (e.g., `SET ARITHABORT`, `SET ANSI_NULLS`). The cached execution plan might be optimized for one set of parameters and inefficient for another. Solutions: 1) Add `OPTION (RECOMPILE)` to the procedure. 2) Use local variables inside the procedure to avoid parameter sniffing: `DECLARE @LocalParam = @InputParam`. 3) Check `sys.dm_exec_query_stats` for the cached plan's parameters. 4) Ensure the application uses the same SET options as SSMS by executing `SET ARITHABORT ON` before the procedure call.

17. The React app is working, but when you refresh the page on a route like `/documents/123`, you get a 404 from the server. Why?
    - **Answer:** This is the classic SPA routing issue. The web server (Nginx in PROXPERT, IIS in DRMS) doesn't know about client-side routes. When you refresh `/documents/123`, the server tries to find a file at that path and returns 404. The fix: configure the web server to serve `index.html` for all non-file routes. For Nginx: `try_files $uri $uri/ /index.html`. For IIS: URL Rewrite rule with `<match url=".*" />` and `<action type="Rewrite" url="index.html" />`. For Angular specifically, you also need to set `<base href="/">` correctly in `index.html`.

18. A background job that sends notification emails has been running for 6 hours (normally finishes in 5 minutes). What's wrong?
    - **Answer:** This sounds like an infinite loop or a very slow operation. I'd check the background service logs for the current iteration. Possible causes: 1) The SMTP server is down, and each email is timing out before moving to the next. 2) A database lock is blocking the queue processing. 3) A bug in the processing logic is causing the same email to be processed repeatedly (no "mark as processed" step, or the update is not persisting). 4) The `CancellationToken` is not being respected, and a hang is occurring. I'd kill the background service, investigate the `EmailQueue` table for duplicate/recurring records, fix the bug, add a processing timeout, and implement a circuit breaker for the SMTP server.

19. The API is running slow during peak hours but fine otherwise. What's your analysis approach?
    - **Answer:** First, I'd check metrics in Application Insights: request rate, response time percentiles, dependency call times. I'd look for the bottleneck: is it the database (high CPU, blocking), the API itself (CPU-bound code), or an external service? I'd check Azure SQL's DTU/CPU usage and top queries by duration. Common fixes: 1) Add database indexing for the queries running during peak. 2) Implement caching for frequently accessed data. 3) Scale out the App Service (add instances). 4) Implement database read replicas for reporting queries. 5) Optimize the slowest API endpoints first. In PROXPERT, we found that a specific CMS endpoint was doing N+1 queries, which we fixed with `.Include()`.

20. A deployment to staging works, but when the slot is swapped to production, the site is down. What could cause this?
    - **Answer:** Common slot swap issues: 1) **Connection string swap settings** — if the staging slot's connection string is set to be "sticky" (slot-specific), it might point to the staging database. When swapped to production, the app might connect to the wrong database. 2) **Warm-up failure** — the swap didn't trigger the warm-up request, so the production slot isn't initialized. 3) **Configuration mismatch** — an app setting that exists in staging but not in production (or vice versa) causes a startup crash. 4) **Extension version mismatch** — Azure extensions (like the ASP.NET Core hosting bundle) might differ between slots. Fix: ensure all setting slots are correctly configured, test the swap in a non-production environment, and check the swap operation history in Azure Portal.

21. A user says they can see documents they shouldn't have access to. Investigate.
    - **Answer:** This is a security issue with top priority. I'd: 1) Check the audit logs to see which user accessed which documents. 2) Check the user's roles and permissions in the database. 3) Check if the `TenantId` or permission filter was accidentally removed from a recent code change (check Git diff). 4) Check if the RBAC cache was corrupted (clear Redis cache and verify). 5) Check if the JWT token contains the correct claims. 6) Reproduce the issue by creating a test user with limited permissions. I'd also check if the issue is in the frontend only (hiding UI but data still accessible via API) or in the backend (API actually returns unauthorized data). If it's the backend, roll back immediately and fix.

22. You need to add a new column to a table that's referenced in multiple stored procedures and EF Core entities. How do you do this safely?
    - **Answer:** The safe approach: 1) Add migration to create the column as nullable (so existing code still works). 2) Update the EF Core entity and DTOs. 3) Update stored procedures that need the new column — add it to SELECT lists, INSERT statements, etc. 4) Deploy the database migration first (separate from the application deployment). 5) Deploy the application update. 6) After the application is deployed and verified, backfill the new column with data if needed. 7) If the column should be NOT NULL, add the NOT NULL constraint after backfilling. This avoids issues with existing code trying to insert into the table without the new column.

23. The OAuth2 login flow works in development but fails in production with "redirect_uri_mismatch". What's wrong?
    - **Answer:** The redirect URI registered in the OAuth2 provider (Azure AD/Entra ID) must exactly match the callback URL your application uses. In development, it's probably `http://localhost:3000/callback`, but in production, it should be `https://yourdomain.com/callback`. The mismatch occurs because the production URL wasn't added to the allowed redirect URIs in the OAuth provider configuration. I'd check the Azure AD app registration's "Redirect URIs" list and add the production callback URL. Also ensure the `REACT_APP_REDIRECT_URI` environment variable is correctly set in production.

24. A user reports that when they upload a PDF document, the system says it saved successfully, but the document isn't visible anywhere. What happened?
    - **Answer:** This could be an optimistic UI update that failed silently. The frontend likely shows the document optimistically before the API confirms. If the API call failed (e.g., file too large, invalid format), the optimistic update wasn't rolled back. I'd check: 1) Browser DevTools Network tab to see if the upload API call succeeded. 2) Application Insights for the API request and any errors. 3) The document storage (Blob Storage or file system) to see if the file exists. 4) The database to see if the document metadata was saved. Fix: ensure the frontend properly handles upload errors and removes optimistic items from the list. Also, add a "refresh" button so users can manually reload.

25. A new team member accidentally pushed a sensitive connection string to the repository. What do you do?
    - **Answer:** First, assume the secret is compromised. 1) Immediately rotate the compromised secret (regenerate the database password, revoke the access key, etc.). 2) Remove the secret from Git history using `git filter-branch` or `git filter-repo` (BFG Repo-Cleaner tool is easier). 3) Force-push the cleaned history to all branches. 4) Notify the team to rebase their branches on the cleaned history. 5) Add the secret pattern to `.gitignore` and implement a pre-commit hook (e.g., using `git-secrets` or `detect-secrets`) to prevent future leaks. 6) Audit the access logs to see if the secret was exploited. 7) Move all secrets to Azure Key Vault and use environment variables or Key Vault references going forward.

26. The Angular app takes 10 seconds to load initially. How do you improve this?
    - **Answer:** I'd analyze the bundle with `webpack-bundle-analyzer` (or `source-map-explorer`). Common improvements: 1) Lazy load feature modules instead of eagerly loading everything. 2) Enable production mode (`--optimization --build-optimizer`). 3) Remove unused third-party libraries or replace with lighter alternatives. 4) Enable Angular Ivy's tree shaking. 5) Implement route-level code splitting. 6) Add preloading strategy for modules the user is likely to navigate to. 7) Enable HTTP/2 on the server for parallel loading. 8) Add gzip/brotli compression on IIS. 9) Use a CDN for static assets. 10) Implement application preboot to render a meaningful UI while Javascript loads. In DRMS, lazy loading the Admin module (which was rarely used) reduced initial load time significantly.

27. A query that uses a table-valued parameter (TVP) is running slow only when called from the application, not from SSMS. Why?
    - **Answer:** This is almost always a cardinality estimation issue. When calling from the application, the TVP might have few rows during compilation but many rows during execution, causing a suboptimal plan. Or SSMS might have different SET options that change the plan. Solutions: 1) Use `OPTION (RECOMPILE)` in the procedure to get a fresh plan each time. 2) If the TVP row count is relatively stable, update statistics. 3) Check if the application is passing the TVP with a different schema than expected. 4) In DRMS, I faced this and solved it by adding `OPTION (OPTIMIZE FOR UNKNOWN)` for the TVP parameter.

28. The Docker container for the API keeps restarting in production. How do you debug?
    - **Answer:** I'd check the container logs via `docker logs <container-id>` or Azure App Service's Log Stream. Common causes: 1) The application crashes on startup due to missing configuration (connection string, Redis endpoint). 2) Out of memory. 3) Health check is failing, and the orchestrator keeps restarting. 4) A port conflict. I'd check if the container can run locally with the same configuration. I'd also check the App Service's "Container Settings" to ensure the startup command and port mapping are correct. If it's a startup crash, I'd temporarily override the entry point to a sleep command and exec into the container to investigate.

29. Users report that the system becomes unresponsive every day at 2 PM for about 5 minutes. What could be the cause?
    - **Answer:** This is a periodic event. Likely candidates: 1) A scheduled background job (e.g., database backup, ETL process, data cleanup) running in the background and consuming all resources. 2) A database maintenance task (index rebuild, statistics update) causing blocking. 3) An external system integration (e.g., a daily data sync from a legacy system). 4) An IIS application pool recycle at a specific time. I'd check: scheduled tasks in SQL Server Agent, Azure Automation runbooks, App Service's application pool settings, and any job schedulers in the application. I'd also check SQL Server's `sys.dm_exec_requests` during the incident to see what queries are running.

30. A user says clicking the "Export to Excel" button works fine for 10 records but fails silently for 10,000 records. What's wrong?
    - **Answer:** This is likely a timeout or memory issue. The large dataset might: 1) Exceed the API's response timeout (default 30 seconds in Azure). 2) Exceed the memory limit for the API or the frontend. 3) The Excel library might not handle large data efficiently. 4) The database query might be timing out for the larger dataset due to a missing index or inefficient query. Solutions: 1) Implement server-side export (generate the Excel file on the server and return a download link via a background job). 2) Add pagination to the export — export in chunks and combine. 3) Increase the timeout. 4) Optimize the query with better indexing. 5) Use a streaming approach instead of loading all data into memory.

31. You need to deploy a hotfix for a critical security vulnerability. How do you bypass the full CI/CD pipeline safely?
    - **Answer:** 1) Create a hotfix branch from the production tag. 2) Apply the minimal fix. 3) Run only the relevant tests (unit tests for the affected area). 4) Get expedited code review (two-person approval). 5) Deploy to staging, run smoke tests. 6) Deploy to production with a manual approval step. 7) Monitor Application Insights for any anomalies. 8) Merge the hotfix back to the main branch. The key is to minimize changes — only the security fix, no other refactoring or improvements. After the hotfix, we'd investigate the root cause and ensure tests are added to prevent recurrence.

32. An Angular component shows "No data available" immediately (without a loading spinner), but the user knows there are records. What's wrong?
    - **Answer:** The API call likely failed silently. I'd check the browser DevTools Network tab to see if the API call was made and what it returned. The component might be checking `data.length === 0` but the `data` variable is `undefined` (not an empty array) because the async call threw an error that wasn't caught. The fix: ensure the component handles the loading, error, and empty states separately. The template should have: `*ngIf="loading"` for spinner, `*ngIf="error"` for error message, `*ngIf="data && data.length === 0"` for "No data", and `*ngIf="data && data.length > 0"` for the actual data. The component should initialize `data` as an empty array, not `undefined`.

33. You're asked to add a new feature to an existing controller without breaking existing functionality. What's your process?
    - **Answer:** 1) Write a characterization test — capture the current behavior of the existing endpoints in the controller. 2) Add the new endpoint or modify the existing one. 3) Run all existing tests to ensure nothing is broken. 4) Write new tests for the new functionality. 5) Update Swagger/OpenAPI documentation. 6) Update the frontend client code (if applicable). 7) Deploy and monitor. The key is step 1 — having tests that verify existing behavior gives me confidence that I haven't introduced a regression.

34. The application pool in IIS keeps crashing after every deployment until you manually restart it. Why?
    - **Answer:** This is a common issue with ASP.NET Core on IIS. When you deploy new files while the app pool is running, the files might be locked by the running process. The recommended approach: 1) Use `app_offline.htm` — place this file in the app root before deploying, which causes ASP.NET Core to shut down gracefully. 2) Deploy the new files. 3) Remove `app_offline.htm`. 4) The application pool will restart automatically. In DRMS, I automated this in the deployment script: stop the app pool, deploy, start the app pool. I also configured the app pool to use "Auto Start" mode to avoid the cold start delay after restart.

35. The application is running out of database connections, causing "The connection pool has been exhausted" errors. What's happening?
    - **Answer:** This indicates connection leaks — database connections are being created but not properly disposed. Common causes: 1) `SqlConnection` not wrapped in a `using` block. 2) `IQueryable` materialized lazily outside the `using` block. 3) Too many concurrent requests without connection pooling configured properly. 4) A deadlock or long-running query holding connections. I'd search the codebase for any `new SqlConnection` that doesn't use `using`. With EF Core, the connection is managed automatically, but if anyone created raw ADO.NET connections, I'd check those. I'd also review the connection string to ensure `Max Pool Size` is set appropriately.

36. A "mid-approval cancellation" triggers the cancellation email, but it goes to the wrong user. How do you diagnose?
    - **Answer:** I'd check the `WorkflowSteps` table for the specific document to see the approvers list. The cancellation email should go to: 1) All approvers who have already acted (their step status is "Approved" or "Rejected"). 2) All pending approvers (their step status is "Pending"). The bug might be: the email selection query includes the document owner, or excludes a specific approver, or sends to a stale email address. I'd check the stored procedure or LINQ query that fetches recipients. I'd also check the email template to ensure the recipient list is correct. I'd write a test that creates a workflow with multiple approvers, cancels it, and verifies the email queue has entries for the correct recipients.

37. Your React app's admin page shows "403 Forbidden" for a user who was just granted admin access. The user insists they logged out and back in. What's wrong?
    - **Answer:** The permissions are cached. Even if the user logged out and back in, the JWT token might contain the old claims (if the token wasn't refreshed after the role change). The RBAC system in PROXPERT cached permissions in Redis with a TTL. The flow: 1) Admin grants the user admin role. 2) The user's Redis cache still has old permissions. 3) The user needs to wait for the TTL to expire, or we need to invalidate the cache. The fix: when an admin changes a user's roles, we should immediately invalidate that user's Redis cache entry. Also, the frontend should re-fetch permissions on each page load (not just on login). I'd also check if the JWT token contains the roles claim — if so, the token itself needs to be refreshed.

38. A single stored procedure sometimes produces duplicate records in the results, but only under load. Why?
    - **Answer:** Under load, the procedure might be reading data that's being modified concurrently. If the procedure reads a table that's being updated by another transaction, it might see the same row twice (due to row versioning or read consistency level issues). The most likely cause: the procedure reads without a proper isolation level (or uses `READ UNCOMMITTED`/`NOLOCK`) while another transaction is splitting or moving data. The fix: 1) Use `SET TRANSACTION ISOLATION LEVEL SNAPSHOT` or `READ COMMITTED SNAPSHOT` for consistent reads. 2) Add `ORDER BY` to a unique column and use `DISTINCT` if duplicate rows are semantically impossible. 3) Ensure the procedure's logic handles concurrent modifications correctly.

39. The CI pipeline's "Build Docker image" step is failing with "no space left on device". You need to fix it without migrating to a larger agent. What do you do?
    - **Answer:** 1) Clean up the build agent: run `docker system prune -af` to remove unused containers, images, and build cache before the build. 2) Use Azure DevOps's built-in "Clean" option: set `clean: all` on the checkout step. 3) Reduce Docker image size by optimizing the Dockerfile (multi-stage builds, smaller base images, efficient `.dockerignore`). 4) Use a custom build agent with more disk space. 5) In the pipeline YAML, add a cleanup step before docker build. In PROXPERT, we added a daily scheduled job to clean up Docker resources on the build agent.

40. The application uses a third-party API that's rate-limited. During peak hours, requests to this API start failing, which causes our API to return errors. How do you handle this?
    - **Answer:** I'd implement a layered approach: 1) **Caching** — cache the third-party API responses with a TTL (we cached license plate validation results for 1 hour in PROXPERT). 2) **Queueing** — use a queue (in-memory or Azure Service Bus) for non-urgent requests and process them at a controlled rate. 3) **Rate limiting with Polly** — use Polly's `Bulkhead` policy to limit concurrent calls and `WaitAndRetry` with exponential backoff for rate-limited responses. 4) **Circuit breaker** — if the API is consistently failing, open the circuit and fail fast with a friendly message instead of hanging. 5) **Fallback** — provide a degraded experience when the API is unavailable (e.g., "License plate validation unavailable — will be validated later"). 6) **Monitoring** — alert when the third-party API's error rate exceeds a threshold.
