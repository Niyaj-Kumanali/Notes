# Entity Framework

## 1. Executive Summary

Entity Framework Core (EF Core) is Microsoft's open-source, cross-platform object-relational mapper (ORM) for .NET. It enables developers to work with databases using .NET objects, eliminating most of the data-access plumbing code. EF Core provides LINQ query translation, change tracking, migrations, lazy loading, and support for multiple database providers (SQL Server, PostgreSQL, SQLite, Cosmos DB, etc.).

## 2. Core Theory

### Architecture Layers

```
Application Code
    |  LINQ Queries / DbContext
    v
EF Core Runtime
    |  LINQ Expression -> SQL Translation
    v
Database Provider (e.g., Npgsql, Microsoft.Data.SqlClient)
    |  ADO.NET
    v
Database Server
```

### Key Components

- **DbContext**: Unit of work and repository pattern. Manages entity instances, change tracking, and database connections.
- **DbSet<T>**: Represents a collection/table for querying and saving entities.
- **Entity**: POCO class mapped to a database table.
- **Change Tracker**: Tracks state changes (Added, Modified, Deleted, Unchanged, Detached).
- **Model Builder**: Configures entity mappings via Fluent API or data annotations.
- **Migrations**: Code-based schema evolution tracked in the database.

### Entity States

```
Detached -> Added -> Unchanged -> Modified -> Deleted
                                      -> Detached (context disposed)
```

### LINQ Pipeline

```
C# LINQ Query
    |  IQueryable<T>
    v
Expression Tree (Expression<Func<T,bool>>)
    |  EF Query Pipeline
    v
Provider-Specific SQL (e.g., SELECT * FROM ... WHERE ...)
    |  ADO.NET Command
    v
Result Materialization (Entity instances)
```

## 3. Under-the-Hood Deep Dive

### Query Compilation and Caching

```csharp
// EF Core compiles LINQ queries into an internal representation,
// then caches the compiled query plan (query cache).

// First execution: expression -> SQL translation + parameter extraction
// Subsequent executions: cache lookup (by query structure)

// Queries with different parameter values reuse the same cached plan.
// Queries with different structure (different operators) are separate cache entries.

// The cache is a ConcurrentDictionary keyed on the query's expression tree structure
// (structural comparison, not reference equality).
```

### Change Tracking Internals

```csharp
// Each entity tracked is wrapped in an InternalEntityEntry:
internal class InternalEntityEntry
{
    public EntityState EntityState;          // Unchanged/Modified/Added/Deleted
    public ISnapshot OriginalValues;         // Snapshot at load time
    public ISnapshot CurrentValues;          // Current property values
    public ISnapshot StoreGeneratedValues;   // Generated by DB (auto-increment)
    public IKey Key;                         // Primary key info
    public DbContext Context;
    public Dictionary<INavigation, IForeignKey> Navigations;
}

// DetectChanges (called implicitly on SaveChanges):
// 1. For each tracked entity, compare CurrentValues vs OriginalValues
// 2. If properties differ, set EntityState = Modified
// 3. Detect navigation changes (adds/removes)
// 4. Propagate cascade actions
```

### LINQ Translation Pipeline

```csharp
// LINQ IQueryable -> SQL happens in stages:
// 1. Pre-processing: simplify expressions, remove redundant casts
// 2. Convert to query model: internal intermediate representation (SelectExpression)
// 3. Apply null semantics, parameterize constants
// 4. Translate SelectExpression to provider-specific SQL (SqlGenerator)
// 5. Compose query with client-evaluation markers
// 6. Execute via DbCommand

// Example translation:
// context.Products.Where(p => p.Price > 100).OrderBy(p => p.Name).Take(10)
//  ->
// SELECT TOP(@__p_0) [p].[Name], [p].[Price]
// FROM [Products] AS [p]
// WHERE [p].[Price] > @__Price_1
// ORDER BY [p].[Name]
```

### Lazy Loading Proxies

```csharp
// Lazy loading requires:
// 1. Install Microsoft.EntityFrameworkCore.Proxies
// 2. UseLazyLoadingProxies() in OnConfiguring
// 3. Navigation properties must be virtual

// Internally: Castle.Core DynamicProxy creates a proxy subclass
// Overrides navigation property getter -> if navigation is null, issues DB query
// Each navigation access can trigger a separate query (N+1 problem!)
```

## 4. Production Code Examples

```csharp
// DbContext with fluent configuration
public class AppDbContext : DbContext
{
    public DbSet<Product> Products => Set<Product>();
    public DbSet<Category> Categories => Set<Category>();
    public DbSet<Order> Orders => Set<Order>();

    protected override void OnConfiguring(DbContextOptionsBuilder options)
    {
        options.UseSqlServer(_connectionString, o =>
        {
            o.EnableRetryOnFailure(maxRetryCount: 3);
            o.CommandTimeout(30);
            o.MinBatchSize(1);
            o.MaxBatchSize(100);
        });
        options.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
    }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
    }
}
```

```csharp
// Entity configuration with IEntityTypeConfiguration
public class ProductConfiguration : IEntityTypeConfiguration<Product>
{
    public void Configure(EntityTypeBuilder<Product> builder)
    {
        builder.ToTable("Products", "inventory");
        builder.HasKey(p => p.Id);
        builder.Property(p => p.Name).HasMaxLength(200).IsRequired();
        builder.Property(p => p.Price).HasColumnType("decimal(18,2)");
        builder.Property(p => p.CreatedAt)
            .HasDefaultValueSql("GETUTCDATE()")
            .ValueGeneratedOnAdd();

        builder.HasOne(p => p.Category)
            .WithMany(c => c.Products)
            .HasForeignKey(p => p.CategoryId)
            .OnDelete(DeleteBehavior.Restrict);

        builder.HasMany(p => p.Tags)
            .WithMany(t => t.Products)
            .UsingEntity(j => j.ToTable("ProductTagMapping"));

        builder.HasIndex(p => p.Name).IsUnique();
    }
}
```

```csharp
// Repository with compiled queries (EF Core 2.0+)
public class ProductRepository
{
    private static readonly Func<AppDbContext, int, Product?> GetById =
        EF.CompileQuery((AppDbContext ctx, int id) =>
            ctx.Products.AsNoTracking().FirstOrDefault(p => p.Id == id));

    private static readonly Func<AppDbContext, decimal, IAsyncEnumerable<Product>> GetByPrice =
        EF.CompileAsyncQuery((AppDbContext ctx, decimal maxPrice) =>
            ctx.Products.Where(p => p.Price <= maxPrice));

    public Product? GetById(int id)
    {
        using var ctx = CreateContext();
        return GetById(ctx, id); // Compiled -> no LINQ cache lookup overhead
    }
}
```

```csharp
// Efficient bulk update (no N+1)
public async Task UpdateCategoryPricesAsync(int categoryId, decimal percentage)
{
    await _context.Products
        .Where(p => p.CategoryId == categoryId)
        .ExecuteUpdateAsync(setter => setter
            .SetProperty(p => p.Price, p => p.Price * (1 + percentage / 100)));
}
```

```csharp
// Paginated query with total count
public async Task<PagedResult<Product>> GetPagedAsync(
    IQueryable<Product> query,
    int page,
    int pageSize)
{
    var total = await query.CountAsync();
    var items = await query
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .ToListAsync();

    return new PagedResult<Product>
    {
        Items = items,
        Page = page,
        PageSize = pageSize,
        TotalCount = total
    };
}
```

```csharp
// Transaction with savepoints
public async Task TransferStockAsync(int fromId, int toId, int quantity)
{
    await using var transaction = await _context.Database
        .BeginTransactionAsync(IsolationLevel.Serializable);

    try
    {
        var from = await _context.Stocks.FindAsync(fromId);
        var to = await _context.Stocks.FindAsync(toId);

        from.Quantity -= quantity;
        to.Quantity += quantity;

        await _context.SaveChangesAsync();
        await transaction.CreateSavepointAsync("before_audit");

        await _context.AuditLogs.AddAsync(new AuditLog { /* ... */ });
        await _context.SaveChangesAsync();
        await transaction.CommitAsync();
    }
    catch
    {
        await transaction.RollbackToSavepointAsync("before_audit");
        throw;
    }
}
```

## 5. Real-World Scenarios

**Scenario 1: Multi-Tenant SaaS**
- Use global query filters for tenant isolation.
- Separate databases per tenant or shared with TenantId discriminator.
- Use `HasQueryFilter(t => t.TenantId == CurrentTenantId)`.

**Scenario 2: CQRS with Separate Read/Write Models**
- Write: full EF Core with change tracking, optimistic concurrency.
- Read: raw SQL via `FromSqlRaw` or Dapper for optimized queries.
- Use `AsNoTracking` for all reads.

**Scenario 3: High-Throughput Event Sourcing**
- Store events as JSON in a single table.
- Use owned entity types for event payload.
- Use `ToTable("Outbox")` with transactional outbox pattern.

**Scenario 4: Legacy Database Mapping**
- Use `[Key]`, `[Column]`, `[Table]` attributes for existing schema.
- Map stored procedures via `FromSqlRaw`.
- Use `HasDefaultValueSql` for computed columns.

## 6. Performance

```csharp
// AsNoTracking: avoids change tracking overhead
var products = await _context.Products
    .AsNoTracking()
    .Where(p => p.Price > 100)
    .ToListAsync();

// AsNoTrackingWithIdentityResolution: no tracking, but identity map
// (deduplicates entities by PK)

// Projection (Select): avoids loading unnecessary columns
var names = await _context.Products
    .Where(p => p.CategoryId == 1)
    .Select(p => new { p.Id, p.Name })
    .ToListAsync();
```

### Performance Anti-Patterns

```csharp
// BAD: N+1 queries
foreach (var order in orders)
{
    Console.WriteLine(order.Customer.Name); // Each access queries DB again!
}

// FIX: eager loading
var orders = await _context.Orders
    .Include(o => o.Customer)
    .ToListAsync();

// BAD: Cartesian explosion with multiple Includes + ThenInclude
var data = await _context.Orders
    .Include(o => o.Items)
    .Include(o => o.Shipments)  // Multiplies rows
    .ToListAsync();

// FIX: Split queries (EF Core 5+)
var data = await _context.Orders
    .Include(o => o.Items)
    .Include(o => o.Shipments)
    .AsSplitQuery()
    .ToListAsync();

// BAD: retrieving entire table to filter
var result = _context.Products.ToList()
    .Where(p => SomeClientSideCheck(p)); // Client evaluation

// FIX: filter before ToList
var result = _context.Products
    .Where(p => p.Price > 100)
    .ToList();
```

### Benchmark Guide

| Pattern                     | Queries      | Data Transferred | Memory        |
|-----------------------------|--------------|------------------|---------------|
| NoTracking + Select         | 1            | Minimal          | Low           |
| NoTracking                  | 1            | All columns      | Medium        |
| Tracking (default)          | 1            | All columns      | High (snapshot)|
| Lazy Loading (N+1)          | 1+N          | Per entity       | Very High     |
| Split Query (2 Includes)   | 3            | Per entity set   | Medium        |
| Eager Loading (1 Include)   | 1 (JOIN)     | Duplicated rows  | High (cart)   |

## 7. Security

```csharp
// SQL Injection protection
// EF Core parameterizes all LINQ queries automatically
var products = await _context.Products
    .Where(p => p.Name == userInput) // Safe: parameterized
    .ToListAsync();

// Raw SQL with interpolation (safe, uses SqlParameter)
var products = await _context.Products
    .FromSqlInterpolated($"SELECT * FROM Products WHERE Name = {userInput}")
    .ToListAsync();

// DANGEROUS: raw SQL with string concatenation
var sql = $"SELECT * FROM Products WHERE Name = '{userInput}'"; // Injection!
var products = await _context.Products.FromSqlRaw(sql).ToListAsync();

// Connection string security
// Never hardcode connection strings; use User Secrets or Azure Key Vault
// In production: environment variables or managed identity

// Row-Level Security: Use query filters
modelBuilder.Entity<Product>()
    .HasQueryFilter(p => p.TenantId == _currentTenantId);
```

## 8. Common Mistakes

```csharp
// MISTAKE 1: Context lifecycle too long (Captive context)
// DbContext should be scoped (ASP.NET Core: Scoped = per request)

// MISTAKE 2: Missing async
var products = _context.Products.ToList(); // Blocks thread!
// FIX: await _context.Products.ToListAsync()

// MISTAKE 3: Not disposing context
// FIX: use 'using' or DI injection (ASP.NET Core disposes scoped services)

// MISTAKE 4: Tracking overhead for read-only queries
// FIX: .AsNoTracking()

// MISTAKE 5: Including too much (Cartesian explosion)
// FIX: .AsSplitQuery() or multiple queries

// MISTAKE 6: Client-side evaluation of WHERE clause
// EF Core warns about this; move filtering before materialization

// MISTAKE 7: ToList() before pagination
var page = _context.Products.ToList().Skip(10).Take(10); // Loads ALL
// FIX: apply Skip/Take to IQueryable before ToList()

// MISTAKE 8: Not handling concurrency conflicts
// FIX: use [Timestamp] or [ConcurrencyCheck] attributes

// MISTAKE 9: Disposing context before lazy load completes
using var ctx = new AppDbContext();
var product = ctx.Products.First();
Console.WriteLine(product.Category.Name); // ObjectDisposedException!
// FIX: eager load or keep context alive

// MISTAKE 10: N+1 via lazy loading
// FIX: disable lazy loading or explicitly Include
```

## 9. Senior Engineer Perspective

**1. Use compiled queries for hot paths.** `EF.CompileQuery` avoids expression tree parsing and cache lookup.

**2. Batch operations with `ExecuteUpdate`/`ExecuteDelete` (EF Core 7+)** instead of loading entities.

**3. Use raw SQL for complex queries.** EF Core's LINQ translation has limits (window functions, recursive CTEs, full-text search).

```csharp
var products = await _context.Products
    .FromSqlRaw(@"
        SELECT p.*, ROW_NUMBER() OVER (PARTITION BY p.CategoryId ORDER BY p.Price DESC) AS rn
        FROM Products p")
    .Where(p => p.rn <= 3)
    .ToListAsync();
```

**4. Understand query split behavior.** Each split query creates a round trip; use judiciously.

**5. Design DbContext for testability.** Use `IDbContextFactory<T>` for Blazor and worker services.

**6. Consider compiled models** (`dotnet ef dbcontext optimize`) for startup time reduction in large models.

**7. Use `HasConversion` for value objects** (e.g., `Email`, `Money`).

```csharp
modelBuilder.Entity<User>()
    .Property(u => u.Email)
    .HasConversion(v => v.Value, v => Email.Create(v));
```

## 17. Revision Notes

- DbContext is scoped (per request). Do not inject as singleton.
- `AsNoTracking` reduces overhead for read-only queries.
- `Include`/`ThenInclude` for eager loading; `AsSplitQuery` to avoid Cartesian explosion.
- `ExecuteUpdate`/`ExecuteDelete` for bulk operations without loading entities.
- Global query filters for soft delete and multi-tenancy.
- `FromSqlInterpolated` is safe (parameterized); `FromSqlRaw` with concatenation is dangerous.
- Concurrency: use `[Timestamp]` (row version) or `[ConcurrencyCheck]`.
- Migrations: `dotnet ef migrations add`, `dotnet ef database update`.
- Compiled queries for hot paths via `EF.CompileQuery`.
- `ToQueryString()` for debugging generated SQL.
