# CI/CD

---

## Overview

**Definition:** CI/CD (Continuous Integration and Continuous Delivery/Deployment) is a set of automated practices that form the backbone of modern software delivery. Continuous Integration means every developer's code change is automatically built and tested as it is committed to the shared repository, often multiple times per day. Continuous Delivery extends this by ensuring the software is always in a deployable state — the build, test, and staging deployment happens automatically, but a manual gate controls the final push to production. Continuous Deployment takes automation to its logical endpoint where every change that passes all pipeline stages is automatically released to production without any human intervention.

**Why It Exists:** Before CI/CD, teams operated in silos where developers would work on features for weeks or months and then attempt an integration just before a release. These "integration hell" periods were notoriously painful — merge conflicts piled up, tests revealed breaking changes across components, and the final deployment was a high-stakes manual operation performed late at night. CI/CD fundamentally changes this by shortening the feedback loop from weeks to minutes. When a developer commits code, they know within minutes whether their change integrates correctly with the rest of the system, whether existing tests still pass, and whether the artifact can be deployed. This rapid feedback catches integration issues when they are still small and cheap to fix, dramatically reduces manual errors by automating repetitive deployment steps, and enables organizations to release software at a cadence that matches their business needs — whether that is multiple times per day or once per month.

**Key Concepts:** Continuous Integration is the practice of automatically building and testing every commit to the shared repository. The core rule is simple: commit to main at least once per day, and the build must pass before the next commit is made. Continuous Delivery means the software is always in a deployable state — the pipeline produces a production-ready artifact that has passed all tests and security scans, but a manual approval step controls whether it actually reaches production. Continuous Deployment removes even that manual gate — every change that passes the pipeline goes straight to production. Pipeline as Code means the pipeline definition (stages, steps, triggers, conditions) lives in a version-controlled file alongside the application code — a Jenkinsfile in Groovy, a GitHub Actions workflow in YAML, or a GitLab CI configuration. This brings the benefits of version control — code review, branching, history, and audit trails — to the pipeline itself. Build Once Deploy Many enforces that a single immutable artifact is produced during the CI phase, and that exact artifact is promoted through every environment from development to production. The artifact built in CI must be byte-for-byte identical to the one deployed in production — no rebuilding, no environment-specific patches, no configuration embedded in the binary.

## Core Pipeline Stages

**Source / Commit** — Every pipeline begins with a trigger. The most common triggers are a push to a specific branch or the opening of a pull request. Branch filters ensure that only relevant branches trigger the pipeline — you typically run the full pipeline on main and develop branches, but only run linting and unit tests on short-lived feature branches to save time and compute. Path filters take this further by excluding changes to documentation, configuration files, or other non-code artifacts. For monorepos, path filters are essential — a change to the authentication service should not trigger the pipeline for the payment service. The branch strategy determines how triggers are structured: trunk-based development (merge to main multiple times daily) works best for CI/CD because every merge is small and frequently integrated, while GitHub Flow (feature branches to main) is a practical compromise that still enables continuous integration.

```yaml
trigger:
  branches:
    include: [main, develop]
  paths:
    exclude: [docs/*, README.md]
```

**Lint & Static Analysis** — Before any tests run, the pipeline should fail fast on code quality issues. Linters enforce coding standards — ESLint for JavaScript, Pylint for Python, RuboCop for Ruby, StyleCop for C. Static analysis tools like SonarQube, CodeQL, or Roslyn Analyzers detect potential bugs, security vulnerabilities, and code smells without executing the code. SAST (Static Application Security Testing) tools like Checkmarx, Fortify, or Semgrep scan source code for security issues such as SQL injection, cross-site scripting, or hardcoded credentials. This stage should complete in seconds to minutes, not hours. Running it first in the pipeline ensures that obvious issues are caught before expensive integration tests or builds are executed. Failing fast saves both compute resources and developer time.

**Unit Tests** — Unit tests are the foundation of the testing pyramid: fast, isolated, and numerous. Each test validates a single unit of behavior in isolation — a single function, method, or class — with all external dependencies mocked or stubbed. Unit tests must run on every commit without exception. If a unit test fails, the pipeline stops immediately — no further stages execute. The industry target is 70% code coverage or higher, but coverage percentage alone is misleading; the quality of tests matters more than the quantity. A well-written unit test suite runs in under five minutes for most projects and provides a safety net that allows developers to refactor with confidence. Test frameworks like JUnit, NUnit, pytest, and Jest provide the infrastructure, while mocking frameworks like Moq, Mockito, or unittest.mock enable isolation.

**Build** — The build stage compiles source code and produces immutable, versioned artifacts. For compiled languages (C, Java, Go, Rust), this means running the compiler and packaging the output into a distributable format — a DLL, JAR, EXE, or binary. For interpreted languages (JavaScript, Python, Ruby), the build stage may involve transpilation (TypeScript to JavaScript), bundling (Webpack, Vite), dependency installation (npm ci, pip install), or packaging (Docker image). Every artifact must be uniquely versioned using semantic versioning combined with the commit SHA — for example, `1.2.3+b4a7c9f`. This ensures traceability from the artifact back to the exact source code and commit that produced it. The artifact is then published to a registry — Docker Hub, GitHub Packages, Artifactory, ECR, Azure Artifacts — where it can be promoted through environments.

```yaml
- job: Build
  steps:
    - script: npm ci && npm run build
    - task: PublishBuildArtifacts@1
      inputs:
        PathtoPublish: 'dist'
        ArtifactName: 'drop'
```

**Integration Tests** — Where unit tests verify individual components in isolation, integration tests verify that components work together correctly. These tests connect to real databases, call real APIs, read from real message queues, and interact with real file systems. Integration tests are slower than unit tests (minutes instead of seconds) but provide higher confidence that the system actually works. They should run on every push to the main branch and on pull requests targeting main. A common pattern is to spin up test containers using Docker Compose or Testcontainers to provide the real dependencies in the CI environment. The goal is not to cover every possible scenario (unit tests handle that) but to verify that the components are wired together correctly and that the interfaces between them are compatible.

**Security Scan** — Modern CI/CD pipelines include multiple layers of security scanning. SAST scans analyze source code for vulnerabilities without executing it. Dependency scanning checks third-party libraries against known vulnerability databases — tools like npm audit, OWASP Dependency-Check, Snyk, or Dependabot. Container scanning tools like Trivy, Clair, or Anchore scan Docker images for known vulnerabilities in base images and installed packages. SBOM (Software Bill of Materials) generation creates a machine-readable inventory of all components in the artifact — a requirement for supply chain security compliance (Executive Order 14028, PCI DSS 4.0). The pipeline should fail if critical or high-severity vulnerabilities are found, with the severity threshold configurable per environment. Development environments might allow moderate vulnerabilities while production blocks everything above low severity.

```yaml
- job: Security
  steps:
    - uses: aquasecurity/trivy-action@master
      with:
        scan-type: fs
        severity: HIGH,CRITICAL
    - script: |
        npm audit --audit-level=high
```

**Deploy to Staging** — The staging environment is a production-like environment where the full stack is deployed and tested before reaching production. Staging should mirror production as closely as possible — same infrastructure, same scale, same configuration, same data volume (anonymized). After deployment, smoke tests verify that the application started correctly, that health endpoints respond, and that critical paths work. Then E2E tests run the full user workflows against the staging environment. If any smoke test or critical E2E test fails, the pipeline stops and the artifact is not promoted further. Staging is also where performance tests, load tests, and security penetration tests should be executed periodically.

**Deploy to Production** — The final stage pushes the artifact to production. For Continuous Delivery, this stage requires manual approval — a human reviews the pipeline results and clicks "approve" in the CI/CD tool. For Continuous Deployment, this stage is fully automated with environment-specific gates: health check monitoring, error rate thresholds, latency budgets. If the deployment causes error rates to spike or latency to increase beyond the threshold, the pipeline automatically rolls back. Production deployment strategies include rolling updates (gradually replacing instances), blue-green deployments (switching traffic between two identical environments), and canary deployments (routing a small percentage of traffic to the new version). The choice depends on the application's architecture, risk tolerance, and recovery requirements.

```yaml
- stage: Deploy_Prod
  dependsOn: Deploy_Staging
  condition: eq(variables['Build.SourceBranch'], 'refs/heads/main')
  trigger: manual
  jobs:
    - job: Deploy
      steps:
        - script: helm upgrade app ./chart --values prod-values.yaml
```

Here is a complete reference pipeline that ties all the stages together:

```yaml
trigger:
  branches: { include: [main, develop] }
  paths: { exclude: [docs/*, README.md] }

stages:
  - stage: CI
    jobs:
      - job: Lint
        steps:
          - script: npm run lint
      - job: Test
        steps:
          - script: npm run test -- --coverage
      - job: Build
        steps:
          - script: npm ci && npm run build
          - task: PublishBuildArtifacts@1
            inputs: { PathtoPublish: 'dist', ArtifactName: 'drop' }
  - stage: SecurityScan
    dependsOn: CI
    jobs:
      - job: TrivyScan
        steps:
          - uses: aquasecurity/trivy-action@master
            with: { scan-type: fs, severity: HIGH,CRITICAL }
  - stage: Deploy_Staging
    dependsOn: SecurityScan
    jobs:
      - job: Deploy
        steps:
          - script: helm upgrade app ./chart --values staging-values.yaml
  - stage: Deploy_Prod
    dependsOn: Deploy_Staging
    condition: eq(variables['Build.SourceBranch'], 'refs/heads/main')
    trigger: manual
```

## Common Mistakes

- **Building artifacts in multiple stages** — The most fundamental CI/CD anti-pattern is building the artifact in the CI stage and then rebuilding it in the deployment stage. This guarantees that what is tested in staging is not what is deployed to production. The artifact must be built exactly once in CI, published to a registry, and then promoted by reference through every subsequent environment. Rebuilding introduces the possibility of environment-specific differences — different dependency versions, different compiler versions, different configuration files being baked in. The "Build Once, Deploy Many" principle exists specifically to prevent this inconsistency.
  - **Why it looks correct:** Rebuilding seems like a natural way to inject environment-specific configuration, and it's not obvious that a byte-for-byte identical binary is actually the goal.
- **Hardcoded secrets in pipeline YAML** — It is alarmingly common to find database passwords, API keys, or cloud credentials hardcoded directly in pipeline configuration files. Because these files are typically stored in version control, anyone with access to the repository has access to production credentials. Even worse, the secrets remain in the git history after they are removed from the file. Secrets must always be stored in the CI/CD tool's built-in secret management — GitHub Secrets, GitLab CI Variables, Azure DevOps Variable Groups, or Jenkins Credentials. For cloud authentication, OIDC (OpenID Connect) eliminates the need for static secrets altogether by allowing the CI/CD tool to exchange a short-lived token with the cloud provider.
  - **Why it looks correct:** Putting a variable in the YAML file is the most straightforward way to get it into the pipeline, and it works during initial setup without any visible security issue.
- **No database changes in pipeline** — Many teams have excellent CI/CD pipelines for application code but handle database migrations as a separate, manual step. This creates a dangerous gap — the application deployed by the pipeline expects certain schema changes to exist, but those changes were applied manually (or not at all). Database migrations must be part of the pipeline, version-controlled alongside the application code, and executed as part of the deployment process. Tools like Flyway and Liquibase manage schema changes as versioned migration scripts, tracking which migrations have been applied to each database instance.
  - **Why it looks correct:** Database changes feel different from code changes — they're stateful and irreversible, so keeping them separate seems prudent rather than dangerous.
- **Building on every branch without filter** — Running the full CI/CD pipeline on every branch, including short-lived feature branches, wastes compute resources and developer time. A documentation change does not need to trigger security scans and deployment to staging. Use branch filters to run the full pipeline only on main, develop, and release branches. Use path filters to skip pipeline execution entirely for changes to documentation, configuration files, or other non-code artifacts. Feature branches should run only linting and unit tests — fast checks that verify the code is syntactically correct and the basic logic works.
  - **Why it looks correct:** More testing feels better, and running the full pipeline everywhere seems like the safest approach — the cost just isn't visible until the CI bill arrives or developers start waiting in queues.
- **Ignoring flaky tests** — Flaky tests — tests that sometimes pass and sometimes fail without any code change — are a slow poison for CI/CD pipelines. When developers see random failures, they start ignoring pipeline results. They re-run the pipeline without investigating. They stop trusting the test suite. Eventually, real failures slip through because everyone has learned that "the pipeline fails all the time." Flaky tests must be immediately quarantined — moved to a separate test suite that is not part of the CI gate — and assigned to someone to fix. No new flaky tests should be added to the main test suite until the fix is in place. Treat flaky tests as production incidents: they erode the trust that makes CI/CD valuable.
  - **Why it looks correct:** A test that passes most of the time seems like a minor nuisance rather than a systemic problem, and re-running the pipeline is faster than investigating the root cause.
- **Long-running pipelines** — If a CI/CD pipeline takes more than 15-30 minutes to complete, developers will start working around it. They will batch commits to avoid waiting. They will skip the pipeline on small changes. They will push directly to main to bypass the gate. A slow pipeline is almost as bad as no pipeline because it incentivizes the same behaviors that CI/CD is meant to eliminate. Fix slow pipelines by parallelizing independent stages, running tests in parallel across multiple agents, caching dependencies and build outputs, implementing incremental builds (only build what changed), and moving expensive tests (E2E, performance) to post-deploy runs rather than the CI gate.
  - **Why it looks correct:** A comprehensive pipeline that tests everything feels thorough — the team doesn't realize developers are working around it until someone pushes a breaking change directly to main to "save time."
- **No artifact versioning** — Deploying artifacts without versioning means you cannot trace a production issue back to the exact code that caused it. You cannot roll back to a known good version because you do not know which version was previously deployed. Every artifact must have a unique, immutable identifier that includes the version number and the commit SHA — for example, `1.2.3+b4a7c9f`. This identifier is embedded in the artifact metadata, recorded in the deployment log, and correlated with monitoring and observability tools. When an incident occurs, the version tag tells you exactly which commit, which dependencies, and which build produced the running artifact.
  - **Why it looks correct:** The artifact works regardless of whether it has a version tag, and adding versioning seems like overhead when you're just trying to ship.
- **Manual deployment steps** — Any manual step in the deployment process is an opportunity for human error. Did you run the migration script before deploying the new version? Did you update the environment variables? Did you verify the health check? Manual steps are also slow — a five-minute automated deployment can become a thirty-minute manual process if someone has to SSH into servers, run commands, and visually verify outputs. The goal of CI/CD is to automate every step of the deployment process from commit to production. If a step cannot be automated today, document it, automate it tomorrow, and treat it as technical debt.
  - **Why it looks correct:** Manual steps feel safer — a human checking each stage seems more reliable than trusting an automated script, and the extra time seems worth the "quality."
- **No rollback strategy** — Every deployment carries the risk of failure. The question is not whether a deployment will fail, but whether the recovery from failure is fast and reliable. Without an automated rollback strategy, recovery requires someone to manually identify the failure, determine the previous good version, and execute the rollback steps — all while production is degraded or down. Automated rollback should be triggered by health check failures, error rate spikes, or latency increases immediately after deployment. The rollback should deploy the previous artifact version through the same pipeline stages, creating an audit trail of the recovery.
  - **Why it looks correct:** Planning for failure feels pessimistic, and most deployments succeed — so investing in rollback automation seems like over-engineering until the first bad deployment takes the site down for an hour.
- **Environment drift** — When environments are configured manually or through different processes, they inevitably drift apart. Staging might have different instance sizes, different database configurations, different network policies than production. When this happens, the pipeline that passes in staging can fail in production because of unanticipated differences. The solution is Infrastructure as Code (IaC) — defining all environment configurations in version-controlled configuration files (Terraform, CloudFormation, ARM templates, Pulumi). Every environment is provisioned from the same IaC templates, with environment-specific values injected through parameter files that are also version-controlled.
  - **Why it looks correct:** Setting up staging "like production" manually once seems sufficient — the subtle differences only become apparent months later when a staging-only config causes a pipeline to pass but production to fail.

## Key Design Considerations

**Build Once, Deploy Many** — This is the single most important principle in CI/CD pipeline design. The CI stage produces an artifact — a Docker image, a compiled binary, a packaged application — that is immutable and versioned. That exact artifact is then promoted through staging, QA, and production environments without being rebuilt or modified. The artifact's integrity is verified at each stage (checksum verification, signature validation), and environment-specific configuration is injected at deploy time through environment variables, configuration files, or Kubernetes ConfigMaps. This principle eliminates the most common source of deployment failures: the difference between what was tested and what was deployed. It also enables reliable rollback — if version 1.2.3 works in production, deploying version 1.2.2 is guaranteed to restore the previous state because the artifact is byte-for-byte identical to what was previously tested.

**Pipeline as Code** — Storing pipeline definitions in version control alongside the application code is a foundational practice that brings all the benefits of software engineering to CI/CD. Pipeline as Code enables code review for pipeline changes, so a teammate can catch a misconfigured security scan or a missing deployment step before it reaches production. It provides a complete audit trail of who changed the pipeline, when, and why. It supports branching — experiment with a new pipeline stage on a feature branch, test it, and merge it to main when ready. It also enables reproducibility: given a specific commit hash, you can reconstruct the exact pipeline that built and deployed that version. The most common pipeline-as-code formats are YAML (GitHub Actions, GitLab CI, Azure DevOps), Groovy DSL (Jenkins Pipeline), and HCL (Waypoint).

**Branch Strategy** — The choice of branching strategy directly impacts how CI/CD pipelines are structured. Trunk-Based Development is the purest CI/CD approach: developers merge to main multiple times per day, feature branches last hours not days, and every merge triggers the full pipeline. This maximizes integration frequency and minimizes merge conflicts. GitHub Flow is a middle ground: feature branches are created from main, pull requests trigger CI, and merges to main trigger CD. GitFlow is the most structured approach with separate branches for features, develop, releases, and hotfixes — it works well for scheduled releases but creates friction for continuous deployment because the release branch introduces a batching step. The choice depends on the team's release cadence: trunk-based for SaaS products deployed multiple times per day, GitHub Flow for teams that deploy daily, and GitFlow for products with scheduled, versioned releases.

**Deployment Strategies** — Rolling deployments gradually replace instances in the target environment, one by one or in small batches. This is the simplest strategy and works well for stateless applications, but it is slow to roll out and slow to roll back (each instance must be replaced). Blue-Green deployments maintain two identical environments: the current "blue" environment serves production traffic while the "green" environment is deployed and tested. Once validated, the router or load balancer switches traffic from blue to green in an instant. Rollback is equally instant — switch back. The trade-off is cost: you need double the infrastructure during deployment. Canary deployments route a small percentage of traffic (1%, 5%, 10%) to the new version while the old version handles the rest. If metrics remain healthy, traffic is gradually shifted to the new version. Canary deployments are resource-efficient and low-risk but require sophisticated traffic routing and monitoring infrastructure. Feature Flags decouple deployment from release entirely: code with new features is deployed to production but hidden behind a configuration toggle. The feature is enabled for internal testing, then gradually rolled out to users, and instantly disabled if issues arise. This is the most flexible approach but introduces complexity around flag management and the risk of accumulating untoggled flags.

**DORA Metrics** — The four key DevOps metrics defined by the DORA (DevOps Research and Assessment) team provide a quantitative framework for measuring CI/CD effectiveness. Deployment Frequency measures how often an organization successfully releases to production — elite performers deploy multiple times per day. Lead Time for Changes measures the time from code commit to the code successfully running in production — elite performers achieve less than one hour. Mean Time to Recover (MTTR) measures how long it takes to restore service after an incident — elite performers recover in under one hour. Change Failure Rate measures the percentage of deployments that cause a failure in production — elite performers have a failure rate below 5%. These metrics are correlated: teams that deploy frequently also tend to have lower failure rates and faster recovery times, because frequent deployments are smaller, less risky, and the deployment process is well-practiced. Tracking DORA metrics over time reveals whether pipeline improvements are actually moving the needle.

```yaml
# DORA metric tracking example
deployment_frequency: "daily"
lead_time_for_changes: "4 hours"
mean_time_to_recover: "30 minutes"
change_failure_rate: "2%"
```

**Pipeline Security** — The CI/CD pipeline has access to production infrastructure, which makes it a high-value target for attackers. Compromise the pipeline and you can inject malicious code into production artifacts. The security principles for pipeline design include: least privilege for all CI/CD credentials (a build job does not need production access); never hardcode secrets in pipeline definitions; use OIDC for cloud provider authentication (no static secrets to leak); sign all commits and artifacts with GPG or Sigstore; generate and store an SBOM for every build; scan all dependencies for known vulnerabilities; restrict service connections to specific environments and require approval for production access; and use hermetic builds that download dependencies from a curated, scanned registry rather than the public internet.

## Real-World Scenarios

**Scenario 1: Enterprise CI/CD Migration from Jenkins to GitHub Actions**

A company with 200 Jenkins pipelines running in a self-hosted Jenkins cluster needs to migrate to GitHub Actions. The motivation is reducing maintenance overhead — the Jenkins cluster requires dedicated infrastructure, plugin management, and security patching — while gaining tighter integration with GitHub repositories. The migration strategy follows a phased approach: first, audit all 200 pipelines and categorize them by complexity — simple (build-only, no deployment), medium (build-test-deploy to one environment), complex (multi-stage, multi-environment, custom plugins). Port the simple build-only pipelines first to build team confidence with GitHub Actions. Create reusable composite actions for common patterns — build-node-app, docker-build-and-push, deploy-to-aks — so each migrated pipeline is just a few lines of YAML that references these shared actions.

Run both Jenkins and GitHub Actions in parallel for three months, routing a subset of repositories to GitHub Actions while keeping the rest on Jenkins. Use a feature parity checklist to ensure the new pipelines match the old ones in functionality: same triggers, same test execution, same artifact publishing, same deployment targets. Migrate deployment pipelines last, as they carry the highest risk. Use the GitHub Actions Importer tool (GitHub's official migration utility) to automate the conversion of Jenkinsfiles to GitHub Actions workflows — it handles syntax translation and identifies Jenkins plugins that have no GitHub Actions equivalent, flagging them for manual conversion.

From day one of the migration, implement OIDC for AWS and Azure authentication. Jenkins likely used static service principal credentials or AWS access keys stored in Jenkins credentials. GitHub Actions OIDC allows each workflow run to request a short-lived token directly from the cloud provider, eliminating the need to store and rotate static credentials. This is a significant security improvement that should be a non-negotiable requirement for the new pipeline architecture.

```yaml
# GitHub Actions workflow replacing Jenkins pipeline
name: CI/CD Pipeline
on:
  push:
    branches: [main]
    paths-ignore: ['docs/**', 'README.md']
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
  security:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: aquasecurity/trivy-action@master
        with:
          scan-type: fs
          severity: HIGH,CRITICAL
  deploy:
    needs: security
    if: success()
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsDeploy
          aws-region: us-east-1
      - run: |
          echo "Deploying application..."
          aws ecs update-service --cluster prod --service app --force-new-deployment
```

**Scenario 2: Zero-Downtime Database Migration Pipeline**

A SaaS company needs to deploy database schema changes to a production PostgreSQL database without causing downtime. The application serves thousands of concurrent users and cannot tolerate more than a few seconds of unavailability. The solution is the Expand-Contract (also called Parallel Change) migration pattern, implemented through Flyway version-controlled migrations.

The pipeline has three phases. Phase 1 (Expand): Before the new application version is deployed, the pipeline runs migration scripts that are strictly additive — creating new columns, new tables, new indexes — but never removing or renaming existing schema elements. This phase is safe because the current application version does not reference the new schema elements. If anything goes wrong, the migration is rolled back without affecting the running application. Phase 2 (Deploy): The new application version is deployed. This version is written to read from both the old and new schema elements — it can handle the case where the new column exists (already created in phase 1) or does not (if a rollback occurred). The application writes to both old and new locations during this transition period. Phase 3 (Contract): After the deployment is verified and stable, a second set of migration scripts removes the deprecated schema elements — drops old columns, old tables, and renames transitional structures. This phase occurs in a subsequent pipeline run, hours or days after the deployment, ensuring there is time to detect and fix any issues before the removal.

For rollback support, each migration script has a paired undo script. If the post-deployment health checks fail (error rate spike, latency increase, failed smoke tests), the pipeline triggers an automatic rollback: the application is redeployed with the previous version, and the database is rolled back to the pre-expand state using the undo scripts. The key insight is that backward-compatible schema changes enable safe rollback — the old application version can still read the database correctly because no schema elements were removed or renamed.

```yaml
# expand-contract migration pattern
stages:
  - stage: Expand
    jobs:
      - job: AddNewColumns
        steps:
          - script: flyway migrate -target=expand_version
  - stage: Deploy
    jobs:
      - job: DeployApp
        steps:
          - script: helm upgrade app ./chart
  - stage: Contract
    dependsOn: Deploy
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - job: RemoveOldColumns
        steps:
          - script: flyway migrate -target=contract_version
```

**Scenario 3: Multi-Cloud CI/CD with Compliance Gates**

A regulated financial services company deploys to both AWS and Azure, with PCI-DSS compliance requirements that mandate security scanning, dependency auditing, artifact signing, and approval workflows for every production deployment. The CI/CD architecture must treat both clouds as equal deployment targets while maintaining a single CI pipeline.

The CI stage is cloud-agnostic: it builds the application, runs unit and integration tests, and produces a platform-agnostic Docker image. This single artifact is published to both AWS ECR and Azure ACR registries simultaneously, with the same version tag. Two separate CD pipelines — one for AWS, one for Azure — consume the same artifact from their respective registries. Each CD pipeline has cloud-specific deployment logic (Terraform modules for AWS vs. Azure, service connections for each cloud, environment-specific configuration) but both deploy the identical artifact.

Compliance gates are enforced at multiple points in the pipeline. The first gate is the security scan stage in CI — Trivy scans for vulnerabilities and the pipeline fails if any CRITICAL severity vulnerability is found. The second gate is the dependency check using OWASP Dependency-Check — the pipeline fails if any dependency has a known CVE with a CVSS score above 7.0. The third gate is SBOM generation — every build produces a CycloneDX-format SBOM that is stored alongside the artifact and submitted to the company's GRC (Governance, Risk, and Compliance) platform. The fourth gate is manual approval for production — a designated security officer must approve the deployment after reviewing the scan results, the SBOM, and the change request. The fifth gate is post-deployment validation — automated compliance checks run in production to verify that the deployed environment matches the security baseline.

## Scenario-Based Questions

1. **Q: Design a CI/CD system for a monorepo with 100+ microservices.**
   - **A:** A monorepo with 100+ services presents unique CI/CD challenges because building and testing every service on every commit would be prohibitively slow and expensive. The solution combines path triggers, dependency graph analysis, and parallel execution. Path triggers ensure that only the services affected by a given commit are built and tested — a change to `services/auth/src/` triggers only the auth service pipeline. Dependency graph analysis determines which services depend on the changed service and adds them to the build queue. Matrix builds test services across multiple runtime versions (Node 18, Node 20, Node 22) in parallel. A fan-out/fan-in pattern dispatches independent service builds to parallel agents and aggregates results before promotion gates. Each service produces an independently versioned artifact with semantic versioning driven by conventional commits (fix = PATCH, feat = MINOR, breaking change = MAJOR). The key trade-off is between build speed and confidence: building only affected services is fast but risks missing cross-service integration issues, which is why a nightly full rebuild of all services is essential.

2. **Q: How would you implement progressive delivery (canary, feature flags) in CI/CD?**
   - **A:** Progressive delivery combines canary deployments with feature flags to minimize risk while enabling rapid releases. In the CI/CD pipeline, the canary stage deploys the new version to a small percentage of infrastructure — typically 1-5% of instances — while the remaining 95-99% continues running the previous version. Traffic is routed proportionally using a service mesh (Istio, Linkerd) or a cloud load balancer's weighted target groups. The pipeline monitors key metrics — error rate, p99 latency, CPU utilization, business metrics like conversion rate — and compares them against the baseline. If metrics remain healthy for a configurable observation period (5-30 minutes), traffic is gradually increased to 25%, 50%, 75%, and finally 100%. If any metric exceeds the threshold at any point, the pipeline automatically rolls back by routing all traffic back to the previous version.

   Feature flags complement canary deployments by decoupling deployment from release. Code is deployed behind a flag that is initially off, then the flag is enabled for internal testing through the pipeline's post-deploy verification stage. The flag is gradually rolled out to users (1%, 10%, 50%, 100%) through a feature management platform like LaunchDarkly or Flagsmith. If issues arise, the flag is toggled off instantly — no rollback needed. The pipeline integrates feature flag status into the deployment process: a deployment is not considered complete until the relevant feature flags have been enabled for a percentage of users and verified.

3. **Q: Design a zero-downtime deployment strategy for a stateful application.**
   - **A:** Stateful applications — those with databases, file storage, or in-memory caches — require extra care during deployment because the state must be preserved and compatible across versions. The blue-green deployment pattern with backward-compatible database migrations provides the best balance of safety and speed for stateful applications. In the prepare phase, a full parallel environment (green) is provisioned alongside the current production environment (blue). The database migration phase applies forward-compatible schema changes — adding columns, creating new tables, adding indexes — but never removing or renaming existing structures. This ensures both blue and green can operate against the same database. The green application is deployed and health-checked against the database while still receiving no traffic.

   During cutover, the load balancer or DNS is switched from blue to green in a controlled manner. The old blue application remains running with active connections draining naturally — the blue application handles in-flight requests but accepts no new traffic. If green fails health checks during the observation window, traffic is switched back to blue instantly. Once green is confirmed stable, the contract phase removes deprecated schema elements (renaming old columns, dropping unused tables) in a subsequent deployment window. For applications that cannot tolerate even a brief period of dual-version coexistence, a read-only mode during cutover — where the database accepts reads but queues writes — can provide a clean transition, though this introduces brief write unavailability that must be acceptable to the business.

4. **Q: How do you ensure compliance (SOC2, HIPAA) in a CI/CD pipeline?**
   - **A:** Compliance requirements like SOC2 and HIPAA mandate controls over code changes, access, and audit trails that must be reflected in the CI/CD pipeline. Every commit must be signed by the developer, and the pipeline verifies signatures before building. The pipeline itself enforces that all security scans pass before any deployment is allowed — SAST, dependency scanning, container scanning, and secret detection must all report zero critical and high findings. Production deployments require explicit approval from a designated compliance officer or security team member, enforced through the CI/CD tool's environment protection rules and approval gates. Every deployment produces an immutable audit trail: who approved it, what artifact was deployed, what commit triggered it, what the scan results were, and what the post-deployment health check showed. Artifacts are cryptographically signed using Sigstore or GPG, and signatures are verified before deployment. SBOMs in SPDX or CycloneDX format are generated for every build and archived alongside the audit log. For SOC2 specifically, the pipeline must demonstrate separation of duties between developers and deployers, which means the person who wrote the code cannot be the sole approver for production deployment.

5. **Q: Design a pipeline that supports multi-cloud deployment (AWS, Azure, GCP).**
   - **A:** A multi-cloud pipeline must abstract cloud-specific implementation details while maintaining the principle of Build Once Deploy Many. The CI stage is completely cloud-agnostic — it builds the application, runs tests, and produces a Docker image or platform-agnostic package. This artifact is pushed to registries in all three clouds (ECR, ACR, GCR/GAR) with the same tag. Cloud-specific deployment logic is encapsulated in reusable pipeline templates or composite actions — one template for AWS (using CloudFormation or Terraform with AWS provider), one for Azure (ARM or Terraform with Azure provider), one for GCP (Deployment Manager or Terraform with GCP provider). The templates are parameterized for environment (dev, staging, prod), and environment-specific configuration files are stored in a separate repository with appropriate access controls.

   A unified artifact registry service — either a cloud-agnostic registry like Artifactory or Harbor, or a multi-region replication setup — ensures the artifact is available in the region closest to each cloud's compute resources. Pipeline variables control which cloud target is active for a given deployment, with the ability to deploy to multiple clouds in parallel for disaster recovery testing. Compliance scanning runs once in CI (not per cloud), ensuring consistent security posture. The trade-offs are significant: multi-cloud pipelines are more complex to maintain, require expertise in each cloud platform, and the IaC templates must be kept in sync across providers. For most organizations, a single-cloud strategy with a disaster recovery replica is simpler and more reliable than true multi-cloud.

6. **Q: How do you handle database schema changes during deployment?**
   - **A:** Database schema changes are one of the highest-risk operations in a deployment because they are stateful — unlike application code, the database cannot be versioned and recreated. The expand-contract (parallel change) pattern is the industry standard for safe, zero-downtime schema migrations. In the expand phase, additive changes are applied: new columns with NULL defaults, new tables, new indexes. These are safe because existing application code does not reference them and will continue to function unchanged. The application is then deployed with code that reads from both old and new schema structures and writes to both. After the deployment is stable, the contract phase removes deprecated schema elements: old columns, old tables, renamed indexes. This phase runs in a separate pipeline execution, often hours or days later, ensuring adequate time for validation.

   Each migration script must have a corresponding rollback script. Flyway and Liquibase manage this by executing numbered migration files in order and tracking which have been applied. The pipeline always runs migrations before deploying the application, ensuring the schema is ready before the new code attempts to use it. Environment-specific migration strategies include: blue-green deployments where migrations run against both databases before the cutover; staging environments where migrations are tested against production-sized data; and pre-prod environments where the full migration + deploy sequence is validated end-to-end. The golden rule: never remove or rename a database object that the old application version might reference, because the old version must continue working during a rollback.

7. **Q: Design a CI/CD pipeline for ML models (MLOps).**
   - **A:** MLOps pipelines differ from traditional CI/CD in several critical ways: the "build" involves training a model rather than compiling code, the "test" involves evaluating model accuracy rather than running unit tests, and the "deployment" involves serving a model rather than hosting a web application. The pipeline stages are: data validation (validate input data quality and schema using Great Expectations or TensorFlow Data Validation), feature engineering (compute and store features using Tecton or Feast), model training (train using MLflow, Kubeflow, or SageMaker), model evaluation (compare model metrics against the current production model — if the new model is not an improvement, the pipeline stops), model registration (register the model in MLflow Model Registry or SageMaker Model Registry with metadata about training run, data version, and hyperparameters), model deployment to staging (deploy the model endpoint and run shadow traffic comparing against production), A/B testing in production (route a percentage of inference requests to the new model), and monitoring (track model drift, data drift, and prediction accuracy over time, triggering pipeline re-execution when drift thresholds are exceeded).

   Data versioning is essential for reproducibility — use DVC (Data Version Control) or LakeFS to version the training dataset and link it to the model version. Experiment tracking with MLflow records every training run's parameters, metrics, and artifacts, enabling comparison across runs. The pipeline is triggered by new data availability, code changes to the training pipeline, or a scheduled retraining cadence (daily, weekly). The key difference from application CI/CD: model evaluation is probabilistic, not deterministic — the new model must be statistically better than the current one, and the definition of "better" depends on business metrics (accuracy, precision, recall, F1, AUC-ROC) that must be configured per use case.

8. **Q: How do you implement artifact promotion with security gates?**
   - **A:** Artifact promotion is the process of moving a verified artifact from one environment to the next, with each environment requiring the artifact to pass that environment's specific security and quality gates. In a typical four-environment model (dev to staging to QA to production), the artifact starts in the development environment after the CI build passes. Promotion to staging requires: all unit tests pass with minimum 80% coverage, integration tests pass, SAST and dependency scans report no critical vulnerabilities, and the artifact is cryptographically signed. Promotion to QA adds: E2E tests against staging pass, performance benchmark results are within acceptable range (no regressions beyond 5%), and container scan (Trivy, Clair) reports no high-severity vulnerabilities. Promotion to production adds: all previous gates still pass, the artifact has been in QA for a minimum observation period (24 hours by default), a security team member has approved the promotion, and the SBOM has been submitted to the GRC platform.
   - **Interview follow-up:** How would you handle a critical hotfix that needs to bypass the 24-hour observation period in QA?

   Each promotion is a pipeline stage that does not rebuild the artifact but instead updates the artifact's metadata and environment tags in the registry. The staging registry tag `staging-v1.2.3` becomes `qa-v1.2.3` after QA gates pass, then `prod-v1.2.3` after production gates pass. The same Docker image digest — the SHA256 hash of the image — is verified at each promotion step, ensuring the artifact has not been tampered with between environments. If any gate fails, the artifact is not promoted, and the failure is reported to the team with details about which gate failed and why.

9. **Q: Describe the testing pyramid in CI/CD.**
   - **A:** The testing pyramid is a model that describes the ideal distribution of automated tests in a software project. The base of the pyramid is the broadest and contains unit tests — fast, isolated tests that validate individual functions, methods, or classes. Unit tests should constitute 70% or more of the total test suite. They run in milliseconds each and execute on every commit. The middle layer contains integration tests that verify component interactions — API calls between services, database queries, message queue operations. These tests are slower (seconds to minutes) and constitute about 20% of the suite. They run on every push to main and on pull requests. The top layer contains end-to-end (E2E) tests that validate complete user workflows across the entire system stack. E2E tests are slow (minutes to hours), fragile, and constitute about 10% of the suite. They run against the staging environment after deployment, not in the CI gate.
   - **Interview follow-up:** What happens to the pyramid model when a microservice has no UI and no E2E test can be written — does the pyramid collapse or transform?

   The inverse pattern — the "ice cream cone" anti-pattern — occurs when teams have too many E2E tests and too few unit tests. This produces a test suite that is slow, flaky, and expensive to maintain, discouraging developers from running it frequently. In CI/CD, the testing strategy maps directly to pipeline stages: unit tests run first in CI (fast feedback), integration tests run next (medium feedback), and E2E tests run post-deploy to staging (slowest feedback). Test impact analysis — using tools like Nx or Bazel to determine which tests are affected by a code change — can optimize which tests run in each CI cycle, running only the relevant unit and integration tests for a given change rather than the entire suite.

10. **Q: How do you handle versioning in a microservices CI/CD pipeline?**
    - **A:** In a microservices architecture, each service is independently versioned and deployable. Semantic versioning (MAJOR.MINOR.PATCH) is the standard scheme: PATCH for backward-compatible bug fixes, MINOR for backward-compatible feature additions, and MAJOR for breaking changes. The version is derived from the git commit history using conventional commits — a `fix:` commit bumps PATCH, a `feat:` commit bumps MINOR, and a `BREAKING CHANGE:` commit bumps MAJOR. A git tag in the format `service-name-v1.2.3` triggers the release pipeline for that specific service. The artifact (Docker image, JAR, npm package) is tagged with this version and stored in the service's registry namespace — for example, `registry.example.com/auth-service:v1.2.3+b4a7c9f`.
    - **Interview follow-up:** How do you handle the case where Service A v2.0.0 introduces a breaking API change and Service B has not yet upgraded its consumer — do you block the deployment or allow coexistence?

    Service dependencies are managed through API contracts rather than shared versioning. Each service publishes its API contract (OpenAPI/Swagger for REST, protobuf for gRPC, AsyncAPI for event-driven), and consumer-driven contract testing (Pact) validates that service consumers and producers are compatible. The pipeline for each service includes a contract verification stage that runs the consumer tests against the producer's latest API. This approach allows services to version and deploy independently without coordinated releases. The trade-off is that independent versioning can lead to dependency hell if too many services are on different major versions simultaneously, which is why API versioning in the URL path or request header is essential — `/v1/users` and `/v2/users` can coexist in production while consumers migrate gradually.

## Interview Questions

1. **What is the difference between Continuous Integration and Continuous Delivery?**
   - **A:** Continuous Integration (CI) is the practice of automatically building and testing every code change that is committed to the shared repository. Every developer merges to main at least once per day, and each merge triggers an automated build and test suite. The goal of CI is to catch integration issues early — within minutes of the commit — while the change is still small and fresh in the developer's mind. Continuous Delivery (CD) builds on CI by ensuring that every change that passes the CI pipeline is automatically deployed to a staging environment and is in a deployable state for production. The key difference is the production deployment gate: CD requires manual approval for production release. Continuous Deployment goes further by removing that gate entirely — every change that passes all pipeline stages is automatically released to production. The choice between CD and Continuous Deployment depends on regulatory requirements, risk tolerance, and organizational maturity. Highly regulated industries (finance, healthcare) typically use CD with manual approval gates, while SaaS companies with strong automated testing and monitoring often adopt Continuous Deployment.

2. **What is the testing pyramid in CI/CD?**
   - **A:** The testing pyramid models the ideal distribution of test types in a software project. At the base are unit tests — numerous, fast (milliseconds each), isolated, and covering individual functions or methods. They should constitute 70% or more of your test suite. In the middle are integration tests — fewer, slower (seconds to minutes), but higher confidence because they test component interactions with real dependencies. They should be about 20% of the suite. At the top are end-to-end (E2E) tests — fewest, slowest (minutes), and most fragile, but they validate complete user workflows across the entire system. They should be about 10% of the suite. In the CI/CD pipeline, this maps to: CI runs unit and integration tests on every commit, while E2E tests run against the staging environment after deployment. The anti-pattern is the "ice cream cone" — too many E2E tests, too few unit tests — which results in a slow, flaky, expensive test suite. The key insight is that unit tests provide the fastest feedback for the most common failures, while E2E tests provide high-confidence validation for the few scenarios that are too complex to test at lower levels.

3. **What is Build Once Deploy Many?**
   - **A:** Build Once Deploy Many is a CI/CD principle stating that the software artifact should be built exactly once in the CI stage and then promoted through all downstream environments without being rebuilt. The artifact — a Docker image, compiled binary, or packaged application — is built in the CI stage, assigned a unique version identifier (semantic version + commit SHA), and published to an artifact registry. Each subsequent environment (dev, staging, QA, production) promotes the exact same artifact by reference, injecting environment-specific configuration at deploy time through environment variables, configuration files, or Kubernetes ConfigMaps. This eliminates the most common source of deployment failures: the artifact tested in staging is different from the artifact deployed to production. It also enables reliable rollback by deploying the previous artifact version. The principle is enforced by verifying the artifact's checksum or cryptographic signature at each promotion step.

4. **What is artifact immutability and why does it matter?**
   - **A:** An immutable artifact, once created and versioned, is never modified, overwritten, or mutated. Each version is uniquely identified by a combination of semantic version and commit SHA — for example, `1.2.3+b4a7c9f` — and this identifier is embedded in the artifact's metadata. If a fix is needed, a new artifact is built with an incremented version (1.2.4), not a modification of the existing artifact. Immutability enables three critical capabilities. First, audit trail: given a version tag, you can trace back to the exact source code, dependencies, and build environment that produced the running artifact. Second, reproducibility: deploying version 1.2.2 to roll back from 1.2.3 is guaranteed to produce the same result as the previous deployment of 1.2.2. Third, safe promotion: the artifact tested in staging is provably identical to the one deployed in production. Without immutability, the "same build" could produce different results due to dependency version drift, compiler differences, or configuration changes — destroying the trust that makes CI/CD valuable.

5. **What is the difference between a canary and blue-green deployment?**
   - **A:** Blue-green deployment maintains two full, identical environments — blue (current production) and green (new version). The deployment process involves deploying the new version to green, running health checks and smoke tests against green, and then switching the router or load balancer from blue to green in an instant. Rollback is equally instant — switch back to blue. Blue-green provides zero-downtime deployments and instant rollback, but the trade-off is cost: during deployment, you need double the infrastructure (both environments running simultaneously). This cost is acceptable for critical applications but can be prohibitive for large-scale or resource-intensive systems. Canary deployment takes a more gradual approach: the new version is deployed to a small subset of instances (1-5% of the total), a small percentage of traffic is routed to it, and metrics are monitored for a configurable observation period. If metrics remain healthy, traffic is gradually increased (25%, 50%, 75%, 100%). If metrics degrade at any point, traffic is routed back to the old version. Canary is more resource-efficient than blue-green because it does not require a full parallel environment, but rollback is slower (traffic must be gradually shifted, not instantly switched). Choose blue-green for applications requiring instant rollback (e.g., payment processing) and canary for gradual risk reduction (e.g., feature releases).

6. **What is CI/CD pipeline as code?**
   - **A:** Pipeline as Code is the practice of defining the CI/CD pipeline configuration in a version-controlled file stored alongside the application code, rather than configuring the pipeline through a web UI or API in the CI/CD tool. Common examples include Jenkinsfile (Groovy DSL), GitHub Actions workflows (.github/workflows/*.yml), GitLab CI (.gitlab-ci.yml), and Azure DevOps pipelines (azure-pipelines.yml). Storing pipelines in version control brings the same benefits as version control for application code: code review for pipeline changes, branching and merging for pipeline experiments, a complete audit trail of who changed what and when, and the ability to reproduce the exact pipeline configuration for any historical commit. It also enables pipeline templates and shared libraries — common pipeline logic can be packaged, versioned, and reused across multiple repositories. The alternative — manually configuring pipelines through a web UI — is fragile, untraceable, and error-prone because there is no history, no review process, and no way to roll back a broken pipeline configuration.

7. **What are DORA metrics?**
   - **A:** DORA (DevOps Research and Assessment) metrics are four key performance indicators that measure the effectiveness of a software delivery process. Deployment Frequency measures how often an organization successfully releases to production — elite performers deploy multiple times per day, high performers deploy weekly to monthly, medium performers deploy monthly to every six months, and low performers deploy less than every six months. Lead Time for Changes measures the time from code commit to the code running in production — elite performers achieve less than one hour, while low performers take months. Mean Time to Recover (MTTR) measures how long it takes to restore service after an incident — elite performers recover in under one hour. Change Failure Rate measures the percentage of deployments that cause a failure in production — elite performers have a failure rate below 5%, while low performers fail 46-60% of the time. These metrics are correlated: organizations that deploy frequently also tend to have lower failure rates because frequent deployments are smaller, less risky, and the deployment process is well-practiced and automated. The 2023 DORA report found that elite performers deploy 973x more frequently than low performers, with a lead time 657x faster.

8. **How do you handle secrets in a CI/CD pipeline?**
   - **A:** Secrets — database passwords, API keys, cloud credentials, encryption keys — must never be hardcoded in pipeline configuration files or stored in version control. The first line of defense is the CI/CD tool's built-in secret management: GitHub Secrets, GitLab CI Variables, Azure DevOps Variable Groups, or Jenkins Credentials. These store secrets encrypted at rest and inject them as environment variables at runtime. The second line of defense is a dedicated secrets management solution: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, or GCP Secret Manager. These provide additional features like automatic rotation, access auditing, and fine-grained access policies. The third line of defense — and the gold standard for cloud deployments — is OIDC (OpenID Connect). With OIDC, the CI/CD workflow authenticates directly with the cloud provider using a short-lived token that is automatically scoped to a specific role or service principal. No static credentials are stored or exchanged — the cloud provider trusts the CI/CD tool's identity. For Kubernetes deployments, external secrets operators (External Secrets Operator, Sealed Secrets) synchronize secrets from Vault or cloud secret managers into Kubernetes secrets without storing them in Git. The key principle is: secrets should exist only in memory at runtime, never on disk, never in source control, never in pipeline logs.

9. **What is trunk-based development and how does it relate to CI/CD?**
   - **A:** Trunk-Based Development (TBD) is a branching strategy where developers merge their code changes to the main branch (trunk) multiple times per day. Feature branches are short-lived — typically lasting hours, not days — and often implemented as short-lived branches or even direct commits to main for experienced teams. There are no long-lived release branches; releases are created from main at the desired cadence. This branching strategy is tightly coupled with CI/CD because frequent merging to main enables continuous integration — every merge triggers the CI pipeline, which catches integration issues within minutes. Long-lived feature branches (the GitFlow model with weeks-long feature branches) directly contradict CI/CD because they delay integration, allowing merge conflicts and integration issues to accumulate. TBD reduces the complexity of CI/CD pipelines because there is only one significant branch to build and deploy from, eliminating the need for complex merge-back strategies. The trade-off is that TBD requires strong feature flag management — incomplete features must be hidden behind flags rather than isolated on branches. Organizations that adopt TBD typically see improved deployment frequency and reduced lead time for changes.

10. **What is the role of a package/artifact registry in CI/CD?**
    - **A:** A package or artifact registry is the central storage system for immutable, versioned build artifacts produced by the CI pipeline. Common registries include Docker Hub, GitHub Packages, Artifactory, Azure Artifacts, Amazon ECR, Google Artifact Registry, and Sonatype Nexus. The registry stores Docker images, npm packages, NuGet packages, JAR files, Python wheels, and any other distributable artifact format. The registry is the key enabler of the Build Once Deploy Many principle — the CI pipeline publishes to the registry, and each environment pulls the exact same artifact from the registry. Registries also support artifact promotion, where the same artifact is tagged with environment-specific labels (`staging-v1.2.3`, `prod-v1.2.3`) without being rebuilt or modified. Security integration is critical: registries can be configured to require vulnerability scanning before allowing pull operations, and they provide access control so that production artifacts require different permissions than development artifacts. Retention policies in the registry automatically clean up old artifact versions, balancing storage costs against the need to keep recent versions available for rollback.

## Developer Recommendations

- **Build Once, Deploy Many — never rebuild for a different environment** — Rebuilding for each environment guarantees inconsistency. The artifact tested in staging must be byte-for-byte identical to production. Use versioned artifacts in a registry. Each environment promotes the same artifact. Environment config is injected at deploy time, not build time. Without this, you cannot trust your CI/CD. This principle is so fundamental that it should be enforced in the pipeline itself — the build stage should publish the artifact to a registry and immediately verify its checksum. Any subsequent stage that attempts to rebuild the artifact should fail. For Docker-based deployments, this means using the exact image digest (SHA256) rather than a mutable tag like `latest`. The image built in CI is pulled by digest in every subsequent environment, guaranteeing that what ran in staging is exactly what runs in production. If you need environment-specific binaries (e.g., different CPU architectures), produce all variants in the CI stage as separate, independently versioned artifacts, each with its own unique identifier.

- **Fail fast with a proper testing strategy** — Run fast unit tests first (seconds), then integration tests (minutes), then security scans, then deploy. Don't put expensive E2E tests in the CI path — run them post-deploy against staging. Use test impact analysis to run only tests relevant to changed code. Every minute of CI time that can be saved is developer throughput regained. The order matters: unit tests catch the most common failures (logic errors, incorrect calculations, edge cases) and run in milliseconds. If a unit test fails, there is no point in running integration tests or deploying — the code is already known to be broken. Organize tests into three tiers that correspond to pipeline stages: tier 1 (unit tests, run on every commit, must pass in under 5 minutes), tier 2 (integration tests, run on every PR and main push, must pass in under 15 minutes), and tier 3 (E2E, performance, and security tests, run post-deploy to staging, can take 30-60 minutes). This tiered approach ensures developers get fast feedback on common failures while still catching integration and system-level issues before they reach production.

- **Use feature flags to decouple deployment from release** — Feature flags allow deploying code that isn't yet active. Deploy safely behind a toggle, enable for internal testing, gradually roll out to users, instantly disable if issues arise. No rollback needed — just toggle off. Tools: LaunchDarkly, Flagsmith, Unleash. Trade-off: flag management complexity and tech debt from untoggled flags. Feature flags transform the deployment process from a high-risk event into a routine operation. Without feature flags, every deployment carries the risk that a new feature contains a bug that affects all users immediately. With feature flags, the deployment deploys the code behind an off-toggle, and the release is a separate, reversible action — enabling the flag for 1% of users, monitoring metrics, then ramping up. This separation is the foundation of continuous deployment: you can deploy multiple times per day because each deployment is low-risk (the new code is inactive). The pipeline should include feature flag verification steps that confirm the flag is configured correctly before the post-deploy release process begins. The primary risk is flag technical debt — flags that are permanently enabled but never removed. Mitigate this with flag lifecycle management: every flag should have an expiration date or a required cleanup ticket created when it is enabled for 100% of users.

- **Automate everything — including rollback** — Manual rollbacks are slow and error-prone (what if you forget a step?). Implement automatic rollback triggered by health check failures. Every deployment should have a tested rollback script. The rollback should also be a pipeline run (with audit trail). If you need to SSH into production to fix a deployment, your CI/CD is incomplete. An automated rollback strategy has three components. First, health check monitoring: immediately after deployment, the pipeline monitors the production health endpoint, error rate, p99 latency, and any custom business metrics. Second, rollback trigger: if any monitored metric exceeds its threshold for a configurable period (e.g., error rate above 1% for 30 seconds), the pipeline automatically initiates rollback. Third, rollback execution: the rollback deploys the previous artifact version through the same pipeline stages, updating the deployment record with a "rolled back" status and including the reason for rollback. The rollback pipeline should be tested regularly — schedule a quarterly "game day" where the team intentionally deploys a broken artifact and verifies that the automated rollback works correctly. This builds confidence in the system and identifies gaps before a real incident occurs.

- **Monitor pipeline health with DORA metrics** — Track Deployment Frequency, Lead Time, MTTR, and Change Failure Rate. If lead time is increasing, your pipeline has bottlenecks. If failure rate is high, your testing is inadequate. If MTTR is high, your rollback automation is weak. Set improvement targets and review monthly. Elite DevOps teams ship 208x more frequently with 7x lower change failure rate. Start by instrumenting your CI/CD tool to emit these metrics automatically. GitHub Actions, GitLab CI, and Azure DevOps all support deployment tracking that feeds into DORA metric dashboards. Set up a dashboard in your observability platform (Grafana, Datadog, Splunk) that displays these four metrics as time-series charts. Review them in your monthly DevOps retrospective: did lead time increase last month? Why? Did deployment frequency drop? What blocked releases? Use the metrics to drive improvement initiatives, not to blame teams. A team that discovers their lead time is 8 hours and sets a target of 4 hours has a clear, measurable improvement goal. The DORA metrics work because they are system-level outcomes, not individual performance indicators — they measure the effectiveness of your CI/CD system, not the people who use it.

- **Secure the pipeline itself — not just the app it deploys** — The CI/CD pipeline has access to production. If compromised, the attacker owns production. Use: signed commits, OIDC for cloud auth (no static secrets), minimal permissions per job, environment protection rules, dependency review, artifact signing, and hermetic builds. Treat the pipeline as the most critical security boundary. Supply chain attacks like SolarWinds and CodeCov demonstrated that attackers target CI/CD systems precisely because one compromised pipeline can infect thousands of downstream deployments. Implement the SLSA (Supply-chain Levels for Software Artifacts) framework to assess and improve your pipeline security posture. At minimum, achieve SLSA Level 2: build steps are defined in version control, the build runs on a dedicated platform (not a developer's laptop), and artifacts are cryptographically signed. Strive for SLSA Level 3: the build platform enforces that build steps cannot be modified at runtime, dependencies are fetched only from verified sources (hermetic builds), and the pipeline runs with the principle of least privilege — each job gets only the permissions it needs, not the maximum permissions available. Regular pipeline security audits should verify that no stale credentials exist, that all service connections use OIDC or short-lived tokens, that pipeline logs do not leak secrets, and that only authorized users can modify production deployment pipelines.

## Summary

CI/CD is a foundational practice that transforms software delivery from a high-risk manual process into a reliable, automated, and measurable workflow. The core principles — Build Once Deploy Many, Pipeline as Code, immutable artifacts, automated testing at every level, and progressive delivery — work together to shorten feedback loops, reduce deployment risk, and enable organizations to ship software at a cadence that matches their business needs. The DORA metrics provide a quantitative framework for measuring pipeline effectiveness, while security practices like OIDC authentication, artifact signing, and SBOM generation protect the pipeline itself from compromise. A well-designed CI/CD system ultimately enables teams to deploy with confidence, recover quickly from failures, and focus their energy on delivering value rather than managing releases.
