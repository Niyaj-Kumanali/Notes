# AWS

---

## Overview

**Definition:** Amazon Web Services (AWS) is the leading cloud computing platform, offering over 200 services across compute, storage, databases, networking, machine learning, security, and analytics. AWS operates on a pay-as-you-go pricing model, meaning customers only pay for the resources they actually consume, with no upfront commitments or long-term contracts required. The platform serves millions of customers globally, from startups to enterprises to government agencies, with an estimated 33% market share of the cloud infrastructure market as of 2025. AWS's massive scale allows it to offer lower prices than most competitors while maintaining industry-leading breadth and depth of services.

**Why It Exists:** AWS enables on-demand, pay-as-you-go access to scalable infrastructure, eliminating the need for upfront hardware investment and enabling rapid global deployment. Before AWS, launching a new application required purchasing servers, networking equipment, and data center space — a process that could take weeks or months. With AWS, developers can provision virtual servers, databases, and networking in minutes through a web console, CLI, or API. This paradigm shift has democratized access to enterprise-grade infrastructure, allowing startups to compete with established companies without massive capital expenditure. AWS's global infrastructure spans 33+ regions and 105+ availability zones, enabling customers to deploy applications close to their users anywhere in the world.

**Key Concepts:**
- **Regions** — AWS's geographic areas that each contain 3 or more availability zones. Each region is completely independent and isolated from other regions, providing fault tolerance and stability. When designing applications, choosing the right region balances latency, cost, compliance, and service availability. For example, `us-east-1` (Northern Virginia) has the most services available, while `ap-southeast-1` (Singapore) may be better for Asian user bases.
- **Availability Zones (AZs)** — Physically isolated data centers within a region, each with independent power, cooling, and networking. AZs are connected through low-latency, high-bandwidth fiber links, enabling synchronous replication between them. Deploying across multiple AZs is the primary mechanism for achieving high availability in AWS. A typical multi-AZ architecture distributes application instances across 3 AZs so that if one AZ fails, the application continues running on the remaining two.
- **Edge Locations** — CDN endpoints for Amazon CloudFront that cache content close to end users. There are over 600+ edge locations globally, far more than AWS regions. Edge locations provide content caching, Lambda@Edge execution, and DDoS protection through AWS Shield. They are distinct from regions and AZs — they are not suitable for running application logic (except via Lambda@Edge) but excel at static content delivery.
- **Shared Responsibility Model** — AWS secures the cloud (physical security, hardware, networking, hypervisor), while customers secure what's in the cloud (OS updates, application code, IAM configuration, data encryption). This means AWS is responsible for "security of the cloud," but customers are responsible for "security in the cloud." For example, if an S3 bucket is publicly accessible, that is the customer's responsibility — AWS provides the tools (Block Public Access, bucket policies), but the customer must configure them correctly.
- **Well-Architected Framework** — Six pillars: Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, and Sustainability. This framework provides best practices for designing and operating reliable, secure, efficient, and cost-effective systems in the AWS cloud. The Well-Architected Tool in the AWS Management Console allows teams to review their workloads against these pillars, generating actionable recommendations. Regular well-architected reviews (at least quarterly for critical workloads) help identify architectural risks before they cause production incidents.

## Core Services

**EC2 (Compute):** Elastic Compute Cloud provides virtual machines with a vast selection of instance families optimized for different workloads. General-purpose instances like t3 and m6i offer a balanced mix of compute, memory, and networking for standard applications. Compute-optimized instances (c6i, c7g) are designed for CPU-intensive workloads such as batch processing, scientific modeling, and gaming servers, delivering up to 30% better price-performance than previous generations. Memory-optimized instances (r6i, x2idn) support in-memory databases like Redis and SAP HANA with up to 24 TB of RAM. Storage-optimized instances (i3, i4i) provide high, low-latency SSD storage for databases and data warehousing, with up to 30 TB of NVMe SSD storage attached directly to the host. GPU instances (p4d, g5) deliver the computational power needed for machine learning training, video rendering, and graphics-intensive applications, with p4d instances featuring 8 NVIDIA A100 GPUs and 400 Gbps networking. EC2 offers flexible pricing models: On-Demand (pay by the hour/second with no commitment), Reserved Instances (up to 72% discount for 1-3 year terms), Spot Instances (up to 90% discount for fault-tolerant, stateless workloads), and Savings Plans (flexible discount across compute families). EC2 Auto Scaling automatically adjusts the number of instances based on demand, ensuring applications have the right capacity at all times while minimizing costs. Key design decisions include choosing the right instance family for the workload, selecting appropriate storage (EBS vs. Instance Store), and configuring security groups and VPC placement for network isolation.

**Lambda (Serverless):** AWS Lambda allows you to run code without provisioning or managing servers. You upload your code (or write it in the Lambda console), configure triggers (API Gateway, S3 events, SQS messages, DynamoDB streams, scheduled events via EventBridge), and Lambda handles all scaling, patching, and capacity management automatically. Lambda supports multiple languages including Node.js, Python, Java, Go, .NET, and Ruby, each with its own runtime managed by AWS. The service scales automatically — from zero to thousands of concurrent executions based on incoming traffic — by launching new execution environments as needed. Lambda is billed per invocation ($0.20 per 1M requests) and per duration (rounded to the nearest millisecond, $0.0000166667 per GB-second). Key limitations include a maximum 15-minute execution timeout, a maximum of 10 GB of memory (allocated in 1 MB increments), a maximum deployment package size of 250 MB (uncompressed, including layers), and a maximum of 1,000 concurrent executions (soft limit, adjustable via support request). Lambda functions run in a sandboxed execution environment that includes an /tmp directory with 512 MB to 10,240 MB of storage (proportional to memory allocation). Cold starts occur when Lambda launches a new execution environment — this adds 200ms-1s of latency (significantly less for Java and .NET with SnapStart, which uses VM snapshots to restore execution environments in under 200ms). Lambda is ideal for event-driven architectures, data processing pipelines, web API backends (via API Gateway or Lambda Function URLs), and as glue code connecting AWS services. For long-running workloads or those requiring consistent performance under high load, consider using containers on ECS or EKS instead.

**ECS / EKS (Containers):** Amazon ECS is AWS's native container orchestration service that eliminates the complexity of managing a control plane. ECS uses task definitions (JSON documents describing containers) and services (scheduling and maintaining desired task counts). It integrates deeply with other AWS services — IAM roles per task, VPC networking per task (awsvpc mode), CloudWatch logs, Service Auto Scaling, and ALB integration. ECS supports two launch types: EC2 (you manage the cluster of EC2 instances) and Fargate (serverless — you define tasks, AWS manages the infrastructure). Fargate eliminates the need to provision, configure, or scale clusters of virtual machines for running containers. You simply define your container requirements (CPU, memory, networking), and Fargate launches the containers with appropriate isolation. Amazon EKS is managed Kubernetes that handles the Kubernetes control plane (etcd, API server, scheduler) while you manage worker nodes or use Fargate for serverless Kubernetes pods. EKS runs upstream Kubernetes certified by CNCF, meaning standard kubectl commands, Helm charts, and Kubernetes tooling work without modification. EKS supports a broad ecosystem of Kubernetes add-ons (Istio, Prometheus, Fluentd, ArgoCD) and integrates with AWS services through IAM roles for service accounts (IRSA) and pod identity. Key differences between ECS and EKS: ECS is simpler, more AWS-integrated, and easier to operate; EKS is more portable, has a larger ecosystem, and supports complex networking and service mesh configurations. Most teams choose ECS for AWS-only deployments and EKS for multi-cloud or Kubernetes-native workflows.

**S3 (Storage):** Amazon Simple Storage Service provides highly durable object storage with 99.999999999% (11 nines) durability across multiple AZs within a region. S3 stores data as objects within buckets, where each object consists of data, a key (unique identifier), and metadata (system-defined and user-defined). Objects can range from 0 bytes to 5 TB in size. S3 offers multiple storage classes that balance cost and access frequency: STANDARD (frequent access, highest durability, millisecond retrieval), INTELLIGENT_TIERING (automatically moves objects between access tiers based on usage patterns, adding a small monitoring fee), STANDARD_IA (infrequent access but rapid retrieval when needed, with a per-GB retrieval fee), ONEZONE_IA (lower cost by storing in only one AZ, suitable for recreatable data), GLACIER (archive retrieval in minutes to hours, with retrieval times of 1-5 minutes for expedited, 3-5 hours for standard), GLACIER_DEEP_ARCHIVE (lowest cost archive with retrieval times of 12 hours, ideal for compliance and regulatory data). S3 features include versioning (protects against accidental deletion), object lock (write-once-read-many for compliance), replication (cross-region and same-region), server-side encryption (SSE-S3, SSE-KMS, SSE-C), event notifications (to Lambda, SQS, SNS), and static website hosting. Access control is managed through bucket policies (resource-based), IAM policies (identity-based), ACLs (legacy), and Access Points (per-application access with restricted network boundaries). S3 also supports multipart uploads for large objects (upload parts in parallel for faster uploads) and range GETs for partial object retrieval (useful for streaming and parallel downloads). Common use cases include backup and restore, data lakes (with AWS Glue and Athena), static website hosting, content distribution (with CloudFront), and application data storage.

**RDS / DynamoDB (Databases):** Amazon RDS provides managed relational databases including PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, and Amazon Aurora. RDS automates time-consuming database administration tasks like hardware provisioning, database setup, patching, and backups. Automated backups enable point-in-time recovery to any second within the retention period (35 days max). RDS Multi-AZ deployments create a standby replica in a different AZ with synchronous replication for high availability — failover occurs automatically within 60-120 seconds. Read replicas (up to 15 per database) reduce read load on the primary and support cross-region replication for disaster recovery. Amazon Aurora is a MySQL- and PostgreSQL-compatible relational database built for the cloud, offering 5x the throughput of standard MySQL and 3x the throughput of standard PostgreSQL. Aurora uses a distributed storage system that replicates data across 3 AZs with 6 copies (2 copies per AZ), providing higher durability and availability than standard RDS. Aurora features include Auto Scaling (storage grows automatically up to 128 TB), Aurora Serverless (automatic scaling based on demand), Global Database (cross-region replication with <1 second lag), and backtrack (rewind the database to a specific point in time without restoring from backup). Amazon DynamoDB is a fully managed NoSQL key-value and document database delivering single-digit-millisecond latency at any scale. DynamoDB uses a serverless architecture — no servers to provision, patch, or manage — and scales automatically by partitioning data and requests across multiple servers. Data is stored on SSD storage across 3 AZs in an AWS region for high durability. Key DynamoDB concepts include tables (collection of items), items (collection of attributes), primary keys (partition key or partition + sort key), secondary indexes (LSI and GSI for alternative access patterns), DynamoDB Streams (time-ordered sequence of item changes), and Time to Live (TTL) for automatic item expiration. DynamoDB supports two read/write capacity modes: provisioned (specify RCU/WCU with auto-scaling) and on-demand (pay-per-request, suitable for unpredictable workloads). DynamoDB Accelerator (DAX) is an in-memory cache that reduces read latency from milliseconds to microseconds. Common use cases include JSON document stores, session management, metadata caches, gaming leaderboards, IoT data, and event sourcing.

**VPC (Networking):** Amazon Virtual Private Cloud enables you to provision a logically isolated section of the AWS cloud where you can launch AWS resources in a virtual network that you define. You have complete control over your virtual networking environment, including IP address range selection (CIDR blocks), subnet creation (public for internet-facing resources, private for internal resources), route table configuration, and network gateway management. A VPC spans all AZs in a region but individual subnets exist within a single AZ. Key VPC components include Internet Gateways (IGW — allows public internet access for resources with public IPs), NAT Gateways (allows private subnet resources to initiate outbound traffic to the internet while preventing inbound connections), route tables (control traffic direction between subnets and gateways), Network ACLs (stateless firewalls at the subnet level supporting allow and deny rules), and Security Groups (stateful firewalls at the instance/ENI level supporting allow rules only). VPC Peering connects two VPCs using AWS's internal network (no internet transit, no transitive peering). For connecting multiple VPCs in a hub-spoke topology, AWS Transit Gateway provides a single gateway that connects thousands of VPCs and on-premises networks through a central hub. VPN Gateway enables encrypted connections between VPC and on-premises networks over the internet. AWS Direct Connect provides dedicated private network connections from on-premises to AWS, bypassing the internet entirely for consistent network performance. VPC Endpoints (Gateway and Interface types) allow private connectivity to AWS services (S3, DynamoDB, etc.) without traversing the public internet. VPC Flow Logs capture IP traffic information for security analysis and troubleshooting. Common VPC design patterns include the 3-tier architecture (web, application, database subnets in separate tiers), multi-VPC with Transit Gateway for large organizations, and VPC sharing for centralized network management.

**IAM (Identity and Access Management):** AWS Identity and Access Management enables you to manage access to AWS services and resources securely. IAM provides the infrastructure to control authentication (who can sign in) and authorization (what actions they can perform). Core IAM entities include users (individual people or applications with permanent credentials), groups (collections of users with shared permissions), roles (identities with temporary credentials assumed by trusted entities — users, applications, or AWS services), and policies (JSON documents defining permissions). IAM best practices include following the principle of least privilege (grant only the permissions needed to perform a task), using IAM roles for applications (instead of long-term access keys), enabling MFA for all users, using condition keys to restrict access based on specific attributes (IP address, time of day, MFA status, etc.), and rotating credentials regularly. IAM Access Analyzer helps identify resources shared with external entities. IAM Identity Center (formerly AWS SSO) provides centralized management of workforce access across multiple AWS accounts and business applications. The difference between identity-based policies (attached to IAM users, groups, or roles) and resource-based policies (attached to resources like S3 buckets) is critical — resource-based policies control who can access the resource, while identity-based policies control what the identity can do. IAM Roles for EC2 (instance profiles) provide temporary credentials to EC2 instances via the instance metadata service, eliminating the need to store AWS credentials on instances. For CI/CD, OIDC federation allows GitHub Actions or GitLab CI to assume IAM roles without storing long-lived AWS keys.

```yaml
# VPC Architecture Design
VPC:
  CIDR: 10.0.0.0/16        # Main VPC with 65,536 IP addresses
  Subnets:
    Public:                  # Internet-facing subnets (load balancers, bastion hosts)
      - 10.0.1.0/24         # AZ-a: 256 IPs
      - 10.0.2.0/24         # AZ-b: 256 IPs
    Private:                 # Application and database subnets (no direct internet access)
      - 10.0.3.0/24         # AZ-a application
      - 10.0.4.0/24         # AZ-b application
      - 10.0.5.0/24         # AZ-a database
      - 10.0.6.0/24         # AZ-b database
  Gateways:
    - Internet Gateway       # Attached to public subnets for inbound/outbound internet traffic
    - NAT Gateway            # Deployed in public subnet, enables private subnet egress
    - Transit Gateway        # Optional: connects multiple VPCs and on-prem networks
```

## Common Mistakes

**Default VPC** — Using the default VPC in any region is a security risk because it has an open internet gateway, unrestricted security groups (all traffic allowed by default), and no subnet segmentation. Always create custom VPCs with proper CIDR planning, subnet isolation (public/private), and least-privilege security groups. The default VPC is a convenience feature for getting started quickly, not a production-grade network design.

**Open security groups (0.0.0.0/0)** — Allowing traffic from any IP (0.0.0.0/0) on management ports like SSH (22) and RDP (3389) makes your instances vulnerable to brute-force attacks and port scanning. Restrict security group rules to specific IP ranges or use AWS Systems Manager Session Manager for shell access, which doesn't require open inbound ports. For HTTP/S traffic, use CloudFront or ALB in front of instances to absorb DDoS attacks.

**No IAM roles for EC2** — Hardcoding AWS access keys on EC2 instances creates credential management headaches: keys must be rotated, securely stored, and can leak through log files or source code. IAM roles with instance profiles automatically provide temporary credentials through the EC2 metadata service (169.254.169.254), eliminating the need to manage keys entirely. The credentials are automatically rotated every 6 hours by AWS.

**No CloudTrail** — CloudTrail records API activity across your AWS account, providing the audit trail needed for security analysis, resource change tracking, and compliance reporting. Without CloudTrail, you cannot determine who deleted an S3 bucket, terminated an EC2 instance, or modified a security group. Enable CloudTrail in all regions with log file validation and send logs to a centralized S3 bucket in a security audit account.

**Single-AZ deployment** — Deploying critical workloads in a single Availability Zone means a power outage, network failure, or hardware issue in that AZ takes your entire application offline. Always deploy across multiple AZs — this is the single most impactful architectural decision for availability. An ALB distributing traffic across instances in 3 AZs can tolerate the loss of one entire AZ without impact.

**No Auto Scaling** — Manually managing instance counts based on demand leads to either over-provisioning (wasting money) or under-provisioning (poor performance, downtime). Auto Scaling Groups (ASGs) automatically maintain a desired instance count and adjust based on CloudWatch metrics (CPU, memory, request count) or scheduled scaling for predictable traffic patterns. Combine ASGs with ALBs for seamless traffic distribution during scaling events.

**Public S3 buckets** — Publicly accessible S3 buckets have been the source of countless data breaches exposing millions of customer records. Always block public access at the account level via S3 Block Public Access settings, and use pre-signed URLs for temporary access to specific objects. If a bucket must be public (e.g., static website hosting), use a bucket policy that explicitly limits access and enable CloudTrail logging for all object access.

**Root account daily use** — The root user has unrestricted access to the entire AWS account, including the ability to close the account. Never use root credentials for everyday tasks. Create IAM users with administrative privileges and enable MFA on the root account. Store root account credentials securely (preferably in a password manager accessible only by account administrators) and only use them for tasks that require root privileges (changing support plan, closing account).

**No cost budgets** — Without proactive cost monitoring, AWS bills can balloon unexpectedly from forgotten resources, unused storage, or elevated data transfer costs. Set up AWS Budgets with alerts at 50%, 80%, and 100% of budget thresholds. Use Cost Explorer to analyze spending patterns and identify cost-saving opportunities. Tag all resources with cost center and environment tags to enable granular cost allocation reports.

**Over-provisioned resources** — Most production workloads use less than 50% of their provisioned resources, leading to significant wasted spending. Right-size instances by monitoring CloudWatch metrics (CPU, memory, network I/O) and using AWS Compute Optimizer for instance type recommendations. Consider switching to Auto Scaling with smaller instances that scale out rather than up, providing both cost savings and better availability.

## Key Design Considerations

**VPC Architecture** — Design with multiple AZs (at least 2, ideally 3 for critical workloads), public/private subnet isolation (public for load balancers and bastion hosts; private for application and database tiers), NAT gateways in each AZ for private subnet egress (each NAT Gateway is an AZ failure domain), and Transit Gateway for connecting multiple VPCs in a hub-and-spoke topology. For large organizations, use a centralized VPC for shared services (Directory Services, monitoring, CI/CD agents) with VPC Peering or Transit Gateway attachments to workload VPCs. Reserve at least 50% of the VPC CIDR for future growth.

**High Availability** — Use Application Load Balancers across AZs (at least 2 subnets in different AZs) with health checks on the application endpoint. Configure Auto Scaling Groups with a minimum of 2 instances across AZs and spread across instance types to avoid single-instance-type failure. Use RDS Multi-AZ for automatic failover of relational databases (synchronous standby replica in another AZ) and read replicas in different regions for disaster recovery. Use ElastiCache with cluster mode and replica nodes in different AZs for cache high availability. For DNS-level failover, configure Route 53 with health checks and failover routing.

**Disaster Recovery** — Four DR strategies with increasing complexity and cost: Backup & Restore (cheapest, highest RTO — hours/days, snapshot data to S3 and restore in another region), Pilot Light (core services running in minimal footprint in DR region, scale up when failover triggers), Warm Standby (scaled-down but fully functional environment in DR region, scales up on failover), and Multi-Site Active-Active (both regions handle traffic simultaneously, lowest RTO/RPO — seconds/minutes, most expensive). Define RPO (Recovery Point Objective — how much data loss is acceptable) and RTO (Recovery Time Objective — how long to recover) with business stakeholders, then choose the appropriate DR strategy.

**Security** — Implement defense in depth: IAM least privilege (grant only necessary actions, use condition keys for additional restrictions), encryption in transit (TLS 1.2+ enforced via ALB listener policies, ELB security policies), encryption at rest (KMS with automatic key rotation, S3 SSE, EBS encryption), network security (security groups, NACLs, WAF for application-layer protection), monitoring (CloudTrail for API audit trail, AWS Config for resource configuration compliance, GuardDuty for threat detection), and secrets management (Secrets Manager for database credentials, Parameter Store for configuration data).

**Cost Optimization** — Use Spot instances for fault-tolerant, stateless workloads (batch processing, CI/CD agents, data analytics) for 60-90% savings compared to On-Demand. Purchase Reserved Instances or Savings Plans for baseline compute (30-72% discount depending on term and payment option). Implement S3 lifecycle policies to automatically transition objects to cheaper storage classes (STANDARD → STANDARD_IA after 30 days → GLACIER after 90 days → DEEP_ARCHIVE after 365 days). Right-size instances based on CloudWatch metrics and AWS Compute Optimizer recommendations. Tag everything with cost allocation tags (CostCenter, Environment, Project) and use AWS Budgets with alerts.

**Infrastructure as Code** — Use AWS CloudFormation or Terraform to define all infrastructure as version-controlled, reviewable code. Tag all resources with consistent tags (Environment, Owner, CostCenter, Application) for cost allocation, automation, and operational management. Use CI/CD to validate and deploy IaC changes — cfn-lint or terraform plan in CI, approval gates for production deployments. Use AWS AppConfig for application configuration separate from infrastructure. Never manually provision resources through the console for production workloads — manual changes create configuration drift that leads to unreproducible environments.

## Real-World Scenarios

**Scenario 1: Multi-Region Active-Active E-Commerce Platform with Global Database Replication**

**Context:** A global e-commerce company needs sub-second response times worldwide with 99.99% availability. Their current single-region deployment in us-east-1 serves customers globally, resulting in 2-3 second page load times for users in Asia and Europe. The company is losing customers to competitors with faster sites. They need a multi-region architecture that provides local response times, handles regional outages gracefully, and keeps operational costs within 20% of the current budget.

**Problem:** Designing a multi-region active-active e-commerce architecture requires solving several challenges: database writes must be accepted locally but replicated globally, session state must be available across regions, shopping cart data cannot be lost during failover, and the deployment must handle partial failures gracefully (one AZ in one region failing should not impact availability). Additionally, the architecture must support local pricing, tax calculations, and payment methods specific to each region.

**Resolution:** Use Route 53 latency-based routing with health checks to direct users to the nearest operational region. In each region, deploy an ALB and Auto Scaling Group across 3 AZs for the application tier, ensuring each region independently handles its own requests. Use Amazon RDS Aurora Global Database for the relational layer — the primary region handles writes and the database automatically replicates to up to 5 secondary regions with less than 1 second of latency. For session state and shopping cart data, use DynamoDB Global Tables with multi-master replication, providing single-digit-millisecond access anywhere in the world. Store and serve product images via S3 with Cross-Region Replication, fronted by CloudFront with multiple origin configurations for static and dynamic content. Implement Route 53 failover routing with active health checks — if a region becomes unhealthy, traffic is automatically redirected to the nearest healthy region within 30 seconds.

```yaml
# Route 53 DNS failover with primary/secondary regions and health checks
MyDNSRecord:
  Type: AWS::Route53::RecordSetGroup
  Properties:
    HostedZoneId: !Ref HostedZone
    RecordSets:
      - Name: api.example.com
        Type: A
        SetIdentifier: primary
        Region: us-east-1
        AliasTarget:
          DNSName: !GetAtt PrimaryALB.DNSName
          HostedZoneId: !GetAtt PrimaryALB.CanonicalHostedZoneID
        Failover: PRIMARY
        HealthCheckId: !Ref PrimaryHealthCheck    # Route 53 pings the /health endpoint every 10 seconds
      - Name: api.example.com
        Type: A
        SetIdentifier: secondary
        Region: eu-west-1
        AliasTarget:
          DNSName: !GetAtt SecondaryALB.DNSName
          HostedZoneId: !GetAtt SecondaryALB.CanonicalHostedZoneID
        Failover: SECONDARY
        HealthCheckId: !Ref SecondaryHealthCheck
```

**Scenario 2: Cost-Optimized CI/CD Infrastructure at Scale with Fargate and Spot**

**Context:** A startup runs 50+ microservices with development, staging, and production environments. Their EC2 costs have ballooned to $40,000 per month, with many instances running 24/7 despite only being utilized during business hours (dev environment) or intermittently (CI/CD build agents). The CTO has mandated a 50% cost reduction without sacrificing developer productivity or deployment frequency.

**Problem:** The current infrastructure uses permanent EC2 instances for both CI/CD build agents and application hosting. Build agents are idle ~60% of the time but incur full costs. Development environments run full-size instances around the clock even though developers only work 8-10 hours per day. The staging environment has the same capacity as production but receives only 5% of the traffic.

**Resolution:** Migrate all stateless microservices from EC2 to ECS Fargate, eliminating the need to manage EC2 instances entirely. Fargate automatically scales from zero — development services can scale to zero during non-business hours using scheduled auto-scaling policies. Use Fargate Spot for non-critical workloads, achieving 60-70% cost savings over regular Fargate pricing. For CI/CD build agents, use EC2 Spot instances in a dedicated Auto Scaling Group that scales based on build queue depth — instances launch only when builds are queued and terminate when idle. Right-size all remaining On-Demand instances based on CloudWatch metrics, and purchase Compute Savings Plans for the baseline compute (30-40% discount). Implement S3 lifecycle policies to move CI/CD logs and build artifacts to STANDARD_IA after 30 days and GLACIER after 90 days.

```bash
# Spot instance interruption handling script for CI/CD agents
SPOT_META="http://169.254.169.254/latest/meta-data/spot/termination-time"

# Check if this instance has received a spot termination notice (2-minute warning)
curl -s $SPOT_META
if [ $? -eq 0 ]; then
  echo "Spot termination notice received. Draining jobs..."
  # Stop the build agent gracefully, letting in-progress jobs finish
  systemctl stop my-service
  # Signal the Auto Scaling Group to launch a replacement instance before this one terminates
  aws autoscaling complete-lifecycle-action \
    --lifecycle-hook-name spot-termination \
    --auto-scaling-group-name my-asg \
    --lifecycle-action-result CONTINUE \
    --instance-id $(curl -s http://169.254.169.254/latest/meta-data/instance-id)
  echo "Instance drained, ready for termination"
fi
```

**Scenario 3: HIPAA-Compliant Secure Data Lake for Healthcare Analytics**

**Context:** A healthcare company needs to ingest 5 TB of IoT device data per day from medical monitors and build a HIPAA-compliant data lake for analytics. The data includes protected health information (PHI) and must be encrypted at rest and in transit, access must be auditable, and permissions must be fine-grained to the column level for different research teams. The company must pass a HIPAA audit within 6 months.

**Problem:** Building a data lake that meets HIPAA compliance requirements involves multiple overlapping challenges: all PHI data must be encrypted with keys that are automatically rotated, access must be restricted to authorized researchers and clinicians based on their role, data in transit between on-premises medical devices and AWS must never traverse the public internet, access logs must be retained for 7 years, and the system must support queries from both data scientists (Athena/QuickSight) and operational dashboards (Real-time analytics).

**Resolution:** Use S3 with SSE-KMS (AWS Key Management Service) for server-side encryption with automatic key rotation enabled. Block all public access at the account level and configure bucket policies that restrict access to specific VPC endpoints using aws:SourceVpce conditions. Use AWS Glue for ETL with IAM roles scoped to specific databases and tables, and AWS Lake Formation for fine-grained column-level and row-level security — researchers can only see de-identified data unless they have explicit approval for PHI columns. Set up VPC Endpoints for S3 and Glue so data never traverses the public internet. Enable CloudTrail with log file validation and AWS Config with HIPAA-security rules for continuous compliance auditing. Use Athena for ad-hoc SQL queries and QuickSight for dashboards, both scoped through Lake Formation permissions.

## Scenario-Based Questions

1. **Q: You are building a multi-region e-commerce platform with RPO < 1 second and RTO < 5 minutes. How do you design the database layer?**

   **A:** For this stringent RPO/RTO requirement, use Amazon RDS Aurora Global Database for the relational data layer. Aurora Global Database supports a single primary region for writes with up to 5 secondary regions that receive replication with less than 1 second of latency. Failover to a secondary region completes in under 1 minute because the secondary already has all the data — it just needs to promote itself to primary. For session and cart data (which is typically higher velocity and lower durability requirements), use DynamoDB Global Tables with multi-master replication, giving you single-digit-millisecond writes in any region. The trade-off with DynamoDB Global Tables is potential conflicts from concurrent writes to the same key in different regions — applications must implement conflict resolution strategies (last-writer-wins, application-level merging, or custom resolution). Implement application-level retry with exponential backoff to handle the brief unavailability during failover. Test the failover process quarterly with GameDays that simulate region failures, measuring actual RTO/RPO against targets.

2. **Q: Your production EC2 instance running a critical batch job crashed at 3 AM. How do you design for automatic recovery?**

   **A:** Configure the EC2 instance as part of an Auto Scaling Group with min=1, max=1 to ensure the instance is automatically replaced if it fails. Use an Application Load Balancer with a health check that probes the application endpoint (e.g., `/health` returning 200) at regular intervals. After 3 consecutive health check failures, the ASG terminates the unhealthy instance and launches a new one. To prevent data loss, the batch job should store its progress state in Amazon SQS or DynamoDB before processing each work unit — the new instance reads the queue/database to determine where to resume. Use termination lifecycle hooks to let the dying instance drain in-flight work before termination. Set up CloudWatch alarms that trigger SNS notifications so the on-call engineer is alerted, but in most cases the ASG recovers the instance before the engineer even wakes up.

3. **Q: Your team accidentally exposed an S3 bucket with customer PII data. How do you prevent this going forward?**

   **A:** Implement a multi-layered defense that makes accidental public exposure nearly impossible. Layer 1: Enable S3 Block Public Access at the AWS account level — this is a setting that overrides any bucket-level public access settings, effectively making it impossible to make any bucket public. Layer 2: Configure bucket policies with explicit Deny statements for any public access, using NotPrincipal or NotAction to allow only specific roles. Layer 3: Use AWS Config managed rules (`s3-bucket-public-read-prohibited` and `s3-bucket-public-write-prohibited`) with auto-remediation via Systems Manager Automation Documents to automatically remove public access if it's ever enabled. Layer 4: Add IAM policy conditions requiring approve-before-create workflows for `s3:PutBucketPolicy` actions. Layer 5: Enable GuardDuty with S3 threat detection to monitor for suspicious access patterns. Layer 6: Create CloudWatch Events/EventBridge rules that trigger alerts whenever `PutBucketPolicy` or `PutBucketAcl` events occur, sending notifications to the security team.

4. **Q: You are designing a serverless data pipeline processing 10 million events/hour with variable traffic spikes. How do you handle throttling?**

   **A:** Use Amazon Kinesis Data Streams as the ingestion layer, which can handle 1 MB/second or 1,000 records/second per shard. For 10M events/hour, estimate approximately 2,778 events/second — you'll need at least 3 shards (with headroom) or use Kinesis Data Firehose for near-real-time delivery to S3 without managing shards. Configure Lambda consumers with reserved concurrency to prevent downstream throttling — without reserved concurrency, Lambda can scale up and throttle other functions sharing the same account. Set up an SQS dead-letter queue for events that fail processing after all retry attempts are exhausted. Lambda's burst concurrency limit (500-3000 per region) and account concurrency limit (1000 default per region) are soft limits that can be increased via support ticket. If Lambda throttles during extreme spikes, events remain in Kinesis for up to 7 days (default retention period), so no data is lost. Pre-provision Lambda concurrency for the baseline event rate to avoid cold starts at the beginning of a traffic spike.

5. **Q: You need to migrate a 5 TB on-premise SQL Server database to RDS with less than 30 minutes of downtime. What migration strategy do you use?**

   **A:** Use AWS Database Migration Service (DMS) with ongoing change data capture (CDC) for a near-zero-downtime migration. Phase 1: Perform a full load migration where DMS copies the entire 5 TB database from on-premise to RDS — this runs during business hours and takes several hours but doesn't impact the source database. Phase 2: After the full load, DMS continuously replicates ongoing changes using log-based CDC (reading SQL Server transaction logs), keeping the target database synchronized with sub-second latency. Phase 3: During the scheduled maintenance window, stop writes to the source application, let CDC catch up (typically 1-5 minutes), verify data integrity with row counts and checksums on a sample of tables, then redirect the application's connection string to the new RDS endpoint using a DNS CNAME swap for instant traffic redirect. The rollback plan is critical: keep the source database writable and do not terminate the DMS replication task until you've confirmed the new system is stable — you can reverse the CNAME swap instantly if issues arise.

6. **Q: Your VPC architecture is running out of IP addresses. How do you design for CIDR exhaustion without disrupting existing workloads?**

   **A:** Add secondary CIDR blocks to the existing VPC — each VPC supports up to 5 CIDR blocks total. Create new subnets in the secondary CIDR and migrate workloads gradually by launching new resources in the expanded subnets and decommissioning old ones. If the primary VPC CIDR is completely exhausted (cannot add more CIDRs), use Transit Gateway to connect separate VPCs — create a new VPC with additional IP space and connect both VPCs through the Transit Gateway so resources in the old VPC can communicate with resources in the new VPC. For future-proofing, follow the VPC design best practices: use /16 CIDRs as the default, reserve a /20 per AZ for each workload (don't allocate all subnets up front), and leave 50% of the VPC CIDR unallocated for future growth. The best long-term solution is to adopt IPv6 — every EC2 instance gets a globally unique IPv6 address, eliminating the need for NAT gateways (which are also constrained by available Elastic IPs). Implement a dual-stack architecture (IPv4 + IPv6) so existing IPv4-dependent services continue working while new services use IPv6.

7. **Q: Your CI/CD pipeline builds are slow because Docker layers aren't cached between runs. How do you solve this for ECS/Fargate deployments?**

   **A:** Docker layer caching is essential for fast builds. For AWS CodeBuild, use the `--cache-from` flag with the previously built image stored in ECR — CodeBuild pulls the cached image and Docker uses its layers during the build. Structure your Dockerfile to maximize layer caching by ordering instructions from least to most frequently changing: start with OS packages and system dependencies (rarely change), then application dependencies (package.json/go.mod), and finally the application code (changes most frequently). This way, the OS layer and dependency layers are cached from previous builds and only the code layer needs rebuilding. Use BuildKit (the modern Docker build engine) with inline cache for more efficient caching. For GitHub Actions, use the `docker/build-push-action` with `cache-from: type=gha` and `cache-to: type=gha,mode=max` which stores cache in the GitHub Actions cache — this shares cache across workflow runs without requiring a separate registry.

8. **Q: Your organization has 50 AWS accounts with no cost visibility. How do you implement cost governance?**

   **A:** Use AWS Organizations with consolidated billing to get a single bill for all accounts, making it possible to see aggregate costs and share volume discounts. Implement Service Control Policies (SCPs) to restrict expensive services (e.g., prevent creation of GPU instances, RDS db.r5.24xlarge, or untagged resources) at the organization or OU level. Enforce a mandatory tagging strategy (CostCenter, Environment, Owner, Application) using AWS Config rules and SCPs that deny resource creation without required tags — without tags, you cannot allocate costs to specific teams or projects. Set AWS Budgets at the account and OU level with notifications at 50%, 80%, and 100% of budget thresholds, sending alerts to the finance team and the relevant application team's Slack channel. Use Cost Explorer for historical analysis and forecasting. Implement chargeback: generate monthly cost reports per CostCenter using AWS Cost and Usage Reports published to S3, then visualize in QuickSight so each team sees their infrastructure costs.

9. **Q: You are building a PCI-DSS compliant workload on AWS. What specific controls do you implement?**

   **A:** PCI-DSS compliance requires a comprehensive set of controls: (1) Use a VPC with no public subnets for cardholder data — all payment processing happens in private subnets with AWS PrivateLink for access to AWS services. (2) Enable CloudTrail in all regions with log file validation enabled and SSE-KMS encryption, storing logs in a separate audit account with 7-year retention. (3) IAM with explicit Deny for any action on cardholder data outside approved roles and service accounts. (4) KMS with automatic key rotation for all encryption keys, using Customer Managed Keys (CMK) for cardholder data encryption. (5) Enforce TLS 1.2+ through ALB listener security policies. (6) AWS Config rules for all PCI-DSS required controls with auto-remediation for violations. (7) GuardDuty and Security Hub for continuous monitoring and threat detection. (8) Systems Manager Patch Manager with maintenance windows for automated OS patching. (9) SCPs at the organization level that prevent disabling of CloudTrail, Config, or GuardDuty — this provides a defense against an attacker trying to cover their tracks. (10) Amazon Inspector for quarterly vulnerability scans of all EC2 instances and container images.

10. **Q: Your Lambda function times out at 15 minutes for a long-running data processing job. How do you redesign?**

    **A:** Lambda's 15-minute timeout is a hard limit, so you must decompose the job into smaller units of work. The most scalable approach is to break the job into chunks that each complete within the Lambda timeout — use SQS to queue the work items and have each Lambda invocation process one item. For jobs with many independent units of work, use AWS Step Functions with a distributed map state, which can orchestrate up to 10,000 parallel Lambda executions, each processing a batch of records. For jobs that genuinely need more than 15 minutes of continuous compute (e.g., video transcoding, large file processing), use ECS Fargate tasks launched via Step Functions (`RunTask` integration) — Fargate tasks have no maximum execution time and can run for hours. ECS tasks can be launched within the same Step Functions workflow, so you get the benefits of serverless orchestration with the flexibility of long-running containers. For cold start optimization, enable Lambda SnapStart (for Java and .NET runtimes) which reduces startup latency from seconds to under 200ms by restoring from a pre-initialized snapshot.

## Interview Questions

1. **What is the difference between a Security Group and a NACL?**
   Security Groups are stateful firewalls — if you allow inbound traffic, the outbound return traffic is automatically allowed regardless of outbound rules. They operate at the instance/ENI level and support allow rules only (no deny rules). Network ACLs are stateless — each direction of traffic must be explicitly allowed. They operate at the subnet level and support both allow and deny rules, evaluated in numeric order. Security Groups are evaluated as a whole (all rules are evaluated before deciding to allow traffic), while NACLs are evaluated in rule number order (first matching rule wins). Use Security Groups as the primary security mechanism and NACLs as a secondary layer for explicit deny rules (e.g., block specific IP ranges at the subnet level).

2. **What is an S3 Transfer Acceleration?**
   S3 Transfer Acceleration uses AWS edge locations to accelerate uploads over long geographical distances. Instead of uploading directly to the S3 bucket region, files are uploaded to the nearest edge location, which then transfers the data to the S3 bucket over AWS's optimized private network. This is particularly beneficial for global users uploading to a single bucket region, for example, users in Europe uploading to a bucket in us-west-2. Transfer Acceleration costs additional per-GB transfer fees. Before enabling it, use the S3 Transfer Acceleration Speed Comparison tool to verify that it would actually improve performance for your specific use case — for some regions, the standard internet path may already be fast enough.

3. **Explain horizontal vs vertical scaling on AWS.**
   Horizontal scaling (scaling out) adds more instances to distribute the load — an Auto Scaling Group adds EC2 instances behind an ALB as demand increases. This approach provides unlimited theoretical scaling (add more instances), higher availability (failure of one instance doesn't affect others), and zero downtime during scaling events. Vertical scaling (scaling up) increases the size of existing instances — changing from t3.micro (2 vCPU, 1 GB RAM) to t3.large (2 vCPU, 8 GB RAM). Vertical scaling has hard limits (maximum instance size), requires downtime (stop, resize, start), and creates a single point of failure. In AWS, horizontal scaling is strongly preferred for production workloads.

4. **What is an Internet Gateway and when do you need a NAT Gateway?**
   An Internet Gateway (IGW) is a horizontally scaled, redundant VPC component that allows communication between a VPC and the internet. Resources with public IP addresses in subnets with route tables pointing to the IGW can communicate bidirectionally with the internet. A NAT Gateway allows resources in private subnets to initiate outbound connections to the internet (e.g., download patches, access external APIs) while preventing the internet from initiating inbound connections. Use an IGW for public-facing resources (web servers, load balancers); use a NAT Gateway for private resources that need outbound-only internet access (backend services downloading updates, databases accessing external services).

5. **How does AWS Shield protect against DDoS attacks?**
   AWS Shield Standard is included free with all AWS services and protects against common Layer 3 and Layer 4 attacks like SYN floods, UDP floods, and reflection attacks. It usesAWS's global network infrastructure to absorb and mitigate attacks. AWS Shield Advanced ($3,000/month per organization) provides additional protections including enhanced detection and mitigation of larger and more sophisticated DDoS attacks, near real-time visibility into attacks via CloudWatch metrics, DDoS cost protection (AWS will credit your bill for resource scaling costs during an attack), and access to the DDoS Response Team (DRT) for 24/7 support during active attacks. For Layer 7 (application layer) protection, pair Shield Advanced with AWS WAF.

6. **What is the difference between an ALB, NLB, and CLB?**
   Application Load Balancer (ALB) operates at Layer 7 and supports content-based routing — path-based (`/api/*` → Target Group A, `/web/*` → Target Group B), host-based, query string, and HTTP header routing. It supports WebSocket, HTTP/2, and gRPC protocols. Network Load Balancer (NLB) operates at Layer 4 with extreme performance (up to 25 million requests per second) and ultra-low latency (under 100ms). It supports TCP, UDP, and TLS, preserves the client source IP (useful for logging), and supports static/elastic IP addresses. Classic Load Balancer (CLB) is the legacy ELB (deprecated) with limited features and performance. In general, use ALB for HTTP/HTTPS workloads, NLB when you need extreme performance or static IP addresses, and avoid CLB entirely for new deployments.

7. **Explain the AWS Well-Architected Framework.**
   The Well-Architected Framework consists of six pillars: Operational Excellence (run and monitor systems to deliver business value, continuously improve processes and procedures), Security (protect data, systems, and assets through risk assessment, mitigation strategies, and controls), Reliability (ensure a workload performs its intended function correctly and consistently when expected), Performance Efficiency (use IT and computing resources efficiently to meet system requirements), Cost Optimization (run systems to deliver business value at the lowest price point), and Sustainability (minimize environmental impact, maximize energy efficiency). The Well-Architected Tool provides a consistent approach for reviewing architectures against these pillars, generating a report with identified risks and recommended improvements. AWS recommends conducting a Well-Architected Review at least quarterly for critical workloads and after significant architectural changes.

8. **What is the difference between EBS and Instance Store?**
   Amazon EBS (Elastic Block Store) provides persistent block storage that survives instance stops, terminations, and failures — you can detach an EBS volume from one instance and attach it to another. EBS volumes support snapshots (point-in-time backups to S3), encryption, and provisioned IOPS. Maximum volume size is 16 TB. Instance Store provides temporary, ephemeral storage physically attached to the host computer. It offers the highest possible IOPS (physically attached NVMe drives) but data is lost if the instance stops, terminates, or fails. Use EBS for databases, application data, and any state that must persist. Use Instance Store for temporary data, caches, scratch space, and data that can be regenerated. For high-performance databases, combine both: use Instance Store for database logs and temporary files, and EBS for the actual database files.

9. **How do you implement blue-green deployment on AWS?**
   Blue-green deployment involves maintaining two identical environments — currently serving (blue) and new version (green). Deploy the new version to the green environment (second Auto Scaling Group behind a second Target Group). After deployment validation (smoke tests, health checks), update the ALB listener rule to route traffic from the blue target group to the green target group. If the deployment succeeds, keep green and decommission blue. If issues arise, switch traffic back to blue (instant rollback). AWS CodeDeploy automates this process. For Lambda-based applications, use Lambda aliases with weighted routing — gradually shift traffic from the old alias to the new alias in 1% increments, continuously monitoring error rates before increasing the traffic percentage.

10. **What is CloudFormation and how does it differ from Terraform?**
    CloudFormation is AWS's native Infrastructure as Code service that defines AWS resources in YAML or JSON templates. Key advantages: drift detection (detect manual changes to resources), StackSets for deploying across multiple accounts/regions, no state file management (state is managed by AWS), and deep integration with all AWS services (new services support CloudFormation on day one). Terraform is cloud-agnostic — it manages resources across AWS, Azure, GCP, and even non-cloud providers (DNS, SaaS). It uses HCL syntax (more flexible than JSON), supports remote state backends (S3, Terraform Cloud) for collaboration, has a broader provider ecosystem beyond AWS, and offers more advanced logic constructs (count, for_each, ternary, functions). Choose CloudFormation for AWS-only deployments or teams that want simplified state management. Choose Terraform for multi-cloud environments or teams that need advanced infrastructure orchestration features.

## Developer Recommendations

**Use IAM roles over access keys** — Long-lived access keys are one of the top breach vectors in AWS. IAM roles with STS temporary credentials (valid for 15 minutes to 12 hours) eliminate the need to rotate keys, store them securely, or risk leaking them. For EC2, use instance profiles that automatically provide credentials through the instance metadata service (169.254.169.254). For CI/CD, use OIDC federation — GitHub Actions, GitLab CI, and CircleCI can assume IAM roles directly without storing any AWS keys. For local development, use AWS SSO with `aws sso login`, which provides temporary credentials through AWS's identity center. The benefit is that if someone leaks temporary credentials, they expire within hours; if someone leaks an access key, they have indefinite access until the key is manually rotated. The only trade-off is the initial setup complexity of configuring OIDC trust policies or SSO permission sets, but this one-time effort eliminates ongoing key management overhead.

**Tag everything, enforce tagging with SCPs** — Without a comprehensive tagging strategy, cost allocation becomes guesswork, resource identification requires manual searching, and automation scripts cannot target specific resources. Define a mandatory set of tags for every resource: CostCenter (which team/org pays), Environment (production, staging, development), Owner (who to contact), Application (which app uses this), and DataClassification (public, internal, confidential, PII). Enforce mandatory tags using Service Control Policies that deny resource creation when required tags are missing — use `aws:RequestTag` and `aws:ResourceTag` condition keys. Use tag-based IAM policies for fine-grained access control (e.g., developers can only stop EC2 instances tagged Environment=Dev). The cost is the planning effort for tag schema design and the operational friction when someone forgets tags and their CI/CD pipeline fails. The benefit is clarity: within 5 minutes, anyone can determine who owns any resource and what it costs.

**Use S3 Intelligent-Tiering for unpredictable access patterns** — Manually choosing between S3 storage classes for data with unknown access patterns leads to overpaying (choosing STANDARD for rarely-accessed data) or incurring retrieval fees (choosing IA for frequently-accessed data). S3 Intelligent-Tiering monitors access patterns at the object level and automatically moves objects between three access tiers (Frequent, Infrequent, and Archive Instant) based on usage, with no impact on performance or API changes. It charges a small monitoring fee of $0.0025 per 1,000 objects, which is typically far less than the overpayment from choosing the wrong storage class manually. The feature is ideal for data lakes, logs, content repositories, and any use case where access patterns are unpredictable or change over time. For data that never changes (stable access patterns from day one), standard storage class selection may be cheaper since you avoid the monitoring fee.

**Prefer managed services over self-managed — know the trade-off** — Fully managed services like RDS, ElastiCache, and DynamoDB reduce operational burden significantly but typically cost more and offer less control than self-managed alternatives. For example, RDS PostgreSQL costs approximately 2-3x more than running PostgreSQL on an EC2 instance yourself, but it saves 10+ hours per week of operational tasks: patch management, backup management, storage provisioning, failover configuration, and performance tuning. The decision framework should be: use managed services when the operational complexity of running the service yourself outweighs the cost premium. Reserve self-managed solutions for cases where you need specific configurations that managed services don't support (custom plugins, specific database versions, specialized hardware configurations). In practice, start with managed services and only self-manage when you have a specific, justified reason.

**Implement cost-aware development practices** — Developers are the primary drivers of cloud costs, yet most have no visibility into the cost implications of their architectural choices. Implement cost-awareness as a cultural and technical practice. Use Cost Explorer with resource-level tags so every team can see their exact costs. Set AWS Budgets that send alerts directly to the development team's Slack or email when costs exceed thresholds. Implement cost gates in CI/CD — a pipeline can check the estimated monthly cost increase of a deployment and fail if it exceeds 10% of the current baseline. Use `aws-nuke` to automatically clean up ephemeral environments (feature branch deployments, test environments) after they're no longer needed. The trade-off is the engineering time to build these cost controls, but this is typically recovered within weeks from prevented overspend. The most important practice is making cost visible — developers who see the cost of their choices naturally make more cost-effective decisions.

**Design for failure from day one** — Building multi-AZ or multi-region architecture is much harder to retrofit than to design in from the start. Even in development environments, use at least 2 subnets (even if they're in the same AZ) and implement circuit breakers, retries with exponential backoff, and bulkheads (isolated resource pools per workload). Use AWS Fault Injection Simulator (FIS) to regularly test failure modes — FIS can terminate EC2 instances, throttle API calls, inject latency, and disrupt Availability Zones to verify your system's resilience. Every external dependency (database, cache, external API) should have a fallback: cache data when the database is unavailable, degrade gracefully when a downstream service fails, and maintain a static "maintenance mode" page for catastrophic failures. The single most common objection to multi-AZ design is cost (double the infrastructure), but this is not cost optimization — it's deferred risk. The cost of an hour of downtime for a production application almost always exceeds the premium for multi-AZ deployment.

**Use Infrastructure as Code for everything** — Every piece of infrastructure should be defined in code — CloudFormation or Terraform for resources, SSM Parameter Store for configuration, and AppConfig for feature flags and application configuration. The rule is simple: if it can be automated, never configure it manually through the console. Manual configuration changes produce configuration drift — the difference between what's defined in your IaC templates and what's actually running. Drift is the enemy of reliability because it makes environments unreproducible and introduces unknown variables into incident response. Use IaC linting and security scanning tools (cfn-lint, tfsec, checkov) in your CI/CD pipeline to catch security misconfigurations and policy violations before deployment. The upfront cost of writing IaC takes slightly longer than clicking through the console, but the long-term benefit of reproducible, auditable, and version-controlled infrastructure is immeasurable.

**Monitor the right metrics, not everything** — Collecting every available CloudWatch metric creates two problems: high monitoring costs (each metric costs $0.30/month) and signal-to-noise ratio issues (too many alerts desensitize the team). Instead, focus on the Four Golden Signals per service: latency (time to respond to requests), traffic (requests per second), errors (error rate as a percentage of traffic), and saturation (how "full" the service is — CPU, memory, queue depth). Set up composite CloudWatch alarms that combine multiple conditions before alerting — for example, alert only when error rate is elevated AND latency is high simultaneously, reducing false positives. Use CloudWatch Contributor Insights to analyze high-cardinality traffic data (which API keys are causing the most errors, which user agents are slowest). The trade-off is that building focused, meaningful dashboards takes more initial thought than dumping all metrics into CloudWatch, but the result is a monitoring system that actually helps you understand and respond to production issues.
